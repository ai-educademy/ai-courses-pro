# 🔧 機能エンジニアリングに関する質問

経験豊富な ML エンジニアが知っている秘密は次のとおりです。**選択したモデルは、モデルに供給する機能よりもはるかに重要です。** 優れた機能を備えた単純なロジスティック回帰は、ほとんどの場合、貧弱な機能を備えたディープ ニューラル ネットワークに勝ります。面接官が特徴エンジニアリングの質問を好むのはそのためです。面接官は、アルゴリズムだけでなく、機械学習の *データ* 側を理解しているかどうかをテストします。

---

## 🤔 面接官が特徴エンジニアリングを気にする理由

特徴量エンジニアリングは、ドメインの知識、データの直感、エンジニアリング スキルが交わる部分にあります。面接官が「ライドシェアの到着時間予測システムの機能を設計してください」と尋ねると、次のことをテストします。

- データ内にどのような信号が存在するかについて創造的に考えることができますか?
- 生データがどのようにモデル入力に変換されるか理解していますか?
- 漏洩、希薄性、規模などの問題を予測できますか?
- 制作上の制約 (レイテンシー、ストレージ、鮮度) について考えますか?

<Callout>一般的な面接パターン: 面接官はビジネス上の問題について説明し、機能のブレインストーミングを依頼します。まず、利用可能なデータ ソースについて尋ねます。これは、理論だけでなく実現可能性について考えていることを示しています。
</Callout>

## 📦 機能の種類

### 数値的特徴

生の数値はモデルに直接入力できますが、多くの場合、変換によってメリットが得られます。

- **標準化**: 中心から平均 0、スケールから単位分散 (SVM、KNN などの距離ベースのモデルに必須)
- **ログ変換**: 右に偏った分布 (収入、ページビュー) を圧縮します。
- **ビニング**: 連続値を離散バケットに変換します (年齢 → 年齢グループ)

```python
import numpy as np
from sklearn.preprocessing import StandardScaler

# Log transform for skewed feature
df['log_income'] = np.log1p(df['income'])

# Standardisation
scaler = StandardScaler()
df[['age_scaled', 'income_scaled']] = scaler.fit_transform(df[['age', 'income']])
```

### カテゴリ特徴

国、製品カテゴリ、ユーザーセグメントなどの非数値データ。エンコード戦略は重要です:

|方法 |いつ使用するか |長所 |短所 |
|---|---|---|---|
|ワンホットエンコーディング |低カーディナリティ (< 20 カテゴリ) |シンプルで順序の仮定はありません |スパース、高次元 |
|ラベルエンコーディング |順序カテゴリ (低/中/高) |コンパクト |非順序 | に対する誤った順序付けを意味します。
|ターゲットエンコーディング |高いカーディナリティ (都市、郵便番号) |カテゴリとターゲットの関係を把握 |データ漏洩のリスク |
|埋め込み |非常に高いカーディナリティ、深層学習 |密な表現を学習します |ニューラルネットワークが必要 |

<ThinkAboutIt>あなたは推奨モデルを構築していて、その特徴の 1 つが 500,000 の一意の値を持つ `product_id` です。ワンホット エンコーディングでは 500K のスパース列が作成されます。どのようなエンコード戦略を検討しますか?また、トレードオフは何ですか?
</ThinkAboutIt>

### 時間的特徴

時間ベースのデータにはシグナルが豊富に含まれています。適切に抽出できれば、次のようになります。

- **循環エンコーディング**: 時刻、曜日 (周期的な性質をキャプチャするには、sin/cos を使用します)
- **ラグ特徴**: t-1、t-7、t-30 の値 (時系列にとって重要)
- **ローリング統計**: 7 日間の移動平均、30 日間のローリング標準偏差
- **イベントからの経過時間**: 最後の購入からの日数、最後のログインからの時間

```python
# Cyclical encoding for hour of day
df['hour_sin'] = np.sin(2 * np.pi * df['hour'] / 24)
df['hour_cos'] = np.cos(2 * np.pi * df['hour'] / 24)

# Lag and rolling features
df['sales_lag_7'] = df['sales'].shift(7)
df['sales_rolling_mean_7'] = df['sales'].rolling(window=7).mean()
```

### テキスト機能

モデルがテキスト データを使用する必要がある場合:

- **Bag of Words / TF-IDF**: シンプルで解釈しやすく、従来の ML とうまく連携します
- **単語埋め込み**: Word2Vec、GloVe — 意味論的な意味を捉える高密度表現
- **文の埋め込み**: BERT、文-BERT — コンテキスト表現
- **手作り**: 単語数、平均単語長、感情スコア、特定のキーワードの存在

### インタラクション機能

モデルが単独では学習できない可能性のある関係を捕捉する特徴の組み合わせ:

- **機能のクロス**: `city × device_type` (都市部のモバイル ユーザーは地方のデスクトップ ユーザーとは異なる行動をします)
- **比率**: `clicks / impressions` = クリックスルー率
- **違い**: `current_price - avg_price` = 相対価格シグナル

## 🧹 欠落データの処理

欠落したデータは本番環境のいたるところに存在します。あなたのアプローチはあなたの経験レベルを示しています:

**シンプルな戦略:**
- 行を削除します (欠落データがまれでランダムな場合のみ)
- 平均/中央値 (数値) または最頻値 (カテゴリ) を入力します。
- センチネル値 (-1 または "UNKNOWN") を入力します。

**より良い戦略:**
- バイナリ インジケーター フィーチャを作成します: `is_income_missing` (データが欠落しているという *事実* は有益である可能性があります!)
- モデルベースの代入 (KNN インピューター、反復インピューター) を使用します。
- ツリーベースのモデルの場合、多くの実装は欠損値をネイティブに処理します。

```python
# Indicator feature + median imputation
df['is_income_missing'] = df['income'].isna().astype(int)
df['income'] = df['income'].fillna(df['income'].median())
```

<FunFact>有名な Netflix 賞コンテストでは、最も強力な機能の 1 つは、単純に *ユーザーが映画を評価したかどうか* であり、評価自体ではありませんでした。評価が欠落しているパターンにより、評価そのものよりもユーザーの好みが明らかになりました。
</FunFact>

## 🔍 特徴選択方法

機能が多ければ多いほど良いとは限りません。特徴の選択により、過剰適合が軽減され、待ち時間が改善され、モデルが解釈可能になります。

### フィルターメソッド
ターゲットとの統計的相関によって特徴をランク付けします。高速ですが、特徴の相互作用は無視されます。
・相関係数（数値目標）
- 相互情報 (どのような種類の特徴でも機能します)
- カイ二乗検定 (カテゴリ特徴)

### ラッパーメソッド
さまざまな特徴サブセットを使用してモデルをトレーニングします。正確ではありますが、コストがかかります。
- 前方選択: 空から開始し、一度に 1 つずつ最適な機能を追加します
- 逆方向削除: すべての機能から開始し、最も役に立たない機能を一度に削除します。

### 埋め込みメソッド
特徴の選択はモデルのトレーニング プロセスに組み込まれています。
- **L1 正則化** (Lasso): 重要でない特徴の重みを正確にゼロにします。
- **ツリーベースの重要度**: 勾配ブーストされたツリーは特徴重要度スコアを報告します

```python
from sklearn.feature_selection import SelectKBest, mutual_info_classif

# Select top 20 features by mutual information
selector = SelectKBest(mutual_info_classif, k=20)
X_selected = selector.fit_transform(X, y)
```

## 🏭 本番環境における機能エンジニアリング

インタビューレベルの特徴エンジニアリングはノートブックにとどまりません。生産上の考慮事項は次のとおりです。

### フィーチャー ストア

フィーチャー ストアは、フィーチャーを管理、保存、提供するための集中システムです。それは解決します:
- **一貫性**: トレーニングとサービスで同じ機能定義
- **再利用性**: チームは機能を再実装するのではなく共有します。
- **鮮度**: スケジュールされたパイプラインにより機能を最新の状態に保ちます

人気のあるツール: **Feast**、**Tecton**、**Hopsworks**、**AWS SageMaker Feature Store**

### トレーニングとサービスのスキュー

ML における最も危険な本番環境のバグ: トレーニング中とサービング中に特徴量が異なる方法で計算されます。一般的な原因:
- バッチ (トレーニング) とリアルタイム (サービス) で異なるコード パス
- サービス提供パス内の古い特徴値
- 環境間でライブラリのバージョンが異なる

<Callout>面接官が本番環境における機能エンジニアリングについて質問するときは、必ずトレーニングとサービスのスキューについて言及してください。これは、ほとんどの候補者が見落としており、ほとんどの実稼働 ML システムが悩まされている問題です。
</Callout>

## 🔑 重要なポイント

- **特徴はアルゴリズムに優先します** — モデル アーキテクチャよりも特徴エンジニアリングにより多くの時間を投資します
- **エンコーディングをカーディナリティに一致させる**: 低位の場合はワンホット、高位の場合はターゲット エンコーディングまたはエンベディング
- **データ欠損は単なる問題ではなく機能です** - インジケーター変数を作成します
- **漏洩に注意してください** — 機能が真実であるには良すぎると思われる場合は、おそらくその機能が真実である可能性があります。
- **本番環境について考える**: 機能ストア、トレーニングとサービスのスキュー、レイテンシの制約
- **一般的な問題に対するブレーンストーミング機能**を練習します: 推奨事項、不正行為、ETA 予測、検索
