# ⚙️ MLOps और प्रोडक्शन एमएल

एक आंकड़ा आपके इंटरव्यू की तैयारी को दिशा देना चाहिए: **87% एमएल मॉडल कभी प्रोडक्शन तक नहीं पहुंचते।** Jupyter notebook और भरोसेमंद, scalable एमएल सेवा के बीच बहुत बड़ा अंतर है, और कंपनियों को ऐसे इंजीनियरों की सख्त ज़रूरत है जो यह अंतर पाट सकें। MLOps इंटरव्यू सवाल जांचते हैं कि क्या आप मॉडल को "मेरी मशीन पर चलता है" से "शनिवार सुबह 3 बजे भी लाखों उपयोगकर्ताओं के लिए भरोसेमंद चलता है" तक ले जा सकते हैं।

## 🧭 MLOps सच में क्या कवर करता है

MLOps वे practices हैं जो DevOps अनुशासन को मशीन लर्निंग में लाते हैं। यह पूरे एमएल lifecycle में फैला होता है:

```
Data → Feature Engineering → Training → Evaluation → Deployment → Monitoring → Retraining
  ↑                                                                              |
  └──────────────────────────── Feedback Loop ────────────────────────────────────┘
```

मुख्य स्तंभों में शामिल हैं:
- **एमएल के लिए CI/CD**: केवल code नहीं, data, features और models की automated testing
- **Experiment tracking**: hyperparameters, metrics और artefacts का व्यवस्थित रिकॉर्ड
- **Model versioning**: कौन-सा model version किस traffic को serve कर रहा है, यह track करना
- **Model serving**: predictions को उपयोगकर्ताओं तक भरोसेमंद और तेज़ पहुंचाना
- **Monitoring**: production में models कब degrade होते हैं, यह पहचानना

<Callout>
MLOps और पारंपरिक DevOps में सबसे बड़ा अंतर: software में code changes चीज़ें तोड़ते हैं। एमएल में *data* changes चीज़ें तोड़ते हैं, अक्सर चुपचाप, बिना किसी error logs के।
</Callout>

## 🚀 मॉडल सर्विंग पैटर्न

आप predictions कैसे serve करते हैं, यह आपकी latency requirements, scale और predictions कितनी बार बदलनी चाहिए, इस पर निर्भर करता है।

### Batch Inference

Schedule पर predictions पहले से compute करें (hourly, daily) और lookup के लिए store करें।

**सबसे अच्छा किसके लिए**: email recommendations, daily risk scores, weekly reports

```
Schedule → Load data → Run model → Write predictions to DB → Serve from DB
```

**लाभ**: simple infrastructure, बड़े models इस्तेमाल हो सकते हैं, cost-effective
**कमी**: predictions stale हो सकती हैं, real-time context पर प्रतिक्रिया नहीं दे सकता

### Real-Time Inference (Model-as-a-Service)

मॉडल API के पीछे चलता है। हर request prediction trigger करता है।

**सबसे अच्छा किसके लिए**: search ranking, fraud detection, chatbots

```
User request → API Gateway → Feature lookup → Model inference → Response
```

**लाभ**: fresh predictions, real-time context इस्तेमाल हो सकता है
**कमी**: latency-sensitive, model size और serving infrastructure optimise करने पड़ते हैं

### Embedded Model

मॉडल सीधे application या device में bundle होता है।

**सबसे अच्छा किसके लिए**: mobile apps, IoT devices, edge computing

**लाभ**: network latency नहीं, offline काम करता है
**कमी**: update करना कठिन, device resources से सीमित

## 📊 Experiment Tracking

Tracking के बिना एमएल experiments चलाना lab notebook के बिना science करने जैसा है। आपको रिकॉर्ड करना चाहिए:

- **Hyperparameters**: learning rate, batch size, architecture choices
- **Metrics**: training loss, हर epoch पर validation metrics
- **Artefacts**: model checkpoints, feature importance plots, confusion matrices
- **Environment**: library versions, इस्तेमाल hardware, random seeds

### लोकप्रिय tools

| Tool | Strengths | Deployment |
|---|---|---|
| **MLflow** | Open-source, model registry, wide adoption | Self-hosted or managed |
| **Weights & Biases (W&B)** | Beautiful UI, collaboration features, sweeps | Cloud-hosted |
| **Neptune.ai** | Lightweight, good for teams | Cloud-hosted |
| **TensorBoard** | Free, tightly integrated with TensorFlow | Local or embedded |

```python
import mlflow

mlflow.set_experiment("fraud-detection-v2")

with mlflow.start_run():
    mlflow.log_param("learning_rate", 0.001)
    mlflow.log_param("n_estimators", 500)

    model = train_model(X_train, y_train)
    metrics = evaluate_model(model, X_test, y_test)

    mlflow.log_metric("auc_roc", metrics["auc_roc"])
    mlflow.log_metric("precision", metrics["precision"])
    mlflow.sklearn.log_model(model, "model")
```

## 🔍 प्रोडक्शन में एमएल मॉनिटरिंग

पारंपरिक software monitoring errors और latency track करती है। एमएल monitoring एक अहम परत जोड़ती है: **क्या मॉडल अभी भी अच्छी predictions कर रहा है?**

### Drift के प्रकार

**Data drift** (covariate shift): input features का distribution बदलता है। उदाहरण: pre-pandemic data पर trained e-commerce model को home office equipment searches में उछाल दिखता है।

**Concept drift**: features और target का संबंध बदलता है। उदाहरण: recession के दौरान credit scoring model में "employment status" feature का अर्थ बदल जाता है।

**Prediction drift**: model outputs का distribution बदलता है, भले inputs समान दिखें।

### क्या monitor करें

| Signal | कैसे पहचानें | Action |
|---|---|---|
| Input feature distributions | Statistical tests (KS test, PSI) | Data pipeline जांचें |
| Prediction distribution | समय के साथ mean, variance, percentiles track करें | Baseline period से compare करें |
| Model performance (जब labels उपलब्ध हों) | ground truth के विरुद्ध accuracy, F1, आदि track करें | threshold से नीचे हो तो retraining trigger करें |
| Latency | P50, P95, P99 response times | Infrastructure scale करें या model optimise करें |
| Data quality | Null rates, schema violations, volume anomalies | Data engineering team को alert करें |

```python
from scipy.stats import ks_2samp

# Kolmogorov-Smirnov test for distribution shift
def detect_drift(reference_data, current_data, threshold=0.05):
    statistic, p_value = ks_2samp(reference_data, current_data)
    return p_value < threshold  # True = drift detected
```

<FunFact>
जब Zillow के "Zestimate" home-pricing model ने 2021 के असामान्य housing market में concept drift झेला, तो कंपनी ने अपने ही model की predictions पर आधारित home purchases में $500 million से अधिक गंवाए, और अंततः अपना home-flipping business बंद कर दिया।
</FunFact>

## 🔄 मशीन लर्निंग के लिए CI/CD

एमएल CI/CD code testing से आगे जाता है। आपको data, features और models भी validate करने होते हैं।

### एमएल Testing Pyramid

```
              ┌──────────────┐
              │  Model Tests  │  ← Does the model meet quality thresholds?
             ┌┴──────────────┴┐
             │  Feature Tests  │  ← Are features computed correctly?
            ┌┴────────────────┴┐
            │  Data Validation  │  ← Is the data schema correct? Missing values?
           ┌┴──────────────────┴┐
           │    Unit Tests       │  ← Does the code work?
           └────────────────────┘
```

**Data validation**: schema, null rates, value ranges, row counts जांचें
**Feature tests**: verify करें कि feature transformations expected outputs देती हैं
**Model tests**: deployment से पहले सुनिश्चित करें कि trained model minimum quality thresholds से ऊपर है

## 💰 इन्फ़्रास्ट्रक्चर विचार

प्रोडक्शन एमएल की वास्तविक लागत होती है। इंटरव्यूअर देखना चाहते हैं कि आपको लागत की समझ है:

### GPU प्रबंधन

- **Training**: cost savings के लिए spot/preemptible instances इस्तेमाल करें (checkpointing के साथ!)
- **Serving**: GPU requirements घटाने के लिए model distillation या quantisation पर विचार करें
- **Autoscaling**: GPU instances को peak capacity नहीं, traffic patterns के आधार पर scale करें

### लागत optimisation रणनीतियां

- **Model compression**: pruning, quantisation, knowledge distillation
- **Caching**: repeated inputs के लिए predictions cache करें
- **Tiered serving**: अधिकांश requests के लिए सस्ता model, expensive model केवल confidence कम होने पर
- **Right-sizing**: जब fine-tuned 7B model quality का 95% पा लेता है, तो 175B parameter model serve न करें

```
Cost per prediction ≈ (GPU cost per hour) / (predictions per hour)

Example:
- GPU instance: $3/hour
- Model throughput: 1,000 predictions/second
- Cost per prediction: $3 / 3,600,000 ≈ $0.0000008
```

## 🏗️ आम इंटरव्यू सवाल

इन सवालों पर चर्चा के लिए तैयार रहें:

1. "नया model production में कैसे deploy करेंगे, पूरा flow बताएं"। training से canary deployment और full rollout तक पूरी pipeline बताएं
2. "Production में degrade हो रहे model को कैसे संभालेंगे?" monitoring, root cause analysis, rollback, retraining
3. "Model retraining और model updating में क्या अंतर है?" नए data पर full retraining बनाम incremental/online learning
4. "एमएल experiments में reproducibility कैसे सुनिश्चित करते हैं?" code, data और config के लिए version control; fixed seeds; containerisation
5. "अपना ideal एमएल platform बताएं"। feature store, experiment tracker, model registry, serving infrastructure, monitoring dashboard

<Callout>
MLOps इंटरव्यू सवालों के जवाब में technical decisions को business impact से हमेशा जोड़ें। "हम canary deployments इसलिए इस्तेमाल करते हैं क्योंकि खराब model rollback करने में lost revenue में X लागत आती है" सिर्फ़ technical setup बताने से अधिक प्रभावी है।
</Callout>

## 🔑 मुख्य बातें

- **MLOps model development और production के बीच का अंतर पाटता है**। यह आज सबसे अधिक मांग वाला एमएल कौशल है
- **Serving patterns समझदारी से चुनें**: cost के लिए batch, freshness के लिए real-time, edge के लिए embedded
- **Latency से आगे monitor करें**: data drift, concept drift और model degradation silent killers हैं
- **हर experiment track करें**: parameters, metrics, artefacts और environment
- **एमएल pipeline test करें**, सिर्फ़ code नहीं: data validation, feature tests और model quality gates
- **लागत सोचें**: model compression, caching और tiered serving infrastructure bills घटाते हैं
