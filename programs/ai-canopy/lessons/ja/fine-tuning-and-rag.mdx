# 微調整と RAG - 企業がデータに合わせて AI をカスタマイズする方法

汎用 LLM は世界についてはよく知っていますが、会社の内部文書、独自のデータ、ドメイン固有の用語については何も知りません。このレッスンでは、そのギャップを埋めるための 2 つの主なアプローチ、**微調整** と **検索拡張生成 (RAG)** について説明します。

## 汎用モデルでは不十分な理由

会社固有の返品ポリシー、社内製品コード、または医療プロトコルに関する顧客の質問に答えるように GPT-4 に依頼することを想像してください。それはできません。その情報はトレーニング データに含まれていません。

企業には、大規模モデルの**一般的なインテリジェンス**と、自社のドメインの**特有の知識**を組み合わせたAIが必要です。そこに到達するには 2 つの道があり、正しい方を選択することが非常に重要です。

<Callout>よくある誤解は、単に LLM に「データをアップロード」できるということです。実際には、モデルをカスタマイズするには、重みを再トレーニングする (微調整) か、取得パイプライン (RAG) を構築するかのいずれかが必要です。どちらも慎重な計画が必要なエンジニアリング作業です。
</Callout>

## 微調整: モデルに新しいトリックを教える

微調整では、事前トレーニングされたモデルを取得し、独自のデータセットでトレーニングを続けます。モデルの重みは、ドメインの言語、スタイル、知識を反映するように更新されます。

**微調整が必要な場合:**
- モデルが特定のトーンや書き方を一貫して採用する必要があります。
- ドメインには、基本モデルではうまく処理できない特殊な用語が含まれています。
- より高速な推論が必要です (知識は取得されるのではなく「焼き付けられる」)。

**プロセス:**
1. ドメイン内に高品質のサンプルのデータセット (通常は数百から数千の入出力ペア) を準備します。
2. 基本モデル (Llama 3、Mistral など) を選択します。
3. 致命的な忘れを避けるために、低い学習率で数エポックトレーニングします。
4. 保持されたテストデータを評価します。

<FunFact>ブルームバーグは、3,630 億トークンの金融データを微調整して BloombergGPT を構築しました。結果として得られたモデルは、決算報告のセンチメント分析や SEC 提出書類における指定事業体認識などの財務 NLP タスクにおいて、汎用モデルを大幅に上回りました。
</FunFact>

## LoRA と QLoRA: 効率的な微調整

従来の微調整では**すべて**のモデルパラメータが更新されるため、膨大なGPUメモリが必要になります。 700 億のパラメーター モデルには、勾配ストレージだけで数百ギガバイトが必要です。

**LoRA (Low-Rank Adaptation)** はこれをエレガントに解決します。
- すべての重みを更新する代わりに、LoRA は元のモデルをフリーズし、小さな **トレーニング可能なアダプター行列** を各レイヤーに追加します。
- これらのアダプターは通常、0.1 ～ 1% の追加パラメーターのみを追加します。
- その結果、わずかなコストでほぼ同等のパフォーマンスが得られます。

**QLoRA** はさらに、フリーズしたモデルを 4 ビット精度に量子化し、メモリ要件を大幅に削減します。 48GB の VRAM を備えた単一のコンシューマ GPU で 70B パラメータ モデルを微調整できます。

## RAG: 検索拡張生成

RAG はまったく異なるアプローチを採用しています。モデルを変更する代わりに、**クエリ時に外部ドキュメントへのアクセスを許可します**。

**RAG の仕組み:**
1. **インデックス** - ドキュメントはチャンクに分割され、埋め込みモデルを使用して数値ベクトル (埋め込み) に変換されます。
2. **保存** - これらのベクトルは、高速な類似性検索のためにベクトル データベースに保存されます。
3. **取得** - ユーザーが質問すると、クエリも埋め込まれ、最も関連性の高いドキュメント チャンクが取得されます。
4. **生成** - 取得されたチャンクがコンテキストとしてプロンプトに挿入され、LLM は実際のドキュメントに基づいた回答を生成します。

**RAG を使用する場合:**
- ナレッジ ベースは頻繁に変更されます (新しいドキュメント、ポリシーの更新)。
- 出典の引用とトレーサビリティが必要です。
- 微調整にかかるコストと複雑さを避けたい。
- 事実の正確さが重要であり、幻覚は最小限に抑える必要があります。

<ThinkAboutIt>RAG はクエリ時にモデルに関連ドキュメントを提供しますが、最終的な答えはモデルによって生成されます。モデルの応答が、取得した文書の内容を超えた幻覚ではなく、実際に文書の内容を反映していることをどのように検証できますか?
</ThinkAboutIt>

## ベクトル データベース

ベクトル データベースは、高次元エンベディングの保存と検索を目的として構築されています。

|データベース |タイプ |主な機能 |
|----------|------|---------------|
| **松ぼっくり** |マネージドクラウド |完全にホストされたシンプルな API |
| **ウィアビエイト** |オープンソース |ハイブリッド検索 (ベクトル + キーワード) |
| **pgvector** | PostgreSQL 拡張機能 |既存の Postgres データベースを使用する |
| **クロマ** |オープンソース |軽量でプロトタイピングに最適 |
| **クドラント** |オープンソース |高性能、Rust ベース |

ベクター データベースの選択は、規模、既存のインフラストラクチャ、およびマネージド ホスティングが必要かセルフホステッド ソリューションを好むかによって異なります。

## 微調整する場合と RAG を使用する場合

|考察 |微調整 |ラグ |
|---------------|-------------|-----|
| **データの鮮度** |静的 (再トレーニングして更新) |動的 (いつでもドキュメントを更新) |
| **コスト** |より高い前払い (トレーニング) |前払いおよび継続的な取得コストの削減 |
| **トレーサビリティ** |低い (暗黙的な知識) |高 (ソース文書を引用できる) |
| **スタイル/行動** |トーンとフォーマットに優れています |即時指示に限定 |
| **幻覚のリスク** |中程度 |下部 (文書に基づいて) |

**最良の実稼働システムは、多くの場合、両方を組み合わせています。** ドメイン固有の言語とスタイルに合わせて微調整し、RAG を使用してクエリ時に最新の事実のコンテンツを挿入します。

<FunFact>英国の国民保健サービスは、LLM を臨床ガイドラインや薬物相互作用データベースに接続する RAG システムを試験的に導入しました。医師は自然言語で質問し、最新の NICE ガイドラインに基づいた、参照ページ付きの回答を受け取ることができます。
</FunFact>

## 実際の例

- **カスタマー サポート** - 小売業者は、トーンについて過去のサポート チケットに基づいてモデルを微調整し、製品カタログと返品ポリシーに対して RAG を使用して事実に基づく回答を求めます。
- **法的文書分析** - 法律事務所は RAG を使用して何百万件もの訴訟文書を検索し、LLM が新しい事件ごとに関連する判例を要約します。
- **医療 Q&A** - 医療提供者は査読済みの文献に対して RAG を使用するため、臨床医は自然言語で質問し、引用付きで証拠に基づいた回答を得ることができます。

## 本番 RAG パイプラインの構築

堅牢な RAG システムには、ベクトル データベースと LLM だけでは必要ありません。主な考慮事項は次のとおりです。

- **チャンク戦略** - ドキュメントをどのように分割するかは非常に重要です。大きすぎるコンテンツや無関係なコンテンツは信号を弱めます。小さすぎるとコンテキストが失われます。多くの場合、10 ～ 20% の重複チャンクがうまく機能します。
- **再ランキング** - 最初のベクトル取得後、クロスエンコーダの再ランキング機能により結果を関連性によって並べ替えることができ、回答の品質が大幅に向上します。
- **評価** - 検索の精度 (正しいチャンクが見つかりましたか?) と生成の忠実度 (答えはチャンクを反映したか?) を個別に測定します。
- **ハイブリッド検索** - ベクトルの類似性と従来のキーワード検索 (BM25) を組み合わせることで、セマンティック検索だけでは正確な用語や頭字語を見逃すケースを検出します。
