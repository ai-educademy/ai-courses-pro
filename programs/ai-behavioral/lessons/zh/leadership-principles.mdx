# 领导原则——每个行为问题背后隐藏的准则

在亚马逊，循环中的每一位面试官都被分配了一个特定的领导原则来进行调查。在谷歌，面试官会根据“Google性”和领导力信号对你进行评分，并使用结构化的评分标准。在 Meta，他们评估您“快速行动”和“建立社会价值”的能力。这些并不是模糊的文化氛围——它们是**具有明确的提高标准的期望的评分标准**，你的故事必须准确地反映它们。

## 为什么领导原则很重要

领导原则是评估您整个面试的镜头。两名候选人可以讲述相同的故事——其中一位获得“强力聘用”，另一位获得“不聘用”——完全基于他们的故事表面的**信号**。

<Callout>你不会被问“你是一个好人吗？”你会被问到“你能提供证据证明你在压力下证明了这一具体原则吗？”将每个原则视为需要具体故事的复选框。
</Callout>

## 亚马逊 16 项领导力原则 — 深入探究

亚马逊的原则是最明确、最广泛研究的。每家科技公司都会借鉴这些知识，因此掌握这些知识可以让你做好广泛的准备。

|原理|他们真正评估的是什么？您可能会听到的问题 |
|----------|------------------------|------------------------|
| **客户痴迷** |您是否从客户出发并逆向工作？ | “告诉我一次您将客户需求置于内部便利之上的经历。” |
| **所有权** |您是否代表整个公司而不仅仅是您的团队行事？ | “描述一次你修复了工作范围之外的问题的经历。” |
| **发明和简化** |你能找到复杂问题的简单解决方案吗？ | “告诉我一次你简化复杂流程的经历。” |
| **深入了解** |当指标不同时，您是否会密切关注细节并进行审核？ | “举个例子，说明你何时发现了别人错过的问题。” |
| **不同意并承诺** |一旦做出决定，你能挑战并完全承诺吗？ | “告诉我一次你不同意团队决定的经历。” |
| **交付成果** |尽管遇到挫折，您是否仍能按时交付？ | “描述一下你在紧迫的期限内交付的一次时间。” |

<FunFact>亚马逊面试官接受过培训，可以根据原则至少提出两个后续问题。如果你最初的故事很肤浅，后续的故事就会揭露它。准备深度——而不仅仅是广度——是“雇佣”和“倾向”的区别所在。
</FunFact>

## Google 的“Googleyness”和领导力信号

谷歌没有像亚马逊那样发布正式列表，但他们的面试标题评估了四个领域：**一般认知能力**、**角色相关知识**、**领导力**和**Google性**。最后两个是行为方面的。

**Google 的领导力**意味着：
- 当出现歧义时介入领导，即使没有头衔
- 帮助他人成功，而不仅仅是自己
- 尽管存在不确定性，但仍能应对复杂性并取得进展

**谷歌性**意味着：
- 在模糊性中蓬勃发展，将结构带入混乱
- 以尊重和谦虚的态度对待同事
- 即使没有人在场，也能做正确的事

<Callout>谷歌明确重视**新兴领导力**——领导是因为情况需要，而不是因为你的头衔授予它。你的故事应该展示你的进步，而不是被任命。
</Callout>

## 在没有管理头衔的情况下展现领导力

这是候选人最常见的担忧：“我从来没有管理过任何人——我如何表现出领导力？”

面试中的领导力是关于**影响力、主动性和影响力**，而不是人数。

- **影响力**：“我提出了一个新的测试策略，并通过运行试点和共享数据说服三个团队采用它。”
- **倡议**：“我注意到我们的待命操作手册已经过时。我创建了一个工作组，重写了它们，并将事件响应时间缩短了 40%。”
- **影响**：“我指导了两名初级工程师完成他们的第一个系统设计。两人现在都独立领导功能。”

<ThinkAboutIt>回想一下您上次改变团队工作方式的时间——您改进的流程、您引入的工具或您提出的标准。这就是你的领导力故事，即使你的头衔是“软件工程师”。
</ThinkAboutIt>

## 关键原则的 STAR 答案示例

### 客户痴迷

> **情况：** 我们的忠诚度应用程序具有 4 星级评级，但客户对礼品卡余额检查的投诉激增 — 每周 200 张票。
>
> **任务：** 作为忠诚度团队的技术主管，我需要诊断为什么尽管该功能在技术上有效，但客户仍感到沮丧。
>
> **行动：** 我自己提取了客户支持记录，发现由于同步调用旧主机，余额检查花了 8 秒。我提出了一个异步缓存层，在一周内构建了概念验证，并提出了显示预计门票减少的业务案例。然后，我领导了实施工作，与缓存基础设施的平台团队进行协调。
>
> **结果：** 余额检查响应时间从 8 秒下降到 400 毫秒。该类别的支持请求在一个月内下降了 85%。该方法被复制用于其他三个遗留集成。

### 不同意并承诺

> **情况：** 我的团队正在评估我们的新 API 网关是采用 GraphQL 还是继续使用 REST。我非常喜欢基于前端开发人员经验数据的 GraphQL。
>
> **任务：** 我需要展示我的案例，但最终支持团队做出的任何决定。
>
> **行动：** 我准备了一份包含基准、开发人员体验调查和迁移成本估算的比较文档。在架构审查期间，我清楚地呈现了数据。由于现有的生态系统和较低的培训成本，团队选择了 REST。尽管我不同意，但我完全承诺 - 我领导了 REST API 设计，编写了风格指南，并且从未在私下谈话中破坏决定。
>
> **结果：** REST API 按时交付，前端团队适应良好。六个月后，当我们重新审视新产品的 API 策略时，我的原始数据帮助我们有针对性地采用 GraphQL，使其更有意义。我通过完全投入而建立的信任让我的意见在第二次变得更加重要。

## 准备你的故事矩阵

最有效的准备技术是构建**原则到故事矩阵**。创建一个电子表格，其中原则为行，您的故事为列。

1. 列出目标公司的原则（如果没有公布原则，则列出五项核心能力）
2. 写下 8-10 个职业生涯中的精彩明星故事
3. 将每个故事映射到它可以展示的两个或三个原则
4. 找出差距——任何没有故事的原则都需要准备一个新的原则
5. 从每个映射原则的角度排练每个故事

## 常见陷阱

- **原则填充**：尝试在一个答案中触及五个原则。选择一个，钉住它，然后让后续行动揭示深度。
- **通用故事**：“我通过做好工作表现出主人翁精神”不是主人翁精神 - 这是最低限度的。展示你如何“超越”你的角色。
- **忽略负面因素**：像“有主心骨；不同意并承诺”这样的原则需要表现出真正的紧张感。没有冲突的经过净化的故事是没有说服力的。
- **忘记“承诺”部分**：许多候选人讲述了巨大的分歧故事，但忘记表明他们完全致力于最终决定。

<ThinkAboutIt>查看您的目标角色的职位描述。哪三项领导原则最有可能在该级别得到评估？你们每个人都有无懈可击的故事吗？
</ThinkAboutIt>

## 要点

- **领导原则是评分标准**，而不是励志海报。将它们视为清单。
- **构建故事矩阵** 将 8-10 个故事映射到所有相关原则，并填补每个空白。
- **领导力是影响力，而不是权威。** 您不需要管理头衔来展示领导力。
- **深度胜过广度。** 为每个故事准备两到三个后续问题。
- **在不同公司之间调整你的矩阵**——基本主题非常一致。

获得录用通知的候选人并不是那些拥有最令人印象深刻的职业生涯的人。他们能够通过与面试官评分精确对应的故事来“证明”自己的影响力。
