# Debuggen unter Druck

Eine besondere Art von Stress entsteht durch das Debuggen von Code, während jemand Sie beobachtet und ein Timer herunterzählt. Ihre Handflächen werden schwitzig, Ihr Kopf wird leer und plötzlich können Sie sich nicht mehr daran erinnern, wie eine for-Schleife funktioniert. Jeder Ingenieur war dort. Der Unterschied zwischen Kandidaten, die scheitern, und solchen, die glänzen, liegt nicht im bloßen Talent, sondern in einem systematischen Prozess, der auch dann funktioniert, wenn Ihr Gehirn in Panik geraten möchte. Diese Lektion vermittelt Ihnen diesen Prozess.

## Das RIIFV-Debugging-Framework

Wenn Ihnen in einem Vorstellungsgespräch fehlerhafter Code ausgehändigt wird, widerstehen Sie dem Drang, sofort mit der Suche nach dem Fehler zu beginnen. Befolgen Sie stattdessen diesen fünfstufigen Rahmen:

### R – Reproduzieren

Bestätigen Sie, dass der Fehler vorliegt, und verstehen Sie seine Symptome.

- Welches Verhalten ist zu erwarten?
- Wie ist das tatsächliche Verhalten?
- Unter welchen Eingaben tritt der Fehler auf?

```python
# You're told this function should return the second largest element
def second_largest(nums):
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second:
            second = num
    return second

# Step 1: Reproduce with test cases
print(second_largest([3, 1, 4, 1, 5]))  # Expected: 4, Got: 4 ✓
print(second_largest([5, 5, 5]))         # Expected: 5, Got: -inf ✗ — BUG!
print(second_largest([1]))               # Expected: None?, Got: -inf — Edge case
```

### I – Isolieren

Grenzen Sie ein, wo der Käfer lebt. Nutzen Sie das Prinzip „Teile und herrsche“:

- Liegt der Fehler in der Eingabeanalyse, der Logik oder der Ausgabe?
- Welche bestimmte Zeile oder welcher Block führt zu dem falschen Ergebnis?
- Können Sie es auf einen minimal fehlerhaften Testfall eingrenzen?

### I – Identifizieren

Bestimmen Sie nach der Isolierung die Grundursache – nicht nur das Symptom:

- **Symptom**: Gibt `-inf` für `[5, 5, 5]` zurück
- **Grundursache**: Die Bedingung `elif num > second` behandelt keine Duplikate. Wenn alle Elemente gleich sind, ist `num > first` nur einmal wahr und `num > second` ist für die verbleibenden gleichen Elemente niemals wahr.

### F – Fix

Wenden Sie den minimalen Fix an, der die Grundursache behebt, ohne neue Fehler einzuführen:

```python
def second_largest(nums):
    if len(nums) < 2:
        return None
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second and num != first:  # Handle case: distinct second
            second = num
    return second if second != float('-inf') else first  # All same → return that value
```

<ThinkAboutIt>Warten Sie – sollte `second_largest([5, 5, 5])` 5 oder Keine zurückgeben? Das ist zweideutig und in einem echten Vorstellungsgespräch sollten Sie dem Interviewer genau diese Art von Frage stellen. Die Klärung von Anforderungen gehört zum Debugging.</ThinkAboutIt>

### V – Überprüfen

Bestätigen Sie, dass die Fehlerbehebung in allen Fällen funktioniert – dem ursprünglichen Fehlerfall, Randfällen und zuvor bestandenen Fällen:

```python
assert second_largest([3, 1, 4, 1, 5]) == 4    # Normal case
assert second_largest([5, 5, 5]) == 5            # Duplicates
assert second_largest([1, 2]) == 1               # Minimum valid input
assert second_largest([1]) is None               # Too few elements
assert second_largest([-1, -2, -3]) == -2        # Negative numbers
```

<Callout>Führen Sie Ihre ursprünglichen Testfälle immer erneut aus, nachdem Sie einen Fehler behoben haben. Es kommt überraschend häufig vor, dass ein Fehler behoben und gleichzeitig ein anderer eingeführt wird. Der Schritt „Überprüfen“ fängt Regressionen auf, die Sie das Vorstellungsgespräch kosten würden.</Callout>

## Gängige Formate für Debugging-Interviews

### Format 1: „Hier ist fehlerhafter Code – beheben“

Sie erhalten eine Funktion mit 1-3 Fehlern. RIIFV anwenden:
- Lesen Sie den Code und verstehen Sie die Absicht
- Führen Sie mentale Testfälle durch, um Fehler zu finden
- Beheben Sie jeden Fehler und erläutern Sie Ihre Argumentation

### Format 2: „Dieses System ist kaputt – diagnostizieren Sie es“

Ihnen wird ein Szenario angezeigt: „Benutzer berichten, dass auf der Checkout-Seite manchmal der falsche Preis angezeigt wird.“ Sie müssen:
- Stellen Sie klärende Fragen („Manchmal? Ist es zufällig oder folgt es einem Muster?“)
- Hypothesen bilden („Könnte ein Caching-Problem, eine Rennbedingung oder ein Fehler bei der Währungsumrechnung sein“)
- Schlagen Sie Untersuchungsschritte in der Reihenfolge ihrer Priorität vor

### Format 3: „Dieses Live-System debuggen“ (Paar-Debugging)

Sie und der Interviewer debuggen gemeinsam. Sie können die Rolle eines Teamkollegen oder eines Systems spielen:
- Verbalisieren Sie Ihren Denkprozess
- Schlagen Sie vor, was Sie zuerst überprüfen würden und warum
- Interpretieren Sie die von ihnen bereitgestellten Protokolle und Metriken

## Beim Debuggen laut denken

Der größte Unterschied zwischen dem Debuggen allein und dem Debuggen in einem Interview besteht darin, dass Sie erzählen müssen. So machen Sie es, ohne dass es sich gezwungen anfühlt:

**Erläutern Sie Ihre Beobachtungen**:
„Ich sehe, dass die Funktion eine Liste akzeptiert und die zweitgrößte zurückgeben sollte. Lassen Sie mich dies anhand eines einfachen Beispiels nachvollziehen …“

**Hypothesen bilden**:
„Mein erster Gedanke ist, dass Randfälle möglicherweise nicht wie doppelte Werte behandelt werden. Lassen Sie mich mit [5, 5, 5] testen ...“

**Erläutern Sie Ihre Argumentation**:
„Die Bedingung `num > second` ist niemals wahr, wenn alle Werte gleich sind, weil `first` bereits 5 ist und die verbleibenden 5 nicht größer als `second` sind, was auch `-inf` ist ... Moment, eigentlich ist `5 > -inf` wahr, also wird Sekunde zu 5 beim zweiten Element ... Hmm, lassen Sie mich das genauer verfolgen.“

**Gib zu, wenn du falsch liegst**:
„Eigentlich war meine ursprüngliche Hypothese falsch. Lassen Sie mich das noch einmal nachvollziehen …“

<FunFact>Untersuchungen des Psychologen Gary Klein ergaben, dass erfahrene Debugger Probleme bis zu zehnmal schneller lösen als Anfänger, und zwar nicht, weil sie schlauer sind, sondern weil sie Muster aus früheren Erfahrungen erkennen. Aus diesem Grund ist das Üben mit verschiedenen Fehlertypen wichtiger als reine Intelligenz.</FunFact>

## Strategischer Einsatz von Print-Statements

In einem Coding-Interview sind print-Anweisungen Ihr Debugger. Nutzen Sie sie strategisch:

```python
def merge_sorted_lists(list1, list2):
    result = []
    i = j = 0
    while i < len(list1) and j < len(list2):
        print(f"Comparing list1[{i}]={list1[i]} with list2[{j}]={list2[j]}")
        if list1[i] <= list2[j]:
            result.append(list1[i])
            i += 1
        else:
            result.append(list2[j])
            j += 1
        print(f"Result so far: {result}")

    # Don't forget: add remaining elements
    result.extend(list1[i:])
    result.extend(list2[j:])
    print(f"Final result: {result}")
    return result
```

**Tipps für effektives Drucken-Debugging**:
- Drucken an Entscheidungspunkten (vor if/else, innerhalb von Schleifen)
- Fügen Sie Variablennamen und Indizes in die Ausgabe ein
- Drucken Sie vor und nach der vermuteten Fehlerstelle
- Entfernen Sie Ausdrucke oder kommentieren Sie sie aus, bevor Sie Ihre endgültige Lösung einreichen

## Debuggen verteilter Systeme

Bei Vorstellungsgesprächen auf höherer Ebene werden Sie möglicherweise zum Debuggen verteilter Systeme gefragt:

### Das Debugging-Toolkit

| Werkzeug/Technik | Was es verrät |
|---|---|
| **Protokolle** (strukturiert, mit Korrelations-IDs) | Ablauf, Fehlerdetails |
| **Metriken** (Latenz, Fehlerrate, Durchsatz) | Trends und Anomalien |
| **Traces** (verteilte Ablaufverfolgung) | Anforderungsfluss über Dienste hinweg |
| **Gesundheitschecks** | Welche Komponenten werden abgebaut |

### Systematischer Ansatz

1. **Überprüfen Sie die Metrik-Dashboards** – handelt es sich um einen Anstieg oder eine allmähliche Verschlechterung?
2. **Den Umfang eingrenzen** – welcher Dienst, Endpunkt oder welche Region ist betroffen?
3. **Überprüfen Sie die letzten Bereitstellungen** – „Was hat sich geändert?“ ist die Frage mit dem höchsten Signal
4. **Follow the Trace** – Verwenden Sie Korrelations-IDs, um eine fehlgeschlagene Anfrage dienstübergreifend zu verfolgen
5. **Abhängigkeiten prüfen** – ist ein Downstream-Dienst (Datenbank, Cache, Drittanbieter-API) die Ursache?

```
User reports slow checkout
→ Metrics show p99 latency spike at 14:30
→ Correlated with deployment of payment-service v2.3.1
→ Traces show payment-service waiting 10s on database query
→ Database query plan changed due to missing index after schema migration
→ Root cause: migration in v2.3.1 dropped an index
→ Fix: recreate index, add migration test
```

## Zeitmanagement während Debugging-Runden

Eine typische Debugging-Runde dauert 30–45 Minuten. Planen Sie Ihre Zeit ein:

| Phase | Zeit | Aktivität |
|---|---|---|
| **Verstehen** | 5 Minuten | Lesen Sie den Code, klären Sie das Problem, identifizieren Sie erwartetes und tatsächliches Verhalten |
| **Reproduzieren** | 5 Minuten | Testfälle erstellen, die den Fehler auslösen |
| **Isolieren & Identifizieren** | 10 Minuten | Grenzen Sie die Grundursache mithilfe von Ablaufverfolgungs- und Druckanweisungen ein |
| **Reparieren** | 5 Minuten | Wenden Sie die minimale, korrekte Korrektur | an
| **Überprüfen** | 5 Minuten | Testen Sie den Fix in allen Fällen, einschließlich Randfällen |

<Callout>Wenn Sie nach 15 Minuten den Fehler noch nicht gefunden haben, treten Sie einen Schritt zurück und ändern Sie Ihren Ansatz. Lesen Sie die Problemstellung noch einmal – möglicherweise haben Sie das erwartete Verhalten falsch verstanden. Probieren Sie einen völlig anderen Testfall aus. Manchmal liegt der Fehler in Ihren Annahmen und nicht im Code.</Callout>

## Was tun, wenn Sie nicht weiterkommen?

1. **Lesen Sie die Problemstellung noch einmal** – möglicherweise haben Sie eine falsche Annahme getroffen
2. **Versuchen Sie es mit einem minimalen Testfall** – reduzieren Sie die Eingabe auf den kleinsten Fall, der immer noch fehlschlägt
3. **Zeile für Zeile nachzeichnen** – verfolgen Sie bei Bedarf mit Stift und Papier jede Variable
4. **Überprüfen Sie die Grenzen** – erste Iteration, letzte Iteration, leere Eingabe
5. **Erklären Sie dem Interviewer das Problem** – „Rubber Duck Debugging“ funktioniert auch bei einem menschlichen Publikum
6. **Bitten Sie um einen Hinweis** – das ist viel besser, als 10 Minuten lang schweigend zu sitzen

## Wichtige Erkenntnisse

- **Verwenden Sie das RIIFV-Framework**: Reproduzieren → Isolieren → Identifizieren → Korrigieren → Verifizieren. Es funktioniert unter Druck, weil es Ihrem Gehirn einen Prozess gibt, wenn der Instinkt versagt.
- **Kontinuierlich laut denken**: Erzählen Sie Ihre Beobachtungen, Hypothesen und Überlegungen. Schweigen ist Ihr Feind in einem Debugging-Interview.
- **Randfälle priorisieren**: Die meisten Interviewfehler verbergen sich in leeren Eingaben, Duplikaten, negativen Zahlen oder Randbedingungen.
- **Druckauszüge sind Ihr Freund**: Setzen Sie sie an Entscheidungspunkten strategisch ein und bereinigen Sie sie, bevor Sie sie fertigstellen.
- **Wissen Sie, wann Sie drehen müssen**: Wenn Ihr Ansatz nach 10–15 Minuten nicht funktioniert, treten Sie einen Schritt zurück und versuchen Sie es mit einem völlig anderen Winkel.
