# Grundlagen des Systemdesigns

Beim Systemdesign-Interview entscheiden leitende Ingenieure über Erfolg oder Misserfolg. Im Gegensatz zur Codierung von Interviews mit eindeutig richtigen Antworten testet das Systemdesign Ihre Fähigkeit, mit Mehrdeutigkeiten umzugehen, Kompromisse einzugehen und Architekturentscheidungen zu kommunizieren. Die gute Nachricht? Es gibt ein wiederholbares Framework, das für jede Frage funktioniert. Die tolle Neuigkeit? Sobald Sie die Bausteine ​​verstanden haben, können Sie alles entwerfen, von einem URL-Shortener bis hin zu einer globalen Messaging-Plattform. Lassen Sie uns dieses Toolkit erstellen.

## Das 4-Schritte-Framework

Jedes Systemdesign-Interview sollte dieser Struktur folgen. Interviewer erwarten es, und es verhindert, dass Sie sich voreilig ins Detail stürzen.

### Schritt 1: Klärung der Anforderungen (5 Minuten)

Beginnen Sie niemals mit dem Entwerfen, ohne Fragen zu stellen. Hier demonstrieren Sie Produktdenken.

**Funktionale Anforderungen** – was das System tut:
- „Sollten Benutzer Nachrichten an Gruppen senden können oder nur 1:1?“
- „Brauchen wir Echtzeitbenachrichtigungen?“
- „Soll der Feed chronologisch oder geordnet sein?“

**Nichtfunktionale Anforderungen** – wie gut es funktioniert:
- „Wie hoch ist das erwartete Lese-/Schreibverhältnis?“
- „Welche Latenz ist akzeptabel?“
- „Brauchen wir eine starke Konstanz oder ist eine letztendliche Konstanz in Ordnung?“

<Callout>Klärende Fragen zu stellen ist kein Zeichen von Schwäche – es ist das Älteste, was man als Ingenieur tun kann. Interviewer lassen die Anforderungen absichtlich vage, um zu sehen, ob Sie sie klarstellen oder blind mit dem Entwerfen beginnen.</Callout>

### Schritt 2: Schätzung der Rückseite des Umschlags (3 Minuten)

Schnelle Berechnungen verankern Ihr Design in der Realität und verhindern Über- oder Unterentwicklung.

```
Example: Design Twitter

Daily Active Users (DAU): 300M
Tweets per day: 300M × 2 = 600M tweets/day
Reads per day: 300M × 100 = 30B reads/day (read-heavy)
Tweets per second: 600M / 86400 ≈ 7,000 writes/sec
Reads per second: 30B / 86400 ≈ 350,000 reads/sec
Storage per tweet: ~300 bytes text + metadata ≈ 500 bytes
Daily storage: 600M × 500B = 300GB/day ≈ 110TB/year
```

Diese Zahlen verraten Ihnen: Dieses System ist extrem leselastig, benötigt Caching und wird enorm viel Speicherplatz ansammeln.

### Schritt 3: High-Level-Design (10 Minuten)

Zeichnen Sie die Architektur mit den Hauptkomponenten. Beginnen Sie einfach und fügen Sie dann nach Bedarf Komplexität hinzu.

```
Client → Load Balancer → API Servers → Service Layer
                                          ↓
                              ┌───────────┼───────────┐
                              ↓           ↓           ↓
                           Database     Cache      Message Queue
                                          ↓           ↓
                                       CDN        Workers
```

Gehen Sie die wichtigsten Benutzerabläufe durch:
– „Wenn ein Benutzer einen Tweet postet, validiert ihn der API-Server, schreibt in die Datenbank und sendet ihn an den Fan-Out-Dienst …“
- „Wenn ein Benutzer seinen Feed öffnet, überprüfen wir zuerst den Cache …“

### Schritt 4: Deep Dive (15 Minuten)

Der Interviewer wählt 1-2 Bereiche aus, um tiefer zu gehen. Seien Sie bereit, Kompromisse im Detail zu besprechen.

<ThinkAboutIt>Wenn Sie ein Benachrichtigungssystem entwerfen würden, würden Sie Benachrichtigungen sofort an alle Follower senden (Fan-Out beim Schreiben) oder den Feed berechnen, wenn jeder Benutzer ihn anfordert (Fan-Out beim Lesen)? Welche Kompromisse gibt es für Nutzer mit Millionen Followern?</ThinkAboutIt>

## Die Bausteine

Stellen Sie sich diese als Legostücke vor. Jedes Systemdesign ist eine andere Anordnung derselben Blöcke.

### Load Balancer

Verteilen Sie den Datenverkehr auf mehrere Server. Kennen Sie drei Strategien:
- **Round Robin** – einfache, gleichmäßige Verteilung
- **Kleinste Verbindungen** – sendet an den Server mit den wenigsten aktiven Verbindungen
- **Konsistentes Hashing** – Routen basierend auf dem Anfrageinhalt (nützlich für das Caching)

### Caches

Die wirkungsvollste Leistungsoptimierung. Denken Sie an diese Cache-Muster:

```
Write-through:  App → Cache → DB  (consistent, higher write latency)
Write-back:     App → Cache ... → DB  (fast writes, risk of data loss)
Cache-aside:    App checks cache → miss → read DB → populate cache
```

**Cache-Räumung**: LRU (Least Recent Used) ist die Standardantwort in Interviews. Erwähnen Sie TTL (Time-To-Live) für zeitkritische Daten.

<FunFact>Laut einem berühmten Artikel von Jeff Dean erhöht ein einzelner Cache-Fehler, der auf die Festplatte statt in den Speicher geht, die Latenz um etwa das Hundertfache. Aus diesem Grund ist die Caching-Strategie oft die wirkungsvollste Entwurfsentscheidung – das Lesen aus dem Cache (1 ms) vs. das Lesen von der Festplatte (10 ms) vs. ein rechenzentrumsübergreifender Lesevorgang (150 ms) sind unterschiedliche Größenordnungen.</FunFact>

### Datenbanken

| Geben Sie | ein Verwenden Sie Wann | Beispiele |
|---|---|---|
| **Relational (SQL)** | ACID-Transaktionen, komplexe Abfragen, strukturierte Daten | PostgreSQL, MySQL |
| **Dokumentenspeicher** | Flexible Schemata, verschachtelte Daten, schnelle Iteration | MongoDB, DynamoDB |
| **Breite Spalte** | Riesiger Umfang, Zeitreihen, schreibintensiv | Cassandra, HBase |
| **Grafik** | Beziehungsintensive Daten, soziale Netzwerke | Neo4j, Neptun |

**Datenbankskalierung**:
- **Vertikale Skalierung**: größere Maschine (begrenzte Obergrenze)
- **Lesereplikate**: getrennter Lese- und Schreibverkehr
- **Sharding**: Partitionieren Sie Daten über mehrere Datenbanken (nach Benutzer-ID, Geografie usw.)

### Nachrichtenwarteschlangen

Entkoppeln Sie Produzenten von Konsumenten. Unverzichtbar für:
- Asynchrone Verarbeitung (E-Mail nach der Anmeldung senden)
- Lastnivellierung (Verkehrsspitzen absorbieren)
- Ereignisgesteuerte Architekturen

```
Producer → [Message Queue] → Consumer
           (Kafka, SQS,      (Workers that
            RabbitMQ)          process at
                               their own pace)
```

### CDNs (Content Delivery Networks)

Zwischenspeichern Sie statische Inhalte (Bilder, CSS, JS) auf Edge-Servern in der Nähe der Benutzer. Erwähnen Sie CDNs immer dann, wenn das System Medien bereitstellt oder über eine globale Benutzerbasis verfügt.

## Fragen zum klassischen Systemdesign

### Entwerfen Sie einen URL-Shortener (z. B. bit.ly)

**Wichtige Entscheidungen**:
- Generieren Sie Funktionscodes mit Base62-Kodierung (a-z, A-Z, 0-9)
- Verwenden Sie für die Einzigartigkeit einen zähler- oder hashbasierten Ansatz
- Leselastig → beliebte URLs aggressiv zwischenspeichern
- Datenbank: einfacher Schlüsselwertspeicher (short_code → original_url)

```
POST /shorten  { "url": "https://example.com/very/long/path" }
→ Returns: { "short_url": "https://bit.ly/abc123" }

GET /abc123
→ 301 Redirect to original URL (301 = permanent, cacheable by browser)
```

### Entwerfen Sie ein Chat-System (z. B. WhatsApp)

**Wichtige Entscheidungen**:
- WebSockets für bidirektionale Kommunikation in Echtzeit
- Nachrichtenspeicher: schreiboptimierte Datenbank (Cassandra)
- Online-Präsenz: Heartbeat-Mechanismus mit Timeout
- Gruppennachrichten: Verteilung an alle Gruppenmitglieder über die Nachrichtenwarteschlange

### Entwerfen Sie einen Newsfeed (z. B. Twitter/Facebook)

**Wichtige Entscheidungen**:
- **Fan-out beim Schreiben** für Benutzer mit < 10.000 Followern (Feeds vor der Berechnung)
- **Fan-out beim Lesen** für prominente Benutzer (Berechnung auf Anfrage, um das Schreiben in Millionen von Feeds zu vermeiden)
- Hybrider Ansatz: Die meisten Systeme nutzen beide Strategien
- Ranking: ML-basierte Relevanzbewertung gegenüber reiner chronologischer Reihenfolge

## Umgang mit Schätzungsfragen

Interviewer fragen gerne: „Wie viele X braucht Y?“ Verwenden Sie diese Anker:

| Metrisch | Wert |
|---|---|
| QPS für einen einzelnen Webserver | ~1.000-10.000 |
| QPS für eine einzelne Datenbank | ~1.000-5.000 |
| Cache-Leselatenz | ~1ms |
| Datenbank-Leselatenz | ~5-10ms |
| Rechenzentrumsübergreifende Latenz | ~100-150ms |
| 1 Million Sekunden | ~12 Tage |
| 1 Milliarde Sekunden | ~32 Jahre |

## Kommunikationstipps während des Systemdesigns

Ihre Kommunikation ist genauso wichtig wie Ihr Design. Üben Sie diese Gewohnheiten:

1. **Strukturieren Sie Ihre Gedanken**: „Lassen Sie mich mit den Anforderungen beginnen, dann mit der Schätzung und dann mit dem High-Level-Design.“
2. **Geben Sie Kompromisse explizit an**: „Wir könnten SQL für die Konsistenz oder NoSQL für die Skalierung verwenden. Angesichts unserer leseintensiven Arbeitslast würde ich zu NoSQL mit einer Caching-Ebene tendieren.“
3. **Bestätigen Sie, was Sie nicht wissen**: „Ich bin mir über den genauen Replikationsfaktor für Kafka nicht sicher, aber ich weiß, dass er konfigurierbar ist und normalerweise auf 3 eingestellt ist.“
4. **Kontaktieren Sie den Interviewer**: „Ich habe das High-Level-Design behandelt. Möchten Sie, dass ich mich eingehend mit dem Datenbankschema oder der Caching-Strategie befasse?“

<Callout>Der größte Fehler bei Systemdesign-Interviews besteht darin, zu früh zu tief in die Tiefe zu gehen. Widerstehen Sie dem Drang, das Datenbankschema in den ersten 5 Minuten zu entwerfen. Beginnen Sie weit und schränken Sie es dann ein, je nachdem, was der Interviewer untersuchen möchte.</Callout>

## Wichtige Erkenntnisse

- **Folgen Sie dem 4-Stufen-Framework**: Anforderungen → Schätzung → High-Level-Design → Deep Dive. Es funktioniert jedes Mal.
- **Kennen Sie Ihre Bausteine**: Load Balancer, Caches, Datenbanken, Nachrichtenwarteschlangen und CDNs sind das Vokabular des Systemdesigns.
- **Kompromisse sind der Punkt**: Es gibt keine perfekten Designs – nur Kompromisse. Formulieren Sie sie klar.
- **Schätzungen begründen Ihr Design**: Eine schnelle Berechnung auf der Rückseite des Umschlags verhindert, dass Sie zu viel oder zu wenig entwickeln.
- **Kommunikation ist die halbe Note**: Strukturieren Sie Ihre Gedanken, geben Sie Annahmen an und sprechen Sie regelmäßig mit dem Interviewer.
- **Üben Sie mit echten Systemen**: Studieren Sie, wie Twitter, WhatsApp, YouTube und Uber tatsächlich funktionieren. Ihre Technikblogs sind Goldgruben.
