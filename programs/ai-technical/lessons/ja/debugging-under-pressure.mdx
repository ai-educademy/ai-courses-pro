# プレッシャーの下でのデバッグ

誰かがあなたを監視し、タイマーがカウントダウンしている間にコードをデバッグすることには、特別な種類のストレスがかかります。手のひらは汗ばみ、頭は真っ白になり、突然 for ループがどのように機能するのか思い出せなくなります。エンジニアなら誰もがそこにいたことがあるでしょう。崩れ去る候補者と輝く候補者の違いは、生の才能ではありません。それは、脳がパニックになりそうになったときでも機能する体系的なプロセスがあるかどうかです。このレッスンではそのプロセスを説明します。

## RIIFV デバッグ フレームワーク

面接でバグのあるコードを渡された場合は、すぐにバグのスキャンを開始したいという衝動を抑えてください。代わりに、次の 5 段階のフレームワークに従ってください。

### R — 再現

バグの存在を確認し、その症状を理解します。

- 期待される動作は何ですか?
――実際の動きはどうなのでしょうか？
- どのような入力でバグが発生しますか?

```python
# You're told this function should return the second largest element
def second_largest(nums):
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second:
            second = num
    return second

# Step 1: Reproduce with test cases
print(second_largest([3, 1, 4, 1, 5]))  # Expected: 4, Got: 4 ✓
print(second_largest([5, 5, 5]))         # Expected: 5, Got: -inf ✗ — BUG!
print(second_largest([1]))               # Expected: None?, Got: -inf — Edge case
```

### 私は孤立します

バグが生息している場所を絞り込みます。分割統治の考え方を使用します。

- バグは入力解析、ロジック、または出力にありますか?
- 間違った結果を生成する特定の行またはブロックはどれですか?
- 最小限の失敗テスト ケースに分離できますか?

### 私は識別します

分離したら、症状だけでなく根本原因を特定します。

- **症状**: `[5, 5, 5]`に対して`-inf`が返されます
- **根本原因**: `elif num > second` 条件では重複が処理されません。すべての要素が等しい場合、`num > first`は 1 回だけ真になり、残りの等しい要素では `num > second` が真になることはありません。

### F — 修正

新しいバグを導入することなく根本原因に対処する最小限の修正を適用します。

```python
def second_largest(nums):
    if len(nums) < 2:
        return None
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second and num != first:  # Handle case: distinct second
            second = num
    return second if second != float('-inf') else first  # All same → return that value
```

<ThinkAboutIt>待ってください — `second_largest([5, 5, 5])` は 5 を返すべきですか、それとも None を返すべきですか?これは曖昧であり、実際の面接では、まさにこれが面接官に尋ねるべき種類の質問です。要件の明確化はデバッグの一部です。</ThinkAboutIt>

### V — 確認する

元の失敗したケース、エッジ ケース、以前に合格したケースなど、すべてのケースに対して修正が機能することを確認します。

```python
assert second_largest([3, 1, 4, 1, 5]) == 4    # Normal case
assert second_largest([5, 5, 5]) == 5            # Duplicates
assert second_largest([1, 2]) == 1               # Minimum valid input
assert second_largest([1]) is None               # Too few elements
assert second_largest([-1, -2, -3]) == -2        # Negative numbers
```

<Callout>バグを修正した後は、必ず元のテスト ケースを再実行してください。あるバグを修正しながら別のバグを導入することは驚くほど一般的です。 「検証」ステップでは、面接に費用がかかる可能性のある回帰を検出します。</Callout>

## 一般的なデバッグインタビュー形式

### 形式 1: 「これはバグのあるコードです - 修正してください」

1 ～ 3 個のバグのある機能を受け取ります。 RIIFV を適用します。
- コードを読んで意図を理解する
- メンタルテストケースを実行して失敗を見つける
- それぞれのバグを修正し、その理由を説明します

### 形式 2: 「このシステムは壊れています — 診断してください」

「チェックアウト ページに間違った価格が表示されることがあるというユーザーの報告があります。」というシナリオが与えられました。次のことを行う必要があります。
- 明確な質問をする (「時々? それはランダムですか? それともパターンに従っていますか?」)
- 仮説を立てる (「キャッシュの問題、競合状態、通貨換算のバグの可能性がある」)
- 優先順位に基づいた調査手順を提案します。

### 形式 3: 「このライブ システムをデバッグする」(ペア デバッグ)

あなたと面接官は一緒にデバッグします。彼らはチームメイトまたはシステムの役割を果たすことができます。
- 思考プロセスを言語化する
- 最初に確認する内容とその理由を提案します
- ログとログが提供するメトリクスを解釈する

## デバッグ中に声に出して考える

単独でのデバッグとインタビューでのデバッグの最大の違いは、ナレーションが必要であることです。強制的に感じさせずにそれを行う方法は次のとおりです。

**あなたの所見を述べてください**:
「この関数はリストを受け取り、2 番目に大きいリストを返す必要があることがわかりました。簡単な例でトレースしてみましょう...」

**仮説を立てる**:
「最初に考えたのは、値の重複などの特殊なケースは処理できないのではないかということです。[5, 5, 5] でテストしてみましょう...」

**理由を説明してください**:
「すべての値が等しい場合、条件 `num > second` は決して真ではありません。なぜなら、`first` はすでに 5 であり、残りの 5 は `-inf` でもある `second` より大きくないからです...待て、実際には `5 > -inf` は true なので、2 番目の要素では 2 番目は 5 になります... うーん、もっと注意深くトレースしましょう。」

**自分が間違っているときは認めてください**:
「実は、私の最初の仮説は間違っていました。もう一度辿ってみましょう…」

<FunFact>心理学者のゲイリー・クライン氏の研究によると、熟練したデバッガーは初心者よりも最大 10 倍速く問題を解決できますが、これは彼らが賢いからではなく、過去の経験からパターンを認識しているためです。これが、生のインテリジェンスよりもさまざまな種類のバグを扱う練習の方が重要である理由です。</FunFact>

## Print ステートメントの戦略的使用

コーディング面接では、print ステートメントがデバッガーになります。戦略的に使用してください。

```python
def merge_sorted_lists(list1, list2):
    result = []
    i = j = 0
    while i < len(list1) and j < len(list2):
        print(f"Comparing list1[{i}]={list1[i]} with list2[{j}]={list2[j]}")
        if list1[i] <= list2[j]:
            result.append(list1[i])
            i += 1
        else:
            result.append(list2[j])
            j += 1
        print(f"Result so far: {result}")

    # Don't forget: add remaining elements
    result.extend(list1[i:])
    result.extend(list2[j:])
    print(f"Final result: {result}")
    return result
```

**効果的な印刷デバッグのためのヒント**:
- 決定点で出力 (if/else の前、ループ内)
- 出力に変数名とインデックスを含めます。
- バグが疑われる箇所の前後を印刷します。
- 最終的なソリューションを提出する前に、印刷物を削除するかコメントアウトしてください。

## 分散システムのデバッグ

上級レベルの面接では、分散システムのデバッグについて質問される場合があります。

### デバッグ ツールキット

|ツール/テクニック |明らかになること |
|---|---|
| **ログ** (構造化、相関 ID 付き) |イベントのシーケンス、エラーの詳細 |
| **メトリクス** (レイテンシー、エラー率、スループット) |傾向と異常 |
| **トレース** (分散トレーシング) |サービス間のリクエスト フロー |
| **健康診断** |どのコンポーネントが劣化しているのか |

### 体系的なアプローチ

1. **メトリクス ダッシュボードを確認します** - 急激に変化しているのか、それとも徐々に低下しているのか?
2. **範囲を狭める** — どのサービス、エンドポイント、またはリージョンが影響を受けますか?
3. **最近の展開を確認す​​る** - 「何が変更されましたか?」最もシグナルの高い質問です
4. **トレースを追跡する** - 相関 ID を使用して、サービス全体で失敗したリクエストを追跡します
5. **依存関係を確認** — ダウンストリーム サービス (データベース、キャッシュ、サードパーティ API) が根本原因ですか?

```
User reports slow checkout
→ Metrics show p99 latency spike at 14:30
→ Correlated with deployment of payment-service v2.3.1
→ Traces show payment-service waiting 10s on database query
→ Database query plan changed due to missing index after schema migration
→ Root cause: migration in v2.3.1 dropped an index
→ Fix: recreate index, add migration test
```

## デバッグラウンド中の時間管理

一般的なデバッグ ラウンドは 30 ～ 45 分です。時間の予算を立ててください:

|フェーズ |時間 |アクティビティ |
|---|---|---|
| **理解しました** | 5分 |コードを読み、問題を明確にし、予想される動作と実際の動作を特定します。
| **再現** | 5分 |バグを引き起こすテスト ケースを作成する |
| **隔離と特定** | 10分 |トレースおよび print ステートメントを使用して根本原因を絞り込む |
| **修正** | 5分 |最小限の正しい修正を適用します。
| **確認してください** | 5分 |エッジケースを含むすべてのケースに対して修正をテストします。

<Callout>15 分経過してもバグが見つからない場合は、一歩下がってアプローチを変更してください。問題文をもう一度読んでください。予想される動作を誤解している可能性があります。まったく異なるテストケースを試してください。場合によっては、バグはコード内ではなく、あなたの仮定の中にあることがあります。</Callout>

## 行き詰まったときの対処法

1. **問題文をもう一度読んでください** - 間違った仮定をしている可能性があります
2. **最小限のテスト ケースを試してください** - それでも失敗する最小のケースに入力を減らします。
3. **一行ずつトレース** — 必要に応じてペンと紙を使用し、すべての変数を追跡します
4. **境界を確認** — 最初の反復、最後の反復、空の入力
5. **面接官に問題を説明します** — 「ラバーダック デバッグ」は人間の聴衆でも機能します
6. **ヒントを求める** — これは 10 分間黙って座っているよりもはるかに良いです

## 重要なポイント

- **RIIFV フレームワークを使用**: 再現 → 分離 → 特定 → 修正 → 検証。本能が働かなくなったときに脳にプロセスを与えるため、プレッシャーの下でも機能します。
- **継続的に声に出して考える**: 観察、仮説、推論を話します。デバッグインタビューでは沈黙は敵です。
- **エッジ ケースを優先する**: インタビューのバグのほとんどは、空の入力、重複、負の数、または境界条件に隠れています。
- **印刷ステートメントはあなたの友人です**: 決定時点で戦略的に使用し、最終決定する前にクリーンアップしてください。
- **ピボットのタイミングを知る**: 10 ～ 15 分経ってもアプローチがうまくいかない場合は、一歩下がって、まったく別の角度から試してください。
