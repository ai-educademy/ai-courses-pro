# システム設計の基礎

システム設計の面接は、上級エンジニアの成否が決まる場所です。明確な正解があるコーディング面接とは異なり、システム設計では、曖昧さを回避し、トレードオフを行い、アーキテクチャ上の決定を伝達する能力がテストされます。良いニュースは？あらゆる質問に有効な、反復可能なフレームワークがあります。素晴らしいニュースですか？構成要素を理解すると、URL 短縮ツールから世界規模のメッセージング プラットフォームに至るまで、あらゆるものを設計できます。そのツールキットを構築しましょう。

## 4 ステップのフレームワーク

すべてのシステム設計インタビューはこの構造に従う必要があります。面接官はそれを期待しているので、時期尚早に詳細を説明する必要がなくなります。

### ステップ 1: 要件の明確化 (5 分)

質問せずにデザインを開始しないでください。ここで製品の考え方を実証します。

**機能要件** - システムの機能:
- 「ユーザーはグループにメッセージを送信できるようにすべきですか、それとも 1 対 1 だけを送信できるようにすべきですか?」
- 「リアルタイム通知は必要ですか?」
- 「フィードは時系列かランク付けすべきですか?」

**非機能要件** - どれだけうまく機能するか:
- 「予想される読み取り/書き込み比率はどれくらいですか?」
- 「どの程度の遅延が許容されますか?」
- 「強い整合性が必要ですか、それとも結果整合性で大丈夫ですか?」

<Callout>明確な質問をすることは、弱さの表れではありません。それは、上級エンジニアとしてできる最もできることです。面接官は、あなたが明確にするのか、それともやみくもに設計を始めるのかを見極めるために、意図的に要件を曖昧なままにします。</Callout>

### ステップ 2: 封筒裏の推定 (3 分)

素早い計算により、設計を現実に基づいて行うことができ、エンジニアリングの過剰または不足を防ぎます。

```
Example: Design Twitter

Daily Active Users (DAU): 300M
Tweets per day: 300M × 2 = 600M tweets/day
Reads per day: 300M × 100 = 30B reads/day (read-heavy)
Tweets per second: 600M / 86400 ≈ 7,000 writes/sec
Reads per second: 30B / 86400 ≈ 350,000 reads/sec
Storage per tweet: ~300 bytes text + metadata ≈ 500 bytes
Daily storage: 600M × 500B = 300GB/day ≈ 110TB/year
```

これらの数字からわかるのは、このシステムは非常に読み取り負荷が高く、キャッシュが必要であり、大量のストレージが蓄積されることです。

### ステップ 3: 大まかな設計 (10 分)

主要なコンポーネントを含むアーキテクチャを描画します。単純なものから始めて、必要に応じて複雑さを追加してください。

```
Client → Load Balancer → API Servers → Service Layer
                                          ↓
                              ┌───────────┼───────────┐
                              ↓           ↓           ↓
                           Database     Cache      Message Queue
                                          ↓           ↓
                                       CDN        Workers
```

主なユーザー フローを順を追って説明します。
- 「ユーザーがツイートを投稿すると、API サーバーがそれを検証し、データベースに書き込み、ファンアウト サービスにプッシュします...」
- 「ユーザーがフィードを開くと、まずキャッシュをチェックします...」

### ステップ 4: 詳細 (15 分)

面接官はさらに深く掘り下げる分野を 1 ～ 2 つ選びます。トレードオフについて詳しく話し合う準備をしてください。

<ThinkAboutIt>通知システムを設計している場合、すべてのフォロワーに通知をすぐにプッシュしますか (書き込み時にファンアウト)、それとも各ユーザーがフィードを要求したときにフィードを計算しますか (読み取り時にファンアウト)。何百万ものフォロワーを持つユーザーにとってのトレードオフは何ですか?</ThinkAboutIt>

## ビルディングブロック

これらをレゴの部品と考えてください。すべてのシステム設計は、同じブロックの異なる配置です。

### ロードバランサ

トラフィックを複数のサーバーに分散します。 3 つの戦略を知ってください。
- **ラウンドロビン** - シンプルで平等な分配
- **最小接続** - アクティブな接続が最も少ないサーバーに送信します。
- **一貫性のあるハッシュ** - リクエストの内容に基づくルート (キャッシュに役立ちます)

### キャッシュ

単一で最も影響力のあるパフォーマンスの最適化。次のキャッシュ パターンを覚えておいてください。

```
Write-through:  App → Cache → DB  (consistent, higher write latency)
Write-back:     App → Cache ... → DB  (fast writes, risk of data loss)
Cache-aside:    App checks cache → miss → read DB → populate cache
```

**キャッシュの削除**: LRU (最も最近使用されていないもの) は、インタビューにおけるデフォルトの回答です。時間に依存するデータについては、TTL (Time-To-Live) について言及します。

<FunFact>Jeff Dean による有名な論文によると、単一のキャッシュ ミスがメモリではなくディスクに転送されると、遅延が約 100 倍増加します。多くの場合、キャッシュ戦略が最も影響力のある設計上の決定となるのはこのためです。キャッシュからの読み取り (1ms)、ディスクからの読み取り (10ms)、データセンター間読み取り (150ms) は桁違いです。</FunFact>

### データベース

|タイプ |いつ使用する |例 |
|---|---|---|
| **リレーショナル (SQL)** | ACID トランザクション、複雑なクエリ、構造化データ | PostgreSQL、MySQL |
| **ドキュメント ストア** |柔軟なスキーマ、ネストされたデータ、迅速な反復 | MongoDB、DynamoDB |
| **ワイドカラム** |大規模なスケール、時系列、書き込み負荷の高い |カサンドラ、HBase |
| **グラフ** |人間関係を重視したデータ、ソーシャル ネットワーク | Neo4j、ネプチューン |

**データベースのスケーリング**:
- **垂直スケーリング**: より大きなマシン (上限が制限されている)
- **リードレプリカ**: 読み取りトラフィックと書き込みトラフィックを分離します。
- **シャーディング**: 複数のデータベース間でデータを分割します (ユーザー ID、地理などによって)

### メッセージキュー

生産者と消費者を切り離す。必須:
- 非同期処理（サインアップ後にメールを送信）
- 負荷平準化（トラフィックの急増を吸収）
- イベント駆動型アーキテクチャ

```
Producer → [Message Queue] → Consumer
           (Kafka, SQS,      (Workers that
            RabbitMQ)          process at
                               their own pace)
```

### CDN (コンテンツ配信ネットワーク)

静的コンテンツ (画像、CSS、JS) をユーザーに近いエッジ サーバーにキャッシュします。システムがメディアを提供する場合、またはグローバルなユーザー ベースを持つ場合は常に、CDN について言及します。

## 典型的なシステム設計の質問

### URL 短縮ツールを設計する (例: bit.ly)

**重要な決定事項**:
- Base62 エンコーディング (a ～ z、A ～ Z、0 ～ 9) を使用してショート コードを生成します。
- 一意性を確保するためにカウンターまたはハッシュベースのアプローチを使用する
- 読み取りが多い → 人気のある URL を積極的にキャッシュする
- データベース: 単純なキーと値のストア (short_code → original_url)

```
POST /shorten  { "url": "https://example.com/very/long/path" }
→ Returns: { "short_url": "https://bit.ly/abc123" }

GET /abc123
→ 301 Redirect to original URL (301 = permanent, cacheable by browser)
```

### チャット システムを設計する (例: WhatsApp)

**重要な決定事項**:
- リアルタイム双方向通信のための WebSocket
- メッセージ ストレージ: 書き込みに最適化されたデータベース (Cassandra)
- オンライン プレゼンス: タイムアウト付きのハートビート メカニズム
- グループ メッセージ: メッセージ キューを介してすべてのグループ メンバーにファンアウトします。

### ニュースフィードをデザインする (例: Twitter/Facebook)

**重要な決定事項**:
- **書き込み時のファンアウト** (フォロワーが 10,000 人未満のユーザーの場合) (フィードの事前計算)
- 有名人ユーザー向けの **読み取り時のファンアウト** (数百万のフィードへの書き込みを回避するために、リクエストに応じて計算します)
- ハイブリッド アプローチ: ほとんどのシステムは両方の戦略を使用します。
- ランキング: 純粋な時系列順に基づく ML ベースの関連性スコアリング

## 見積もりに関する質問の処理

面接官は「Y には X が何個必要ですか?」と尋ねるのが大好きです。これらのアンカーを使用します。

|メトリック |値 |
|---|---|
|単一の Web サーバーの QPS | ~1,000-10,000 |
|単一データベースの QPS | ~1,000-5,000 |
|キャッシュ読み取りレイテンシ | ~1ms |
|データベース読み取りレイテンシ | ~5-10ms |
|データセンター間の遅延 | ~100-150ms |
| 100万秒 | ～12日 |
| 10億秒 | ～32歳 |

## システム設計時のコミュニケーションのヒント

コミュニケーションはデザインと同じくらい重要です。次の習慣を実践してください。

1. **考えを組み立てる**: 「まず要件、次に見積もり、次に概要設計から始めましょう。」
2. **トレードオフを明示的に説明**: 「一貫性のために SQL を使用することも、スケールのために NoSQL を使用することもできます。読み取りの多いワークロードを考慮すると、キャッシュ レイヤーを備えた NoSQL を使用することになります。」
3. **わからないことを認識する**: 「Kafka の正確なレプリケーション係数についてはわかりませんが、構成可能であり、通常は 3 に設定されることは知っています。」
4. **面接官に確認してください**: 「高レベルの設計については説明しました。データベース スキーマまたはキャッシュ戦略について詳しく説明してもよろしいですか?」

<Callout>システム設計の面接における最大の間違いは、あまりに早く深入りしすぎることです。最初の 5 分間は、データベース スキーマを設計したいという衝動を抑えてください。まず広く始めて、面接官が調べたいことに基づいて狭くしていきます。</Callout>

## 重要なポイント

- **4 ステップのフレームワークに従います**: 要件 → 見積もり → 高レベルの設計 → 詳細。毎回機能します。
- **構成要素を理解する**: ロード バランサー、キャッシュ、データベース、メッセージ キュー、CDN はシステム設計の語彙です。
- **トレードオフが重要です**: 完璧な設計は存在しません。あるのはトレードオフだけです。それらを明確に表現してください。
- **見積もりは設計の根拠となる**: 素早い計算により、オーバーエンジニアリングまたはアンダーエンジニアリングを防ぎます。
- **コミュニケーションは成績の半分です**: 自分の考えを構成し、仮定を述べ、面接官に定期的に確認してください。
- **実際のシステムを使って練習する**: Twitter、WhatsApp、YouTube、Uber が実際にどのように動作するかを学びます。彼らのエンジニアリング ブログは宝の山です。
