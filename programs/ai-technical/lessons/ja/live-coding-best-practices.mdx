# ライブコーディングのベストプラクティス

LeetCode メディアは寝ている間に解くことができますが、画面共有の相手側に人間を置くと、突然指がセミコロンの位置を忘れてしまいます。ライブ コーディングの面接はパフォーマンスです。最終的なコードだけでなく、そこに至るまでの過程が評価されます。合格した受験者が常に最速のプログラマーであるとは限りません。彼らは明確にコミュニケーションを取り、挫折に適切に対処し、プレッシャーの下でも読みやすいコードを書く人たちです。このレッスンでは、その候補者になることを教えます。

## 環境のセットアップ

第一印象は重要です。 CoderPad、HackerRank、または VS Code Live Share を開くと、面接官はすでに意見を形成しています。

### プラットフォーム固有のヒント

**CoderPad** (最も一般的):
- 面接を開始する前に、ドロップダウンから言語を選択してください
- 組み込みの「実行」ボタンを使用します - 出力がコンソール ペインに表示されることを確認します
- 自動インデントと構文ハイライトが利用可能

**ハッカーランク**:
- 問題文を注意深く読んでください - 入力は標準入力から取得されます
- テスト ケースは自動的に実行されます。予想される形式を理解する
- カスタム テスト ケースを左側のパネルに追加できます

**VS Code Live Share / Google ドキュメント**:
- オートコンプリートや構文強調表示はありません (おそらく)
- 手作業で一貫してインデントを行う - 規律を示します
- Google ドキュメントの場合: 等幅フォント (Courier New) を使用します。

<Callout>ライブコーディング面接の前に、5 分間の環境チェックを行ってください。プラットフォームを開き、「Hello World」を作成して実行します。面接中にプラットフォームをいじると貴重な時間が無駄になり、自信が揺らぎます。</Callout>

### 言語の選択

印象的に聞こえる言語ではなく、自分が最も流暢に話せる言語を選択してください。そうは言っても、考慮すべき点は次のとおりです。

|言語 |長所 |短所 |
|---|---|---|
| **Python** |簡潔で豊富な標準ライブラリ、高速な書き込み |実行時間が遅くなり、型が曖昧になる |
| **ジャワ** |強力なタイピング、面接官はシステム設計にそれを期待 |冗長、定型文 |
| **JavaScript** |フロントエンドの役割に適しており、柔軟性があります |風変わりな型強制。アルゴリズムではあまり一般的ではありません。
| **C++** |実行時間が速く、低レベルのスキルを示します |エラーが発生しやすい冗長な STL |

## Talk-Aloud プロトコル

これは最も影響力のある面接スキルであり、ほとんどの候補者が軽視しているスキルです。あなたの内なる独白は、外なる独白になる必要があります。

### 各段階で言うべきこと

**問題を読む** (0 ～ 3 分):
- 「問題を理解していることを確認させてください。...を見つける必要があります。」
- 「明確な質問がいくつかあります。入力を空にすることはできますか? 負の数を使用することはできますか?」
- 「私の理解を確認するために、いくつかの例を考えさせてください。」

**アプローチの計画** (3 ～ 7 分):
- 「私が最初に考えたのは、入れ子になったループを使用した総当り的なアプローチです。つまり、O(n²) になります。」
- 「これまでに見た要素を追跡するには、ハッシュ マップを使用するともっとうまくできると思います。」
- 「エッジケースについて考えさせてください: 空の入力、単一要素、すべての重複...」

**コードの作成** (7 ～ 25 分):
- 「関数シグネチャを設定し、エッジケースを処理することから始めます。」
- 「今、配列を反復処理し、各要素をチェックしています...」
- 「O(1) ルックアップが必要なので、ここではハッシュ マップを選択します。」

**テスト** (25 ～ 30 分):
- 「例でトレースしてみましょう: ターゲット 9 の入力 [2, 7, 11, 15] の場合...」
- 「空の配列のエッジケースもチェックする必要があります...」
- 「うーん、この場合の出力は一致しません。5 行目を見てみましょう...」

<ThinkAboutIt>最後に黙って問題を解決したときのことを思い出してください。社内の意思決定プロセスはどのようなものでしたか?それらの小さな決定をそれぞれどのように外部化しますか?一人で問題を解決する場合でも、自分の考えを言語化する練習をしてください。面接中に自然にできるようになります。</ThinkAboutIt>

## プレッシャーの下でクリーンなコードを書く

ストレスがかかると、最初に犠牲になるのはコードの品質です。意図的な習慣でこれに対抗してください。

### 意味のある名前を使用する

```python
# Under pressure (what many candidates write)
def solve(a, t):
    d = {}
    for i, v in enumerate(a):
        if t - v in d:
            return [d[t - v], i]
        d[v] = i

# What you should write
def two_sum(nums, target):
    seen = {}
    for index, num in enumerate(nums):
        complement = target - num
        if complement in seen:
            return [seen[complement], index]
        seen[num] = index
```

2 番目のバージョンでは、作成に 10 秒余分に時間がかかりますが、デバッグが 10 倍簡単になり、面接官に好印象を与えました。

### ヘルパー関数はあなたの味方です

```python
# Extract reusable logic into named functions
def is_valid_move(board, row, col):
    return 0 <= row < len(board) and 0 <= col < len(board[0])

def get_neighbours(row, col):
    return [(row + dr, col + dc) for dr, dc in [(0, 1), (0, -1), (1, 0), (-1, 0)]]
```

ヘルパー関数を使用すると、認知負荷が軽減され、コードが自己文書化され、「このヘルパーは後で実装します。今のところは機能するものと仮定してください」と言えるようになります。

<FunFact>ペア プログラミング (ライブ コーディングのインタビューをシミュレートするもの) に関する研究では、ペアはソロ プログラマーよりも欠陥が 15% 少ないコードを生成しますが、時間が約 15% 長くかかることが示されています。面接では、面接官との「ペア」の力関係が実際にあなたに有利に働きます。率直にコミュニケーションをとれば、一人では見逃してしまう間違いを彼らが見つけてくれるでしょう。</FunFact>

## ヒントを適切に処理する

面接官はヒントを与えます。それは失敗の兆候ではなく、会話です。どのように対応するかが重要です:

**ヒントに対する適切な応答**:
- 「それは素晴らしい指摘です。ここでスタックを使用することを提案していると思います。それがどのように役立つか考えさせてください...」
- 「ああ、なるほど、最初に入力を並べ替えれば、2 ポインタ アプローチが可能になります。再構成しましょう。」
- 「ありがとう、そのような特殊なケースは考慮していませんでした。負の数の処理を追加させてください。」

**悪い反応**:
- ヒントを無視してアプローチを続ける
- 「わかっています、まさにそうしようとしていたところです」（防御的）
- 敗北したか狼狽しているように見える

<Callout>ヒントを与える面接官は、あなたの成功を手助けしようとしているのです。多くの候補者は、複数のヒントを受け取った後に採用されます。重要なのは、ヒントを受け入れ、適応し、協力できることを示すことです。ヒントをもらった後も、失敗したアプローチに頑固に固執するのは危険信号です。</Callout>

## 時間管理: 35 分プラン

一般的な 35 分のコーディング問題の場合:

|フェーズ |分 |何をすべきか |
|---|---|---|
| **明確にしてください** | 0-5 |問題を読んで、質問し、例を書きます |
| **計画** | 5-8 |アプローチと複雑さを話し合い、面接官の同意を得る |
| **コード** | 8-25 | Talk-Aloud でクリーンで読みやすいコードを作成する |
| **テスト** | 25-30 |例を手動でトレースし、エッジ ケースを確認します。
| **最適化** | 30-35 |可能な改善、代替アプローチについて話し合う |

### よくあるタイミングの間違い

1. **計画なしにコーディングに 15 分を費やす** - 結局書き直すことになる
2. **決してテストしない** - 提出して「うまくいくと思います」と言うのは危険信号です
3. **実用的なソリューションを得る前に最適化する** - まず解決してから改善します
4. **1 つのアプローチに時間がかかりすぎる** - 10 分経っても効果がなければ、面接官にもっと良い方向性があるかどうか尋ねます

## 「完了」と言う前にソリューションをテストする

テストせずに「終わった」とは決して言わないでください。体系的なアプローチは次のとおりです。

```python
# Step 1: Trace through the provided example
# Input: [1, 2, 3, 4, 5], target = 9
# i=0: complement=9-1=8, not in seen, seen={1:0}
# i=1: complement=9-2=7, not in seen, seen={1:0, 2:1}
# ...
# i=3: complement=9-4=5, not in seen, seen={1:0, 2:1, 3:2, 4:3}
# i=4: complement=9-5=4, 4 IS in seen at index 3 → return [3, 4] ✓

# Step 2: Test edge cases
# Empty array: [] → should return [] or None
# Single element: [5], target=5 → no pair possible
# Negative numbers: [-1, 2, 3], target=1 → [-1, 2] at indices [0, 1]
# Duplicates: [3, 3], target=6 → should return [0, 1]
```

このテストプロセスを言語化します。徹底的さを示し、面接官よりも先にバグを発見します。

## 行き詰まったときの対処法

立ち往生することは失敗ではありません。黙って立ち往生するのは失敗です。あなたの脱出計画は次のとおりです。

1. **問題をもう一度言い直す** - 声に出して言うと、新たな視点が明らかになることがあります
2. **小さな例に取り組む** - 小さなケースを手動で解決すると、アルゴリズムが明らかになる可能性があります
3. **関連する問題について考える** - 「これを聞くと、スライディング ウィンドウ パターンを思い出します...」
4. **制約を考慮する** - n ≤ 1000 の場合、O(n²) 解が許容される可能性があります。
5. **問題を単純化** - 最初に単純なバージョンを解決してから、複雑さを加えます
6. **ヒントを求める** - 「ハッシュ マップを使用して周波数を追跡することを検討していますが、ウィンドウの縮小をどのように処理するかがわかりません。正しい方向を教えていただけますか?」

```python
# When stuck, try the "brute force first" strategy:
# 1. Write the O(n²) solution — it's usually straightforward
# 2. Identify the bottleneck (usually the inner loop)
# 3. Ask: "Can I eliminate this inner loop with a data structure?"
# 4. This often leads naturally to the optimal solution
```

## 解決後のディスカッション

解決策がうまくいったとしても、面接は終わったわけではありません。以下の準備をしてください。

- **「時間と空間の複雑さは何ですか?」** - これを常に用意してください。
- **「最適化できますか?」** - 実装が間に合わない場合でも、トレードオフについて話し合う
- **「これはエッジケースにどのように対処しますか?」** - 運用シナリオについて考えたことを示します
- **「入力が 10 億要素だったらどうなるでしょうか?」** - これはシステム設計思考に焦点を当てます

```python
# Example post-solution discussion:
# "My solution is O(n) time and O(n) space.
#  The space is used by the hash map which stores at most n elements.
#  If memory is a constraint, we could sort the array first and use
#  two pointers for O(n log n) time and O(1) space — but we'd need

#  For 1 billion elements, we might need to partition the data

```

## 重要なポイント

- **継続的に大声で話す**: 沈黙は敵です。問題解決のプロセスを最初から最後まで説明します。
- **コーディング前に明確にする**: 5 分間の質問により、間違った方向のコーディングを 15 分間節約できます。
- **プレッシャーの下でもクリーンなコードを作成**: 意味のある名前、ヘルパー関数、スケルトンファーストのアプローチにより、デバッグが容易になり、面接官に好印象を与えます。
- **体系的にテストします**: 「完了」を宣言する前に、例と特殊なケースをトレースします。
- **ヒントや挫折には適切に対処してください**: 立ち往生するのは正常なことです。重要なのは、どのように回復するかです。
- **時間を管理します**: 計画 (5 分) → コード (17 分) → テスト (5 分) → ディスカッション (5 分)。問題に基づいて調整しますが、テストをスキップしないでください。
