# التصحيح تحت الضغط

هناك نوع خاص من التوتر يأتي من تصحيح الأخطاء البرمجية بينما يراقبك شخص ما ويقوم جهاز ضبط الوقت بالعد التنازلي. تتعرق راحة يدك، ويصبح عقلك فارغًا، وفجأة لا يمكنك تذكر كيفية عمل حلقة for. لقد كان كل مهندس هناك. الفرق بين المرشحين الذين ينهارون وأولئك الذين يتألقون ليس في الموهبة الخام، بل في وجود عملية منهجية تعمل حتى عندما يريد عقلك الذعر. يمنحك هذا الدرس هذه العملية.

## إطار تصحيح أخطاء RIIFV

عندما يتم تسليمك رمز خطأ في إحدى المقابلات، قاوم الرغبة في البدء فورًا في البحث عن الخطأ. بدلاً من ذلك، اتبع إطار الخطوات الخمس هذا:

### R - إعادة إنتاج

التأكد من وجود الخلل وفهم أعراضه.

- ما هو السلوك المتوقع؟
- ما هو السلوك الفعلي؟
- تحت أي مدخلات يحدث الخطأ؟

```python
# You're told this function should return the second largest element
def second_largest(nums):
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second:
            second = num
    return second

# Step 1: Reproduce with test cases
print(second_largest([3, 1, 4, 1, 5]))  # Expected: 4, Got: 4 ✓
print(second_largest([5, 5, 5]))         # Expected: 5, Got: -inf ✗ — BUG!
print(second_largest([1]))               # Expected: None?, Got: -inf — Edge case
```

### أنا - عزل

تضييق نطاق المكان الذي تعيش فيه الحشرة. استخدم أسلوب فرق تسد:

- هل الخلل في تحليل الإدخال أم المنطق أم الإخراج؟
- ما هو الخط أو الكتلة المحددة التي تنتج نتيجة خاطئة؟
- هل يمكنك عزلها في حالة اختبار فاشلة إلى الحد الأدنى؟

### أنا - تحديد

بمجرد عزله، حدد السبب الجذري - وليس فقط العرض:

- **الأعراض**: إرجاع `-inf` مقابل `[5, 5, 5]`
- **السبب الجذري**: الشرط `elif num > second` لا يتعامل مع التكرارات. عندما تكون جميع العناصر متساوية، فإن `num > first` يكون صحيحًا مرة واحدة فقط، و`num > second` لا يكون صحيحًا أبدًا بالنسبة للعناصر المتساوية المتبقية.

### ف - إصلاح

قم بتطبيق الحد الأدنى من الإصلاح الذي يعالج السبب الجذري دون إدخال أخطاء جديدة:

```python
def second_largest(nums):
    if len(nums) < 2:
        return None
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second and num != first:  # Handle case: distinct second
            second = num
    return second if second != float('-inf') else first  # All same → return that value
```

<ThinkAboutIt>انتظر - هل يجب أن يُرجع `second_largest([5, 5, 5])` 5 أم لا شيء؟ هذا أمر غامض، وفي مقابلة حقيقية، هذا هو بالضبط نوع السؤال الذي يجب عليك طرحه على القائم بإجراء المقابلة. يعد توضيح المتطلبات جزءًا من تصحيح الأخطاء.</ThinkAboutIt>

### الخامس - التحقق

تأكد من أن الإصلاح يعمل لجميع الحالات - الحالة الفاشلة الأصلية، وحالات الحافة، وحالات النجاح السابقة:

```python
assert second_largest([3, 1, 4, 1, 5]) == 4    # Normal case
assert second_largest([5, 5, 5]) == 5            # Duplicates
assert second_largest([1, 2]) == 1               # Minimum valid input
assert second_largest([1]) is None               # Too few elements
assert second_largest([-1, -2, -3]) == -2        # Negative numbers
```

<Callout>قم دائمًا بإعادة تشغيل حالات الاختبار الأصلية بعد إصلاح الخلل. من الشائع بشكل مدهش إصلاح خطأ واحد أثناء إدخال خطأ آخر. تكتشف خطوة "التحقق" الانحدارات التي قد تكلفك المقابلة.</Callout>

## تنسيقات مقابلة التصحيح الشائعة

### التنسيق 1: "إليك رمز الأخطاء - أصلحه"

تتلقى دالة تحتوي على 1-3 أخطاء. تطبيق رييف:
- اقرأ الكود وافهم النية
- تشغيل حالات الاختبار العقلي للعثور على حالات الفشل
- أصلح كل خطأ واشرح أسبابك

### التنسيق 2: "هذا النظام معطل - قم بتشخيصه"

لقد تم إعطاؤك سيناريو: "أبلغ المستخدمون أن صفحة الدفع تعرض أحيانًا سعرًا خاطئًا." أنت بحاجة إلى:
- اطرح أسئلة توضيحية ("أحيانًا؟ هل الأمر عشوائي أم أنه يتبع نمطًا؟")
- فرضيات النموذج ("قد تكون مشكلة في التخزين المؤقت، أو حالة سباق، أو خطأ في تحويل العملة")
- اقتراح خطوات التحقيق حسب ترتيب الأولوية

### التنسيق 3: "تصحيح أخطاء هذا النظام المباشر" (تصحيح الأخطاء الزوجية)

تقوم أنت والقائم بإجراء المقابلة بتصحيح الأخطاء معًا. قد يلعبون دور زميل في الفريق أو نظام:
- لفظيا عملية التفكير الخاصة بك
- اقترح ما الذي يجب عليك التحقق منه أولاً ولماذا
- تفسير السجلات والمقاييس التي يقدمونها

## التفكير بصوت عالٍ أثناء تصحيح الأخطاء

أكبر فرق بين تصحيح الأخطاء بمفردك وتصحيح الأخطاء في المقابلة هو أنك تحتاج إلى السرد. إليك كيفية القيام بذلك دون الشعور بالإجبار:

**اذكر ملاحظاتك**:
"أرى أن الدالة تأخذ قائمة ويجب أن تُرجع ثاني أكبر قائمة. اسمحوا لي أن أتتبع ذلك بمثال بسيط..."

**نموذج الفرضيات**:
"فكرتي الأولى هي أنه قد لا يتعامل مع حالات الحافة مثل القيم المكررة. اسمح لي بالاختبار باستخدام [5، 5، 5]..."

** اشرح أسبابك **:
"الشرط `num > second` ليس صحيحًا أبدًا عندما تكون جميع القيم متساوية لأن `first` يساوي 5 بالفعل، والخمسات المتبقية ليست أكبر من `second` وهو أيضًا `-inf`... انتظر، في الواقع `5 > -inf` صحيح، لذا تصبح الثانية 5 على العنصر الثاني... حسنًا، دعني أتتبع بعناية أكبر."

**اعترف بالخطأ**:
"في الواقع، كانت فرضيتي الأولية غير صحيحة. اسمحوا لي أن أعيد تتبع هذا..."

<FunFact>وجدت الأبحاث التي أجراها عالم النفس غاري كلاين أن مصححي الأخطاء الخبراء يحلون المشكلات بسرعة تصل إلى 10 مرات أسرع من المبتدئين، ليس لأنهم أكثر ذكاءً، ولكن لأنهم يتعرفون على الأنماط من التجارب السابقة. هذا هو السبب في أن التدريب على أنواع الأخطاء المتنوعة أكثر أهمية من الذكاء الخام.</FunFact>

## الاستخدام الاستراتيجي للبيانات المطبوعة

في مقابلة البرمجة، تعد البيانات المطبوعة بمثابة مصحح الأخطاء. استخدمها بشكل استراتيجي:

```python
def merge_sorted_lists(list1, list2):
    result = []
    i = j = 0
    while i < len(list1) and j < len(list2):
        print(f"Comparing list1[{i}]={list1[i]} with list2[{j}]={list2[j]}")
        if list1[i] <= list2[j]:
            result.append(list1[i])
            i += 1
        else:
            result.append(list2[j])
            j += 1
        print(f"Result so far: {result}")

    # Don't forget: add remaining elements
    result.extend(list1[i:])
    result.extend(list2[j:])
    print(f"Final result: {result}")
    return result
```

**نصائح لتصحيح أخطاء الطباعة بفعالية**:
- الطباعة عند نقاط القرار (قبل إذا/إلا، الحلقات الداخلية)
- تضمين أسماء المتغيرات والمؤشرات في الإخراج
- الطباعة قبل وبعد موقع الخطأ المشتبه فيه
- قم بإزالة المطبوعات أو التعليق عليها قبل إرسال الحل النهائي

## تصحيح أخطاء الأنظمة الموزعة

بالنسبة للمقابلات رفيعة المستوى، قد يتم سؤالك عن تصحيح أخطاء الأنظمة الموزعة:

### مجموعة أدوات التصحيح

| الأداة/التقنية | ما يكشف |
|---|---|
| **السجلات** (منظمة، مع معرفات الارتباط) | تسلسل الأحداث، تفاصيل الخطأ |
| **المقاييس** (زمن الوصول، معدل الخطأ، الإنتاجية) | الاتجاهات والشذوذات |
| **آثار** (التتبع الموزع) | تدفق الطلب عبر الخدمات |
| **فحوصات الصحة** | ما هي المكونات المتدهورة |

### نهج منهجي

1. **التحقق من لوحات معلومات المقاييس** - هل هو ارتفاع أم تدهور تدريجي؟
2. **تضييق النطاق** - ما هي الخدمة أو نقطة النهاية أو المنطقة المتأثرة؟
3. **تحقق من عمليات النشر الأخيرة** - "ما الذي تغير؟" هو السؤال الأعلى إشارة
4. **اتبع التتبع** - استخدم معرفات الارتباط لتتبع الطلب الفاشل عبر الخدمات
5. **التحقق من التبعيات** - هل الخدمة النهائية (قاعدة البيانات، ذاكرة التخزين المؤقت، واجهة برمجة تطبيقات الطرف الثالث) هي السبب الجذري؟

## إدارة الوقت أثناء جولات التصحيح

تستغرق جولة التصحيح النموذجية 30-45 دقيقة. حدد وقتك:

| المرحلة | الوقت | النشاط |
|---|---|---|
| **افهم** | 5 دقائق | اقرأ الكود، ووضح المشكلة، وحدد السلوك المتوقع مقابل السلوك الفعلي |
| ** إعادة إنتاج ** | 5 دقائق | قم بإنشاء حالات اختبار تؤدي إلى ظهور الخطأ |
| **عزل وتحديد** | 10 دقائق | تضييق نطاق السبب الجذري باستخدام عبارات التتبع والطباعة |
| **إصلاح** | 5 دقائق | قم بتطبيق الإصلاح الأدنى الصحيح |
| **التحقق** | 5 دقائق | اختبر الإصلاح على جميع الحالات، بما في ذلك حالات الحافة |

<Callout>إذا مر 15 دقيقة ولم تجد الخطأ، فتراجع وغير أسلوبك. أعد قراءة بيان المشكلة - ربما تكون قد أسأت فهم السلوك المتوقع. جرب حالة اختبار مختلفة تمامًا. في بعض الأحيان يكون الخطأ في افتراضاتك، وليس في الكود.</Callout>

## ماذا تفعل عندما تكون عالقًا

1. **أعد قراءة بيان المشكلة** - ربما تكون قد قمت بافتراض غير صحيح
2. **جرب حالة اختبار بسيطة** - قم بتقليل الإدخال إلى أصغر حالة لا تزال تفشل
3. **التتبع سطرًا تلو الآخر** - باستخدام القلم والورقة، إذا لزم الأمر، تتبع كل متغير
4. **تحقق من الحدود** - التكرار الأول، التكرار الأخير، إدخال فارغ
5. **اشرح المشكلة للمحاور** - "تصحيح أخطاء البطة المطاطية" ينجح حتى مع الجمهور البشري
6. **اطلب تلميحًا** - هذا أفضل بكثير من الجلوس في صمت لمدة 10 دقائق

## الوجبات السريعة الرئيسية

- **استخدم إطار عمل RIIFV**: إعادة إنتاج → عزل → تحديد → إصلاح → التحقق. إنه يعمل تحت الضغط لأنه يمنح عقلك عملية عندما تفشل الغريزة.
- **فكر بصوت عالٍ بشكل مستمر**: اسرد ملاحظاتك وافتراضاتك واستدلالاتك. الصمت هو عدوك في مقابلة التصحيح.
- **منح الأولوية لحالات الحافة**: تختبئ معظم أخطاء المقابلة في المدخلات الفارغة أو التكرارات أو الأرقام السالبة أو الشروط الحدودية.
- **اطبع البيانات هي صديقتك**: استخدمها بشكل استراتيجي عند نقاط اتخاذ القرار، ثم نظفها قبل الانتهاء منها.
- **اعرف متى تقوم بالتدوير**: إذا لم ينجح أسلوبك بعد 10-15 دقيقة، فتراجع وجرب زاوية مختلفة تمامًا.
