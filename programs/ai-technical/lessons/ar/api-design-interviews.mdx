# مقابلات تصميم API

واجهات برمجة التطبيقات هي عقود بين الأنظمة، وتصميمها بشكل جيد هو مهارة تفصل بين كبار المهندسين وصغارهم. في مقابلة تصميم واجهة برمجة التطبيقات (API)، أنت لا تكتب نقاط النهاية فحسب - بل توضح أنك تفهم كيف سيستخدم المستهلكون نظامك، وكيف سيتطور بمرور الوقت، وأين توجد أوضاع الفشل. سواء طُلب منك تصميم بوابة دفع أو واجهة برمجة تطبيقات لمنصة التواصل الاجتماعي، فإن المبادئ هي نفسها. دعونا السيطرة عليهم.

## مبادئ تصميم REST API

يظل REST هو نموذج API المهيمن في المقابلات. الأسس التي يجب عليك إثباتها:

### التصميم الموجه نحو الموارد

فكر في الأسماء (الموارد)، وليس الأفعال (الأفعال). يجب أن تمثل عناوين URL الأشياء، ويجب أن تمثل أساليب HTTP الإجراءات المتعلقة بهذه الأشياء.

```
✅ Good:
GET    /users/123              — Fetch user 123
POST   /users                  — Create a new user
PUT    /users/123              — Replace user 123
PATCH  /users/123              — Partially update user 123
DELETE /users/123              — Delete user 123

❌ Bad:
GET    /getUser?id=123
POST   /createUser
POST   /deleteUser/123
```

<Callout>يحكي التسلسل الهرمي للموارد النظيفة قصة واجهة برمجة التطبيقات (API). `/users/123/orders/456/items` يقرأ بشكل طبيعي: "المستخدم 123 يطلب 456 عنصرًا." إذا كانت بنية عنوان URL الخاص بك لا تبدو وكأنها جملة، فأعد النظر في تصميم الموارد لديك.</Callout>

### طرق HTTP ورموز الحالة

تعرف على هذه الأشياء الباردة - سيختبر القائمون على المقابلات دقتك:

| الطريقة | عاجز؟ | حالة الاستخدام |
|---|---|---|
| احصل على | نعم | اقرأ موردًا (لا يتغير أبدًا) |
| مشاركة | لا | إنشاء مورد |
| ضع | نعم | الاستبدال الكامل للمورد |
| التصحيح | لا* | تحديث جزئي |
| حذف | نعم | إزالة مورد |

*من الناحية الفنية، لا يعد برنامج PATCH غير فعال، على الرغم من أن عمليات التنفيذ غالبًا ما تكون كذلك.*

**رموز الحالة التي يجب أن تعرفها**:
- `200 OK` — النجاح بجسم الاستجابة
- `201 Created` — تم إنشاء المورد (يتضمن رأس `Location`)
- `204 No Content` — النجاح بدون نص الاستجابة (شائع في DELETE)
- `400 Bad Request` — أرسل العميل بيانات غير صالحة
- `401 Unauthorized` — المصادقة مطلوبة
- `403 Forbidden` — موثق ولكن غير مصرح به
- `404 Not Found` — المورد غير موجود
- `409 Conflict` — تعارض مع الحالة الحالية (نسخة مكررة، عدم تطابق الإصدار)
- `429 Too Many Requests` — السعر محدود
- `500 Internal Server Error` — انكسر شيء ما من جانبنا

### ترقيم الصفحات

لا تقم أبدًا بإرجاع قوائم غير محدودة. ثلاثة أنماط شائعة:

```json
// Offset-based (simple but poor for large datasets)
GET /users?offset=20&limit=10

// Cursor-based (preferred for feeds and large datasets)
GET /users?cursor=eyJ0aW1lIjoiMjAyNC0wMS0wMSJ9&limit=10

// Response includes pagination metadata
{
  "data": [...],
  "pagination": {
    "next_cursor": "eyJ0aW1lIjoiMjAyNC0wMS0wMiJ9",
    "has_more": true
  }
}
```

<ThinkAboutIt>لماذا يُفضل ترقيم الصفحات المستند إلى المؤشر على نظام الإزاحة لمجموعات البيانات الكبيرة التي يتم تحديثها بشكل متكرر؟ ضع في اعتبارك ما يحدث عند إدراج عناصر جديدة أثناء قيام المستخدم بترقيم النتائج.</ThinkAboutIt>

### الإصدار

تتطور واجهات برمجة التطبيقات. تصميم لذلك من اليوم الأول.

```
// URL versioning (most common, explicit)
GET /v1/users/123
GET /v2/users/123

// Header versioning (cleaner URLs, less discoverable)
GET /users/123
Accept: application/vnd.myapi.v2+json
```

في المقابلات، يعد إصدار عنوان URL هو الحل الآمن ما لم يستكشف القائم بالمقابلة البدائل على وجه التحديد.

### استجابات الخطأ

تفصل استجابات الأخطاء المتسقة والغنية بالمعلومات بين واجهات برمجة التطبيقات الرائعة والواجهات المحبطة:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request body contains invalid fields.",
    "details": [
      {
        "field": "email",
        "message": "Must be a valid email address."
      },
      {
        "field": "age",
        "message": "Must be a positive integer."
      }
    ],
    "request_id": "req_abc123"
  }
}
```

قم دائمًا بتضمين `request_id` لتصحيح الأخطاء و`code` المقروء آليًا إلى جانب `message` القابل للقراءة بواسطة الإنسان.

## GraphQL في المقابلات

أصبحت أسئلة GraphQL شائعة بشكل متزايد، خاصة في الشركات ذات احتياجات الواجهة الأمامية المعقدة.

** المزايا الرئيسية للتوضيح **:
- يطلب العملاء البيانات التي يحتاجونها بالضبط (بدون جلب زائد)
- نقطة نهاية واحدة تقلل من الرحلات ذهابًا وإيابًا
- المخطط المكتوب بقوة بمثابة وثائق

```graphql
# Schema definition
type User {
  id: ID!
  name: String!
  email: String!
  orders(first: Int, after: String): OrderConnection!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

# Query — client specifies exactly what it needs
query {
  user(id: "123") {
    name
    orders(first: 5) {
      edges {
        node {
          total
          status
        }
      }
    }
  }
}
```

**المقايضات التي يجب مناقشتها**: يضيف GraphQL التعقيد على جانب الخادم (سلاسل المحلل، واستعلامات N+1، والتخزين المؤقت أكثر صعوبة). بالنسبة لواجهات برمجة تطبيقات CRUD البسيطة، غالبًا ما يكون REST هو الخيار الأفضل.

<FunFact>تم تطوير GraphQL داخليًا في فيسبوك في عام 2012 لحل مشكلة محددة في أداء الأجهزة المحمولة: حيث تطلب موجز الأخبار بيانات من العديد من الخدمات الخلفية المختلفة، وكان إجراء مكالمات REST متعددة من الأجهزة المحمولة على شبكات بطيئة يؤدي إلى توقف الأداء. لقد كان مفتوح المصدر في عام 2015.</FunFact>

## أساسيات أمان واجهة برمجة التطبيقات

يجب أن تتطرق كل مقابلة لتصميم واجهة برمجة التطبيقات (API) إلى الأمان. قم بتغطية هذه الأساسيات:

### المصادقة والترخيص

```
Authentication (AuthN): WHO are you?
→ API Keys, OAuth 2.0, JWT tokens

Authorisation (AuthZ): WHAT can you do?
→ Role-based (RBAC), Scope-based, Resource-based
```

```
// JWT in Authorization header
GET /users/123/orders
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

// API Key (for server-to-server)
GET /analytics/reports
X-API-Key: sk_live_abc123...
```

### تحديد المعدل

حماية واجهة برمجة التطبيقات (API) الخاصة بك من سوء الاستخدام وضمان الاستخدام العادل:

```
// Rate limit headers in response
HTTP/1.1 200 OK
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1640995200

// When limit is exceeded
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

ناقش إستراتيجيات تحديد المعدل: لكل مستخدم، ولكل IP، ولكل نقطة نهاية، والحدود المتدرجة لخطط API المختلفة.

## سيناريوهات المقابلة الحقيقية

### تصميم واجهة برمجة تطبيقات الدفع

متطلبات التوضيح:
- ما طرق الدفع؟ (البطاقة، التحويل البنكي، المحفظة)
- هل نحن بحاجة إلى العجز الجنسي؟ (نعم - دائمًا للمدفوعات)
- ماذا عن المبالغ المستردة والنزاعات؟

```
POST /v1/payments
{
  "amount": 4999,           // Always use smallest currency unit (cents)
  "currency": "GBP",
  "payment_method": "pm_card_visa_123",
  "idempotency_key": "order_789_attempt_1",
  "metadata": {
    "order_id": "order_789"
  }
}

Response: 201 Created
{
  "id": "pay_abc123",
  "status": "processing",
  "amount": 4999,
  "currency": "GBP",
  "created_at": "2024-01-15T10:30:00Z"
}
```

<Callout>بالنسبة لواجهات برمجة تطبيقات الدفع، ناقش دائمًا مفاتيح العجز. يحدث فشل في الشبكة، ويعيد العملاء المحاولة، وبدون العجز، ستفرض رسومًا على العملاء مرتين. يضمن مفتاح العجز أن إعادة محاولة نفس الطلب تؤدي إلى نفس النتيجة.</Callout>

**قرارات التصميم الرئيسية التي يجب مناقشتها**:
- المبالغ بأصغر وحدة عملة (سنت/بنس) لتجنب مشكلات الفاصلة العائمة
- مفاتيح العجز لإعادة المحاولة الآمنة
- عمليات الاسترجاعات عبر Webhook لتحديثات الحالة غير المتزامنة
- اعتبارات الامتثال PCI

### تصميم واجهة برمجة تطبيقات الوسائط الاجتماعية

```
// Post creation
POST /v1/posts
{
  "content": "Hello world!",
  "media_ids": ["media_123"],
  "visibility": "public"
}

// Feed retrieval with cursor pagination
GET /v1/feed?cursor=abc&limit=20

// Interactions
POST /v1/posts/{post_id}/likes
DELETE /v1/posts/{post_id}/likes
POST /v1/posts/{post_id}/comments
```

ناقش التصفية والبحث وكيفية تجميع الخلاصة (يرتبط نموذج السحب مقابل الدفع بتصميم النظام).

## الأخطاء الشائعة في مقابلات تصميم API

1. **كشف التنفيذ الداخلي** — لا تدع أسماء أعمدة قاعدة البيانات أو المعرفات الداخلية تتسرب إلى واجهة برمجة التطبيقات. استخدم DTOs.
2. **التسمية غير المتسقة** — اختر `snake_case` أو `camelCase` والتزم به في كل مكان.
3. **ترقيم الصفحات مفقود** — يجب أن تدعم أي نقطة نهاية قائمة ترقيم الصفحات.
4. **لا توجد مناقشة بشأن التعامل مع الأخطاء** — أظهر رأيك في أوضاع الفشل.
5. **تجاهل التوافق مع الإصدارات السابقة** — تؤدي إضافة الحقول المطلوبة إلى نقاط النهاية الحالية إلى انقطاع العملاء.
6. **استخدام الأفعال في عناوين URL** — `/createUser` بدلاً من `POST /users`.

## الوجبات السريعة الرئيسية

- **فكر في الموارد**: صمم عناوين URL حول الأسماء، واسمح لطرق HTTP بالتعامل مع الأفعال.
- **تعرف على رموز الحالة الخاصة بك**: تظهر رموز الحالة الدقيقة أنك تفهم دلالات HTTP.
- **ترقيم الصفحات دائمًا**: تعتبر الإجابات غير المحدودة في القائمة علامة حمراء في المقابلات.
- **التصميم للفشل**: العجز، والاستجابات للأخطاء، وتحديد المعدل يُظهر التفكير في الاستعداد للإنتاج.
- **الأمان ليس اختياريًا**: يجب أن تكون المصادقة والترخيص وتحديد المعدل جزءًا من كل مناقشة حول تصميم واجهة برمجة التطبيقات.
- **المقايضات الواضحة**: REST مقابل GraphQL، والاتساق مقابل المرونة، والبساطة مقابل القوة - يرغب القائمون على إجراء المقابلات في سماع أسبابك.
