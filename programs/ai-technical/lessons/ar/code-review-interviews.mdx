# مقابلات مراجعة الكود

تعد مقابلات مراجعة القواعد واحدة من أكثر الجولات التي تم الاستخفاف بها في عملية التوظيف - وواحدة من أكثر الجولات كشفًا. بينما تختبر مقابلات البرمجة ما إذا كان بإمكانك كتابة التعليمات البرمجية، تختبر مقابلات مراجعة التعليمات البرمجية ما إذا كان بإمكانك قراءتها والسبب وراء ذلك وتحسينها. فهي تكشف كيف تفكر في الجودة، وكيف تحدد أولويات التعليقات، وكيف تتواصل مع المهندسين الآخرين. يقوم العديد من المرشحين بالتحضير لعدة أشهر على LeetCode ولكنهم يدخلون في جولة مراجعة الكود وهم غير مستعدين تمامًا. لا تكن ذلك الشخص.

## ما هي مقابلات مراجعة الكود التي يتم اختبارها فعليًا؟

يبحث القائمون على المقابلات الذين يقيمون مهاراتك في مراجعة التعليمات البرمجية عن خمسة أشياء:

1. **اكتشاف الأخطاء** — هل يمكنك اكتشاف الأخطاء المنطقية وحالات الحافة وحالات السباق؟
2. **حس التصميم** — هل تتعرف على انتهاكات مبادئ SOLID، أو التجريدات السيئة، أو التعليمات البرمجية التي سيكون من الصعب صيانتها؟
3. **الوعي الأمني** — هل يمكنك تحديد نقاط الضعف في الحقن أو عيوب المصادقة أو مخاطر التعرض للبيانات؟
4. **مهارة التواصل** — هل يمكنك شرح القضايا بشكل واضح وبناء؟
5. **تحديد الأولويات** — هل تركز على الأمور الأكثر أهمية، أم تتجاهل الأسماء المتغيرة؟

<Callout>الخطأ الأكثر شيوعًا في مقابلات مراجعة التعليمات البرمجية هو قضاء كل وقتك في مشكلات الأسلوب (التسمية والتنسيق) مع عدم وجود أخطاء فعلية. يقوم القائمون على المقابلات بزرع الأخطاء الحرجة جنبًا إلى جنب مع مشكلات الأسلوب لمعرفة ما تعطيه الأولوية.</Callout>

## نهج المراجعة المنهجية

لا تقم بمسح الرمز ضوئيًا بشكل عشوائي. استخدم نهجًا منظمًا قائمًا على التمرير:

### تمرير 1: فهم النية (دقيقتان)

قبل انتقاد أي شيء، افهم ما تحاول الكود القيام به:
- قراءة أسماء الوظائف/الفئات والتعليقات
- تحديد المدخلات والمخرجات
- فهم منطق الأعمال

### التمريرة 2: التصحيح (5 دقائق)

هذا هو المكان الذي تجد فيه الأخطاء. تحقق بشكل منهجي:
- **حالات الحافة**: المدخلات الفارغة، والقيم الخالية، والعناصر المفردة، والقيم القصوى
- **أخطاء متقطعة**: حدود الحلقة، وفهرسة المصفوفة
- **أخطاء منطقية**: شروط غير صحيحة، عبارات فاصل مفقودة، عامل تشغيل خاطئ
- **مشكلات التزامن**: الحالة المشتركة القابلة للتغيير، وظروف السباق
- **معالجة الأخطاء**: الاستثناءات غير المكتشفة، والتحققات الفارغة المفقودة

### المرور 3: التصميم وقابلية الصيانة (3 دقائق)

البحث عن القضايا الهيكلية:
- وظائف تفعل أشياء كثيرة جدًا (انتهاك المسؤولية الفردية)
- اقتران محكم بين المكونات
- الأرقام السحرية والقيم المشفرة
- التجريدات المفقودة أو التجريدات غير الضرورية
- ازدواجية الكود

### التمريرة 4: الأداء والأمان (دقيقتان)

- استعلامات قاعدة البيانات غير الضرورية في الحلقات (مشكلة N+1)
- فقدان التحقق من صحة المدخلات أو التعقيم
- كشف البيانات الحساسة في السجلات أو الردود
- خوارزميات غير فعالة حيث توجد بدائل أفضل

## أنماط الأخطاء الشائعة التي يجب اكتشافها

تدريب عينيك على التقاط هذه الأخطاء عالية التردد:

### أخطاء مرجعية فارغة

```java
// Bug: user could be null
public String getUserEmail(Long userId) {
    User user = userRepository.findById(userId);
    return user.getEmail();  // NullPointerException if user not found
}

// Fixed
public String getUserEmail(Long userId) {
    return userRepository.findById(userId)
        .map(User::getEmail)
        .orElseThrow(() -> new UserNotFoundException(userId));
}
```

```java
public List<User> getUsers() {
```

### حقن SQL

```python
# Bug: SQL injection vulnerability

    query = f"SELECT * FROM users WHERE username = '{username}'"
    return db.execute(query)

# Fixed: parameterised query
def get_user(username):
    query = "SELECT * FROM users WHERE username = %s"
    return db.execute(query, (username,))
```

<FunFact>وجدت دراسة أجريت على أكثر من 100.000 مراجعة للأكواد البرمجية في Google أن حوالي 25% من جميع تعليقات المراجعة تدور حول "الصحة" - أي الأخطاء الفعلية أو الأخطاء المنطقية. 25% أخرى تتعلق بـ "الفهم" - مما يجعل فهم التعليمات البرمجية أسهل. يمثل الأسلوب والتنسيق أقل من 10% من التعليقات الموضوعية.</FunFact>

## تحديد أولويات ملاحظاتك

في مقابلة محدودة الوقت، ليست كل ردود الفعل متساوية. استخدم إطار الأولوية هذا:

| الأولوية | الفئة | مثال |
|---|---|---|
| 🔴 **حرجة** | الأخطاء والثغرات الأمنية وفقدان البيانات | حقن SQL، وظروف السباق، والمرجعية الخالية |
| 🟠 **عالي** | قضايا التصميم، مشاكل الأداء | استعلامات N+1، معالجة الأخطاء المفقودة، الاقتران المحكم |
| 🟡 **متوسطة** | قابلية الصيانة وسهولة القراءة | الشروط المعقدة، الوثائق المفقودة، الأرقام السحرية |
| 🟢 **منخفض** | الأسلوب، تحسينات طفيفة | تسمية المتغير، طلب الاستيراد، إعادة البناء الثانوية |

في المقابلة، اقضي 80% من وقتك في 🔴 و 🟠 العناصر. اذكر 🟡 العناصر باختصار. المس 🟢 العناصر فقط إذا كان لديك وقت متبقي وعثرت بالفعل على المشكلات المهمة.

## توصيل تعليقات المراجعة

إن كيفية تقديم التعليقات أمر مهم بقدر أهمية التعليقات نفسها. يقوم القائمون على المقابلات بتقييم مهارات التعاون لديك.

**افعل هذا**:
- "لاحظت أن هذا الاستعلام موجود داخل حلقة، مما قد يتسبب في حدوث مشكلات في أداء N+1. قد نرغب في تجميع هذا في استعلام واحد."
- "يبدو أن هذا قد يؤدي إلى ظهور NullPointerException إذا لم يتم العثور على المستخدم. هل يمكننا إضافة علامة اختيار فارغة أو استخدام اختياري هنا؟"
- "استخدام جيد لنمط الإستراتيجية هنا - فهو يجعل إضافة أنواع دفع جديدة أمرًا سهلاً."

**ليس هذا**:
- "هذا الرمز خاطئ." (صريحة جدًا، لا يوجد تفسير)
- "لن أكتب الأمر بهذه الطريقة أبدًا." (يحركها الأنا)
- "قم بتغيير اسم المتغير هذا." (الدراجة على العناصر ذات الأولوية المنخفضة)

<Callout>اشرح دائمًا *السبب* وراء تعليقاتك، وليس فقط *السبب*. "هذا يجب أن يستخدم الاستعلامات ذات المعلمات" على ما يرام. "يجب أن يستخدم هذا استعلامات ذات معلمات لأن تسلسل السلسلة الحالي عرضة لهجمات حقن SQL" أفضل بكثير.</Callout>

## مثال لمراجعة التعليمات البرمجية

إليك وظيفة قد يُطلب منك مراجعتها في المقابلة:

```python
def process_orders(orders):
    results = []
    for order in orders:
        user = db.query(f"SELECT * FROM users WHERE id = {order['user_id']}")
        if user:
            total = 0
            for item in order['items']:
                price = db.query(f"SELECT price FROM products WHERE id = {item['product_id']}")
                total = total + price[0] * item['quantity']
                if item['quantity'] > 100:
                    total = total * 0.9
            if total > 0:
                results.append({'user': user, 'total': total, 'order_id': order['id']})
    return results
```

** المراجعة القوية ستحدد: **

1. 🔴 **حقن SQL** (السطر 4، 7): استيفاء السلسلة في استعلامات SQL. استخدم الاستعلامات ذات المعلمات.
2. 🔴 **مشكلة استعلام N+1** (السطر 4، 7): استعلامان في قاعدة البيانات لكل طلب، واحد لكل عنصر. بالنسبة لـ 100 طلب يحتوي كل منها على 10 عناصر، فهذا يعني 1100 استفسار. دفعة في استعلامات واحدة.
3. 🟠 **لا توجد معالجة للأخطاء**: `price[0]` سوف يتعطل إذا لم يتم العثور على المنتج. `db.query` يمكن أن تفشل.
4. 🟠 **منطق الخصم مخفي**: الخصم 10% للكمية > 100 هو قاعدة عمل مدفونة في حلقات متداخلة. استخرجه.
5. 🟡 **الرقم السحري**: `0.9` و`100` يجب تسمية الثوابت (`BULK_DISCOUNT_RATE`، `BULK_THRESHOLD`).
6. 🟡 **الوظيفة تفعل الكثير**: جلب المستخدمين، وحساب الإجماليات، وتطبيق الخصومات - ينتهك المسؤولية الفردية.

## الوجبات السريعة الرئيسية

- **استخدم أسلوبًا منظمًا**: التمريرات المتعددة (الهدف ← الصحة ← التصميم ← الأداء/الأمان) تكتشف مشكلات أكثر من المسح العشوائي.
- **تحديد الأولويات بلا رحمة**: الأخطاء الحرجة والمشكلات الأمنية أولاً، والأسلوب أخيرًا. يقوم القائمون على المقابلات بزرع كليهما لاختبار حكمك.
- **التواصل بشكل بناء**: اشرح *السبب*، واقترح البدائل، واعترف بالأنماط الجيدة التي تراها.
- **تعرف على أنماط الأخطاء الشائعة**: تظهر المراجع الفارغة، والأخطاء المتفرقة، وتسريبات الموارد، وإدخال SQL، وحالات السباق في كل مقابلة لمراجعة التعليمات البرمجية تقريبًا.
- **التدرب على قراءة التعليمات البرمجية**: اقضِ بعض الوقت في قراءة طلبات السحب مفتوحة المصدر على GitHub. تختلف مهارة قراءة التعليمات البرمجية عن كتابتها، ومعظم المهندسين لا يمارسونها بشكل كافٍ.
