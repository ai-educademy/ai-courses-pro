# API డిజైన్ ఇంటర్వ్యూలు

APIలు సిస్టమ్‌ల మధ్య ఒప్పందాలు, మరియు వాటిని చక్కగా రూపొందించడం అనేది సీనియర్ ఇంజనీర్‌లను జూనియర్‌ల నుండి వేరు చేసే నైపుణ్యం. API డిజైన్ ఇంటర్వ్యూలో, మీరు కేవలం ఎండ్‌పాయింట్‌లను మాత్రమే రాయడం లేదు — వినియోగదారులు మీ సిస్టమ్‌ను ఎలా ఉపయోగిస్తారో, కాలక్రమేణా అది ఎలా అభివృద్ధి చెందుతుంది మరియు వైఫల్య మోడ్‌లు ఎక్కడ ఉన్నాయో మీరు అర్థం చేసుకున్నారని మీరు ప్రదర్శిస్తున్నారు. మీరు చెల్లింపు గేట్‌వే లేదా సోషల్ మీడియా ప్లాట్‌ఫారమ్ APIని డిజైన్ చేయమని అడిగినా, సూత్రాలు ఒకే విధంగా ఉంటాయి. వాటిపై పట్టుసాధిద్దాం.

## REST API డిజైన్ సూత్రాలు

ఇంటర్వ్యూలలో REST ఆధిపత్య API ఉదాహరణగా మిగిలిపోయింది. మీరు తప్పనిసరిగా ప్రదర్శించాల్సిన పునాదులు:

### రిసోర్స్-ఓరియెంటెడ్ డిజైన్

నామవాచకాలలో (వనరులు) ఆలోచించండి, క్రియలు (చర్యలు) కాదు. URLలు విషయాలను సూచించాలి మరియు HTTP పద్ధతులు ఆ విషయాలపై చర్యలను సూచిస్తాయి.

```
✅ Good:
GET    /users/123              — Fetch user 123
POST   /users                  — Create a new user
PUT    /users/123              — Replace user 123
PATCH  /users/123              — Partially update user 123
DELETE /users/123              — Delete user 123

❌ Bad:
GET    /getUser?id=123
POST   /createUser
POST   /deleteUser/123
```

<Callout>క్లీన్ రిసోర్స్ హైరార్కీ API కథను చెబుతుంది. `/users/123/orders/456/items` సహజంగా చదువుతుంది: "వినియోగదారు 123 యొక్క ఆర్డర్ 456 అంశాలు." మీ URL నిర్మాణం వాక్యం వలె చదవకపోతే, మీ వనరుల రూపకల్పనను పునఃపరిశీలించండి.</Callout>

### HTTP పద్ధతులు మరియు స్థితి కోడ్‌లు

ఈ చలిని తెలుసుకోండి - ఇంటర్వ్యూ చేసేవారు మీ ఖచ్చితత్వాన్ని పరీక్షిస్తారు:

| పద్ధతి | దుర్మార్గుడా? | కేసు ఉపయోగించండి |
|---|---|---|
| పొందండి | అవును | ఒక వనరును చదవండి (ఎప్పుడూ మార్చవద్దు) |
| పోస్ట్ | కాదు | ఒక వనరు సృష్టించు |
| పెట్టు | అవును | వనరు యొక్క పూర్తి భర్తీ |
| ప్యాచ్ | కాదు* | పాక్షిక నవీకరణ |
| తొలగించు | అవును | ఒక వనరును తీసివేయండి |

*PATCH సాంకేతికంగా ఐడెమ్‌పోటెంట్‌గా హామీ ఇవ్వబడదు, అయినప్పటికీ అమలులు తరచుగా ఉంటాయి.*

**మీరు తప్పక తెలుసుకోవలసిన స్థితి కోడ్‌లు**:
- `200 OK` — రెస్పాన్స్ బాడీతో విజయం
- `201 Created` — వనరు సృష్టించబడింది (`Location` హెడర్‌తో సహా)
- `204 No Content` — ప్రతిస్పందన లేని అంశంతో విజయం (తొలగించడానికి సాధారణం)
- `400 Bad Request` — క్లయింట్ చెల్లని డేటాను పంపారు
- `401 Unauthorized` — ప్రమాణీకరణ అవసరం
- `403 Forbidden` — ప్రమాణీకరించబడింది కానీ అధికారం లేదు
- `404 Not Found` — వనరు ఉనికిలో లేదు
- `409 Conflict` — ప్రస్తుత స్థితితో వైరుధ్యం (నకిలీ, సంస్కరణ అసమతుల్యత)
- `429 Too Many Requests` — రేట్ పరిమితం
- `500 Internal Server Error` — మా వైపు ఏదో విరిగింది

### పేజినేషన్

అపరిమిత జాబితాలను ఎప్పుడూ తిరిగి ఇవ్వవద్దు. మూడు సాధారణ నమూనాలు:

```json
// Offset-based (simple but poor for large datasets)
GET /users?offset=20&limit=10

// Cursor-based (preferred for feeds and large datasets)
GET /users?cursor=eyJ0aW1lIjoiMjAyNC0wMS0wMSJ9&limit=10

// Response includes pagination metadata
{
  "data": [...],
  "pagination": {
    "next_cursor": "eyJ0aW1lIjoiMjAyNC0wMS0wMiJ9",
    "has_more": true
  }
}
```

<ThinkAboutIt>పెద్ద, తరచుగా అప్‌డేట్ చేయబడిన డేటాసెట్‌ల కోసం ఆఫ్‌సెట్-ఆధారిత కంటే కర్సర్-ఆధారిత పేజినేషన్‌కు ఎందుకు ప్రాధాన్యత ఇవ్వబడుతుంది? వినియోగదారు ఫలితాల ద్వారా పేజినేట్ చేస్తున్నప్పుడు కొత్త అంశాలు చొప్పించబడినప్పుడు ఏమి జరుగుతుందో పరిశీలించండి.</ThinkAboutIt>

### సంస్కరణ

APIలు అభివృద్ధి చెందుతాయి. మొదటి రోజు నుండి దాని కోసం డిజైన్ చేయండి.

```
// URL versioning (most common, explicit)
GET /v1/users/123
GET /v2/users/123

// Header versioning (cleaner URLs, less discoverable)
GET /users/123
Accept: application/vnd.myapi.v2+json
```

ఇంటర్వ్యూలలో, ఇంటర్వ్యూయర్ ప్రత్యేకంగా ప్రత్యామ్నాయాలను అన్వేషించనంత వరకు URL సంస్కరణ సురక్షితమైన సమాధానం.

### లోపం ప్రతిస్పందనలు

స్థిరమైన, సమాచార లోపం ప్రతిస్పందనలు గొప్ప APIలను నిరాశపరిచే వాటి నుండి వేరు చేస్తాయి:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request body contains invalid fields.",
    "details": [
      {
        "field": "email",
        "message": "Must be a valid email address."
      },
      {
        "field": "age",
        "message": "Must be a positive integer."
      }
    ],
    "request_id": "req_abc123"
  }
}
```

డీబగ్గింగ్ కోసం ఎల్లప్పుడూ `request_id` మరియు మానవులు చదవగలిగే `message`తో పాటు మెషిన్-రీడబుల్ `code`ని చేర్చండి.

## ఇంటర్వ్యూలలో GraphQL

GraphQL ప్రశ్నలు చాలా సాధారణం, ముఖ్యంగా సంక్లిష్టమైన ఫ్రంటెండ్ అవసరాలు కలిగిన కంపెనీలలో.

**ఉచ్చరించడానికి ముఖ్య ప్రయోజనాలు**:
- క్లయింట్లు తమకు అవసరమైన డేటాను ఖచ్చితంగా అభ్యర్థిస్తారు (అతిగా పొందడం లేదు)
- సింగిల్ ఎండ్ పాయింట్ రౌండ్ ట్రిప్‌లను తగ్గిస్తుంది
- గట్టిగా టైప్ చేసిన స్కీమా డాక్యుమెంటేషన్‌గా పనిచేస్తుంది

```graphql
# Schema definition
type User {
  id: ID!
  name: String!
  email: String!
  orders(first: Int, after: String): OrderConnection!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

# Query — client specifies exactly what it needs
query {
  user(id: "123") {
    name
    orders(first: 5) {
      edges {
        node {
          total
          status
        }
      }
    }
  }
}
```

** చర్చించడానికి ట్రేడ్-ఆఫ్‌లు**: GraphQL సర్వర్ వైపు సంక్లిష్టతను జోడిస్తుంది (పరిష్కార గొలుసులు, N+1 ప్రశ్నలు, కాషింగ్ కష్టం). సాధారణ CRUD APIల కోసం, REST తరచుగా ఉత్తమ ఎంపిక.

<FunFact>నిర్దిష్ట మొబైల్ పనితీరు సమస్యను పరిష్కరించడానికి 2012లో Facebookలో GraphQL అంతర్గతంగా అభివృద్ధి చేయబడింది: న్యూస్ ఫీడ్‌కు అనేక విభిన్న బ్యాకెండ్ సేవల నుండి డేటా అవసరం మరియు స్లో నెట్‌వర్క్‌లలో మొబైల్ పరికరాల నుండి బహుళ REST కాల్‌లు చేయడం పనితీరును నాశనం చేస్తోంది. ఇది 2015లో ఓపెన్ సోర్స్ చేయబడింది.</FunFact>

## API సెక్యూరిటీ బేసిక్స్

ప్రతి API డిజైన్ ఇంటర్వ్యూ భద్రతను తాకాలి. ఈ ఆవశ్యకాలను కవర్ చేయండి:

### ప్రమాణీకరణ మరియు ఆథరైజేషన్

```
Authentication (AuthN): WHO are you?
→ API Keys, OAuth 2.0, JWT tokens

Authorisation (AuthZ): WHAT can you do?
→ Role-based (RBAC), Scope-based, Resource-based
```

```
// JWT in Authorization header
GET /users/123/orders
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

// API Key (for server-to-server)
GET /analytics/reports
X-API-Key: sk_live_abc123...
```

### రేటు పరిమితి

దుర్వినియోగం నుండి మీ APIని రక్షించండి మరియు సరసమైన వినియోగాన్ని నిర్ధారించండి:

```
// Rate limit headers in response
HTTP/1.1 200 OK
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1640995200

// When limit is exceeded
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

రేట్ పరిమితం చేసే వ్యూహాలను చర్చించండి: ఒక్కో వినియోగదారు, ఒక్కో IP, ఒక్కో ముగింపు పాయింట్ మరియు వివిధ API ప్లాన్‌ల కోసం టైర్డ్ పరిమితులు.

## నిజమైన ఇంటర్వ్యూ దృశ్యాలు

### చెల్లింపు APIని రూపొందించండి

స్పష్టం చేయడానికి అవసరాలు:
- ఏ చెల్లింపు పద్ధతులు? (కార్డ్, బ్యాంక్ బదిలీ, వాలెట్)
- మనకు చిత్తశుద్ధి అవసరమా? (అవును — ఎల్లప్పుడూ చెల్లింపుల కోసం)
- వాపసు మరియు వివాదాల గురించి ఏమిటి?

```
POST /v1/payments
{
  "amount": 4999,           // Always use smallest currency unit (cents)
  "currency": "GBP",
  "payment_method": "pm_card_visa_123",
  "idempotency_key": "order_789_attempt_1",
  "metadata": {
    "order_id": "order_789"
  }
}

Response: 201 Created
{
  "id": "pay_abc123",
  "status": "processing",
  "amount": 4999,
  "currency": "GBP",
  "created_at": "2024-01-15T10:30:00Z"
}
```

<Callout>చెల్లింపు APIల కోసం, ఎల్లప్పుడూ ఐడెంపోటెన్సీ కీలను చర్చించండి. నెట్‌వర్క్ వైఫల్యాలు సంభవిస్తాయి, క్లయింట్‌లు మళ్లీ ప్రయత్నిస్తారు మరియు బలహీనత లేకుండా, మీరు కస్టమర్‌లకు రెండుసార్లు ఛార్జ్ చేస్తారు. ఐడెంపోటెన్సీ కీ అదే అభ్యర్థనను మళ్లీ ప్రయత్నించడం అదే ఫలితాన్ని ఉత్పత్తి చేస్తుందని నిర్ధారిస్తుంది.</Callout>

** చర్చించడానికి ముఖ్య డిజైన్ నిర్ణయాలు**:
- ఫ్లోటింగ్ పాయింట్ సమస్యలను నివారించడానికి అతి చిన్న కరెన్సీ యూనిట్ (సెంట్లు/పెన్స్)లో మొత్తాలు
- సురక్షితమైన పునఃప్రయత్నాల కోసం ఐడెంపోటెన్సీ కీలు
- అసమకాలీకరణ స్థితి నవీకరణల కోసం Webhook కాల్‌బ్యాక్‌లు
- PCI సమ్మతి పరిగణనలు

### సోషల్ మీడియా APIని డిజైన్ చేయండి

```
// Post creation
POST /v1/posts
{
  "content": "Hello world!",
  "media_ids": ["media_123"],
  "visibility": "public"
}

// Feed retrieval with cursor pagination
```

## API డిజైన్ ఇంటర్వ్యూలలో సాధారణ తప్పులు

1. **అంతర్గత అమలును బహిర్గతం చేయడం** — డేటాబేస్ కాలమ్ పేర్లు లేదా అంతర్గత IDలను APIలోకి లీక్ చేయనివ్వవద్దు. DTOలను ఉపయోగించండి.
2. **అస్థిరమైన నామకరణం** — `snake_case` లేదా `camelCase`ని ఎంచుకుని, ప్రతిచోటా దానికి కట్టుబడి ఉండండి.
3. **మిస్సింగ్ పేజినేషన్** — ఏదైనా లిస్ట్ ఎండ్ పాయింట్ తప్పనిసరిగా పేజినేషన్‌కు మద్దతివ్వాలి.
4. **ఎర్రర్ హ్యాండ్లింగ్ డిస్కషన్** — ఫెయిల్యూర్ మోడ్‌ల గురించి మీరు ఆలోచించినట్లు చూపండి.
5. **వెనుక అనుకూలతను విస్మరించడం** — ఇప్పటికే ఉన్న ఎండ్‌పాయింట్‌లకు అవసరమైన ఫీల్డ్‌లను జోడించడం క్లయింట్‌లను విచ్ఛిన్నం చేస్తుంది.
6. **URLలలో క్రియలను ఉపయోగించడం** — `POST /users`కి బదులుగా `/createUser`.

## కీలక టేకావేలు

- ** వనరులలో ఆలోచించండి**: నామవాచకాల చుట్టూ URLలను రూపొందించండి, HTTP పద్ధతులను క్రియలను నిర్వహించనివ్వండి.
- **మీ స్థితి కోడ్‌లను తెలుసుకోండి**: ఖచ్చితమైన స్థితి కోడ్‌లు మీరు HTTP సెమాంటిక్స్‌ను అర్థం చేసుకున్నట్లు చూపుతాయి.
- **ఎల్లప్పుడూ పేజినేట్ చేయండి**: అపరిమిత జాబితా ప్రతిస్పందనలు ఇంటర్వ్యూలలో ఎరుపు జెండా.
- **వైఫల్యం కోసం డిజైన్**: ఐడెంపోటెన్సీ, ఎర్రర్ రెస్పాన్స్ మరియు రేటు పరిమితం చేయడం ఉత్పత్తి-సన్నద్ధత ఆలోచనను చూపుతుంది.
- **భద్రత ఐచ్ఛికం కాదు**: ప్రమాణీకరణ, అధికారం మరియు రేటు పరిమితి ప్రతి API డిజైన్ చర్చలో భాగంగా ఉండాలి.
- ** ట్రేడ్-ఆఫ్‌లను ఉచ్చరించండి**: REST వర్సెస్ GraphQL, స్థిరత్వం వర్సెస్ వశ్యత, సరళత వర్సెస్ శక్తి — ఇంటర్వ్యూ చేసేవారు మీ వాదనను వినాలనుకుంటున్నారు.
