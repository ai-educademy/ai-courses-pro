# సిస్టమ్ డిజైన్ ఫండమెంటల్స్

సిస్టమ్ డిజైన్ ఇంటర్వ్యూ అనేది సీనియర్ ఇంజనీర్‌లను తయారు చేయడం లేదా విచ్ఛిన్నం చేయడం. స్పష్టమైన సరైన సమాధానాలతో కోడింగ్ ఇంటర్వ్యూలకు భిన్నంగా, సిస్టమ్ డిజైన్ అస్పష్టతను నావిగేట్ చేయడానికి, ట్రేడ్-ఆఫ్‌లను చేయడానికి మరియు నిర్మాణ నిర్ణయాలను కమ్యూనికేట్ చేయడానికి మీ సామర్థ్యాన్ని పరీక్షిస్తుంది. శుభవార్త? ప్రతి ప్రశ్నకు పని చేసే పునరావృత ఫ్రేమ్‌వర్క్ ఉంది. గొప్ప వార్త? మీరు బిల్డింగ్ బ్లాక్‌లను అర్థం చేసుకున్న తర్వాత, మీరు URL షార్ట్‌నర్ నుండి గ్లోబల్-స్కేల్ మెసేజింగ్ ప్లాట్‌ఫారమ్ వరకు దేనినైనా డిజైన్ చేయవచ్చు. ఆ టూల్‌కిట్‌ను తయారు చేద్దాం.

## 4-దశల ఫ్రేమ్‌వర్క్

ప్రతి సిస్టమ్ డిజైన్ ఇంటర్వ్యూ ఈ నిర్మాణాన్ని అనుసరించాలి. ఇంటర్వ్యూ చేసేవారు దీనిని ఆశించారు మరియు ఇది మిమ్మల్ని అకాల వివరాలలోకి రాకుండా చేస్తుంది.

### దశ 1: అవసరాల స్పష్టీకరణ (5 నిమిషాలు)

ప్రశ్నలు అడగకుండా డిజైన్ చేయడం ప్రారంభించవద్దు. ఇక్కడే మీరు ఉత్పత్తి ఆలోచనను ప్రదర్శిస్తారు.

**ఫంక్షనల్ అవసరాలు** — సిస్టమ్ ఏమి చేస్తుంది:
- "వినియోగదారులు సమూహాలకు సందేశాలను పంపగలరా లేదా కేవలం 1:1?"
- "మాకు నిజ-సమయ నోటిఫికేషన్‌లు అవసరమా?"
- "ఫీడ్ కాలక్రమానుసారంగా ఉండాలా లేదా ర్యాంక్ చేయబడాలా?"

** నాన్-ఫంక్షనల్ అవసరాలు** — ఇది ఎంత బాగా చేస్తుంది:
- "అంచనా రీడ్/రైట్ నిష్పత్తి ఎంత?"
- "ఏ జాప్యం ఆమోదయోగ్యమైనది?"
- "మనకు బలమైన అనుగుణ్యత అవసరమా లేదా చివరికి స్థిరత్వం సరేనా?"

<Callout>స్పష్టమైన ప్రశ్నలు అడగడం బలహీనతకు సంకేతం కాదు - ఇది మీరు చేయగలిగే అత్యంత సీనియర్ ఇంజనీర్ పని. మీరు స్పష్టం చేస్తారా లేదా గుడ్డిగా డిజైన్ చేయడం ప్రారంభిస్తారా అని చూడటానికి ఇంటర్వ్యూలు ఉద్దేశపూర్వకంగా అవసరాలను అస్పష్టంగా ఉంచారు.</Callout>

### దశ 2: బ్యాక్-ఆఫ్-ఎన్వలప్ అంచనా (3 నిమిషాలు)

త్వరిత గణితం మీ డిజైన్‌ను వాస్తవంగా ఆధారం చేస్తుంది మరియు ఇంజినీరింగ్‌లో ఎక్కువ లేదా తక్కువ చేయడాన్ని నిరోధిస్తుంది.

```
Example: Design Twitter

Daily Active Users (DAU): 300M
Tweets per day: 300M × 2 = 600M tweets/day
Reads per day: 300M × 100 = 30B reads/day (read-heavy)
Tweets per second: 600M / 86400 ≈ 7,000 writes/sec
Reads per second: 30B / 86400 ≈ 350,000 reads/sec
Storage per tweet: ~300 bytes text + metadata ≈ 500 bytes
Daily storage: 600M × 500B = 300GB/day ≈ 110TB/year
```

ఈ సంఖ్యలు మీకు తెలియజేస్తాయి: ఈ సిస్టమ్ చాలా రీడ్-హెవీగా ఉంది, కాషింగ్ అవసరం మరియు భారీ నిల్వను కూడగట్టుకుంటుంది.

### దశ 3: ఉన్నత-స్థాయి డిజైన్ (10 నిమిషాలు)

ప్రధాన భాగాలతో నిర్మాణాన్ని గీయండి. సరళంగా ప్రారంభించండి, ఆపై అవసరమైన విధంగా సంక్లిష్టతను జోడించండి.

```
Client → Load Balancer → API Servers → Service Layer
                                          ↓
                              ┌───────────┼───────────┐
                              ↓           ↓           ↓
                           Database     Cache      Message Queue
                                          ↓           ↓
                                       CDN        Workers
```

ప్రధాన వినియోగదారు ప్రవాహాల ద్వారా నడవండి:
- "ఒక వినియోగదారు ట్వీట్‌ను పోస్ట్ చేసినప్పుడు, API సర్వర్ దానిని ధృవీకరిస్తుంది, డేటాబేస్‌కు వ్రాస్తుంది మరియు ఫ్యాన్-అవుట్ సేవకు పుష్ చేస్తుంది..."
- "ఒక వినియోగదారు వారి ఫీడ్‌ని తెరిచినప్పుడు, మేము ముందుగా కాష్‌ని తనిఖీ చేస్తాము..."

### దశ 4: డీప్ డైవ్ (15 నిమిషాలు)

ఇంటర్వ్యూయర్ లోతుగా వెళ్లడానికి 1-2 ప్రాంతాలను ఎంచుకుంటారు. ట్రేడ్-ఆఫ్‌లను వివరంగా చర్చించడానికి సిద్ధంగా ఉండండి.

<ThinkAboutIt>మీరు నోటిఫికేషన్ సిస్టమ్‌ను రూపొందిస్తుంటే, మీరు వెంటనే ఫాలోయర్‌లందరికీ నోటిఫికేషన్‌లను పంపిస్తారా (వ్రాయడంలో ఫ్యాన్-అవుట్) లేదా ప్రతి వినియోగదారు అభ్యర్థించినప్పుడు (అభిమానిని చదవడం) ఫీడ్‌ను గణిస్తారా? లక్షలాది మంది అనుచరులు ఉన్న వినియోగదారులకు ట్రేడ్-ఆఫ్‌లు ఏమిటి?</ThinkAboutIt>

## బిల్డింగ్ బ్లాక్స్

వీటిని లెగో ముక్కలుగా భావించండి. ప్రతి సిస్టమ్ డిజైన్ అదే బ్లాక్‌ల యొక్క విభిన్న అమరిక.

### లోడ్ బ్యాలెన్సర్లు

బహుళ సర్వర్‌లలో ట్రాఫిక్‌ని పంపిణీ చేయండి. మూడు వ్యూహాలను తెలుసుకోండి:
- **రౌండ్ రాబిన్** — సాధారణ, సమాన పంపిణీ
- **తక్కువ కనెక్షన్‌లు** — తక్కువ సక్రియ కనెక్షన్‌లతో సర్వర్‌కు పంపుతుంది
- ** స్థిరమైన హాషింగ్** — అభ్యర్థన కంటెంట్ ఆధారంగా మార్గాలు (కాషింగ్ కోసం ఉపయోగపడతాయి)

### కాష్‌లు

అత్యంత ప్రభావవంతమైన ఏకైక పనితీరు ఆప్టిమైజేషన్. ఈ కాష్ నమూనాలను గుర్తుంచుకో:

```
Write-through:  App → Cache → DB  (consistent, higher write latency)
Write-back:     App → Cache ... → DB  (fast writes, risk of data loss)
Cache-aside:    App checks cache → miss → read DB → populate cache
```

**కాష్ తొలగింపు**: LRU (తక్కువ ఇటీవల ఉపయోగించబడింది) అనేది ఇంటర్వ్యూలలో డిఫాల్ట్ సమాధానం. సమయ-సెన్సిటివ్ డేటా కోసం TTL (టైమ్-టు-లైవ్)ని పేర్కొనండి.

<FunFact>జెఫ్ డీన్ యొక్క ప్రసిద్ధ పత్రం ప్రకారం, మెమరీకి బదులుగా డిస్క్‌కి వెళ్ళే ఒక కాష్ మిస్ 100x జాప్యాన్ని జోడిస్తుంది. అందుకే కాషింగ్ వ్యూహం తరచుగా అత్యంత ప్రభావవంతమైన డిజైన్ నిర్ణయం - కాష్ నుండి చదవడం (1ms) వర్సెస్ డిస్క్ నుండి రీడింగ్ (10ms) వర్సెస్ క్రాస్-డేటాసెంటర్ రీడ్ (150ms) అనేది మాగ్నిట్యూడ్ యొక్క విభిన్న ఆర్డర్‌లు.</FunFact>

### డేటాబేస్‌లు

| రకం | ఎప్పుడు ఉపయోగించండి | ఉదాహరణలు |
|---|---|---|
| **రిలేషనల్ (SQL)** | ACID లావాదేవీలు, సంక్లిష్ట ప్రశ్నలు, నిర్మాణాత్మక డేటా | PostgreSQL, MySQL |
| **పత్రాల దుకాణం** | సౌకర్యవంతమైన స్కీమాలు, సమూహ డేటా, వేగవంతమైన పునరావృతం | MongoDB, DynamoDB |
| **వైడ్-కాలమ్** | భారీ స్కేల్, టైమ్-సిరీస్, రైట్-హెవీ | కాసాండ్రా, HBase |
| **గ్రాఫ్** | సంబంధం-భారీ డేటా, సోషల్ నెట్‌వర్క్‌లు | Neo4j, నెప్ట్యూన్ |

**డేటాబేస్ స్కేలింగ్**:
- **వర్టికల్ స్కేలింగ్**: పెద్ద యంత్రం (పరిమిత సీలింగ్)
- ** ప్రతిరూపాలను చదవండి**: వేరుగా చదవడం మరియు వ్రాయడం ట్రాఫిక్
- **షార్డింగ్**: బహుళ డేటాబేస్‌లలోని విభజన డేటా (యూజర్ ID, భౌగోళిక శాస్త్రం మొదలైనవి)

### సందేశ క్యూలు

వినియోగదారుల నుండి ఉత్పత్తిదారులను విడదీయండి. దీనికి అవసరం:
- అసమకాలిక ప్రాసెసింగ్ (సైన్అప్ తర్వాత ఇమెయిల్ పంపండి)
- లోడ్ లెవలింగ్ (ట్రాఫిక్ స్పైక్‌లను గ్రహించడం)
- ఈవెంట్ ఆధారిత నిర్మాణాలు

```
Producer → [Message Queue] → Consumer
           (Kafka, SQS,      (Workers that
            RabbitMQ)          process at
                               their own pace)
```

### CDNలు (కంటెంట్ డెలివరీ నెట్‌వర్క్‌లు)

వినియోగదారులకు దగ్గరగా ఉండే ఎడ్జ్ సర్వర్‌ల వద్ద స్టాటిక్ కంటెంట్ (చిత్రాలు, CSS, JS) కాష్ చేయండి. సిస్టమ్ మీడియాను అందించినప్పుడు లేదా గ్లోబల్ యూజర్ బేస్ కలిగి ఉన్నప్పుడల్లా CDNలను పేర్కొనండి.

## క్లాసిక్ సిస్టమ్ డిజైన్ ప్రశ్నలు

### URL షార్ట్‌నర్‌ని డిజైన్ చేయండి (ఉదా., బిట్.ly)

**ముఖ్య నిర్ణయాలు**:
- బేస్62 ఎన్‌కోడింగ్ (a-z, A-Z, 0-9) ఉపయోగించి షార్ట్ కోడ్‌లను రూపొందించండి
- ప్రత్యేకత కోసం కౌంటర్ లేదా హాష్ ఆధారిత విధానాన్ని ఉపయోగించండి
- రీడ్-హెవీ → జనాదరణ పొందిన URLలను దూకుడుగా కాష్ చేయండి
- డేటాబేస్: సాధారణ కీ-విలువ స్టోర్ (షార్ట్_కోడ్ → అసలు_url)

```
POST /shorten  { "url": "https://example.com/very/long/path" }
→ Returns: { "short_url": "https://bit.ly/abc123" }

GET /abc123
→ 301 Redirect to original URL (301 = permanent, cacheable by browser)
```

## కీలక టేకావేలు

- **4-దశల ఫ్రేమ్‌వర్క్‌ను అనుసరించండి**: అవసరాలు → అంచనా → హై-లెవల్ డిజైన్ → డీప్ డైవ్. ఇది ప్రతిసారీ పనిచేస్తుంది.
- **మీ బిల్డింగ్ బ్లాక్‌లను తెలుసుకోండి**: లోడ్ బ్యాలెన్సర్‌లు, కాష్‌లు, డేటాబేస్‌లు, మెసేజ్ క్యూలు మరియు CDNలు సిస్టమ్ డిజైన్ యొక్క పదజాలం.

- **అంచనా మీ డిజైన్‌ను ఆధారం చేస్తుంది**: శీఘ్ర బ్యాక్-ఆఫ్-ఎన్వలప్ గణితం మిమ్మల్ని ఓవర్-ఇంజనీరింగ్ లేదా అండర్-ఇంజనీరింగ్ నుండి నిరోధిస్తుంది.
