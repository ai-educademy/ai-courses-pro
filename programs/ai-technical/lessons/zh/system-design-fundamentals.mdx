# 系统设计基础

系统设计面试是高级工程师成败的关键。与具有明确正确答案的编码面试不同，系统设计测试您处理歧义、做出权衡和传达架构决策的能力。好消息？有一个适用于每个问题的可重复框架。好消息？一旦了解了构建块，您就可以设计从 URL 缩短器到全球范围的消息传递平台的任何内容。让我们构建该工具包。

## 四步框架

每次系统设计面试都应该遵循这个结构。面试官对此抱有期望，这可以防止你陷入过早的细节中。

### 第 1 步：澄清需求（5 分钟）

永远不要在没有提出问题的情况下开始设计。这是您展示产品思维的地方。

**功能要求** — 系统的功能：
- “用户应该能够向群组发送消息，还是只能一对一发送消息？”
- “我们需要实时通知吗？”
- “提要应该按时间顺序还是排名？”

**非功能性需求**——它的表现如何：
- “预期的读/写比率是多少？”
- “什么延迟是可以接受的？”
- “我们需要强一致性还是最终一致性可以？”

<Callout>提出澄清问题并不是软弱的表现——这是你能做的最高级工程师的事情。面试官故意把需求说得含糊不清，看你是否会澄清或盲目地开始设计。</Callout>

### 第 2 步：粗略估计（3 分钟）

快速数学使您的设计符合现实，并防止设计过度或不足。

```
Example: Design Twitter

Daily Active Users (DAU): 300M
Tweets per day: 300M × 2 = 600M tweets/day
Reads per day: 300M × 100 = 30B reads/day (read-heavy)
Tweets per second: 600M / 86400 ≈ 7,000 writes/sec
Reads per second: 30B / 86400 ≈ 350,000 reads/sec
Storage per tweet: ~300 bytes text + metadata ≈ 500 bytes
Daily storage: 600M × 500B = 300GB/day ≈ 110TB/year
```

这些数字告诉您：这个系统的读取量非常大，需要缓存，并且会积累大量存储。

### 第 3 步：高级设计（10 分钟）

绘制包含主要组件的架构。从简单开始，然后根据需要增加复杂性。

```
Client → Load Balancer → API Servers → Service Layer
                                          ↓
                              ┌───────────┼───────────┐
                              ↓           ↓           ↓
                           Database     Cache      Message Queue
                                          ↓           ↓
                                       CDN        Workers
```

浏览主要用户流程：
- “当用户发布推文时，API 服务器会验证它，写入数据库，然后推送到扇出服务......”
- “当用户打开他们的提要时，我们首先检查缓存......”

### 第 4 步：深入探讨（15 分钟）

面试官会选择1-2个领域进行深入探讨。准备好详细讨论权衡。

<ThinkAboutIt>如果您正在设计一个通知系统，您会立即向所有关注者推送通知（写入时扇出）还是在每个用户请求时计算提要（读取时扇出）？对于拥有数百万粉丝的用户来说，权衡是什么？</ThinkAboutIt>

## 构建模块

将这些视为乐高积木。每个系统设计都是相同模块的不同排列。

### 负载均衡器

跨多个服务器分配流量。了解三个策略：
- **循环** — 简单、均等的分配
- **最少连接** — 发送到活动连接最少的服务器
- **一致散列** — 基于请求内容的路由（对于缓存有用）

### 缓存

最具影响力的性能优化。记住这些缓存模式：

```
Write-through:  App → Cache → DB  (consistent, higher write latency)
Write-back:     App → Cache ... → DB  (fast writes, risk of data loss)
Cache-aside:    App checks cache → miss → read DB → populate cache
```

**缓存驱逐**：LRU（最近最少使用）是面试中的默认答案。对于时间敏感的数据，请提及 TTL（生存时间）。

<FunFact>根据 Jeff Dean 的一篇著名论文，进入磁盘而不是内存的单个缓存未命中会增加大约 100 倍的延迟。这就是为什么缓存策略通常是最有影响力的设计决策——从缓存读取（1ms）与从磁盘读取（10ms）与跨数据中心读取（150ms）是不同的数量级。</FunFact>

### 数据库

|类型 |使用时间 |示例 |
|---|---|---|
| **关系 (SQL)** | ACID 事务、复杂查询、结构化数据 | PostgreSQL、MySQL |
| **文件存储** |灵活的模式、嵌套的数据、快速迭代 | MongoDB、DynamoDB |
| **宽柱** |大规模、时间序列、写入量大 |卡桑德拉、HBase |
| **图表** |关系型数据、社交网络 | Neo4j、海王星 |

**数据库扩展**：
- **垂直缩放**：更大的机器（上限有限）
- **只读副本**：分离读写流量
- **分片**：跨多个数据库对数据进行分区（按用户 ID、地理位置等）

### 消息队列

将生产者与消费者脱钩。必不可少：
- 异步处理（注册后发送电子邮件）
- 负载均衡（吸收流量峰值）
- 事件驱动架构

```
Producer → [Message Queue] → Consumer
           (Kafka, SQS,      (Workers that
            RabbitMQ)          process at
                               their own pace)
```

### CDN（内容交付网络）

在靠近用户的边缘服务器缓存静态内容（图像、CSS、JS）。当系统提供媒体服务或拥有全球用户群时，请提及 CDN。

## 经典系统设计问题

### 设计一个 URL 缩短器（例如 bit.ly）

**关键决定**：
- 使用base62编码生成短代码（a-z、A-Z、0-9）
- 使用计数器或基于哈希的方法来确保唯一性
- 大量读取 → 积极缓存流行的 URL
- 数据库：简单的键值存储（short_code→original_url）

```
POST /shorten  { "url": "https://example.com/very/long/path" }
→ Returns: { "short_url": "https://bit.ly/abc123" }

GET /abc123
→ 301 Redirect to original URL (301 = permanent, cacheable by browser)
```

### 设计一个聊天系统（例如 WhatsApp）

**关键决定**：
- 用于实时双向通信的WebSockets
- 消息存储：写优化数据库（Cassandra）
- 在线状态：带超时的心跳机制
- 群组消息：通过消息队列扇出到所有群组成员

### 设计新闻源（例如 Twitter/Facebook）

**关键决定**：
- **写入时扇出**，适用于关注者数 < 10K 的用户（预计算提要）
- **名人用户的读取时扇出**（根据请求计算以避免写入数百万个提要）
- 混合方法：大多数系统都使用这两种策略
- 排名：基于机器学习的相关性评分，而不是纯粹的时间顺序

## 处理估算问题

面试官喜欢问“Y 需要多少 X？”使用这些锚点：

|公制|价值|
|---|---|
|单个Web服务器的QPS | 〜1,000-10,000 |
|单库QPS | 〜1,000-5,000 |
|缓存读取延迟| 〜1毫秒|
|数据库读取延迟| 〜5-10ms |
|跨数据中心延迟 | 〜100-150ms |
| 100万秒| ~12 天 |
| 10 亿秒 | ~32 岁 |

## 系统设计期间的沟通技巧

您的沟通与您的设计一样重要。练习这些习惯：

1. **构建你的想法**：“让我从需求开始，然后是估计，然后是高层设计。”
2. **明确地说明权衡**：“我们可以使用 SQL 来实现一致性，也可以使用 NoSQL 来实现扩展。考虑到我们的读取工作量很大，我倾向于使用带有缓存层的 NoSQL。”
3. **承认你不知道的事情**：“我不确定 Kafka 的确切复制因子，但我知道它是可配置的，通常设置为 3。”
4. **与面试官交流**：“我已经介绍了高层设计。您希望我深入研究数据库模式或缓存策略吗？”

<Callout>系统设计面试中最大的错误是太深入太早。抵制在前 5 分钟内设计数据库架构的冲动。从广泛开始，然后根据面试官想要探索的内容缩小范围。</Callout>

## 要点

- **遵循 4 步框架**：需求 → 估算 → 高层设计 → 深入研究。每次都有效。
- **了解您的构建块**：负载均衡器、缓存、数据库、消息队列和 CDN 是系统设计的词汇。
- **权衡才是重点**：没有完美的设计——只有权衡。清楚地表达它们。
- **估算为您的设计奠定基础**：快速的粗略数学可防止您过度设计或设计不足。
- **沟通是成绩的一半**：构建你的想法，陈述假设，并定期与面试官核实。
- **使用真实系统进行练习**：研究 Twitter、WhatsApp、YouTube 和 Uber 的实际工作原理。他们的工程博客是金矿。
