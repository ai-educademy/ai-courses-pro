# Live Coding की Best Practices

आप LeetCode mediums नींद में solve कर सकते हैं, लेकिन screen share के दूसरे छोर पर इंसान बैठते ही आपकी उंगलियाँ semicolons भूल जाती हैं। Live coding interviews एक performance हैं। इसमें final code ही नहीं, वहाँ तक पहुँचने का तरीका भी judge होता है। जो candidates pass करते हैं, वे हमेशा सबसे तेज़ coders नहीं होते। वे वे लोग होते हैं जो साफ़ communicate करते हैं, setbacks को संभालते हैं, और pressure में भी readable code लिखते हैं। यह पाठ आपको वही candidate बनना सिखाता है।

## अपना Environment Setup करना

First impressions matter करते हैं। जब आप CoderPad, HackerRank या VS Code Live Share खोलते हैं, interviewer पहले से opinions बना रहा होता है।

### Platform-Specific Tips

**CoderPad** (सबसे common):
- Interview शुरू होने से पहले dropdown से अपनी language चुनें
- Built-in Run button इस्तेमाल करें। जानें कि output console pane में आता है
- Auto-indent और syntax highlighting available हैं

**HackerRank**:
- Problem statement ध्यान से पढ़ें। Inputs stdin से आते हैं
- Test cases automatically run होते हैं। Expected format समझें
- Custom test cases left panel में add किए जा सकते हैं

**VS Code Live Share / Google Docs**:
- Auto-complete या syntax highlighting शायद न हो
- हाथ से consistent indent करें। यह discipline दिखाता है
- Google Docs के लिए monospace font (Courier New) इस्तेमाल करें

<Callout>किसी भी live coding interview से पहले 5-minute environment check करें। Platform खोलें, "Hello World" लिखें, और run करें। Interview के दौरान platform से जूझना precious minutes बर्बाद करता है और confidence हिला देता है।</Callout>

### Language Choice

वह language चुनें जिसमें आप सबसे fluent हैं, वह नहीं जो आपको impressive लगती है। फिर भी, इन बातों पर विचार करें:

| Language | Pros | Cons |
|---|---|---|
| **Python** | Concise, rich standard library, fast to write | Slower runtime, type ambiguity |
| **Java** | Strong typing, interviewers expect it for system design | Verbose, boilerplate |
| **JavaScript** | Good for frontend roles, flexible | Quirky type coercion, less common for algorithms |
| **C++** | Fast runtime, shows low-level skills | Error-prone, verbose STL |

## Talk-Aloud Protocol

यह सबसे impact वाला interview skill है, और वही जिसे अधिकतर candidates neglect करते हैं। आपका inner monologue outer monologue बनना चाहिए।

### हर Stage पर क्या कहें

**Problem पढ़ते समय** (minutes 0-3):
- "मैं पहले confirm कर लूँ कि problem समझी है: हमें find करना है..."
- "कुछ clarifying questions: क्या input empty हो सकता है? क्या negative numbers हो सकते हैं?"
- "मैं अपनी understanding verify करने के लिए कुछ examples सोचता हूँ।"

**Approach plan करते समय** (minutes 3-7):
- "मेरा पहला विचार nested loops वाला brute-force approach है। वह O(n²) होगा।"
- "मुझे लगता है कि seen elements track करने के लिए hash map से बेहतर कर सकते हैं।"
- "मैं edge cases सोचता हूँ: empty input, single element, all duplicates..."

**Code लिखते समय** (minutes 7-25):
- "मैं function signature और edge cases से start करूँगा।"
- "अब मैं array iterate कर रहा हूँ, और हर element के लिए check कर रहा हूँ..."
- "मैं यहाँ hash map चुन रहा हूँ क्योंकि हमें O(1) lookups चाहिए।"

**Testing** (minutes 25-30):
- "मैं example trace करता हूँ: input [2, 7, 11, 15] with target 9..."
- "Empty array edge case भी check करना चाहिए..."
- "Hmm, इस case के लिए output match नहीं कर रहा। मैं line 5 देखता हूँ..."

<ThinkAboutIt>पिछली बार जब आपने कोई problem silently solve की थी, आपका internal decision process क्या था? आप उन micro-decisions को बाहरी रूप से कैसे बोलेंगे? अकेले problems solve करते समय भी अपनी thinking verbalise करें। Interview में यह natural हो जाता है।</ThinkAboutIt>

## Pressure में Clean Code लिखना

Stress में code quality सबसे पहले गिरती है। Deliberate habits से इसे रोकें:

### Meaningful Names इस्तेमाल करें

```python
# Under pressure (what many candidates write)
def solve(a, t):
    d = {}
    for i, v in enumerate(a):
        if t - v in d:
            return [d[t - v], i]
        d[v] = i

# What you should write
def two_sum(nums, target):
    seen = {}
    for index, num in enumerate(nums):
        complement = target - num
        if complement in seen:
            return [seen[complement], index]
        seen[num] = index
```

दूसरा version लिखने में 10 extra seconds लगते हैं, लेकिन debugging 10x आसान हो जाती है, और interviewer पर अच्छा असर पड़ता है।

### Skeleton से Start करें

Logic भरने से पहले structure लिखें:

```python
def merge_intervals(intervals):
    # Edge case
    if not intervals:
        return []

    # Sort by start time
    intervals.sort(key=lambda x: x[0])

    # Merge overlapping intervals
    merged = [intervals[0]]
    for current in intervals[1:]:
        # TODO: merge logic
        pass

    return merged
```

यह implementation से पहले interviewer को आपका plan दिखाता है। इसका मतलब यह भी है कि अगर time खत्म हो जाए, तो भी उन्हें सही high-level approach दिखती है।

### Helper Functions आपके साथी हैं

```python
# Extract reusable logic into named functions
def is_valid_move(board, row, col):
    return 0 <= row < len(board) and 0 <= col < len(board[0])

def get_neighbours(row, col):
    return [(row + dr, col + dc) for dr, dc in [(0, 1), (0, -1), (1, 0), (-1, 0)]]
```

Helper functions cognitive load घटाते हैं, code self-documenting बनाते हैं, और आपको कहने देते हैं: "मैं इस helper को बाद में implement करूँगा। अभी मान लें कि यह काम करता है।"

<FunFact>Pair programming पर studies (जिसे live coding interviews simulate करते हैं) बताती हैं कि pairs solo programmers की तुलना में 15% fewer defects वाला code produce करते हैं, लेकिन लगभग 15% अधिक time लेते हैं। Interview में interviewer के साथ "pair" dynamic आपके पक्ष में काम कर सकता है, अगर आप openly communicate करें।</FunFact>

## Hints को Gracefully Handle करना

Interviewers hints देते हैं। यह failure का sign नहीं है। यह conversation है। आपका response मायने रखता है:

**Hints पर अच्छे responses**:
- "यह point useful है। लगता है आप यहाँ stack इस्तेमाल करने की ओर इशारा कर रहे हैं। मैं सोचता हूँ कि यह कैसे help करेगा..."
- "समझ आया। अगर मैं input पहले sort करूँ, तो two-pointer approach possible हो जाता है। मैं restructure करता हूँ।"
- "मैंने वह edge case consider नहीं किया था। मैं negative numbers के लिए handling add करता हूँ।"

**खराब responses**:
- Hint ignore करके अपने approach पर चलते रहना
- "मुझे पता है, मैं वही करने वाला था" (defensive)
- Defeated या flustered दिखना

<Callout>Hint देने वाला interviewer आपको सफल होने में मदद कर रहा है। कई candidates multiple hints के बाद भी hire होते हैं। मायने यह रखता है कि आप hint लेते हैं, adapt करते हैं, और collaboration दिखाते हैं। Hint के बाद भी failing approach पर अड़े रहना red flag है।</Callout>

## Time Management: 35-Minute Plan

Typical 35-minute coding problem के लिए:

| Phase | Minutes | What To Do |
|---|---|---|
| **Clarify** | 0-5 | Problem पढ़ें, questions पूछें, examples लिखें |
| **Plan** | 5-8 | Approach और complexity discuss करें, interviewer buy-in लें |
| **Code** | 8-25 | Talk-aloud के साथ clean, readable code लिखें |
| **Test** | 25-30 | Examples manually trace करें, edge cases check करें |
| **Optimise** | 30-35 | Possible improvements और alternative approaches discuss करें |

### Common Timing Mistakes

1. **Plan के बिना 15 मिनट coding करना**: अंत में rewrite करना पड़ता है
2. **कभी test न करना**: submit करके "I think it works" कहना red flag है
3. **Working solution से पहले optimise करना**: पहले solve करें, फिर improve करें
4. **एक approach पर बहुत देर टिके रहना**: अगर 10 मिनट में काम नहीं कर रहा, interviewer से पूछें कि क्या better direction है

## "Done" कहने से पहले Solution Test करना

Testing के बिना कभी "done" न कहें। यह systematic approach इस्तेमाल करें:

```python
# Step 1: Trace through the provided example
# Input: [1, 2, 3, 4, 5], target = 9
# i=0: complement=9-1=8, not in seen, seen={1:0}
# i=1: complement=9-2=7, not in seen, seen={1:0, 2:1}
# ...
# i=3: complement=9-4=5, not in seen, seen={1:0, 2:1, 3:2, 4:3}
# i=4: complement=9-5=4, 4 IS in seen at index 3 → return [3, 4] ✓

# Step 2: Test edge cases
# Empty array: [] → should return [] or None
# Single element: [5], target=5 → no pair possible
# Negative numbers: [-1, 2, 3], target=1 → [-1, 2] at indices [0, 1]
# Duplicates: [3, 3], target=6 → should return [0, 1]
```

इस testing process को verbalise करें। यह thoroughness दिखाता है और bugs interviewer से पहले पकड़ता है।

## जब आप अटक जाएँ तो क्या करें

अटकना failure नहीं है। चुपचाप अटके रहना failure है। यह escape plan रखें:

1. **Problem restate करें**: कई बार aloud बोलने से नया angle दिखता है
2. **Small example पर काम करें**: tiny case manually solve करने से algorithm दिख सकता है
3. **Related problems सोचें**: "यह sliding window pattern जैसा लग रहा है..."
4. **Constraints देखें**: अगर n ≤ 1000 है, तो O(n²) solution acceptable हो सकता है
5. **Problem simplify करें**: पहले simpler version solve करें, फिर complexity जोड़ें
6. **Hint माँगें**: "मैं frequencies track करने के लिए hash map सोच रहा हूँ, लेकिन window shrinking handle करने में sure नहीं हूँ। क्या आप direction दे सकते हैं?"

```python
# When stuck, try the "brute force first" strategy:
# 1. Write the O(n²) solution — it's usually straightforward
# 2. Identify the bottleneck (usually the inner loop)
# 3. Ask: "Can I eliminate this inner loop with a data structure?"
# 4. This often leads naturally to the optimal solution
```

## Post-Solution Discussion

Solution काम करने के बाद interview खत्म नहीं होता। इनके लिए ready रहें:

- **"Time और space complexity क्या है?"**: यह हमेशा तैयार रखें
- **"क्या आप इसे optimise कर सकते हैं?"**: अगर implement न कर सकें, तब भी trade-offs discuss करें
- **"यह edge cases कैसे handle करेगा?"**: दिखाएँ कि आपने production scenarios सोचे हैं
- **"अगर input 1 billion elements हो तो?"**: यह system design thinking की ओर pivot करता है

```python
# Example post-solution discussion:
# "My solution is O(n) time and O(n) space.
#  The space is used by the hash map which stores at most n elements.
#  If memory is a constraint, we could sort the array first and use
#  two pointers for O(n log n) time and O(1) space — but we'd need
#  to modify the input array or create a copy.
#  For 1 billion elements, we might need to partition the data
#  and process in chunks, or use external sorting."
```

## मुख्य बातें

- **लगातार सोचकर बोलें**: start से finish तक problem-solving process narrate करें। Silence आपका enemy है।
- **Coding से पहले clarify करें**: 5 मिनट के questions गलत direction में 15 मिनट बचाते हैं।
- **Pressure में भी clean code लिखें**: meaningful names, helper functions और skeleton-first approach debugging आसान बनाते हैं और interviewers को प्रभावित करते हैं।
- **Systematically test करें**: "done" कहने से पहले examples और edge cases trace करें।
- **Hints और setbacks gracefully handle करें**: अटकना normal है। आप recover कैसे करते हैं, यही मायने रखता है।
- **Time manage करें**: plan (5min) → code (17min) → test (5min) → discuss (5min)। Problem के हिसाब से adjust करें, लेकिन testing कभी skip न करें।
