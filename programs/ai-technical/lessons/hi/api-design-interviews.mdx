# एपीआई डिज़ाइन साक्षात्कार

एपीआई सिस्टम के बीच अनुबंध हैं, और उन्हें अच्छी तरह से डिजाइन करना एक कौशल है जो वरिष्ठ इंजीनियरों को जूनियर से अलग करता है। एपीआई डिज़ाइन साक्षात्कार में, आप केवल समापन बिंदु नहीं लिख रहे हैं - आप यह प्रदर्शित कर रहे हैं कि आप समझते हैं कि उपभोक्ता आपके सिस्टम का उपयोग कैसे करेंगे, यह समय के साथ कैसे विकसित होगा, और विफलता मोड कहां हैं। चाहे आपसे पेमेंट गेटवे या सोशल मीडिया प्लेटफ़ॉर्म एपीआई डिज़ाइन करने के लिए कहा जाए, सिद्धांत समान हैं। आइए उन पर महारत हासिल करें।

## रेस्ट एपीआई डिज़ाइन सिद्धांत

साक्षात्कारों में REST प्रमुख API प्रतिमान बना हुआ है। आपको जिन आधारों का प्रदर्शन करना होगा:

### संसाधन-उन्मुख डिज़ाइन

संज्ञा (संसाधन) में सोचें, क्रिया (क्रिया) में नहीं। यूआरएल को चीजों का प्रतिनिधित्व करना चाहिए, और HTTP तरीकों को उन चीजों पर कार्रवाई का प्रतिनिधित्व करना चाहिए।

```
✅ Good:
GET    /users/123              — Fetch user 123
POST   /users                  — Create a new user
PUT    /users/123              — Replace user 123
PATCH  /users/123              — Partially update user 123
DELETE /users/123              — Delete user 123

❌ Bad:
GET    /getUser?id=123
POST   /createUser
POST   /deleteUser/123
```

<Callout>एक स्वच्छ संसाधन पदानुक्रम एपीआई की कहानी बताता है। `/users/123/orders/456/items` स्वाभाविक रूप से पढ़ता है: "उपयोगकर्ता 123 का ऑर्डर 456 का आइटम।" यदि आपकी यूआरएल संरचना एक वाक्य की तरह नहीं पढ़ती है, तो अपने संसाधन डिज़ाइन पर पुनर्विचार करें।</Callout>

### HTTP तरीके और स्थिति कोड

इन बातों को जानें - साक्षात्कारकर्ता आपकी सटीकता का परीक्षण करेंगे:

| विधि | नपुंसक? | केस का प्रयोग करें |
|---|---|---|
| प्राप्त करें | हाँ | एक संसाधन पढ़ें (कभी भी परिवर्तन न करें) |
| पोस्ट | नहीं | एक संसाधन बनाएँ |
| डालो | हाँ | किसी संसाधन का पूर्ण प्रतिस्थापन |
| पैच | नहीं* | आंशिक अद्यतन |
| हटाएं | हाँ | एक संसाधन निकालें |

*पैच तकनीकी रूप से निष्क्रिय होने की गारंटी नहीं है, हालांकि कार्यान्वयन अक्सर होता है।*

**स्थिति कोड जो आपको अवश्य जानना चाहिए**:
- `200 OK` - प्रतिक्रिया निकाय के साथ सफलता
- `201 Created` - निर्मित संसाधन (`Location` हेडर शामिल करें)
- `204 No Content` - बिना किसी प्रतिक्रिया निकाय के सफलता (DELETE के लिए सामान्य)
- `400 Bad Request` - क्लाइंट ने अमान्य डेटा भेजा
- `401 Unauthorized` - प्रमाणीकरण आवश्यक है
- `403 Forbidden` - प्रमाणित लेकिन अधिकृत नहीं
- `404 Not Found` - संसाधन मौजूद नहीं है
- `409 Conflict` - वर्तमान स्थिति के साथ संघर्ष (डुप्लिकेट, संस्करण बेमेल)
- `429 Too Many Requests` - दर सीमित
- `500 Internal Server Error` - हमारी तरफ से कुछ टूट गया

### पृष्ठांकन

असीमित सूचियाँ कभी न लौटाएँ। तीन सामान्य पैटर्न:

```json
// Offset-based (simple but poor for large datasets)
GET /users?offset=20&limit=10

// Cursor-based (preferred for feeds and large datasets)
GET /users?cursor=eyJ0aW1lIjoiMjAyNC0wMS0wMSJ9&limit=10

// Response includes pagination metadata
{
  "data": [...],
  "pagination": {
    "next_cursor": "eyJ0aW1lIjoiMjAyNC0wMS0wMiJ9",
    "has_more": true
  }
}
```

<ThinkAboutIt>बड़े, बार-बार अपडेट किए जाने वाले डेटासेट के लिए ऑफसेट-आधारित की तुलना में कर्सर-आधारित पेजिनेशन को प्राथमिकता क्यों दी जाती है? विचार करें कि जब कोई उपयोगकर्ता परिणामों को पेजिनेट कर रहा होता है तो नए आइटम डालने पर क्या होता है।</ThinkAboutIt>

### संस्करण

एपीआई विकसित होते हैं। पहले दिन से ही इसके लिए डिज़ाइन करें।

```
// URL versioning (most common, explicit)
GET /v1/users/123
GET /v2/users/123

// Header versioning (cleaner URLs, less discoverable)
GET /users/123
Accept: application/vnd.myapi.v2+json
```

साक्षात्कारों में, यूआरएल संस्करण सुरक्षित उत्तर है जब तक कि साक्षात्कारकर्ता विशेष रूप से विकल्पों की खोज नहीं करता।

### त्रुटि प्रतिक्रियाएँ

सुसंगत, सूचनात्मक त्रुटि प्रतिक्रियाएँ महान एपीआई को निराशाजनक एपीआई से अलग करती हैं:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request body contains invalid fields.",
    "details": [
      {
        "field": "email",
        "message": "Must be a valid email address."
      },
      {
        "field": "age",
        "message": "Must be a positive integer."
      }
    ],
    "request_id": "req_abc123"
  }
}
```

हमेशा डिबगिंग के लिए `request_id` और मानव-पठनीय `message` के साथ एक मशीन-पठनीय `code` शामिल करें।

## साक्षात्कार में ग्राफक्यूएल

ग्राफक्यूएल प्रश्न तेजी से आम होते जा रहे हैं, खासकर जटिल फ्रंटएंड जरूरतों वाली कंपनियों में।

**स्पष्ट करने के मुख्य लाभ**:
- ग्राहक ठीक उसी डेटा का अनुरोध करते हैं जिसकी उन्हें आवश्यकता है (कोई अति-प्राप्ति नहीं)
- सिंगल एंडपॉइंट राउंड ट्रिप को कम करता है
- दृढ़तापूर्वक टाइप किया गया स्कीमा दस्तावेज़ीकरण के रूप में कार्य करता है

```graphql
# Schema definition
type User {
  id: ID!
  name: String!
  email: String!
  orders(first: Int, after: String): OrderConnection!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

# Query — client specifies exactly what it needs
query {
  user(id: "123") {
    name
    orders(first: 5) {
      edges {
        node {
          total
          status
        }
      }
    }
  }
}
```

**व्यापार पर चर्चा**: ग्राफक्यूएल सर्वर साइड पर जटिलता जोड़ता है (रिज़ॉल्वर चेन, एन+1 क्वेरीज़, कैशिंग कठिन है)। सरल CRUD API के लिए, REST अक्सर बेहतर विकल्प होता है।

<FunFact>ग्राफक्यूएल को एक विशिष्ट मोबाइल प्रदर्शन समस्या को हल करने के लिए 2012 में फेसबुक में आंतरिक रूप से विकसित किया गया था: समाचार फ़ीड को कई अलग-अलग बैकएंड सेवाओं से डेटा की आवश्यकता होती थी, और धीमे नेटवर्क पर मोबाइल उपकरणों से कई आरईएसटी कॉल करने से प्रदर्शन खराब हो रहा था। इसे 2015 में ओपन-सोर्स किया गया था।</FunFact>

## एपीआई सुरक्षा मूल बातें

प्रत्येक एपीआई डिज़ाइन साक्षात्कार में सुरक्षा पर ध्यान देना चाहिए। इन आवश्यक चीजों को कवर करें:

### प्रमाणीकरण और प्राधिकरण

```
Authentication (AuthN): WHO are you?
→ API Keys, OAuth 2.0, JWT tokens

Authorisation (AuthZ): WHAT can you do?
→ Role-based (RBAC), Scope-based, Resource-based
```

```
// JWT in Authorization header
GET /users/123/orders
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...

// API Key (for server-to-server)
GET /analytics/reports
X-API-Key: sk_live_abc123...
```

### दर सीमित करना

अपने एपीआई को दुरुपयोग से बचाएं और उचित उपयोग सुनिश्चित करें:

```
// Rate limit headers in response
HTTP/1.1 200 OK
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1640995200

// When limit is exceeded
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

दर सीमित करने की रणनीतियों पर चर्चा करें: प्रति-उपयोगकर्ता, प्रति-आईपी, प्रति-एंडपॉइंट, और विभिन्न एपीआई योजनाओं के लिए स्तरीय सीमाएं।

## वास्तविक साक्षात्कार परिदृश्य

### एक भुगतान एपीआई डिज़ाइन करें

स्पष्ट करने की आवश्यकताएँ:
- भुगतान के कौन से तरीके? (कार्ड, बैंक हस्तांतरण, वॉलेट)
- क्या हमें निष्क्रियता की आवश्यकता है? (हाँ - हमेशा भुगतान के लिए)
- रिफंड और विवादों के बारे में क्या?

```
POST /v1/payments
{
  "amount": 4999,           // Always use smallest currency unit (cents)
  "currency": "GBP",
  "payment_method": "pm_card_visa_123",
  "idempotency_key": "order_789_attempt_1",
  "metadata": {
    "order_id": "order_789"
  }
}

Response: 201 Created
{
  "id": "pay_abc123",
  "status": "processing",
  "amount": 4999,
  "currency": "GBP",
  "created_at": "2024-01-15T10:30:00Z"
}
```

<Callout>भुगतान एपीआई के लिए, हमेशा निष्क्रियता कुंजियों पर चर्चा करें। नेटवर्क विफल हो जाता है, ग्राहक पुनः प्रयास करते हैं, और निष्क्रियता के बिना, आप ग्राहकों से दोगुना शुल्क लेंगे। इडेम्पोटेंसी कुंजी यह सुनिश्चित करती है कि समान अनुरोध को पुनः प्रयास करने से समान परिणाम प्राप्त होता है।</Callout>

**चर्चा के लिए मुख्य डिज़ाइन निर्णय**:
- फ्लोटिंग-पॉइंट समस्याओं से बचने के लिए राशि सबसे छोटी मुद्रा इकाई (सेंट/पेंस) में
- सुरक्षित पुनर्प्रयासों के लिए निष्क्रियता कुंजियाँ
- एसिंक स्टेटस अपडेट के लिए वेबहुक कॉलबैक
- पीसीआई अनुपालन संबंधी विचार

### एक सोशल मीडिया एपीआई डिज़ाइन करें

```
// Post creation
POST /v1/posts
{
  "content": "Hello world!",
  "media_ids": ["media_123"],
  "visibility": "public"
}

// Feed retrieval with cursor pagination
GET /v1/feed?cursor=abc&limit=20

// Interactions
POST /v1/posts/{post_id}/likes
DELETE /v1/posts/{post_id}/likes
POST /v1/posts/{post_id}/comments
```

फ़िल्टरिंग, खोज और फ़ीड को कैसे इकट्ठा किया जाता है, इस पर चर्चा करें (पुल बनाम पुश मॉडल सिस्टम डिज़ाइन पर वापस निर्भर करता है)।

## एपीआई डिज़ाइन साक्षात्कार में सामान्य गलतियाँ

1. **आंतरिक कार्यान्वयन को उजागर करना** - डेटाबेस कॉलम नाम या आंतरिक आईडी को एपीआई में लीक न होने दें। डीटीओ का प्रयोग करें.
2. **असंगत नामकरण** - `snake_case` या `camelCase` चुनें और इसे हर जगह चिपकाएँ।
3. **अनुपलब्ध पेजिनेशन** - किसी भी सूची समापन बिंदु को पेजिनेशन का समर्थन करना चाहिए।
4. **कोई त्रुटि प्रबंधन चर्चा नहीं** - दिखाएं कि आप विफलता मोड के बारे में सोचते हैं।
5. **पिछली संगतता को अनदेखा करना** - मौजूदा एंडपॉइंट में आवश्यक फ़ील्ड जोड़ने से क्लाइंट टूट जाते हैं।
6. **यूआरएल में क्रियाओं का उपयोग** - `POST /users` के बजाय `/createUser`।

## चाबी छीनना

- **संसाधनों के बारे में सोचें**: संज्ञाओं के आसपास यूआरएल डिज़ाइन करें, HTTP विधियों को क्रियाओं को संभालने दें।
- **अपने स्टेटस कोड को जानें**: सटीक स्टेटस कोड दर्शाते हैं कि आप HTTP शब्दार्थ को समझते हैं।
- **हमेशा पेजिनेट करें**: असीमित सूची प्रतिक्रियाएँ साक्षात्कार में एक खतरे का संकेत होती हैं।
- **विफलता के लिए डिज़ाइन**: निष्क्रियता, त्रुटि प्रतिक्रियाएँ, और दर सीमित करना उत्पादन-तत्परता सोच को दर्शाता है।
- **सुरक्षा वैकल्चुनता नहीं है**: प्रमाणीकरण, प्राधिकरण और दर सीमित करना प्रत्येक एपीआई डिज़ाइन चर्चा का हिस्सा होना चाहिए।
- **स्पष्ट व्यापार-बंद**: REST बनाम GraphQL, स्थिरता बनाम लचीलापन, सरलता बनाम शक्ति - साक्षात्कारकर्ता आपका तर्क सुनना चाहते हैं।
