# API डिज़ाइन इंटरव्यू

API सिस्टमों के बीच अनुबंध होते हैं, और उन्हें अच्छी तरह डिज़ाइन करना वह कौशल है जो वरिष्ठ इंजीनियरों को जूनियर से अलग करता है। API डिज़ाइन इंटरव्यू में आप सिर्फ़ endpoints नहीं लिख रहे होते। आप दिखा रहे होते हैं कि consumers आपके सिस्टम का उपयोग कैसे करेंगे, वह समय के साथ कैसे बदलेगा, और failure modes कहाँ हैं। चाहे आपसे payment gateway डिज़ाइन करने को कहा जाए या social media platform API, सिद्धांत वही रहते हैं। आइए इन्हें पक्का करें।

## REST API डिज़ाइन सिद्धांत

इंटरव्यू में REST अब भी प्रमुख API paradigm है। ये आधार आपको दिखाने होंगे:

### Resource-Oriented Design

Nouns (resources) में सोचें, verbs (actions) में नहीं। URLs को चीज़ों को दिखाना चाहिए, और HTTP methods को उन चीज़ों पर होने वाली actions को।

```
✅ Good:
GET    /users/123              — Fetch user 123
POST   /users                  — Create a new user
PUT    /users/123              — Replace user 123
PATCH  /users/123              — Partially update user 123
DELETE /users/123              — Delete user 123

❌ Bad:
GET    /getUser?id=123
POST   /createUser
POST   /deleteUser/123
```

<Callout>एक साफ़ resource hierarchy API की कहानी बताती है। `/users/123/orders/456/items` स्वाभाविक रूप से पढ़ा जाता है: "user 123 के order 456 के items." अगर आपकी URL structure वाक्य जैसी नहीं पढ़ी जाती, तो resource design पर फिर से सोचें।</Callout>

### HTTP Methods और Status Codes

इन्हें ठंडे दिमाग से याद रखें। इंटरव्यूअर आपकी precision जाँचेंगे:

| Method | Idempotent? | Use Case |
|---|---|---|
| GET | Yes | resource पढ़ना (कभी mutate नहीं करना) |
| POST | No | resource बनाना |
| PUT | Yes | resource का पूरा replacement |
| PATCH | No* | partial update |
| DELETE | Yes | resource हटाना |

*PATCH technically idempotent guaranteed नहीं है, हालांकि implementations अक्सर होती हैं।*

**Status codes जो आपको जानने चाहिए**:
- `200 OK`: response body के साथ success
- `201 Created`: resource created (`Location` header शामिल करें)
- `204 No Content`: response body के बिना success (DELETE के लिए common)
- `400 Bad Request`: client ने invalid data भेजा
- `401 Unauthorized`: authentication required
- `403 Forbidden`: authenticated है लेकिन authorised नहीं
- `404 Not Found`: resource मौजूद नहीं है
- `409 Conflict`: current state से conflict (duplicate, version mismatch)
- `429 Too Many Requests`: rate limited
- `500 Internal Server Error`: हमारी side पर कुछ टूटा

### Pagination

Unbounded lists कभी return न करें। तीन common patterns:

```json
// Offset-based (simple but poor for large datasets)
GET /users?offset=20&limit=10

// Cursor-based (preferred for feeds and large datasets)
GET /users?cursor=eyJ0aW1lIjoiMjAyNC0wMS0wMSJ9&limit=10

// Response includes pagination metadata
{
  "data": [...],
  "pagination": {
    "next_cursor": "eyJ0aW1lIjoiMjAyNC0wMS0wMiJ9",
    "has_more": true
  }
}
```

<ThinkAboutIt>बड़े और लगातार update होने वाले datasets के लिए offset-based pagination की तुलना में cursor-based pagination को क्यों पसंद किया जाता है? सोचें कि user जब results paginate कर रहा हो और उसी समय नए items insert हो जाएँ, तो क्या होता है।</ThinkAboutIt>

### Versioning

API बदलते हैं। पहले दिन से इसके लिए design करें।

```
// URL versioning (most common, explicit)
GET /v1/users/123
GET /v2/users/123

// Header versioning (cleaner URLs, less discoverable)
GET /users/123
Accept: application/vnd.myapi.v2+json
```

इंटरव्यू में URL versioning safe answer है, जब तक interviewer alternatives पर specifically explore न करे।

### Error Responses

Consistent और informative error responses बेहतरीन API को frustrating API से अलग करते हैं:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request body contains invalid fields.",
    "details": [
      {
        "field": "email",
        "message": "Must be a valid email address."
      },
      {
        "field": "age",
        "message": "Must be a positive integer."
      }
    ],
    "request_id": "req_abc123"
  }
}
```

Debugging के लिए हमेशा `request_id` शामिल करें, और human-readable `message` के साथ machine-readable `code` भी दें।

## GraphQL इंटरव्यू में

GraphQL questions अब अधिक common हो रहे हैं, खासकर उन companies में जिनकी frontend needs complex हैं।

**बताने लायक मुख्य advantages**:
- Clients exactly वही data request करते हैं जो उन्हें चाहिए (over-fetching नहीं)
- Single endpoint round trips घटाता है
- Strongly typed schema documentation जैसा काम करता है

```graphql
# Schema definition
type User {
  id: ID!
  name: String!
  email: String!
  orders(first: Int, after: String): OrderConnection!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

# Query — client specifies exactly what it needs
query {
  user(id: "123") {
    name
    orders(first: 5) {
      edges {
        node {
          total
          status
        }
      }
    }
  }
}
```

**Trade-offs discuss करें**: GraphQL server side पर complexity बढ़ाता है (resolver chains, N+1 queries, caching कठिन होती है)। Simple CRUD APIs के लिए REST अक्सर बेहतर choice है।

<FunFact>GraphQL को Facebook में 2012 में एक specific mobile performance problem हल करने के लिए internally develop किया गया था: News Feed को कई backend services से data चाहिए था, और धीमे networks पर mobile devices से कई REST calls करना performance खत्म कर रहा था। इसे 2015 में open-source किया गया।</FunFact>

## API Security Basics

हर API design interview में security पर बात होनी चाहिए। ये essentials cover करें:

### Authentication और Authorisation

```
Authentication (AuthN): WHO are you?
→ API Keys, OAuth 2.0, JWT tokens

Authorisation (AuthZ): WHAT can you do?
→ Role-based (RBAC), Scope-based, Resource-based
```

```
// JWT in Authorization header
GET /users/123/orders
Authorization: ******

// API Key (for server-to-server)
GET /analytics/reports
X-API-Key: sk_live_abc123...
```

### Rate Limiting

अपनी API को abuse से बचाएँ और fair usage सुनिश्चित करें:

```
// Rate limit headers in response
HTTP/1.1 200 OK
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1640995200

// When limit is exceeded
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

Rate limiting strategies discuss करें: per-user, per-IP, per-endpoint, और अलग API plans के लिए tiered limits.

## Real Interview Scenarios

### Payment API design करें

Clarify करने वाली requirements:
- कौन से payment methods? (Card, bank transfer, wallet)
- क्या idempotency चाहिए? (हाँ, payments के लिए हमेशा)
- Refunds और disputes का क्या?

```
POST /v1/payments
{
  "amount": 4999,           // Always use smallest currency unit (cents)
  "currency": "GBP",
  "payment_method": "pm_card_visa_123",
  "idempotency_key": "order_789_attempt_1",
  "metadata": {
    "order_id": "order_789"
  }
}

Response: 201 Created
{
  "id": "pay_abc123",
  "status": "processing",
  "amount": 4999,
  "currency": "GBP",
  "created_at": "2024-01-15T10:30:00Z"
}
```

<Callout>Payment APIs के लिए हमेशा idempotency keys discuss करें। Network failures होते हैं, clients retry करते हैं, और idempotency के बिना customers से दो बार charge हो सकता है। Idempotency key सुनिश्चित करती है कि same request retry करने पर same result मिले।</Callout>

**Discuss करने लायक मुख्य design decisions**:
- Floating-point issues से बचने के लिए amounts smallest currency unit (cents/pence) में
- Safe retries के लिए idempotency keys
- Async status updates के लिए webhook callbacks
- PCI compliance considerations

### Social Media API design करें

```
// Post creation
POST /v1/posts
{
  "content": "Hello world!",
  "media_ids": ["media_123"],
  "visibility": "public"
}

// Feed retrieval with cursor pagination
GET /v1/feed?cursor=abc&limit=20

// Interactions
POST /v1/posts/{post_id}/likes
DELETE /v1/posts/{post_id}/likes
POST /v1/posts/{post_id}/comments
```

Filtering, search, और feed कैसे assemble होती है, यह discuss करें (pull vs push model system design से जुड़ता है)।

## API Design Interviews में Common Mistakes

1. **Internal implementation expose करना**: database column names या internal IDs को API में leak न होने दें। DTOs इस्तेमाल करें।
2. **Inconsistent naming**: `snake_case` या `camelCase` चुनें और हर जगह वही रखें।
3. **Pagination गायब होना**: कोई भी list endpoint pagination support करे।
4. **Error handling discussion नहीं करना**: दिखाएँ कि आप failure modes सोचते हैं।
5. **Backwards compatibility ignore करना**: मौजूदा endpoints में required fields जोड़ना clients को तोड़ता है।
6. **URLs में verbs इस्तेमाल करना**: `/createUser` के बजाय `POST /users`।

## मुख्य बातें

- **Resources में सोचें**: URLs nouns के around design करें, verbs HTTP methods संभालते हैं।
- **Status codes जानें**: precise status codes बताते हैं कि आप HTTP semantics समझते हैं।
- **हमेशा paginate करें**: unbounded list responses interviews में red flag हैं।
- **Failure के लिए design करें**: idempotency, error responses और rate limiting production-readiness thinking दिखाते हैं।
- **Security optional नहीं है**: authentication, authorisation और rate limiting हर API design discussion का हिस्सा होने चाहिए।
- **Trade-offs समझाएँ**: REST vs GraphQL, consistency vs flexibility, simplicity vs power. Interviewers आपकी reasoning सुनना चाहते हैं।
