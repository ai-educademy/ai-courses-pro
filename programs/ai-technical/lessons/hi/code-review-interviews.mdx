# Code Review इंटरव्यू

Code review interviews hiring process के सबसे कम आँके गए rounds में से हैं, और सबसे ज़्यादा खुलासा भी करते हैं। Coding interviews जाँचते हैं कि आप code लिख सकते हैं या नहीं। Code review interviews जाँचते हैं कि आप code पढ़ सकते हैं, उसके बारे में reason कर सकते हैं, और उसे improve कर सकते हैं या नहीं। वे दिखाते हैं कि आप quality के बारे में कैसे सोचते हैं, feedback कैसे prioritise करते हैं, और दूसरे engineers से कैसे communicate करते हैं। कई candidates LeetCode पर महीनों तैयारी करते हैं लेकिन code review round में बिल्कुल unprepared पहुँचते हैं। आप वह व्यक्ति न बनें।

## Code Review Interviews असल में क्या जाँचते हैं

Interviewers आपके code review skills में पाँच चीज़ें देखते हैं:

1. **Bug detection**: क्या आप logical errors, edge cases और race conditions पकड़ सकते हैं?
2. **Design sense**: क्या आप SOLID principles के violations, कमजोर abstractions या maintain करने में कठिन code पहचानते हैं?
3. **Security awareness**: क्या आप injection vulnerabilities, authentication flaws या data exposure risks पहचान सकते हैं?
4. **Communication skill**: क्या आप issues साफ़ और constructive ढंग से समझा सकते हैं?
5. **Prioritisation**: क्या आप असली बात पर focus करते हैं, या variable names पर bikeshed करते हैं?

<Callout>Code review interviews में सबसे common गलती style issues (naming, formatting) पर पूरा समय खर्च करना है, जबकि actual bugs छूट जाते हैं। Interviewers जानबूझकर critical bugs को style issues के साथ रखते हैं ताकि देखें कि आप क्या prioritise करते हैं।</Callout>

## Systematic Review Approach

Code को random scan न करें। Structured pass-based approach इस्तेमाल करें:

### Pass 1: Intent समझें (2 मिनट)

Critique करने से पहले समझें कि code क्या करने की कोशिश कर रहा है:
- Function/class names और comments पढ़ें
- Inputs और outputs पहचानें
- Business logic समझें

### Pass 2: Correctness (5 मिनट)

यहीं आप bugs खोजते हैं। Systematically check करें:
- **Edge cases**: empty inputs, null values, single elements, maximum values
- **Off-by-one errors**: loop boundaries, array indexing
- **Logic errors**: incorrect conditions, missing break statements, wrong operator
- **Concurrency issues**: shared mutable state, race conditions
- **Error handling**: uncaught exceptions, missing null checks

### Pass 3: Design और Maintainability (3 मिनट)

Structural issues खोजें:
- Functions बहुत ज़्यादा काम कर रहे हैं (Single Responsibility violation)
- Components में tight coupling
- Magic numbers और hardcoded values
- Missing abstractions या unnecessary abstractions
- Code duplication

### Pass 4: Performance और Security (2 मिनट)

- Loops में unnecessary database queries (N+1 problem)
- Missing input validation या sanitisation
- Logs या responses में exposed sensitive data
- Inefficient algorithms जहाँ बेहतर alternatives मौजूद हों

## पकड़ने लायक Common Bug Patterns

इन high-frequency bugs को पकड़ने के लिए अपनी नज़र train करें:

### Null Reference Errors

```java
// Bug: user could be null
public String getUserEmail(Long userId) {
    User user = userRepository.findById(userId);
    return user.getEmail();  // NullPointerException if user not found
}

// Fixed
public String getUserEmail(Long userId) {
    return userRepository.findById(userId)
        .map(User::getEmail)
        .orElseThrow(() -> new UserNotFoundException(userId));
}
```

### Off-by-One Errors

```python
# Bug: misses the last element
def find_max(numbers):
    max_val = numbers[0]
    for i in range(1, len(numbers) - 1):  # Should be len(numbers)
        if numbers[i] > max_val:
            max_val = numbers[i]
    return max_val
```

### Resource Leaks

```java
// Bug: connection is never closed if an exception occurs
public List<User> getUsers() {
    Connection conn = dataSource.getConnection();
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT * FROM users");
    // process results...
    conn.close();
    return users;
}

// Fixed: use try-with-resources
public List<User> getUsers() {
    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery("SELECT * FROM users")) {
        // process results...
        return users;
    }
}
```

### SQL Injection

```python
# Bug: SQL injection vulnerability
def get_user(username):
    query = f"SELECT * FROM users WHERE username = '{username}'"
    return db.execute(query)

# Fixed: parameterised query
def get_user(username):
    query = "SELECT * FROM users WHERE username = %s"
    return db.execute(query, (username,))
```

<FunFact>Google में 100,000 से अधिक code reviews के एक study ने पाया कि लगभग 25% review comments "correctness" पर होते हैं: actual bugs या logic त्रुटियाँ। और 25% "comprehension" पर होते हैं: code को समझने में आसान बनाना। Style और formatting substantive comments के 10% से कम थे।</FunFact>

### Concurrency Bugs

```java
// Bug: race condition — check-then-act is not atomic
public void transferMoney(Account from, Account to, BigDecimal amount) {
    if (from.getBalance().compareTo(amount) >= 0) {
        // Another thread could modify balance here
        from.setBalance(from.getBalance().subtract(amount));
        to.setBalance(to.getBalance().add(amount));
    }
}
```

<ThinkAboutIt>ऊपर वाले concurrency bug को आप कैसे fix करेंगे? कम से कम तीन approaches सोचें: synchronisation, optimistic locking और database-level transactions. High-throughput system में हर approach के trade-offs क्या हैं?</ThinkAboutIt>

## अपने Feedback को Prioritise करना

Time-limited interview में हर feedback बराबर नहीं होता। यह priority framework इस्तेमाल करें:

| Priority | Category | Example |
|---|---|---|
| 🔴 **Critical** | Bugs, security vulnerabilities, data loss | SQL injection, race conditions, null dereference |
| 🟠 **High** | Design issues, performance problems | N+1 queries, missing error handling, tight coupling |
| 🟡 **Medium** | Maintainability, readability | Complex conditionals, missing documentation, magic numbers |
| 🟢 **Low** | Style, minor improvements | Variable naming, import ordering, minor refactors |

इंटरव्यू में अपना 80% समय 🔴 और 🟠 items पर लगाएँ। 🟡 items briefly mention करें। 🟢 items को तभी छुएँ जब समय बचा हो और important issues मिल चुके हों।

## Review Feedback Communicate करना

आप feedback कैसे देते हैं, यह feedback जितना ही महत्वपूर्ण है। Interviewers आपकी collaboration skills evaluate कर रहे होते हैं।

**यह करें**:
- "मुझे दिख रहा है कि यह query loop के अंदर है, जिससे N+1 performance issues हो सकते हैं। शायद हमें इसे एक single query में batch करना चाहिए।"
- "User न मिलने पर यह NullPointerException throw कर सकता है। क्या हम null check जोड़ें या यहाँ Optional इस्तेमाल करें?"
- "Strategy pattern का यह उपयोग अच्छा है। इससे नए payment types जोड़ना straightforward हो जाता है।"

**यह नहीं**:
- "यह code गलत है।" (बहुत blunt, explanation नहीं)
- "मैं इसे कभी ऐसे नहीं लिखता।" (ego-driven)
- "इस variable name को बदलो।" (low-priority item पर bikeshedding)

<Callout>Feedback के पीछे *why* हमेशा समझाएँ, सिर्फ़ *what* नहीं। "यह parameterised queries इस्तेमाल करे" ठीक है। "यह parameterised queries इस्तेमाल करे क्योंकि current string concatenation SQL injection attacks के लिए vulnerable है" कहीं बेहतर है।</Callout>

## Example Code Review Walkthrough

यह एक function है जिसे आपको interview में review करने को कहा जा सकता है:

```python
def process_orders(orders):
    results = []
    for order in orders:
        user = db.query(f"SELECT * FROM users WHERE id = {order['user_id']}")
        if user:
            total = 0
            for item in order['items']:
                price = db.query(f"SELECT price FROM products WHERE id = {item['product_id']}")
                total = total + price[0] * item['quantity']
                if item['quantity'] > 100:
                    total = total * 0.9
            if total > 0:
                results.append({'user': user, 'total': total, 'order_id': order['id']})
    return results
```

**एक strong review ये पहचानेगा:**

1. 🔴 **SQL Injection** (lines 4, 7): SQL queries में string interpolation. Parameterised queries इस्तेमाल करें।
2. 🔴 **N+1 Query Problem** (lines 4, 7): हर order पर दो database queries, और हर item पर एक। 100 orders और 10 items each के लिए 1,100 queries. Single queries में batch करें।
3. 🟠 **Error handling नहीं**: Product न मिलने पर `price[0]` crash करेगा। `db.query` fail हो सकता है।
4. 🟠 **Discount logic hidden है**: quantity > 100 पर 10% discount nested loops में दबा business rule है। इसे extract करें।
5. 🟡 **Magic number**: `0.9` और `100` named constants होने चाहिए (`BULK_DISCOUNT_RATE`, `BULK_THRESHOLD`)।
6. 🟡 **Function बहुत ज़्यादा काम करता है**: users fetch करना, totals calculate करना, discounts apply करना। Single Responsibility violate होता है।

## मुख्य बातें

- **Structured approach इस्तेमाल करें**: कई passes (intent → correctness → design → performance/security) random scanning से ज़्यादा issues पकड़ते हैं।
- **निर्दयता से prioritise करें**: critical bugs और security issues पहले, style आख़िर में। Interviewers दोनों रखते हैं ताकि judgement test हो।
- **Constructively communicate करें**: *why* explain करें, alternatives सुझाएँ, और अच्छे patterns को acknowledge करें।
- **Common bug patterns जानें**: null references, off-by-one errors, resource leaks, SQL injection और race conditions लगभग हर code review interview में दिखते हैं।
- **Code पढ़ने का अभ्यास करें**: GitHub पर open-source pull requests पढ़ें। Code पढ़ने का skill code लिखने से अलग है, और अधिकतर engineers इसका पर्याप्त अभ्यास नहीं करते।
