# कोड समीक्षा साक्षात्कार

कोड समीक्षा साक्षात्कार नियुक्ति प्रक्रिया में सबसे कम महत्व वाले दौरों में से एक है - और सबसे अधिक खुलासा करने वाले दौरों में से एक है। कोडिंग साक्षात्कार में यह परीक्षण किया जाता है कि क्या आप कोड लिख सकते हैं, कोड समीक्षा साक्षात्कार परीक्षण करते हैं कि क्या आप इसे पढ़ सकते हैं, इसके बारे में तर्क कर सकते हैं और इसमें सुधार कर सकते हैं। वे बताते हैं कि आप गुणवत्ता के बारे में कैसे सोचते हैं, आप फीडबैक को कैसे प्राथमिकता देते हैं और आप अन्य इंजीनियरों के साथ कैसे संवाद करते हैं। कई उम्मीदवार लीटकोड पर महीनों तक तैयारी करते हैं लेकिन कोड समीक्षा दौर में पूरी तरह से बिना तैयारी के चले जाते हैं। वह व्यक्ति मत बनो.

## कौन सा कोड समीक्षा साक्षात्कार वास्तव में परीक्षण करता है

आपके कोड समीक्षा कौशल का मूल्यांकन करने वाले साक्षात्कारकर्ता पाँच चीज़ों की तलाश कर रहे हैं:

1. **बग का पता लगाना** - क्या आप तार्किक त्रुटियों, किनारे के मामलों और दौड़ की स्थितियों का पता लगा सकते हैं?
2. **डिज़ाइन सेंस** - क्या आप SOLID सिद्धांतों, ख़राब अमूर्तताओं, या कोड के उल्लंघन को पहचानते हैं जिन्हें बनाए रखना कठिन होगा?
3. **सुरक्षा जागरूकता** - क्या आप इंजेक्शन की कमजोरियों, प्रमाणीकरण दोषों या डेटा एक्सपोज़र जोखिमों की पहचान कर सकते हैं?
4. **संचार कौशल** - क्या आप मुद्दों को स्पष्ट और रचनात्मक ढंग से समझा सकते हैं?
5. **प्राथमिकता** - क्या आप उस पर ध्यान केंद्रित करते हैं जो सबसे ज्यादा मायने रखता है, या क्या आप परिवर्तनशील नामों पर ध्यान केंद्रित करते हैं?

<Callout>कोड समीक्षा साक्षात्कारों में सबसे आम गलती अपना सारा समय शैली के मुद्दों (नामकरण, स्वरूपण) पर खर्च करना है जबकि वास्तविक बग गायब हैं। यह देखने के लिए कि आप क्या प्राथमिकता देते हैं, साक्षात्कारकर्ता जानबूझकर शैली संबंधी मुद्दों के साथ-साथ महत्वपूर्ण बग भी लगाते हैं।</Callout>

## व्यवस्थित समीक्षा दृष्टिकोण

कोड को बेतरतीब ढंग से स्कैन न करें. एक संरचित पास-आधारित दृष्टिकोण का उपयोग करें:

### पास 1: इरादे को समझें (2 मिनट)

किसी भी चीज़ की आलोचना करने से पहले, समझें कि कोड क्या करने का प्रयास कर रहा है:
- फ़ंक्शन/वर्ग के नाम और टिप्पणियाँ पढ़ें
- इनपुट और आउटपुट को पहचानें
- व्यावसायिक तर्क को समझें

### पास 2: शुद्धता (5 मिनट)

यहीं पर आपको बग मिलते हैं। व्यवस्थित रूप से जांचें:
- **एज केस**: खाली इनपुट, शून्य मान, एकल तत्व, अधिकतम मान
- **ऑफ-बाय-वन त्रुटियाँ**: लूप सीमाएँ, सरणी अनुक्रमण
- **तर्क संबंधी त्रुटियां**: गलत स्थितियां, गुम ब्रेक स्टेटमेंट, गलत ऑपरेटर
- **समवर्ती मुद्दे**: साझा परिवर्तनीय स्थिति, दौड़ की स्थिति
- **त्रुटि प्रबंधन**: न पकड़े गए अपवाद, गायब शून्य जाँचें

### पास 3: डिज़ाइन और रखरखाव (3 मिनट)

संरचनात्मक मुद्दों की तलाश करें:
- बहुत सारे कार्य करने वाले कार्य (एकल उत्तरदायित्व का उल्लंघन)
- घटकों के बीच मजबूत युग्मन
- जादुई संख्याएं और हार्डकोडेड मान
- गुम अमूर्तता या अनावश्यक अमूर्तता
- कोड दोहराव

### पास 4: प्रदर्शन और सुरक्षा (2 मिनट)

- लूप में अनावश्यक डेटाबेस क्वेरीज़ (एन+1 समस्या)
- इनपुट सत्यापन या स्वच्छता का अभाव
- लॉग या प्रतिक्रियाओं में संवेदनशील डेटा उजागर करना
- अकुशल एल्गोरिदम जहां बेहतर विकल्प मौजूद हैं

## सामान्य बग पैटर्न का पता लगाएं

इन उच्च-आवृत्ति बगों को पकड़ने के लिए अपनी आँखों को प्रशिक्षित करें:

### शून्य संदर्भ त्रुटियाँ

```java
// Bug: user could be null
public String getUserEmail(Long userId) {
    User user = userRepository.findById(userId);
    return user.getEmail();  // NullPointerException if user not found
}

// Fixed
public String getUserEmail(Long userId) {
    return userRepository.findById(userId)
        .map(User::getEmail)
        .orElseThrow(() -> new UserNotFoundException(userId));
}
```

### एक-एक करके त्रुटियाँ

```python
# Bug: misses the last element
def find_max(numbers):
    max_val = numbers[0]
    for i in range(1, len(numbers) - 1):  # Should be len(numbers)
        if numbers[i] > max_val:
            max_val = numbers[i]
    return max_val

### संसाधन लीक

// Bug: connection is never closed if an exception occurs
public List<User> getUsers() {
    Connection conn = dataSource.getConnection();

// Fixed: use try-with-resources
public List<User> getUsers() {
    try (Connection conn = dataSource.getConnection();

        // process results...

}
```

## आपकी प्रतिक्रिया को प्राथमिकता देना

समय-सीमित साक्षात्कार में, सभी प्रतिक्रियाएँ समान नहीं होती हैं। इस प्राथमिकता ढांचे का उपयोग करें:

| प्राथमिकता | श्रेणी | उदाहरण |
|---|---|---|
| 🔴 **महत्वपूर्ण** | बग, सुरक्षा कमजोरियाँ, डेटा हानि | एसक्यूएल इंजेक्शन, दौड़ की स्थिति, शून्य डीरेफ़रेंस |
| 🟠 **उच्च** | डिज़ाइन संबंधी समस्याएं, प्रदर्शन संबंधी समस्याएं | एन+1 क्वेरीज़, त्रुटि प्रबंधन गायब, टाइट कपलिंग |
| 🟡 **मध्यम** | रख-रखाव, पठनीयता | जटिल सशर्तताएँ, गुम दस्तावेज, जादुई संख्याएँ |
| 🟢 **कम** | शैली, मामूली सुधार | परिवर्तनीय नामकरण, आयात आदेश, छोटे रिफैक्टर |

इंटरव्यू में अपना 80% समय 🔴 और 🟠 आइटम पर खर्च करें। 🟡 आइटमों का संक्षेप में उल्लेख करें। केवल 🟢 आइटम को स्पर्श करें यदि आपके पास समय शेष है और आपको पहले से ही महत्वपूर्ण मुद्दे मिल गए हैं।

## संचार समीक्षा प्रतिक्रिया

आप फीडबैक कैसे देते हैं यह उतना ही मायने रखता है जितना फीडबैक स्वयं। साक्षात्कारकर्ता आपके सहयोग कौशल का मूल्यांकन कर रहे हैं।

**यह करो**:
- "मैंने देखा है कि यह क्वेरी एक लूप के अंदर है, जो N+1 प्रदर्शन समस्याओं का कारण बन सकती है। हम इसे एक ही क्वेरी में बैच करना चाह सकते हैं।"
- "ऐसा लगता है कि यदि उपयोगकर्ता नहीं मिला तो यह नुललपोइनटेरेक्सकेपशन फेंक सकता है। क्या हम यहां एक शून्य चेक जोड़ सकते हैं या वैकल्चुनता का उपयोग कर सकते हैं?"
- "यहां रणनीति पैटर्न का अच्छा उपयोग है - यह नए भुगतान प्रकारों को जोड़ना आसान बनाता है।"

**यह नहीं**:
- "यह कोड गलत है।" (बहुत स्पष्ट, कोई स्पष्टीकरण नहीं)
- "मैं इसे इस तरह कभी नहीं लिखूंगा।" (अहंकार से प्रेरित)
- "इस वेरिएबल नाम को बदलें।" (कम प्राथमिकता वाली वस्तुओं पर बाइकशेडिंग)

<Callout>हमेशा अपनी प्रतिक्रिया के पीछे *क्यों* को स्पष्ट करें, न कि केवल *क्या* को। "इसमें पैरामीटरयुक्त प्रश्नों का उपयोग करना चाहिए" ठीक है। "इसमें पैरामीटरयुक्त प्रश्नों का उपयोग करना चाहिए क्योंकि वर्तमान स्ट्रिंग संयोजन SQL इंजेक्शन हमलों के प्रति संवेदनशील है" बहुत बेहतर है।</Callout>

## उदाहरण कोड समीक्षा वॉकथ्रू

यहां एक फ़ंक्शन है जिसकी आपको साक्षात्कार में समीक्षा करने के लिए कहा जा सकता है:

```python
def process_orders(orders):
    results = []
    for order in orders:
        user = db.query(f"SELECT * FROM users WHERE id = {order['user_id']}")
        if user:
            total = 0
            for item in order['items']:
                price = db.query(f"SELECT price FROM products WHERE id = {item['product_id']}")
                total = total + price[0] * item['quantity']
                if item['quantity'] > 100:
                    total = total * 0.9
            if total > 0:
                results.append({'user': user, 'total': total, 'order_id': order['id']})
    return results
```

**एक मजबूत समीक्षा से पता चलेगा:**

1. 🔴 **एसक्यूएल इंजेक्शन** (पंक्तियाँ 4, 7): एसक्यूएल प्रश्नों में स्ट्रिंग इंटरपोलेशन। पैरामीटरयुक्त क्वेरीज़ का उपयोग करें.
2. 🔴 **एन+1 क्वेरी समस्या** (पंक्तियाँ 4, 7): प्रति ऑर्डर दो डेटाबेस क्वेरीज़, प्रति आइटम एक। प्रत्येक 10 आइटम वाले 100 ऑर्डर के लिए, यह 1,100 प्रश्न हैं। एकल प्रश्नों में बैच.
3. 🟠 **कोई त्रुटि प्रबंधन नहीं**: `price[0]` यदि उत्पाद नहीं मिला तो क्रैश हो जाएगा। `db.query` विफल हो सकता है.
4. 🟠 **छूट का तर्क छिपा हुआ है**: मात्रा > 100 के लिए 10% की छूट नेस्टेड लूप्स में छिपा हुआ एक व्यावसायिक नियम है। इसे निकालें.
5. 🟡 **जादुई संख्या**: `0.9` और `100` को स्थिरांक (`BULK_DISCOUNT_RATE`, `BULK_THRESHOLD`) नाम दिया जाना चाहिए।
6. 🟡 **कार्य बहुत अधिक करता है**: उपयोगकर्ताओं को लाना, कुल की गणना करना, छूट लागू करना - एकल उत्तरदायित्व का उल्लंघन करता है।

## चाबी छीनना

- **एक संरचित दृष्टिकोण का उपयोग करें**: एकाधिक पास (इरादा → शुद्धता → डिज़ाइन → प्रदर्शन/सुरक्षा) यादृच्छिक स्कैनिंग की तुलना में अधिक समस्याएं पकड़ते हैं।
- **बेरहमी से प्राथमिकता दें**: गंभीर बग और सुरक्षा मुद्दे पहले, शैली बाद में। साक्षात्कारकर्ता आपके निर्णय का परीक्षण करने के लिए दोनों का रोपण करते हैं।
- **रचनात्मक ढंग से संवाद करें**: *क्यों* को समझाएं, विकल्प सुझाएं, और आपके द्वारा देखे गए अच्छे पैटर्न को स्वीकार करें।
- **सामान्य बग पैटर्न को जानें**: शून्य संदर्भ, ऑफ-बाय-वन त्रुटियां, संसाधन लीक, एसक्यूएल इंजेक्शन, और दौड़ की स्थिति लगभग हर कोड समीक्षा साक्षात्कार में दिखाई देती है।
- **कोड पढ़ने का अभ्यास करें**: GitHub पर ओपन-सोर्स पुल अनुरोधों को पढ़ने में समय व्यतीत करें। कोड पढ़ने का कौशल उसे लिखने से अलग है, और अधिकांश इंजीनियर इसका पर्याप्त अभ्यास नहीं करते हैं।
