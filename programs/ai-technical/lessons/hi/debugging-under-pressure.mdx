# दबाव में डिबगिंग

एक विशेष प्रकार का तनाव होता है जो डिबगिंग कोड से आता है जब कोई आपको देखता है और टाइमर उल्टी गिनती करता है। आपकी हथेलियों में पसीना आ जाता है, आपका दिमाग खाली हो जाता है और अचानक आपको याद नहीं रहता कि फॉर लूप कैसे काम करता है। हर इंजीनियर वहां रहा है. ढहने वाले और चमकने वाले उम्मीदवारों के बीच का अंतर कच्ची प्रतिभा नहीं है - यह एक व्यवस्थित प्रक्रिया है जो तब भी काम करती है जब आपका मस्तिष्क घबराना चाहता है। यह पाठ आपको वह प्रक्रिया सिखाता है।

## आरआईआईएफवी डिबगिंग फ्रेमवर्क

जब किसी साक्षात्कार में आपको बग कोड सौंपा जाता है, तो बग के लिए तुरंत स्कैनिंग शुरू करने की इच्छा से बचें। इसके बजाय, इस पाँच-चरणीय रूपरेखा का पालन करें:

### आर - पुनरुत्पादन

पुष्टि करें कि बग मौजूद है और उसके लक्षणों को समझें।

- अपेक्षित व्यवहार क्या है?
- वास्तविक व्यवहार क्या है?
- बग किस इनपुट के अंतर्गत होता है?

```python
# You're told this function should return the second largest element
def second_largest(nums):
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second:
            second = num
    return second

# Step 1: Reproduce with test cases
print(second_largest([3, 1, 4, 1, 5]))  # Expected: 4, Got: 4 ✓
print(second_largest([5, 5, 5]))         # Expected: 5, Got: -inf ✗ — BUG!
print(second_largest([1]))               # Expected: None?, Got: -inf — Edge case
```

### मैं - अलग-थलग

जहां बग रहता है उसे सीमित करें। बांटो और राज करो की सोच का प्रयोग करें:

- क्या बग इनपुट पार्सिंग, लॉजिक या आउटपुट में है?
- कौन सी विशिष्ट लाइन या ब्लॉक गलत परिणाम उत्पन्न करता है?
- क्या आप इसे न्यूनतम असफल परीक्षण मामले में अलग कर सकते हैं?

### मैं - पहचानें

एक बार अलग हो जाने पर, मूल कारण निर्धारित करें - न कि केवल लक्षण:

- **लक्षण**: `[5, 5, 5]` के लिए रिटर्न `-inf`
- **मूल कारण**: `elif num > second` स्थिति डुप्लिकेट को संभाल नहीं पाती है। जब सभी तत्व समान होते हैं, तो `num > first` केवल एक बार सत्य होता है, और शेष समान तत्वों के लिए `num > second` कभी भी सत्य नहीं होता है।

### एफ - ठीक करें

नए बग पेश किए बिना मूल कारण को संबोधित करने वाला न्यूनतम समाधान लागू करें:

```python
def second_largest(nums):
    if len(nums) < 2:
        return None
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second and num != first:  # Handle case: distinct second
            second = num
    return second if second != float('-inf') else first  # All same → return that value
```

<ThinkAboutIt>रुको - क्या `second_largest([5, 5, 5])` को 5 या कोई नहीं लौटाना चाहिए? यह अस्पष्ट है, और एक वास्तविक साक्षात्कार में, आपको साक्षात्कारकर्ता से बिल्कुल इसी प्रकार का प्रश्न पूछना चाहिए। आवश्यकताओं को स्पष्ट करना डिबगिंग का हिस्सा है।</ThinkAboutIt>

### वी - सत्यापित करें

पुष्टि करें कि सभी मामलों के लिए फिक्स काम करता है - मूल विफल मामला, किनारे के मामले और पहले से गुजर रहे मामले:

```python
assert second_largest([3, 1, 4, 1, 5]) == 4    # Normal case
assert second_largest([5, 5, 5]) == 5            # Duplicates
assert second_largest([1, 2]) == 1               # Minimum valid input
assert second_largest([1]) is None               # Too few elements
assert second_largest([-1, -2, -3]) == -2        # Negative numbers
```

<Callout>बग को ठीक करने के बाद हमेशा अपने मूल परीक्षण मामलों को दोबारा चलाएं। एक बग को ठीक करते समय दूसरे को शामिल करना आश्चर्यजनक रूप से आम बात है। "सत्यापित करें" चरण उन प्रतिगमनों को पकड़ता है जिनके कारण आपको साक्षात्कार देना पड़ेगा।</Callout>

## सामान्य डिबगिंग साक्षात्कार प्रारूप

### प्रारूप 1: "यहां बग्गी कोड है - इसे ठीक करें"

आपको 1-3 बग वाला एक फ़ंक्शन प्राप्त होता है। आरआईआईएफवी लागू करें:
- कोड पढ़ें और आशय समझें
- असफलताओं का पता लगाने के लिए मानसिक परीक्षण के मामले चलाएँ
- प्रत्येक बग को ठीक करें और अपना तर्क स्पष्ट करें

### प्रारूप 2: "यह प्रणाली टूट गई है - इसका निदान करें"

आपको एक परिदृश्य दिया गया है: "उपयोगकर्ता रिपोर्ट करते हैं कि चेकआउट पृष्ठ कभी-कभी गलत कीमत दिखाता है।" आपको चाहिए:
- स्पष्ट प्रश्न पूछें ("कभी-कभी? क्या यह यादृच्छिक है, या यह एक पैटर्न का पालन करता है?")
- परिकल्पनाएँ बनाएं ("कैशिंग समस्या, दौड़ की स्थिति या मुद्रा रूपांतरण बग हो सकता है")
- जांच चरणों को प्राथमिकता क्रम में प्रस्तावित करें

### प्रारूप 3: "इस लाइव सिस्टम को डीबग करें" (जोड़ी डिबगिंग)

आप और साक्षात्कारकर्ता एक साथ डिबग करते हैं। वे टीम के साथी या सिस्टम की भूमिका निभा सकते हैं:
- अपनी विचार प्रक्रिया को मौखिक रूप से व्यक्त करें
- प्रस्तावित करें कि आप पहले क्या जाँचेंगे और क्यों
- उनके द्वारा प्रदान किए गए लॉग और मेट्रिक्स की व्याख्या करें

## डिबगिंग करते समय ज़ोर से सोचना

अकेले डिबगिंग और साक्षात्कार में डिबगिंग के बीच सबसे बड़ा अंतर यह है कि आपको वर्णन करने की आवश्यकता है। बिना किसी दबाव के इसे कैसे करें, यहां बताया गया है:

**अपनी टिप्पणियाँ बताएं**:
"मैं देख रहा हूं कि फ़ंक्शन एक सूची लेता है और उसे दूसरी सबसे बड़ी सूची लौटानी चाहिए। मैं एक सरल उदाहरण से इसका पता लगाना चाहता हूं..."

**परिकल्पनाएँ बनाएँ**:
"मेरा पहला विचार यह है कि यह डुप्लिकेट मान जैसे किनारे के मामलों को संभाल नहीं सकता है। मुझे [5, 5, 5] के साथ परीक्षण करने दें..."

**अपना तर्क स्पष्ट करें**:
"स्थिति `num > second` कभी सत्य नहीं होती जब सभी मान समान होते हैं क्योंकि `first` पहले से ही 5 है, और शेष 5s `second` से अधिक नहीं हैं जो कि `-inf` भी है... रुकिए, वास्तव में `5 > -inf` सत्य है, इसलिए दूसरे तत्व पर दूसरा 5 हो जाता है... हम्म, मुझे और अधिक ध्यान से पता लगाने दीजिए।"

**जब आप गलत हों तो स्वीकार करें**:
"वास्तव में, मेरी प्रारंभिक परिकल्पना गलत थी। मुझे इसे फिर से पता लगाने दीजिए..."

<FunFact>मनोवैज्ञानिक गैरी क्लेन के शोध में पाया गया कि विशेषज्ञ डिबगर्स नौसिखियों की तुलना में समस्याओं को 10 गुना तेजी से हल करते हैं, इसलिए नहीं कि वे अधिक होशियार हैं, बल्कि इसलिए कि वे पिछले अनुभव के पैटर्न को पहचानते हैं। यही कारण है कि विविध प्रकार के बग के साथ अभ्यास करना कच्ची बुद्धि से अधिक मायने रखता है।</FunFact>

## प्रिंट स्टेटमेंट का रणनीतिक उपयोग

एक कोडिंग साक्षात्कार में, प्रिंट स्टेटमेंट आपके डिबगर होते हैं। इनका रणनीतिक उपयोग करें:

```python
def merge_sorted_lists(list1, list2):
    result = []
    i = j = 0
    while i < len(list1) and j < len(list2):
        print(f"Comparing list1[{i}]={list1[i]} with list2[{j}]={list2[j]}")
        if list1[i] <= list2[j]:
            result.append(list1[i])
            i += 1
        else:
            result.append(list2[j])
            j += 1
        print(f"Result so far: {result}")

    # Don't forget: add remaining elements
    result.extend(list1[i:])
    result.extend(list2[j:])
    print(f"Final result: {result}")
    return result
```

**प्रभावी प्रिंट डिबगिंग के लिए युक्तियाँ**:
- निर्णय बिंदुओं पर प्रिंट करें (यदि/अन्यथा से पहले, लूप के अंदर)
- आउटपुट में वेरिएबल नाम और सूचकांक शामिल करें
- संदिग्ध बग स्थान से पहले और बाद में प्रिंट करें
- अपना अंतिम समाधान सबमिट करने से पहले प्रिंट निकालें या टिप्पणी करें

## डिबगिंग वितरित सिस्टम

वरिष्ठ स्तर के साक्षात्कार के लिए, आपसे वितरित सिस्टम को डीबग करने के बारे में पूछा जा सकता है:

### डिबगिंग टूलकिट

| उपकरण/तकनीक | इससे क्या पता चलता है |
|---|---|
| **लॉग** (संरचित, सहसंबंध आईडी के साथ) | घटनाओं का क्रम, त्रुटि विवरण |
| **मेट्रिक्स** (विलंबता, त्रुटि दर, थ्रूपुट) | रुझान और विसंगतियाँ |
| **निशान** (वितरित अनुरेखण) | सेवाओं में प्रवाह का अनुरोध करें |
| **स्वास्थ्य जांच** | किन घटकों का क्षरण होता है |

### व्यवस्थित दृष्टिकोण

1. **मेट्रिक्स डैशबोर्ड जांचें** — क्या यह वृद्धि है या क्रमिक गिरावट है?
2. **दायरा सीमित करें** — कौन सी सेवा, समापन बिंदु, या क्षेत्र प्रभावित है?
3. **हाल की तैनाती की जाँच करें** - "क्या बदला?" उच्चतम-संकेत प्रश्न है
4. **ट्रेस का पालन करें** - सेवाओं में विफल अनुरोध को ट्रैक करने के लिए सहसंबंध आईडी का उपयोग करें
5. **निर्भरता की जांच करें** - क्या डाउनस्ट्रीम सेवा (डेटाबेस, कैश, तृतीय-पक्ष एपीआई) इसका मूल कारण है?

## डिबगिंग राउंड के दौरान समय प्रबंधन

एक सामान्य डिबगिंग राउंड 30-45 मिनट का होता है। अपने समय का बजट बनाएं:

| चरण | समय | गतिविधि |
|---|---|---|
| **समझे** | 5 मिनट | कोड पढ़ें, समस्या स्पष्ट करें, अपेक्षित बनाम वास्तविक व्यवहार की पहचान करें |
| **पुनरुत्पादन** | 5 मिनट | बग को ट्रिगर करने वाले परीक्षण मामले बनाएं |
| **पृथक करें और पहचानें** | 10 मिनट | ट्रेसिंग और प्रिंट स्टेटमेंट का उपयोग करके मूल कारण को कम करें |
| **ठीक** | 5 मिनट | न्यूनतम, सही समाधान लागू करें |
| **सत्यापित करें** | 5 मिनट | किनारे के मामलों सहित सभी मामलों के विरुद्ध समाधान का परीक्षण करें |

<Callout>यदि आप 15 मिनट तक पहुँच चुके हैं और आपको बग नहीं मिला है, तो पीछे हटें और अपना दृष्टिकोण बदलें। समस्या कथन को दोबारा पढ़ें - हो सकता है कि आपने अपेक्षित व्यवहार को गलत समझा हो। एक बिल्कुल अलग परीक्षण केस आज़माएँ। कभी-कभी बग आपकी धारणाओं में होता है, कोड में नहीं।</Callout>

## जब आप फंस जाएं तो क्या करें

1. **समस्या कथन को दोबारा पढ़ें** - हो सकता है कि आपने गलत धारणा बना ली हो
2. **न्यूनतम परीक्षण केस आज़माएं** - सबसे छोटे केस में इनपुट कम करें जो अभी भी विफल रहता है
3. **पंक्ति दर पंक्ति ट्रेस करें** - यदि आवश्यक हो तो कलम और कागज के साथ, प्रत्येक चर को ट्रैक करें
4. **सीमाओं की जाँच करें** - पहला पुनरावृत्ति, अंतिम पुनरावृत्ति, खाली इनपुट
5. **साक्षात्कारकर्ता को समस्या समझाएं** - "रबर डक डिबगिंग" मानव दर्शकों के साथ भी काम करता है
6. **संकेत मांगें** - यह 10 मिनट तक मौन बैठने से कहीं बेहतर है

## चाबी छीनना

- **आरआईआईएफवी ढांचे का उपयोग करें**: पुन: प्रस्तुत करें → अलग करें → पहचानें → ठीक करें → सत्यापित करें। यह दबाव में काम करता है क्योंकि जब वृत्ति विफल हो जाती है तो यह आपके मस्तिष्क को एक प्रक्रिया देता है।
- **लगातार जोर से सोचें**: अपने अवलोकन, परिकल्पना और तर्क बताएं। डिबगिंग साक्षात्कार में चुप्पी आपकी दुश्मन है।
- **किनारे के मामलों को प्राथमिकता दें**: अधिकांश साक्षात्कार बग खाली इनपुट, डुप्लिकेट, नकारात्मक संख्याओं या सीमा स्थितियों में छिपे होते हैं।
- **प्रिंट स्टेटमेंट आपके मित्र हैं**: निर्णय बिंदुओं पर रणनीतिक रूप से उनका उपयोग करें, और अंतिम रूप देने से पहले उन्हें साफ़ करें।
- **जानें कि कब घूमना है**: यदि आपका दृष्टिकोण 10-15 मिनट के बाद काम नहीं कर रहा है, तो पीछे हटें और एक पूरी तरह से अलग कोण का प्रयास करें।
