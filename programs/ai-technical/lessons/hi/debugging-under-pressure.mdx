# दबाव में Debugging

जब कोई आपको देख रहा हो और timer चल रहा हो, तब code debug करने का तनाव अलग ही होता है। हथेलियाँ पसीजती हैं, दिमाग blank हो जाता है, और अचानक for loop भी याद नहीं रहता। हर engineer वहाँ रहा है। जो candidates टूट जाते हैं और जो चमकते हैं, उनके बीच फर्क raw talent नहीं है। फर्क है एक systematic process का, जो तब भी काम करे जब आपका दिमाग panic करना चाहता हो। यह पाठ आपको वही process देता है।

## RIIFV Debugging Framework

जब interview में आपको buggy code दिया जाए, तो तुरंत bug खोजने के लिए scan करने की इच्छा रोकें। इसके बजाय यह five-step framework follow करें:

### R: Reproduce

Confirm करें कि bug मौजूद है और उसके symptoms समझें।

- Expected behaviour क्या है?
- Actual behaviour क्या है?
- Bug किन inputs पर आता है?

```python
# You're told this function should return the second largest element
def second_largest(nums):
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second:
            second = num
    return second

# Step 1: Reproduce with test cases
print(second_largest([3, 1, 4, 1, 5]))  # Expected: 4, Got: 4 ✓
print(second_largest([5, 5, 5]))         # Expected: 5, Got: -inf ✗ — BUG!
print(second_largest([1]))               # Expected: None?, Got: -inf — Edge case
```

### I: Isolate

Bug कहाँ है, इसे narrow करें। Divide-and-conquer thinking इस्तेमाल करें:

- Bug input parsing में है, logic में, या output में?
- कौन सी specific line या block wrong result पैदा कर रहा है?
- क्या आप इसे minimal failing test case तक isolate कर सकते हैं?

### I: Identify

Isolate होने के बाद root cause तय करें, सिर्फ symptom नहीं:

- **Symptom**: `[5, 5, 5]` के लिए `-inf` return होता है
- **Root cause**: `elif num > second` condition duplicates handle नहीं करती। जब सभी elements equal हों, `num > first` सिर्फ एक बार true होता है, और बाकी equal elements के लिए `num > second` कभी true नहीं होता।

### F: Fix

Root cause को address करने वाला minimal fix apply करें, बिना नए bugs introduce किए:

```python
def second_largest(nums):
    if len(nums) < 2:
        return None
    first = second = float('-inf')
    for num in nums:
        if num > first:
            second = first
            first = num
        elif num > second and num != first:  # Handle case: distinct second
            second = num
    return second if second != float('-inf') else first  # All same → return that value
```

<ThinkAboutIt>रुकिए: क्या `second_largest([5, 5, 5])` को 5 return करना चाहिए या None? यह ambiguous है, और real interview में यही वह सवाल है जो आपको interviewer से पूछना चाहिए। Requirements clarify करना debugging का हिस्सा है।</ThinkAboutIt>

### V: Verify

Confirm करें कि fix सभी cases पर काम करता है: original failing case, edge cases और पहले passing cases:

```python
assert second_largest([3, 1, 4, 1, 5]) == 4    # Normal case
assert second_largest([5, 5, 5]) == 5            # Duplicates
assert second_largest([1, 2]) == 1               # Minimum valid input
assert second_largest([1]) is None               # Too few elements
assert second_largest([-1, -2, -3]) == -2        # Negative numbers
```

<Callout>Bug fix करने के बाद अपने original test cases हमेशा फिर से run करें। एक bug fix करते हुए दूसरा introduce करना बहुत common है। "Verify" step वही regressions पकड़ता है जो interview cost कर सकते हैं।</Callout>

## Common Debugging Interview Formats

### Format 1: "यह Buggy Code है, इसे Fix करें"

आपको 1-3 bugs वाला function मिलता है। RIIFV apply करें:
- Code पढ़ें और intent समझें
- Failures खोजने के लिए mental test cases run करें
- हर bug fix करें और अपनी reasoning explain करें

### Format 2: "यह System Broken है, Diagnose करें"

आपको scenario दिया जाता है: "Users report कर रहे हैं कि checkout page कभी-कभी wrong price दिखाता है।" आपको यह करना होता है:
- Clarifying questions पूछें ("Sometimes? Random है या कोई pattern follow करता है?")
- Hypotheses बनाएँ ("Caching issue, race condition या currency conversion bug हो सकता है")
- Priority order में investigation steps propose करें

### Format 3: "यह Live System Debug करें" (Pair Debugging)

आप और interviewer साथ debug करते हैं। वे teammate या system की role play कर सकते हैं:
- अपना thought process verbalise करें
- पहले क्या check करेंगे और क्यों, propose करें
- Logs और metrics interpret करें जो वे देते हैं

## Debugging के दौरान सोचकर बोलना

अकेले debugging और interview में debugging के बीच सबसे बड़ा फर्क है कि आपको narrate करना पड़ता है। इसे forced लगे बिना ऐसे करें:

**अपनी observations बताएं**:
"मुझे दिख रहा है कि function list लेता है और second largest return करना चाहिए। मैं simple example से trace करता हूँ..."

**Hypotheses बनाएँ**:
"मेरा पहला विचार है कि यह duplicate values जैसे edge cases handle नहीं कर रहा होगा। मैं [5, 5, 5] से test करता हूँ..."

**अपनी reasoning समझाएँ**:
"Condition `num > second` कभी true नहीं होगी जब सभी values equal हों क्योंकि `first` पहले से 5 है, और बाकी 5s `second` से greater नहीं हैं जो `-inf` है... रुकिए, actually `5 > -inf` true है, इसलिए second दूसरे element पर 5 हो जाता है... मुझे इसे और carefully trace करना चाहिए।"

**गलत होने पर स्वीकार करें**:
"Actually, मेरी initial hypothesis incorrect थी। मैं इसे फिर से trace करता हूँ..."

<FunFact>Psychologist Gary Klein के research ने पाया कि expert debuggers novices से 10x तक तेज़ problems solve करते हैं, इसलिए नहीं कि वे ज़्यादा smart हैं, बल्कि इसलिए कि वे past experience से patterns पहचानते हैं। इसी वजह से diverse bug types के साथ practice raw intelligence से अधिक मायने रखती है।</FunFact>

## Print Statements का Strategic Use

Coding interview में print statements आपका debugger हैं। उन्हें strategically use करें:

```python
def merge_sorted_lists(list1, list2):
    result = []
    i = j = 0
    while i < len(list1) and j < len(list2):
        print(f"Comparing list1[{i}]={list1[i]} with list2[{j}]={list2[j]}")
        if list1[i] <= list2[j]:
            result.append(list1[i])
            i += 1
        else:
            result.append(list2[j])
            j += 1
        print(f"Result so far: {result}")

    # Don't forget: add remaining elements
    result.extend(list1[i:])
    result.extend(list2[j:])
    print(f"Final result: {result}")
    return result
```

**Effective print debugging tips**:
- Decision points पर print करें (if/else से पहले, loops के अंदर)
- Output में variable names और indices शामिल करें
- Suspected bug location से पहले और बाद में print करें
- Final solution submit करने से पहले prints remove या comment out करें

## Distributed Systems Debugging

Senior-level interviews में आपसे distributed systems debugging पर पूछा जा सकता है:

### Debugging Toolkit

| Tool/Technique | What It Reveals |
|---|---|
| **Logs** (structured, with correlation IDs) | Events का sequence, error details |
| **Metrics** (latency, error rate, throughput) | Trends और anomalies |
| **Traces** (distributed tracing) | Services के across request flow |
| **Health checks** | कौन से components degraded हैं |

### Systematic Approach

1. **Metrics dashboards check करें**: spike है या gradual degradation?
2. **Scope narrow करें**: कौन सा service, endpoint या region affected है?
3. **Recent deployments check करें**: "what changed?" सबसे high-signal question है
4. **Trace follow करें**: failing request को services across track करने के लिए correlation IDs use करें
5. **Dependencies check करें**: क्या downstream service (database, cache, third-party API) root cause है?

```
User reports slow checkout
→ Metrics show p99 latency spike at 14:30
→ Correlated with deployment of payment-service v2.3.1
→ Traces show payment-service waiting 10s on database query
→ Database query plan changed due to missing index after schema migration
→ Root cause: migration in v2.3.1 dropped an index
→ Fix: recreate index, add migration test
```

## Debugging Rounds में Time Management

Typical debugging round 30-45 मिनट का होता है। अपना time budget करें:

| Phase | Time | Activity |
|---|---|---|
| **Understand** | 5 min | Code पढ़ें, problem clarify करें, expected vs actual behaviour पहचानें |
| **Reproduce** | 5 min | Bug trigger करने वाले test cases बनाएँ |
| **Isolate & Identify** | 10 min | Tracing और print statements से root cause narrow करें |
| **Fix** | 5 min | Minimal, correct fix apply करें |
| **Verify** | 5 min | Edge cases सहित सभी cases पर fix test करें |

<Callout>अगर 15 मिनट में bug नहीं मिला, तो पीछे हटें और approach बदलें। Problem statement फिर से पढ़ें। शायद expected behaviour गलत समझा है। बिल्कुल अलग test case आज़माएँ। कई बार bug आपके assumptions में होता है, code में नहीं।</Callout>

## जब आप अटक जाएँ तो क्या करें

1. **Problem statement फिर से पढ़ें**: आपने कोई incorrect assumption बना लिया हो सकता है
2. **Minimal test case आज़माएँ**: input को सबसे छोटे failing case तक reduce करें
3. **Line by line trace करें**: ज़रूरत हो तो pen and paper से, हर variable track करें
4. **Boundaries check करें**: first iteration, last iteration, empty input
5. **Problem interviewer को explain करें**: "rubber duck debugging" human audience के साथ भी काम करता है
6. **Hint माँगें**: 10 मिनट चुप बैठने से यह कहीं बेहतर है

## मुख्य बातें

- **RIIFV framework इस्तेमाल करें**: Reproduce → Isolate → Identify → Fix → Verify. Pressure में यह इसलिए काम करता है क्योंकि instinct fail होने पर brain को process देता है।
- **लगातार सोचकर बोलें**: observations, hypotheses और reasoning narrate करें। Debugging interview में silence आपका enemy है।
- **Edge cases prioritise करें**: अधिकतर interview bugs empty inputs, duplicates, negative numbers या boundary conditions में छिपे होते हैं।
- **Print statements आपके साथी हैं**: decision points पर strategically use करें, और finalise करने से पहले साफ़ करें।
- **कब pivot करना है जानें**: अगर approach 10-15 मिनट में काम नहीं कर रही, तो पीछे हटकर बिल्कुल अलग angle आज़माएँ।
