# सिस्टम डिज़ाइन की बुनियाद

System design interview वह जगह है जहाँ senior engineers बनते या टूटते हैं। Coding interview में अक्सर स्पष्ट सही उत्तर होता है, लेकिन system design आपकी ambiguity संभालने, trade-offs करने और architectural decisions communicate करने की क्षमता जाँचता है। अच्छी बात यह है कि हर सवाल के लिए काम आने वाला repeatable framework है। और उससे भी अच्छी बात: building blocks समझ आने के बाद आप URL shortener से लेकर global-scale messaging platform तक कुछ भी design कर सकते हैं। आइए यह toolkit बनाते हैं।

## 4-Step Framework

हर system design interview को इस structure का पालन करना चाहिए। Interviewers इसकी अपेक्षा करते हैं, और यह आपको premature detail में भटकने से बचाता है।

### Step 1: Requirements Clarification (5 मिनट)

सवाल पूछे बिना कभी design शुरू न करें। यहीं आप product thinking दिखाते हैं।

**Functional requirements**: system क्या करता है:
- "क्या users groups को messages भेज पाएँगे, या सिर्फ 1:1?"
- "क्या हमें real-time notifications चाहिए?"
- "Feed chronological होना चाहिए या ranked?"

**Non-functional requirements**: system कितनी अच्छी तरह करता है:
- "Expected read/write ratio क्या है?"
- "कितनी latency acceptable है?"
- "क्या strong consistency चाहिए या eventual consistency ठीक है?"

<Callout>Clarifying questions पूछना weakness नहीं है। यह सबसे senior-engineer वाली चीज़ है। Interviewers जानबूझकर requirements vague छोड़ते हैं ताकि देखें कि आप clarify करेंगे या आँख बंद करके design शुरू कर देंगे।</Callout>

### Step 2: Back-of-Envelope Estimation (3 मिनट)

जल्दी की गई calculation आपके design को reality में टिकाती है और over-engineering या under-engineering से बचाती है।

```
Example: Design Twitter

Daily Active Users (DAU): 300M
Tweets per day: 300M × 2 = 600M tweets/day
Reads per day: 300M × 100 = 30B reads/day (read-heavy)
Tweets per second: 600M / 86400 ≈ 7,000 writes/sec
Reads per second: 30B / 86400 ≈ 350,000 reads/sec
Storage per tweet: ~300 bytes text + metadata ≈ 500 bytes
Daily storage: 600M × 500B = 300GB/day ≈ 110TB/year
```

ये numbers बताते हैं: यह system बहुत read-heavy है, caching चाहिए, और storage बहुत तेज़ी से बढ़ेगा।

### Step 3: High-Level Design (10 मिनट)

Major components के साथ architecture draw करें। सरल शुरुआत करें, फिर ज़रूरत के अनुसार complexity जोड़ें।

```
Client → Load Balancer → API Servers → Service Layer
                                          ↓
                              ┌───────────┼───────────┐
                              ↓           ↓           ↓
                           Database     Cache      Message Queue
                                          ↓           ↓
                                       CDN        Workers
```

मुख्य user flows समझाएँ:
- "जब user tweet post करता है, API server उसे validate करता है, database में लिखता है, और fan-out service को भेजता है..."
- "जब user feed खोलता है, हम पहले cache check करते हैं..."

### Step 4: Deep Dive (15 मिनट)

Interviewer 1-2 areas चुनकर गहराई में जाएगा। Trade-offs detail में discuss करने के लिए तैयार रहें।

<ThinkAboutIt>अगर आप notification system design कर रहे हों, तो क्या आप सभी followers को तुरंत notifications push करेंगे (fan-out on write) या हर user के request करने पर feed compute करेंगे (fan-out on read)? Millions followers वाले users के लिए trade-offs क्या हैं?</ThinkAboutIt>

## Building Blocks

इन्हें Lego pieces की तरह सोचें। हर system design इन्हीं blocks की अलग arrangement है।

### Load Balancers

Traffic को कई servers में बाँटते हैं। तीन strategies जानें:
- **Round Robin**: सरल, बराबर distribution
- **Least Connections**: सबसे कम active connections वाले server को भेजता है
- **Consistent Hashing**: request content के आधार पर route करता है, caching में उपयोगी

### Caches

सबसे अधिक प्रभाव डालने वाला performance ऑप्टिमाइज़ेशन। ये cache patterns याद रखें:

```
Write-through:  App → Cache → DB  (consistent, higher write latency)
Write-back:     App → Cache ... → DB  (fast writes, risk of data loss)
Cache-aside:    App checks cache → miss → read DB → populate cache
```

**Cache eviction**: LRU (Least Recently Used) interviews में default answer है। Time-sensitive data के लिए TTL (Time-To-Live) mention करें।

<FunFact>Jeff Dean के प्रसिद्ध paper के अनुसार, memory के बजाय disk तक जाने वाला एक cache miss लगभग 100x latency जोड़ता है। इसी वजह से caching strategy अक्सर सबसे प्रभावशाली design decision होती है। cache से पढ़ना (1ms), disk से पढ़ना (10ms), और cross-datacenter read (150ms) अलग-अलग orders of magnitude हैं।</FunFact>

### Databases

| Type | कब उपयोग करें | Examples |
|---|---|---|
| **Relational (SQL)** | ACID transactions, complex queries, structured data | PostgreSQL, MySQL |
| **Document Store** | Flexible schemas, nested data, rapid iteration | MongoDB, DynamoDB |
| **Wide-Column** | Massive scale, time-series, write-heavy | Cassandra, HBase |
| **Graph** | Relationship-heavy data, social networks | Neo4j, Neptune |

**Database scaling**:
- **Vertical scaling**: बड़ी machine, लेकिन सीमित ceiling
- **Read replicas**: read और write traffic अलग करना
- **Sharding**: data को कई databases में partition करना, जैसे user ID या geography से

### Message Queues

Producers और consumers को decouple करते हैं। इनके लिए essential हैं:
- Asynchronous processing, जैसे signup के बाद email भेजना
- Load levelling, traffic spikes absorb करना
- Event-driven architectures

```
Producer → [Message Queue] → Consumer
           (Kafka, SQS,      (Workers that
            RabbitMQ)          process at
                               their own pace)
```

### CDNs (Content Delivery Networks)

Static content (images, CSS, JS) को users के पास edge servers पर cache करते हैं। जब system media serve करता हो या global user base हो, तो CDN mention करें।

## Classic System Design Questions

### URL Shortener design करें (जैसे bit.ly)

**मुख्य decisions**:
- Short codes बनाने के लिए base62 encoding (a-z, A-Z, 0-9) इस्तेमाल करें
- Uniqueness के लिए counter या hash-based approach इस्तेमाल करें
- Read-heavy system है, इसलिए popular URLs को aggressively cache करें
- Database: simple key-value store (short_code → original_url)

```
POST /shorten  { "url": "https://example.com/very/long/path" }
→ Returns: { "short_url": "https://bit.ly/abc123" }

GET /abc123
→ 301 Redirect to original URL (301 = permanent, cacheable by browser)
```

### Chat System design करें (जैसे WhatsApp)

**मुख्य decisions**:
- Real-time bidirectional communication के लिए WebSockets
- Message storage: write-optimised database (Cassandra)
- Online presence: timeout वाला heartbeat mechanism
- Group messages: message queue से सभी group members को fan-out

### News Feed design करें (जैसे Twitter/Facebook)

**मुख्य decisions**:
- 10K से कम followers वाले users के लिए **fan-out on write** (feeds pre-compute करें)
- Celebrity users के लिए **fan-out on read** (millions feeds में लिखने से बचने के लिए request पर compute करें)
- Hybrid approach: अधिकतर systems दोनों strategies इस्तेमाल करते हैं
- Ranking: pure chronological order के बजाय ML-based relevance scoring

## Estimation Questions संभालना

Interviewers "Y को कितने X चाहिए?" पूछना पसंद करते हैं। ये anchors इस्तेमाल करें:

| Metric | Value |
|---|---|
| एक web server का QPS | ~1,000-10,000 |
| एक database का QPS | ~1,000-5,000 |
| Cache read latency | ~1ms |
| Database read latency | ~5-10ms |
| Cross-datacenter latency | ~100-150ms |
| 1 million seconds | ~12 days |
| 1 billion seconds | ~32 years |

## System Design के दौरान Communication Tips

आपकी communication आपके डिज़ाइन जितनी ही महत्वपूर्ण है। इन आदतों का अभ्यास करें:

1. **अपने विचार structure करें**: "मैं requirements से शुरू करूँगा, फिर estimation, फिर high-level डिज़ाइन।"
2. **Trade-offs स्पष्ट कहें**: "Consistency के लिए SQL इस्तेमाल कर सकते हैं या scale के लिए NoSQL.  हमारे read-heavy workload को देखते हुए मैं caching layer के साथ NoSQL की ओर झुकूँगा।"
3. **जो नहीं जानते उसे स्वीकार करें**: "Kafka के exact replication factor को लेकर मुझे पक्का नहीं है, लेकिन मुझे पता है कि यह configurable है और आम तौर पर 3 रखा जाता है।"
4. **Interviewer से check-in करें**: "मैंने high-level design cover कर लिया है। क्या आप database schema या caching strategy में गहराई में जाना चाहेंगे?"

<Callout>System design interviews में सबसे बड़ी गलती बहुत जल्दी बहुत गहराई में जाना है। पहले 5 मिनट में database schema design करने की इच्छा रोकें। पहले wide जाएँ, फिर interviewer जिस क्षेत्र को explore करना चाहता है उसके आधार पर narrow करें।</Callout>

## मुख्य बातें

- **4-step framework follow करें**: requirements → estimation → high-level design → गहराई में जाना। यह हर बार काम करता है।
- **Building blocks जानें**: load balancers, caches, databases, message queues और CDNs system design की vocabulary हैं।
- **Trade-offs ही असली बात हैं**: perfect designs नहीं होते, सिर्फ trade-offs होते हैं। उन्हें स्पष्ट रूप से समझाएँ।
- **Estimation design को जमीन पर टिकाती है**: quick back-of-envelope math over-engineering और under-engineering दोनों से बचाता है।
- **Communication आधी grade है**: विचारों को structure करें, assumptions बताएं, और नियमित रूप से interviewer से check-in करें।
- **Real systems से अभ्यास करें**: Twitter, WhatsApp, YouTube और Uber सच में कैसे काम करते हैं, यह पढ़ें। उनके engineering blogs सोने की खान हैं।
