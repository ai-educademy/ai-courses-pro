# Práticas recomendadas de codificação ao vivo

Você pode resolver mídias LeetCode enquanto dorme, mas coloque um ser humano do outro lado de um compartilhamento de tela e de repente seus dedos esquecem para onde vão os pontos e vírgulas. As entrevistas de codificação ao vivo são uma performance – onde você é julgado não apenas pelo código final, mas também por como chegar lá. Os candidatos aprovados nem sempre são os programadores mais rápidos; são eles que se comunicam com clareza, lidam com contratempos com elegância e escrevem códigos legíveis sob pressão. Esta lição ensina você a ser esse candidato.

## Configurando seu ambiente

As primeiras impressões são importantes. Ao abrir o CoderPad, HackerRank ou VS Code Live Share, o entrevistador já está formando opiniões.

### Dicas específicas da plataforma

**CoderPad** (mais comum):
- Escolha seu idioma no menu suspenso antes do início da entrevista
- Use o botão Executar integrado – saiba que a saída aparece no painel do console
- Recuo automático e realce de sintaxe estão disponíveis

**HackerRank**:
- Leia a declaração do problema com atenção - as entradas vêm de stdin
- Os casos de teste são executados automaticamente; entenda o formato esperado
- Casos de teste personalizados podem ser adicionados no painel esquerdo

**Compartilhamento ao vivo do VS Code/Google Docs**:
- Sem preenchimento automático ou destaque de sintaxe (possivelmente)
- Recuar consistentemente à mão – mostra disciplina
- Para Google Docs: use uma fonte monoespaçada (Courier New)

<Callout>Antes de qualquer entrevista de codificação ao vivo, faça uma verificação de ambiente de 5 minutos. Abra a plataforma, escreva um “Hello World” e execute-a. Atrapalhar-se com a plataforma durante a entrevista desperdiça minutos preciosos e abala sua confiança.</Callout>

### Escolha do idioma

Escolha o idioma em que você é mais fluente, e não aquele que você acha que parece impressionante. Dito isto, aqui está o que considerar:

| Idioma | Prós | Contras |
|---|---|---|
| **Píton** | Biblioteca padrão rica e concisa, rápida de escrever | Tempo de execução mais lento, tipo ambiguidade |
| **Java** | Digitação forte, os entrevistadores esperam isso para o design do sistema | Detalhado, clichê |
| **JavaScript** | Bom para funções de front-end, flexível | Coerção de tipo peculiar, menos comum para algoritmos |
| **C++** | Tempo de execução rápido, mostra habilidades de baixo nível | STL detalhado e sujeito a erros |

## O protocolo Talk-Aloud

Esta é a habilidade de entrevista mais impactante e aquela que a maioria dos candidatos negligencia. Seu monólogo interno precisa se tornar um monólogo externo.

### O que dizer em cada fase

**Lendo o problema** (minutos 0-3):
- "Deixe-me ter certeza de que entendi o problema: precisamos encontrar..."
- "Algumas questões esclarecedoras: a entrada pode estar vazia? Pode haver números negativos?"
- "Deixe-me pensar em alguns exemplos para verificar meu entendimento."

**Planejando sua abordagem** (minutos 3 a 7):
- "Meu primeiro pensamento é uma abordagem de força bruta usando loops aninhados - isso seria O(n²)."
- "Acho que podemos fazer melhor com um mapa hash para rastrear os elementos que vimos."
- "Deixe-me pensar em casos extremos: entrada vazia, elemento único, todas duplicadas..."

**Escrevendo código** (minutos 7 a 25):
- "Vou começar configurando a assinatura da função e lidando com casos extremos."
- "Agora estou iterando pelo array e para cada elemento que estou verificando..."
- "Estou escolhendo um mapa hash aqui porque precisamos de pesquisas O(1)."

**Teste** (minutos 25-30):
- "Deixe-me seguir com o exemplo: para entrada [2, 7, 11, 15] com alvo 9..."
- "Eu também deveria verificar o caso extremo de um array vazio..."
- "Hmm, minha saída para este caso não corresponde. Deixe-me ver a linha 5..."

<ThinkAboutIt>Pense na última vez em que você resolveu um problema silenciosamente. Qual foi o seu processo de decisão interno? Como você externalizaria cada uma dessas microdecisões? Pratique verbalizar seu pensamento mesmo ao resolver problemas sozinho – isso se torna natural durante a entrevista.</ThinkAboutIt>

## Escrevendo código limpo sob pressão

Sob estresse, a qualidade do código é a primeira vítima. Combata isso com hábitos deliberados:

### Use nomes significativos

```python
# Under pressure (what many candidates write)
def solve(a, t):
    d = {}
    for i, v in enumerate(a):
        if t - v in d:
            return [d[t - v], i]
        d[v] = i

# What you should write
def two_sum(nums, target):
    seen = {}
    for index, num in enumerate(nums):
        complement = target - num
        if complement in seen:
            return [seen[complement], index]
        seen[num] = index
```

A segunda versão leva 10 segundos extras para ser escrita, mas torna a depuração 10 vezes mais fácil – e impressiona o entrevistador.

### Funções auxiliares são suas amigas

```python
# Extract reusable logic into named functions
def is_valid_move(board, row, col):
    return 0 <= row < len(board) and 0 <= col < len(board[0])

def get_neighbours(row, col):
    return [(row + dr, col + dc) for dr, dc in [(0, 1), (0, -1), (1, 0), (-1, 0)]]
```

As funções auxiliares reduzem a carga cognitiva, tornam seu código autodocumentado e permitem que você diga "Implementarei esse auxiliar mais tarde — por enquanto, suponha que funcione".

<FunFact>Estudos sobre programação em pares (que simulam entrevistas de codificação ao vivo) mostram que pares produzem código com 15% menos defeitos do que programadores solo, mas levam cerca de 15% mais tempo. Em uma entrevista, a dinâmica do “par” com o entrevistador realmente funciona a seu favor – eles podem detectar erros que você não perceberia sozinho, se você se comunicasse abertamente.</FunFact>

## Lidando com dicas com elegância

Os entrevistadores dão dicas. Não é um sinal de fracasso – é uma conversa. Como você responde é importante:

**Boas respostas às dicas**:
- "Esse é um ótimo ponto - acho que você está sugerindo que eu use uma pilha aqui. Deixe-me pensar em como isso ajuda..."
- "Ah, entendo - se eu classificar a entrada primeiro, a abordagem de dois ponteiros se torna possível. Deixe-me reestruturar."
- "Obrigado, eu não tinha considerado esse caso extremo. Deixe-me adicionar tratamento para números negativos."

**Respostas ruins**:
- Ignorando a dica e continuando sua abordagem
- "Eu sei, eu estava prestes a fazer isso" (defensivo)
- Parecendo derrotado ou confuso

<Callout>Um entrevistador que dá dicas está tentando ajudá-lo a ter sucesso. Muitos candidatos são contratados após receberem diversas dicas – o que importa é que você entenda a dica, se adapte e mostre que pode colaborar. Seguir teimosamente uma abordagem fracassada após uma dica é um sinal de alerta.</Callout>

## Gerenciamento de tempo: o plano de 35 minutos

Para um problema típico de codificação de 35 minutos:

| Fase | Minutos | O que fazer |
|---|---|---|
| **Esclarecer** | 0-5 | Leia o problema, faça perguntas, escreva exemplos |
| **Plano** | 5-8 | Discuta a abordagem e a complexidade, obtenha a adesão do entrevistador |
| **Código** | 8-25 | Escreva código limpo e legível com talk-aloud |
| **Teste** | 25-30 | Rastreie os exemplos manualmente, verifique os casos extremos |
| **Otimizar** | 30-35 | Discutir possíveis melhorias e abordagens alternativas |

### Erros comuns de tempo

1. **Gastar 15 minutos codificando sem um plano** – você acaba reescrevendo
2. **Nunca testar** — enviar e dizer “Acho que funciona” é um sinal de alerta
3. **Otimizar antes de obter uma solução funcional** — resolva primeiro e depois melhore
4. **Gastar muito tempo em uma abordagem** — se não funcionar após 10 minutos, pergunte ao entrevistador se há uma orientação melhor

## Testando sua solução antes de dizer "Concluído"

Nunca diga "Terminei" sem testar. Aqui está uma abordagem sistemática:

```python
# Step 1: Trace through the provided example
# Input: [1, 2, 3, 4, 5], target = 9
# i=0: complement=9-1=8, not in seen, seen={1:0}
# i=1: complement=9-2=7, not in seen, seen={1:0, 2:1}
# ...
# i=3: complement=9-4=5, not in seen, seen={1:0, 2:1, 3:2, 4:3}
# i=4: complement=9-5=4, 4 IS in seen at index 3 → return [3, 4] ✓

# Step 2: Test edge cases
# Empty array: [] → should return [] or None
# Single element: [5], target=5 → no pair possible
# Negative numbers: [-1, 2, 3], target=1 → [-1, 2] at indices [0, 1]
# Duplicates: [3, 3], target=6 → should return [0, 1]
```

Verbalize este processo de teste. Ele mostra meticulosidade e detecta bugs antes do entrevistador.

## O que fazer quando você está preso

Ficar preso não é um fracasso – ficar preso silenciosamente é. Aqui está o seu plano de fuga:

1. **Reafirme o problema** – às vezes dizer isso em voz alta revela um novo ângulo
2. **Trabalhar com um pequeno exemplo** — resolver manualmente um pequeno caso pode revelar o algoritmo
3. **Pense em problemas relacionados** — "Isso me lembra o padrão de janela deslizante..."
4. **Considere as restrições** — se n ≤ 1000, uma solução O(n²) pode ser aceitável
5. **Simplifique o problema** — resolva primeiro uma versão mais simples e depois adicione complexidade
6. **Peça uma dica** — "Estou pensando em usar um mapa hash para rastrear frequências, mas não tenho certeza de como lidar com a redução da janela. Você poderia me indicar a direção certa?"

```python
# When stuck, try the "brute force first" strategy:
# 1. Write the O(n²) solution — it's usually straightforward
# 2. Identify the bottleneck (usually the inner loop)
# 3. Ask: "Can I eliminate this inner loop with a data structure?"
# 4. This often leads naturally to the optimal solution
```

## A discussão pós-solução

Depois que sua solução funcionar, a entrevista ainda não acabou. Esteja pronto para:

- **"Qual é a complexidade de tempo e espaço?"** — tenha sempre isso pronto
- **"Você consegue otimizá-lo?"** — discuta as compensações mesmo que você não consiga implementar a tempo
- **"Como isso lidaria com casos extremos?"** — mostre que você pensou sobre cenários de produção
- **"E se a entrada fosse 1 bilhão de elementos?"** - isso gira em torno do pensamento de design de sistema

```python
# Example post-solution discussion:
# "My solution is O(n) time and O(n) space.
#  The space is used by the hash map which stores at most n elements.
#  If memory is a constraint, we could sort the array first and use
#  two pointers for O(n log n) time and O(1) space — but we'd need
#  to modify the input array or create a copy.
#  For 1 billion elements, we might need to partition the data
#  and process in chunks, or use external sorting."
```

## Principais conclusões

- **Fale em voz alta continuamente**: o silêncio é seu inimigo — narre seu processo de resolução de problemas do início ao fim.
- **Esclareça antes de codificar**: 5 minutos de perguntas economizam 15 minutos de codificação na direção errada.
- **Escreva código limpo mesmo sob pressão**: nomes significativos, funções auxiliares e abordagem básica facilitam a depuração e impressionam os entrevistadores.
- **Teste sistematicamente**: analise exemplos e casos extremos antes de declarar "pronto".
- **Lidar com dicas e contratempos com elegância**: ficar preso é normal – como você se recupera é o que importa.
- **Gerencie seu tempo**: planejar (5min) → código (17min) → teste (5min) → discutir (5min). Ajuste com base no problema, mas nunca pule o teste.
