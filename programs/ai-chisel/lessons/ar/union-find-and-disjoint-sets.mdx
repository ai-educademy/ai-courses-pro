## مشكلة الاتصال

نظرًا لوجود شبكة من العقد، فإنك تتلقى باستمرار نوعين من الاستعلامات: *ربط العقدة A بالعقدة B* و *هل A وB متصلان؟* القيام بذلك باستخدام BFS/DFS يعني اجتياز الرسم البياني لكل استعلام - وهو بطيء للغاية بالنسبة لملايين العمليات.

**Union-Find** يجيب على كليهما في وقت شبه ثابت.

## النهج الساذج - البحث السريع

قم بتخزين معرف المكون لكل عقدة. للتحقق من الاتصال، قارن المعرفات في O(1). لكن دمج مكونين يفرض عليك تحديث كل عضو في مجموعة واحدة - O(n) لكل اتحاد.

```
IDs:  [0, 0, 0, 3, 3]
       └─group 0─┘ └group 3┘
union(0, 3) → update all 3s to 0 → O(n)
```

نحن بحاجة إلى شيء أفضل.

## هيكل بيانات Union-Find

تشير كل عقدة إلى **أصل**. جذر كل شجرة هو ممثل المكون. ترتبط العقدتان فقط إذا كانتا تشتركان في نفس الجذر.

```python
class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n
```

## البحث باستخدام ضغط المسار

يمكن أن يكون المشي على مؤشرات الوالدين بطيئًا في شجرة عميقة. **ضغط المسار** يعمل على تسوية الشجرة عن طريق توجيه كل عقدة تتم زيارتها مباشرةً إلى الجذر.

```python
def find(self, x):
    if self.parent[x] != x:
        self.parent[x] = self.find(self.parent[x])
    return self.parent[x]
```

قبل وبعد العثور على العقدة 4:

```
Before:  0←1←2←3←4     After:  0←1
                                0←2
                                0←3
                                0←4
```

## الاتحاد حسب الرتبة

قم دائمًا بإرفاق الشجرة الأقصر أسفل الشجرة الأطول. وهذا يحافظ على لوغاريتمي ارتفاع الشجرة ويمنع تدهور السلاسل.

```python
def union(self, x, y):
    rx, ry = self.find(x), self.find(y)
    if rx == ry:
        return False
    if self.rank[rx] < self.rank[ry]:
        rx, ry = ry, rx
    self.parent[ry] = rx
    if self.rank[rx] == self.rank[ry]:
        self.rank[rx] += 1
    return True
```

## خوارزمية MST لـ Kruskal

تعمل Union-Find على تشغيل **خوارزمية Kruskal** للحد الأدنى من الأشجار الممتدة:

1. قم بفرز جميع الحواف حسب الوزن
2. لكل حافة (u، v)، إذا كان `find(u) ≠ find(v)`، أضفه و`union(u, v)`
3. توقف عندما يكون لديك n - 1 من الحواف

يمنع Union-Find الدورات عن طريق رفض الحواف التي تشترك نقاطها النهائية في الجذر بالفعل. الوقت الإجمالي: **O(E log E)** يهيمن عليه الفرز.

<ThinkAboutIt>يستخدم Kruskal Union-Find للكشف عن الدورات. كيف يمكنك اكتشاف دورة باستخدام DFS بدلاً من ذلك، ولماذا يعتبر Union-Find أكثر طبيعية هنا؟ </ThinkAboutIt>

## المشاكل الكلاسيكية

### عدد المكونات المتصلة

تهيئة Union-Find باستخدام العقد n. قم بمعالجة كل حافة بـ `union`. عد الجذور المميزة في النهاية.

### دمج الحسابات (LeetCode 721)

كل حساب لديه رسائل البريد الإلكتروني. إذا كان هناك حسابان يشتركان في البريد الإلكتروني، فإنهما ينتميان إلى نفس الشخص. توحيد الحسابات عن طريق رسائل البريد الإلكتروني المشتركة، ثم تجميعها وفرزها.

### اتصال متكرر (LeetCode 684)

إذا كانت لديك شجرة بالإضافة إلى حافة إضافية، فأوجد الحافة الزائدة. حواف المعالجة بالترتيب - الحافة الأولى حيث ترجع `union` `False` (متصلة بالفعل) هي الإجابة.

<FunFact>تم نشر الدليل على أن Union-Find مع كلا التحسينات يعمل في O(α(n)) بواسطة Tarjan في عام 1975 ويعتبر أحد التحليلات المطفأة الأكثر أناقة في علوم الكمبيوتر.</FunFact>

## متى تختار Union-Find مقابل BFS/DFS

| السيناريو | الخيار الأفضل |
|----------|------------|
| استعلامات الاتصال المتكررة | الاتحاد البحث |
| اجتياز واحد / أقصر مسار | بفس/دفس |
| إضافات الحافة التزايدية | الاتحاد البحث |
| عمليات إزالة الحواف (رسم بياني ديناميكي) | BFS/DFS (أو UF دون اتصال) |
| كروسكال MST | الاتحاد البحث |
| الفرز الطوبولوجي / الدورة في الرسم البياني الموجه | دي إف إس |

يتألق Union-Find عندما تقوم بمعالجة الحواف *بشكل متزايد* وتحتاج إلى فحوصات اتصال سريعة. إذا كنت تجتاز مرة واحدة فقط أو تحتاج إلى معلومات المسار، فالتزم بـ BFS/DFS.
