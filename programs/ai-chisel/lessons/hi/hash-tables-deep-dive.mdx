## हैशिंग क्यों मायने रखती है

जब कोई रिकमेंडेशन इंजन यह जाँचना चाहता है कि आपने उसकी लाखों फ़िल्मों वाली सूची में से कोई फ़िल्म पहले देखी है या नहीं, तो वह सूची को स्कैन नहीं कर सकता। **हैश टेबल** इस प्रश्न का उत्तर औसतन O(1) समय में देती है।

हैश टेबल प्रोडक्शन सॉफ़्टवेयर में सबसे अधिक इस्तेमाल होने वाली डेटा संरचना है। AI सिस्टम फ़ीचर लुकअप, कैशिंग और डीडुप्लिकेशन के लिए इन पर बहुत निर्भर करते हैं।

## हैशिंग कैसे काम करती है

**हैश फ़ंक्शन** इनपुट (स्ट्रिंग, नंबर या ऑब्जेक्ट) लेकर पूर्णांक लौटाता है। यह **हैश कोड** होता है। modulo से उस कोड को **बकेट इंडेक्स** में बदला जाता है:

```
index = hashFunction(key) % numberOfBuckets
```

अच्छा हैश फ़ंक्शन ऐसा होता है:
- **निर्धारक** - वही इनपुट हमेशा वही आउटपुट देता है।
- **समान रूप से वितरित** - कुंजियों को बकेट में बराबरी से फैलाता है।
- **तेज़** - कुंजी के आकार के सापेक्ष O(1) में निकाला जा सके।

### उदाहरण

```
function simpleHash(key, size):
    total = 0
    for char in key:
        total += charCode(char)
    return total % size
```

यह जानबूझकर सरल है। MurmurHash3 या xxHash जैसे प्रोडक्शन हैश फ़ंक्शन बेहतर वितरण के लिए बिट-मिक्सिंग इस्तेमाल करते हैं।

## कोलिज़न संभालना

कोलिज़न अनिवार्य हैं (pigeonhole principle)। दो मुख्य रणनीतियाँ हैं:

### चेनिंग

हर बकेट एंट्री की लिंक्ड लिस्ट या छोटा ऐरे रखता है। कोलाइड होने वाली कुंजियाँ सूची के अंत में जोड़ी जाती हैं।

```
function insert(table, key, value):
    idx = hash(key) % table.size
    for entry in table[idx]:
        if entry.key == key:
            entry.value = value
            return
    table[idx].append((key, value))
```

**लाभ:** सरल, मध्यम लोड पर अच्छा काम करता है।
**हानि:** पॉइंटर पीछा करने के कारण कैश-अनुकूल नहीं।

### ओपन ऐड्रेसिंग

सभी एंट्री सीधे ऐरे में रहती हैं। कोलिज़न होने पर अगले खाली स्लॉट के लिए **प्रोब** किया जाता है।

- **लीनियर प्रोबिंग:** index+1, index+2, … जाँचें।
- **क्वाड्रेटिक प्रोबिंग:** index+1², index+2², … जाँचें।
- **डबल हैशिंग:** स्टेप साइज़ तय करने के लिए दूसरा हैश फ़ंक्शन इस्तेमाल करें।

**लाभ:** बेहतर कैश प्रदर्शन, अतिरिक्त पॉइंटर नहीं।
**हानि:** क्लस्टरिंग से प्रदर्शन गिर सकता है। हटाना पेचीदा है क्योंकि tombstone चाहिए।

<FunFact>Python dictionaries कस्टम प्रोबिंग क्रम के साथ ओपन ऐड्रेसिंग इस्तेमाल करती हैं। CPython का dict इम्प्लीमेंटेशन इतना ऑप्टिमाइज़ है कि आधुनिक हार्डवेयर पर प्रति सेकंड 50 मिलियन से अधिक लुकअप प्रोसेस करता है।</FunFact>

## लोड फ़ैक्टर और रीहैशिंग

**लोड फ़ैक्टर** α = एंट्री की संख्या / बकेट की संख्या। α बढ़ने पर कोलिज़न बढ़ते हैं और प्रदर्शन घटता है।

| लोड फ़ैक्टर | अपेक्षित लुकअप (चेनिंग) |
|------------|----------------------------|
| 0.5 | ~1.25 |
| 0.75 | ~1.375 |
| 1.0 | ~1.5 |
| 2.0 | ~2.0 |

अधिकतर इम्प्लीमेंटेशन α के सीमा से ऊपर जाने पर **रीहैश** करते हैं (आम तौर पर 0.75): बड़ा ऐरे बनता है, हर कुंजी का इंडेक्स फिर निकाला जाता है और उसे फिर डाला जाता है।

रीहैशिंग O(n) है, लेकिन कम बार होती है। इसलिए सम्मिलन की **amortised** लागत O(1) रहती है।

<ThinkAboutIt>रीहैशिंग टेबल का आकार दोगुना करती है और हर एलिमेंट फिर डालती है। अगर आपका AI सिस्टम लाइव अनुरोध स्ट्रीम संभाल रहा हो, तो यह रुकावट लेटेंसी स्पाइक बना सकती है। इसे एक बार में करने के बजाय कई सम्मिलनों में कैसे फैलाएँगे?</ThinkAboutIt>

## Bloom Filters: प्रायिक सदस्यता

**Bloom filter** इस प्रश्न का उत्तर देता है: "क्या यह एलिमेंट सेट में है?"
- **निश्चित नहीं** - एलिमेंट निश्चित रूप से अनुपस्थित है।
- **सम्भवतः हाँ** - एलिमेंट शायद मौजूद है (छोटी false-positive दर)।

यह _k_ हैश फ़ंक्शन और बिट ऐरे इस्तेमाल करता है। सम्मिलन _k_ बिट सेट करता है। लुकअप देखता है कि सभी _k_ बिट सेट हैं या नहीं।

```
function bloomInsert(filter, item):
    for i in 1..k:
        idx = hashFunctions[i](item) % filter.size
        filter.bits[idx] = 1

function bloomContains(filter, item):
    for i in 1..k:
        idx = hashFunctions[i](item) % filter.size
        if filter.bits[idx] == 0: return false
    return true   // probably present
```

**AI उपयोग:** किसी URL को पहले क्रॉल किया गया है या नहीं जाँचना, स्पैम फ़िल्टर करना और कैशिंग लेयर में अनावश्यक डेटाबेस क्वेरी से बचना।

<FunFact>Google Chrome लाखों ज्ञात दुर्भावनापूर्ण URL वाला Bloom filter इस्तेमाल करता है। कोई भी पेज लोड करने से पहले आपका ब्राउज़र फ़िल्टर जाँचता है। अगर वह "probably yes" कहे, तो Chrome पुष्टि के लिए पूरी सूची लाता है।</FunFact>

## Set बनाम Map: कब क्या इस्तेमाल करें

| संरचना | क्या सहेजती है | कब इस्तेमाल करें |
|-----------|--------|----------|
| **Set** | सिर्फ़ कुंजियाँ | सदस्यता जाँच चाहिए: "क्या मैंने इसे पहले देखा है?" |
| **Map** | कुंजी-मान जोड़े | हर कुंजी से डेटा जोड़ना हो: "इस कुंजी का मान क्या है?" |

दोनों हैश टेबल पर आधारित हैं और औसतन O(1) ऑपरेशन देते हैं। डीडुप्लिकेशन, visited tracking और uniqueness constraints के लिए **set** चुनें। लुकअप, कैश और कॉन्फ़िगरेशन स्टोर के लिए **map** चुनें।

<ThinkAboutIt>AI content moderation system को 10 मिलियन प्रतिबंधित वाक्यांशों की blocklist से आने वाले संदेश जाँचने हैं। क्या आप hash set, Bloom filter या दोनों इस्तेमाल करेंगे? मेमोरी, गति और accuracy में क्या समझौते होंगे?</ThinkAboutIt>

## मुख्य बातें

1. हैश टेबल औसत मामले में O(1) लुकअप देती हैं। कैशिंग, इंडेक्सिंग और फ़ीचर इंजीनियरिंग की रीढ़ यही है।
2. कोलिज़न चेनिंग या ओपन ऐड्रेसिंग से संभाले जाते हैं। लोड फ़ैक्टर तय करता है कि रीहैश कब होगा।
3. Bloom filters सदस्यता क्वेरी में बहुत बड़ी मेमोरी बचत के बदले छोटी false-positive दर स्वीकार करते हैं।
4. हैशिंग की अंदरूनी बातें समझने से आप हर AI workload के लिए सही टूल चुनते हैं: set, map या प्रायिक फ़िल्टर।
