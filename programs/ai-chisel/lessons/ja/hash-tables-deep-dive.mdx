## ハッシュが重要な理由

レコメンデーション エンジンが、カタログにある何百万もの映画の中から、ユーザーがすでに視聴したかどうかを確認する必要がある場合、リストをスキャンする余裕はありません。 **ハッシュ テーブル** は、平均 O(1) 時間でその質問に答えます。

ハッシュ テーブルは、運用ソフトウェアで最もよく使用される単一のデータ構造であり、AI システムは、特徴の検索、キャッシュ、重複排除のためにハッシュ テーブルに大きく依存しています。

## ハッシュの仕組み

**ハッシュ関数**は入力 (文字列、数値、またはオブジェクト) を受け取り、整数 (**ハッシュ コード**) を返します。このコードは、モジュロを介して **バケット インデックス**にマッピングされます。

```
index = hashFunction(key) % numberOfBuckets
```

優れたハッシュ関数は次のとおりです。
- **決定的** - 同じ入力は常に同じ出力を生成します。
- **均一** - バケット全体にキーを均等に分散します。
- **高速** - キー サイズに対して O(1) で計算可能。

＃＃＃ 例

```
function simpleHash(key, size):
    total = 0
    for char in key:
        total += charCode(char)
    return total % size
```

これは意図的にナイーブです。MurmurHash3 や xxHash などの実稼働ハッシュ関数はビットミキシングを使用して、はるかに優れた分散を実現します。

## 衝突処理

衝突は避けられません (鳩の巣原理)。 2 つの主な戦略:

### 連鎖

各バケットは、エントリのリンクされたリスト (または小さな配列) を保持します。衝突するキーはリストに追加されます。

```
function insert(table, key, value):
    idx = hash(key) % table.size
    for entry in table[idx]:
        if entry.key == key:
            entry.value = value
            return
    table[idx].append((key, value))
```

**長所:** シンプルで、適度な負荷でうまく動作します。
**短所:** ポインタ追跡のため、キャッシュには不向きです。

### オープンアドレッシング

すべてのエントリは配列内に直接存在します。衝突が発生すると、次の空きスロットを **プローブ**します。

- **線形プローブ:** インデックス+1、インデックス+2、…をチェックします。
- **二次プローブ:** インデックス + 1 ²、インデックス + 2 ² などをチェックします。
- **ダブル ハッシュ:** 2 番目のハッシュ関数を使用してステップ サイズを決定します。

**長所:** キャッシュ パフォーマンスが向上し、余分なポインタが不要になります。
**短所:** クラスタリングはパフォーマンスを低下させる可能性があります。削除は面倒です (トゥームストーンが必要です)。

<FunFact>Python 辞書は、カ​​スタム プローブ シーケンスによるオープン アドレス指定を使用します。 CPython の dict 実装は非常に高度に最適化されているため、最新のハードウェアでは 1 秒あたり 5,000 万件以上のルックアップを処理します。</FunFact>

## 負荷率と再ハッシュ

**負荷係数** α = エントリ数 / バケット数。 α が大きくなると、衝突が増加し、パフォーマンスが低下します。

|負荷率 |予想される検索 (連鎖) |
|-----------|----------------------------|
| 0.5 | ～1.25 |
| 0.75 | ~1.375 |
| 1.0 | ~1.5 |
| 2.0 | ~2.0 |

ほとんどの実装は、α がしきい値 (通常 0.75) を超えると **再ハッシュ** します。より大きな配列を割り当て、すべてのキーのインデックスを再計算し、再挿入します。

再ハッシュは O(n) ですが、発生頻度は低いため、**償却**された挿入コストは O(1) のままです。

<ThinkAboutIt>再ハッシュするとテーブルのサイズが 2 倍になり、すべての要素が再挿入されます。 AI システムがライブ リクエスト ストリームを処理している場合、この一時停止によりレイテンシのスパイクが発生する可能性があります。リハッシュのコストを一度にすべて実行するのではなく、複数の挿入に分散するにはどうすればよいでしょうか?</ThinkAboutIt>

## ブルームフィルター: 確率的メンバーシップ

**ブルーム フィルター**は、「この要素はセットに含まれていますか?」という質問に答えます。と:
- **絶対にありません** - この要素は確かに存在しません。
- **おそらくはい** - 要素が存在する可能性があります (誤検知率が低い)。

_k_ ハッシュ関数とビット配列を使用します。挿入により _k_ ビットが設定されます。 lookup は、すべての _k_ ビットが設定されているかどうかをチェックします。

```
function bloomInsert(filter, item):
    for i in 1..k:
        idx = hashFunctions[i](item) % filter.size
        filter.bits[idx] = 1

function bloomContains(filter, item):
    for i in 1..k:
        idx = hashFunctions[i](item) % filter.size
        if filter.bits[idx] == 0: return false
    return true   // probably present
```

**AI は次の機能を使用します。** URL がすでにクロールされているかどうかを確認し、スパムをフィルタリングし、キャッシュ レイヤーでの冗長なデータベース クエリを回避します。

<FunFact>Google Chrome は、数百万の既知の悪意のある URL を含むブルーム フィルターを使用します。ページを読み込む前に、ブラウザはフィルタをチェックします。「おそらくはい」と表示された場合、Chrome は確認のために完全なリストを取得します。</FunFact>

## セットとマップ: いつどちらを使用するか

|構造 |店舗 |いつ使用する |
|----------|----------|----------|
| **設定** |キーのみ |メンバーシップのチェックが必要です - 「これを前に見たことがありますか?」 |
| **地図** |キーと値のペア |データを各キーに関連付ける必要があります。「このキーの値は何ですか?」 |

どちらもハッシュ テーブルに基づいており、O(1) の平均操作を提供します。重複排除、訪問追跡、および一意性制約の **セット** を選択します。ルックアップ、キャッシュ、構成ストアの **マップ** を選択します。

<ThinkAboutIt>AI コンテンツ モデレーション システムは、受信メッセージを 1,000 万の禁止フレーズのブロックリストと照合してチェックする必要があります。ハッシュ セット、ブルーム フィルター、あるいはその両方を使用しますか?メモリ、速度、精度のトレードオフは何ですか?</ThinkAboutIt>

## 重要なポイント

1. ハッシュ テーブルは、キャッシュ、インデックス作成、および特徴エンジニアリングのバックボーンである O(1) 件の平均的なルックアップを提供します。
2. 衝突はチェーンまたはオープン アドレス指定によって管理されます。負荷係数は、いつ再ハッシュするかを制御します。
3. ブルーム フィルターは、わずかな誤検知率と引き換えに、メンバーシップ クエリのメモリを大幅に節約します。
4. ハッシュの内部構造を理解すると、AI ワークロードごとに適切なツール (セット、マップ、確率フィルター) を選択するのに役立ちます。
