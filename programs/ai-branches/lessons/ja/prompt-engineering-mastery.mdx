# プロンプト エンジニアリング: AI と話す技術 🎯

AI の平凡な応答と優れた応答の違いは、多くの場合、AI 自体とは何の関係もありません。それはすべて、質問の仕方に関係します。

プロンプト エンジニアリングとは、高品質で有用な出力を確実に生成する AI 言語モデルへの入力を作成する実践です。それはコミュニケーションスキル、システム思考、そして構造化された実験です。

良いニュース: エンジニアになる必要はありません。

---

## 🧠 プロンプトが思っている以上に重要である理由

LLM は非常に有能ですが、非常に文字通りでもあります。彼らはあなたが何を質問しようとしたのか知りません。彼らはあなたが「実際に」何を尋ねたかだけを知っています。

プロンプトは本質的にはコンテキスト設定の練習です。あなたはただ質問しているだけではありません。あなたが形作っているのは：
- モデルが果たすべき役割
- 期待する出力形式
- どれだけ詳しく、技術的に説明するか
- どのような制約を尊重すべきか
- 対応の目的は何ですか

これをマスターすると、同じ基礎モデルが数世代にわたってより強力になっているように感じられるでしょう。

## 🎯 ゼロショット プロンプト: 質問してください

プロンプトの最も単純な形式はゼロショットです。例を使用せずにタスクを説明し、モデルにそれを実行するように依頼します。

**前:**
```
Summarise this article.

[article text]
```

**後:**
```
Summarise the following article in 3 bullet points. Each bullet should be 
one sentence. Focus on the main argument, the key evidence, and the 
conclusion. Avoid jargon.

[article text]
```

「後」バージョンでは、形式 (箇条書き 3 つ)、長さ (それぞれ 1 文)、優先順位 (議論、証拠、結論)、およびスタイル (専門用語なし) を指定します。このモデルには、より明確な目標があります。

**よくあるゼロショットの間違い:**
- 漠然とした質問をし、具体的な答えを期待する
- 出力形式の指定を忘れた場合
- 対象読者を明示しない (技術的なものと一般的なもの)
- 長さ制約の省略

<FunFact>OpenAI などの研究によると、推論プロンプトに「ステップごとに考えてみましょう」を追加するだけで、数学や論理の問題の精度が 40 ～ 50% 向上することが示されています。これは最も単純な思考連鎖プロンプトであり、モデルが答えに飛びつくのではなく、その成果を示すよう促すため機能します。
</FunFact>

## 📚 数回のプロンプト: 例から学ぶ

場合によっては、モデルを説明することは、モデルを示すことほど効果的ではありません。 **少数ショット プロンプト** では、実際のタスクを提示する前に、必要な入出力パターンの 2 ～ 5 つの例が提供されます。

**例 - 感情分類:**
```
Classify the sentiment of each customer review as Positive, Negative, or Neutral.

Review: "The delivery was fast but the product was broken."
Sentiment: Negative

Review: "Absolutely love this! Will buy again."
Sentiment: Positive

Review: "It arrived on time."
Sentiment: Neutral

Review: "The quality exceeded my expectations but the packaging was wasteful."
Sentiment: [complete this]
```

これで、モデルは、必要な形式、混合信号の処理方法、および期待される分析の粒度を確認しました。これらの例がなければ、単一の単語ではなく段落が得られる可能性があります。

**少数ショットを使用する場合:**
- モデルが自然に生成しない可能性のある異常な出力形式
- ドメイン固有の分類タスク
- スタイルマッチング（特定の作者の声で書く）
- 複雑な構造の出力 (JSON スキーマ、テーブル)

## 🔗 思考の連鎖: モデルに大声で考えさせる

**思考連鎖 (CoT) プロンプト** は、最終的な答えを与える前に、モデルに問題を段階的に推論するよう求めます。これにより、推論、数学、複数ステップのタスクのパフォーマンスが大幅に向上します。

**CoT なし:**
```
A shop sells apples for £0.50 each. If I buy 7 apples and pay with a £5 note, 
how much change do I get?

Answer: £1.50
```
(正しい場合もあれば、正しくない場合もあり、動作が見えない場合もあります)

**CoT あり:**
```
A shop sells apples for £0.50 each. If I buy 7 apples and pay with a £5 note, 
how much change do I get? Work through this step by step.

Step 1: Cost of 7 apples = 7 × £0.50 = £3.50
Step 2: Change = £5.00 - £3.50 = £1.50
Answer: £1.50
```

目に見える推論によりエラーを見つけることができ、ステップを記述するという行為によって実際にモデルがエラーを起こす可能性が低くなります。

**非常に複雑な問題**の場合は、「ゼロショット CoT」を使用してこれをさらに進めることができます。*「最終的な答えを与える前に、推論を明確に示しながら、段階的に検討してください。」* を追加するだけです。

## 🎭 役割のプロンプト: ペルソナと専門知識

最も強力なテクニックの 1 つは、モデルに特定の役割またはペルソナを与えることです。これにより、関連する知識が活性化され、適切な雰囲気が設定され、多くの場合、専門分野の精度が向上します。

**役割なし:**
```
Explain photosynthesis.
```

**役割:**
```
You are a science teacher explaining photosynthesis to a 12-year-old who 
loves video games. Use gaming analogies where helpful. Be enthusiastic 
and encouraging.
```

2 番目のプロンプトは、根本的に異なる、そして (その聴衆にとっては) はるかに役立つ説明を生成します。

**ロール プロンプトは以下の場合に特に効果的です。**
- 適切なレベルの技術的な説明
- 法的、医学的、または財務上の質問 (常に適切な免責事項を追加してください)
- 特定のスタイルでのクリエイティブな文章
- コードレビュー (「上級 Python 開発者としてこのコードをレビューする」)
- 面接の練習（「あなたはFAANG社の厳しい面接官ですね」）

**完全なシステム プロンプト パターン:**
```
You are [role] with expertise in [domain].
Your audience is [description of user].
Your goal is to [specific objective].
Always [constraint 1].
Never [constraint 2].
Format your response as [format specification].
```

## ⛓️ プロンプトチェーン: 複雑なタスクを分解する

複雑な複数段階のタスクの場合、単一のプロンプトでは十分ではないことがよくあります。 **プロンプト チェーン** は、1 つのプロンプトの出力を次のプロンプトへの入力として使用し、タスクをステップに分割します。

**例 - ブログ投稿を書く:**

1 つのモンスター プロンプトの代わりに、次のように連鎖させます。
1. **プロンプト 1**: 「[トピック] に関するブログ投稿について考えられる 5 つの角度を生成します。それぞれについて 1 行の説明を入力してください。」
2. **プロンプト 2**: 「上からの角度 #3 を使用して、5 つのセクションと箇条書きのサブポイントで詳細な概要を書きます。」
3. **プロンプト 3**: 「概要のセクション 2 を 300 ワードの完全な草稿に拡張し、会話的だが権威のある口調で書きます。」
4. **プロンプト 4**: 「明確にするために草案を確認し、冗長な文を削除し、明確な行動喚起で終わるようにしてください。」

これにより、完成したブログ投稿を一度に要求するよりもはるかに良い結果が得られます。各ステップで、モデルは焦点を絞ったタスクに完全に集中します。

<ThinkAboutIt>プロンプトチェーンは人間の専門家の仕事のやり方を反映しています。優れた著者は、ただ書き始めるだけではなく、ブレインストーミング、概要、下書き、改訂を行います。優れたエンジニアは、ゼロからコードを作成するのではなく、設計、プロトタイプ、テスト、リファクタリングを行います。なぜ AI がこれらのステップをスキップして、最初の試行で傑作を生み出すことを期待できるのでしょうか?
</ThinkAboutIt>

## 🚫 よくある間違いとその修正方法

### 間違い 1: すべてを一度に要求する
❌ *「歴史、技術、アプリケーション、ツール、キャリアパス、将来のトレンドを含む、機械学習の包括的なガイドを作成します。」*

✅ 一度に 1 つのトピックごとに、焦点を絞ったプロンプトに分割します。

### 間違い 2: 否定的な指示のみ
❌ *「専門的になりすぎないでください。あまり詳しく書かないでください。専門用語を含めないでください。」*

✅ *「日常用語を使用して、9 年生レベルで 200 語で書きます。」* - 何をすべきかを伝えます。

### 間違い 3: 出力形式を指定していない
❌ *「電気自動車の長所と短所を列挙してください。」*

✅ *「電気自動車とガソリン車を比較する表を作成します。列を使用します: ファクター、電気自動車、ガソリン。コスト、環境、航続距離、充電、メンテナンス、再販価値をカバーする 6 行を含めます。」*

### 間違い 4: コンテキストを忘れる
❌ *「これをより良く書き直してください。」*

✅ *「この段落は、非技術系幹部向けの技術レポートからのものです。専門用語を削除し、長さを 30% 削減して、冒頭に 1 文の要約を追加するように書き直してください。」*

### 間違い 5: 最初の応答を受け入れてしまう
優秀なプロンプトエンジニアはそれを繰り返します。最初の応答が適切でない場合は、モデルに何を変更するべきかを正確に伝えます: *「口調が形式的すぎるので、もっと会話風にしてください。そして、統計情報を本文ではなくサイドバーに移動してください。」*

## 🔬 高度なテクニック: 構造化された出力

プログラムによる使用 (API、ワークフロー、パイプライン) では、多くの場合、構造化された出力が必要になります。単純に明示的に要求するだけです。

```
Analyse the following job description and return a JSON object with this 
exact structure:
{
  "required_skills": ["skill1", "skill2"],
  "nice_to_have_skills": ["skill3"],
  "seniority_level": "junior|mid|senior",
  "remote_friendly": true|false,
  "key_responsibilities": ["resp1", "resp2", "resp3"]
}

Job description:
[text here]
```

最近の LLM はこの点で非常に優れています。多くの API が有効な JSON 出力を強制する「JSON モード」を提供するようになり、信頼性がさらに高まりました。

## 🏆 プロンプトの実践を構築する

迅速なエンジニアリングは複合的なスキルです。まずは次の習慣から始めましょう。

1. **プロンプト ライブラリを保持する** - 繰り返しのタスクに適したプロンプトを保存します。
2. **A/B テスト** - 2 つの異なるプロンプトで同じタスクを試し、結果を比較します
3. **失敗の診断** - 応答が悪い場合は、どのコンテキストが欠落していたかを尋ねます。何が曖昧だったのでしょうか？
4. **調査結果を読む** - OpenAI、Anthropic、Google DeepMind は、プロンプト手法に関する論文を定期的に出版しています。
5. **他の人に教える** - プロンプトが機能する理由を説明することで、自分自身の理解を強化します

モデルは急速に改良されていますが、熟練したプロンプト エンジニアがモデルから抽出できるものの上限も同様です。ここでの基本、つまり明確さ、具体性、コンテキスト、反復は、使用しているモデルに関係なく、引き続き価値があります。
