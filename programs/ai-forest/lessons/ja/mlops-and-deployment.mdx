# MLOps とデプロイメント

94% の精度を持つ Jupyter ノートブックは製品ではありません。ラップトップを閉じた瞬間、そのモデルは誰の役にも立ちません。 MLOps は、実験と運用の間のギャップを埋める規律であり、ほとんどの AI チームが最も苦労するところです。

## ノートブックが製品版ではない理由

ノートブックは、不適切なセル実行による隠蔽状態、ハードコーディングされたファイル パス、依存関係管理の欠如、再現性ゼロなど、ひどいエンジニアリング習慣を助長します。ノートブックでトレーニングされたモデルは、新しいデータが到着したときに自動的に再トレーニングすることはできず、データが壊れたときにロールバックすることも、劣化を監視することもできません。

本番環境 ML には、**バージョン管理されたコード、バージョン管理されたデータ、バージョン管理されたモデル、および自動化されたパイプライン**が必要です。それ以外はすべてデモです。

## MLOps ライフサイクル

MLOps ライフサイクルは、線形パイプラインではなく、連続ループです。各段階は他の段階にフィードバックされ、組織の成熟度によってこれらの移行がどの程度自動化されるかが決まります。

Google は 3 つの MLOps 成熟度レベルを定義しています。
- **レベル 0** - 手動、スクリプト駆動のプロセス。データサイエンティストはモデルをエンジニアに引き渡します。
- **レベル 1** - 自動化されたトレーニング パイプライン。再トレーニングは新しいデータに対して自動的にトリガーされます。
- **レベル 2** - ML 用の完全な CI/CD。コード、データ、モデルの変更はすべて、自動化されたパイプラインを通過します。

ループのステージ:

1. **データの取り込みと検証** - 受信データを収集、クリーンアップし、スキーマに対して検証します。
2. **特徴エンジニアリング** - 特徴ストアを介して生データをモデル対応特徴に変換します
3. **トレーニング** - 追跡されたハイパーパラメータを使用して再現可能なトレーニング ジョブを実行します
4. **評価** - 保持されたテスト セットを使用して、候補モデルをベースラインと比較します
5. **レジストリ** - 承認されたモデルをメタデータ、系統、および承認ステータスとともに保存します
6. **デプロイメント** - カナリアまたはブルーグリーンロールアウトを使用して API の背後でモデルを提供します
7. **モニタリング** - 予測品質、レイテンシ、スループット、データ ドリフトを追跡します。
8. **再トレーニング** - パフォーマンスが低下したときに新しいトレーニングの実行をトリガーします

## モデル レジストリ

モデル レジストリは、トレーニングされたモデルのバージョン管理システムです。 **MLflow**、**Weights & Biases**、**Neptune** などのツールを使用すると、モデル アーティファクトをトレーニング メトリクス、ハイパーパラメータ、データセット バージョン、プロモーション ステータス (ステージング → 運用 → アーカイブ) とともに保存できます。

レジストリは次のような重要な質問に答えます。 *現在生産されているモデルはどれですか?どのようなデータに基づいてトレーニングされましたか?誰が承認したのですか？その評価指標は何でしたか?*

## 機械学習用の CI/CD

従来の CI/CD テスト コード。 ML CI/CD は、**コード、データ、モデル** の 3 つをテストする必要があります。

- **コード テスト** - 機能エンジニアリング ロジック、データ変換、および API コントラクトの単体テスト
- **データ テスト** - スキーマの検証、分布チェック (新しいデータが予想範囲内にあるか)、および完全性チェック (欠落している列がないか)
- **モデル テスト** - 検証セットのパフォーマンスしきい値、レイテンシ ベンチマーク、バイアス メトリクス、および現在の運用モデルとの比較

機能パイプラインを変更するプル リクエストは、再トレーニングと評価を自動的にトリガーする必要があります。新しいモデルのパフォーマンスがベースラインを下回る場合、PR はブロックされます。

## ML のコンテナ化

本番環境の ML では Docker は交渉の余地がありません。トレーニング環境とサービス環境は同一である必要があります。GPU ドライバー、CUDA バージョン、Python の依存関係がすべて一致する必要がある場合、「自分のマシンで動作する」という問題はさらに大きくなります。

典型的な ML Dockerfile レイヤー: ベース CUDA イメージ → Python 依存関係 → モデル アーティファクト → サービス提供フレームワーク。マルチステージ ビルドでは、ビルド環境をランタイムから分離することで、最終的なイメージを無駄のない状態に保ちます。

ML コンテナ化の主な実践方法:
- **すべての依存関係をピン留め** - 範囲ではなく、`requirements.txt`内の正確なバージョンを使用します
- **ダイジェスト ベースのベース イメージを使用します** - `:latest` の代わりに `nvidia/cuda@sha256:...`
- **トレーニング イメージと提供イメージを分離する** - トレーニング イメージにはコンパイラと開発ツールが必要です。提供イメージにはランタイムのみが必要です
- **脆弱性のスキャン** - ML イメージは深い依存関係ツリーから CVE を継承します

<FunFact>NVIDIA CUDA ベース イメージだけでも 3 GB を超えます。運用チームは、コールド スタート時間とコンテナー レジストリのコストを削減するために、Docker イメージの最適化に日常的に何日も費やしています。</FunFact>

## インフラストラクチャの提供

モデルを提供する方法は、レイテンシーとスループットの要件によって異なります。

|ツール |最適な用途 |主な機能 |
|------|----------|---------------|
| **トーチサーブ** | PyTorch モデル |組み込みのバッチ処理、モデルのバージョン管理 |
| **Triton 推論サーバー** |マルチフレームワーク、GPU |動的バッチ処理、モデルの同時実行 |
| **vLLM** |大規模な言語モデル | PagedAttendance、連続バッチ処理 |
| **TensorFlow の提供** | TF/Keras モデル | gRPC + REST、自動モデルリロード |
| **BentoML** |任意のフレームワーク | Pythonic API、組み込みコンテナ化 |

特に LLM サービスの場合、**vLLM** は業界標準になっています。これは、その PagedAttendance メカニズムが、単純なサービスと比較して GPU メモリの無駄を最大 90% 削減するためです。

## モデルのドリフトを監視する

導入時には正確だったモデルも、時間の経過とともに劣化します。 **データドリフト**は、入力分布が変化した場合（パンデミック後に顧客の行動が変化した場合など）に発生します。 **概念ドリフト**は、入力と出力の間の関係が変化するときに発生します (例: 不正行為のパターンが進化する)。

次の信号を監視します。
- **予測分布** - 出力は変化していますか?いつもよりも信頼性の高い予測ですか?
- **特徴分布** - 現在のデータとトレーニング データを比較する統計テスト (KS テスト、PSI)
- **グランドトゥルースフィードバック** - ラベルが到着したら、ライブ精度/F1を計算し、ベースラインと比較します
- **レイテンシとエラー率** - インフラストラクチャの健全性はモデルの品質に間接的に影響します

<ThinkAboutIt>e コマースの推奨モデルはパンデミック前にトレーニングされていました。パンデミック後の買い物パターンはまったく異なります。このドリフトを自動的に検出するにはどうすればよいでしょうか?また、再トレーニング戦略はどのようなものになりますか?</ThinkAboutIt>

## フィーチャー ストア

特徴ストアは、トレーニングとサービス全体で共有される、特徴の定義と値の一元的なリポジトリです。 **Feast**、**Tecton**、**Hopsworks** などのツールは、特徴がトレーニング中と推論中に異なる方法で計算される場合の、**トレーニングとサービングのスキュー**という重大な問題を解決します。

フィーチャー ストアは、オフライン ストア (トレーニング用のバッチフィーチャー)、オンライン ストア (サービス提供のための低レイテンシーフィーチャー)、およびレジストリ (フィーチャー定義、所有権、系統) を提供します。

## バッチ推論とリアルタイム推論

すべての予測がリアルタイムで行われる必要があるわけではありません。コストの差は非常に大きくなります。

- **バッチ推論** - スケジュールに従って予測を実行します (時間ごと、毎日)。安価で、スポット インスタンスを使用します。推奨事項、リスクスコアリング、レポート生成に最適です。
- **リアルタイム推論** - API を介した 1 秒未満の予測。高価で、常時稼働の GPU インスタンスが必要です。チャットボット、不正行為検出、自律システムに必要です。
- **準リアルタイム (ストリーミング)** - Kafka または Pub/Sub 経由でイベントが到着したときに処理します。パーソナライゼーションや異常検出などのユースケースのレイテンシとコストのバランスをとります。

一般的なパターンは、予測可能なケースの 95% についてバッチ予測を事前計算し、残りの 5% のみをリアルタイム エンドポイントにルーティングすることです。

コスト最適化のヒント: **推論エンドポイントの自動スケール**は、CPU 使用率ではなくリクエスト キューの深さに基づいています。 ML ワークロードはバースト的です。キューの深さをスケーリングすることで、トラフィックの急増時のオーバープロビジョニングとリクエストのタイムアウトの両方を防ぎます。
