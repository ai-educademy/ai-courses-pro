# MLOps 和部署

准确率达到 94% 的 Jupyter 笔记本并不是产品。一旦你关闭笔记本电脑，该模型就不再适用于任何人。 MLOps 是弥合实验和生产之间差距的学科 - 这也是大多数人工智能团队最困难的地方。

## 为什么笔记本电脑没有量产

笔记本电脑鼓励可怕的工程习惯：无序单元执行的隐藏状态、硬编码文件路径、无依赖管理和零再现性。在笔记本中训练的模型无法在新数据到达时自动重新训练，无法在损坏时回滚，也无法监控退化情况。

生产机器学习需要**版本化代码、版本化数据、版本化模型和自动化管道**。其他一切都是演示。

## MLOps 生命周期

MLOps 生命周期是一个连续循环，而不是线性管道。每个阶段都会反馈给其他阶段，组织的成熟度决定了这些转变的自动化程度。

Google 定义了三个 MLOps 成熟度级别：
- **级别 0** - 手动、脚本驱动的流程。数据科学家将模型交给工程师。
- **1 级** - 自动化培训管道。新数据会自动触发重新训练。
- **2 级** - 机器学习的完整 CI/CD。代码、数据和模型更改都通过自动化管道流动。

循环的阶段：

1. **数据摄取和验证** - 根据架构收集、清理和验证传入数据
2. **特征工程** - 通过特征存储将原始数据转换为模型就绪特征
3. **训练** - 使用跟踪的超参数运行可重复的训练作业
4. **评估** - 使用保留的测试集将候选模型与基线进行比较
5. **注册表** - 存储已批准的模型以及元数据、沿袭和批准状态
6. **部署** - 通过金丝雀或蓝绿部署为 API 后面的模型提供服务
7. **监控** - 跟踪预测质量、延迟、吞吐量和数据漂移
8. **再训练** - 当性能下降时触发新的训练运行

## 模型注册表

模型注册表是训练模型的版本控制系统。 **MLflow**、**权重和偏差**和 **Neptune** 等工具可让您存储模型制品及其训练指标、超参数、数据集版本和升级状态（暂存 → 生产 → 存档）。

注册表回答了关键问题：*目前正在生产哪种型号？它是根据什么数据进行训练的？谁批准的？其评估指标是什么？*

## 用于机器学习的 CI/CD

传统的 CI/CD 测试代码。 ML CI/CD 必须测试三件事：**代码、数据和模型**。

- **代码测试** - 功能工程逻辑、数据转换和 API 合约的单元测试
- **数据测试** - 模式验证、分布检查（新数据是否在预期范围内？）和完整性检查（没有缺失列）
- **模型测试** - 验证集的性能阈值、延迟基准、偏差指标以及与当前生产模型的比较

更改功能管道的拉取请求应自动触发重新训练和评估。如果新模型的表现低于基线，PR 就会被阻止。

## 机器学习的容器化

对于生产机器学习来说，Docker 是不容妥协的。您的训练环境和服务环境必须相同 - 当 GPU 驱动程序、CUDA 版本和 Python 依赖项都需要匹配时，“它可以在我的机器上运行”问题会被放大。

典型的 ML Dockerfile 层：基础 CUDA 映像 → Python 依赖项 → 模型工件 → 服务框架。多阶段构建通过将构建环境与运行时分离来保持最终映像的精简。

机器学习容器化的关键实践：
- **固定每个依赖项** - 使用 `requirements.txt` 中的确切版本，而不是范围
- **使用基于摘要的基础图像** - `nvidia/cuda@sha256:...` 而不是 `:latest`
- **单独的训练和服务图像** - 训练图像需要编译器和开发工具；提供图像只需要运行时
- **扫描漏洞** - ML 映像从深度依赖树继承 CVE

<FunFact>仅 NVIDIA CUDA 基础映像就超过 3 GB。生产团队通常会花费数天时间来优化 Docker 映像，以减少冷启动时间和容器注册表成本。</FunFact>

## 服务基础设施

您如何服务模型取决于您的延迟和吞吐量要求：

|工具|最适合 |主要特点|
|------|----------|-------------|
| **火炬服务** | PyTorch 模型 |内置批处理、模型版本控制 |
| **Triton 推理服务器** |多框架、GPU |动态批处理、并发模型执行 |
| **vLLM** |大语言模型 | PagedAttention，连续批处理 |
| **TensorFlow 服务** | TF/Keras 模型 | gRPC + REST，自动模型重新加载 |
| **BentoML** |任何框架 | Pythonic API，内置容器化 |

特别是对于 LLM 服务，**vLLM** 已成为行业标准，因为与简单服务相比，其 PagedAttention 机制可减少高达 90% 的 GPU 内存浪费。

## 监控模型漂移

部署时准确的模型会随着时间的推移而退化。当输入分布发生变化（例如，客户行为在大流行后发生变化）时，就会发生数据漂移。当输入和输出之间的关系发生变化（例如，欺诈模式演变）时，就会发生概念漂移。

监控这些信号：
- **预测分布** - 输出是否发生变化？比平常更可信的预测？
- **特征分布** - 将当前数据与训练数据进行比较的统计测试（KS 测试、PSI）
- **地面实况反馈** - 当标签到达时，计算实时准确度/F1 并与基线进行比较
- **延迟和错误率** - 基础设施健康状况间接影响模型质量

<ThinkAboutIt>您的电子商务推荐模型是在大流行前进行训练的。大流行后的购物模式完全不同。您将如何自动检测这种漂移，您的再训练策略会是什么样的？</ThinkAboutIt>

## 特征商店

特征存储是特征定义和值的集中存储库，在训练和服务之间共享。 **Feast**、**Tecton** 和 **Hopsworks** 等工具解决了 **训练-服务偏差** 的关键问题 - 当特征在训练与推理过程中计算方式不同时。

特征存储提供：离线存储（用于训练的批量特征）、在线存储（用于服务的低延迟特征）和注册表（特征定义、所有权、沿袭）。

## 批量推理与实时推理

并非所有预测都需要实时发生。成本差异是巨大的：

- **批量推理** - 按计划（每小时、每天）运行预测。便宜，使用现货实例。非常适合建议、风险评分、报告生成。
- **实时推理** - 通过 API 进行亚秒级预测。价格昂贵，需要始终在线的 GPU 实例。聊天机器人、欺诈检测、自治系统所需。
- **近实时（流式传输）** - 在事件通过 Kafka 或 Pub/Sub 到达时对其进行处理。平衡个性化和异常检测等用例的延迟和成本。

一种常见的模式是针对 95% 的可预测案例预先计算批量预测，并仅将剩余的 5% 路由到实时端点。

成本优化提示：**自动缩放推理端点**基于请求队列深度，而不是 CPU 利用率。机器学习工作负载是突发性的 - 队列深度的扩展可以防止流量高峰期间的过度配置和请求超时。

<Quiz question="什么时候批量推理优于实时推理？" options="当需要在 100 毫秒内进行预测时|当预测可以按计划预先计算并且延迟并不重要时|当模型对于 GPU 服务来说太小时|当您需要处理并发用户时" answer="1" explanation="当可以提前安排预测时，批量推理是理想的选择 - 它的成本要低得多，因为您可以使用现货实例并且不需要始终在线的 GPU 基础设施。" />
