# MLOps और डिप्लॉयमेंट

94% सटीकता वाली Jupyter notebook उत्पाद नहीं है। Laptop बंद करते ही वह मॉडल किसी की सेवा नहीं करता। MLOps वह discipline है जो experimentation और प्रोडक्शन के बीच का gap भरता है, और यही वह जगह है जहां अधिकतर AI टीमें सबसे अधिक संघर्ष करती हैं।

## Notebooks प्रोडक्शन क्यों नहीं हैं

Notebooks खराब इंजीनियरिंग आदतों को बढ़ावा देती हैं: क्रम से बाहर चलाए गए सेल से छिपी हुई अवस्था, हार्डकोडेड फ़ाइल पथ, डिपेंडेंसी प्रबंधन नहीं और शून्य पुनरुत्पादकता। Notebook में प्रशिक्षित मॉडल नया डेटा आने पर अपने आप फिर प्रशिक्षित नहीं हो सकता, टूटने पर रोलबैक नहीं हो सकता और गिरावट के लिए मॉनिटर नहीं हो सकता।

प्रोडक्शन ML को **versioned code, versioned डेटा, versioned मॉडल और स्वचालित पाइपलाइन** चाहिए। बाकी सब डेमो है।

## MLOps लाइफ़साइकिल

MLOps लाइफ़साइकिल लगातार loop है, linear पाइपलाइन नहीं। हर stage दूसरों में feedback देती है, और आपके organisation की maturity तय करती है कि ये transitions कितने स्वचालित हैं।

Google तीन MLOps maturity levels define करता है:
- **Level 0** - Manual, script-driven प्रक्रिया। डेटा scientists मॉडल engineers को hand off करते हैं।
- **Level 1** - Automated प्रशिक्षण पाइपलाइन। नया डेटा पर रीट्रेनिंग automatically trigger होती है।
- **Level 2** - ML के लिए पूरा CI/CD है। code, डेटा और मॉडल बदलाव सभी स्वचालित पाइपलाइन से गुजरते हैं।

Loop के stages:

1. **डेटा ingestion और validation** - incoming डेटा को schemas के against collect, clean और सत्यापित करें
2. **Feature इंजीनियरिंग** - raw डेटा को फ़ीचर स्टोर के ज़रिए मॉडल-ready फ़ीचर में बदलना करें
3. **प्रशिक्षण** - tracked hyperparameters के साथ reproducible प्रशिक्षण jobs चलाएं
4. **Evaluation** - उम्मीदवार मॉडल को held-out टेस्ट sets के साथ baselines से compare करें
5. **Registry** - approved मॉडल को metadata, lineage और approval status के साथ स्टोर करें
6. **डिप्लॉयमेंट** - मॉडल को canary या blue-green rollout के साथ API के पीछे serve करें
7. **मॉनिटरिंग** - पूर्वानुमान गुणवत्ता, लेटेंसी, throughput और डेटा drift ट्रैक करें
8. **Retraining** - प्रदर्शन degrade होने पर new प्रशिक्षण runs trigger करें

## मॉडल registries

मॉडल रजिस्ट्री आपके प्रशिक्षित मॉडल के लिए वर्ज़न control सिस्टम है। **MLflow**, **Weights & Biases** और **Neptune** जैसे टूल आपको मॉडल artefacts को प्रशिक्षण metrics, hyperparameters, डेटासेट वर्ज़न और promotion status (staging → प्रोडक्शन → archived) के साथ स्टोर करने देते हैं।

Registry महत्वपूर्ण questions का जवाब देती है: *कौन सा मॉडल अभी प्रोडक्शन में है? वह किस डेटा पर प्रशिक्षित था? किसने approve किया? उसके evaluation metrics क्या थे?*

## Machine Learning के लिए CI/CD

Traditional CI/CD code टेस्ट करता है। ML CI/CD को तीन चीज़ें टेस्ट करनी होती हैं: **code, डेटा और मॉडल**।

- **Code टेस्ट** - फ़ीचर इंजीनियरिंग logic, डेटा transformations और API contracts के यूनिट टेस्ट
- **डेटा टेस्ट** - schema validation, वितरण checks (क्या नया डेटा expected ranges में है?) और completeness checks (missing columns नहीं)
- **मॉडल टेस्ट** - validation sets पर प्रदर्शन thresholds, लेटेंसी benchmarks, bias metrics और current प्रोडक्शन मॉडल से comparison

Feature पाइपलाइन बदलने वाले pull request को रीट्रेनिंग और evaluation automatically trigger करनी चाहिए। अगर new मॉडल baseline से कम perform करता है, PR block हो जाता है।

## ML के लिए Containerisation

प्रोडक्शन ML के लिए Docker अनिवार्य है। आपका प्रशिक्षण परिवेश और सर्विंग परिवेश एक जैसे होना चाहिए: GPU ड्राइवर, CUDA versions और Python डिपेंडेंसी सब मेल करने हों तो "it works on my machine" समस्या और बढ़ जाती है।

Typical ML Dockerfile layers: base CUDA image → Python डिपेंडेंसी → मॉडल artefacts → सर्विंग फ़्रेमवर्क। Multi-stage builds build परिवेश को रनटाइम से अलग करके final image lean रखते हैं।

ML containerisation के key practices:
- **हर dependency pin करें** - `requirements.txt` में ranges नहीं, exact versions इस्तेमाल करें
- **Digest-based base images इस्तेमाल करें** - `:latest` के बजाय `nvidia/cuda@sha256:...`
- **प्रशिक्षण और सर्विंग images अलग रखें** - प्रशिक्षण images को compilers और dev टूल चाहिए; सर्विंग images को केवल रनटाइम चाहिए
- **Vulnerabilities scan करें** - ML images deep dependency trees से CVEs inherit करती हैं

<FunFact>NVIDIA CUDA base image अकेली 3 GB से अधिक होती है। प्रोडक्शन टीमें cold-start times और container रजिस्ट्री लागत घटाने के लिए Docker images ऑप्टिमाइज़ करने में नियमित रूप से days लगाती हैं।</FunFact>

## सर्विंग इन्फ्रास्ट्रक्चर

आप मॉडल कैसे serve करते हैं, यह आपकी लेटेंसी और throughput requirements पर निर्भर करता है:

| Tool | Best For | Key Feature |
|------|----------|-------------|
| **TorchServe** | PyTorch मॉडल | Built-in batching, मॉडल versioning |
| **Triton इन्फ़रेंस Server** | Multi-फ़्रेमवर्क, GPU | Dynamic batching, concurrent मॉडल कार्यान्वयन |
| **vLLM** | Large language मॉडल | PagedAttention, लगातार batching |
| **TensorFlow सर्विंग** | TF/Keras मॉडल | gRPC + REST, automatic मॉडल reload |
| **BentoML** | Any फ़्रेमवर्क | Pythonic API, built-in containerisation |

LLM सर्विंग के लिए विशेष रूप से **vLLM** उद्योग मानक बन गया है क्योंकि उसका PagedAttention mechanism naive सर्विंग की तुलना में GPU memory waste को 90% तक घटाता है।

## मॉडल drift की मॉनिटरिंग

डिप्लॉयमेंट पर accurate मॉडल समय के साथ degrade होगा। **डेटा drift** तब होता है जब इनपुट वितरण बदलता है (जैसे पोस्ट-पैंडेमिक customer behaviour shift)। **Concept drift** तब होता है जब इनपुट और आउटपुट का संबंध बदलता है (जैसे fraud patterns evolve)।

इन signals को मॉनिटर करें:
- **Prediction वितरण** - क्या आउटपुट shift हो रहे हैं? usual से अधिक हाई-कॉन्फ़िडेंस पूर्वानुमान?
- **Feature distributions** - current डेटा और प्रशिक्षण डेटा की तुलना करने वाले statistical टेस्ट (KS टेस्ट, PSI)
- **Ground truth feedback** - लेबल आने पर live सटीकता/F1 कम्प्यूट करें और baseline से compare करें
- **Latency और error rates** - इन्फ्रास्ट्रक्चर स्वास्थ्य अप्रत्यक्ष रूप से मॉडल गुणवत्ता प्रभावित करती है

<ThinkAboutIt>आपका e-commerce recommendation मॉडल प्री-पैंडेमिक प्रशिक्षित था। पोस्ट-पैंडेमिक shopping patterns पूरी तरह अलग हैं। आप इस drift को automatically कैसे detect करेंगे और आपकी रीट्रेनिंग strategy कैसी होगी?</ThinkAboutIt>

## Feature stores

Feature स्टोर फ़ीचर definitions और values की centralised repository है, जो प्रशिक्षण और सर्विंग में shared होती है। **Feast**, **Tecton** और **Hopsworks** जैसे टूल **प्रशिक्षण-सर्विंग skew** की महत्वपूर्ण समस्या हल करते हैं: जब प्रशिक्षण और इन्फ़रेंस के दौरान फ़ीचर अलग तरीके से कम्प्यूट होते हैं।

Feature stores provide करते हैं: offline स्टोर (प्रशिक्षण के लिए batch फ़ीचर), online स्टोर (सर्विंग के लिए कम-लेटेंसी फ़ीचर) और रजिस्ट्री (फ़ीचर definitions, ownership, lineage)।

## Batch vs Real-Time इन्फ़रेंस

हर पूर्वानुमान वास्तविक time में नहीं चाहिए। लागत difference बहुत बड़ा है:

- **Batch इन्फ़रेंस** - schedule पर पूर्वानुमान चलाएं (hourly, daily)। सस्ता, spot instances इस्तेमाल करता है। recommendations, risk scoring, report generation के लिए उपयुक्त।
- **रीयल-टाइम इन्फ़रेंस** - API के ज़रिए sub-second पूर्वानुमान। महंगा, हमेशा-चालू GPU instances मांगता है। chatbots, fraud detection, autonomous सिस्टम के लिए आवश्यक।
- **Near-रीयल-टाइम (streaming)** - Kafka या Pub/Sub के ज़रिए events आते ही प्रक्रिया करें। personalisation और anomaly detection जैसे उपयोग cases के लिए लेटेंसी और लागत balance करता है।

Common pattern है कि predictable 95% cases के लिए batch पूर्वानुमान pre-कम्प्यूट करें और केवल बाकी 5% को रीयल-टाइम endpoint पर route करें।

Cost ऑप्टिमाइज़ेशन tip: **autoscale इन्फ़रेंस endpoints** request queue depth के आधार पर करें, CPU utilisation पर नहीं। ML workloads bursty होते हैं: queue depth पर स्केलिंग traffic spikes के दौरान over-provisioning और request timeouts दोनों रोकती है।
