# AI उत्पाद बनाना

अधिकतर AI प्रोजेक्ट कभी प्रोडक्शन तक नहीं पहुंचते। काम करने वाली notebook और विश्वसनीय उत्पाद के बीच बहुत बड़ा अंतर है: इन्फ्रास्ट्रक्चर, मॉनिटरिंग, टीम प्रक्रियाएं और लागत प्रबंधन तक फैला हुआ। यह पाठ उस अंतर को सफलतापूर्वक पार करने के लिए ज़रूरी बातें बताता है।

## क्या AI सही समाधान है?

कोड की एक भी लाइन लिखने से पहले, AI उत्पाद विकास का सबसे महत्वपूर्ण सवाल पूछें: क्या इस समस्या को सच में AI चाहिए? जवाब आपकी उम्मीद से ज़्यादा बार "नहीं" होता है।

**AI सही चुनाव है जब:**
- समस्या बड़े पैमाने पर pattern recognition से जुड़ी हो (fraud detection, image classification)
- नियम इतने जटिल या अधिक हों कि उन्हें manual रूप से encode करना व्यावहारिक न हो
- डेटा उपलब्ध, उच्च-गुणवत्ता वाला और वास्तविक दुनिया की स्थितियों का प्रतिनिधि हो
- probabilistic उत्तर (90% confidence) स्वीकार्य हो
- automation का मूल्य सिस्टम बनाने और बनाए रखने की लागत से काफ़ी अधिक हो

**AI गलत चुनाव है जब:**
- सरल नियम या heuristics समस्या को विश्वसनीय रूप से हल कर देते हों
- आपके पास पर्याप्त प्रशिक्षण डेटा न हो
- निर्णयों को पूरी explainability के साथ 100% सटीकता चाहिए (कुछ regulatory contexts)
- ML सिस्टम की maintenance लागत लाभ से अधिक हो

<Callout>
**10x नियम:** अगर AI speed, सटीकता या लागत में non-AI विकल्प की तुलना में कम से कम 10x सुधार नहीं देता, तो ML सिस्टम बनाए रखने की operational complexity शायद ही सार्थक होती है।
</Callout>

## सही मॉडल चुनना

हर समस्या को large language मॉडल की ज़रूरत नहीं होती। गलत मॉडल type चुनना AI उत्पाद विकास की सबसे महंगी गलतियों में से एक है। काम के हिसाब से टूल चुनें:

| Problem Type | Best Approach | Example |
|---|---|---|
| Tabular पूर्वानुमान | Gradient boosted trees (XGBoost, LightGBM) | Churn पूर्वानुमान, pricing |
| Image tasks | CNNs or vision transformers | Quality inspection, OCR |
| Text classification | फ़ाइन-ट्यून किए गए BERT or smaller LLMs | Sentiment analysis, routing |
| Generative text | LLMs (GPT, Claude, Llama) | Chatbots, सामग्री generation |
| Time series | Prophet, N-BEATS, or temporal CNNs | Demand forecasting |

## तेज़ प्रोटोटाइपिंग: 3-दिन sprint

Iteration की गति हर बार perfection से बेहतर होती है। जो टीमें सत्यापित करने से पहले महीनों तक बनाती रहती हैं, वे assumptions पर resources बर्बाद करती हैं। विचारों को जल्दी सत्यापित करने के लिए यह फ़्रेमवर्क इस्तेमाल करें:

**दिन 1 - Scope और डेटा.** वह एक metric तय करें जो सच में मायने रखता है। यह non-negotiable है: स्पष्ट success metric के बिना आप कुछ भी evaluate नहीं कर सकते। न्यूनतम व्यवहार्य dataset इकट्ठा करें या simulate करें। उसे पूरी तरह साफ़ न करें: usable बनाने जितना ही करें।

**दिन 2 - Build और टेस्ट.** मौजूदा मॉडल या API इस्तेमाल करें। उसे minimal interface (Streamlit, Gradio या सरल API) में wrap करें। कुछ ऐसा बनाएं जिसके साथ इंसान interact कर सके।

**दिन 3 - Validate.** इसे वास्तविक उपयोगकर्ता या stakeholders के सामने रखें: ऐसे colleagues नहीं जो polite रहेंगे, बल्कि वे लोग जो solution के लिए सच में pay करेंगे। अपने success metric के against measure करें। निर्णय लें: kill, पिवट या निवेश।

## MLOps की ज़रूरी बातें

प्रोडक्शन ML के लिए कठोर operational practices चाहिए, जो अधिकतर डेटा scientists academic settings में नहीं सीखते। मूल सिद्धांत deceptively सरल है: **सब कुछ वर्ज़न करें, सब कुछ automate करें।** लेकिन कार्यान्वयन discipline और सही tooling मांगता है।

**क्या वर्ज़न करें:**
- **Code** - मानक Git वर्कफ़्लो
- **डेटा** - डेटासेट वर्ज़न ट्रैक करने के लिए DVC, Delta Lake या समान टूल इस्तेमाल करें
- **मॉडल** - metadata के साथ मॉडल artefacts स्टोर करें (hyperparameters, प्रशिक्षण डेटा hash, evaluation metrics और lineage)
- **Configurations** - परिवेश variables, फ़ीचर flags, मॉडल parameters और सर्विंग configurations

**Pipeline automation:**
- schedule या डेटा drift detection पर रीट्रेनिंग trigger करें
- held-out टेस्ट set के against evaluation automate करें
- प्रदर्शन thresholds पर डिप्लॉयमेंट gate करें
- मॉडल rollouts के लिए blue-green या canary डिप्लॉयमेंट इस्तेमाल करें

<FunFact>
Google के शोध ने पाया कि वास्तविक-world ML सिस्टम code का केवल लगभग 5% actual मॉडल होता है। शेष 95% डेटा पाइपलाइन, सर्विंग इन्फ्रास्ट्रक्चर, मॉनिटरिंग और configuration management होता है।
</FunFact>

## मॉनिटरिंग: समस्याओं को उपयोगकर्ता से पहले पकड़ना

मॉडल deploy करना finish line नहीं है: यह starting line है। proper मॉनिटरिंग के बिना मॉडल चुपचाप degrade होते हैं, और जब तक किसी को पता चलता है, नुकसान हो चुका होता है।

**डेटा drift** - इनपुट डेटा वितरण समय के साथ बदलता है। प्री-पैंडेमिक shopping डेटा पर प्रशिक्षित मॉडल पोस्ट-पैंडेमिक patterns पर fail होगा। फ़ीचर distributions को लगातार मॉनिटर करें और Kolmogorov-Smirnov टेस्ट या Population Stability Index जैसे टेस्ट से statistically significant shifts पर alert करें।

**मॉडल गिरावट** - डेटा drift के बिना भी वास्तविक world बदलने से मॉडल प्रदर्शन घट सकती है। User behaviour evolve होता है, competitors market बदलते हैं और seasonal patterns परिणाम बदलते हैं। पूर्वानुमान confidence, error rates और बिज़नेस metrics लगातार ट्रैक करें।

**मुख्य मॉनिटरिंग अभ्यास:**
- सभी पूर्वानुमान को इनपुट, आउटपुट और confidence scores के साथ log करें
- defined thresholds से नीचे सटीकता drops के लिए स्वचालित alerts setup करें
- rolling window पर live प्रदर्शन की baseline मॉडल से तुलना करें
- edge cases और लो-कॉन्फ़िडेंस पूर्वानुमान की periodic मानवीय review schedule करें
- मॉडल metrics के साथ बिज़नेस metrics ट्रैक करें: conversions गिरें तो सटीकता का कोई अर्थ नहीं

## लागत ऑप्टिमाइज़ेशन रणनीतियां

AI इन्फ़रेंस लागत तेज़ी से अनियंत्रित हो सकती हैं। समझदार आर्किटेक्चर decisions इन्हें manage करते हैं।

**Practical strategies:**
1. **Complexity के आधार पर route करें** - सरल queries के लिए cheap, fast मॉडल इस्तेमाल करें और expensive मॉडल तक सिर्फ़ ज़रूरत पड़ने पर escalate करें। इससे अकेले लागत 60-80% तक कट सकती है।
2. **Aggressively cache करें** - अगर same या similar queries दोहराती हैं, responses cache करें। Semantic caching (exact text नहीं, meaning से मेल करना) विशेष रूप से प्रभावी है।
3. **Batch इन्फ़रेंस** - non-urgent requests को off-peak hours में batches में प्रक्रिया करें ताकि GPU utilisation अधिकतम हो।
4. **मॉडल क्वांटाइज़ करें** - 4-bit या 8-bit quantisation अधिकतर अनुप्रयोग में न्यूनतम गुणवत्ता हानि के साथ लागत 50-75% तक घटा सकता है।
5. **Infrastructure right-size करें** - प्रशिक्षण के लिए spot instances, सर्विंग के लिए reserved instances और demand के आधार पर auto-स्केल इस्तेमाल करें।

## मुख्य बातें

AI उत्पाद बनाना मूल रूप से उत्पाद और इंजीनियरिंग challenge है, सिर्फ़ machine सीखना challenge नहीं। इन principles को पास रखें:

- building से पहले सत्यापित करें कि AI सच में सही solution है
- मॉडल type को समस्या से मेल करें: LLM हमेशा answer नहीं हैं
- months नहीं, days में prototype करें, existing मॉडल और सरल interfaces के साथ
- सब कुछ वर्ज़न करें: code, डेटा, मॉडल और configurations
- प्रोडक्शन में डेटा drift और मॉडल गिरावट लगातार मॉनिटर करें
- routing, caching, batching और quantisation से लागत ऑप्टिमाइज़ करें

सबसे अच्छे AI उत्पाद ऐसी टीमें बनाती हैं जो technology और बिज़नेस समस्या दोनों को गहराई से समझती हैं। उत्पाद thinking के बिना तकनीकी excellence ऐसे impressive डेमो तक ले जाती है जिन्हें कोई इस्तेमाल नहीं करता।
