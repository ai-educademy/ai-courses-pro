# End-to-End ML Pipeline - कच्चे डेटा से डिप्लॉय किए गए मॉडल तक

अधिकतर ट्यूटोरियल `model.fit()` पर रुक जाते हैं। प्रोडक्शन में यह काम का मुश्किल से 20% है। यह पाठ आपको **पूरे ML जीवनचक्र** से ले जाता है, वही pipeline जो Spotify के recommendation engines, Stripe के fraud detection और Google की search ranking को चलाती है।

## 🗺️ ML जीवनचक्र एक नज़र में

<Illustration src="/images/lessons/end-to-end-ml-pipeline.svg" alt="डेटा ingestion से monitoring तक ML pipeline चरणों का आरेख" caption="Production ML pipeline के आठ चरण, हर चरण संभावित failure point है।" />

हर production ML system इन चरणों से गुजरता है:

1. **Data Collection** - APIs, databases, event streams, web scraping
2. **Data Cleaning** - nulls संभालना, deduplication, type coercion
3. **Feature Engineering** - कच्चे signals को model-ready features में बदलना
4. **Model Selection** - समस्या से मेल खाने वाली architectures चुनना
5. **Training** - GPU/CPU orchestration, hyperparameter tuning
6. **Evaluation** - offline metrics, A/B testing, fairness audits
7. **Deployment** - serving infrastructure, latency budgets
8. **Monitoring** - drift detection, alerting, retraining trigger

## 📦 Data Collection और Versioning

कच्चा डेटा आपकी नींव है। उसे source code की तरह मानें: **हर चीज़ version करें**।

```bash
# Initialise DVC in your repo
dvc init
dvc remote add -d storage s3://my-ml-data-bucket

# Track a dataset
dvc add data/transactions.csv
git add data/transactions.csv.dvc .gitignore
git commit -m "Track raw transaction dataset v1"
dvc push
```

**DVC** (Data Version Control) आपको किसी भी ऐतिहासिक dataset पर `git checkout` करने देता है। Git tags के साथ मिलकर आप किसी भी समय बिंदु से कोई भी experiment दोबारा बना सकते हैं।

<FunFact>Netflix अपनी data pipelines के माध्यम से प्रतिदिन 1.5 trillion से अधिक events process करता है, यानी लगभग 17 million events हर सेकंड उसके recommendation models तक पहुँचते हैं।</FunFact>

## 🛠️ Feature Engineering - जहां प्रतियोगिताएं जीती जाती हैं

Features, algorithms से ज़्यादा मायने रखते हैं। शानदार features वाला gradient-boosted tree, कमजोर features वाले deep neural network को हरा देता है।

```python
import pandas as pd

df = pd.read_csv("data/transactions.csv", parse_dates=["timestamp"])

# Temporal features
df["hour"] = df["timestamp"].dt.hour
df["is_weekend"] = df["timestamp"].dt.dayofweek >= 5

# Aggregation features
user_stats = df.groupby("user_id")["amount"].agg(["mean", "std", "count"])
user_stats.columns = ["user_avg_amount", "user_std_amount", "user_txn_count"]
df = df.merge(user_stats, on="user_id")

# Ratio features
df["amount_vs_avg"] = df["amount"] / df["user_avg_amount"]
```

## 🧪 MLflow के साथ Experiment Tracking

जो आपने आज़माया उसे कभी खोने न दें। MLflow parameters, metrics और artefacts को अपने आप log करता है।

```python
import mlflow
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import f1_score

mlflow.set_experiment("fraud-detection-v2")

with mlflow.start_run(run_name="gbm-baseline"):
    params = {"n_estimators": 500, "max_depth": 6, "learning_rate": 0.05}
    mlflow.log_params(params)

    model = GradientBoostingClassifier(**params)
    model.fit(X_train, y_train)

    score = f1_score(y_test, model.predict(X_test))
    mlflow.log_metric("f1_score", score)
    mlflow.sklearn.log_model(model, "model")
```

MLflow UI में runs की तुलना करें, फिर सबसे अच्छे model को staging → production lifecycle tags के साथ **Model Registry** में promote करें।

## 🚀 Pipeline as Code - Orchestration

Manual steps टूटते हैं। Orchestration frameworks का उपयोग करके अपनी pipeline को code में encode करें:

| Tool | Best For | Key Strength |
|------|----------|-------------|
| **Kubeflow Pipelines** | Kubernetes-native ML | मौजूदा K8s clusters पर स्केल करता है |
| **Apache Airflow** | Complex DAG scheduling | परिपक्व ecosystem, व्यापक अपनापन |
| **Prefect** | Modern Python workflows | Pythonic API, उत्कृष्ट error handling |
| **ZenML** | MLOps abstraction | Stack-agnostic, कोई भी tool plug करें |

<ThinkAboutIt>आपके पास ऐसी pipeline है जो हर रात retrain करती है, लेकिन आपका डेटा हर घंटे बदलता है। Retraining frequency तय करते समय आप किन trade-offs को तौलेंगे: cost, staleness, infrastructure complexity?</ThinkAboutIt>

## 🌐 Model Serving और Deployment

आपके model को API चाहिए। दो प्रमुख patterns हैं:

**REST API** - सरल, HTTP-आधारित, moderate throughput के लिए अच्छा:
```python
# FastAPI model server
from fastapi import FastAPI
import joblib

app = FastAPI()
model = joblib.load("model.pkl")

@app.post("/predict")
async def predict(features: dict):
    prediction = model.predict([list(features.values())])
    return {"prediction": int(prediction[0])}
```

**gRPC** - binary protocol, REST से 2-10× तेज़, internal microservices और high-throughput scenarios के लिए आदर्श।

### Canary Deployments

कभी भी 100% traffic सीधे नए model को न भेजें। **Canary releases** इस्तेमाल करें: 5% → 25% → 50% → 100% route करें और हर चरण पर error rates मॉनिटर करें। Metrics खराब हों, तो तुरंत रोल बैक करें।

## 📊 Monitoring और Feedback Loop

Deployment अंतिम रेखा नहीं है, यह शुरुआत की गोली है। इन चीज़ों को मॉनिटर करें:

- **Data drift** - input distributions का training data से बदलना
- **Concept drift** - features और target के बीच संबंध का बदलना
- **Performance degradation** - accuracy/latency metrics का गिरना

**Evidently AI**, **WhyLabs** और **Arize** जैसे tools drift dashboards देते हैं। जब drift thresholds से ऊपर जाए, तो ताज़ा production data के साथ automatic retraining trigger करें, और feedback loop बंद करें।

## 🎯 मुख्य बातें

- **हर चीज़** version करें: code, data, models और pipeline configs
- Feature engineering, architecture changes से ज़्यादा ROI देती है
- Pipelines को code के रूप में encode करें, manual steps technical debt हैं
- Canary releases के साथ डिप्लॉय करें और लगातार मॉनिटर करें
- Feedback loop (production data → retraining) ही demos को production systems से अलग करता है
