# System Design Mock Interview - 45 मिनट की Senior Engineer Simulation

System design interviews senior engineers को बाकी लोगों से अलग करते हैं। कोई एक सही उत्तर नहीं होता। Interviewers आपकी **structured thinking**, trade-off analysis और ambiguity में अस्पष्टता में रास्ता बनाने की क्षमता का मूल्यांकन करते हैं। यह पाठ पूरा 45-minute simulation है।

## 🎯 समस्या: Food Delivery System Design करें

*"Uber Eats या Deliveroo जैसा food delivery platform design करें जो customers, restaurants और delivery drivers को connect करता है."*

<Illustration src="/images/lessons/system-design-mock-interview.svg" alt="User, restaurant, order और driver services के साथ food delivery system की high-level architecture" caption="Food delivery platform के चार core domains, हर एक अपनी service वाला bounded context है।" />

## Phase 1: Requirements Gathering (5 minutes)

**तुरंत boxes बनाना शुरू न करें।** पहले clarifying questions पूछें:

**Functional requirements:**
- Customers restaurants browse करें, menus देखें, orders place करें, delivery real time में track करें
- Restaurants menus manage करें, orders accept/reject करें, preparation status update करें
- Drivers delivery requests प्राप्त करें, pickup/dropoff तक नेविगेट करें, delivery की पुष्टि करें
- Order lifecycle के दौरान real-time estimated delivery time (EDT) दिखे

**Non-functional requirements:**
- **Availability**: 99.99% uptime (≈52 minutes downtime per year)
- **Latency**: search < 200ms, order placement < 500ms, location updates < 1s
- **Scale**: 50M monthly active users, 5M orders per day, peak पर 500K concurrent users
- **Consistency**: search के लिए eventual consistency acceptable, payments के लिए strong consistency

## Phase 2: API Design (5 minutes)

Architecture से पहले core contracts परिभाषित करें:

```
# Customer APIs
GET    /api/v1/restaurants?lat={}&lng={}&cuisine={}  → Restaurant[]
GET    /api/v1/restaurants/{id}/menu                  → Menu
POST   /api/v1/orders                                 → Order
GET    /api/v1/orders/{id}/track                      → OrderStatus + DriverLocation

# Restaurant APIs
PATCH  /api/v1/restaurants/{id}/menu/items/{itemId}   → MenuItem
POST   /api/v1/orders/{id}/accept                     → Order
POST   /api/v1/orders/{id}/ready                      → Order

# Driver APIs
POST   /api/v1/drivers/{id}/location                  → void (fire-and-forget)
POST   /api/v1/deliveries/{id}/accept                 → Delivery
POST   /api/v1/deliveries/{id}/complete               → Delivery
```

**Key decision**: real-time driver tracking के लिए WebSockets इस्तेमाल करें, बाकी सबके लिए REST.

## Phase 3: High-Level Architecture (10 minutes)

### Core Services

| Service | Responsibility | Database |
|---------|---------------|----------|
| **User Service** | Authentication, profiles, addresses | PostgreSQL |
| **Restaurant Service** | Menus, availability, hours | PostgreSQL + Elasticsearch |
| **Order Service** | Order lifecycle, state machine | PostgreSQL (strong consistency) |
| **Driver Service** | Driver location, availability, matching | Redis (location) + PostgreSQL |
| **Payment Service** | Charges, refunds, restaurant payouts | PostgreSQL (ACID required) |
| **Notification Service** | Push, SMS, email notifications | Message queue consumer |

### Communication Patterns

- **Synchronous**: API Gateway → individual services (REST/gRPC)
- **Asynchronous**: Order events **Kafka** में publish होते हैं, Payment, Notification और Analytics services consume करती हैं
- **Real-time**: Driver location updates WebSocket → **Redis** में geospatial indexing के साथ stored

<FunFact>Uber globally प्रति second 1 million से अधिक location updates process करता है। उन्होंने hexagonal hierarchical grids का उपयोग करके अपना geospatial indexing system (H3) बनाया क्योंकि traditional latitude/longitude queries scale पर साथ नहीं दे पाती थीं।</FunFact>

## Phase 4: Deep Dive - Critical Components (15 minutes)

### Driver Matching Algorithm

जब order pickup के लिए ready होता है, matching service को optimal driver assign करना होता है:

```
Score(driver) = w1 × (1 / distance_to_restaurant)
              + w2 × driver_rating
              + w3 × (1 / current_active_orders)
              + w4 × acceptance_rate
```

**Implementation**: restaurant से 5km के भीतर drivers के लिए Redis `GEORADIUS` query करें, हर candidate को score करें, highest-scoring available driver असाइन करें। Decline होने पर 30-second timeout के साथ अगले driver को ऑफ़र करें।

### Real-Time Order Tracking

```
Client ←→ WebSocket Gateway ←→ Driver Service
                                    ↑
                              Redis GEO Store
                            (GEOADD, GEOPOS)
```

Drivers हर 4 seconds में GPS coordinates publish करते हैं। WebSocket gateway active orders के location updates subscribe करता है और उन्हें customer's device पर push करता है। **Redis Pub/Sub** fan-out को efficiently handle करता है।

### Estimated Delivery Time

EDT एक **multi-stage prediction** है:

```
EDT = restaurant_prep_time + driver_pickup_travel + dropoff_travel + buffer

Where:
- restaurant_prep_time  → ML model trained on historical order data per restaurant
- driver_pickup_travel  → distance/traffic API (Google Maps, Mapbox)
- dropoff_travel        → same routing API
- buffer                → dynamic, increases during rain/peak hours
```

<ThinkAboutIt>ऊपर का matching algorithm fixed weights (w1-w4) इस्तेमाल करता है। आप इसे ऐसे learning system में कैसे evolve करेंगे जो delivery speed और driver satisfaction दोनों optimise करे?</ThinkAboutIt>

### Payment Processing

Payments **two-phase pattern** follow करते हैं:

1. **Authorise** - order placed होने पर funds reserve करें (hold करें, charge नहीं)
2. **Capture** - delivery confirmation के बाद actual amount charge करें

यह order modifications, cancellations और partial refunds को gracefully handle करता है। Retries के दौरान double-charging रोकने के लिए हर payment request पर **idempotency key** इस्तेमाल करें।

<Quiz question="तुरंत चार्ज करने की बजाय two-phase payment pattern (authorise then capture) क्यों इस्तेमाल करें?" options="यह single charge से तेज़ है|यह cancellations, modifications और refunds को complex reversal logic के बिना संभालता है|Payment providers इसे require करते हैं|यह transaction fees घटाता है" answer="1" explanation="Authorise-then-capture आपको funds hold करने देता है बिना final charge commit किए। अगर restaurant cancel करता है या order बदलता है, तो आप authorisation release कर देते हैं, refund processing की ज़रूरत नहीं होती। इससे edge cases बहुत सरल हो जाते हैं।" />

## Phase 5: Scaling और Bottlenecks (10 minutes)

### Database Scaling

- **Order Service**: `order_id` से shard करें। Orders independent हैं, horizontal scaling straightforward है
- **Restaurant Service**: search queries के लिए read replicas, full-text और geospatial search के लिए Elasticsearch
- **Driver Location**: geospatial indexing के साथ Redis Cluster. Pure in-memory, sub-millisecond reads

### Peak Load (Surge) संभालना

Peak times पर (Friday 7pm, major sporting events), order volume 10× spike कर सकता है:

- Queue depth के आधार पर application pods की **auto-scaling**, CPU पर नहीं
- Supply और demand balance करने के लिए **surge pricing**, driver supply कम हो तो delivery fees बढ़ाएँ
- Peak के दौरान abuse रोकने के लिए per user **rate limiting**
- Downstream services पर **circuit breakers**, cascading failure की बजाय graceful degradation

### Single Points of Failure

| Component | Mitigation |
|-----------|-----------|
| API Gateway | Load balancer के पीछे multiple instances, health checks |
| Kafka | Replication factor 3 वाला multi-broker cluster |
| Redis | Automatic failover के लिए Redis Sentinel |
| Payment provider | Automatic fallback वाला secondary provider |

<ThinkAboutIt>Interviewer पूछता है: "Peak period के दौरान payment service 30 seconds के लिए down हो जाए तो क्या होता है?" Exact failure mode, orders पर असर और recovery कैसा दिखेगा, यह walk through करें।</ThinkAboutIt>

## 💡 Interview Tips

1. **अपना time व्यवस्थित करें** - requirements पर 30 minutes न लगाएँ
2. **Trade-offs स्पष्ट बोलें** - "मैंने X को Y पर इसलिए चुना क्योंकि..."
3. **Simple से शुरू करें, फिर scale करें** - पहले 1× load के लिए design करें, फिर 100× address करें
4. **बोलते समय draw करें** - visual communication evaluation का आधा हिस्सा है
5. **Unknowns स्वीकार करें** - "मुझे इसे benchmark करना होगा, लेकिन मेरी hypothesis है..."

## 🎯 मुख्य बातें

- हमेशा requirements से शुरू करें, functional और non-functional
- Architecture diagrams से पहले API contracts design करें
- 2-3 components में deep dive करें, सभी को सतही रूप से नहीं
- हर architectural choice में trade-offs होते हैं, उन्हें नाम से बताएं
- Timer के साथ अभ्यास करें: 45 minutes, no extensions
