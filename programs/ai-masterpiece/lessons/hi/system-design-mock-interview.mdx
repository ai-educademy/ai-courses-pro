# सिस्टम डिज़ाइन मॉक इंटरव्यू - 45 मिनट का सेनिओर इंजीनियर सिमुलेशन

सिस्टम डिज़ाइन इंटरव्यू सेनिओर इंजीनियर को बाकियों से अलग करते हैं। कोई एक सही जवाब नहीं होता - इनटेरविएवेरस आपकी **संरचित सोच**, टरदे-ओफ़फ़ विश्लेषण, और अमबिगुइटय नविगटे करने की क्षमता मूल्यांकन करते हैं। यह पाठ एक पूरा 45 मिनट का सिम्युलेशन है।

## फसे 1: ज़रूरतें समझना (5 मिनट)

**तुरंत बोक्सेस बनाना शुरू न करें।** पहले कलरिफ़यिङ प्रश्न पूछें:

**कार्यात्मक ज़रूरतें:**
- ग्राहक रेस्तरां बरोवसे करें, मेनुस देखें, ऑर्डर रखें करें, रीयल-टाइम डिलीवरी रिकॉर्ड करें
- रेसटौरनटस मेनुस मनगे करें, ऑर्डर अककेपट/रेजेकट करें, परेपरशन सटटुस अपडेट करें
- ड्राइवरस डिलीवरी रिक्वेस्ट रेकेइवे करें, चुनताुप/दरोपोफ़फ़ तक नविगटे करें, डिलीवरी कोनफ़िरम करें
- पूरे ऑर्डर जीवनचक्र में रीयल-टाइम अनुमानित डिलीवरी समय (EDT) दिखे

**गैर-कार्यात्मक ज़रूरतें:**
- **अवैलबिलिटय**: 99.99% उपटिमे (≈52 मिनट दोवनटिमे प्रति वर्ष)
- **लेटेंसी**: सर्च < 200ms, ऑर्डर प्लेसमेंट < 500ms, लोकेशन अपडेट < 1s
- **सकले**: 50M मोनथलय अकटिवे यूज़र, 5M ऑर्डर प्रति दिन, पीक पर 500K कोनकुररेनट यूज़र
- **संगति**: सर्च के लिए अंततः संगति ठीक; पेमेंट के लिए मज़बूत संगति

## फसे 2: API डिज़ाइन (5 मिनट)

आर्किटेक्चर से पहले कोरे कोनटरकटस परिभाषित करें:

```
# Customer APIs
GET    /api/v1/restaurants?lat={}&lng={}&cuisine={}  → Restaurant[]
GET    /api/v1/restaurants/{id}/menu                  → Menu
POST   /api/v1/orders                                 → Order
GET    /api/v1/orders/{id}/track                      → OrderStatus + DriverLocation

# Restaurant APIs
PATCH  /api/v1/restaurants/{id}/menu/items/{itemId}   → MenuItem
POST   /api/v1/orders/{id}/accept                     → Order
POST   /api/v1/orders/{id}/ready                      → Order

# Driver APIs
POST   /api/v1/drivers/{id}/location                  → void (fire-and-forget)
POST   /api/v1/deliveries/{id}/accept                 → Delivery
POST   /api/v1/deliveries/{id}/complete               → Delivery
```

**मुख्य बात निर्णय**: रेअल-टिमे ड्राइवर टरकिङ के लिए वेबसोकेटस, बाकी सब के लिए REST।

## फसे 3: उच्च-लेवेल आर्किटेक्चर (10 मिनट)

### कोरे सेवाएँ

| सर्विस | ज़िम्मेदारी | दटबसे |
|---------|------------|----------|
| **यूज़र सर्विस** | ऑथेंटिकेशन, परोफ़ाइलस, हलेस | PostgreSQL |
| **रेस्तरां सर्विस** | मेन्यू, उपलब्धता, घंटे | PostgreSQL + Elasticsearch |
| **ओरदेर सर्विस** | ओरदेर लिफ़ेकयकले, सटटे मचिने | PostgreSQL (मज़बूत संगति) |
| **ड्राइवर सर्विस** | ड्राइवर लोकेशन, उपलब्धता, मैचिंग | Redis (लोकेशन) + PostgreSQL |
| **पयमेनट सर्विस** | चार्जस, रेधन, रेस्तरां पयोउटस | PostgreSQL (ACID ज़रूरीद) |
| **नोटिफ़िकशन सर्विस** | पुश, SMS, ईमेल नोटिफ़िकशनस | मेसगे क्यू कोनसुमेर |

### कोममुनिकशन पैटर्न

- **सयनचरोनोउस**: API गटेवय → इनदिविदुअल सेवाएँ (REST/gRPC)
- **असयनचरोनोउस**: ओरदेर इवेंट **Kafka** पर पुबलिश - पयमेनट, नोटिफ़िकशन, और विश्लेषण सेवाएँ लेते करते हैं
- **रेअल-टिमे**: ड्राइवर लोकेशन अपडेट WebSocket → **Redis** में गेओसपटिअल इनदेक्सिङ के साथ स्टोर

<FunFact>Uber गलोबललय हर सेकंड 1 मिलियन से ज़्यादा लोकेशन अपडेट प्रोसेस करता है। उन्होंने अपना गेओसपटिअल इनदेक्सिङ सिस्टम (H3) हेक्सगोनल पदानुक्रमित गरिदस से बनाया क्योंकि पारंपरिक लटिटुदे/लोङिटुदे क्वेरी इतने स्केल पर काम नहीं कर पा रहीं थीं।</FunFact>

## फसे 4: दीप दिवे - महत्वपूर्ण कोमपोनेनटस (15 मिनट)

### ड्राइवर मैचिंग एल्गोरिदम

जब ऑर्डर पिकअप के लिए रेअदय हो, मैचिंग सर्विस को सर्वोत्तम ड्राइवर असाइन करना होता है:

```
Score(driver) = w1 × (1 / distance_to_restaurant)
              + w2 × driver_rating
              + w3 × (1 / current_active_orders)
              + w4 × acceptance_rate
```

**इमपलेमेनटशन**: Redis `GEORADIUS` से रेस्तरां के 5km के अंदर ड्राइवर क्वेरी करें, हर उम्मीदवार को स्कोर करें, सबसे उच्च-सकोरिङ अवैलबले ड्राइवर असाइन करें। देकलिने हो तो 30-सेकोनद टाइमआउट के साथ अगले ड्राइवर को ऑफ़र।

### रीयल-टाइम ओरदेर टरकिङ

```
Client ←→ WebSocket Gateway ←→ Driver Service
                                    ↑
                              Redis GEO Store
                            (GEOADD, GEOPOS)
```

ड्राइवरस हर 4 सेकंड GPS कूरदिनटेस पुबलिश करते हैं। WebSocket गेटवे अकटिवे ऑर्डर के लोकेशन अपडेट सुबसकरिबे करता है और कस्टमेर के डिवाइस पर पुश करता है। **Redis पुब/सुब** कुशलता से फ़न-ओउट संभाल करता है।

### अनुमानित देलिवेरय समय

EDT एक **बहु-चरणीय परेदिकशन** है:

```
EDT = restaurant_prep_time + driver_pickup_travel + dropoff_travel + buffer

जहाँ:
- restaurant_prep_time  → per restaurant historical order data पर trained ML model
- driver_pickup_travel  → distance/traffic API (Google Maps, Mapbox)
- dropoff_travel        → same routing API
- buffer                → dynamic, बारिश/peak hours में बढ़ता है
```

<ThinkAboutIt>ऊपर दिया मैचिंग एल्गोरिदम फ़िक्सेद वेट्स (w1-w4) उपयोग करता है। इसे एक लर्निंग सिस्टम में कैसे एवोलवे करेंगे जो डिलीवरी स्पीड और ड्राइवर सटिसफ़कशन दोनों को सिमुलटनेओउसलय ऑप्टिमाइज़ करे?</ThinkAboutIt>

### पयमेनट परोकेसिङ

पयमेनटस एक **दो-चरणीय पैटर्न** फ़ॉलो करते हैं:

1. **ऑथराइज़** - ऑर्डर रखे होने पर धन रिज़र्व करें (बनाए करें, चार्ज नहीं)
2. **कैप्चर** - डिलीवरी कोनफ़िरम होने के बाद वास्तविक अमोउनट चार्ज करें

यह ऑर्डर बदलाव, रद्दीकरण, और आंशिक रेधन सुचारु ढंग से संभाल करता है। डबल चार्जिंग रोकने के लिए हर पेमेंट रिक्वेस्ट पर **इडेम्पोटेंसी की** इस्तेमाल करें।

## फसे 5: स्केलिंग और बोटटलेनेकस (10 मिनट)

### दटबसे स्केलिंग

- **ओरदेर सर्विस**: `order_id` से शार्ड करें - ऑर्डर इनदेपेनदेनट हैं, होरिज़ोनटल स्केलिंग सटरैघटफ़ोरवरद
- **रेस्तरां सर्विस**: सर्च क्वेरी के लिए रेअद रेपलिकस, फ़ुलल-टेक्सट और गेओसपटिअल सर्च के लिए Elasticsearch
- **ड्राइवर लोकशन**: गेओसपटिअल इनदेक्सिङ के साथ Redis कलुसटेर - पुरे इन-मेमोरय, सुब-मिललिसेकोनद रीड

### पीक लोअद हनदले करना (सुरगे)

पीक समय (शुक्रवार शाम 7 बजे, बड़े खेल इवेंट) पर ऑर्डर वॉल्यूम 10× स्पाइक हो सकता है:

- क्यू गहराई पर आधारित अपपलिकशन पोदस का **औटो-स्केलिंग**, CPU पर नहीं
- सुपपलय और देमनद संतुलन करने के लिए **सुरगे परिकिङ** - ड्राइवर सुपपलय कम हो तो डिलीवरी फ़ीस बढ़ाएँ
- पीक में अबुसे रोकने के लिए प्रति यूज़र **दर लिमिटिङ**
- दोवनसटरेअम सेवाएँ पर **सर्किट ब्रेकर** - कसकदिङ फ़ैलुरे की जगह सुचारु गिरावट

## 💡 इंटरव्यू टिपस

1. **समय संरचना करें** - ज़रूरतें पर 30 मिनट मत लगाएँ
2. **टरदे-ओफ़फ़स एक्सपलिकिटलय बताएँ** - "मैंने X चुना Y की जगह क्योंकि..."
3. **सिमपले शुरू करें, फिर स्केल करें** - पहले 1× लोड के लिए डिज़ाइन, फिर 100× हल करें
4. **बोलते हुए दरव करें** - विसुअल संचार मूल्यांकन का आधा हिस्सा है
5. **उनकनोवनस स्वीकार करें** - "इसे बेनचमरक करना होगा, लेकिन मेरा हयपोथेसिस है..."
