# システム設計模擬面接 - 45 分間のシニア エンジニア シミュレーション

システム設計の面接では、上級エンジニアを他のエンジニアから切り離します。唯一の正解はありません。面接官はあなたの**構造化された思考**、トレードオフ分析、曖昧さを乗り越える能力を評価します。このレッスンは 45 分間の完全なシミュレーションです。

## 🎯 問題: 食品配送システムの設計

*「顧客、レストラン、配達ドライバーをつなぐ、Uber Eats や Deliveroo のような食品配達プラットフォームを設計します。」*

<Illustration src="/images/lessons/system-design-mock-interview.svg" alt="ユーザー、レストラン、注文、ドライバーのサービスを備えた食品配達システムの高レベルのアーキテクチャ" caption="食品配達プラットフォームの 4 つのコア ドメイン - それぞれが独自のサービスを持つ境界付きコンテキストです。" />

## フェーズ 1: 要件の収集 (5 分)

**すぐにボックスの描画を開始しないでください。** 最初に明確な質問をしてください。

**機能要件:**
- 顧客はレストランを閲覧し、メニューを表示し、注文し、配達をリアルタイムで追跡します
- レストランはメニューの管理、注文の受け入れ/拒否、準備状況の更新を行います
- ドライバーは配送リクエストを受け取り、集荷/降車場所に移動し、配送を確認します
- 注文ライフサイクル全体を通じてリアルタイムの推定納期 (EDT) が表示されます

**非機能要件:**
- **可用性**: 99.99% の稼働時間 (ダウンタイムは年間約 52 分)
- **待ち時間**: 検索 < 200 ミリ秒、注文発注 < 500 ミリ秒、位置情報の更新 < 1 秒
- **規模**: 月間アクティブ ユーザー数 5,000 万人、1 日あたり 500 万件の注文、ピーク時の同時ユーザー数 50 万人
- **一貫性**: 検索に許容される最終的な一貫性。支払いの強力な一貫性

<Quiz question="レストラン検索では結果整合性が許容されるのに、支払い処理では許容されないのはなぜですか?" options="検索は支払いほど重要ではない|多少古いメニューが表示されても許容範囲です。ユーザーに 2 回請求することはできません|最終的な整合性は常に高速です|支払い API は結果整合性をサポートしていません" answer="1" explanation="閉店したばかりのレストランがユーザーに表示されるのは少々不便ですが、再試行すると問題は解決します。しかし、支払いを 2 回処理すると、実際の経済的損害が発生します。不整合のコストによって整合性モデルが決まります。" />

## フェーズ 2: API 設計 (5 分)

アーキテクチャの前にコア コントラクトを定義します。

```
# Customer APIs
GET    /api/v1/restaurants?lat={}&lng={}&cuisine={}  → Restaurant[]
GET    /api/v1/restaurants/{id}/menu                  → Menu
POST   /api/v1/orders                                 → Order
GET    /api/v1/orders/{id}/track                      → OrderStatus + DriverLocation

# Restaurant APIs
PATCH  /api/v1/restaurants/{id}/menu/items/{itemId}   → MenuItem
POST   /api/v1/orders/{id}/accept                     → Order
POST   /api/v1/orders/{id}/ready                      → Order

# Driver APIs
POST   /api/v1/drivers/{id}/location                  → void (fire-and-forget)
POST   /api/v1/deliveries/{id}/accept                 → Delivery
POST   /api/v1/deliveries/{id}/complete               → Delivery
```

**重要な決定**: リアルタイムのドライバー追跡には WebSocket を使用し、その他すべてには REST を使用します。

## フェーズ 3: 高レベルのアーキテクチャ (10 分)

### コアサービス

|サービス |責任 |データベース |
|----------|---------------|----------|
| **ユーザーサービス** |認証、プロファイル、アドレス |ポストグレSQL |
| **レストランサービス** |メニュー、提供状況、営業時間 | PostgreSQL + Elasticsearch |
| **注文サービス** |注文ライフサイクル、ステートマシン | PostgreSQL (強整合性) |
| **ドライバーサービス** |ドライバーの場所、可用性、マッチング | Redis (場所) + PostgreSQL |
| **決済サービス** |チャージ、払い戻し、レストランでの支払い | PostgreSQL (ACID が必要) |
| **通知サービス** |プッシュ、SMS、電子メール通知 |メッセージキューコンシューマ |

### コミュニケーションパターン

- **同期**: API ゲートウェイ → 個別サービス (REST/gRPC)
- **非同期**: **Kafka** に発行された注文イベント - 支払い、通知、および分析サービスによって消費されます
- **リアルタイム**: WebSocket 経由でドライバーの位置を更新 → 地理空間インデックスを使用して **Redis** に保存

<FunFact>Uber は世界中で 1 秒あたり 100 万件を超える位置情報の更新を処理しています。従来の緯度/経度クエリでは大規模化に対応できなかったため、彼らは六角形の階層グリッドを使用して独自の地理空間インデックス システム (H3) を構築しました。</FunFact>

## フェーズ 4: 詳細 - 重要なコンポーネント (15 分)

### ドライバーマッチングアルゴリズム

注文品の受け取り準備が整うと、マッチング サービスは最適なドライバーを割り当てる必要があります。

```
Score(driver) = w1 × (1 / distance_to_restaurant)
              + w2 × driver_rating
              + w3 × (1 / current_active_orders)
              + w4 × acceptance_rate
```

**実装**: レストランから 5 km 以内のドライバーについて Redis `GEORADIUS` をクエリし、各候補をスコアリングし、利用可能な最高スコアのドライバーを割り当てます。拒否された場合は、30 秒のタイムアウトを設けて次のドライバーに申し出ます。

### リアルタイム注文追跡

```
Client ←→ WebSocket Gateway ←→ Driver Service
                                    ↑
                              Redis GEO Store
                            (GEOADD, GEOPOS)
```

ドライバーは 4 秒ごとに GPS 座標を公開します。 WebSocket ゲートウェイは、アクティブな注文の位置情報の更新をサブスクライブし、それらを顧客のデバイスにプッシュします。 **Redis Pub/Sub** はファンアウトを効率的に処理します。

### 配達予定時間

EDT は **多段階予測**です。

```
EDT = restaurant_prep_time + driver_pickup_travel + dropoff_travel + buffer

Where:
- restaurant_prep_time  → ML model trained on historical order data per restaurant
- driver_pickup_travel  → distance/traffic API (Google Maps, Mapbox)
- dropoff_travel        → same routing API
- buffer                → dynamic, increases during rain/peak hours
```

<ThinkAboutIt>上記のマッチング アルゴリズムでは、固定の重み (w1 ～ w4) が使用されます。これを、配達速度とドライバーの満足度を同時に最適化する学習システムにどのように進化させますか?</ThinkAboutIt>

### 支払い処理

支払いは **2 段階のパターン**に従います。

1. **承認** - 注文時に資金を準備します (保留、チャージしません)
2. **キャプチャ** - 配達確認後に実際の金額を請求します

これにより、注文の変更、キャンセル、部分的な返金が適切に処理されます。再試行中の二重請求を防ぐために、すべての支払いリクエストで*冪等キー**を使用してください。

<Quiz question="すぐに請求するのではなく、2 段階の支払いパターン (承認してから回収) を使用するのはなぜですか?" options="1回の充電よりも速い|複雑な取り消しロジックを使用せずにキャンセル、変更、返金を処理します。|決済プロバイダーはそれを要求します|取引手数料を削減します" answer="1" explanation="Authorise-then-capture を使用すると、コミットせずに資金を保持できます。レストランがキャンセルしたり、注文が変更になった場合は、承認を解除するだけで済み、返金処理は必要ありません。これにより、エッジケースが大幅に簡素化されます。" />

## フェーズ 5: スケーリングとボトルネック (10 分)

### データベースのスケーリング

- **注文サービス**: `order_id` によるシャード - 注文は独立しており、水平方向のスケーリングは簡単です
- **レストラン サービス**: 検索クエリ用のリードレプリカ、全文および地理空間検索用の Elasticsearch
- **ドライバーの場所**: 地理空間インデックスを備えた Redis クラスター - 純粋なメモリ内、ミリ秒未満の読み取り

### ピーク負荷 (サージ) への対応

ピーク時（金曜日の午後 7 時、主要なスポーツ イベント）には、注文量が 10 倍に急増する可能性があります。

- CPU ではなくキューの深さに基づいた **自動スケーリング** アプリケーション ポッド
- **需要と供給のバランスを取るための価格急騰** - ドライバーの供給が少ない場合は配達料金を値上げします
- ユーザーごとの**レート制限**により、ピーク時の悪用を防止します
- ダウンストリーム サービスの **サーキット ブレーカー** - カスケード障害に対する正常な機能低下

### 単一障害点

|コンポーネント |緩和 |
|----------|----------|
| APIゲートウェイ |ロードバランサーの背後にある複数のインスタンス、ヘルスチェック |
|カフカ |レプリケーション ファクター 3 のマルチブローカー クラスター |
|レディス |自動フェイルオーバーのための Redis Sentinel |
|決済プロバイダー |自動フォールバックを備えたセカンダリプロバイダー |

<ThinkAboutIt>面接官は「ピーク時に決済サービスが 30 秒間停止した場合はどうなりますか?」と質問します。正確な障害モード、注文がどのような影響を受けるか、回復がどのように行われるかを説明します。</ThinkAboutIt>

## 💡 面接のヒント

1. **時間を構成する** - 要件に 30 分も費やさないでください
2. **トレードオフを明示的に説明** - 「Y ではなく X を選択したのは、...」
3. **シンプルに始めて、その後スケール** - 最初に 1 倍の負荷を想定して設計し、次に 100 倍に対応します
4. **話しながら描く** - 視覚的なコミュニケーションが評価の半分です
5. **未知の部分を認識する** - 「これをベンチマークする必要がありますが、私の仮説は...」

## 🎯 重要なポイント

- 常に要件から始めます - 機能的および非機能的
- アーキテクチャ図の前に API コントラクトを設計する
- 表面的にすべてを説明するのではなく、2 ～ 3 つのコンポーネントを深く掘り下げます
- アーキテクチャ上のあらゆる選択にはトレードオフが伴います - 名前を付けてください
- タイマーを使用した練習: 45 分、延長なし
