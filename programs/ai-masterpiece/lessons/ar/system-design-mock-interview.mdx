# مقابلة وهمية لتصميم النظام - محاكاة لمهندس كبير لمدة 45 دقيقة

تفصل مقابلات تصميم النظام بين كبار المهندسين عن أي شخص آخر. لا توجد إجابة واحدة صحيحة، إذ يقوم القائمون على إجراء المقابلات بتقييم **تفكيرك المنظم** وتحليل المفاضلة وقدرتك على تجاوز الغموض. هذا الدرس عبارة عن محاكاة كاملة مدتها 45 دقيقة.

## 🎯 المشكلة: تصميم نظام توصيل الطعام

*"تصميم منصة لتوصيل الطعام مثل Uber Eats أو Deliveryoo التي تربط العملاء والمطاعم وسائقي التوصيل."*

<Illustration src="/images/lessons/system-design-mock-interview.svg" alt="بنية عالية المستوى لنظام توصيل الطعام مع خدمات المستخدم والمطعم والطلب والسائق" caption="المجالات الأربعة الأساسية لمنصة توصيل الطعام - كل منها عبارة عن سياق محدود مع خدمته الخاصة." />

## المرحلة الأولى: جمع المتطلبات (5 دقائق)

**لا تبدأ أبدًا في رسم المربعات على الفور.** اطرح الأسئلة التوضيحية أولاً:

**المتطلبات الوظيفية:**
- يتصفح العملاء المطاعم ويعرضون القوائم ويقدمون الطلبات ويتتبعون عملية التسليم في الوقت الفعلي
- إدارة المطاعم للقوائم وقبول/رفض الطلبات وتحديث حالة التحضير
- يتلقى السائقون طلبات التسليم، وينتقلون إلى الاستلام/التوصيل، ويؤكدون التسليم
- وقت التسليم المقدر في الوقت الفعلي (EDT) الموضح طوال دورة حياة الطلب

** المتطلبات غير الوظيفية: **
- **التوفر**: وقت تشغيل بنسبة 99.99% (≈52 دقيقة توقف في السنة)
- **زمن الوصول**: البحث <200 مللي ثانية، وضع الطلب <500 مللي ثانية، تحديثات الموقع <1 ثانية
- **النطاق**: 50 مليون مستخدم نشط شهريًا، و5 ملايين طلب يوميًا، و500 ألف مستخدم متزامن في الذروة
- **الاتساق**: الاتساق النهائي المقبول للبحث؛ اتساق قوي للمدفوعات

## المرحلة الثانية: تصميم واجهة برمجة التطبيقات (5 دقائق)

تحديد العقود الأساسية قبل الهندسة المعمارية:

```
# Customer APIs
GET    /api/v1/restaurants?lat={}&lng={}&cuisine={}  → Restaurant[]
GET    /api/v1/restaurants/{id}/menu                  → Menu
POST   /api/v1/orders                                 → Order
GET    /api/v1/orders/{id}/track                      → OrderStatus + DriverLocation

# Restaurant APIs
PATCH  /api/v1/restaurants/{id}/menu/items/{itemId}   → MenuItem
POST   /api/v1/orders/{id}/accept                     → Order
POST   /api/v1/orders/{id}/ready                      → Order

# Driver APIs
POST   /api/v1/drivers/{id}/location                  → void (fire-and-forget)
POST   /api/v1/deliveries/{id}/accept                 → Delivery
POST   /api/v1/deliveries/{id}/complete               → Delivery
```

**القرار الرئيسي**: استخدم WebSockets لتتبع السائق في الوقت الفعلي، وREST لكل شيء آخر.

## المرحلة الثالثة: الهندسة المعمارية رفيعة المستوى (10 دقائق)

### الخدمات الأساسية

| الخدمة | المسؤولية | قاعدة بيانات |
|---------|--------------|----------|
| **خدمة المستخدم** | المصادقة والملفات الشخصية والعناوين | بوستجرس كيو ال |
| ** خدمة المطاعم ** | القوائم، التوفر، ساعات العمل | PostgreSQL + Elasticsearch |
| **خدمة الطلب** | دورة حياة الطلب، آلة الحالة | PostgreSQL (اتساق قوي) |
| ** خدمة السائق ** | موقع السائق، التوفر، المطابقة | ريديس (الموقع) + PostgreSQL |
| **خدمة الدفع** | الرسوم والمبالغ المستردة ومدفوعات المطاعم | PostgreSQL (يتطلب ACID) |
| **خدمة الإخطارات** | إشعارات الدفع والرسائل النصية القصيرة والبريد الإلكتروني | مستهلك قائمة انتظار الرسائل |

### أنماط الاتصال

- **متزامن**: بوابة API ← الخدمات الفردية (REST/gRPC)
- **غير متزامنة**: أحداث الطلب المنشورة على **كافكا** - التي تستهلكها خدمات الدفع والإشعارات والتحليلات
- **في الوقت الفعلي**: تحديثات موقع برنامج التشغيل عبر WebSocket → مخزنة في **Redis** مع الفهرسة الجغرافية المكانية

<FunFact>تقوم أوبر بمعالجة أكثر من مليون تحديث للموقع في الثانية على مستوى العالم. لقد قاموا ببناء نظام الفهرسة الجغرافية المكانية الخاص بهم (H3) باستخدام شبكات هرمية سداسية لأن استعلامات خطوط الطول والعرض التقليدية لا يمكنها مواكبة النطاق.</FunFact>

## المرحلة الرابعة: الغوص العميق - المكونات المهمة (15 دقيقة)

### خوارزمية مطابقة برنامج التشغيل

عندما يكون الطلب جاهزًا للاستلام، يجب أن تقوم الخدمة المطابقة بتعيين برنامج التشغيل الأمثل:

```
Score(driver) = w1 × (1 / distance_to_restaurant)
              + w2 × driver_rating
              + w3 × (1 / current_active_orders)
              + w4 × acceptance_rate
```

**التنفيذ**: الاستعلام عن Redis `GEORADIUS` للسائقين الذين يقعون على بعد 5 كيلومترات من المطعم، وسجل كل مرشح، وقم بتعيين السائق المتاح الحاصل على أعلى الدرجات. إذا تم الرفض، فاعرض على السائق التالي مهلة مدتها 30 ثانية.

### تتبع الطلب في الوقت الحقيقي

```
Client ←→ WebSocket Gateway ←→ Driver Service
                                    ↑
                              Redis GEO Store
                            (GEOADD, GEOPOS)
```

يقوم السائقون بنشر إحداثيات نظام تحديد المواقع العالمي (GPS) كل 4 ثوانٍ. تشترك بوابة WebSocket في تحديثات الموقع للطلبات النشطة وتدفعها إلى جهاز العميل. **يتعامل **Redis Pub/Sub** مع عملية التوزيع بكفاءة.

### وقت التسليم المقدر

EDT هو **تنبؤ متعدد المراحل**:

```
EDT = restaurant_prep_time + driver_pickup_travel + dropoff_travel + buffer

Where:
- restaurant_prep_time  → ML model trained on historical order data per restaurant
- driver_pickup_travel  → distance/traffic API (Google Maps, Mapbox)
- dropoff_travel        → same routing API
- buffer                → dynamic, increases during rain/peak hours
```

<ThinkAboutIt>تستخدم خوارزمية المطابقة أعلاه أوزانًا ثابتة (w1 – w4). كيف يمكنك تطوير هذا إلى نظام تعليمي يعمل على تحسين سرعة التسليم ورضا السائق في وقت واحد؟ </ThinkAboutIt>

### معالجة الدفع

تتبع الدفعات **نمطًا من مرحلتين**:

1. **التفويض** - احتياطي الأموال عند تقديم الطلب (تعليق، عدم تحصيل رسوم)
2. **التقاط** - اشحن المبلغ الفعلي بعد تأكيد التسليم

يتعامل هذا مع تعديلات الطلب والإلغاءات والمبالغ المستردة الجزئية بأمان. استخدم **مفتاح الفاعلية** في كل طلب دفع لمنع الشحن المزدوج أثناء إعادة المحاولة.

## المرحلة الخامسة: القياس والاختناقات (10 دقائق)

### تحجيم قاعدة البيانات

- **خدمة الطلب**: جزء من `order_id` - الطلبات مستقلة، والقياس الأفقي واضح ومباشر
- **خدمة المطاعم**: قراءة النسخ المتماثلة لاستعلامات البحث، وElasticsearch للبحث عن النص الكامل والبحث الجغرافي المكاني
- **موقع السائق**: مجموعة Redis مع الفهرسة الجغرافية المكانية - ذاكرة نقية في الذاكرة، وقراءات أقل من مللي ثانية

### التعامل مع حمل الذروة (الاندفاع)

في أوقات الذروة (الجمعة الساعة 7 مساءً، الأحداث الرياضية الكبرى)، يمكن أن يرتفع حجم الطلب بمقدار 10 مرات:

- **وحدات القياس التلقائي** بناءً على عمق قائمة الانتظار، وليس وحدة المعالجة المركزية
- **التسعير المفاجئ** لتحقيق التوازن بين العرض والطلب - زيادة رسوم التوصيل عندما يكون عرض السائق منخفضًا
- **تحديد السعر** لكل مستخدم لمنع إساءة الاستخدام خلال فترة الذروة
- **قواطع الدائرة** في الخدمات النهائية - تدهور بسيط بسبب الفشل المتتالي

### نقاط الفشل الفردية

| مكون | التخفيف |
|-----------|-----------|
| بوابة API | مثيلات متعددة خلف موازن التحميل، وفحوصات السلامة |
| كافكا | مجموعة متعددة الوسطاء مع عامل النسخ 3 |
| ريديس | Redis Sentinel لتجاوز الفشل التلقائي |
| مزود الدفع | مزود ثانوي مع احتياطي تلقائي |

## 💡 نصائح للمقابلة

1. **نظم وقتك** - لا تقضي 30 دقيقة في المتطلبات
2. **ذكر المقايضات بشكل صريح** - "لقد اخترت X بدلاً من Y لأن..."
3. **ابدأ بسيطًا، ثم قم بالقياس** - تصميم لتحميل 1× أولاً، ثم معالجة 100×
4. **ارسم وأنت تتحدث** - التواصل البصري هو نصف التقييم
5. **الاعتراف بالمجهولات** - "أحتاج إلى قياس ذلك، لكن فرضيتي هي..."

## 🎯 الوجبات السريعة الرئيسية

- ابدأ دائمًا بالمتطلبات - الوظيفية وغير الوظيفية
- تصميم عقود API قبل المخططات المعمارية
- قم بالتعمق في 2-3 مكونات، وليس جميعها بشكل سطحي
- كل خيار معماري يتضمن مقايضات - قم بتسميتها
- التمرين بمؤقت: 45 دقيقة، بدون تمديدات
