# సిస్టమ్ డిజైన్ మాక్ ఇంటర్వ్యూ - 45 నిమిషాల సీనియర్ ఇంజనీర్ సిమ్యులేషన్

సిస్టమ్ డిజైన్ ఇంటర్వ్యూలు సీనియర్ ఇంజనీర్లను మిగతా వారి నుండి వేరు చేస్తాయి. ఒకే సరైన సమాధానం లేదు. ఇంటర్వ్యూయర్లు మీ **నిర్మిత ఆలోచన**, రాజీ విశ్లేషణ, మరియు అస్పష్టతను ఎదుర్కొనే సామర్థ్యాన్ని మూల్యాంకనం చేస్తారు. ఈ పాఠం పూర్తి 45 నిమిషాల సిమ్యులేషన్.

## 🎯 సమస్య: ఫుడ్ డెలివరీ సిస్టమ్ డిజైన్ చేయండి

*"కస్టమర్లు, రెస్టారెంట్లు, మరియు డెలివరీ డ్రైవర్లు ను కనెక్ట్ చేసే Uber Eats లేదా Deliveroo వంటి ఫుడ్ డెలివరీ ప్లాట్‌ఫారమ్ డిజైన్ చేయండి."*

## దశ 1: అవసరాల సేకరణ (5 నిమిషాలు)

**వెంటనే boxes గీయడం మొదలుపెట్టకండి.** ముందుగా స్పష్టీకరణ ప్రశ్నలు అడగండి:

**Functional అవసరాలు:**
- కస్టమర్లు రెస్టారెంట్లు బ్రౌజ్ చేయడం, మెనూలు చూడడం, ఆర్డర్లు పెట్టడం, రియల్ టైమ్ లో డెలివరీ ట్రాక్ చేయడం
- రెస్టారెంట్లు మెనూలు నిర్వహించడం, ఆర్డర్లు అంగీకరించడం/తిరస్కరించడం, తయారీ స్థితిని నవీకరించడం
- డ్రైవర్లు డెలివరీ రిక్వెస్ట్‌లు స్వీకరించడం, పికప్/డ్రాప్‌ఆఫ్‌కు దారి కనుగొనడం, డెలివరీని నిర్ధారించడం
- ఆర్డర్ జీవనచక్రం అంతటా రియల్ టైమ్ అంచనా డెలివరీ సమయం (EDT) చూపించడం

**Non-functional అవసరాలు:**
- **అందుబాటు**: 99.99% పని చేసే సమయం (సంవత్సరానికి ≈52 నిమిషాల పని నిలిచే సమయం)
- **లేటెన్సీ**: సెర్చ్ < 200ms, ఆర్డర్ పెట్టడం < 500ms, స్థానం నవీకరణలు < 1s
- **స్కేల్**: 50M నెలవారీ active వినియోగదారులు, రోజుకు 5M ఆర్డర్లు, పీక్ లో 500K సమకాలిక వినియోగదారులు
- **స్థిరత్వం**: సెర్చ్ కోసం చివరికి వచ్చే స్థిరత్వం సరిపోతుంది; payments కోసం బలమైన స్థిరత్వం

## దశ 2: API డిజైన్ (5 నిమిషాలు)

ఆర్కిటెక్చర్ కంటే ముందు మూల ఒప్పందాలు నిర్వచించండి:

```
# Customer APIs
GET    /api/v1/restaurants?lat={}&lng={}&cuisine={}  → Restaurant[]
GET    /api/v1/restaurants/{id}/menu                  → Menu
POST   /api/v1/orders                                 → Order
GET    /api/v1/orders/{id}/track                      → OrderStatus + DriverLocation

# Restaurant APIs
PATCH  /api/v1/restaurants/{id}/menu/items/{itemId}   → MenuItem
POST   /api/v1/orders/{id}/accept                     → Order
POST   /api/v1/orders/{id}/ready                      → Order

# Driver APIs
POST   /api/v1/drivers/{id}/location                  → void (fire-and-forget)
POST   /api/v1/deliveries/{id}/accept                 → Delivery
POST   /api/v1/deliveries/{id}/complete               → Delivery
```

**కీలక నిర్ణయం**: రియల్ టైమ్ డ్రైవర్ ట్రాకింగ్ కోసం WebSockets, మిగతా అన్నింటికీ REST ఉపయోగించండి.

## దశ 3: ఉన్నత-స్థాయి ఆర్కిటెక్చర్ (10 నిమిషాలు)

### మూల సేవలు

| సేవ | బాధ్యత | డేటాబేస్ |
|---------|--------|----------|
| **వినియోగదారు సేవ** | ప్రామాణీకరణ, ప్రొఫైల్‌లు, చిరునామాలు | PostgreSQL |
| **Restaurant సేవ** | మెనూలు, అందుబాటు, గంటలు | PostgreSQL + Elasticsearch |
| **ఆర్డర్ సర్వీస్** | ఆర్డర్ జీవనచక్రం, స్థితి యంత్రం | PostgreSQL (బలమైన స్థిరత్వం) |
| **Driver సేవ** | డ్రైవర్ స్థానం, అందుబాటు, జతపరచడం | Redis (స్థానం) + PostgreSQL |
| **Payment సేవ** | ఛార్జీలు, రీఫండ్‌లు, రెస్టారెంట్ చెల్లింపులు | PostgreSQL (ACID అవసరం) |
| **నోటిఫికేషన్ సేవ** | పుష్, SMS, ఇమెయిల్ నోటిఫికేషన్‌లు | సందేశం క్యూ కన్స్యూమర్ |

### కమ్యూనికేషన్ నమూనాలు

- **Synchronous**: API గేట్‌వే → వ్యక్తిగత సేవలు (REST/gRPC)
- **Asynchronous**: ఆర్డర్ ఈవెంట్లు **Kafka** కు ప్రచురించండి - చెల్లింపు, నోటిఫికేషన్, మరియు విశ్లేషణలు సేవలు వినియోగిస్తాయి చేస్తాయి
- **రియల్ టైమ్**: డ్రైవర్ స్థానం నవీకరణలు WebSocket ద్వారా → geospatial ఇండెక్సింగ్ తో **Redis** లో నిల్వ

<FunFact>Uber ప్రపంచవ్యాప్తంగా సెకనుకు 1 మిలియన్ కంటే ఎక్కువ స్థానం నవీకరణలు ప్రాసెస్ చేస్తుంది. సాంప్రదాయ అక్షాంశం/రేఖాంశం క్వెరీలు స్కేల్‌లో తట్టుకోలేక వారు షట్కోణ శ్రేణీకృత గ్రిడ్‌లను ఉపయోగించి సొంత భౌగోళిక ఇండెక్సింగ్ సిస్టమ్ (H3) నిర్మించారు.</FunFact>

## దశ 4: లోతైన అధ్యయనం - కీలక భాగాలు (15 నిమిషాలు)

### డ్రైవర్ Matching అల్గారిథమ్

ఆర్డర్ పికప్ కోసం సిద్ధమైనప్పుడు, జతపరచే సేవ ఉత్తమ డ్రైవర్‌ను కేటాయించాలి:

```
Score(driver) = w1 × (1 / distance_to_restaurant)
              + w2 × driver_rating
              + w3 × (1 / current_active_orders)
              + w4 × acceptance_rate
```

**అమలు**: రెస్టారెంట్ నుండి 5km లోపల డ్రైవర్ల కోసం Redis `GEORADIUS` క్వెరీ, ప్రతి అభ్యర్థిని స్కోర్ చేయండి, అత్యధిక స్కోరు ఉన్న అందుబాటులోని డ్రైవర్‌ను కేటాయించండి. తిరస్కరిస్తే, 30 సెకన్ల గడువుతో తదుపరి డ్రైవర్‌కు ఆఫర్ చేయండి.

### రియల్ టైమ్ ఆర్డర్ ట్రాకింగ్

```
Client ←→ WebSocket Gateway ←→ Driver Service
                                    ↑
                              Redis GEO Store
                            (GEOADD, GEOPOS)
```

డ్రైవర్లు ప్రతి 4 సెకన్లకు GPS స్థానాంకాలు ప్రచురిస్తారు. WebSocket గేట్‌వే చురుకైన ఆర్డర్ల కోసం స్థానం నవీకరణలకు చందా అయి కస్టమర్ పరికరానికి పుష్ చేస్తుంది. **Redis Pub/Sub** విస్తరణను సమర్థంగా నిర్వహిస్తుంది.

### Estimated డెలివరీ సమయం

EDT **బహుళ-stage అంచనా**:

```
EDT = restaurant_prep_time + driver_pickup_travel + dropoff_travel + buffer

ఇక్కడ:
- restaurant_prep_time  → ప్రతి restaurant కు historical order data పై train చేసిన ML model
- driver_pickup_travel  → distance/traffic API (Google Maps, Mapbox)
- dropoff_travel        → అదే routing API
- buffer                → dynamic, వర్షం/peak hours లో పెరుగుతుంది
```

<ThinkAboutIt>పై జతపరచే అల్గారిథమ్ స్థిర బరువులు (w1-w4) ఉపయోగిస్తుంది. డెలివరీ వేగం మరియు డ్రైవర్ సంతృప్తి రెండింటినీ ఏకకాలంలో మెరుగుపరచే అభ్యాస సిస్టమ్‌గా దీన్ని ఎలా అభివృద్ధి చేస్తారు?</ThinkAboutIt>

### చెల్లింపు ప్రాసెసింగ్

చెల్లింపులు **రెండు దశల నమూనా** అనుసరిస్తాయి:

1. **ఆథరైజ్** - ఆర్డర్ పెట్టినప్పుడు నిధులను నిల్వ చేయండి (హోల్డ్, ఛార్జ్ కాదు)
2. **స్వీకరించు** - డెలివరీ నిర్ధారణ తర్వాత వాస్తవ మొత్తాన్ని ఛార్జ్ చేయండి

ఇది ఆర్డర్ మార్పులు, రద్దులు, మరియు పాక్షిక రీఫండ్‌లను సునాయాసంగా నిర్వహిస్తుంది. రెండుసార్లు ఛార్జ్ కావడం నివారించడానికి ప్రతి చెల్లింపు రిక్వెస్ట్‌పై **ఐడెంపోటెన్సీ కీ** ఉపయోగించండి.

## దశ 5: స్కేలింగ్ మరియు Bottlenecks (10 నిమిషాలు)

### డేటాబేస్ స్కేలింగ్

- **ఆర్డర్ సర్వీస్**: `order_id` ద్వారా షార్డ్ చేయండి. ఆర్డర్లు స్వతంత్రం, అడ్డంగా స్కేలింగ్ సులభం
- **Restaurant సేవ**: సెర్చ్ క్వెరీలు కోసం చదవు ప్రతిరూపాలు, పూర్తి టెక్స్ట్ మరియు భౌగోళిక సెర్చ్ కోసం Elasticsearch
- **Driver స్థానం**: భౌగోళిక ఇండెక్సింగ్‌తో Redis క్లస్టర్. పూర్తిగా మెమరీలో, మిల్లీసెకండ్ కంటే తక్కువ చదవులు

### పీక్ లోడ్ నిర్వహణ (సర్జ్)

పీక్ సార్లు (శుక్రవారం 7pm, పెద్ద క్రీడా ఈవెంట్లు)లో, ఆర్డర్ పరిమాణం 10× పెరగవచ్చు:

- CPU కాదు, క్యూ లోతు ఆధారంగా అప్లికేషన్ pods **ఆటో-స్కేలింగ్**
- సరఫరా మరియు డిమాండ్ బ్యాలెన్స్ చేయడానికి **సర్జ్ ధర నిర్ణయం** - డ్రైవర్ సరఫరా తక్కువగా ఉన్నప్పుడు డెలివరీ fees పెంచండి
- పీక్ సమయంలో abuse నివారించడానికి వినియోగదారు కు **రేట్ పరిమితం చేసే**
- దిగువ సేవలపై **సర్క్యూట్ బ్రేకర్లు**. వరుస విఫలం కంటే మృదువైన దిగజార్పు
