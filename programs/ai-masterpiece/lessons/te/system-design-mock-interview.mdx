# సిస్టమ్ డిజైన్ మాక్ ఇంటర్వ్యూ - 45 నిమిషాల సీనియర్ ఇంజనీర్ సిమ్యులేషన్

సిస్టమ్ డిజైన్ ఇంటర్వ్యూలు సీనియర్ ఇంజనీర్లను మిగతా వారి నుండి వేరు చేస్తాయి. ఒకే సరైన సమాధానం లేదు - ఇంటర్వ్యూయర్లు మీ **నిర్మిత ఆలోచన**, ట్ర్అడ్ె-ఆఫ్ విశ్లేషణ, మరియు అమ్బ్ిగ్ుిటీ ను నావిగేట్ చేయండి చేసే సామర్థ్యాన్ని మూల్యాంకనం చేయండి చేస్తారు. ఈ పాఠం పూర్తి 45 నిమిషాల సిమ్యులేషన్.

## 🎯 సమస్య: ఫుడ్ డెలివరీ సిస్టమ్ డిజైన్ చేయండి

*"కస్టమర్లు, రెస్టారెంట్లు, మరియు డెలివరీ డ్రైవర్లు ను కనెక్ట్ చేసే Uber Eats లేదా Deliveroo వంటి ఫుడ్ డెలివరీ ప్లాట్‌ఫారమ్ డిజైన్ చేయండి."*

## దశ 1: అవసరాల సేకరణ (5 నిమిషాలు)

**వెంటనే బ్ోక్స్ెస్ గీయడం మొదలుపెట్టకండి.** ముందుగా స్పష్టీకరణ ప్రశ్నలు అడగండి:

**ఫంక్షనల్ అవసరాలు:**
- కస్టమర్లు రెస్టారెంట్లు బ్రౌజ్ చేయడం, మెనూలు చూడడం, ఆర్డర్లు పెట్టడం, రియల్ టైమ్ లో డెలివరీ ట్రాక్ చేయడం
- రెస్టారెంట్లు మెనూలు నిర్వహించండి చేయడం, ఆర్డర్లు అంగీకరించండి/తిరస్కరించండి చేయడం, తయారీ స్థితి నవీకరించు చేయడం
- డ్రైవర్లు డెలివరీ రిక్వెస్ట్‌లు స్వీకరించడం, ప్ిక్ుప్/డ్ర్ోప్ోఫ్ఫ్ కు నావిగేట్ చేయండి చేయడం, డెలివరీ క్ోన్ఫ్ిర్మ్ చేయడం
- క్రమం జీవనచక్రం అంతటా రియల్ టైమ్ ెస్ట్ిమ్అట్ెడ్ డెలివరీ సమయం (*EDT*) చూపించడం

**Non-functional అవసరాలు:**
- **అందుబాటు**: 99.99% అప్‌టైమ్ (సంవత్సరానికి ≈52 నిమిషాల డ్ౌన్ట్ిమ్ె)
- **లేటెన్సీ**: సెర్చ్ < 200ms, క్రమం ప్ల్అక్ెమెంట్ < 500ms, స్థానం నవీకరణలు < 1s
- **స్కేల్**: 50M నెలవారీ చురుకైన వినియోగదారులు, రోజుకు 5M ఆర్డర్లు, పీక్ లో 500K సమకాలిక వినియోగదారులు
- **స్థిరత్వం**: సెర్చ్ కోసం చివరికి వచ్చే స్థిరత్వం సరిపోతుంది; ప్ేమెంట్స్ కోసం బలమైన స్థిరత్వం

## దశ 2: *API* డిజైన్ (5 నిమిషాలు)

ఆర్కిటెక్చర్ కంటే ముందు మూల ఒప్పందాలు నిర్వచించండి:

```
# Customer APIs
GET    /api/v1/restaurants?lat={}&lng={}&cuisine={}  → Restaurant[]
GET    /api/v1/restaurants/{id}/menu                  → Menu
POST   /api/v1/orders                                 → Order
GET    /api/v1/orders/{id}/track                      → OrderStatus + DriverLocation

# Restaurant APIs
PATCH  /api/v1/restaurants/{id}/menu/items/{itemId}   → MenuItem
POST   /api/v1/orders/{id}/accept                     → Order
POST   /api/v1/orders/{id}/ready                      → Order

# Driver APIs
POST   /api/v1/drivers/{id}/location                  → void (fire-and-forget)
POST   /api/v1/deliveries/{id}/accept                 → Delivery
POST   /api/v1/deliveries/{id}/complete               → Delivery
```

**కీలక నిర్ణయం**: రియల్ టైమ్ డ్రైవర్ ట్రాకింగ్ కోసం WebSockets, మిగతా అన్నింటికీ **REST** ఉపయోగించండి.

## దశ 3: ఉన్నత-స్థాయి ఆర్కిటెక్చర్ (10 నిమిషాలు)

### మూల సేవలు

| సేవ | బాధ్యత | డేటాబేస్ |
|---------|--------|----------|
| **వినియోగదారు సేవ** | ప్రామాణీకరణ, ప్రొఫైల్‌లు, చిరునామాలు | **PostgreSQL** |
| **Restaurant సేవ** | మెనూలు, అందుబాటు, గంటలు | **PostgreSQL** + **Elasticsearch** |
| **క్రమం సేవ** | క్రమం జీవనచక్రం, స్థితి యంత్రం | **PostgreSQL** (బలమైన స్థిరత్వం) |
| **Driver సేవ** | డ్రైవర్ స్థానం, అందుబాటు, సరిపోల్చడం | **Redis** (స్థానం) + **PostgreSQL** |
| **Payment సేవ** | Charges, ర్ెఫ్ున్డ్స్, రెస్టారెంట్ ప్ేౌట్స్ | **PostgreSQL** (*ACID* అవసరం) |
| **నోటిఫికేషన్ సేవ** | పుష్, *SMS*, ఇమెయిల్ నోటిఫికేషన్‌లు | సందేశం క్యూ కన్స్యూమర్ |

### కమ్యూనికేషన్ నమూనాలు

- **Synchronous**: **API** గేట్‌వే → వ్యక్తిగత సేవలు (**REST**/గ్ర్ప్క్)
- **Asynchronous**: క్రమం ఈవెంట్లు **Kafka** కు ప్రచురించండి - చెల్లింపు, నోటిఫికేషన్, మరియు విశ్లేషణలు సేవలు వినియోగిస్తాయి చేస్తాయి
- **రియల్ టైమ్**: డ్రైవర్ స్థానం నవీకరణలు WebSocket ద్వారా → గ్ెోస్ప్అషల్ ఇండెక్సింగ్ తో **Redis** లో నిల్వ

<FunFact>*Uber* ప్రపంచవ్యాప్తంగా సెకనుకు 1 మిలియన్ కంటే ఎక్కువ స్థానం నవీకరణలు ప్రక్రియ చేస్తుంది. సాంప్రదాయ ల్అట్ిట్ుడ్ె/ల్ోన్గ్ిట్ుడ్ె క్వెరీలు స్కేల్ లో తట్టుకోలేక వారు హ్ెక్స్అగ్ోన్ల్ హ్ిర్ార్చ్ిక్ల్ గ్ర్ిడ్స్ ఉపయోగించి సొంత గ్ెోస్ప్అషల్ ఇండెక్సింగ్ సిస్టమ్ (H3) నిర్మించారు.</FunFact>

## దశ 4: లోతైన అధ్యయనం - కీలక భాగాలు (15 నిమిషాలు)

### డ్రైవర్ సరిపోల్చడం అల్గారిథమ్

క్రమం ప్ిక్ుప్ కోసం సిద్ధం అయినప్పుడు, సరిపోల్చడం సేవ ఉత్తమ డ్రైవర్ ను కేటాయించండి చేయాలి:

```
Score(driver) = w1 × (1 / distance_to_restaurant)
              + w2 × driver_rating
              + w3 × (1 / current_active_orders)
              + w4 × acceptance_rate
```

**అమలు**: రెస్టారెంట్ నుండి 5km లోపల డ్రైవర్లు కోసం **Redis** `GEORADIUS` క్వెరీ, ప్రతి అభ్యర్థి ను స్కోర్ చేయండి, అత్యధిక-స్క్ర్ింగ్ అందుబాటులో డ్రైవర్ ను కేటాయించండి చేయండి. *Decline* చేస్తే, 30-సెకన్ల ట్ిమ్ెౌట్ తో తదుపరి డ్రైవర్ కు ఆఫర్ చేయండి.

### నిజమైన-సమయం క్రమం ట్రాకింగ్

```
Client ←→ WebSocket Gateway ←→ Driver Service
                                    ↑
                              Redis GEO Store
                            (GEOADD, GEOPOS)
```

డ్రైవర్లు ప్రతి 4 సెకన్లకు *GPS* క్ూర్డ్ిన్అట్ెస్ ప్రచురించండి చేస్తారు. *WebSocket* గేట్‌వే చురుకైన ఆర్డర్లు కోసం స్థానం నవీకరణలు కు స్ుబ్స్క్ర్ిబ్ె అయి కస్టమర్ పరికరం కు పుష్ చేస్తుంది. **Redis Pub/Sub** ఫ్యాన్-అవుట్ ను సమర్థవంతంగా నిర్వహించు చేస్తుంది.

### *Estimated* డెలివరీ సమయం

*EDT* **బహుళ-దశ అంచనా**:

```
EDT = restaurant_prep_time + driver_pickup_travel + dropoff_travel + buffer

ఇక్కడ:
- restaurant_prep_time  → ప్రతి restaurant కు historical order data పై train చేసిన ML model
- driver_pickup_travel  → distance/traffic API (Google Maps, Mapbox)
- dropoff_travel        → అదే routing API
- buffer                → dynamic, వర్షం/peak hours లో పెరుగుతుంది
```

<ThinkAboutIt>పై సరిపోల్చడం అల్గారిథమ్ స్థిర బరువులు (w1–w4) ఉపయోగిస్తుంది. డెలివరీ వేగం మరియు డ్రైవర్ స్అట్ిస్ఫ్అక్షన్ రెండింటినీ ఏకకాలంలో మెరుగుపరచండి చేసే అభ్యాసం సిస్టమ్ గా దీన్ని ఎలా ెవ్ోల్వ్ె చేస్తారు?</ThinkAboutIt>

### చెల్లింపు ప్రాసెసింగ్

*Payments* **రెండు-ఫ్అస్ె నమూనా** అనుసరిస్తాయి:

1. **Authorise** - క్రమం పెట్టినప్పుడు ఫ్ున్డ్స్ ర్ెస్ర్వ్ె చేయండి (ఉంచండి, చ్ార్గ్ె చేయకండి)
2. **పట్టుకోండి** - డెలివరీ క్ోన్ఫ్ిర్మ్అషన్ తర్వాత వాస్తవ అమ్ౌన్ట్ చ్ార్గ్ె చేయండి

ఇది క్రమం మ్ోడ్ిఫ్ిక్అషన్స్, క్అన్క్ెల్ల్అషన్స్, మరియు పాక్షిక ర్ెఫ్ున్డ్స్ ను సునాయాసంగా నిర్వహించు చేస్తుంది. *Double-charging* నివారించడానికి ప్రతి చెల్లింపు రిక్వెస్ట్ పై **ఐడెంపోటెన్సీ కీ** ఉపయోగించండి.

## దశ 5: స్కేలింగ్ మరియు అడ్డంకులు (10 నిమిషాలు)

### డేటాబేస్ స్కేలింగ్

- **క్రమం సేవ**: `order_id` ద్వారా షార్డ్ - ఆర్డర్లు స్వతంత్రం, అడ్డంగా స్కేలింగ్ సులభం
- **Restaurant సేవ**: సెర్చ్ క్వెరీలు కోసం చదవడం ర్ెప్ల్ిక్అస్, పూర్తి-టెక్స్ట్ మరియు గ్ెోస్ప్అషల్ సెర్చ్ కోసం **Elasticsearch**
- **Driver స్థానం**: Geospatial ఇండెక్సింగ్ తో **Redis** క్లస్టర్ - పూర్తి లో-మెమరీ, ఉప-మ్ిల్ల్ైజ్క్ోన్డ్ రీడ్‌లు

### పీక్ లోడ్ నిర్వహించు చేయడం (సర్జ్)

పీక్ సార్లు (శుక్రవారం 7pm, పెద్ద క్రీడా ఈవెంట్లు) లో, క్రమం వ్ోల్ుమ్ె 10× ఒక్కసారిగా పెరుగుదల అవ్వవచ్చు:

- *CPU* కాదు, క్యూ లోతు ఆధారంగా అప్లికేషన్ ప్ోడ్స్ **ఆటో-స్కేలింగ్**
- సరఫరా మరియు డిమాండ్ బ్యాలెన్స్ చేయడానికి **సర్జ్ ధర నిర్ణయం** - డ్రైవర్ సరఫరా తక్కువగా ఉన్నప్పుడు డెలివరీ ఫ్ీస్ పెంచండి
- పీక్ సమయంలో అబ్ుస్ె నివారించడానికి వినియోగదారు కు **రేట్ పరిమితం చేసే**
- *Downstream* సేవలు పై **క్ిర్క్ుిట్ బ్ర్ీక్ర్స్** - క్అస్క్అడ్ింగ్ విఫలం కంటే సునాయాసమైన తగ్గుదల
