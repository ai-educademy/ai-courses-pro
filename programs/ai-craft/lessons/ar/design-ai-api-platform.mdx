## المطالبة بالمقابلة

*"صمم منصة AI API التي تخدم نماذج متعددة للتعلم الآلي للمطورين عبر REST API - على غرار الطريقة التي تخدم بها OpenAI أو Hugging Face النماذج على نطاق واسع."*

يحظى هذا السؤال بشعبية متزايدة في المقابلات لأنه يجمع بين **تصميم منصة API** و**تحديات البنية التحتية لوحدة معالجة الرسومات** الفريدة لأعباء عمل الذكاء الاصطناعي.

## الخطوة 1: جمع المتطلبات

**المتطلبات الوظيفية:**
- خدمة نماذج الذكاء الاصطناعي المتعددة (إنشاء النص، تصنيف الصور، التضمينات) عبر REST API
- مصادقة مفتاح API مع حصص الاستخدام لكل مفتاح
- تتبع الاستخدام وإعداد الفواتير لكل مكالمة API
- دعم إصدارات نماذج متعددة مع اختبار A/B
- تدفق الاستجابات لمهام الجيل طويلة الأمد

** المتطلبات غير الوظيفية: **
- زمن الوصول: p50 أقل من 500 مللي ثانية لنماذج التضمين، وp50 أقل من 2s للنماذج التوليدية
- الإنتاجية: 10.000 طلب في الثانية لجميع النماذج
- التوفر: وقت تشغيل بنسبة 99.9% مع تدهور رائع
- كفاءة التكلفة: وحدات معالجة الرسوميات باهظة الثمن - مما يؤدي إلى تحقيق أقصى استفادة منها

<Callout>تتمتع منصات الذكاء الاصطناعي بزمن انتقال متغير بشكل فريد. قد يستغرق طلب إكمال النص 200 مللي ثانية أو 30 ثانية حسب طول الإخراج. ناقش دائمًا كيفية تعامل تصميمك مع هذا التباين.
</Callout>

## الخطوة الثانية: تصميم واجهة برمجة التطبيقات

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-4", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - list available models
GET  /v1/usage?start=2024-01-01    - usage and billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

يعد البث عبر **الأحداث المرسلة من الخادم (SSE)** أمرًا بالغ الأهمية للنماذج التوليدية - حيث يرى المستخدمون ظهور الرموز المميزة تدريجيًا بدلاً من انتظار الاستجابة الكاملة.

## الخطوة 3: بوابة API والمصادقة

بوابة API هي الباب الأمامي للمنصة:

- **المصادقة** - التحقق من صحة مفاتيح API مقابل مخزن المفاتيح (Redis للسرعة، وقاعدة البيانات للاستمرارية)
- **تحديد السعر** - فرض حدود لكل مفتاح (على سبيل المثال، 60 طلبًا/دقيقة للطبقة المجانية)
- **توجيه الطلب** - توجيه الطلبات إلى مجموعة خدمة النماذج الصحيحة
- **التحقق من صحة الطلب** - التحقق من مخطط الحمولة، وتوافر النموذج، وحدود الرمز المميز

**تنفيذ الحد من المعدل:**
استخدم **عداد النوافذ المنزلقة** في Redis:
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

كل طلب يزيد العداد. إذا تجاوز الحد، قم بإرجاع HTTP 429.

## الخطوة 4: عرض النماذج وتخصيص وحدة معالجة الرسومات

هذا هو المكان الذي تختلف فيه منصات الذكاء الاصطناعي بشكل أساسي عن خدمات الويب التقليدية. وحدات معالجة الرسومات نادرة ومكلفة وتتطلب تنسيقًا متخصصًا.

**طبقة التقديم النموذجية:**
- يتم تحميل النماذج في ذاكرة وحدة معالجة الرسومات باستخدام أطر عمل مثل **Triton Inference Server** أو **vLLM**
- يعمل كل إصدار نموذجي على مجموعة مخصصة من مثيلات وحدة معالجة الرسومات
- قد تتطلب نماذج اللغات الكبيرة (LLMs) **توازي النماذج** عبر وحدات معالجة الرسومات المتعددة

**طلب التجميع:**
طلبات الاستدلال الفردية غير فعالة على وحدات معالجة الرسومات. **التجميع الديناميكي** يجمع طلبات متعددة ويعالجها معًا:
- جمع الطلبات لمدة تصل إلى 10 مللي ثانية أو حتى تصل الدفعة إلى 32 طلبًا
- قم بمعالجة الدفعة بأكملها في تمريرة أمامية واحدة لوحدة معالجة الرسومات
- إرجاع الردود الفردية لكل متصل

يمكن أن يؤدي ذلك إلى تحسين الإنتاجية بمقدار 5-10x مقارنة بمعالجة الطلبات بشكل فردي.

<FunFact>تبلغ تكلفة وحدة معالجة الرسومات NVIDIA H100 الواحدة حوالي 25000 جنيه إسترليني وتستهلك 700 واط من الطاقة. إن تشغيل مجموعة مكونة من 1000 وحدة معالجة رسومات لخدمة النماذج يكلف أكثر من 2 مليون جنيه إسترليني شهريًا من الكهرباء والأجهزة وحدها - وهذا هو سبب أهمية التجميع والاستخدام الفعال بشكل كبير.
</FunFact>

## الخطوة 5: اختبار أ/ب بين إصدارات النماذج

عند نشر إصدار نموذج جديد، تحتاج إلى التحكم في الطرح:

- **تقسيم حركة المرور** - توجيه 5% من الطلبات إلى النموذج الجديد، و95% إلى النموذج الحالي
- **وضع الظل** - قم بتشغيل النموذج الجديد على حركة الإنتاج دون إعادة نتائجه إلى المستخدمين
- **مقارنة المقاييس** - زمن الوصول، ونقاط جودة المخرجات، ومعدلات الخطأ، والتكلفة لكل طلب
- **الطرح التدريجي** - قم بزيادة عدد الزيارات إلى الإصدار الجديد مع تزايد الثقة

يوجد منطق التوجيه في بوابة API:
```
model: "gpt-4"  →  95% → gpt-4-v2.1 (current)
                →   5% → gpt-4-v2.2 (candidate)
```

<ThinkAboutIt>يعد تقييم ما إذا كان إصدار LLM الجديد "أفضل" أمرًا صعبًا بشكل مدهش - على عكس نماذج التصنيف، لا يوجد مقياس دقة بسيط. كيف يمكنك تصميم نظام آلي لتقييم الجودة لنماذج الذكاء الاصطناعي التوليدية؟
</ThinkAboutIt>

## الخطوة 6: تتبع الاستخدام وإعداد الفواتير

عادةً ما يتم تحصيل رسوم واجهات برمجة تطبيقات الذكاء الاصطناعي لكل رمز مميز (رموز الإدخال + الإخراج المميزة لـ LLMs، لكل طلب للنماذج الأخرى).

** مسار الفوترة المستند إلى الأحداث: **
1. تتضمن كل استجابة لواجهة برمجة التطبيقات (API) رأس استخدام: `x-usage-tokens: 847`
2. تم نشر حدث الفوترة إلى كافكا: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. تستهلك خدمة تجميع الفواتير الأحداث والتحديثات التي تقوم بتشغيل الإجماليات
4. تقوم لوحات معلومات الاستخدام بالاستعلام عن البيانات المجمعة من قاعدة بيانات السلاسل الزمنية

**لماذا كافكا؟** يجب أن تكون الفواتير موثوقة ولكن ليس من الضروري أن تكون متزامنة. إذا كانت خدمة الفوترة معطلة مؤقتًا، فسيتم وضع الأحداث في قائمة الانتظار في كافكا وتتم معالجتها عند استعادتها - ولا يتم فقدان أي بيانات استخدام.

## الخطوة 7: الرصد والملاحظة

تتطلب منصات الذكاء الاصطناعي مراقبة تتجاوز خدمات الويب القياسية:

| متري | لماذا يهم |
|--------|----------------|
| زمن الاستدلال (ص50، ص95، ص99) | تجربة المستخدم والامتثال لاتفاقية مستوى الخدمة |
| استخدام GPU | كفاءة التكلفة - وحدات معالجة الرسومات الخاملة تهدر الأموال |
| الرموز في الثانية | سعة الإنتاجية وإشارات القياس |
| معدل الخطأ حسب النموذج | كشف حالات الفشل الخاصة بالنموذج |
| عمق قائمة الانتظار | مشغل القياس - قوائم الانتظار العميقة تعني أن الطلب يتجاوز السعة |
| درجات جودة الإخراج | كشف تدهور النموذج (عبر التقييم الآلي) |

**حدود التنبيه:** يؤدي استخدام وحدة معالجة الرسومات (GPU) الأقل من 40% إلى خفض الحجم؛ يؤدي عمق قائمة الانتظار الذي يزيد عن 100 إلى زيادة الحجم.

## الخطوة 8: القياس التلقائي

إن أعباء عمل الذكاء الاصطناعي لها طلب متغير للغاية. يجب أن يوازن القياس التلقائي بين الاستجابة والتكلفة:

- **القياس الأفقي** - أضف المزيد من مثيلات وحدة معالجة الرسومات عندما يتجاوز عمق قائمة الانتظار أو زمن الاستجابة الحدود القصوى
- **القياس التنبؤي** - استخدم أنماط حركة المرور التاريخية لتوفير السعة مسبقًا قبل الذروة المتوقعة
- **التوسيع إلى الصفر** - بالنسبة للنماذج التي نادرًا ما تستخدم، قم بتدوير جميع المثيلات والبدء البارد عند الطلب
- **التجمعات الدافئة** - احتفظ بعدد صغير من المثيلات مع النماذج المحملة مسبقًا لتجنب زمن الوصول لبدء التشغيل على البارد

تعتبر استراتيجية التوسع إلى الصفر مهمة بشكل خاص للمنصات التي تستضيف مئات النماذج - لا يمكنك الاحتفاظ بكل نموذج محملاً في ذاكرة وحدة معالجة الرسومات في جميع الأوقات.

## الوجبات السريعة الرئيسية

- تجمع منصات AI API بين تصميم API التقليدي وتحديات البنية التحتية الخاصة بوحدة معالجة الرسومات
- يؤدي تجميع الطلبات إلى تحسين إنتاجية وحدة معالجة الرسومات بشكل كبير وكفاءة التكلفة
- يعمل تحديد السعر على حماية كل من المنصة والعملاء من التكاليف الجامحة
- الفوترة غير المتزامنة عبر كافكا تضمن تتبع الاستخدام بشكل موثوق دون حظر الطلبات
- يجب أن يوازن القياس التلقائي بين الاستجابة والتكلفة - التوسع إلى الصفر بالنسبة للنماذج ذات حركة المرور المنخفضة
- تؤدي مراقبة استخدام وحدة معالجة الرسومات وعمق قائمة الانتظار إلى اتخاذ قرارات ذكية للقياس
