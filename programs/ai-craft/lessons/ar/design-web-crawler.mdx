# تصميم زاحف الويب - كيف يقوم Google بفهرسة الإنترنت

يقوم زاحف الويب بتصفح الإنترنت بشكل منهجي لتنزيل صفحات الويب وفهرستها. إنه أساس كل محرك بحث، وتصميم واحد يعلمك عن الأنظمة الموزعة، واجتياز الرسم البياني، والتعامل مع الفوضى في الويب الحقيقي.

## الخطوة 1 - جمع المتطلبات

### المتطلبات الوظيفية
- الزحف إلى صفحات الويب بدءًا من مجموعة من عناوين URL الأولية
- استخراج ومتابعة الارتباطات التشعبية لاكتشاف صفحات جديدة
- تخزين المحتوى الذي تم تنزيله للفهرسة والمعالجة
- احترام ملف robots.txt وقواعد الزحف

### المتطلبات غير الوظيفية
- **المقياس** - الزحف إلى مليار صفحة شهريًا
- **الأدب** - لا تطغى أبدًا على خادم ويب واحد
- **الحداثة** - إعادة الزحف إلى الصفحات المهمة بانتظام
- **المتانة** - التعامل مع HTML المشوه والحلقات اللانهائية والفخاخ العنكبوتية

## الخطوة الثانية – هندسة رفيعة المستوى

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## الخطوة 3 – حلقة الزحف

### زحف BFS مقابل DFS
- **BFS (العرض أولاً)** - مفضل للزحف على الويب. يكتشف مجموعة واسعة من النطاقات بسرعة ويتجنب الوقوع في فخ موقع واحد
- **DFS (العمق أولاً)** - يخاطر بالتعمق بشكل لا نهائي في الصفحات التي يتم إنشاؤها ديناميكيًا قبل اكتشاف المجالات الأخرى

### تصميم حدود URL
الحدود ليست قائمة انتظار بسيطة - إنها نظام أولوية متطور يتكون من مكونين فرعيين:

1. **قائمة الانتظار ذات الأولوية (الأمامية)** - تُصنف عناوين URL حسب الأهمية. تتضمن العوامل نظام ترتيب الصفحات وتكرار التحديث وسلطة المجال
2. **قائمة انتظار المداراة (العودة)** - تضمن أن يكون لكل مجال قائمة انتظار FIFO الخاصة به. يختار المجدول من قوائم انتظار المجال المختلفة لتجنب ضرب أي خادم واحد

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## الخطوة 4 - المداراة وRobots.txt

### احترام ملف Robots.txt
قبل الزحف إلى أي نطاق، قم بإحضار الملف `robots.txt` الخاص به وتخزينه مؤقتًا:

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

قم بتخزين ملف robots.txt مؤقتًا لكل مجال باستخدام TTL (24 ساعة). احترم دائمًا قواعد `Disallow` وتوجيهات `Crawl-delay`.

### تحديد معدل الزحف
حتى بدون `Crawl-delay` صريح، حافظ على الأدب:
- الحد الأقصى لطلب واحد في الثانية لكل مجال (قابل للتكوين)
- استخدم قوائم انتظار تنزيل منفصلة لكل مجال
- تتبع أوقات الاستجابة - إذا تباطأ الخادم، قم بالتراجع تلقائيًا

<FunFact>يقوم زاحف الويب من Google (Googlebot) بالزحف إلى مئات المليارات من الصفحات. لكي نكون مهذبين، فإنه يراقب أوقات استجابة الخادم ويقلل معدل الزحف الخاص به إذا بدأ الموقع في الاستجابة ببطء - مما يسمح لموقع الويب "بالرد" على الزاحف بشكل فعال.</FunFact>

## الخطوة 5 – إلغاء البيانات المكررة

### إلغاء تكرار عنوان URL (فلتر بلوم)
مع وجود مليارات من عناوين URL، يتطلب التحقق مما إذا كان عنوان URL قد تمت رؤيته من قبل بنية بيانات فعالة. يوفر مرشح Bloom عمليات بحث O(1) مع مساحة صغيرة من الذاكرة:

- **المساحة:** ~1 غيغابايت لمليار عنوان URL بمعدل إيجابي كاذب بنسبة 1%
- **المقايضة:** قد تقوم أحيانًا بإعادة الزحف إلى الصفحة (إيجابية كاذبة) ولكن لا تفوت عنوان URL جديدًا أبدًا (لا توجد نتائج سلبية كاذبة)

قم بتطبيع عناوين URL قبل التحقق: إزالة الأجزاء (#)، وفرز معلمات الاستعلام، وكتابة اسم المضيف بأحرف صغيرة، وحل المسارات النسبية.

### إلغاء البيانات المكررة للمحتوى (SimHash)
يمكن أن تقدم عناوين URL المختلفة محتوى متطابقًا (المرايا والمقالات المنسوخة). يقوم SimHash بإنشاء بصمة لمحتوى الصفحة - من المحتمل أن تكون الصفحات ذات بصمات الأصابع المشابهة (مسافة Hamming الصغيرة) نسخًا مكررة:

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## الخطوة 6 - الزحف الموزع

### التحجيم أفقيا
لا يمكن لجهاز واحد أن يزحف إلى مليار صفحة شهريًا. توزيع العمل:

- **التجزئة المتسقة** في أسماء النطاقات تقوم بتعيين كل نطاق إلى عقدة زاحف محددة. وهذا يضمن الأدب - عقدة واحدة فقط تزحف إلى مجال معين
- **حدود URL** مقسمة عبر العقد بناءً على حلقة التجزئة
- **التنسيق** عبر خدمة خفيفة الوزن تدير تعيينات العقد وإعادة التوازن عند انضمام العقد أو مغادرتها

### التخزين المؤقت لقرار DNS
تضيف عمليات بحث DNS 10-100 مللي ثانية لكل طلب. على نطاق واسع، هذا هو عنق الزجاجة الرئيسي:
- احتفظ بذاكرة تخزين مؤقت محلية لنظام أسماء النطاقات (DNS) لكل عقدة زاحف
- الدقة المسبقة لنظام DNS لعناوين URL الموضوعة في قائمة الانتظار
- استخدم محلل DNS مخصصًا لتجنب إرباك خوادم DNS العامة

### كشف مصيدة العنكبوت
يمكن للمواقع الضارة أو سيئة الإنشاء إنشاء مساحات غير محدودة من عناوين URL:
- `/page/1/page/1/page/1/...` - تكرار أنماط المسار
- صفحات التقويم تنشئ عناوين URL لكل تاريخ مستقبلي
- معرفات الجلسة في عناوين URL التي تنشئ عناوين URL فريدة لمحتوى متطابق

**الدفاعات:** الحد الأقصى لطول عنوان URL، والحد الأقصى لعمق الزحف لكل نطاق، واكتشاف الأنماط لهياكل عناوين URL المتكررة، وحدود عدد الصفحات على مستوى النطاق.

<ThinkAboutIt>إذا كنت بحاجة إلى تحديث فهرس البحث، فكيف يمكنك تحديد الصفحات التي تريد إعادة الزحف إليها أولاً؟ فكر في موقع إخباري يتم تحديثه كل ساعة مقابل مقالة ويكيبيديا يتم تغييرها شهريًا. ما الإشارات التي ستستخدمها لتحديد أولويات جدولة إعادة الزحف؟ </ThinkAboutIt>

## الخطوة 7 – الاختناقات والتحسينات

| عنق الزجاجة | الحل |
|-----------|----------|
| زمن الوصول لقرار DNS | ذاكرة التخزين المؤقت DNS المحلية، دفعة ما قبل القرار |
| خوادم بطيئة/غير مستجيبة | المهلات (30 ثانية)، الإدخال/الإخراج غير المتزامن، التخطي بعد إعادة المحاولة |
| تخزين المحتوى الذي تم الزحف إليه | ضغط الصفحات وتخزين المحتوى الذي تم تغييره فقط |
| ذاكرة URL الحدودية | قائمة انتظار الأولوية المدعومة بالقرص (RocksDB) |
| محتوى مكرر | بصمة SimHash، الكشف عن عنوان URL الأساسي |

<ThinkAboutIt>يجب أن توازن محركات البحث بين حداثة الزحف (إعادة الزحف إلى الصفحات بشكل متكرر) والاكتشاف (العثور على صفحات جديدة). إذا كان الزاحف الخاص بك لديه ميزانية ثابتة تبلغ مليون صفحة يوميًا، فكيف يمكنك تقسيم هذه الميزانية بين إعادة الزحف إلى الصفحات الحالية واكتشاف صفحات جديدة؟</ThinkAboutIt>
