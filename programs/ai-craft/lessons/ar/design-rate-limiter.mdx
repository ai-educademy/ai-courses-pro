# تصميم محدد للمعدل - حماية واجهات برمجة التطبيقات على نطاق واسع

يعد تحديد المعدل أحد أكثر موضوعات تصميم النظام عملية. تعتمد كل واجهة برمجة تطبيقات إنتاجية - من GitHub إلى Stripe - عليها لمنع إساءة الاستخدام، وضمان الاستخدام العادل، وحماية الخدمات الخلفية من الإرهاق.

## الخطوة 1 - جمع المتطلبات

### المتطلبات الوظيفية
- تحديد الطلبات بناءً على قواعد قابلة للتكوين (لكل مستخدم أو IP أو مفتاح API)
- إرجاع تعليقات واضحة عند اختناق العميل (HTTP 429)
- دعم قواعد تحديد معدل متعددة في وقت واحد

### المتطلبات غير الوظيفية
- **زمن الوصول المنخفض** - يجب ألا يضيف المحدد أعباء إضافية كبيرة
- **الموزعة** - تعمل عبر خوادم متعددة
- **التسامح مع الأخطاء** - في حالة فشل المحدد، يجب أن تستمر حركة المرور في التدفق (فتح الفشل)

<ThinkAboutIt>هل يجب أن يكون محدد المعدل مفتوحًا (السماح بحركة المرور) أو مغلقًا بشكل فاشل (حظر حركة المرور) عند تعطله؟ ما هي المفاضلات بين موقع التجارة الإلكترونية وواجهة برمجة التطبيقات المصرفية؟ </ThinkAboutIt>

## الخطوة الثانية - خوارزميات تحديد المعدل

### عداد النوافذ الثابتة
تقسيم الوقت إلى نوافذ ثابتة (على سبيل المثال، فترات زمنية مدتها 60 ثانية). زيادة عداد لكل طلب. إعادة تعيين على حدود النافذة. **المشكلة:** يمكن أن تسمح حركة المرور المتلاحقة عند حواف النوافذ بمضاعفة الحد الأقصى.

### سجل النافذة المنزلقة
قم بتخزين الطابع الزمني لكل طلب. عد الإدخالات داخل النافذة الزائدة. دقيق ولكن **يستهلك الكثير من الذاكرة** - يعد تخزين كل طابع زمني أمرًا مكلفًا على نطاق واسع.

### عداد النافذة المنزلقة
مختلط: يجمع عدد النوافذ الحالية مع جزء مرجح من النافذة السابقة. يوازن بين الدقة وكفاءة الذاكرة.

### خوارزمية دلو الرمز المميز (الأكثر شيوعًا)
يحمل الدلو الرموز المميزة بأقصى سعة. تتم إضافة الرموز بمعدل ثابت. يستهلك كل طلب رمزًا واحدًا. إذا كانت الحاوية فارغة، فسيتم رفض الطلب.

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### مقارنة الخوارزميات

| الخوارزمية | الذاكرة | دقة | التعامل مع الانفجار |
|-----------|-------|----------|----------------|
| نافذة ثابتة | منخفض | منخفض (انفجارات الحافة) | فقير |
| سجل منزلق | عالية | بالضبط | جيد |
| عداد منزلق | متوسطة | تقريبي | جيد |
| دلو الرمز المميز | منخفض | جيد | ممتاز |

## الخطوة 3 - هندسة رفيعة المستوى

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-rate-limiter.svg" alt="تُظهر بنية محدد المعدل العملاء، وبوابة واجهة برمجة التطبيقات (API) مع البرامج الوسيطة التي تحدد المعدل، ومجموعة Redis للحالة الموزعة، وخدمات الواجهة الخلفية" caption="يوجد محدد المعدل في بوابة API، باستخدام Redis لتخزين العداد الموزع" />

### مكان وضع محدد السعر
- **جانب العميل** - سهل الانتحال، وغير موثوق
- **من جانب الخادم** - لكل مثيل فقط، ولا يتم قياسه
- **بوابة واجهة برمجة التطبيقات / البرامج الوسيطة** - أفضل نهج للأنظمة الموزعة؛ مركزية التنفيذ في جميع الحالات

## الخطوة 4 - الغوص العميق: تحديد المعدل الموزع

### نصوص Redis + Lua
في الإعداد الموزع، يجب أن تشترك الخوادم المتعددة في حالة تحديد المعدل. يعد Redis هو الاختيار القياسي بسبب عملياته الذرية وزمن الوصول الذي يقل عن المللي ثانية.

يضمن نص Lua الذرية - يحدث الفحص والتخفيض في عملية Redis واحدة، مما يمنع حالات السباق:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### رؤوس الاستجابة
تعمل محددات الأسعار المصممة جيدًا على توصيل الحالة إلى العملاء:
- `X-RateLimit-Limit: 100` - الحد الأقصى للطلبات لكل نافذة
- `X-RateLimit-Remaining: 42` - الطلبات المتبقية
- `X-RateLimit-Reset: 1672531200` - عصر UTC عند إعادة ضبط النافذة
- HTTP `429 Too Many Requests` برأس `Retry-After`

## الخطوة 5 - التعامل مع حالات الحافة

### ظروف السباق
بدون العمليات الذرية، يمكن للطلبات المتزامنة تجاوز الحدود. الحلول: نصوص Redis Lua أو معاملات Redis `MULTI/EXEC`.

### أبعاد تحديد المعدل
تطبيق الحدود على مستويات متعددة في وقت واحد:
- **لكل مستخدم** - 100 طلب/دقيقة للمستخدمين المعتمدين
- **لكل IP** - 50 طلبًا/الدقيقة لحركة المرور المجهولة
- **لكل مفتاح API** - خطط متدرجة (مجانية: 10/دقيقة، احترافية: 1000/دقيقة)

### انحراف الساعة الموزع
قد يكون للخوادم ساعات مختلفة قليلاً. استخدم وقت خادم Redis كمصدر وحيد للحقيقة بدلاً من الاعتماد على الطوابع الزمنية لخادم التطبيق.

<FunFact>تسمح واجهة برمجة تطبيقات REST الخاصة بـ GitHub بـ 5000 طلب في الساعة للمستخدمين المصادق عليهم ولكن 60 طلبًا فقط في الساعة للطلبات غير المصادق عليها. يستخدم Stripe أسلوب النافذة المنزلقة مع حدود منفصلة لمفاتيح API للوضع المباشر والاختبار.</FunFact>

## الخطوة 6 - الاختناقات والتحسينات

| عنق الزجاجة | الحل |
|-----------|----------|
| Redis نقطة فشل واحدة | مجموعة Redis مع النسخ المتماثل |
| زمن وصول الشبكة إلى Redis | ذاكرة تخزين مؤقت محلية في الذاكرة مع مزامنة دورية |
| مفاتيح التشغيل السريع (مفاتيح API الشائعة) | شظية عبر عقد Redis متعددة |
| قاعدة تقييم النفقات العامة | قواعد الترجمة المسبقة وتكوينات ذاكرة التخزين المؤقت |
