# تصميم نظام إعلام - الدفع والبريد الإلكتروني والرسائل النصية القصيرة بمقياس ملياري

ترسل التطبيقات الحديثة مليارات الإشعارات يوميًا عبر قنوات متعددة. يعلمك تصميم هذا النظام معلومات عن قوائم انتظار الرسائل وعمليات تكامل الجهات الخارجية ومعالجة حالات الفشل بأمان على نطاق واسع.

## الخطوة 1 - جمع المتطلبات

### المتطلبات الوظيفية
- دعم قنوات متعددة: دفع الإخطارات، والبريد الإلكتروني، والرسائل القصيرة، وداخل التطبيق
- يمكن للمستخدمين تكوين تفضيلات الإشعارات وإلغاء الاشتراك في كل قناة
- رسائل نموذجية مع التخصيص (على سبيل المثال، "مرحبًا {name}، تم شحن طلبك")
- تقديم الدعم للإخطارات المجدولة والفورية

### المتطلبات غير الوظيفية
- **قابلية التوسع** - التعامل مع أكثر من 10 مليون إشعار يوميًا
- **الموثوقية** - لا توجد إخطارات مفقودة؛ التسليم مرة واحدة على الأقل
- **زمن الوصول المنخفض** - يتم تسليم الإشعارات العاجلة في غضون ثوانٍ
- **قابل للتوسيع** - من السهل إضافة قنوات جديدة (WhatsApp، Slack)

<ThinkAboutIt>هل يجب أن يتم تسليم الإشعار مرة واحدة بالضبط أم مرة واحدة على الأقل؟ ضع في اعتبارك تجربة المستخدم في تلقي رسالة نصية قصيرة مكررة مقابل فقدان تنبيه أمني مهم.</ThinkAboutIt>

## الخطوة الثانية – هندسة رفيعة المستوى

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### المكونات الأساسية
1. **خدمة الإشعارات** - للتحقق من صحة الطلبات، والتحقق من تفضيلات المستخدم، وعرض النماذج، ووضع الرسائل في قائمة الانتظار
2. **قوائم انتظار الرسائل** - قوائم انتظار منفصلة لكل قناة من أجل القياس والعزل بشكل مستقل
3. **عمال التسليم** - عمال خاصون بالقناة يتعاملون مع مكالمات واجهة برمجة التطبيقات التابعة لجهات خارجية
4. **خدمة النماذج** - تقوم بتخزين وعرض قوالب الإشعارات مع استبدال المتغيرات

## الخطوة 3 – الغوص العميق: المكونات الرئيسية

### تفضيلات المستخدم وإلغاء الاشتراك
تفضيلات المتجر لكل مستخدم ولكل نوع إشعار:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

تتحقق خدمة الإشعارات من التفضيلات **قبل** وضع قائمة الانتظار - لا ترسل مطلقًا ما لا يريده المستخدم.

### قوائم الانتظار ذات الأولوية
ليست كل الإخطارات متساوية. استخدم مستويات الأولوية:
- **حرجة** - تنبيهات أمنية، رموز OTP → تتم معالجتها على الفور
- **مرتفع** - تأكيدات الطلب، إيصالات الدفع → ثانية
- **متوسط** - التفاعلات الاجتماعية، التعليقات → دقائق مقبولة
- **منخفض** - التسويق والتوصيات → يمكن تجميعها على دفعات

## الخطوة 4 - الموثوقية والتعامل مع الفشل

### إلغاء البيانات المكررة
منع الإخطارات المكررة باستخدام مفتاح العجز. قبل المعالجة، تحقق من وجود معرف الإشعار في مخزن إلغاء البيانات المكررة (Redis مع TTL):

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### أعد المحاولة مع التراجع الأسي
تفشل خدمات الطرف الثالث. تنفيذ عمليات إعادة المحاولة مع زيادة التأخير:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### تحديد المعدل لكل مستخدم
حماية المستخدمين من إرهاق الإشعارات:
- الحد الأقصى 3 إشعارات في الساعة لكل مستخدم
- بريد إلكتروني تسويقي واحد كحد أقصى يوميًا
- تجاوز الإخطارات الأمنية حدود المعدل

<FunFact>يرسل فيسبوك أكثر من 10 مليار إشعار دفع يوميًا. للتعامل مع هذا الأمر، قاموا ببناء مسار إعلام مخصص يمكنه معالجة ملايين الرسائل في الثانية، مع مسارات تسليم منفصلة لنظامي التشغيل iOS (APNs) وAndroid (FCM).</FunFact>

## الخطوة 5 – تكامل الطرف الثالث

| قناة | مقدم | البروتوكول | التحديات |
|---------|---------|---------|------------|
| ادفع (iOS) | نقاط الوصول | HTTP/2 | إدارة الرمز المميز، حدود الدفع الصامتة |
| دفع (أندرويد) | اف سي ام | HTTP | البث الموضوعي |
| البريد الإلكتروني | سيندغريد/SES | SMTP/API | إمكانية التسليم، مرشحات البريد العشوائي |
| الرسائل القصيرة | تويليو | ريست API | التكلفة لكل رسالة، الامتثال الإقليمي |
| داخل التطبيق | ويب سوكيت | وس | إدارة الاتصال، التخزين المؤقت دون اتصال |

### خط أنابيب التحليلات
تتبع دورة حياة الإشعارات لكل رسالة:
- **تم الإنشاء** → **في قائمة الانتظار** → **تم الإرسال** → **تم التسليم** → **مفتوحة** → **تم النقر عليها**

قم بتخزين الأحداث في قاعدة بيانات سلاسل زمنية أو تدفق أحداث لإعداد تقارير لوحة المعلومات: معدلات التسليم، ومعدلات الفتح، ومعدلات النقر إلى الظهور لكل قناة ونوع إشعار.

## الخطوة 6 - الاختناقات والتحسينات

| عنق الزجاجة | الحل |
|-----------|----------|
| حدود أسعار الطرف الثالث | قائمة انتظار مع إنتاجية يمكن التحكم فيها لكل مزود |
| عرض القالب على نطاق واسع | قوالب مشتركة للعرض المسبق والتخزين المؤقت |
| عمليات البحث التفضيلية لكل رسالة | تخزين تفضيلات المستخدم مؤقتًا في Redis |
| ذروة ارتفاع حركة المرور | مقياس تلقائي للعمال بناءً على عمق قائمة الانتظار |
| التسليم عبر المنطقة | نشر العمال بالقرب من نقاط نهاية الموفر |
