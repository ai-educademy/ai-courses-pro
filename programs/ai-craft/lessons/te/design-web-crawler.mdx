# వెబ్ క్రాలర్ డిజైన్ చేయండి - Google ఇంటర్నెట్‌ను ఎలా ఇండెక్స్ చేస్తుంది

వెబ్ క్రాలర్ క్రమబద్ధంగా ఇంటర్నెట్‌ను బ్రౌజ్ చేసి వెబ్ పేజీలు ను download మరియు ఇండెక్స్ చేస్తుంది. ఇది ప్రతి సెర్చ్ ఇంజిన్ కు పునాది, మరియు దీన్ని డిజైన్ చేయడం వల్ల విస్తరిత సిస్టమ్‌లు, గ్రాఫ్ traversal, మరియు నిజమైన వెబ్ యొక్క complexities ను నిర్వహించు చేయడం నేర్చుకుంటారు.

## దశ 1 - అవసరాలు సేకరణ

### Functional అవసరాలు
- Seed URLs సెట్ నుండి వెబ్ పేజీలు క్రాల్ చేయడం
- Hyperlinks extract చేసి కొత్త పేజీలు గుర్తించండి చేయడం
- Download చేసిన కంటెంట్ ను ఇండెక్సింగ్ మరియు ప్రాసెసింగ్ కోసం నిల్వ చేయడం
- robots.txt మరియు క్రాల్ politeness rules పాటించడం

### Non-Functional అవసరాలు
- **స్కేల్** - నెలకు 1 బిలియన్ పేజీలు క్రాల్ చేయడం
- **Politeness** - ఏ ఒక్క వెబ్ సర్వర్ ను overload చేయకపోవడం
- **Freshness** - ముఖ్యమైన పేజీలు ను క్రమం తప్పకుండా re-క్రాల్ చేయడం
- **Robustness** - malformed HTML, infinite loops, మరియు spider traps ను నిర్వహించు చేయడం

## దశ 2 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## దశ 3 - క్రాల్ లూప్

### BFS వర్సెస్ DFS Crawling
- **BFS (Breadth-First)** - వెబ్ crawling కోసం ఇష్టపడతారు. త్వరగా అనేక domains గుర్తించండి చేస్తుంది మరియు ఒకే సైట్ లో లోతుగా చిక్కుకోకుండా నిరోధిస్తుంది
- **DFS (లోతు-First)** - ఇతర domains గుర్తించండి చేయకముందే dynamically సృష్టించిన పేజీలు లో infinitely లోతైన గా వెళ్ళే రిస్క్ ఉంది

### URL అగ్రశ్రేణి డిజైన్
అగ్రశ్రేణి ఒక సులభమైన క్యూ కాదు - ఇది రెండు ఉప-భాగాలు తో ఉన్న sophisticated ప్రాధాన్యం సిస్టమ్:

1. **ప్రాధాన్యం క్యూ (Front)** - URLs ను importance ఆధారంగా ర్యాంక్ చేస్తుంది. PageRank, నవీకరించు frequency, మరియు డొమైన్ authority వంటి factors ఉంటాయి
2. **Politeness క్యూ (Back)** - ప్రతి డొమైన్ కు దాని స్వంత FIFO క్యూ ఉంటుంది. ఒక scheduler వివిధ డొమైన్ క్యూలు నుండి pick చేస్తుంది, తద్వారా ఏ ఒక్క సర్వర్ పై అధిక లోడ్ పడదు

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## దశ 4 - Politeness మరియు Robots.txt

### Robots.txt పాటించడం
ఏదైనా డొమైన్ ను క్రాల్ చేయడానికి ముందు, దాని `robots.txt` ఫైల్ ను fetch మరియు క్యాష్ చేయండి:

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

ప్రతి డొమైన్ యొక్క robots.txt ను TTL (24 గంటలు) తో క్యాష్ చేయండి. `Disallow` rules మరియు `Crawl-delay` directives ను ఎల్లప్పుడూ పాటించండి.

### క్రాల్ రేట్ పరిమితం చేసే
స్పష్టమైన `Crawl-delay` లేకపోయినా politeness కొనసాగించండి:
- ప్రతి డొమైన్ కు సెకండ్ కు గరిష్ట 1 రిక్వెస్ట్ (మార్చుకోగల)
- ప్రతి డొమైన్ కు separate download క్యూలు ఉపయోగించండి
- రెస్పాన్స్ సార్లు ట్రాక్ చేయండి - సర్వర్ నెమ్మది అయితే, automatically back ఆఫ్ అవ్వండి

<FunFact>Google యొక్క వెబ్ క్రాలర్ (Googlebot) వందల billions పేజీలు క్రాల్ చేస్తుంది. Polite గా ఉండటానికి, ఇది సర్వర్ రెస్పాన్స్ సార్లు monitor చేస్తుంది మరియు ఒక సైట్ నెమ్మది గా respond చేయడం మొదలుపెడితే క్రాల్ రేట్ తగ్గిస్తుంది - effectively వెబ్‌సైట్ ను క్రాలర్ కు వ్యతిరేకంగా "పుష్ back" చేయనిస్తుంది.</FunFact>

## దశ 5 - డీడూప్లికేషన్

### URL డీడూప్లికేషన్ (బ్లూమ్ ఫిల్టర్)
Billions URLs తో, ఒక URL ను ఇంతకు ముందు చూశామా అని తనిఖీ చేయడానికి efficient డేటా నిర్మాణం అవసరం. బ్లూమ్ ఫిల్టర్ O(1) లుక్‌అప్‌లు ను చిన్న మెమరీ footprint తో అందిస్తుంది:

- **Space:** 1 బిలియన్ URLs కు ~1 GB, 1% తప్పుడు పాజిటివ్ రేట్ తో
- **Trade-ఆఫ్:** అప్పుడప్పుడు పేజీ re-క్రాల్ అవ్వవచ్చు (తప్పుడు పాజిటివ్) కానీ కొత్త URL ఎప్పటికీ మిస్ అవడం కాదు (no తప్పుడు negatives)

తనిఖీ చేయడానికి ముందు URLs normalize చేయండి: fragments (#) తొలగించండి, క్వెరీ పరామీటర్లు క్రమబద్ధీకరించండి చేయండి, hostname lowercase చేయండి, మరియు relative మార్గాలు resolve చేయండి.

### కంటెంట్ డీడూప్లికేషన్ (SimHash)
వేర్వేరు URLs identical కంటెంట్ సర్వ్ చేయండి చేయవచ్చు (mirrors, copied articles). SimHash పేజీ కంటెంట్ యొక్క fingerprint సృష్టించు చేస్తుంది - సారూప్య fingerprints (చిన్న Hamming distance) ఉన్న పేజీలు likely duplicates:

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## దశ 6 - విస్తరిత Crawling

### Horizontally స్కేల్ చేయడం
ఒక్క machine నెలకు బిలియన్ పేజీలు క్రాల్ చేయలేదు. పనిని విస్తరించండి చేయండి:

- డొమైన్ names పై **స్థిరమైన హ్యాషింగ్** ప్రతి డొమైన్ ను స్పష్టంగా క్రాలర్ నోడ్ కు assign చేస్తుంది. ఇది politeness నిర్ధారించండి చేస్తుంది - ఒక given డొమైన్ ను ఒకే నోడ్ క్రాల్ చేస్తుంది
- **URL అగ్రశ్రేణి** హ్యాష్ ring ఆధారంగా నోడ్‌లు మధ్య పార్టిషన్ అవుతుంది
- నోడ్ assignments manage చేసి, నోడ్‌లు join లేదా leave అయినప్పుడు rebalance చేసే తేలికపాటి సేవ ద్వారా **coordination**

### DNS Resolution క్యాషింగ్
DNS లుక్‌అప్‌లు ప్రతి రిక్వెస్ట్ కు 10-100ms జోడించు చేస్తాయి. స్కేల్ వద్ద ఇది ప్రధాన bottleneck:
- ప్రతి క్రాలర్ నోడ్ కు స్థానిక DNS క్యాష్ ఉంచండి
- క్యూ లో ఉన్న URLs కోసం బ్యాచ్ DNS ముందస్తు-resolution చేయండి
- పబ్లిక్ DNS సర్వర్‌లు overload కాకుండా dedicated DNS resolver ఉపయోగించండి

### Spider Trap గుర్తింపు
హానికరమైన లేదా poorly built sites infinite URL spaces సృష్టించండి చేయవచ్చు:
- `/page/1/page/1/page/1/...` - repeating మార్గం నమూనాలు
- ప్రతి భవిష్యత్ date కు URLs సృష్టించు చేసే calendar పేజీలు
- Identical కంటెంట్ కు ప్రత్యేక URLs సృష్టించండి చేసే URLs లో Session IDs

**రక్షణలు:** గరిష్ట URL length, ప్రతి డొమైన్ కు గరిష్ట క్రాల్ లోతు, repetitive URL structures కోసం నమూనా గుర్తింపు, మరియు డొమైన్-స్థాయి పేజీ లెక్క పరిమితులు.

<ThinkAboutIt>సెర్చ్ ఇండెక్స్ ను fresh గా ఉంచాలంటే, ఏ పేజీలు ను ముందుగా re-క్రాల్ చేయాలో ఎలా decide చేస్తారు? ప్రతి గంటకు నవీకరించు అయ్యే news సైట్ వర్సెస్ నెలకోసారి మారే Wikipedia వ్యాసం గురించి ఆలోచించండి. Re-క్రాల్ scheduling prioritise చేయడానికి ఏ సంకేతాలు ఉపయోగిస్తారు?</ThinkAboutIt>

|-----------|----------|
| DNS resolution లేటెన్సీ | స్థానిక DNS క్యాష్, బ్యాచ్ ముందస్తు-resolution |
| నెమ్మది/unresponsive సర్వర్‌లు | Timeouts (30s), async I/O, మళ్లీ ప్రయత్నాలు తర్వాత skip |
| Crawled కంటెంట్ నిల్వ | పేజీలు compress చేయడం, changed కంటెంట్ మాత్రమే నిల్వ చేయడం |
| URL అగ్రశ్రేణి మెమరీ | Disk-backed ప్రాధాన్యం క్యూ (RocksDB) |
| Duplicate కంటెంట్ | SimHash fingerprinting, canonical URL గుర్తింపు |

<ThinkAboutIt>సెర్చ్ ఇంజిన్‌లు క్రాల్ freshness (పేజీలు ను తరచుగా re-క్రాల్ చేయడం) మరియు ఆవిష్కరణ (కొత్త పేజీలు కనుగొనడం) మధ్య బ్యాలెన్స్ చేయాలి. మీ క్రాలర్ కు రోజుకు 1 మిలియన్ పేజీలు అనే స్థిర బడ్జెట్ ఉంటే, ఆ బడ్జెట్ ను ఉన్న పేజీలు re-క్రాల్ చేయడం మరియు కొత్త పేజీలు గుర్తించండి చేయడం మధ్య ఎలా విభజిస్తారు?</ThinkAboutIt>
