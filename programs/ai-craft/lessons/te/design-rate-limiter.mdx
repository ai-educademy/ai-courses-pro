# రేట్ లిమిటర్ డిజైన్ చేయండి - APIs ను స్కేల్ లో ప్రొటెక్ట్ చేయడం

రేట్ పరిమితం చేసే అనేది అత్యంత ప్రాయోగిక సిస్టమ్ డిజైన్ విషయాలు లో ఒకటి. ప్రతి ప్రొడక్షన్ API - GitHub నుండి Stripe వరకు - abuse నివారించడానికి, fair వినియోగం నిర్ధారించడానికి మరియు backend సేవలు overload కాకుండా రక్షించడానికి దీనిపై ఆధారపడుతుంది.

## దశ 1 - అవసరాలు సేకరణ

### Functional అవసరాలు
- మార్చుకోగల rules ఆధారంగా రిక్వెస్ట్‌లు పరిమితి చేయండి (ప్రతి వినియోగదారు, IP లేదా API కీ)
- Client throttle అయినప్పుడు స్పష్టమైన ఫీడ్‌బ్యాక్ ఇవ్వండి (HTTP 429)
- ఏకకాలంలో అనేక రేట్ పరిమితం చేసే rules మద్దతు చేయండి

### Non-Functional అవసరాలు
- **Low లేటెన్సీ** - లిమిటర్ significant overhead జోడించు చేయకూడదు
- **విస్తరిత** - అనేక సర్వర్‌లు లో పనిచేయాలి
- **లోపం-tolerant** - లిమిటర్ విఫలమవుతుంది అయితే, ట్రాఫిక్ ప్రవాహం అవుతూనే ఉండాలి (విఫలమవుతుంది-open)

<ThinkAboutIt>రేట్ లిమిటర్ crash అయినప్పుడు విఫలమవుతుంది-open (ట్రాఫిక్ అనుమతించండి చేయడం) అవ్వాలా లేదా విఫలమవుతుంది-closed (ట్రాఫిక్ బ్లాక్ చేయడం) అవ్వాలా? E-commerce సైట్ వర్సెస్ banking API కి ట్రేడ్‌ఆఫ్‌లు ఏమిటి?</ThinkAboutIt>

## దశ 2 - రేట్ పరిమితం చేసే అల్గారిథమ్‌లు

### స్థిర విండో కౌంటర్
సమయం ను స్థిర windows గా divide చేయండి (ఉదా., 60-సెకండ్ ఇంటర్వల్‌లు). ప్రతి రిక్వెస్ట్ కి కౌంటర్ increment చేయండి. విండో boundaries వద్ద reset చేయండి. **సమస్య:** విండో ఎడ్జ్‌లు వద్ద burst ట్రాఫిక్ 2× పరిమితి ని అనుమతించండి చేయవచ్చు.

### స్లైడింగ్ విండో లాగ్
ప్రతి రిక్వెస్ట్ యొక్క timestamp నిల్వ చేయండి. Trailing విండో లోని entries లెక్క చేయండి. Precise కానీ **మెమరీ-తీవ్ర** - స్కేల్ లో ప్రతి timestamp నిల్వ చేయడం expensive.

### స్లైడింగ్ విండో కౌంటర్
ఒక మిశ్రమ విధానం: ప్రస్తుత విండో లెక్క ను మునుపటి విండో యొక్క బరువులు ఇచ్చిన భాగం తో కలపడం చేయండి. ఖచ్చితత్వం మరియు మెమరీ efficiency ని బ్యాలెన్స్ చేస్తుంది.

### టోకెన్ బకెట్ అల్గారిథమ్ (అత్యంత ప్రజాదరణ పొందిన)
ఒక బకెట్ గరిష్ట capacity వరకు టోకెన్‌లు hold చేస్తుంది. టోకెన్‌లు స్థిర రేట్ లో జోడించు అవుతాయి. ప్రతి రిక్వెస్ట్ ఒక టోకెన్ వినియోగిస్తాయి చేస్తుంది. బకెట్ empty అయితే, రిక్వెస్ట్ తిరస్కరించండి అవుతుంది.

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### అల్గారిథమ్ పోలిక

| అల్గారిథమ్ | మెమరీ | ఖచ్చితత్వం | Burst నిర్వహణ |
|-----------|--------|----------|----------------|
| స్థిర విండో | తక్కువ | తక్కువ (ముందంజ bursts) | బలహీనం |
| స్లైడింగ్ లాగ్ | ఎక్కువ | ఖచ్చితమైన | మంచిది |
| స్లైడింగ్ కౌంటర్ | మధ్యస్థం | Approximate | మంచిది |
| టోకెన్ బకెట్ | తక్కువ | మంచిది | అద్భుతం |

## దశ 3 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

### రేట్ లిమిటర్ ఎక్కడ ఉంచాలి
- **Client-side** - spoof చేయడం సులభం, నమ్మదగినది కాదు
- **సర్వర్-side** - ప్రతి-ఇన్‌స్టాన్స్ మాత్రమే, స్కేల్ కాదు
- **API Gateway / Middleware** - విస్తరిత సిస్టమ్‌లు కి అత్యుత్తమ విధానం; అన్ని ఇన్‌స్టాన్స్‌లు లో centralised enforcement

## దశ 4 - లోతైన అధ్యయనం: విస్తరిత రేట్ పరిమితం చేసే

### Redis + Lua స్క్రిప్ట్‌లు
విస్తరిత సెటప్ లో, అనేక సర్వర్‌లు రేట్ పరిమితం చేసే స్థితి పంచుకోండి చేయాలి. Redis ప్రామాణిక ఎంపిక ఎందుకంటే దాని atomic ఆపరేషన్లు మరియు ఉప-millisecond లేటెన్సీ.

Lua స్క్రిప్ట్ atomicity నిర్ధారిస్తుంది - తనిఖీ-మరియు-decrement ఒకే Redis operation లో జరుగుతుంది, race conditions నివారిస్తుంది:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### రెస్పాన్స్ Headers
బాగా డిజైన్ చేసిన రేట్ limiters clients కి స్థితి కమ్యూనికేట్ చేయండి చేస్తాయి:
- `X-RateLimit-Limit: 100` - ప్రతి విండో గరిష్ట రిక్వెస్ట్‌లు
- `X-RateLimit-Remaining: 42` - మిగిలిన రిక్వెస్ట్‌లు
- `X-RateLimit-Reset: 1672531200` - విండో reset అయ్యే UTC epoch
- HTTP `429 Too Many Requests` తో `Retry-After` header

## దశ 5 - ముందంజ సందర్భాలు నిర్వహించు చేయడం

### Race Conditions
Atomic ఆపరేషన్లు లేకుండా, సమకాలిక రిక్వెస్ట్‌లు పరిమితులు bypass చేయవచ్చు. పరిష్కారాలు: Redis Lua స్క్రిప్ట్‌లు లేదా Redis `MULTI/EXEC` transactions.

### రేట్ పరిమితం చేసే Dimensions
ఏకకాలంలో అనేక స్థాయులు లో పరిమితులు apply చేయండి:
- **ప్రతి వినియోగదారు** - authenticated వినియోగదారులు కి 100 రిక్వెస్ట్‌లు/నిమిషం
- **ప్రతి IP** - anonymous ట్రాఫిక్ కి 50 రిక్వెస్ట్‌లు/నిమిషం
- **ప్రతి API కీ** - tiered plans (ఉచిత: 10/నిమి, pro: 1000/నిమి)

### విస్తరిత Clock Skew
సర్వర్‌లు clocks కొంచెం వేర్వేరు గా ఉండవచ్చు. అప్లికేషన్ సర్వర్ timestamps పై ఆధారపడకుండా Redis సర్వర్ సమయం ను ఒకే సోర్స్ of truth గా వాడండి.

<FunFact>GitHub REST API authenticated వినియోగదారులు కి గంటకు 5,000 రిక్వెస్ట్‌లు అనుమతించండి చేస్తుంది కానీ unauthenticated రిక్వెస్ట్‌లు కి గంటకు 60 మాత్రమే. Stripe స్లైడింగ్ విండో విధానం వాడుతుంది, ప్రత్యక్ష మరియు పరీక్ష mode API కీలు కి separate పరిమితులు తో.</FunFact>

## దశ 6 - Bottlenecks మరియు Optimisations

| Bottleneck | పరిష్కారం |
|-----------|----------|
| Redis ఒకే స్థానం of విఫలం | ప్రతిరూపణ తో Redis క్లస్టర్ |
| Redis కి నెట్‌వర్క్ లేటెన్సీ | Periodic sync తో స్థానిక లో-మెమరీ క్యాష్ |
| Hot కీలు (ప్రజాదరణ పొందిన API కీలు) | అనేక Redis నోడ్‌లు లో shard చేయండి |
| Rule మూల్యాంకనం overhead | Rules ముందస్తు-compile చేయండి, configurations క్యాష్ చేయండి |
