# రేట్ లిమిటర్ డిజైన్ చేయండి - *APIs* ను స్కేల్ లో ప్రొటెక్ట్ చేయడం

రేట్ పరిమితం చేసే అనేది అత్యంత ప్రాయోగిక సిస్టమ్ డిజైన్ విషయాలు లో ఒకటి. ప్రతి ప్రొడక్షన్ *API* - *GitHub* నుండి *Stripe* వరకు - అబ్ుస్ె నివారించడానికి, ఫ్ైర్ వినియోగం నిర్ధారించడానికి మరియు బ్అక్ెన్డ్ సేవలు ోవ్ర్ల్ోఅడ్ కాకుండా రక్షించడానికి దీనిపై ఆధారపడుతుంది.

## దశ 1 - అవసరాలు సేకరణ

### ఫంక్షనల్ అవసరాలు
- మార్చుకోగల నియమాలు ఆధారంగా రిక్వెస్ట్‌లు పరిమితి చేయండి (ప్రతి వినియోగదారు, IP లేదా *API* కీ)
- క్లయింట్ థ్రాటిల్ అయినప్పుడు స్పష్టమైన ఫీడ్‌బ్యాక్ ఇవ్వండి (*HTTP* 429)
- ఏకకాలంలో అనేక రేట్ పరిమితం చేసే నియమాలు మద్దతు చేయండి

### ఫంక్షనల్ కాని అవసరాలు
- **తక్కువ లేటెన్సీ** - లిమిటర్ ప్రాముఖ్యమైన అదనపు భారం జోడించు చేయకూడదు
- **విస్తరిత** - అనేక సర్వర్‌లు లో పనిచేయాలి
- **లోపం-ట్ోల్ర్అన్ట్** - లిమిటర్ విఫలమవుతుంది అయితే, ట్రాఫిక్ ప్రవాహం అవుతూనే ఉండాలి (విఫలమవుతుంది-తెరిచి ఉన్న)

<ThinkAboutIt>రేట్ లిమిటర్ క్ర్అష్ అయినప్పుడు విఫలమవుతుంది-తెరిచి ఉన్న (ట్రాఫిక్ అనుమతించండి చేయడం) అవ్వాలా లేదా విఫలమవుతుంది-క్ల్ోస్ెడ్ (ట్రాఫిక్ బ్లాక్ చేయడం) అవ్వాలా? *E-commerce* సైట్ వర్సెస్ బ్అన్క్ింగ్ *API* కి ట్రేడ్‌ఆఫ్‌లు ఏమిటి?</ThinkAboutIt>

## దశ 2 - రేట్ పరిమితం చేసే అల్గారిథమ్‌లు

### స్థిర విండో కౌంటర్
సమయం ను స్థిర వ్ిన్డ్ౌస్ గా విభజించండి చేయండి (ఉదా., 60-సెకండ్ ఇంటర్వల్‌లు). ప్రతి రిక్వెస్ట్ కి కౌంటర్ ిన్క్ర్ెమెంట్ చేయండి. విండో హద్దులు వద్ద ర్ెస్ెట్ చేయండి. **సమస్య:** విండో ఎడ్జ్‌లు వద్ద బ్ుర్స్ట్ ట్రాఫిక్ 2× పరిమితి ని అనుమతించండి చేయవచ్చు.

### స్లైడింగ్ విండో లాగ్
ప్రతి రిక్వెస్ట్ యొక్క ట్ిమ్ెస్ట్అమ్ప్ నిల్వ చేయండి. *Trailing* విండో లోని ఎంట్రీలు లెక్క చేయండి. స్పష్టమైన కానీ **మెమరీ-తీవ్ర** - స్కేల్ లో ప్రతి ట్ిమ్ెస్ట్అమ్ప్ నిల్వ చేయడం ఖరీదైన.

### స్లైడింగ్ విండో కౌంటర్
ఒక మిశ్రమ విధానం: ప్రస్తుత విండో లెక్క ను మునుపటి విండో యొక్క బరువులు ఇచ్చిన భాగం తో కలపడం చేయండి. ఖచ్చితత్వం మరియు మెమరీ సామర్థ్యం ని బ్యాలెన్స్ చేస్తుంది.

### టోకెన్ బకెట్ అల్గారిథమ్ (అత్యంత ప్రజాదరణ పొందిన)
ఒక బకెట్ గరిష్ట సామర్థ్యం వరకు టోకెన్‌లు ఉంచండి చేస్తుంది. టోకెన్‌లు స్థిర రేట్ లో జోడించు అవుతాయి. ప్రతి రిక్వెస్ట్ ఒక టోకెన్ వినియోగిస్తాయి చేస్తుంది. బకెట్ ెమ్ప్ట్య్ అయితే, రిక్వెస్ట్ తిరస్కరించండి అవుతుంది.

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### అల్గారిథమ్ పోలిక

| అల్గారిథమ్ | మెమరీ | ఖచ్చితత్వం | *Burst* నిర్వహణ |
|-----------|--------|----------|----------------|
| స్థిర విండో | తక్కువ | తక్కువ (ముందంజ బ్ుర్స్ట్స్) | బలహీనం |
| స్లైడింగ్ లాగ్ | ఎక్కువ | ఖచ్చితమైన | మంచిది |
| స్లైడింగ్ కౌంటర్ | మధ్యస్థం | *Approximate* | మంచిది |
| టోకెన్ బకెట్ | తక్కువ | మంచిది | అద్భుతం |

## దశ 3 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

### రేట్ లిమిటర్ ఎక్కడ ఉంచాలి
- **Client-వైపు** - స్ప్ూఫ్ చేయడం సులభం, నమ్మదగినది కాదు
- **సర్వర్-వైపు** - ప్రతి-ఇన్‌స్టాన్స్ మాత్రమే, స్కేల్ కాదు
- **API గేట్‌వే / Middleware** - విస్తరిత సిస్టమ్‌లు కి అత్యుత్తమ విధానం; అన్ని ఇన్‌స్టాన్స్‌లు లో క్ెన్ట్ర్ల్ైజ్డ్ ెన్ఫ్ర్క్ెమెంట్

## దశ 4 - లోతైన అధ్యయనం: విస్తరిత రేట్ పరిమితం చేసే

### *Redis* + *Lua* స్క్రిప్ట్‌లు
విస్తరిత సెటప్ లో, అనేక సర్వర్‌లు రేట్ పరిమితం చేసే స్థితి పంచుకోండి చేయాలి. *Redis* ప్రామాణిక ఎంపిక ఎందుకంటే దాని అట్ోమ్ిక్ ఆపరేషన్లు మరియు ఉప-మ్ిల్ల్ైజ్క్ోన్డ్ లేటెన్సీ.

*Lua* స్క్రిప్ట్ అట్ోమ్ిక్ిటీ నిర్ధారిస్తుంది - తనిఖీ-మరియు-డ్ెక్ర్ెమెంట్ ఒకే *Redis* ఆపరేషన్ లో జరుగుతుంది, ర్అక్ె క్ోన్డ్ిషన్స్ నివారిస్తుంది:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### రెస్పాన్స్ *Headers*
బాగా డిజైన్ చేసిన రేట్ ల్ిమ్ిట్ర్స్ క్ల్ిెన్ట్స్ కి స్థితి కమ్యూనికేట్ చేయండి చేస్తాయి:
- `X-RateLimit-Limit: 100` - ప్రతి విండో గరిష్ట రిక్వెస్ట్‌లు
- `X-RateLimit-Remaining: 42` - మిగిలిన రిక్వెస్ట్‌లు
- `X-RateLimit-Reset: 1672531200` - విండో ర్ెస్ెట్ అయ్యే *UTC* ెప్ోచ్
- *HTTP* `429 Too Many Requests` తో `Retry-After` హ్ీడ్ర్

## దశ 5 - ముందంజ సందర్భాలు నిర్వహించు చేయడం

### *Race* *Conditions*
*Atomic* ఆపరేషన్లు లేకుండా, సమకాలిక రిక్వెస్ట్‌లు పరిమితులు దాటవేయడం చేయవచ్చు. పరిష్కారాలు: *Redis* *Lua* స్క్రిప్ట్‌లు లేదా *Redis* `MULTI/EXEC` ట్ర్అన్స్అక్షన్స్.

### రేట్ పరిమితం చేసే *Dimensions*
ఏకకాలంలో అనేక స్థాయులు లో పరిమితులు వర్తింపజేయండి చేయండి:
- **ప్రతి వినియోగదారు** - ాత్ెన్ట్ిక్అట్ెడ్ వినియోగదారులు కి 100 రిక్వెస్ట్‌లు/నిమిషం
- **ప్రతి IP** - అన్ోన్య్మ్స్ ట్రాఫిక్ కి 50 రిక్వెస్ట్‌లు/నిమిషం
- **ప్రతి API కీ** - ట్ిర్ెడ్ ప్ల్అన్స్ (ఉచిత: 10/నిమి, ప్ర్ో: 1000/నిమి)

### విస్తరిత *Clock* *Skew*
సర్వర్‌లు క్ల్ోక్స్ కొంచెం వేర్వేరు గా ఉండవచ్చు. అప్లికేషన్ సర్వర్ ట్ిమ్ెస్ట్అమ్ప్స్ పై ఆధారపడకుండా *Redis* సర్వర్ సమయం ను ఒకే సోర్స్ of ట్ర్ుత్ గా వాడండి.

<FunFact>*GitHub* *REST* *API* ాత్ెన్ట్ిక్అట్ెడ్ వినియోగదారులు కి గంటకు 5,000 రిక్వెస్ట్‌లు అనుమతించండి చేస్తుంది కానీ ున్ాత్ెన్ట్ిక్అట్ెడ్ రిక్వెస్ట్‌లు కి గంటకు 60 మాత్రమే. *Stripe* స్లైడింగ్ విండో విధానం వాడుతుంది, ప్రత్యక్ష మరియు పరీక్ష మ్ోడ్ె *API* కీలు కి వేరు పరిమితులు తో.</FunFact>

## దశ 6 - అడ్డంకులు మరియు మెరుగుదలలు

|-----------|----------|
| *Redis* ఒకే స్థానం of విఫలం | ప్రతిరూపణ తో *Redis* క్లస్టర్ |
| *Redis* కి నెట్‌వర్క్ లేటెన్సీ | *Periodic* సమకాలీకరణ తో స్థానిక లో-మెమరీ క్యాష్ |
| హాట్ కీలు (ప్రజాదరణ పొందిన *API* కీలు) | అనేక *Redis* నోడ్‌లు లో షార్డ్ చేయండి |
| నియమం మూల్యాంకనం అదనపు భారం | నియమాలు ముందస్తు-క్ోమ్ప్ిల్ చేయండి, క్ోన్ఫ్ిగ్ుర్అషన్స్ క్యాష్ చేయండి |
