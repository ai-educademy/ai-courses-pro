# రేట్ లిమిటర్ డిజైన్ చేయండి - APIs ను స్కేల్ లో ప్రొటెక్ట్ చేయడం

రేట్ పరిమితం చేసే అనేది అత్యంత ప్రాయోగిక సిస్టమ్ డిజైన్ విషయాలు లో ఒకటి. ప్రతి ప్రొడక్షన్ API - GitHub నుండి Stripe వరకు - దుర్వినియోగం నివారించడానికి, న్యాయమైన వినియోగం నిర్ధారించడానికి మరియు వెనుక భాగం సేవలు అధిక భారం కాకుండా రక్షించడానికి దీనిపై ఆధారపడుతుంది.

## దశ 1 - అవసరాలు సేకరణ

### కార్యాత్మక అవసరాలు
- మార్చుకోగల నియమాలు ఆధారంగా రిక్వెస్ట్‌లు పరిమితి చేయండి (ప్రతి వినియోగదారు, IP లేదా API కీ)
- క్లయింట్ నియంత్రణ అయినప్పుడు స్పష్టమైన ఫీడ్‌బ్యాక్ ఇవ్వండి (HTTP 429)
- ఏకకాలంలో అనేక రేట్ పరిమితం చేసే నియమాలు మద్దతు చేయండి

### అకార్యాత్మక అవసరాలు
- **తక్కువ లేటెన్సీ** - లిమిటర్ గణనీయమైన భారం జోడించకూడదు
- **విస్తరిత** - అనేక సర్వర్‌లు లో పనిచేయాలి
- **లోపాన్ని తట్టుకునే** - లిమిటర్ విఫలమైతే, ట్రాఫిక్ ప్రవాహం అవుతూనే ఉండాలి (విఫలమైనప్పుడు తెరిచి ఉండే)

<ThinkAboutIt>రేట్ లిమిటర్ కూలిపోవడం అయినప్పుడు విఫలమైనప్పుడు తెరిచి ఉండే (ట్రాఫిక్ అనుమతించడం) అవ్వాలా లేదా విఫలమైనప్పుడు మూసే (ట్రాఫిక్ బ్లాక్ చేయడం) అవ్వాలా? ఈ-కామర్స్ సైట్ వర్సెస్ బ్యాంకింగ్ API కి ట్రేడ్‌ఆఫ్‌లు ఏమిటి?</ThinkAboutIt>

## దశ 2 - రేట్ పరిమితం చేసే అల్గారిథమ్‌లు

### స్థిర విండో కౌంటర్
సమయం ను స్థిర విండోలుగా విభజించండి (ఉదా., 60-సెకండ్ ఇంటర్వల్‌లు). ప్రతి రిక్వెస్ట్ కి కౌంటర్ పెంచండి. విండో సరిహద్దులు వద్ద మళ్లీ మొదలుపెట్టండి. **సమస్య:** విండో ఎడ్జ్‌లు వద్ద ఒక్కసారిగా రావడం ట్రాఫిక్ 2× పరిమితి ని అనుమతించవచ్చు.

### స్లైడింగ్ విండో లాగ్
ప్రతి రిక్వెస్ట్ యొక్క సమయముద్ర నిల్వ చేయండి. వెనుకనున్న విండో లోని నమోదులు లెక్కించండి. ఖచ్చితమైన కానీ **మెమరీ-తీవ్ర** - స్కేల్ లో ప్రతి సమయముద్ర నిల్వ చేయడం ఖరీదైన.

### స్లైడింగ్ విండో కౌంటర్
ఒక మిశ్రమ విధానం: ప్రస్తుత విండో లెక్క ను మునుపటి విండో యొక్క బరువులు ఇచ్చిన భాగం తో కలపండి. ఖచ్చితత్వం మరియు మెమరీ సామర్థ్యం ని బ్యాలెన్స్ చేస్తుంది.

### టోకెన్ బకెట్ అల్గారిథమ్ (అత్యంత ప్రజాదరణ పొందిన)
ఒక బకెట్ గరిష్ట సామర్థ్యం వరకు టోకెన్‌లు ఉంచుతుంది. టోకెన్‌లు స్థిర రేట్ లో జోడించబడతాయి. ప్రతి రిక్వెస్ట్ ఒక టోకెన్ వినియోగిస్తుంది. బకెట్ ఖాళీ అయితే, రిక్వెస్ట్ తిరస్కరించబడుతుంది.

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### అల్గారిథమ్ పోలిక

| అల్గారిథమ్ | మెమరీ | ఖచ్చితత్వం | Burst నిర్వహణ |
|-----------|--------|----------|----------------|
| స్థిర విండో | తక్కువ | తక్కువ (ముందంజ ఒక్కసారిగా వచ్చే ట్రాఫిక్) | బలహీనం |
| స్లైడింగ్ లాగ్ | ఎక్కువ | ఖచ్చితమైన | మంచిది |
| స్లైడింగ్ కౌంటర్ | మధ్యస్థం | సుమారు | మంచిది |
| టోకెన్ బకెట్ | తక్కువ | మంచిది | అద్భుతం |

## దశ 3 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

### రేట్ లిమిటర్ ఎక్కడ ఉంచాలి
- **క్లయింట్-వైపు** - spoof చేయడం సులభం, నమ్మదగినది కాదు
- **సర్వర్-వైపు** - ప్రతి-ఇన్‌స్టాన్స్ మాత్రమే, స్కేల్ కాదు
- **API Gateway / Middleware** - విస్తరిత సిస్టమ్‌లు కి అత్యుత్తమ విధానం; అన్ని ఇన్‌స్టాన్స్‌లు లో కేంద్రీకృత అమలు

## దశ 4 - లోతైన అధ్యయనం: విస్తరిత రేట్ పరిమితం చేసే

### Redis + Lua స్క్రిప్ట్‌లు
విస్తరిత సెటప్ లో, అనేక సర్వర్‌లు రేట్ పరిమితం చేసే స్థితి పంచుకోవాలి. Redis ప్రామాణిక ఎంపిక ఎందుకంటే దాని అణు స్థాయి ఆపరేషన్లు మరియు ఉప-మిల్లీసెకన్ లేటెన్సీ.

Lua స్క్రిప్ట్ అణు సమగ్రత నిర్ధారిస్తుంది: తనిఖీ-మరియు-తగ్గింపు ఒకే Redis కార్యాచరణ లో జరుగుతుంది, పోటీ పరిస్థితులు నివారిస్తుంది:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### రెస్పాన్స్ Headers
బాగా డిజైన్ చేసిన రేట్ limiters క్లయింట్లు కి స్థితి కమ్యూనికేట్ చేస్తాయి:
- `X-RateLimit-Limit: 100` - ప్రతి విండో గరిష్ట రిక్వెస్ట్‌లు
- `X-RateLimit-Remaining: 42` - మిగిలిన రిక్వెస్ట్‌లు
- `X-RateLimit-Reset: 1672531200` - విండో మళ్లీ మొదలు అయ్యే UTC epoch
- HTTP `429 Too Many Requests` తో `Retry-After` హెడర్

## దశ 5 - ముందంజ సందర్భాలు నిర్వహించడం

### పోటీ పరిస్థితులు
అణు ఆపరేషన్లు లేకుండా, సమకాలిక రిక్వెస్ట్‌లు పరిమితులు దాటివెళ్లడం చేయవచ్చు. పరిష్కారాలు: Redis Lua స్క్రిప్ట్‌లు లేదా Redis `MULTI/EXEC` లావాదేవీలు.

### రేట్ పరిమితం చేసే Dimensions
ఏకకాలంలో అనేక స్థాయులు లో పరిమితులు అమలు చేయండి:
- **ప్రతి వినియోగదారు** - ప్రామాణీకరించిన వినియోగదారులు కి 100 రిక్వెస్ట్‌లు/నిమిషం
- **ప్రతి IP** - anonymous ట్రాఫిక్ కి 50 రిక్వెస్ట్‌లు/నిమిషం
- **ప్రతి API కీ** - స్థాయి వారీ ప్రణాళికలు (ఉచిత: 10/నిమి, pro: 1000/నిమి)

### విస్తరిత గడియార వ్యత్యాసం
సర్వర్‌లు గడియారాలు కొంచెం వేర్వేరు గా ఉండవచ్చు. అప్లికేషన్ సర్వర్ సమయముద్రలు పై ఆధారపడకుండా Redis సర్వర్ సమయం ను ఒకే నిజానికి ఏకైక ఆధారం గా వాడండి.

<FunFact>GitHub REST API ప్రామాణీకరించిన వినియోగదారులు కి గంటకు 5,000 రిక్వెస్ట్‌లు అనుమతిస్తుంది కానీ ప్రామాణీకరించని రిక్వెస్ట్‌లు కి గంటకు 60 మాత్రమే. Stripe స్లైడింగ్ విండో విధానం వాడుతుంది, ప్రత్యక్ష మరియు పరీక్ష మోడ్ API కీలు కి వేరు పరిమితులు తో.</FunFact>
