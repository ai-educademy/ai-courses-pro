## ఇంటర్వ్యూ ప్రాంప్ట్

*"అనేక machine learning models ను developers కు REST API ద్వారా serve చేసే AI API platform డిజైన్ చేయండి, OpenAI లేదా Hugging Face స్థాయిలో మోడళ్లు serve చేస్తున్నట్లుగా."*

ఈ ప్రశ్న ఇంటర్వ్యూల్లో బాగా ప్రాచుర్యం పొందుతోంది, ఎందుకంటే ఇది **API platform design** ను AI workloads కు ప్రత్యేకమైన **GPU infrastructure challenges** తో కలుపుతుంది.

## దశ 1: అవసరాలు Gathering

**Functional అవసరాలు:**
- అనేక AI మోడళ్లు (టెక్స్ట్ సృష్టి, image వర్గీకరణ, ఎంబెడ్డింగ్‌లు) ను REST API ద్వారా సర్వ్ చేయండి చేయడం
- API కీ ప్రామాణీకరణ తో ప్రతి-కీ వినియోగం quotas
- ప్రతి API కాల్ కి వినియోగం ట్రాకింగ్ మరియు billing
- అనేక మోడల్ వెర్షన్‌లు కు A/B పరీక్షలు తో మద్దతు
- పొడవైన-నడుస్తున్న సృష్టి పనులు కోసం స్ట్రీమింగ్ రెస్పాన్స్‌లు

**Non-functional అవసరాలు:**
- లేటెన్సీ: ఎంబెడ్డింగ్ మోడళ్లు కి p50 500ms లోపు, generative మోడళ్లు కి p50 2s లోపు
- థ్రూపుట్: అన్ని మోడళ్లు లో 10,000 రిక్వెస్ట్‌లు ప్రతి సెకండ్
- అందుబాటు: graceful degradation తో 99.9% uptime
- ఖర్చు efficiency: GPUs ఖరీదైనవి - utilisation maximize చేయాలి

<Callout>
AI వేదికలు కు చాలా variable లేటెన్సీ ఉంటుంది. ఒక టెక్స్ట్ completion రిక్వెస్ట్ అవుట్‌పుట్ length ని బట్టి 200ms లేదా 30 సెకన్లు పట్టవచ్చు. మీ డిజైన్ ఈ variance ను ఎలా నిర్వహించు చేస్తుందో ఎప్పుడూ discuss చేయండి.
</Callout>

## దశ 2: API డిజైన్

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-6-astra", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - available models list
GET  /v1/usage?start=2024-01-01    - usage మరియు billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

Generative మోడళ్లు కోసం **సర్వర్-Sent ఈవెంట్లు (SSE)** ద్వారా స్ట్రీమింగ్ చాలా కీలకమైన - వినియోగదారులు పూర్తి రెస్పాన్స్ కోసం వేచి ఉండండి చేయకుండా టోకెన్‌లు progressively కనిపిస్తాయి.

## దశ 3: API గేట్‌వే మరియు ప్రామాణీకరణ

API గేట్‌వే వేదిక యొక్క front door:

- **ప్రామాణీకరణ** - API కీలు ను కీ నిల్వ తో ధృవీకరించండి చేయండి (వేగం కోసం Redis, persistence కోసం డేటాబేస్)
- **రేట్ పరిమితం చేసే** - ప్రతి-కీ పరిమితులు enforce చేయండి (ఉదా., ఉచిత tier కోసం 60 రిక్వెస్ట్‌లు/నిమిషం)
- **రిక్వెస్ట్ రూటింగ్** - రిక్వెస్ట్‌లు ను సరైన మోడల్-సర్వింగ్ క్లస్టర్ కి ప్రత్యక్ష చేయండి
- **రిక్వెస్ట్ ధృవీకరణ** - payload స్కీమా, మోడల్ అందుబాటు, టోకెన్ పరిమితులు తనిఖీ చేయండి

**రేట్ పరిమితం చేసే implementation:**
Redis లో **స్లైడింగ్ విండో కౌంటర్** వాడండి:
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

ప్రతి రిక్వెస్ట్ కౌంటర్ ను increment చేస్తుంది. పరిమితి exceed అయితే HTTP 429 తిరిగి ఇవ్వండి.

## దశ 4: మోడల్ సర్వింగ్ మరియు GPU Allocation

ఇక్కడ AI వేదికలు సాంప్రదాయ వెబ్ సేవలు నుండి fundamentally భిన్నంగా ఉంటాయి. GPUs scarce, ఖరీదైనవి మరియు specialised orchestration అవసరం.

**మోడల్ సర్వింగ్ పొర:**
- **Triton ఇన్‌ఫరెన్స్ సర్వర్** లేదా **vLLM** లాంటి ఫ్రేమ్‌వర్క్‌లు తో మోడళ్లు ను GPU మెమరీ లోకి లోడ్ చేస్తారు
- ప్రతి మోడల్ వెర్షన్ dedicated GPU ఇన్‌స్టాన్స్‌లు pool లో నడపండి అవుతుంది
- పెద్ద భాష మోడళ్లు (LLMs) కు అనేక GPUs లో **మోడల్ parallelism** అవసరం కావచ్చు

**రిక్వెస్ట్ batching:**
GPUs లో వ్యక్తిగత ఇన్‌ఫరెన్స్ రిక్వెస్ట్‌లు inefficient. **Dynamic batching** అనేక రిక్వెస్ట్‌లు ను గుంపు చేసి కలిసి ప్రక్రియ చేస్తుంది:
- 10ms వరకు లేదా బ్యాచ్ 32 రిక్వెస్ట్‌లు చేరే వరకు collect చేయండి
- మొత్తం బ్యాచ్ ను ఒక GPU forward pass లో ప్రక్రియ చేయండి
- ప్రతి caller కు వ్యక్తిగత రెస్పాన్స్‌లు తిరిగి ఇవ్వండి

Individually ప్రక్రియ చేయడంతో పోలిస్తే ఇది థ్రూపుట్ ను 5-10x మెరుగుపరచండి చేయగలదు.

<FunFact>
ఒక NVIDIA H100 GPU ధర సుమారు £25,000 మరియు 700 watts శక్తి వినియోగిస్తాయి చేస్తుంది. మోడల్ సర్వింగ్ కోసం 1,000 GPUs క్లస్టర్ నడపడానికి electricity మరియు hardware లో మాత్రమే నెలకు £2 మిలియన్ కంటే ఎక్కువ ఖర్చు అవుతుంది - అందుకే efficient batching మరియు utilisation చాలా ముఖ్యం.
</FunFact>

## దశ 5: మోడల్ వెర్షన్‌లు మధ్య A/B పరీక్షలు

కొత్త మోడల్ వెర్షన్ డిప్లాయ్ చేయండి చేసేటప్పుడు controlled rollout అవసరం:

- **ట్రాఫిక్ splitting** - 5% రిక్వెస్ట్‌లు కొత్త మోడల్ కు, 95% ప్రస్తుత మోడల్ కు మార్గం చేయండి
- **Shadow mode** - ప్రొడక్షన్ ట్రాఫిక్ లో కొత్త మోడల్ నడపండి చేయండి కానీ ఫలితాలు వినియోగదారులు కు రిటర్న్ చేయకండి
- **మెట్రిక్స్ పోలిక** - లేటెన్సీ, అవుట్‌పుట్ నాణ్యత స్కోర్లు, error రేట్లు, ఖర్చు ప్రతి రిక్వెస్ట్
- **Gradual rollout** - confidence పెరిగే కొద్దీ కొత్త వెర్షన్ కు ట్రాఫిక్ పెంచండి

రూటింగ్ logic API గేట్‌వే లో ఉంటుంది:
```
model: "gpt-6-astra"  →  95% → gpt-6-astra (current)
                →   5% → claude-opus-5-5 (candidate)
```

<ThinkAboutIt>
కొత్త LLM వెర్షన్ "మెరుగైన" అని మూల్యాంకనం చేయండి చేయడం surprisingly కష్టం - వర్గీకరణ మోడళ్లు లా సులభమైన ఖచ్చితత్వం metric ఉండదు. Generative AI మోడళ్లు కోసం ఆటోమేటెడ్ నాణ్యత మూల్యాంకనం సిస్టమ్ మీరు ఎలా డిజైన్ చేస్తారు?
</ThinkAboutIt>

## దశ 6: వినియోగం ట్రాకింగ్ మరియు Billing

AI APIs సాధారణంగా ప్రతి టోకెన్ bill చేస్తాయి (LLMs కు ఇన్‌పుట్ + అవుట్‌పుట్ టోకెన్‌లు, ఇతర మోడళ్లు కు ప్రతి రిక్వెస్ట్).

**ఈవెంట్-driven billing పైప్‌లైన్:**
1. ప్రతి API రెస్పాన్స్ లో వినియోగం header ఉంటుంది: `x-usage-tokens: 847`
2. Kafka కు billing ఈవెంట్ ప్రచురించండి అవుతుంది: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. Billing aggregation సేవ ఈవెంట్లు వినియోగిస్తాయి చేసి నడుస్తున్న totals నవీకరించు చేస్తుంది
4. వినియోగం డ్యాష్‌బోర్డ్‌లు సమయం-series డేటాబేస్ నుండి aggregated డేటా క్వెరీ చేస్తాయి

**Kafka ఎందుకు?** Billing reliable గా ఉండాలి కానీ సమకాలిక గా ఉండాల్సిన అవసరం లేదు. Billing సేవ temporarily down అయితే, ఈవెంట్లు Kafka లో క్యూ అవుతాయి మరియు recover అయినప్పుడు ప్రక్రియ అవుతాయి - వినియోగం డేటా ఏదీ lost కాదు.

## దశ 7: పర్యవేక్షణ మరియు Observability

AI వేదికలు కు ప్రామాణిక వెబ్ సేవలు కంటే ఎక్కువ పర్యవేక్షణ అవసరం:

| Metric | ఎందుకు ముఖ్యం |
|--------|---------------|
| ఇన్‌ఫరెన్స్ లేటెన్సీ (p50, p95, p99) | వినియోగదారు అనుభవం మరియు SLA అనుసరణ |
| GPU utilisation | ఖర్చు efficiency - idle GPUs డబ్బు వృథా చేస్తాయి |
| టోకెన్‌లు ప్రతి సెకండ్ | థ్రూపుట్ capacity మరియు స్కేలింగ్ సంకేతాలు |
| Error రేట్ ద్వారా మోడల్ | మోడల్-స్పష్టంగా failures గుర్తించండి చేయడం |
| క్యూ లోతు | స్కేలింగ్ ప్రేరేపణ - లోతైన క్యూలు అంటే డిమాండ్ capacity కంటే ఎక్కువ |
| అవుట్‌పుట్ నాణ్యత స్కోర్లు | మోడల్ degradation గుర్తించండి చేయడం (ఆటోమేటెడ్ eval ద్వారా) |

**Alerting thresholds:** GPU utilisation 40% కంటే తగ్గితే స్కేల్-down ప్రేరేపణ; క్యూ లోతు 100 కంటే ఎక్కువైతే స్కేల్-up ప్రేరేపణ.

## దశ 8: ఆటో-స్కేలింగ్

AI workloads కు చాలా variable డిమాండ్ ఉంటుంది. ఆటో-స్కేలింగ్ responsiveness మరియు ఖర్చు ను బ్యాలెన్స్ చేయాలి:

- **Horizontal స్కేలింగ్** - క్యూ లోతు లేదా లేటెన్సీ thresholds exceed అయినప్పుడు మరిన్ని GPU ఇన్‌స్టాన్స్‌లు జోడించు చేయండి
- **Predictive స్కేలింగ్** - expected peaks ముందు capacity ముందస్తు-provision చేయడానికి historical ట్రాఫిక్ నమూనాలు వాడండి
- **స్కేల్-కు-zero** - rarely used మోడళ్లు కోసం అన్ని ఇన్‌స్టాన్స్‌లు shut down చేసి డిమాండ్ మీద cold-ప్రారంభించండి చేయండి
- **Warm pools** - cold-ప్రారంభించండి లేటెన్సీ నివారించండి చేయడానికి కొన్ని ఇన్‌స్టాన్స్‌లు మోడళ్లు ముందస్తు-loaded గా ఉంచండి

స్కేల్-కు-zero వ్యూహం వందల మోడళ్లు host చేసే వేదికలు కు ప్రత్యేకంగా ముఖ్యం - ప్రతి మోడల్ ను ఎల్లప్పుడూ GPU మెమరీ లో loaded గా ఉంచలేరు.

## ముఖ్యమైన Takeaways

- AI API వేదికలు సాంప్రదాయ API డిజైన్ ను GPU-స్పష్టంగా మౌలిక సదుపాయాలు challenges తో కలపడం చేస్తాయి
- రిక్వెస్ట్ batching GPU థ్రూపుట్ మరియు ఖర్చు efficiency ని dramatically మెరుగుపరచండి చేస్తుంది
- రేట్ పరిమితం చేసే వేదిక మరియు కస్టమర్లు ను runaway ఖర్చులు నుండి protect చేస్తుంది
- Kafka ద్వారా asynchronous billing రిక్వెస్ట్‌లు బ్లాక్ చేయకుండా reliable వినియోగం ట్రాకింగ్ నిర్ధారించండి చేస్తుంది
- ఆటో-స్కేలింగ్ responsiveness మరియు ఖర్చు ను బ్యాలెన్స్ చేయాలి - low-ట్రాఫిక్ మోడళ్లు కోసం స్కేల్-కు-zero
- GPU utilisation మరియు క్యూ లోతు monitor చేయడం intelligent స్కేలింగ్ నిర్ణయాలు drive చేస్తుంది
