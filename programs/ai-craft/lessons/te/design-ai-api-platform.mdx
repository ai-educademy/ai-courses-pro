## ఇంటర్వ్యూ ప్రాంప్ట్

*"అనేక యంత్ర అభ్యాస మోడళ్లు ను డెవలపర్‌లు కు REST API ద్వారా అందించే AI API వేదిక డిజైన్ చేయండి, OpenAI లేదా Hugging Face స్థాయిలో మోడళ్లు అందిస్తున్నట్లుగా."*

ఈ ప్రశ్న ఇంటర్వ్యూల్లో బాగా ప్రాచుర్యం పొందుతోంది, ఎందుకంటే ఇది **API వేదిక రూపకల్పన** ను AI పనిభారాలు కు ప్రత్యేకమైన **GPU మౌలిక సదుపాయాల సవాళ్లు** తో కలుపుతుంది.

## దశ 1: అవసరాలు సేకరణ

**కార్యాత్మక అవసరాలు:**
- అనేక AI మోడళ్లు (టెక్స్ట్ సృష్టి, చిత్ర వర్గీకరణ, ఎంబెడ్డింగ్‌లు) ను REST API ద్వారా అందించడం
- API కీ ప్రామాణీకరణ తో ప్రతి-కీ వినియోగం పరిమితులు
- ప్రతి API కాల్ కి వినియోగం ట్రాకింగ్ మరియు బిల్లింగ్
- అనేక మోడల్ వెర్షన్‌లు కు A/B పరీక్షలు తో మద్దతు
- పొడవైన-నడుస్తున్న సృష్టి పనులు కోసం స్ట్రీమింగ్ రెస్పాన్స్‌లు

**అకార్యాత్మక అవసరాలు:**
- లేటెన్సీ: ఎంబెడ్డింగ్ మోడళ్లు కి p50 500ms లోపు, సృష్టి మోడళ్లు కి p50 2s లోపు
- థ్రూపుట్: అన్ని మోడళ్లు లో 10,000 రిక్వెస్ట్‌లు ప్రతి సెకండ్
- అందుబాటు: సాఫీగా సామర్థ్యం తగ్గించే విధానం తో 99.9% అందుబాటు సమయం
- ఖర్చు సామర్థ్యం: GPUs ఖరీదైనవి - వినియోగం గరిష్ఠం చేయాలి చేయాలి

<Callout>
AI వేదికలు కు చాలా మారే లేటెన్సీ ఉంటుంది. ఒక టెక్స్ట్ పూర్తి రిక్వెస్ట్ అవుట్‌పుట్ పొడవు ని బట్టి 200ms లేదా 30 సెకన్లు పట్టవచ్చు. మీ డిజైన్ ఈ వ్యత్యాసం ను ఎలా నిర్వహిస్తుందో ఎప్పుడూ వివరించండి.
</Callout>

## దశ 2: API డిజైన్

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-6-astra", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - available models list
GET  /v1/usage?start=2024-01-01    - usage మరియు billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

సృష్టి మోడళ్లు కోసం **సర్వర్ పంపే ఈవెంట్లు (SSE)** ద్వారా స్ట్రీమింగ్ చాలా కీలకమైన - వినియోగదారులు పూర్తి రెస్పాన్స్ కోసం వేచి ఉండకుండా టోకెన్‌లు దశలవారీగా కనిపిస్తాయి.

## దశ 3: API గేట్‌వే మరియు ప్రామాణీకరణ

API గేట్‌వే వేదిక యొక్క ప్రధాన ప్రవేశద్వారం:

- **ప్రామాణీకరణ** - API కీలు ను కీ నిల్వ తో ధృవీకరించండి (వేగం కోసం Redis, స్థిర నిల్వ కోసం డేటాబేస్)
- **రేట్ పరిమితం చేసే** - ప్రతి-కీ పరిమితులు అమలు చేయండి (ఉదా., ఉచిత స్థాయి కోసం 60 రిక్వెస్ట్‌లు/నిమిషం)
- **రిక్వెస్ట్ రూటింగ్** - రిక్వెస్ట్‌లు ను సరైన మోడల్-సర్వింగ్ క్లస్టర్ కి ప్రత్యక్ష చేయండి
- **రిక్వెస్ట్ ధృవీకరణ** - payload స్కీమా, మోడల్ అందుబాటు, టోకెన్ పరిమితులు తనిఖీ చేయండి

**రేట్ పరిమితం చేసే అమలు విధానం:**
Redis లో **స్లైడింగ్ విండో కౌంటర్** వాడండి:
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

ప్రతి రిక్వెస్ట్ కౌంటర్ ను పెంచుతుంది చేస్తుంది. పరిమితి మించితే అయితే HTTP 429 తిరిగి ఇవ్వండి.

## దశ 4: మోడల్ సర్వింగ్ మరియు GPU Allocation

ఇక్కడ AI వేదికలు సాంప్రదాయ వెబ్ సేవలు నుండి మౌలికంగా భిన్నంగా ఉంటాయి. GPUs అరుదైన, ఖరీదైనవి మరియు ప్రత్యేక సమన్వయం అవసరం.

**మోడల్ సర్వింగ్ పొర:**
- **Triton ఇన్‌ఫరెన్స్ సర్వర్** లేదా **vLLM** లాంటి ఫ్రేమ్‌వర్క్‌లు తో మోడళ్లు ను GPU మెమరీ లోకి లోడ్ చేస్తారు
- ప్రతి మోడల్ వెర్షన్ ప్రత్యేక GPU ఇన్‌స్టాన్స్‌లు సమూహం లో నడుస్తుంది
- పెద్ద భాష మోడళ్లు (LLMs) కు అనేక GPUs లో **మోడల్ సమాంతరism** అవసరం కావచ్చు

**రిక్వెస్ట్ బ్యాచింగ్:**
GPUs లో వ్యక్తిగత ఇన్‌ఫరెన్స్ రిక్వెస్ట్‌లు అసమర్థమైన. **Dynamic బ్యాచింగ్** అనేక రిక్వెస్ట్‌లు ను గుంపు చేసి కలిసి ప్రాసెస్ చేస్తుంది:
- 10ms వరకు లేదా బ్యాచ్ 32 రిక్వెస్ట్‌లు చేరే వరకు సేకరించండి
- మొత్తం బ్యాచ్ ను ఒక GPU ముందుకు గణన దశ లో ప్రాసెస్ చేయండి
- ప్రతి caller కు వ్యక్తిగత రెస్పాన్స్‌లు తిరిగి ఇవ్వండి

Individually ప్రక్రియ చేయడంతో పోలిస్తే ఇది థ్రూపుట్ ను 5-10x మెరుగుపరచగలదు.

ఒక NVIDIA H100 GPU ధర సుమారు £25,000 మరియు 700 వాట్లు శక్తి వినియోగిస్తుంది. మోడల్ సర్వింగ్ కోసం 1,000 GPUs క్లస్టర్ నడపడానికి విద్యుత్ మరియు హార్డ్‌వేర్ లో మాత్రమే నెలకు £2 మిలియన్ కంటే ఎక్కువ ఖర్చు అవుతుంది - అందుకే సమర్థమైన బ్యాచింగ్ మరియు వినియోగం చాలా ముఖ్యం.
</FunFact>

## దశ 5: మోడల్ వెర్షన్‌లు మధ్య A/B పరీక్షలు

కొత్త మోడల్ వెర్షన్ డిప్లాయ్ చేసేటప్పుడు నియంత్రిత విడుదల అవసరం:

- **ట్రాఫిక్ విభజన** - 5% రిక్వెస్ట్‌లు కొత్త మోడల్ కు, 95% ప్రస్తుత మోడల్ కు మార్గం మళ్లించండి
- **నీడ మోడ్** - ప్రొడక్షన్ ట్రాఫిక్ లో కొత్త మోడల్ నడపండి, కానీ ఫలితాలు వినియోగదారులు కు తిరిగి ఇవ్వకండి
- **మెట్రిక్స్ పోలిక** - లేటెన్సీ, అవుట్‌పుట్ నాణ్యత స్కోర్లు, లోపం రేట్లు, ఖర్చు ప్రతి రిక్వెస్ట్
- **దశలవారీ విడుదల** - నమ్మకం పెరిగే కొద్దీ కొత్త వెర్షన్ కు ట్రాఫిక్ పెంచండి

రూటింగ్ తర్కం API గేట్‌వే లో ఉంటుంది:
```
model: "gpt-6-astra"  →  95% → gpt-6-astra (current)
                →   5% → claude-opus-5-5 (candidate)
```

<ThinkAboutIt>
కొత్త LLM వెర్షన్ "మెరుగైన" అని మూల్యాంకనం చేయడం ఆశ్చర్యంగా కష్టం - వర్గీకరణ మోడళ్లు లా సులభమైన ఖచ్చితత్వం కొలమానం ఉండదు. సృష్టి AI మోడళ్లు కోసం ఆటోమేటెడ్ నాణ్యత మూల్యాంకనం సిస్టమ్ మీరు ఎలా డిజైన్ చేస్తారు?
</ThinkAboutIt>

## దశ 6: వినియోగం ట్రాకింగ్ మరియు బిల్లింగ్

AI APIs సాధారణంగా ప్రతి టోకెన్ bill చేస్తాయి (LLMs కు ఇన్‌పుట్ + అవుట్‌పుట్ టోకెన్‌లు, ఇతర మోడళ్లు కు ప్రతి రిక్వెస్ట్).

**ఈవెంట్-ఆధారిత బిల్లింగ్ పైప్‌లైన్:**
1. ప్రతి API రెస్పాన్స్ లో వినియోగం హెడర్ ఉంటుంది: `x-usage-tokens: 847`
2. Kafka కు బిల్లింగ్ ఈవెంట్ ప్రచురించండి అవుతుంది: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. బిల్లింగ్ సమీకరణ సేవ ఈవెంట్లు వినియోగిస్తాయి చేసి నడుస్తున్న మొత్తాలు నవీకరిస్తుంది
4. వినియోగం డ్యాష్‌బోర్డ్‌లు సమయం-శ్రేణి డేటాబేస్ నుండి సమీకరించిన డేటా క్వెరీ చేస్తాయి

## దశ 8: ఆటో-స్కేలింగ్

AI పనిభారాలు కు చాలా మారే డిమాండ్ ఉంటుంది. ఆటో-స్కేలింగ్ స్పందన వేగం మరియు ఖర్చు ను బ్యాలెన్స్ చేయాలి:

- **అడ్డ స్కేలింగ్** - క్యూ లోతు లేదా లేటెన్సీ గడులు మించితే అయినప్పుడు మరిన్ని GPU ఇన్‌స్టాన్స్‌లు జోడించండి
- **ఊహాత్మక స్కేలింగ్** - ఆశించిన గరిష్ఠ రద్దీ ముందు సామర్థ్యం ముందస్తు-కేటాయించడానికి గత ట్రాఫిక్ నమూనాలు వాడండి
- **శూన్యానికి స్కేల్** - అరుదుగా వాడే మోడళ్లు కోసం అన్ని ఇన్‌స్టాన్స్‌లు ఆపివేసి చేసి డిమాండ్ మీద శీతల ప్రారంభ చేయండి
- **సిద్ధ సమూహాలు** - శీతల ప్రారంభ లేటెన్సీ నివారించడానికి కొన్ని ఇన్‌స్టాన్స్‌లు మోడళ్లు ముందస్తు-లోడ్ చేసి ఉంచండి

శూన్యానికి స్కేల్ వ్యూహం వందల మోడళ్లు నిర్వహించే వేదికలు కు ప్రత్యేకంగా ముఖ్యం - ప్రతి మోడల్ ను ఎల్లప్పుడూ GPU మెమరీ లో లోడ్ చేసి ఉంచలేరు.
