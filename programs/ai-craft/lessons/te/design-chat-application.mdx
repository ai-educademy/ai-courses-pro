## ఇంటర్వ్యూ ప్రాంప్ట్

*"WhatsApp లేదా Slack లాంటి చాట్ అప్లికేషన్ డిజైన్ చేయండి - ఒకటి-కు-ఒకటి మ్ెస్స్అగ్ింగ్, గుంపు చ్అట్స్, మరియు ఆన్‌లైన్ ఉనికి ిన్డ్ిక్అట్ర్స్ మద్దతు చేయాలి."*

సిస్టమ్ డిజైన్ ఇంటర్వ్యూలు లో ఇది చాలా ప్రజాదరణ పొందిన ప్రశ్న ఎందుకంటే ఒకే సమస్య లో రియల్ టైమ్ కమ్యూనికేషన్, కనెక్షన్ నిర్వహణ, నిల్వ at స్కేల్, మరియు విస్తరిత సిస్టమ్ ట్రేడ్‌ఆఫ్‌లు - అన్నీ పరీక్ష చేస్తుంది.

## దశ 1: అవసరాలు సేకరణ

**ఫంక్షనల్ అవసరాలు:**
- డెలివరీ మరియు చదవడం ర్ెక్ెిప్ట్స్ తో ఒకటి-కు-ఒకటి మ్ెస్స్అగ్ింగ్
- గుంపు చాట్ (500 మ్ెమ్బ్ర్స్ వరకు)
- ఆన్‌లైన్/ఆఫ్‌లైన్ ఉనికి ిన్డ్ిక్అట్ర్స్
- సందేశం చరిత్ర మరియు సెర్చ్
- ఆఫ్‌లైన్ వినియోగదారులు కు పుష్ నోటిఫికేషన్‌లు

**Non-functional అవసరాలు:**
- తక్కువ లేటెన్సీ: సందేశాలు 200ms లోపు చేరవేయండి అవ్వాలి
- అధిక అందుబాటు: 99.99% అప్‌టైమ్
- ఒక సంభాషణ లో సందేశం ర్డ్ర్ింగ్ గ్ుార్అన్ట్ీడ్
- 50 మిలియన్ సమకాలిక కనెక్షన్‌లు మద్దతు

<Callout>
ఫంక్షనల్ కాని అవసరాలు ను ఎల్లప్పుడూ స్పష్టంగా సంఖ్యలు తో పరిమాణాత్మకంగా చెప్పండి చేయండి. "వేగంగా డెలివరీ" వ్అగ్ుె - "ఉప-200ms డెలివరీ" అంటే మీకు డొమైన్ అర్థమైందని చూపిస్తుంది.
</Callout>

## దశ 2: *API* డిజైన్

*REST*-మాత్రమే సిస్టమ్‌లు కు భిన్నంగా, చాట్ కు **ద్విదిశ కమ్యూనికేషన్** అవసరం. మనకు రెండు ప్ర్ోట్ోక్ోల్స్ కావాలి:

**REST API** (న్ోన్-రియల్ టైమ్ ఆపరేషన్లు కోసం):
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket** (రియల్ టైమ్ మ్ెస్స్అగ్ింగ్ కోసం):
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## దశ 3: *WebSocket* కనెక్షన్ నిర్వహణ

ప్రతి కలిసిన వినియోగదారు ఒక ప్ర్స్ిస్ట్ెన్ట్ *WebSocket* కనెక్షన్ నిర్వహించండి చేస్తారు. 50 మిలియన్ సమకాలిక వినియోగదారులు వద్ద ఇది పెద్ద ఇంజినీరింగ్ సవాలు.

**కనెక్షన్ సర్వర్‌లు** (గేట్‌వే సర్వర్‌లు అని కూడా అంటారు) *WebSocket* కనెక్షన్‌లు ఉంచండి చేస్తాయి. ప్రతి సర్వర్ సుమారు 50,000-100,000 సమకాలిక కనెక్షన్‌లు నిర్వహించు చేయగలదు, అంటే మనకు 500-1,000 కనెక్షన్ సర్వర్‌లు కావాలి.

ఒక **కనెక్షన్ రిజిస్ట్రీ** (**Redis** క్లస్టర్) ప్రతి వినియోగదారు ని వారి కనెక్షన్ సర్వర్ కు మ్యాప్ చేస్తుంది:
```
user_123 → ws-server-042
user_456 → ws-server-187
```

వినియోగదారు A, వినియోగదారు B కి సందేశం పంపినప్పుడు ప్రవాహం ఇలా ఉంటుంది:
1. సందేశం, A యొక్క కనెక్షన్ సర్వర్ కి *WebSocket* ద్వారా వస్తుంది
2. సర్వర్, *Redis* లో B యొక్క కనెక్షన్ సర్వర్ ను ల్ూక్ up చేస్తుంది
3. సందేశం అంతర్గత మ్ెస్స్అగ్ింగ్ ద్వారా B యొక్క కనెక్షన్ సర్వర్ కు మార్గం అవుతుంది
4. B యొక్క సర్వర్, B యొక్క *WebSocket* లో సందేశం పుష్ చేస్తుంది

## దశ 4: సందేశం నిల్వ

చాట్ అప్లికేషన్‌లు చాలా పెద్ద వ్ోల్ుమ్ెస్ లో డేటా సృష్టించు చేస్తాయి. *WhatsApp* రోజుకు 100 బిలియన్ కంటే ఎక్కువ సందేశాలు ప్రక్రియ చేస్తుంది.

**నిల్వ వ్యూహం:**
- **ఇటీవలి సందేశాలు** - వేగంగా డేటా నిల్వ (**Cassandra** లేదా **HBase**) లో, సంభాషణ ID తో ప్ార్ట్ిషన్ెడ్
- **సందేశం ఇండెక్స్** - **Elasticsearch** ద్వారా సెర్చ్ సాధ్యం చేయండి చేస్తుంది
- **మీడియా ఫైళ్లు** - ోబ్జ్ెక్ట్ నిల్వ (S3) లో *CDN* డెలివరీ తో

**స్కీమా డిజైన్ (Cassandra):**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

ఈ డిజైన్ వల్ల ఒక సంభాషణ లోని అన్ని సందేశాలు ఒకే పార్టిషన్ లో క్ో-ల్ోక్అట్ెడ్ అవుతాయి, "పాత సందేశాలు లోడ్ చేయి" క్వెరీలు చాలా సమర్థమైన అవుతాయి - ఒకే పార్టిషన్ లో స్ెక్వ్ెన్షల్ చదవడం.

## దశ 5: ఉనికి సిస్టమ్

ఎవరు ఆన్‌లైన్ లో ఉన్నారో చూపించడం సులభమైన గా అనిపిస్తుంది కానీ స్కేల్ వద్ద స్ుర్ప్ర్ిస్ింగ్ల్య్ ట్ర్ిక్య్. మీ సంప్రదిస్తుంది జాబితా లోని ప్రతి వినియోగదారు కోసం ప్రతి కొన్ని సెకన్లు కు డేటాబేస్ ప్ోల్ల్ చేయడం సాధ్యం కాదు.

**Heartbeat విధానం:**
1. కలిసిన క్ల్ిెన్ట్స్ ప్రతి 30 సెకన్లు కు *WebSocket* ద్వారా హ్ీర్ట్బ్ీట్ పంపుతాయి
2. సర్వర్ ఒక *Redis* కీ ను 60 సెకన్లు *TTL* తో నవీకరించు చేస్తుంది: `presence:user_123 → online (TTL 60s)`
3. *Heartbeat* రాకపోతే కీ గడువు ముగియాలి అవుతుంది మరియు వినియోగదారు ఆఫ్‌లైన్ గా కనిపిస్తారు

**స్థితి నవీకరణలు కోసం ఫ్యాన్-అవుట్:**
ఒక వినియోగదారు ఆన్‌లైన్ వచ్చినప్పుడు, వారి స్థితి ఆన్‌లైన్ ఉన్న అన్ని క్ోన్ట్అక్ట్స్ కు పుష్ అవ్వాలి. 500 క్ోన్ట్అక్ట్స్ ఉన్న వినియోగదారు కోసం, ఏ క్ోన్ట్అక్ట్స్ ఆన్‌లైన్ లో ఉన్నారో తనిఖీ చేసి వారికి మాత్రమే ఉనికి నవీకరణలు పంపాలి - **ల్అజ్య్ ఫ్యాన్-అవుట్** ఆఫ్‌లైన్ వినియోగదారులు కు బ్ర్ోఅడ్క్అస్ట్ చేయడం నివారిస్తుంది.

<FunFact>
*WhatsApp* యొక్క "చివరి స్ీన్" ఫీచర్ ప్రపంచవ్యాప్తంగా ున్ెక్స్ప్ెక్ట్ెడ్ సోషల్ డ్ర్అమ్అ కలిగించింది. కొన్ని దేశాల్లో సంబంధం డ్ిస్ప్ుట్ెస్ పెరిగాయి ఎందుకంటే ప్ార్ట్న్ర్స్ ఒకరినొకరి ఖచ్చితమైన ల్అస్ట్-అక్ట్ివ్ ట్ిమ్ెస్ట్అమ్ప్స్ చూడగలిగారు. *WhatsApp* చివరకు ఈ సమాచారం దాచడానికి గోప్యత క్ోన్ట్ర్ోల్స్ జోడించు చేసింది.
</FunFact>

## దశ 6: పుష్ నోటిఫికేషన్‌లు

వినియోగదారు ఆఫ్‌లైన్ అయినప్పుడు (చురుకైన *WebSocket* లేదు), సందేశాలు పుష్ నోటిఫికేషన్‌లు ద్వారా చేరాలి.

సందేశం ప్రవాహం మారుతుంది:
1. కనెక్షన్ రిజిస్ట్రీ వినియోగదారు B ఆఫ్‌లైన్ అని చూపిస్తుంది
2. సందేశం డేటాబేస్ లో "ున్డ్ెల్ివ్ర్ెడ్" స్థితి తో నిల్వ అవుతుంది
3. నోటిఫికేషన్ సేవ *APNs* (*iOS*) లేదా *FCM* (*Android*) ద్వారా పుష్ పంపుతుంది
4. వినియోగదారు B ర్ెక్ోన్న్ెక్ట్ అయినప్పుడు, ున్డ్ెల్ివ్ర్ెడ్ సందేశాలు ఫ్ెట్చ్ చేసి *WebSocket* ద్వారా పంపబడతాయి
5. *Receipt* క్ోన్ఫ్ిర్మ్ చేయడానికి డెలివరీ ర్ెక్ెిప్ట్స్ తిరిగి పంపబడతాయి

## దశ 7: E2E ఎన్‌క్రిప్షన్ *Basics*

ఇంటర్వ్యూ చర్చలు లో E2E ెన్క్ర్య్ప్షన్ గురించి మెంట్ిోన్ చేయడం భద్రత అవ్ార్ెనెస్ చూపిస్తుంది:

- ప్రతి వినియోగదారు తమ పరికరం మీద **పబ్లిక్/ప్రైవేట్ కీ జంట** సృష్టించు చేస్తారు
- సందేశాలు స్ెన్డ్ర్ పరికరం నుండి బయటకు వెళ్ళే ముందు ర్ెక్ిప్ిెన్ట్ యొక్క పబ్లిక్ కీ తో ెన్క్ర్య్ప్ట్ అవుతాయి
- సర్వర్ కు క్ిఫ్ర్ట్ెక్స్ట్ మాత్రమే కనిపిస్తుంది - సందేశం కంటెంట్ చదవలేదు
- గుంపు చ్అట్స్ ఒక **పంచుకున్న గుంపు కీ** వాడతాయి, మ్ెమ్బ్ర్స్ జ్ోిన్ లేదా వదలండి అయినప్పుడు ర్ోట్అట్ె అవుతుంది

అంటే సర్వర్ యొక్క సందేశం నిల్వ లో ెన్క్ర్య్ప్ట్ెడ్ బ్ల్ోబ్స్ మాత్రమే ఉంటాయి, డేటా అనుసరణ దృష్ట్యా ఇది నిజంగా సులభమైన.

## ఇంటర్వ్యూ చిట్కాలు

1. **WebSocket నిర్ణయం తో ప్రారంభించండి చేయండి** - ఈ స్కేల్ వద్ద *HTTP* ప్ోల్ల్ింగ్ ఎందుకు పని కాదో వివరించండి చేయండి
2. **కనెక్షన్ సామర్థ్యం పరిమాణాత్మకంగా చెప్పండి చేయండి** - సర్వర్ పరిమితులు అర్థమయ్యాయని చూపించండి (~50-100K కనెక్షన్‌లు ప్రతి సర్వర్)
3. **ఆఫ్‌లైన్ డెలివరీ అడ్డ్ర్ెస్స్ చేయండి** - చాలా అభ్యర్థులు వినియోగదారులు ఎల్లప్పుడూ కలిసిన ఉండరని మరచిపోతారు
4. **సందేశం ర్డ్ర్ింగ్ మెంట్ిోన్ చేయండి** - ట్ిమ్ెస్ట్అమ్ప్-ఆధారిత ర్డ్ర్ింగ్ తో ఘర్షణ పరిష్కారం

*Slack* మరియు *WhatsApp* సందేశం చరిత్ర కోసం చాలా భిన్నమైన విధానాలు తీసుకుంటాయి. *WhatsApp* సందేశాలు ను పరికరం మీద నిల్వ చేస్తుంది మరియు కొత్త పరికరాలు కు పూర్తి చరిత్ర సమకాలీకరణ చేయదు. *Slack* అంతా సర్వర్-వైపు నిల్వ చేసి పూర్తి సెర్చ్ అందిస్తుంది. ప్రతి విధానం యొక్క గోప్యత, ఖర్చు, మరియు వినియోగదారు అనుభవం ట్రేడ్‌ఆఫ్‌లు ఏమిటి?

## కీ ముఖ్యాంశాలు

- చాట్ సిస్టమ్‌లు కు రియల్ టైమ్ ద్విదిశ కమ్యూనికేషన్ కోసం *WebSockets* అవసరం
- స్కేల్ వద్ద కనెక్షన్ నిర్వహణ కు వినియోగదారులు-కు-సర్వర్‌లు మ్యాపింగ్ రిజిస్ట్రీ అవసరం
