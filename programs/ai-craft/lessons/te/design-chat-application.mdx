## ఇంటర్వ్యూ ప్రాంప్ట్

*"WhatsApp లేదా Slack లాంటి చాట్ అప్లికేషన్ డిజైన్ చేయండి: ఒకరికి ఒకరు సందేశాలు, గ్రూప్ చాట్‌లు, ఆన్‌లైన్ ఉనికి సూచనలు కు మద్దతు ఉండాలి."*

వ్యవస్థ రూపకల్పన ఇంటర్వ్యూs లో ఇది చాలా ప్రాచుర్యం పొందిన ప్రశ్న, ఎందుకంటే ఒకే సమస్యలో తక్షణ కమ్యూనికేషన్, కనెక్షన్ నిర్వహణ, పెద్ద స్థాయి నిల్వ, విస్తరిత వ్యవస్థలు రాజీలు అన్నీ పరీక్షిస్తాయి.

## దశ 1: అవసరాలు సేకరణ

**కార్యాత్మక అవసరాలు:**
- డెలివరీ మరియు చదవడం రసీదులు తో ఒకటి-కు-ఒకటి messaging
- గుంపు చాట్ (500 సభ్యులు వరకు)
- ఆన్‌లైన్/ఆఫ్‌లైన్ ఉనికి సూచికలు
- సందేశం చరిత్ర మరియు సెర్చ్
- ఆఫ్‌లైన్ వినియోగదారులు కు పుష్ నోటిఫికేషన్‌లు

**అకార్యాత్మక అవసరాలు:**
- తక్కువ లేటెన్సీ: సందేశాలు 200ms లోపు చేరాలి
- అధిక అందుబాటు: 99.99% అందుబాటు సమయం
- ఒక సంభాషణ లో సందేశం క్రమం హామీ ఇచ్చిన
- 50 మిలియన్ సమకాలిక కనెక్షన్‌లు మద్దతు

<Callout>
అకార్యాత్మక అవసరాలు ను ఎల్లప్పుడూ స్పష్టంగా సంఖ్యలు తో లెక్కగా చెప్పండి చేయండి. "వేగంగా డెలివరీ" అస్పష్ట - "ఉప-200ms డెలివరీ" అంటే మీకు డొమైన్ అర్థమైందని చూపిస్తుంది.
</Callout>

## దశ 2: API డిజైన్

కేవలం REST సిస్టమ్‌లు కు భిన్నంగా, చాట్ కు **రెండు దిశల కమ్యూనికేషన్** అవసరం. మనకు రెండు ప్రోటోకాళ్లు కావాలి:

**REST API** (non-రియల్ టైమ్ ఆపరేషన్లు కోసం):
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket** (రియల్ టైమ్ messaging కోసం):
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## దశ 3: WebSocket కనెక్షన్ నిర్వహణ

ప్రతి కలిసిన వినియోగదారు ఒక persistent WebSocket కనెక్షన్ నిర్వహించండి చేస్తారు. 50 మిలియన్ సమకాలిక వినియోగదారులు వద్ద ఇది పెద్ద ఇంజినీరింగ్ సవాలు.

**కనెక్షన్ సర్వర్‌లు** (గేట్‌వే సర్వర్‌లు అని కూడా అంటారు) WebSocket కనెక్షన్‌లు ఉంచుతాయి. ప్రతి సర్వర్ సుమారు 50,000-100,000 సమకాలిక కనెక్షన్‌లు నిర్వహించగలదు, అంటే మనకు 500-1,000 కనెక్షన్ సర్వర్‌లు కావాలి.

ఒక **కనెక్షన్ రిజిస్ట్రీ** (Redis క్లస్టర్) ప్రతి వినియోగదారు ని వారి కనెక్షన్ సర్వర్ కు మ్యాప్ చేస్తుంది:
```
user_123 → ws-server-042
user_456 → ws-server-187
```

వినియోగదారు A, వినియోగదారు B కి సందేశం పంపినప్పుడు ప్రవాహం ఇలా ఉంటుంది:
1. సందేశం, A యొక్క కనెక్షన్ సర్వర్ కి WebSocket ద్వారా వస్తుంది
2. సర్వర్, Redis లో B యొక్క కనెక్షన్ సర్వర్ ను చూడండి up చేస్తుంది
3. సందేశం అంతర్గత messaging ద్వారా B యొక్క కనెక్షన్ సర్వర్ కు మార్గం అవుతుంది
4. B యొక్క సర్వర్, B యొక్క WebSocket లో సందేశం పుష్ చేస్తుంది

## దశ 4: సందేశం నిల్వ

చాట్ అప్లికేషన్‌లు చాలా పెద్ద పరిమాణంs లో డేటా సృష్టించు చేస్తాయి. WhatsApp రోజుకు 100 బిలియన్ కంటే ఎక్కువ సందేశాలు ప్రాసెస్ చేస్తుంది.

**నిల్వ వ్యూహం:**
- **ఇటీవలి సందేశాలు** - వేగంగా డేటా నిల్వ (Cassandra లేదా HBase) లో, సంభాషణ ID తో విభజించిన
- **సందేశం ఇండెక్స్** - Elasticశోధన ద్వారా సెర్చ్ సాధ్యం చేస్తుంది
- **మీడియా ఫైళ్లు** - ఆబ్జెక్ట్ నిల్వ (S3) లో CDN డెలివరీ తో

**స్కీమా డిజైన్ (Cassandra):**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

ఈ డిజైన్ వల్ల ఒక సంభాషణ లోని అన్ని సందేశాలు ఒకే పార్టిషన్ లో కలిసి ఉంచబడతాయి, "పాత సందేశాలు లోడ్ చేయి" క్వెరీలు చాలా సమర్థంగా ఉంటాయి - ఒకే పార్టిషన్ లో వరుస చదవడం.

## దశ 5: ఉనికి సిస్టమ్

ఎవరు ఆన్‌లైన్ లో ఉన్నారో చూపించడం సులభమైన గా అనిపిస్తుంది కానీ స్కేల్ వద్ద ఆశ్చర్యంగా కష్టమైన. మీ సంప్రదిస్తుంది జాబితా లోని ప్రతి వినియోగదారు కోసం ప్రతి కొన్ని సెకన్లు కు డేటాబేస్ అడుగు చేయడం సాధ్యం కాదు.

**హార్ట్‌బీట్ విధానం:**
1. కనెక్ట్ అయిన క్లయింట్లు ప్రతి 30 సెకన్లు కు WebSocket ద్వారా హార్ట్‌బీట్ పంపుతాయి
2. సర్వర్ ఒక Redis కీ ను 60 సెకన్లు TTL తో నవీకరిస్తుంది: `presence:user_123 → online (TTL 60s)`
3. హార్ట్‌బీట్ రాకపోతే కీ గడువు ముగియాలి అవుతుంది మరియు వినియోగదారు ఆఫ్‌లైన్ గా కనిపిస్తారు

**స్థితి నవీకరణలు కోసం విస్తృత పంపిణీ:**
ఒక వినియోగదారు ఆన్‌లైన్ వచ్చినప్పుడు, వారి స్థితి ఆన్‌లైన్ ఉన్న అన్ని పరిచయాలు కు పుష్ అవ్వాలి. 500 పరిచయాలు ఉన్న వినియోగదారు కోసం, ఏ పరిచయాలు ఆన్‌లైన్ లో ఉన్నారో తనిఖీ చేసి వారికి మాత్రమే ఉనికి నవీకరణలు పంపాలి - **మందగ విస్తృత పంపిణీ** ఆఫ్‌లైన్ వినియోగదారులు కు ప్రసారం చేయడం నివారిస్తుంది.

<FunFact>
WhatsApp యొక్క "చివరిసారి చూసిన సమయం" ఫీచర్ ప్రపంచవ్యాప్తంగా unఆశించిన సోషల్ drama కలిగించింది. కొన్ని దేశాల్లో సంబంధ వివాదాలు పెరిగాయి ఎందుకంటే భాగస్వాములు ఒకరినొకరి ఖచ్చితమైన చివరి క్రియాశీల సమయం సమయముద్రలు చూడగలిగారు. WhatsApp చివరకు ఈ సమాచారం దాచడానికి గోప్యత నియంత్రణలు జోడించు చేసింది.
</FunFact>

## దశ 6: పుష్ నోటిఫికేషన్‌లు

వినియోగదారు ఆఫ్‌లైన్ అయినప్పుడు (క్రియాశీల WebSocket లేదు), సందేశాలు పుష్ నోటిఫికేషన్‌లు ద్వారా చేరాలి.

సందేశం ప్రవాహం మారుతుంది:
1. కనెక్షన్ రిజిస్ట్రీ వినియోగదారు B ఆఫ్‌లైన్ అని చూపిస్తుంది
2. సందేశం డేటాబేస్ లో "పంపని" స్థితి తో నిల్వ అవుతుంది
3. నోటిఫికేషన్ సేవ APNs (iOS) లేదా FCM (Android) ద్వారా పుష్ పంపుతుంది
4. వినియోగదారు B మళ్లీ కనెక్ట్ అయినప్పుడు అయినప్పుడు, పంపని సందేశాలు తెచ్చుకోండి చేసి WebSocket ద్వారా పంపబడతాయి
5. రసీదు confirm చేయడానికి డెలివరీ రసీదులు తిరిగి పంపబడతాయి

<ThinkAboutIt>
500 సభ్యులు ఉన్న గుంపు చాట్‌లు లో విస్తృత పంపిణీ సవాలు ఉంటుంది. 400 సభ్యులు ఆఫ్‌లైన్ ఉన్న గుంపు కు సందేశం పంపితే, 400 పుష్ నోటిఫికేషన్‌లు పంపాలి. పీక్ గంటలు లో నోటిఫికేషన్ సేవలు ను ముంచెత్తవచ్చు చేయకుండా వీటిని ఎలా బ్యాచ్ మరియు రేట్-పరిమితి చేస్తారు?
</ThinkAboutIt>

## దశ 7: E2E గుప్తీకరణ మౌలికాలు

ఇంటర్వ్యూ చర్చలు లో E2E గుప్తీకరణ గురించి చెప్పడం భద్రత అవగాహన చూపిస్తుంది:

- ప్రతి వినియోగదారు తమ పరికరం మీద **పబ్లిక్/ప్రైవేట్ కీ pair** సృష్టించు చేస్తారు
- సందేశాలు పంపినవారు పరికరం నుండి బయటకు వెళ్ళే ముందు స్వీకర్త యొక్క పబ్లిక్ కీ తో గుప్తీకరించు అవుతాయి
- సర్వర్ కు ciphertext మాత్రమే కనిపిస్తుంది - సందేశం కంటెంట్ చదవలేదు
- గుంపు చాట్‌లు ఒక **పంచుకున్న గుంపు కీ** వాడతాయి, సభ్యులు చేరినప్పుడు లేదా వెళ్లినప్పుడు అయినప్పుడు మార్చండి అవుతుంది

అంటే సర్వర్ యొక్క సందేశం నిల్వ లో గుప్తీకరించిన బ్లాబ్‌లు మాత్రమే ఉంటాయి, డేటా అనుసరణ దృష్ట్యా ఇది నిజంగా సరళమైన.

## దశ 8: మిలియన్లు కు స్కేల్ చేయడం

**కీ స్కేలింగ్ వ్యూహాలు:**
- **కనెక్షన్ సర్వర్‌లు** అడ్డంగా స్కేల్ అవుతాయి - వినియోగదారులు పెరిగేకొద్దీ సర్వర్‌లు జోడించండి

- **డేటాబేస్ షార్డింగ్** సంభాషణ ID ద్వారా నిల్వ లోడ్ విస్తరించండి చేస్తుంది
- **భౌగోళిక వితరణ** - లేటెన్సీ తగ్గించడానికి అనేక ప్రాంతాలు లో కనెక్షన్ సర్వర్‌లు డిప్లాయ్ చేయండి

## ఇంటర్వ్యూ Tips

1. **WebSocket నిర్ణయం తో ప్రారంభించండి** - ఈ స్కేల్ వద్ద HTTP పోలింగ్ ఎందుకు పని కాదో వివరించండి
2. **కనెక్షన్ సామర్థ్యం లెక్కగా చెప్పండి చేయండి** - సర్వర్ పరిమితులు అర్థమయ్యాయని చూపించండి (~50-100K కనెక్షన్‌లు ప్రతి సర్వర్)
3. **ఆఫ్‌లైన్ డెలివరీ పరిష్కరించండి** - చాలా అభ్యర్థులు వినియోగదారులు ఎల్లప్పుడూ కలిసే ఉండరని మరచిపోతారు
4. **సందేశం క్రమం చెప్పండి చేయండి** - సమయముద్ర ఆధారిత ఆధారిత క్రమం తో ఘర్షణ పరిష్కారం
