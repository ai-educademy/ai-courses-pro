## ఇంటర్వ్యూ ప్రాంప్ట్

*"WhatsApp లేదా Slack లాంటి chat application డిజైన్ చేయండి: one-to-one messaging, group chats, online presence indicators కు మద్దతు ఉండాలి."*

System design interviews లో ఇది చాలా ప్రాచుర్యం పొందిన ప్రశ్న, ఎందుకంటే ఒకే సమస్యలో తక్షణ కమ్యూనికేషన్, connection management, పెద్ద స్థాయి storage, distributed systems trade-offs అన్నీ పరీక్షిస్తాయి.

## దశ 1: అవసరాలు Gathering

**Functional అవసరాలు:**
- డెలివరీ మరియు చదవడం receipts తో ఒకటి-కు-ఒకటి messaging
- గుంపు చాట్ (500 members వరకు)
- ఆన్‌లైన్/offline ఉనికి indicators
- సందేశం చరిత్ర మరియు సెర్చ్
- Offline వినియోగదారులు కు పుష్ నోటిఫికేషన్‌లు

**Non-functional అవసరాలు:**
- Low లేటెన్సీ: సందేశాలు 200ms లోపు deliver అవ్వాలి
- అధిక అందుబాటు: 99.99% uptime
- ఒక conversation లో సందేశం ordering guaranteed
- 50 మిలియన్ సమకాలిక కనెక్షన్‌లు మద్దతు

<Callout>
Non-functional అవసరాలు ను ఎల్లప్పుడూ స్పష్టంగా సంఖ్యలు తో quantify చేయండి. "వేగంగా డెలివరీ" vague - "ఉప-200ms డెలివరీ" అంటే మీకు డొమైన్ అర్థమైందని చూపిస్తుంది.
</Callout>

## దశ 2: API డిజైన్

REST-only సిస్టమ్‌లు కు భిన్నంగా, చాట్ కు **bidirectional కమ్యూనికేషన్** అవసరం. మనకు రెండు protocols కావాలి:

**REST API** (non-రియల్ టైమ్ ఆపరేషన్లు కోసం):
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket** (రియల్ టైమ్ messaging కోసం):
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## దశ 3: WebSocket కనెక్షన్ నిర్వహణ

ప్రతి కలిసిన వినియోగదారు ఒక persistent WebSocket కనెక్షన్ నిర్వహించండి చేస్తారు. 50 మిలియన్ సమకాలిక వినియోగదారులు వద్ద ఇది పెద్ద ఇంజినీరింగ్ సవాలు.

**కనెక్షన్ సర్వర్‌లు** (గేట్‌వే సర్వర్‌లు అని కూడా అంటారు) WebSocket కనెక్షన్‌లు hold చేస్తాయి. ప్రతి సర్వర్ సుమారు 50,000-100,000 సమకాలిక కనెక్షన్‌లు నిర్వహించు చేయగలదు, అంటే మనకు 500-1,000 కనెక్షన్ సర్వర్‌లు కావాలి.

ఒక **కనెక్షన్ రిజిస్ట్రీ** (Redis క్లస్టర్) ప్రతి వినియోగదారు ని వారి కనెక్షన్ సర్వర్ కు మ్యాప్ చేస్తుంది:
```
user_123 → ws-server-042
user_456 → ws-server-187
```

వినియోగదారు A, వినియోగదారు B కి సందేశం పంపినప్పుడు ప్రవాహం ఇలా ఉంటుంది:
1. సందేశం, A యొక్క కనెక్షన్ సర్వర్ కి WebSocket ద్వారా వస్తుంది
2. సర్వర్, Redis లో B యొక్క కనెక్షన్ సర్వర్ ను look up చేస్తుంది
3. సందేశం అంతర్గత messaging ద్వారా B యొక్క కనెక్షన్ సర్వర్ కు మార్గం అవుతుంది
4. B యొక్క సర్వర్, B యొక్క WebSocket లో సందేశం పుష్ చేస్తుంది

## దశ 4: సందేశం నిల్వ

చాట్ అప్లికేషన్‌లు చాలా పెద్ద volumes లో డేటా సృష్టించు చేస్తాయి. WhatsApp రోజుకు 100 బిలియన్ కంటే ఎక్కువ సందేశాలు ప్రక్రియ చేస్తుంది.

**నిల్వ వ్యూహం:**
- **ఇటీవలి సందేశాలు** - వేగంగా datastore (Cassandra లేదా HBase) లో, conversation ID తో partitioned
- **సందేశం ఇండెక్స్** - Elasticsearch ద్వారా సెర్చ్ enable చేస్తుంది
- **మీడియా files** - object నిల్వ (S3) లో CDN డెలివరీ తో

**స్కీమా డిజైన్ (Cassandra):**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

ఈ డిజైన్ వల్ల ఒక conversation లోని అన్ని సందేశాలు ఒకే పార్టిషన్ లో co-located అవుతాయి, "పాత సందేశాలు లోడ్ చేయి" క్వెరీలు చాలా efficient అవుతాయి - ఒకే పార్టిషన్ లో sequential చదవడం.

## దశ 5: ఉనికి సిస్టమ్

ఎవరు ఆన్‌లైన్ లో ఉన్నారో చూపించడం సులభమైన గా అనిపిస్తుంది కానీ స్కేల్ వద్ద surprisingly tricky. మీ సంప్రదిస్తుంది జాబితా లోని ప్రతి వినియోగదారు కోసం ప్రతి కొన్ని సెకన్లు కు డేటాబేస్ poll చేయడం సాధ్యం కాదు.

**Heartbeat విధానం:**
1. కలిసిన clients ప్రతి 30 సెకన్లు కు WebSocket ద్వారా heartbeat పంపుతాయి
2. సర్వర్ ఒక Redis కీ ను 60 సెకన్లు TTL తో నవీకరించు చేస్తుంది: `presence:user_123 → online (TTL 60s)`
3. Heartbeat రాకపోతే కీ గడువు ముగియాలి అవుతుంది మరియు వినియోగదారు offline గా కనిపిస్తారు

**స్థితి నవీకరణలు కోసం fan-out:**
ఒక వినియోగదారు ఆన్‌లైన్ వచ్చినప్పుడు, వారి స్థితి ఆన్‌లైన్ ఉన్న అన్ని contacts కు పుష్ అవ్వాలి. 500 contacts ఉన్న వినియోగదారు కోసం, ఏ contacts ఆన్‌లైన్ లో ఉన్నారో తనిఖీ చేసి వారికి మాత్రమే ఉనికి నవీకరణలు పంపాలి - **lazy fan-out** offline వినియోగదారులు కు broadcast చేయడం నివారిస్తుంది.

<FunFact>
WhatsApp యొక్క "last seen" ఫీచర్ ప్రపంచవ్యాప్తంగా unexpected సోషల్ drama కలిగించింది. కొన్ని దేశాల్లో relationship disputes పెరిగాయి ఎందుకంటే partners ఒకరినొకరి ఖచ్చితమైన last-active timestamps చూడగలిగారు. WhatsApp చివరకు ఈ సమాచారం దాచడానికి గోప్యత controls జోడించు చేసింది.
</FunFact>

## దశ 6: పుష్ నోటిఫికేషన్‌లు

వినియోగదారు offline అయినప్పుడు (active WebSocket లేదు), సందేశాలు పుష్ నోటిఫికేషన్‌లు ద్వారా చేరాలి.

సందేశం ప్రవాహం మారుతుంది:
1. కనెక్షన్ రిజిస్ట్రీ వినియోగదారు B offline అని చూపిస్తుంది
2. సందేశం డేటాబేస్ లో "undelivered" స్థితి తో నిల్వ అవుతుంది
3. నోటిఫికేషన్ సేవ APNs (iOS) లేదా FCM (Android) ద్వారా పుష్ పంపుతుంది
4. వినియోగదారు B reconnect అయినప్పుడు, undelivered సందేశాలు fetch చేసి WebSocket ద్వారా పంపబడతాయి
5. Receipt confirm చేయడానికి డెలివరీ receipts తిరిగి పంపబడతాయి

<ThinkAboutIt>
500 members ఉన్న గుంపు chats లో fan-out సవాలు ఉంటుంది. 400 members offline ఉన్న గుంపు కు సందేశం పంపితే, 400 పుష్ నోటిఫికేషన్‌లు పంపాలి. పీక్ గంటలు లో నోటిఫికేషన్ సేవలు ను overwhelm చేయకుండా వీటిని ఎలా బ్యాచ్ మరియు రేట్-పరిమితి చేస్తారు?
</ThinkAboutIt>

## దశ 7: E2E Encryption Basics

ఇంటర్వ్యూ చర్చలు లో E2E encryption గురించి mention చేయడం భద్రత awareness చూపిస్తుంది:

- ప్రతి వినియోగదారు తమ device మీద **పబ్లిక్/ప్రైవేట్ కీ pair** సృష్టించు చేస్తారు
- సందేశాలు sender device నుండి బయటకు వెళ్ళే ముందు recipient యొక్క పబ్లిక్ కీ తో encrypt అవుతాయి
- సర్వర్ కు ciphertext మాత్రమే కనిపిస్తుంది - సందేశం కంటెంట్ చదవలేదు
- గుంపు chats ఒక **పంచుకున్న గుంపు కీ** వాడతాయి, members join లేదా leave అయినప్పుడు rotate అవుతుంది

అంటే సర్వర్ యొక్క సందేశం నిల్వ లో encrypted blobs మాత్రమే ఉంటాయి, డేటా అనుసరణ దృష్ట్యా ఇది నిజంగా simpler.

## దశ 8: మిలియన్లు కు స్కేల్ చేయడం

**కీ స్కేలింగ్ వ్యూహాలు:**
- **కనెక్షన్ సర్వర్‌లు** horizontally స్కేల్ అవుతాయి - వినియోగదారులు పెరిగేకొద్దీ సర్వర్‌లు జోడించు చేయండి
- **సందేశం రూటింగ్** inter-సర్వర్ కమ్యూనికేషన్ కోసం Kafka లేదా Redis Pub/ఉప వాడుతుంది
- **డేటాబేస్ షార్డింగ్** conversation ID ద్వారా నిల్వ లోడ్ విస్తరించండి చేస్తుంది
- **Geographic వితరణ** - లేటెన్సీ తగ్గించడానికి అనేక regions లో కనెక్షన్ సర్వర్‌లు డిప్లాయ్ చేయండి చేయండి
- **సందేశం క్యూ buffering** - పీక్ వినియోగం గంటలు లో spikes absorb చేస్తుంది

## ఇంటర్వ్యూ Tips

1. **WebSocket నిర్ణయం తో ప్రారంభించండి చేయండి** - ఈ స్కేల్ వద్ద HTTP polling ఎందుకు పని కాదో explain చేయండి
2. **కనెక్షన్ capacity quantify చేయండి** - సర్వర్ పరిమితులు అర్థమయ్యాయని చూపించండి (~50-100K కనెక్షన్‌లు ప్రతి సర్వర్)
3. **Offline డెలివరీ address చేయండి** - చాలా అభ్యర్థులు వినియోగదారులు ఎల్లప్పుడూ కలిసిన ఉండరని మరచిపోతారు
4. **సందేశం ordering mention చేయండి** - timestamp-ఆధారిత ordering తో ఘర్షణ resolution
