# విస్తరిత క్యాష్ డిజైన్ చేయండి - Redis ఆర్కిటెక్చర్ మొదటి నుంచి

సిస్టమ్ పనితీరు మెరుగుపరచడానికి క్యాషింగ్ అత్యంత ప్రభావవంతమైన పద్ధతి. బాగా డిజైన్ చేసిన విస్తరిత క్యాష్, డేటాబేస్ భారం ను 90% కంటే ఎక్కువ తగ్గించగలదు. స్పందన సమయాలు ను వందల మిల్లీసెకన్లు నుంచి మిల్లీసెకనుకంటే తక్కువ స్థాయికి తీసుకురాగలదు.

## దశ 1 - అవసరాలు సేకరణ

### కార్యాత్మక అవసరాలు
- ఐచ్చిక TTL (జీవనకాలం) తో కీ-విలువ జంటలు నిల్వ చేయడం
- సాధారణ కార్యాచరణలు కు మద్దతు ఇవ్వడం: GET, SET, DELETE, గుంపు కార్యకలాపాలు
- అడ్డ స్కేలింగ్ కోసం డేటాను అనేక నోడ్‌లు లో విస్తరించడం

### అకార్యాత్మక అవసరాలు
- **తక్కువ లేటెన్సీ** - క్యాష్ హిట్‌లు కోసం ఉప-మిల్లీసెకన్ రీడ్‌లు
- **అధిక థ్రూపుట్** - ప్రతి నోడ్ కు 100K+ ఆపరేషన్లు ప్రతి సెకండ్
- **అధిక అందుబాటు** - క్యాష్ వైఫల్యాలు వల్ల సిస్టమ్ down కాకూడదు
- **స్కేల్ సామర్థ్యం** - downtime లేకుండా నోడ్‌లు జోడించడం

### ఎప్పుడు క్యాష్ చేయాలి
- **చదవడం-భారీ పనిభారాలు** - రీడ్‌లు, రైట్‌లు కంటే చాలా ఎక్కువగా ఉన్నప్పుడు
- **Expensive computations** - ML మోడల్ ఇన్‌ఫరెన్స్ ఫలితాలు, క్లిష్టమైన సమీకరణs
- **తరచుగా ప్రాప్తించే డేటా** - వినియోగదారు సెషన్‌లు, ప్రోడక్ట్ క్యాటలాగ్‌లు, కాన్ఫిగరేషన్

## దశ 2 - క్యాషింగ్ వ్యూహాలు

### క్యాష్-పక్కన విధానం (మందగ లోడింగ్)
అత్యంత సాధారణ నమూనా. అప్లికేషన్ ముందుగా క్యాష్ తనిఖీ చేస్తుంది; మిస్ అవడం అయితే డేటాబేస్ నుండి చదవడం చేసి, ఆ తర్వాత క్యాష్ నింపండి చేస్తుంది:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**ప్రయోజనాలు:** నిజంగా రిక్వెస్ట్ చేసినదే క్యాష్ అవుతుంది. **అప్రయోజనాలు:** క్యాష్ మిస్‌లు వల్ల లేటెన్సీ పెరుగుతుంది; డేటా పాతది కాగలదు.

### చదవడం-ద్వారా
మిస్ అవడం అయినప్పుడు క్యాష్ స్వయంగా డేటాబేస్ రీడ్‌లు నిర్వహించు చేస్తుంది. అప్లికేషన్ క్యాష్ పొర తో మాత్రమే కమ్యూనికేట్ చేస్తుంది, ఇది డేటా సోర్స్ ను abstract చేస్తుంది.

### రైట్-త్రూ
ప్రతి రాత క్యాష్ మరియు డేటాబేస్ రెండింటికీ సమకాలికంగా వెళ్తుంది. క్యాష్ ఎల్లప్పుడూ స్థిరంగా ఉంటుంది కానీ రాత లేటెన్సీ పెరుగుతుంది.

### రాయండి-తర్వాత రాయడం (రాయండి-వెనుక)
రైట్‌లు వెంటనే క్యాష్ లోకి వెళ్తాయి; క్యాష్ అసమకాలికంగా బ్యాచ్‌లు లో డేటాబేస్ కు ఫ్లష్ చేస్తుంది. రాత లేటెన్సీ తక్కువ కానీ ఫ్లష్ చేయకముందే క్యాష్ నోడ్ కూలిపోవడం అయితే డేటా నష్టం రిస్క్ ఉంటుంది.

| వ్యూహం | స్థిరత్వం | చదవడం లేటెన్సీ | రాత లేటెన్సీ | వాడండి సందర్భం |
|----------|-------------|-------------|---------------|----------|
| క్యాష్-పక్కన విధానం | చివరికి వచ్చే | మిస్ అవడం జరిమానా | N/A | సాధారణ ఉద్దేశం |
| చదవడం-ద్వారా | చివరికి వచ్చే | మిస్ అవడం జరిమానా | N/A | సరళీకృత రీడ్‌లు |

## దశ 3 - తొలగింపు Policies

క్యాష్ నిండినప్పుడు, ఏ నమోదులు తొలగించాలి?

- **LRU (Least Recently Used)** - చాలా కాలంగా యాక్సెస్ కాని నమోదు ను తొలగిస్తుంది. అత్యుత్తమ సాధారణ ప్రయోజన విధానం
- **LFU (Least Frequently Used)** - అతి తక్కువసార్లు యాక్సెస్ అయిన నమోదు ను తొలగిస్తుంది. వంగిన యాక్సెస్ నమూనాలు కు మెరుగైనది
- **TTL-ఆధారిత** - యాక్సెస్ తో సంబంధం లేకుండా నమోదులు నిర్ధారిత సమయం తర్వాత గడువు ముగియాలి అవుతాయి. డేటా తాజాదనం కు అవసరం
- **యాదృచ్ఛిక** - ఆశ్చర్యకరంగా ప్రభావవంతం మరియు అమలు చేయండి చేయడానికి చాలా సరళం

<FunFact>Redis ఒక సుమారు అంచనా వేసిన LRU అల్గారిథమ్ వాడుతుంది, ఇది కొన్ని కీలు ను నమూనా చేసి (డిఫాల్ట్: 5) వాటిలో ఇటీవల అతి తక్కువగా వాడినది ను తొలగిస్తుంది. ఇది నిజమైన LRU అంత ఖచ్చితంగా ఉంటుంది కానీ యాక్సెస్ క్రమం ట్రాక్ చేయడానికి అదనపు మెమరీ భారం లేకుండా అవసరం.</FunFact>

## దశ 4 - వితరణ కోసం స్థిరమైన హ్యాషింగ్

### సులభమైన హ్యాషింగ్ సమస్య
`hash(key) % N` నోడ్‌లు తో, ఒక నోడ్ జోడించు లేదా తొలగించండి చేస్తే దాదాపు అన్ని కీలు మళ్లీ మ్యాప్ అవుతాయి, ఇది భారీ క్యాష్ మిస్ అవడం తుఫాను కు కారణమవుతుంది.

### Virtual నోడ్‌లు తో స్థిరమైన హ్యాషింగ్
స్థిరమైన హ్యాషింగ్ కీలు మరియు నోడ్‌లు రెండింటినీ ఒక వలయం పై మ్యాప్ చేస్తుంది. ప్రతి కీ వలయం పై తదుపరి గడియార దిశలో నోడ్ కు కేటాయించు అవుతుంది:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**Virtual నోడ్‌లు** అసమాన వితరణ సమస్యను పరిష్కరిస్తాయి. ప్రతి భౌతిక నోడ్ కు వలయం పై అనేక స్థానాలు ఉంటాయి, తక్కువ భౌతిక నోడ్‌లు ఉన్నప్పటికీ సమతుల్య లోడ్ నిర్ధారిస్తాయి.

ఒక నోడ్ జోడించు లేదా తొలగించండి అయినప్పుడు, వలయం పై దాని పక్కనున్న కీలు మాత్రమే మళ్లీ మ్యాప్ అవుతాయి - దాదాపు `K/N` కీలు (ఇక్కడ K మొత్తం కీలు మరియు N నోడ్ లెక్క), అన్నీ కాదు.

## దశ 5 - క్యాష్ తొక్కిసలాట నివారణ

ఒక ప్రజాదరణ పొందిన క్యాష్ చేసిన నమోదు గడువు ముగియాలి అయినప్పుడు వందల సమకాలిక రిక్వెస్ట్‌లు ఏకకాలంలో క్యాష్ మిస్ అవడం అయి డేటాబేస్ ను హిట్ చేస్తాయి చేస్తే **క్యాష్ stampede** జరుగుతుంది.

### పరిష్కారాలు

**Mutex/Locking:** క్యాష్ మిస్ అవడం అయినప్పుడు విస్తరిత లాక్ పొందండి చేయండి. ఒకే రిక్వెస్ట్ డేటాబేస్ నుండి తెచ్చుకోండి చేస్తుంది; మిగతావి క్యాష్ మళ్లీ నింపండి అయ్యేవరకు వేచి ఉంటాయి.

**Probabilistic Early Expiry:** ప్రతి రిక్వెస్ట్ కు TTL నిజంగా గడువు ముగియాలి కాకముందే క్యాష్ తాజా పరచడం చేసే చిన్న యాదృచ్ఛిక అవకాశం ఉంటుంది. ఇది గడువు సమయంలో ఒక్కసారిగా దూసుకొచ్చే గుంపు సృష్టించడానికి బదులుగా తాజా పరచడం లోడ్ ను సమయంలో పంపిణీ చేస్తుంది.

**నేపథ్యం నేపథ్య తాజాకరణ:** ఒక నేపథ్యం ప్రక్రియ ప్రజాదరణ పొందిన క్యాష్ నమోదులు ను గడువు ముగియాలి కాకముందే తాజా పరచడం చేస్తుంది. వేడిగా ఉన్న కీలు కోసం క్యాష్ ఎప్పటికీ ఖాళీ కాదు.

<ThinkAboutIt>ఒక ఒక్కసారిగా జరిగే అమ్మకం ను ఊహించండి, ఒక ప్రోడక్ట్ పేజీ కు 100,000 రిక్వెస్ట్‌లు ప్రతి సెకండ్ వస్తున్నాయి. ప్రోడక్ట్ వివరాలు క్యాష్ నమోదు గడువు ముగియాలి అవుతుంది. Stampede నివారణ లేకుండా, 100K రిక్వెస్ట్‌లు అన్నీ ఒకేసారి డేటాబేస్ ను హిట్ చేస్తాయి చేస్తాయి. మీరు ఏ నివారణ వ్యూహం ఎంచుకుంటారు, ఎందుకు?</ThinkAboutIt>

## దశ 6 - Redis క్లస్టర్ ఆర్కిటెక్చర్

Redis క్లస్టర్ అత్యంత విస్తృతంగా డిప్లాయ్ చేయండి చేయబడిన విస్తరిత క్యాష్:

- **16,384 హ్యాష్ slots** మాస్టర్స్ నోడ్‌లు లో విస్తరించండి అవుతాయి
- ప్రతి కీ `CRC16(key) % 16384` ద్వారా slot కు మ్యాప్ అవుతుంది
- **ప్రతిరూపణ:** ప్రతి మాస్టర్స్ కు వైఫల్య మార్పిడి కోసం ఒకటి లేదా అంతకంటే ఎక్కువ ప్రతిరూపాలు ఉంటాయి
- **Automatic వైఫల్య మార్పిడి:** మాస్టర్స్ విఫలమైతే, ప్రతిరూపం సెకన్లు లో పైకి తీసుకురండి అవుతుంది

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### కీ మెట్రిక్స్ Monitor చేయడం
- **హిట్ చేస్తాయి నిష్పత్తి** - లక్ష్య 95%+; 80% కంటే తక్కువ క్యాషింగ్ సమస్య ను సూచిస్తుంది
- **మెమరీ వినియోగం** - తొలగింపులు నివారించడానికి 80% కంటే తక్కువగా ఉంచండి
- **తొలగింపు రేట్** - ఎక్కువ తొలగింపులు అంటే క్యాష్ తగినంత చిన్నది
- **లేటెన్సీ శతకాలు** - క్యాష్ హిట్‌లు కోసం p99 1ms కంటే తక్కువగా ఉండాలి

## దశ 7 - నిజమైన-ప్రపంచం క్యాషింగ్ నమూనాలు

| నమూనా | Implementation | TTL |
|---------|---------------|-----|
| Session నిల్వ | `SET session:{id} {data}` | 30 నిమిషాలు |
| API రెస్పాన్స్ క్యాష్ | `SET api:/users/123 {json}` | 5 నిమిషాలు |
| డేటాబేస్ క్వెరీ క్యాష్ | `SET query:{hash} {result}` | 1 నిమిషం |
| రేట్ లిమిటర్ కౌంటర్ | `INCR ratelimit:{user}:{window}` | విండో వ్యవధి |
| ఫీచర్ fఆలస్యాలతో | `HSET features {flag} {value}` | 10 సెకన్లు |

### క్యాష్ Invalidation
కంప్యూటర్ సైన్స్ లో అత్యంత కఠినమైన సమస్య (పేర్లు పెట్టడం తో పాటు):
- **TTL-ఆధారిత** - సరళం, TTL వ్యవధి పాటు పాతదిness ను సహిస్తుంది
- **ఈవెంట్-ఆధారిత** - డేటా మారినప్పుడు చెల్లుబాటు రద్దు ఈవెంట్లు ప్రచురించండి చేయండి (Kafka లేదా Redis ప్రచురణ/ఉప ద్వారా)
- **వెర్షన్-ఆధారిత** - క్యాష్ కీ లో వెర్షన్ చేర్చండి; రైట్‌లు లో వెర్షన్ పెంచండి, పాత నమోదులు ప్రభావవంతంగా చెల్లనివిగా చేయడం అవుతాయి
