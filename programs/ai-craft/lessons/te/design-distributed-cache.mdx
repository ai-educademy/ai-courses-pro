# విస్తరిత క్యాష్ డిజైన్ చేయండి - Redis ఆర్కిటెక్చర్ మొదటి నుంచి

సిస్టమ్ పనితీరు మెరుగుపరచడానికి క్యాషింగ్ అత్యంత ప్రభావవంతమైన టెక్నిక్. బాగా డిజైన్ చేసిన విస్తరిత క్యాష్ డేటాబేస్ లోడ్ ను 90%+ తగ్గించగలదు మరియు రెస్పాన్స్ సార్లు ను వందల milliseconds నుండి ఉప-millisecond కు తీసుకురాగలదు.

## దశ 1 - అవసరాలు సేకరణ

### Functional అవసరాలు
- ఐచ్చిక TTL (సమయం-కు-ప్రత్యక్ష) తో కీ-విలువ pairs నిల్వ చేయడం
- సాధారణ ఆపరేషన్లు మద్దతు చేయడం: GET, సెట్, DELETE, మరియు bulk ఆపరేషన్లు
- Horizontal స్కేలింగ్ కోసం డేటా ను అనేక నోడ్‌లు లో విస్తరించండి చేయడం

### Non-Functional అవసరాలు
- **Low లేటెన్సీ** - క్యాష్ hits కోసం ఉప-millisecond రీడ్‌లు
- **అధిక థ్రూపుట్** - ప్రతి నోడ్ కు 100K+ ఆపరేషన్లు ప్రతి సెకండ్
- **అధిక అందుబాటు** - క్యాష్ failures వల్ల సిస్టమ్ down కాకూడదు
- **Scalability** - downtime లేకుండా నోడ్‌లు జోడించు చేయడం

### ఎప్పుడు క్యాష్ చేయాలి
- **చదవడం-భారీ workloads** - రీడ్‌లు, రైట్‌లు కంటే చాలా ఎక్కువగా ఉన్నప్పుడు
- **Expensive computations** - ML మోడల్ ఇన్‌ఫరెన్స్ ఫలితాలు, క్లిష్టమైన aggregations
- **Frequently accessed డేటా** - వినియోగదారు sessions, ప్రోడక్ట్ catalogues, configuration

## దశ 2 - క్యాషింగ్ వ్యూహాలు

### క్యాష్-Aside (Lazy Loading)
అత్యంత సాధారణ నమూనా. అప్లికేషన్ ముందుగా క్యాష్ తనిఖీ చేస్తుంది; మిస్ అవడం అయితే డేటాబేస్ నుండి చదవడం చేసి, ఆ తర్వాత క్యాష్ populate చేస్తుంది:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**ప్రయోజనాలు:** నిజంగా రిక్వెస్ట్ చేసినదే క్యాష్ అవుతుంది. **అప్రయోజనాలు:** క్యాష్ misses వల్ల లేటెన్సీ పెరుగుతుంది; డేటా stale కాగలదు.

### చదవడం-ద్వారా
మిస్ అవడం అయినప్పుడు క్యాష్ స్వయంగా డేటాబేస్ రీడ్‌లు నిర్వహించు చేస్తుంది. అప్లికేషన్ క్యాష్ పొర తో మాత్రమే కమ్యూనికేట్ చేయండి చేస్తుంది, ఇది డేటా సోర్స్ ను abstract చేస్తుంది.

### రాయండి-ద్వారా
ప్రతి రాయండి క్యాష్ మరియు డేటాబేస్ రెండింటికీ synchronously వెళ్తుంది. క్యాష్ ఎల్లప్పుడూ స్థిరమైన గా ఉంటుంది కానీ రాయండి లేటెన్సీ పెరుగుతుంది.

### రాయండి-Behind (రాయండి-Back)
రైట్‌లు వెంటనే క్యాష్ లోకి వెళ్తాయి; క్యాష్ asynchronously బ్యాచ్‌లు లో డేటాబేస్ కు flush చేస్తుంది. రాయండి లేటెన్సీ తక్కువ కానీ flush చేయకముందే క్యాష్ నోడ్ crash అయితే డేటా loss రిస్క్ ఉంటుంది.

| వ్యూహం | స్థిరత్వం | చదవడం లేటెన్సీ | రాయండి లేటెన్సీ | వాడండి సందర్భం |
|----------|-------------|-------------|---------------|----------|
| క్యాష్-Aside | చివరికి వచ్చే | మిస్ అవడం penalty | N/A | సాధారణ purpose |
| చదవడం-ద్వారా | చివరికి వచ్చే | మిస్ అవడం penalty | N/A | Simplified రీడ్‌లు |
| రాయండి-ద్వారా | బలమైన | వేగంగా | Slower | స్థిరత్వం-కీలకమైన |
| రాయండి-Behind | చివరికి వచ్చే | వేగంగా | వేగంగా | రాయండి-భారీ workloads |

## దశ 3 - తొలగింపు Policies

క్యాష్ నిండినప్పుడు, ఏ entries తొలగించాలి?

- **LRU (Least Recently Used)** - చాలా కాలంగా యాక్సెస్ కాని entry ను evict చేస్తుంది. అత్యుత్తమ సాధారణ-purpose policy
- **LFU (Least Frequently Used)** - అతి తక్కువసార్లు యాక్సెస్ అయిన entry ను evict చేస్తుంది. Skewed యాక్సెస్ నమూనాలు కు మెరుగైనది
- **TTL-ఆధారిత** - యాక్సెస్ తో సంబంధం లేకుండా entries నిర్ధారిత సమయం తర్వాత గడువు ముగియాలి అవుతాయి. డేటా freshness కు అవసరం
- **Random** - ఆశ్చర్యకరంగా ప్రభావవంతం మరియు అమలు చేయండి చేయడానికి చాలా సరళం

<FunFact>Redis ఒక approximated LRU అల్గారిథమ్ వాడుతుంది, ఇది కొన్ని కీలు ను sample చేసి (డిఫాల్ట్: 5) వాటిలో least recently used ను evict చేస్తుంది. ఇది true LRU అంత ఖచ్చితమైన గా ఉంటుంది కానీ యాక్సెస్ క్రమం ట్రాక్ చేయడానికి zero additional మెమరీ overhead అవసరం.</FunFact>

## దశ 4 - వితరణ కోసం స్థిరమైన హ్యాషింగ్

### సులభమైన హ్యాషింగ్ సమస్య
`hash(key) % N` నోడ్‌లు తో, ఒక నోడ్ జోడించు లేదా తొలగించండి చేస్తే దాదాపు అన్ని కీలు remap అవుతాయి, ఇది massive క్యాష్ మిస్ అవడం storm కు కారణమవుతుంది.

### Virtual నోడ్‌లు తో స్థిరమైన హ్యాషింగ్
స్థిరమైన హ్యాషింగ్ కీలు మరియు నోడ్‌లు రెండింటినీ ఒక ring పై మ్యాప్ చేస్తుంది. ప్రతి కీ ring పై తదుపరి clockwise నోడ్ కు assign అవుతుంది:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**Virtual నోడ్‌లు** అసమాన వితరణ సమస్యను పరిష్కరిస్తాయి. ప్రతి భౌతిక నోడ్ కు ring పై అనేక positions ఉంటాయి, తక్కువ భౌతిక నోడ్‌లు ఉన్నప్పటికీ balanced లోడ్ నిర్ధారిస్తాయి.

ఒక నోడ్ జోడించు లేదా తొలగించండి అయినప్పుడు, ring పై దాని adjacent కీలు మాత్రమే remap అవుతాయి - దాదాపు `K/N` కీలు (ఇక్కడ K మొత్తం కీలు మరియు N నోడ్ లెక్క), అన్నీ కాదు.

## దశ 5 - క్యాష్ Stampede Prevention

ఒక ప్రజాదరణ పొందిన cached entry గడువు ముగియాలి అయినప్పుడు వందల సమకాలిక రిక్వెస్ట్‌లు ఏకకాలంలో క్యాష్ మిస్ అవడం అయి డేటాబేస్ ను హిట్ చేస్తాయి చేస్తే **క్యాష్ stampede** జరుగుతుంది.

### పరిష్కారాలు

**Mutex/Locking:** క్యాష్ మిస్ అవడం అయినప్పుడు విస్తరిత lock acquire చేయండి. ఒకే రిక్వెస్ట్ డేటాబేస్ నుండి fetch చేస్తుంది; మిగతావి క్యాష్ repopulate అయ్యేవరకు వేచి ఉండండి చేస్తాయి.

**Probabilistic Early Expiry:** ప్రతి రిక్వెస్ట్ కు TTL నిజంగా గడువు ముగియాలి కాకముందే క్యాష్ refresh చేసే చిన్న random chance ఉంటుంది. ఇది expiry సమయంలో thundering herd సృష్టించడానికి బదులుగా refresh లోడ్ ను సమయంలో spread చేస్తుంది.

**నేపథ్యం Refresh:** ఒక నేపథ్యం ప్రక్రియ ప్రజాదరణ పొందిన క్యాష్ entries ను గడువు ముగియాలి కాకముందే refresh చేస్తుంది. Hot కీలు కోసం క్యాష్ ఎప్పటికీ empty కాదు.

<ThinkAboutIt>ఒక flash sale ను ఊహించండి, ఒక ప్రోడక్ట్ పేజీ కు 100,000 రిక్వెస్ట్‌లు ప్రతి సెకండ్ వస్తున్నాయి. ప్రోడక్ట్ details క్యాష్ entry గడువు ముగియాలి అవుతుంది. Stampede prevention లేకుండా, 100K రిక్వెస్ట్‌లు అన్నీ ఒకేసారి డేటాబేస్ ను హిట్ చేస్తాయి చేస్తాయి. మీరు ఏ prevention వ్యూహం ఎంచుకుంటారు, ఎందుకు?</ThinkAboutIt>

## దశ 6 - Redis క్లస్టర్ ఆర్కిటెక్చర్

Redis క్లస్టర్ అత్యంత విస్తృతంగా డిప్లాయ్ చేయండి చేయబడిన విస్తరిత క్యాష్:

- **16,384 హ్యాష్ slots** మాస్టర్స్ నోడ్‌లు లో విస్తరించండి అవుతాయి
- ప్రతి కీ `CRC16(key) % 16384` ద్వారా slot కు మ్యాప్ అవుతుంది
- **ప్రతిరూపణ:** ప్రతి మాస్టర్స్ కు failover కోసం ఒకటి లేదా అంతకంటే ఎక్కువ replicas ఉంటాయి
- **Automatic failover:** మాస్టర్స్ విఫలమవుతుంది అయితే, replica సెకన్లు లో promote అవుతుంది

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### కీ మెట్రిక్స్ Monitor చేయడం
- **హిట్ చేస్తాయి నిష్పత్తి** - లక్ష్య 95%+; 80% కంటే తక్కువ క్యాషింగ్ సమస్య ను సూచిస్తుంది
- **మెమరీ వినియోగం** - evictions నివారించడానికి 80% కంటే తక్కువగా ఉంచండి
- **తొలగింపు రేట్** - ఎక్కువ evictions అంటే క్యాష్ undersized
- **లేటెన్సీ percentiles** - క్యాష్ hits కోసం p99 1ms కంటే తక్కువగా ఉండాలి

## దశ 7 - నిజమైన-ప్రపంచం క్యాషింగ్ నమూనాలు

| నమూనా | Implementation | TTL |
|---------|---------------|-----|
| Session నిల్వ | `SET session:{id} {data}` | 30 నిమిషాలు |
| API రెస్పాన్స్ క్యాష్ | `SET api:/users/123 {json}` | 5 నిమిషాలు |
| డేటాబేస్ క్వెరీ క్యాష్ | `SET query:{hash} {result}` | 1 నిమిషం |
| రేట్ లిమిటర్ కౌంటర్ | `INCR ratelimit:{user}:{window}` | విండో వ్యవధి |
| ఫీచర్ flags | `HSET features {flag} {value}` | 10 సెకన్లు |

### క్యాష్ Invalidation
కంప్యూటర్ సైన్స్ లో అత్యంత కఠినమైన సమస్య (naming things తో పాటు):
- **TTL-ఆధారిత** - సరళం, TTL వ్యవధి పాటు staleness ను సహిస్తుంది
- **ఈవెంట్-driven** - డేటా మారినప్పుడు invalidation ఈవెంట్లు ప్రచురించండి చేయండి (Kafka లేదా Redis Pub/ఉప ద్వారా)
- **వెర్షన్-ఆధారిత** - క్యాష్ కీ లో వెర్షన్ చేర్చండి; రైట్‌లు లో వెర్షన్ increment చేయండి, పాత entries ప్రభావవంతంగా చెల్లనివిగా చేయడం అవుతాయి
