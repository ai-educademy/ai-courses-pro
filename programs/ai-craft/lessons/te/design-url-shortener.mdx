## ఇంటర్వ్యూ ప్రాంప్ట్

*"బిట్.ly లాంటి URL సంక్షిప్తీకరణ సేవ డిజైన్ చేయండి - పొడవైన URLs తీసుకుని చిన్న, ప్రత్యేక కోడ్‌లు ఇవ్వాలి."*

ఇది సిస్టమ్ డిజైన్ లో అత్యంత సాధారణ మొదటి ప్రశ్న, ఎందుకంటే ఇది చూడటానికి సింపుల్‌గా కనిపిస్తుంది కానీ మూల భావనలు అన్నీ కవర్ చేస్తుంది చేస్తుంది: *API* డిజైన్, ఎన్‌కోడింగ్ వ్యూహాలు, డేటాబేస్ ఎంపికలు, క్యాషింగ్ మరియు స్కేలింగ్. పాఠం 1 లోని నిర్మిత ఫ్రేమ్‌వర్క్ ఉపయోగించి దీన్ని పరిష్కరించండి చేద్దాం.

## దశ 1: అవసరాలు సేకరణ (5 నిమిషాలు)

**ఫంక్షనల్ అవసరాలు:**
- పొడవైన *URL* నుండి చిన్న ప్రత్యేక *URL* సృష్టించు చేయడం
- చిన్న *URL* రీడైరెక్ట్ అయినప్పుడు అసలు పొడవైన *URL* రావాలి
- వినియోగదారులు ఐచ్చిక గా కస్టమ్ చిన్న కోడ్‌లు సెట్ చేసుకోవచ్చు
- లింకులు మార్చుకోగల కాలం తర్వాత గడువు ముగియాలి అవ్వాలి (డిఫాల్ట్: 5 సంవత్సరాలు)
- ప్రాథమిక విశ్లేషణలు: క్లిక్ లెక్క, రిఫరర్, భౌగోళికం

**Non-functional అవసరాలు:**
- నెలకు 100 మిలియన్ *URLs* సృష్టించు (~40 ప్రతి సెకండ్)
- చదవడం-భారీ: 100:1 చదవడం-కు-రాయండి నిష్పత్తి → 4,000 ర్ెడ్ిర్ెక్ట్స్ ప్రతి సెకండ్
- *URL* ర్ెడ్ిర్ెక్షన్ లేటెన్సీ 50ms కంటే తక్కువ
- చిన్న *URLs* సాధ్యమైనంత చిన్నగా ఉండాలి
- అధిక అందుబాటు - పనిచేయని లింక్ చెడు వినియోగదారు అనుభవం

<Callout>
ప్రతి సిస్టమ్ డిజైన్ ఇంటర్వ్యూ ను స్పష్టత కోసం ప్రశ్నలు అడగడంతో మొదలుపెట్టండి. స్పష్టమైన సంఖ్యలు రాయడం (40 రైట్‌లు/స్ెక్, 4,000 రీడ్‌లు/స్ెక్) మీరు స్కేల్ గురించి పరిమాణాత్మకంగా ఆలోచించగలరని చూపిస్తుంది.
</Callout>

## దశ 2: *API* డిజైన్ (5 నిమిషాలు)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**HTTP 301 vs 302 ఎందుకు?**
- **301 (శాశ్వత రీడైరెక్ట్)** - బ్రౌజర్లు దీన్ని క్యాష్ చేస్తాయి, సర్వర్‌లు పై లోడ్ తగ్గిస్తుంది
- **302 (తాత్కాలిక రీడైరెక్ట్)** - బ్రౌజర్లు ఎల్లప్పుడూ మన సర్వర్‌లు ని హిట్ చేస్తాయి చేస్తాయి, ఖచ్చితమైన విశ్లేషణలు వచ్చేలా

క్లిక్‌లు ట్రాక్ చేసే సేవ కి **302 మెరుగైన ఎంపిక** ఎందుకంటే ప్రతి రీడైరెక్ట్ మన సర్వర్‌లు ద్వారా వెళ్తుంది.

## దశ 3: ఎన్‌కోడింగ్ వ్యూహం

ప్రధాన సవాలు: చిన్న, ప్రత్యేక కోడ్‌లు ఎలా సృష్టించు చేయాలి?

**బేస్62 ఎన్‌కోడింగ్** `[a-zA-Z0-9]` వాడుతుంది - 62 అక్షరాలు. 7-అక్షరం కోడ్ తో 62⁷ = **3.5 ట్రిలియన్** ప్రత్యేక కాంబినేషన్లు వస్తాయి, మన స్కేల్ కి చాలా సరిపోతుంది.

**ఎంపిక A - కౌంటర్-ఆధారిత:**
- ఆటో ఇంక్రిమెంటింగ్ కౌంటర్ (1, 2, 3, ...) ని బేస్62 కి మార్చండి చేయండి
- కౌంటర్ 1000 → `g8` | కౌంటర్ 1000000 → `4c92`
- **ప్రయోజనాలు:** గ్ుార్అన్ట్ీడ్ ప్రత్యేక, సులభమైన, ఢీకొనడాలు ఉండవు
- **అప్రయోజనాలు:** అంచనా వేయగల (వినియోగదారులు తదుపరి *URL* ఊహించగలరు), క్ెన్ట్ర్ల్ైజ్డ్ కౌంటర్ అవసరం

**ఎంపిక B - హ్యాష్-ఆధారిత:**
- పొడవైన *URL* ని MD5/*SHA-*256 తో హ్యాష్ చేసి, బేస్62 యొక్క మొదటి 7 అక్షరాలు తీసుకోండి
- **ప్రయోజనాలు:** స్ట్అట్ెల్స్స్, కేంద్ర సమన్వయం అవసరం లేదు
- **అప్రయోజనాలు:** ఢీకొనడాలు సాధ్యమైన - డేటాబేస్ తనిఖీ చేసి మళ్లీ ప్రయత్నం చేయాలి

**ఎంపిక C - ముందస్తు-సృష్టించిన కీలు (ర్ెక్ోమ్మ్ెన్డ్ెడ్):**
- నేపథ్యం సేవ ముందుగానే మిలియన్లు of ప్రత్యేక బేస్62 కోడ్‌లు సృష్టించు చేసి కీ ప్ూల్ లో నిల్వ చేస్తుంది
- కొత్త *URL* వచ్చినప్పుడు ప్ూల్ నుండి తదుపరి అందుబాటులో కోడ్ తీసుకోండి
- **ప్రయోజనాలు:** వేగంగా, ఢీకొనడం రిస్క్ లేదు, అంచనా వేయగల కాదు
- **అప్రయోజనాలు:** కీ సృష్టి సేవ నిర్వహించండి చేయాలి

<FunFact>
అసలు *TinyURL* సేవ 2002 లో ల్ాన్చ్ అయింది మరియు ఇప్పటికీ నడుస్తోంది. ఒక సమయంలో ఇది రోజుకు 10 లక్షల కంటే ఎక్కువ చిన్న *URLs* సృష్టించు చేసేది. ట్ిన్య్ుర్ల్.క్ోమ్ డొమైన్ చాలా ిక్ోన్ిక్ అయింది, "ట్ిన్య్ుర్ల్" అనే పదం *URL* సంక్షిప్తీకరణ కి సాధారణ కాలవ్యవధి గా మారింది.
</FunFact>

## దశ 4: డేటాబేస్ ఎంపిక మరియు స్కీమా

నెలకు 100 మిలియన్ కొత్త *URLs* మరియు 5 సంవత్సరాల ర్ెట్ెన్షన్ తో, మనం దాదాపు **6 బిలియన్ ర్ెక్ర్డ్స్** నిల్వ చేస్తాం. ఇది సులభమైన కీ-విలువ లుక్‌అప్‌లు తో చదవడం-భారీ వ్ర్క్ల్ోఅడ్.

**డేటాబేస్ ఎంపిక: DynamoDB లేదా Cassandra**
- లుక్‌అప్‌లు ఎల్లప్పుడూ చిన్న కోడ్ (పార్టిషన్ కీ) ద్వారా - క్లిష్టమైన జ్ోిన్స్ అవసరం లేదు
- రెండూ అడ్డంగా స్కేలింగ్ తో భారీ చదవడం థ్రూపుట్ నిర్వహించు చేస్తాయి
- రెండూ పార్టిషన్ కీ ద్వారా ఉప-10ms లుక్‌అప్‌లు ఇస్తాయి

**స్కీమా:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

విశ్లేషణలు కోసం, ప్రత్యేక సమయం-స్ర్ిెస్ పట్టిక వ్యక్తిగత క్లిక్ ఈవెంట్లు నిల్వ చేస్తుంది:
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## దశ 5: క్యాషింగ్ వ్యూహం

4,000 రీడ్‌లు ప్రతి సెకండ్ మరియు భారీ-ట్ైల్డ్ వితరణ (కొన్ని *URLs* కి మిలియన్లు of క్లిక్‌లు వస్తాయి, చాలా వాటికి చాలా తక్కువ) తో క్యాషింగ్ తప్పనిసరి.

**Redis క్యాష్** అత్యధికంగా యాక్సెస్ అయ్యే మ్అప్ప్ింగ్స్ నిల్వ చేస్తుంది:
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**క్యాష్ హిట్ చేస్తాయి ప్రవాహం (వేగంగా మార్గం):**
1. రిక్వెస్ట్ వస్తుంది: `GET /aB3kx9`
2. *Redis* తనిఖీ → క్యాష్ హిట్ చేస్తాయి → 302 రీడైరెక్ట్ రిటర్న్
3. అసమకాలికంగా క్లిక్ ఈవెంట్ ని *Kafka* లో లాగ్ చేయడం

**క్యాష్ మిస్ అవడం ప్రవాహం:**
1. *Redis* తనిఖీ → మిస్ అవడం
2. డేటాబేస్ క్వెరీ → ఫ్ౌన్డ్
3. *Redis* క్యాష్ ప్ోప్ుల్అట్ె చేయడం
4. 302 రీడైరెక్ట్ రిటర్న్

80% క్యాష్ హిట్ చేస్తాయి రేట్ తో, 4,000 రిక్వెస్ట్‌లు లో 800 మాత్రమే డేటాబేస్ ని చేరుకుంటాయి.

## దశ 6: విశ్లేషణలు మరియు క్లిక్ ట్రాకింగ్

క్లిక్ ట్రాకింగ్ వల్ల ర్ెడ్ిర్ెక్ట్స్ నెమ్మది కాకూడదు. రీడైరెక్ట్ రెస్పాన్స్ వెంటనే రిటర్న్ అవ్వాలి, విశ్లేషణలు అసమకాలికంగా ప్రక్రియ అవ్వాలి.

**ఆర్కిటెక్చర్:**
1. రీడైరెక్ట్ హ్అన్డ్ల్ర్ క్లిక్ ఈవెంట్ ని **Kafka** కి ప్రచురించండి చేస్తుంది
2. క్లిక్-ప్రాసెసింగ్ సేవ ఈవెంట్లు వినియోగిస్తాయి చేసి:
   - *URL* రికార్డు లో `click_count` ిన్క్ర్ెమెంట్ చేస్తుంది
   - క్లిక్‌లు పట్టిక లో డ్ెట్ైల్డ్ క్లిక్ డేటా రాస్తుంది
   - స్ట్రీమింగ్ సమీకరణ ద్వారా రియల్ టైమ్ డ్యాష్‌బోర్డ్‌లు నవీకరించు చేస్తుంది

ఈ డ్ెక్ౌప్ల్ింగ్ నెమ్మది విశ్లేషణలు పైప్‌లైన్ రీడైరెక్ట్ లేటెన్సీ ని ఎప్పుడూ ప్రభావం చేయదని నిర్ధారించండి చేస్తుంది.
