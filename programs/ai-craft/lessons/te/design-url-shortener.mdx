## ఇంటర్వ్యూ ప్రాంప్ట్

*"బిట్.ly లాంటి URL సంక్షిప్తీకరణ సేవ డిజైన్ చేయండి - పొడవైన URLs తీసుకుని చిన్న, ప్రత్యేక కోడ్‌లు ఇవ్వాలి."*

ఇది సిస్టమ్ డిజైన్ లో అత్యంత సాధారణ మొదటి ప్రశ్న, ఎందుకంటే ఇది చూడటానికి సింపుల్‌గా కనిపిస్తుంది కానీ మూల భావనలు అన్నీ కవర్ చేస్తుంది చేస్తుంది: API డిజైన్, ఎన్‌కోడింగ్ వ్యూహాలు, డేటాబేస్ ఎంపికలు, క్యాషింగ్ మరియు స్కేలింగ్. పాఠం 1 లోని నిర్మిత ఫ్రేమ్‌వర్క్ ఉపయోగించి దీన్ని పరిష్కరించండి చేద్దాం.

## దశ 1: అవసరాలు సేకరణ (5 నిమిషాలు)

**Functional అవసరాలు:**
- పొడవైన URL నుండి చిన్న ప్రత్యేక URL సృష్టించు చేయడం
- చిన్న URL రీడైరెక్ట్ అయినప్పుడు అసలు పొడవైన URL రావాలి
- వినియోగదారులు ఐచ్చిక గా కస్టమ్ చిన్న కోడ్‌లు సెట్ చేసుకోవచ్చు
- లింకులు మార్చుకోగల కాలం తర్వాత గడువు ముగియాలి అవ్వాలి (డిఫాల్ట్: 5 సంవత్సరాలు)
- ప్రాథమిక విశ్లేషణలు: క్లిక్ లెక్క, రిఫరర్, భౌగోళికం

**Non-functional అవసరాలు:**
- నెలకు 100 మిలియన్ URLs సృష్టించు (~40 ప్రతి సెకండ్)
- చదవడం-భారీ: 100:1 చదవడం-కు-రాయండి నిష్పత్తి → 4,000 redirects ప్రతి సెకండ్
- URL redirection లేటెన్సీ 50ms కంటే తక్కువ
- చిన్న URLs సాధ్యమైనంత చిన్నగా ఉండాలి
- అధిక అందుబాటు - పనిచేయని లింక్ చెడు వినియోగదారు అనుభవం

<Callout>
ప్రతి సిస్టమ్ డిజైన్ ఇంటర్వ్యూ ను స్పష్టత కోసం ప్రశ్నలు అడగడంతో మొదలుపెట్టండి. స్పష్టమైన సంఖ్యలు రాయడం (40 రైట్‌లు/sec, 4,000 రీడ్‌లు/sec) మీరు స్కేల్ గురించి పరిమాణాత్మకంగా ఆలోచించగలరని చూపిస్తుంది.
</Callout>

## దశ 2: API డిజైన్ (5 నిమిషాలు)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**HTTP 301 vs 302 ఎందుకు?**
- **301 (శాశ్వత రీడైరెక్ట్)** - బ్రౌజర్లు దీన్ని క్యాష్ చేస్తాయి, సర్వర్‌లు పై లోడ్ తగ్గిస్తుంది
- **302 (తాత్కాలిక రీడైరెక్ట్)** - బ్రౌజర్లు ఎల్లప్పుడూ మన సర్వర్‌లు ని హిట్ చేస్తాయి చేస్తాయి, ఖచ్చితమైన విశ్లేషణలు వచ్చేలా

Clicks ట్రాక్ చేసే సేవ కి **302 మెరుగైన ఎంపిక** ఎందుకంటే ప్రతి రీడైరెక్ట్ మన సర్వర్‌లు ద్వారా వెళ్తుంది.

## దశ 3: ఎన్‌కోడింగ్ వ్యూహం

ప్రధాన సవాలు: చిన్న, ప్రత్యేక కోడ్‌లు ఎలా సృష్టించు చేయాలి?

**బేస్62 ఎన్‌కోడింగ్** `[a-zA-Z0-9]` వాడుతుంది - 62 అక్షరాలు. 7-అక్షరం కోడ్ తో 62⁷ = **3.5 ట్రిలియన్** ప్రత్యేక కాంబినేషన్లు వస్తాయి, మన స్కేల్ కి చాలా సరిపోతుంది.

**ఎంపిక A - కౌంటర్-ఆధారిత:**
- ఆటో ఇంక్రిమెంటింగ్ కౌంటర్ (1, 2, 3, ...) ని బేస్62 కి మార్చండి చేయండి
- కౌంటర్ 1000 → `g8` | కౌంటర్ 1000000 → `4c92`
- **ప్రయోజనాలు:** guaranteed ప్రత్యేక, సులభమైన, collisions ఉండవు
- **అప్రయోజనాలు:** predictable (వినియోగదారులు తదుపరి URL ఊహించగలరు), centralised కౌంటర్ అవసరం

**ఎంపిక B - హ్యాష్-ఆధారిత:**
- పొడవైన URL ని MD5/SHA-256 తో హ్యాష్ చేసి, బేస్62 యొక్క మొదటి 7 అక్షరాలు తీసుకోండి
- **ప్రయోజనాలు:** stateless, central coordination అవసరం లేదు
- **అప్రయోజనాలు:** collisions సాధ్యమైన - డేటాబేస్ తనిఖీ చేసి మళ్లీ ప్రయత్నం చేయాలి

**ఎంపిక C - ముందస్తు-సృష్టించిన కీలు (recommended):**
- నేపథ్యం సేవ ముందుగానే మిలియన్లు of ప్రత్యేక బేస్62 కోడ్‌లు సృష్టించు చేసి కీ pool లో నిల్వ చేస్తుంది
- కొత్త URL వచ్చినప్పుడు pool నుండి తదుపరి available కోడ్ తీసుకోండి
- **ప్రయోజనాలు:** వేగంగా, collision రిస్క్ లేదు, predictable కాదు
- **అప్రయోజనాలు:** కీ సృష్టి సేవ manage చేయాలి

<FunFact>
అసలు TinyURL సేవ 2002 లో launch అయింది మరియు ఇప్పటికీ నడుస్తోంది. ఒక సమయంలో ఇది రోజుకు 10 లక్షల కంటే ఎక్కువ చిన్న URLs సృష్టించు చేసేది. tinyurl.com డొమైన్ చాలా iconic అయింది, "tinyurl" అనే పదం URL సంక్షిప్తీకరణ కి సాధారణ కాలవ్యవధి గా మారింది.
</FunFact>

## దశ 4: డేటాబేస్ ఎంపిక మరియు స్కీమా

నెలకు 100 మిలియన్ కొత్త URLs మరియు 5 సంవత్సరాల retention తో, మనం దాదాపు **6 బిలియన్ records** నిల్వ చేస్తాం. ఇది సులభమైన కీ-విలువ లుక్‌అప్‌లు తో చదవడం-భారీ workload.

**డేటాబేస్ ఎంపిక: DynamoDB లేదా Cassandra**
- లుక్‌అప్‌లు ఎల్లప్పుడూ చిన్న కోడ్ (పార్టిషన్ కీ) ద్వారా - క్లిష్టమైన joins అవసరం లేదు
- రెండూ horizontal స్కేలింగ్ తో massive చదవడం థ్రూపుట్ నిర్వహించు చేస్తాయి
- రెండూ పార్టిషన్ కీ ద్వారా ఉప-10ms లుక్‌అప్‌లు ఇస్తాయి

**స్కీమా:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

విశ్లేషణలు కోసం, ప్రత్యేక సమయం-series పట్టిక వ్యక్తిగత క్లిక్ ఈవెంట్లు నిల్వ చేస్తుంది:
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## దశ 5: క్యాషింగ్ వ్యూహం

4,000 రీడ్‌లు ప్రతి సెకండ్ మరియు భారీ-tailed వితరణ (కొన్ని URLs కి మిలియన్లు of clicks వస్తాయి, చాలా వాటికి చాలా తక్కువ) తో క్యాషింగ్ తప్పనిసరి.

**Redis క్యాష్** అత్యధికంగా యాక్సెస్ అయ్యే mappings నిల్వ చేస్తుంది:
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**క్యాష్ హిట్ చేస్తాయి ప్రవాహం (వేగంగా మార్గం):**
1. రిక్వెస్ట్ వస్తుంది: `GET /aB3kx9`
2. Redis తనిఖీ → క్యాష్ హిట్ చేస్తాయి → 302 రీడైరెక్ట్ రిటర్న్
3. Asynchronously క్లిక్ ఈవెంట్ ని Kafka లో లాగ్ చేయడం

**క్యాష్ మిస్ అవడం ప్రవాహం:**
1. Redis తనిఖీ → మిస్ అవడం
2. డేటాబేస్ క్వెరీ → found
3. Redis క్యాష్ populate చేయడం
4. 302 రీడైరెక్ట్ రిటర్న్

80% క్యాష్ హిట్ చేస్తాయి రేట్ తో, 4,000 రిక్వెస్ట్‌లు లో 800 మాత్రమే డేటాబేస్ ని చేరుకుంటాయి.

## దశ 6: విశ్లేషణలు మరియు క్లిక్ ట్రాకింగ్

క్లిక్ ట్రాకింగ్ వల్ల redirects నెమ్మది కాకూడదు. రీడైరెక్ట్ రెస్పాన్స్ వెంటనే రిటర్న్ అవ్వాలి, విశ్లేషణలు asynchronously ప్రక్రియ అవ్వాలి.

**ఆర్కిటెక్చర్:**
1. రీడైరెక్ట్ handler క్లిక్ ఈవెంట్ ని **Kafka** కి ప్రచురించండి చేస్తుంది
2. క్లిక్-ప్రాసెసింగ్ సేవ ఈవెంట్లు వినియోగిస్తాయి చేసి:
   - URL రికార్డు లో `click_count` increment చేస్తుంది
   - Clicks పట్టిక లో detailed క్లిక్ డేటా రాస్తుంది
   - స్ట్రీమింగ్ aggregation ద్వారా రియల్ టైమ్ డ్యాష్‌బోర్డ్‌లు నవీకరించు చేస్తుంది

ఈ decoupling నెమ్మది విశ్లేషణలు పైప్‌లైన్ రీడైరెక్ట్ లేటెన్సీ ని ఎప్పుడూ ప్రభావం చేయదని నిర్ధారించండి చేస్తుంది.

URL shorteners కొన్నిసార్లు హానికరమైన లింకులు దాచడానికి వాడతారు. మీరు బిట్.ly డిజైన్ చేస్తుంటే, destination URLs ను phishing లేదా malware కోసం scan చేసే భద్రత తనిఖీ ఎలా అమలు చేయండి చేస్తారు - సంక్షిప్తీకరణ ప్రక్రియ లో significant లేటెన్సీ జోడించు చేయకుండా?

## దశ 7: సిస్టమ్ ను స్కేల్ చేయడం

**Horizontal స్కేలింగ్ విధానం:**
- **API సర్వర్‌లు** stateless - లోడ్ బ్యాలెన్సర్ వెనుక ఇన్‌స్టాన్స్‌లు జోడించు చేసి స్కేల్ చేయండి
- **కీ సృష్టి సేవ** ప్రత్యేక microservice గా నడుస్తుంది, దాని స్వంత ముందస్తు-సృష్టించిన కోడ్‌లు డేటాబేస్ తో
- **Redis క్లస్టర్** స్థిరమైన హ్యాషింగ్ ద్వారా నోడ్‌లు మధ్య క్యాష్ విస్తరించండి చేస్తుంది
- **డేటాబేస్ షార్డింగ్** చిన్న కోడ్ యొక్క మొదటి అక్షరం ద్వారా డేటా సమానంగా విస్తరించండి చేస్తుంది

**పీక్ loads నిర్వహించు చేయడం:**
- Viral ఈవెంట్లు లో ఒక URL కి ప్రతి నిమిషం మిలియన్లు of hits రావచ్చు
- Redis క్యాష్ సహజంగానే దీన్ని absorb చేస్తుంది - ఒక క్యాష్ entry unlimited రీడ్‌లు సర్వ్ చేయండి చేస్తుంది
- Kafka క్లిక్ ఈవెంట్లు buffer చేస్తుంది, విశ్లేషణలు డేటాబేస్ పై రాయండి లోడ్ smooth చేస్తుంది

## ముఖ్యమైన విషయాలు

- ఫ్రేమ్‌వర్క్ అనుసరించండి చేయండి: అవసరాలు → API → ఎన్‌కోడింగ్ → డేటా మోడల్ → ఆర్కిటెక్చర్ → లోతైన dives
- 7 అక్షరాలు తో బేస్62 3.5 ట్రిలియన్ ప్రత్యేక కోడ్‌లు ఇస్తుంది - చాలా సరిపోతుంది
- ముందస్తు-సృష్టించిన కీ pools collision ఇష్యూలు మరియు central కౌంటర్ bottlenecks నివారిస్తాయి
- ఖచ్చితమైన క్లిక్ విశ్లేషణలు కావాలంటే 302 redirects వాడండి (301 కాదు)
- Redis క్యాషింగ్ చదవడం-భారీ workloads కోసం డేటాబేస్ లోడ్ గణనీయంగా తగ్గిస్తుంది
