# నోటిఫికేషన్ సిస్టమ్ డిజైన్ చేయండి - పుష్, ఇమెయిల్, మరియు SMS బిలియన్ స్కేల్ లో

ఆధునిక అప్లికేషన్‌లు రోజూ బిలియన్ల నోటిఫికేషన్‌లు ను అనేక channels ద్వారా పంపుతాయి. ఈ సిస్టమ్ ను డిజైన్ చేయడం వల్ల సందేశం క్యూలు, third-party integrations, మరియు స్కేల్ లో failures ను gracefully నిర్వహించు చేయడం నేర్చుకుంటారు.

## దశ 1 - అవసరాలు సేకరణ

### Functional అవసరాలు
- అనేక channels కు మద్దతు: పుష్ నోటిఫికేషన్‌లు, ఇమెయిల్, SMS, మరియు లో-app
- వినియోగదారులు తమ నోటిఫికేషన్ అభిరుచులు configure చేసుకోగలగాలి మరియు ప్రతి channel కు opt out చేయగలగాలి
- వ్యక్తిగతీకరణ తో templated సందేశాలు (ఉదా., "Hi {పేరు}, మీ క్రమం షిప్ చేయడం అయింది")
- Scheduled మరియు తక్షణ నోటిఫికేషన్‌లు కు మద్దతు

### Non-Functional అవసరాలు
- **Scalability** - రోజుకు 10 మిలియన్+ నోటిఫికేషన్‌లు నిర్వహించు చేయగలగాలి
- **నమ్మకత** - ఏ నోటిఫికేషన్ కూడా పోకూడదు; at-least-once డెలివరీ
- **Low లేటెన్సీ** - urgent నోటిఫికేషన్‌లు సెకన్లలో deliver అవ్వాలి
- **Extensible** - కొత్త channels (WhatsApp, Slack) సులభంగా జోడించు చేయగలగాలి

<ThinkAboutIt>నోటిఫికేషన్ డెలివరీ ఖచ్చితంగా-once ఉండాలా లేదా at-least-once ఉండాలా? ఆలోచించండి - duplicate SMS రావడం వర్సెస్ ఒక కీలకమైన భద్రత alert మిస్ అవడం అవడం.</ThinkAboutIt>

## దశ 2 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### మూల భాగాలు
1. **నోటిఫికేషన్ సేవ** - రిక్వెస్ట్‌లు ధృవీకరించండి చేస్తుంది, వినియోగదారు అభిరుచులు తనిఖీ చేస్తుంది, templates render చేస్తుంది, మరియు సందేశాలు enqueue చేస్తుంది
2. **సందేశం క్యూలు** - ప్రతి channel కు విడిగా క్యూలు, independent స్కేలింగ్ మరియు isolation కోసం
3. **డెలివరీ Workers** - channel-స్పష్టంగా workers, third-party API కాల్‌లు నిర్వహించు చేస్తాయి
4. **Template సేవ** - variable substitution తో నోటిఫికేషన్ templates నిల్వ మరియు render చేస్తుంది

## దశ 3 - లోతైన అధ్యయనం: కీ భాగాలు

### వినియోగదారు అభిరుచులు మరియు Opt-Out
ప్రతి వినియోగదారు మరియు నోటిఫికేషన్ type కు అభిరుచులు నిల్వ చేయండి:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

నోటిఫికేషన్ సేవ enqueue చేయడానికి **ముందే** అభిరుచులు తనిఖీ చేస్తుంది - వినియోగదారు కోరుకోనిది ఎప్పుడూ పంపకూడదు.

### ప్రాధాన్యం క్యూలు
అన్ని నోటిఫికేషన్‌లు సమానం కావు. ప్రాధాన్యం స్థాయులు వాడండి:
- **కీలకమైన** - భద్రత alerts, OTP కోడ్‌లు → వెంటనే ప్రక్రియ
- **అధిక** - క్రమం confirmations, చెల్లింపు receipts → సెకన్లలో
- **Medium** - సోషల్ interactions, comments → నిమిషాల్లో ఆమోదయోగ్యం
- **Low** - marketing, సిఫార్సులు → బ్యాచ్ చేయవచ్చు

## దశ 4 - నమ్మకత మరియు విఫలం నిర్వహణ

### డీడూప్లికేషన్
ఐడెంపోటెన్సీ కీ వాడి duplicate నోటిఫికేషన్‌లు ను ఆపండి. ప్రక్రియ చేయడానికి ముందు, నోటిఫికేషన్ ID డీడూప్లికేషన్ నిల్వ (Redis తో TTL) లో ఉందో లేదో తనిఖీ చేయండి:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### మళ్లీ ప్రయత్నం తో Exponential Backoff
Third-party సేవలు విఫలమవుతుంది అవుతాయి. పెరుగుతున్న delays తో మళ్లీ ప్రయత్నాలు అమలు చేయండి చేయండి:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### ప్రతి వినియోగదారు రేట్ పరిమితం చేసే
వినియోగదారులు ను నోటిఫికేషన్ fatigue నుండి రక్షించండి:
- ప్రతి వినియోగదారు కు గంటకు గరిష్టంగా 3 పుష్ నోటిఫికేషన్‌లు
- రోజుకు గరిష్టంగా 1 marketing ఇమెయిల్
- భద్రత నోటిఫికేషన్‌లు రేట్ పరిమితులు ను bypass చేస్తాయి

<FunFact>Facebook రోజూ 10 బిలియన్ కంటే ఎక్కువ పుష్ నోటిఫికేషన్‌లు పంపుతుంది. దీన్ని నిర్వహించు చేయడానికి వారు ఒక కస్టమ్ నోటిఫికేషన్ పైప్‌లైన్ నిర్మించారు, ఇది సెకనుకు మిలియన్ల సందేశాలు ప్రక్రియ చేయగలదు, iOS (APNs) మరియు Android (FCM) కు విడి డెలివరీ మార్గాలు తో.</FunFact>

## దశ 5 - Third-Party Integration

| Channel | Provider | Protocol | సవాళ్లు |
|---------|----------|----------|---------|
| పుష్ (iOS) | APNs | HTTP/2 | టోకెన్ నిర్వహణ, silent పుష్ పరిమితులు |
| పుష్ (Android) | FCM | HTTP | విషయం-ఆధారిత broadcasting |
| ఇమెయిల్ | SendGrid/SES | SMTP/API | Deliverability, spam ఫిల్టర్లు |
| SMS | Twilio | REST API | ప్రతి సందేశం కు ఖర్చు, regional అనుసరణ |
| లో-App | WebSocket | WS | కనెక్షన్ నిర్వహణ, offline buffering |

### విశ్లేషణలు పైప్‌లైన్
ప్రతి సందేశం యొక్క నోటిఫికేషన్ జీవనచక్రం ను ట్రాక్ చేయండి:
- **Created** → **Queued** → **Sent** → **Delivered** → **Opened** → **Clicked**

Dashboard reporting కోసం ఈవెంట్లు ను సమయం-series డేటాబేస్ లేదా ఈవెంట్ stream లో నిల్వ చేయండి: డెలివరీ రేట్లు, open రేట్లు, మరియు క్లిక్-ద్వారా రేట్లు ప్రతి channel మరియు నోటిఫికేషన్ type వారీగా.

## దశ 6 - Bottlenecks మరియు Optimisations

| Bottleneck | పరిష్కారం |
|-----------|----------|
| Third-party రేట్ పరిమితులు | ప్రతి provider కు controlled థ్రూపుట్ తో క్యూ |
| స్కేల్ లో template rendering | సాధారణ templates ను ముందస్తు-render మరియు క్యాష్ చేయండి |
| ప్రతి సందేశం కు అభిరుచి లుక్‌అప్‌లు | Redis లో వినియోగదారు అభిరుచులు క్యాష్ చేయండి |
| పీక్ ట్రాఫిక్ spikes | క్యూ లోతు ఆధారంగా workers ను ఆటో-స్కేల్ చేయండి |
| Cross-region డెలివరీ | Provider endpoints కు దగ్గరగా workers డిప్లాయ్ చేయండి చేయండి |
