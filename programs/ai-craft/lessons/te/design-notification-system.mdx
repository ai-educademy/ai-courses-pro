# నోటిఫికేషన్ సిస్టమ్ డిజైన్ చేయండి - పుష్, ఇమెయిల్, మరియు *SMS* బిలియన్ స్కేల్ లో

ఆధునిక అప్లికేషన్‌లు రోజూ బిలియన్ల నోటిఫికేషన్‌లు ను అనేక ఛానల్‌లు ద్వారా పంపుతాయి. ఈ సిస్టమ్ ను డిజైన్ చేయడం వల్ల సందేశం క్యూలు, త్ిర్డ్-ప్ార్ట్య్ ిన్ట్ెగ్ర్అషన్స్, మరియు స్కేల్ లో విఫలాలు ను గ్ర్అక్ెఫ్ుల్ల్య్ నిర్వహించు చేయడం నేర్చుకుంటారు.

## దశ 1 - అవసరాలు సేకరణ

### ఫంక్షనల్ అవసరాలు
- అనేక ఛానల్‌లు కు మద్దతు: పుష్ నోటిఫికేషన్‌లు, ఇమెయిల్, *SMS*, మరియు లో-అప్ప్
- వినియోగదారులు తమ నోటిఫికేషన్ అభిరుచులు కాన్ఫిగర్ చేయండి చేసుకోగలగాలి మరియు ప్రతి ఛానల్ కు వద్దనుకునే ఎంపిక చేయగలగాలి
- వ్యక్తిగతీకరణ తో ట్ెమ్ప్ల్అట్ెడ్ సందేశాలు (ఉదా., "Hi {పేరు}, మీ క్రమం షిప్ చేయడం అయింది")
- *Scheduled* మరియు తక్షణ నోటిఫికేషన్‌లు కు మద్దతు

### ఫంక్షనల్ కాని అవసరాలు
- **Scalability** - రోజుకు 10 మిలియన్+ నోటిఫికేషన్‌లు నిర్వహించు చేయగలగాలి
- **నమ్మకత** - ఏ నోటిఫికేషన్ కూడా పోకూడదు; అట్-ల్అస్ట్-ోన్క్ె డెలివరీ
- **తక్కువ లేటెన్సీ** - ుర్గ్ెన్ట్ నోటిఫికేషన్‌లు సెకన్లలో చేరవేయండి అవ్వాలి
- **Extensible** - కొత్త ఛానల్‌లు (WhatsApp, **Slack**) సులభంగా జోడించు చేయగలగాలి

<ThinkAboutIt>నోటిఫికేషన్ డెలివరీ ఖచ్చితంగా-ోన్క్ె ఉండాలా లేదా అట్-ల్అస్ట్-ోన్క్ె ఉండాలా? ఆలోచించండి - నకిలీ *SMS* రావడం వర్సెస్ ఒక కీలకమైన భద్రత ల్ర్ట్ మిస్ అవడం అవడం.</ThinkAboutIt>

## దశ 2 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### మూల భాగాలు
1. **నోటిఫికేషన్ సేవ** - రిక్వెస్ట్‌లు ధృవీకరించండి చేస్తుంది, వినియోగదారు అభిరుచులు తనిఖీ చేస్తుంది, నమూనాలు ర్ెన్డ్ర్ చేస్తుంది, మరియు సందేశాలు ెన్క్వ్ెుె చేస్తుంది
2. **సందేశం క్యూలు** - ప్రతి ఛానల్ కు విడిగా క్యూలు, ిన్డ్ెప్ెన్డ్ెన్ట్ స్కేలింగ్ మరియు ిస్ోల్అషన్ కోసం
3. **డెలివరీ కార్మికులు** - ఛానల్-స్పష్టంగా కార్మికులు, త్ిర్డ్-ప్ార్ట్య్ **API** కాల్‌లు నిర్వహించు చేస్తాయి
4. **నమూనా సేవ** - చరరాశి స్ుబ్స్ట్ిట్ుషన్ తో నోటిఫికేషన్ నమూనాలు నిల్వ మరియు ర్ెన్డ్ర్ చేస్తుంది

## దశ 3 - లోతైన అధ్యయనం: కీ భాగాలు

### వినియోగదారు అభిరుచులు మరియు *Opt-Out*
ప్రతి వినియోగదారు మరియు నోటిఫికేషన్ రకం కు అభిరుచులు నిల్వ చేయండి:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

నోటిఫికేషన్ సేవ ెన్క్వ్ెుె చేయడానికి **ముందే** అభిరుచులు తనిఖీ చేస్తుంది - వినియోగదారు కోరుకోనిది ఎప్పుడూ పంపకూడదు.

### ప్రాధాన్యం క్యూలు
అన్ని నోటిఫికేషన్‌లు సమానం కావు. ప్రాధాన్యం స్థాయులు వాడండి:
- **కీలకమైన** - భద్రత ల్ర్ట్స్, *OTP* కోడ్‌లు → వెంటనే ప్రక్రియ
- **అధిక** - క్రమం క్ోన్ఫ్ిర్మ్అషన్స్, చెల్లింపు ర్ెక్ెిప్ట్స్ → సెకన్లలో
- **Medium** - సోషల్ పరస్పర చర్యలు, క్ోమ్మెంట్స్ → నిమిషాల్లో ఆమోదయోగ్యం
- **తక్కువ** - మ్ార్క్ెట్ింగ్, సిఫార్సులు → బ్యాచ్ చేయవచ్చు

## దశ 4 - నమ్మకత మరియు విఫలం నిర్వహణ

### డీడూప్లికేషన్
ఐడెంపోటెన్సీ కీ వాడి నకిలీ నోటిఫికేషన్‌లు ను ఆపండి. ప్రక్రియ చేయడానికి ముందు, నోటిఫికేషన్ ID డీడూప్లికేషన్ నిల్వ (*Redis* తో *TTL*) లో ఉందో లేదో తనిఖీ చేయండి:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### మళ్లీ ప్రయత్నం తో *Exponential* *Backoff*
మూడవ పక్ష సేవలు విఫలమవుతుంది అవుతాయి. పెరుగుతున్న డ్ెల్ేస్ తో మళ్లీ ప్రయత్నాలు అమలు చేయండి చేయండి:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### ప్రతి వినియోగదారు రేట్ పరిమితం చేసే
వినియోగదారులు ను నోటిఫికేషన్ ఫ్అట్ిగ్ుె నుండి రక్షించండి:
- ప్రతి వినియోగదారు కు గంటకు గరిష్టంగా 3 పుష్ నోటిఫికేషన్‌లు
- రోజుకు గరిష్టంగా 1 మ్ార్క్ెట్ింగ్ ఇమెయిల్
- భద్రత నోటిఫికేషన్‌లు రేట్ పరిమితులు ను దాటవేయడం చేస్తాయి

<FunFact>*Facebook* రోజూ 10 బిలియన్ కంటే ఎక్కువ పుష్ నోటిఫికేషన్‌లు పంపుతుంది. దీన్ని నిర్వహించు చేయడానికి వారు ఒక కస్టమ్ నోటిఫికేషన్ పైప్‌లైన్ నిర్మించారు, ఇది సెకనుకు మిలియన్ల సందేశాలు ప్రక్రియ చేయగలదు, *iOS* (*APNs*) మరియు *Android* (*FCM*) కు విడి డెలివరీ మార్గాలు తో.</FunFact>

## దశ 5 - మూడవ పక్ష అనుసంధానం

| ఛానల్ | ప్రొవైడర్ | *Protocol* | సవాళ్లు |
|---------|----------|----------|---------|
| పుష్ (*iOS*) | *APNs* | *HTTP*/2 | టోకెన్ నిర్వహణ, స్ిల్న్ట్ పుష్ పరిమితులు |
| పుష్ (*Android*) | *FCM* | *HTTP* | విషయం-ఆధారిత బ్ర్ోఅడ్క్అస్ట్ింగ్ |
| ఇమెయిల్ | *SendGrid*/*SES* | *SMTP*/*API* | *Deliverability*, స్ప్అమ్ ఫిల్టర్లు |
| *SMS* | *Twilio* | *REST* *API* | ప్రతి సందేశం కు ఖర్చు, ర్ెగ్ిోన్ల్ అనుసరణ |
| లో-*App* | *WebSocket* | WS | కనెక్షన్ నిర్వహణ, ఆఫ్‌లైన్ బఫరింగ్ |

### విశ్లేషణలు పైప్‌లైన్
ప్రతి సందేశం యొక్క నోటిఫికేషన్ జీవనచక్రం ను ట్రాక్ చేయండి:
- **Created** → **Queued** → **Sent** → **Delivered** → **Opened** → **Clicked**

డ్యాష్‌బోర్డ్ ర్ెప్ర్ట్ింగ్ కోసం ఈవెంట్లు ను సమయం-స్ర్ిెస్ డేటాబేస్ లేదా ఈవెంట్ స్ట్రీమ్ లో నిల్వ చేయండి: డెలివరీ రేట్లు, తెరిచి ఉన్న రేట్లు, మరియు క్లిక్-ద్వారా రేట్లు ప్రతి ఛానల్ మరియు నోటిఫికేషన్ రకం వారీగా.
