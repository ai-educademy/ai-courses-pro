# నోటిఫికేషన్ సిస్టమ్ డిజైన్ చేయండి - పుష్, ఇమెయిల్, మరియు SMS బిలియన్ స్కేల్ లో

ఆధునిక అనువర్తనాలు రోజూ బిలియన్ల నోటిఫికేషన్‌లు ను అనేక ఛానళ్లు ద్వారా పంపుతాయి. ఈ వ్యవస్థ ను డిజైన్ చేయడం ద్వారా సందేశ క్యూలు, మూడో పక్ష అనుసంధానాలు, పెద్ద స్థాయిలో వైఫల్యాలు ను సురక్షితంగా నిర్వహించడం నేర్చుకుంటారు.

## దశ 1 - అవసరాలు సేకరణ

### కార్యాత్మక అవసరాలు
- అనేక ఛానళ్లు కు మద్దతు: పుష్ నోటిఫికేషన్‌లు, ఇమెయిల్, SMS, మరియు యాప్‌లో
- వినియోగదారులు తమ నోటిఫికేషన్ అభిరుచులు అమర్చుకోగలగాలి మరియు ప్రతి ఛానల్ కు తప్పుకోవగలగాలి
- వ్యక్తిగతీకరణ తో నమూనా ఆధారిత సందేశాలు (ఉదా., "Hi {పేరు}, మీ క్రమం షిప్ చేయడం అయింది")
- షెడ్యూల్ చేసిన మరియు తక్షణ నోటిఫికేషన్‌లు కు మద్దతు

### అకార్యాత్మక అవసరాలు
- **స్కేల్ సామర్థ్యం** - రోజుకు 10 మిలియన్+ నోటిఫికేషన్‌లు నిర్వహించగలగాలి
- **నమ్మకత** - ఏ నోటిఫికేషన్ కూడా పోకూడదు; కనీసం ఒకసారి డెలివరీ
- **తక్కువ లేటెన్సీ** - అత్యవసరం నోటిఫికేషన్‌లు సెకన్లలో చేరాలి
- **విస్తరించగల** - కొత్త ఛానళ్లు (WhatsApp, Slack) సులభంగా జోడించగలగాలి

<ThinkAboutIt>నోటిఫికేషన్ డెలివరీ ఖచ్చితంగా-ఒకసారి ఉండాలా లేదా కనీసం ఒకసారి ఉండాలా? ఆలోచించండి - నకిలీ SMS రావడం వర్సెస్ ఒక కీలకమైన భద్రత హెచ్చరిక మిస్ అవడం అవడం.</ThinkAboutIt>

## దశ 2 - అధిక-స్థాయి ఆర్కిటెక్చర్

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### మూల భాగాలు
1. **నోటిఫికేషన్ సేవ** - రిక్వెస్ట్‌లు ధృవీకరిస్తుంది, వినియోగదారు అభిరుచులు తనిఖీ చేస్తుంది, నమూనాలు రెండర్ చేస్తుంది, మరియు సందేశాలు క్యూలో పెడుతుంది
2. **సందేశం క్యూలు** - ప్రతి ఛానల్ కు విడిగా క్యూలు, స్వతంత్ర స్కేలింగ్ మరియు వేరుదనం కోసం
3. **డెలివరీ వర్కర్లు** - ఛానల్-స్పష్టంగా వర్కర్లు, మూడో పక్ష API కాల్‌లు నిర్వహిస్తాయి
4. **Template సేవ** - మారే ప్రతిస్థాపన తో నోటిఫికేషన్ నమూనాలు నిల్వ మరియు రెండర్ చేస్తుంది

## దశ 3 - లోతైన అధ్యయనం: కీ భాగాలు

### వినియోగదారు అభిరుచులు మరియు Opt-Out
ప్రతి వినియోగదారు మరియు నోటిఫికేషన్ రకం కు అభిరుచులు నిల్వ చేయండి:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

నోటిఫికేషన్ సేవ క్యూలో పెట్టడానికి **ముందే** అభిరుచులు తనిఖీ చేస్తుంది - వినియోగదారు కోరుకోనిది ఎప్పుడూ పంపకూడదు.

### ప్రాధాన్యం క్యూలు
అన్ని నోటిఫికేషన్‌లు సమానం కావు. ప్రాధాన్యం స్థాయులు వాడండి:
- **కీలకమైన** - భద్రత హెచ్చరికలు, OTP కోడ్‌లు → వెంటనే ప్రక్రియ
- **అధిక** - క్రమం ధృవీకరణలు, చెల్లింపు రసీదులు → సెకన్లలో
- **Medium** - సోషల్ పరస్పర చర్యలు, వ్యాఖ్యలు → నిమిషాల్లో ఆమోదయోగ్యం
- **తక్కువ** - మార్కెటింగ్, సిఫార్సులు → బ్యాచ్ చేయవచ్చు

## దశ 4 - నమ్మకత మరియు విఫలం నిర్వహణ

### డీడూప్లికేషన్
ఐడెంపోటెన్సీ కీ వాడి నకిలీ నోటిఫికేషన్‌లు ను ఆపండి. ప్రక్రియ చేయడానికి ముందు, నోటిఫికేషన్ ID డీడూప్లికేషన్ నిల్వ (Redis తో TTL) లో ఉందో లేదో తనిఖీ చేయండి:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### మళ్లీ ప్రయత్నం తో ఘాతాంక వెనుకడుగు
మూడో పక్ష సేవలు విఫలమవుతుంది అవుతాయి. పెరుగుతున్న ఆలస్యాలతో తో మళ్లీ ప్రయత్నాలు అమలు చేయండి:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### ప్రతి వినియోగదారు రేట్ పరిమితం చేసే
వినియోగదారులు ను నోటిఫికేషన్ fatigue నుండి రక్షించండి:
- ప్రతి వినియోగదారు కు గంటకు గరిష్టంగా 3 పుష్ నోటిఫికేషన్‌లు
- రోజుకు గరిష్టంగా 1 మార్కెటింగ్ ఇమెయిల్
- భద్రత నోటిఫికేషన్‌లు రేట్ పరిమితులు ను దాటివెళ్లడం చేస్తాయి

<FunFact>Facebook రోజూ 10 బిలియన్ కంటే ఎక్కువ పుష్ నోటిఫికేషన్‌లు పంపుతుంది. దీన్ని నిర్వహించడానికి వారు ఒక కస్టమ్ నోటిఫికేషన్ పైప్‌లైన్ నిర్మించారు, ఇది సెకనుకు మిలియన్ల సందేశాలు ప్రాసెస్ చేయగలదు, iOS (APNs) మరియు Android (FCM) కు విడి డెలివరీ మార్గాలు తో.</FunFact>

## దశ 5 - మూడో పక్ష అనుసంధానం

| Channel | ప్రదాత | ప్రోటోకాల్ | సవాళ్లు |
|---------|----------|----------|---------|
| పుష్ (iOS) | APNs | HTTP/2 | టోకెన్ నిర్వహణ, నిశ్శబ్ద పుష్ పరిమితులు |
| పుష్ (Android) | FCM | HTTP | విషయం ఆధారిత ప్రసారం |
| ఇమెయిల్ | SendGrid/SES | SMTP/API | చేరే సామర్థ్యం, స్పామ్ ఫిల్టర్లు |
| SMS | Twilio | REST API | ప్రతి సందేశం కు ఖర్చు, ప్రాంతీయ అనుసరణ |
| లో-App | WebSocket | WS | కనెక్షన్ నిర్వహణ, ఆఫ్‌లైన్ బఫరింగ్ |

### విశ్లేషణలు పైప్‌లైన్
ప్రతి సందేశం యొక్క నోటిఫికేషన్ జీవనచక్రం ను ట్రాక్ చేయండి:
- **Created** → **Queued** → **Sent** → **Delivered** → **Opened** → **Clicked**

డ్యాష్‌బోర్డు నివేదికల కోసం కోసం ఈవెంట్లు ను సమయం-శ్రేణి డేటాబేస్ లేదా ఈవెంట్ స్ట్రీమ్ లో నిల్వ చేయండి: డెలివరీ రేట్లు, తెరవబడిన రేట్లు, మరియు క్లిక్-ద్వారా రేట్లు ప్రతి ఛానల్ మరియు నోటిఫికేషన్ రకం వారీగా.
