# レート リミッターの設計 - 大規模な API の保護

レート制限は、最も実用的なシステム設計トピックの 1 つです。 GitHub から Stripe までのすべての運用 API は、悪用を防止し、公正な使用を保証し、バックエンド サービスを過剰な負荷から保護するためにこれに依存しています。

## ステップ 1 - 要件の収集

### 機能要件
- 構成可能なルール (ユーザー、IP、または API キーごと) に基づいてリクエストを制限します。
- クライアントが調整されている場合に明確なフィードバックを返します (HTTP 429)
- 複数のレート制限ルールを同時にサポート

### 非機能要件
- **低レイテンシー** - リミッターは重大なオーバーヘッドを追加してはなりません
- **分散** - 複数のサーバー間で動作します
- **フォールトトレラント** - リミッターが失敗した場合でも、トラフィックは引き続き流れるはずです (フェールオープン)

<ThinkAboutIt>レート リミッターは、クラッシュ時にフェール オープン (トラフィックを許可) するか、フェール クローズ (トラフィックをブロック) する必要がありますか?電子商取引サイトとバンキング API のトレードオフは何ですか?</ThinkAboutIt>

## ステップ 2 - レート制限アルゴリズム

### 固定ウィンドウカウンター
時間を固定ウィンドウ (60 秒間隔など) に分割します。リクエストごとにカウンターをインクリメントします。ウィンドウ境界でリセットします。 **問題:** ウィンドウの端でのバースト トラフィックにより、制限の 2 倍が許容される可能性があります。

### スライディング ウィンドウ ログ
すべてのリクエストのタイムスタンプを保存します。トレーリング ウィンドウ内のエントリをカウントします。正確ですが、**メモリを大量に消費します** - すべてのタイムスタンプを保存すると、大規模な場合にコストがかかります。

### 引き違い窓カウンター
ハイブリッド: 現在のウィンドウ数と前のウィンドウの加重部分を組み合わせます。精度とメモリ効率のバランスを保ちます。

### トークン バケット アルゴリズム (最も人気のある)
バケットには、最大容量までトークンが保持されます。トークンは固定レートで追加されます。各リクエストは 1 つのトークンを消費します。バケットが空の場合、リクエストは拒否されます。

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### アルゴリズムの比較

|アルゴリズム |メモリ |精度 |バースト処理 |
|----------|----------|----------|-----|
|固定ウィンドウ |低い |低 (エッジバースト) |悪い |
|スライドログ |高 |正確 |良い |
|スライドカウンター |中 |おおよそ |良い |
|トークンバケット |低い |良い |素晴らしい |

## ステップ 3 - 上位レベルのアーキテクチャ

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-rate-limiter.svg" alt="クライアント、レート制限ミドルウェアを備えた API ゲートウェイ、分散状態の Redis クラスター、およびバックエンド サービスを示すレート リミッター アーキテクチャ" caption="レート リミッターは API ゲートウェイ内にあり、分散カウンター ストレージに Redis を使用します" />

### レート リミッターを配置する場所
- **クライアント側** - なりすましが容易で信頼性が低い
- **サーバー側** - インスタンスごとのみ、スケールしません
- **API ゲートウェイ / ミドルウェア** - 分散システムに最適なアプローチ。すべてのインスタンスにわたる一元的な適用

## ステップ 4 - 詳細: 分散レート制限

### Redis + Lua スクリプト
分散セットアップでは、複数のサーバーがレート制限状態を共有する必要があります。 Redis は、アトミックな操作とミリ秒未満のレイテンシを備えているため、標準的な選択肢です。

Lua スクリプトはアトミック性を保証します。チェックアンドデクリメントは単一の Redis 操作で行われ、競合状態を防ぎます。

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### 応答ヘッダー
適切に設計されたレート リミッターは、状態をクライアントに伝えます。
- `X-RateLimit-Limit: 100` - ウィンドウごとの最大リクエスト数
- `X-RateLimit-Remaining: 42` - リクエストが残っています
- `X-RateLimit-Reset: 1672531200` - ウィンドウがリセットされるときの UTC エポック
- HTTP `429 Too Many Requests` (`Retry-After` ヘッダー付き)

<Quiz question="レート制限のために、別々の GET コマンドと SET コマンドではなく、Lua スクリプトが Redis で使用されるのはなぜですか?" options="Lua は Redis コマンドよりも高速です|Lua スクリプトは Redis 上でアトミックに実行され、競合状態を防止します|Redis は GET/SET をネイティブにサポートしていません|Lua はネットワーク帯域幅を削減します" answer="1" explanation="Lua スクリプトは Redis サーバー上でアトミックに実行されます。アトミック性がないと、2 つの同時リクエストが両方とも同じトークン数を読み取り、両方とも利用可能なトークンを確認し、両方とも減分して、制限が許可するよりも多くのリクエストを許可する可能性があります。" />

## ステップ 5 - エッジケースの処理

### 競合状態
アトミック操作を使用しない場合、同時リクエストは制限を回避できます。解決策: Redis Lua スクリプトまたは Redis `MULTI/EXEC` トランザクション。

### レート制限の次元
複数のレベルで制限を同時に適用します。
- **ユーザーごと** - 認証されたユーザーの場合、100 リクエスト/分
- **IP ごと** - 匿名トラフィックの場合、50 リクエスト/分
- **API キーごと** - 段階的プラン (無料: 10/分、プロ: 1000/分)

### 分散クロックスキュー
サーバーのクロックは若干異なる場合があります。アプリケーション サーバーのタイムスタンプに依存するのではなく、Redis サーバー時間を信頼できる唯一の情報源として使用します。

<FunFact>GitHub の REST API では、認証されたユーザーに対しては 1 時間あたり 5,000 件のリクエストが許可されますが、認証されていないリクエストについては 1 時間あたり 60 件しか許可されません。 Stripe は、ライブ モードとテスト モードの API キーに個別の制限を設けたスライディング ウィンドウ アプローチを使用します。</FunFact>

## ステップ 6 - ボトルネックと最適化

|ボトルネック |ソリューション |
|----------|----------|
| Redis の単一障害点 |レプリケーションを使用した Redis クラスター |
| Redis へのネットワーク遅延 |定期的な同期を備えたローカルのメモリ内キャッシュ |
|ホットキー (一般的な API キー) |複数の Redis ノードにわたるシャード |
|ルール評価のオーバーヘッド |プリコンパイルルール、キャッシュ構成 |
