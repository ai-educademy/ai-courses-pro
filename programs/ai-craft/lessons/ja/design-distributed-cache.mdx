# 分散キャッシュを設計する - Redis アーキテクチャをゼロから作成する

キャッシュは、システムのパフォーマンスを向上させるための最も効果的な手法です。適切に設計された分散キャッシュにより、データベースの負荷が 90% 以上削減され、応答時間が数百ミリ秒からミリ秒未満に短縮されます。

## ステップ 1 - 要件の収集

### 機能要件
- オプションの TTL (有効期間) を使用してキーと値のペアを保存します
- 一般的な操作のサポート: GET、SET、DELETE、および一括操作
- 水平スケーリングのためにデータを複数のノードに分散します

### 非機能要件
- **低レイテンシー** - キャッシュ ヒットの読み取りはミリ秒未満
- **高スループット** - ノードごとに 1 秒あたり 100,000 以上の操作
- **高可用性** - キャッシュ障害によってシステムがダウンすることはありません
- **スケーラビリティ** - ダウンタイムなしでノードを追加

### いつキャッシュするか
- **読み取り負荷の高いワークロード** - 読み取り数が書き込み数を大幅に上回る場合
- **高価な計算** - ML モデルの推論結果、複雑な集計
- **頻繁にアクセスされるデータ** - ユーザー セッション、製品カタログ、構成

## ステップ 2 - キャッシュ戦略

### キャッシュアサイド (遅延読み込み)
最も一般的なパターン。アプリケーションは最初にキャッシュをチェックします。失敗した場合は、データベースから読み取り、キャッシュにデータを追加します。

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**長所:** 実際に要求されたもののみをキャッシュします。 **短所:** キャッシュミスにより遅延が発生します。データが古くなってしまう可能性があります。

### 既読スルー
キャッシュ自体は、ミス時のデータベース読み取りを処理します。アプリケーションは、データ ソースを抽象化するキャッシュ層とのみ通信します。

### ライトスルー
すべての書き込みはキャッシュとデータベースの両方に同期して行われます。キャッシュが常に一貫していることを保証しますが、書き込み遅延が追加されます。

### ライトビハインド (ライトバック)
書き込みはすぐにキャッシュに保存されます。キャッシュはバッチでデータベースに非同期的にフラッシュされます。書き込みレイテンシは低くなりますが、フラッシュする前にキャッシュ ノードがクラッシュするとデータが失われる危険性があります。

|戦略 |一貫性 |読み取りレイテンシ |書き込みレイテンシ |使用例 |
|----------|---------------|---------------|--------------|----------|
|キャッシュアサイド |最終的な |ミスペナルティ |該当なし |汎用 |
|読み切り |最終的な |ミスペナルティ |該当なし |簡略化された読み取り |
|ライトスルー |強い |速い |遅い |一貫性が重要 |
|後書き |最終的な |速い |速い |書き込み負荷の高いワークロード |

## ステップ 3 - 立ち退きポリシー

キャッシュがいっぱいになった場合、どのエントリを削除すればよいでしょうか?

- **LRU (最も最近使用されていない)** - 長期間アクセスされていないエントリを削除します。最適な汎用ポリシー
- **LFU (最も頻繁に使用されない)** - アクセス頻度が最も低いエントリを削除します。偏ったアクセスパターンに適しています
- **TTL ベース** - アクセスに関係なく、エントリは設定された時間が経過すると期限切れになります。データの鮮度に不可欠
- **ランダム** - 驚くほど効果的で、実装は非常に簡単です

<FunFact>Redis は、少数のキー (デフォルト: 5) をサンプリングし、その中で最も最近使用されていないキーを削除する近似 LRU アルゴリズムを使用します。これは真の LRU とほぼ同じ精度ですが、アクセス順序を追跡するために追加のメモリ オーバーヘッドは必要ありません。</FunFact>

## ステップ 4 - 配布用の一貫したハッシュ

### 単純なハッシュの問題
`hash(key) % N` ノードの場合、ノードを追加または削除すると、ほぼすべてのキーが再マップされ、大規模なキャッシュ ミス ストームが発生します。

### 仮想ノードによる一貫性のあるハッシュ
一貫したハッシュでは、キーとノードの両方がリングにマッピングされます。各キーはリング上で時計回りに次のノードに割り当てられます。

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**仮想ノード** は、不均一な分散の問題を解決します。各物理ノードはリング上で複数の位置を取得し、物理ノードが少ない場合でも負荷のバランスを確保します。

ノードが追加または削除されると、リング上のそのノードに隣接するキーのみが再マップされます。すべてではなく、約 `K/N` キー (K は合計キー、N はノード数) です。

<Quiz question="キャッシュ クラスターには 4 つのノードがあります。ノード 3 に障害が発生します。単純なモジュロ ハッシュ (キー % 4 → キー % 3) では、何パーセントのキーが再マッピングされますか?" options="25% (ノード 3 のキーのみ)|50%|75% - ほぼすべてのキーが再マップされます|100%" answer="2" explanation="mod 4 から mod 3 に変更すると、すべてのキーの約 75% が別のノードに再マッピングされます。たとえば、7 にハッシュされたキーはノード 3 (7%4=3) にありましたが、現在はノード 1 (7%3=1) に移動します。これにより、キャッシュミスが大幅に急増します。一貫性のあるハッシュでは、~K/N 個のキーを再マッピングするだけでこの問題を解決できます。" />

## ステップ 5 - キャッシュスタンピードの防止

**キャッシュ スタンピード**は、人気のあるキャッシュされたエントリの有効期限が切れ、数百の同時リクエストが同時にキャッシュをミスしてデータベースにヒットしたときに発生します。

### ソリューション

**ミューテックス/ロック:** キャッシュミスが発生した場合、分散ロックを取得します。データベースからフェッチされるリクエストは 1 つだけです。他のものはキャッシュが再設定されるのを待ちます。

**確率的早期有効期限:** 各リクエストには、TTL が実際に期限切れになる前にキャッシュを更新するランダムな確率がわずかにあります。これにより、有効期限が切れたときに激しい群れを作成するのではなく、時間の経過とともに更新負荷が分散されます。

**バックグラウンド更新:** バックグラウンド プロセスは、人気のあるキャッシュ エントリを有効期限が切れる前に更新します。ホットキーのキャッシュが空になることはありません。

<ThinkAboutIt>商品ページが 1 秒あたり 100,000 件のリクエストを受け取るフラッシュ セールを考えてみましょう。製品詳細キャッシュ エントリの有効期限が切れます。スタンピードを防止しないと、100,000 個のリクエストすべてが同時にデータベースにヒットします。どの予防戦略を選択しますか?その理由も教えてください。</ThinkAboutIt>

## ステップ 6 - Redis クラスターのアーキテクチャ

Redis Cluster は、最も広く導入されている分散キャッシュです。

- **16,384 のハッシュ スロット** マスター ノード全体に分散
- 各キーは `CRC16(key) % 16384` を介してスロットにマッピングされます
- **レプリケーション:** 各マスターにはフェイルオーバー用に 1 つ以上のレプリカがあります
- **自動フェイルオーバー:** マスターに障害が発生した場合、そのレプリカは数秒以内に昇格されます。

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### 主要な指標のモニタリング
- **ヒット率** - 目標 95%+; 80% 未満はキャッシュの問題を示します
- **メモリ使用量** - エビクションを避けるために 80% 未満に維持してください
- **エビクション率** - エビクションが高いということは、キャッシュのサイズが小さいことを意味します
- **レイテンシのパーセンタイル** - キャッシュ ヒットの p99 は 1ms 未満である必要があります

## ステップ 7 - 現実世界のキャッシュ パターン

|パターン |実装 | TTL |
|----------|---------------|-----|
|セッションストア | `SET session:{id} {data}` | 30分 |
| API 応答キャッシュ | `SET api:/users/123 {json}` | 5分 |
|データベースクエリキャッシュ | `SET query:{hash} {result}` | 1分 |
|レート リミッタ カウンタ | `INCR ratelimit:{user}:{window}` |ウィンドウ期間 |
|機能フラグ | `HSET features {flag} {value}` | 10秒 |

### キャッシュの無効化
コンピューターサイエンスにおける最も難しい問題 (物の名前と並んで):
- **TTL ベース** - シンプルで、TTL 期間中の古い状態を許容します
- **イベントドリブン** - データ変更時に無効化イベントを発行します (Kafka または Redis Pub/Sub 経由)
- **バージョンベース** - キャッシュ キーにバージョンを含めます。書き込み時にバージョンをインクリメントして、古いエントリを効果的に無効にします
