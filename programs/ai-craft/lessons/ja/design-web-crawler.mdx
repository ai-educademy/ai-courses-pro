# Web クローラーを設計する - Google がインターネットにインデックスを付ける方法

Web クローラーは、体系的にインターネットを参照して、Web ページをダウンロードし、インデックスを付けます。これはあらゆる検索エンジンの基礎であり、検索エンジンを設計することで、分散システム、グラフ トラバーサル、実際の Web の混乱の処理について学びます。

## ステップ 1 - 要件の収集

### 機能要件
- 一連のシード URL から開始して Web ページをクロールします。
- ハイパーリンクを抽出してたどって、新しいページを発見します
- インデックス作成と処理のためにダウンロードしたコンテンツを保存します
- robots.txt を尊重し、礼儀正しさのルールをクロールする

### 非機能要件
- **スケール** - 毎月 10 億ページをクロール
- **礼儀正しさ** - 単一の Web サーバーに負荷をかけないこと
- **鮮度** - 重要なページを定期的に再クロールします
- **堅牢性** - 不正な形式の HTML、無限ループ、スパイダー トラップを処理します

## ステップ 2 - 上位レベルのアーキテクチャ

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## ステップ 3 - クロール ループ

### BFS と DFS クロール
- **BFS (幅優先)** - Web クローリングに推奨されます。広範囲のドメインを迅速に検出し、単一サイトの奥深くに閉じ込められることを回避します。
- **DFS (深さ優先)** - 他のドメインを発見する前に、動的に生成されたページに無限に深く入るリスクがあります。

### URL フロンティアデザイン
フロンティアは単純なキューではなく、次の 2 つのサブコンポーネントを備えた高度な優先順位システムです。

1. **優先キュー (フロント)** - 重要度によって URL をランク付けします。要素には、PageRank、更新頻度、ドメイン権限が含まれます
2. **ポライトネス キュー (バック)** - 各ドメインに独自の FIFO キューがあることを保証します。スケジューラは、単一のサーバーに負荷がかかることを避けるために、さまざまなドメイン キューから選択します。

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## ステップ 4 - 礼儀正しさと Robots.txt

### Robots の尊重.txt
ドメインをクロールする前に、その `robots.txt` ファイルをフェッチしてキャッシュします。

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

robots.txt をドメインごとに TTL (24 時間) でキャッシュします。 `Disallow` ルールと `Crawl-delay` 指示を常に遵守してください。

### クロール レートの制限
明示的な `Crawl-delay` がなくても、礼儀正しさを維持してください。
- ドメインごとに 1 秒あたり最大 1 リクエスト (構成可能)
- ドメインごとに個別のダウンロード キューを使用する
- 応答時間を追跡 - サーバーの速度が低下した場合は、自動的に停止します

<FunFact>Google のウェブ クローラー (Googlebot) は、数千億のページをクロールします。丁寧に言うと、サーバーの応答時間を監視し、サイトの応答が遅くなった場合はクロール レートを下げ、Web サイトがクローラーに対して効果的に「プッシュバック」できるようにします。</FunFact>

## ステップ 5 - 重複排除

### URL 重複排除 (ブルーム フィルター)
URL が数十億ある場合、URL が以前に参照されたかどうかを確認するには、効率的なデータ構造が必要です。ブルーム フィルターは、少ないメモリ フットプリントで O(1) ルックアップを提供します。

- **スペース:** 誤検知率 1% の場合、10 億 URL に対して最大 1 GB
- **トレードオフ:** 場合によってはページを再クロールすることがありますが (誤検知)、新しい URL を見逃すことはありません (誤検知はありません)。

チェックする前に URL を正規化します。フラグメント (#) を削除し、クエリ パラメーターを並べ替え、ホスト名を小文字にし、相対パスを解決します。

### コンテンツ重複排除 (SimHash)
異なる URL で同一のコンテンツ (ミラー、コピーされた記事) を提供できます。 SimHash はページ コンテンツのフィンガープリントを生成します。同様のフィンガープリント (ハミング距離が小さい) を持つページは重複している可能性があります。

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## ステップ 6 - 分散クロール

### 水平方向のスケーリング
1 台のマシンで毎月 10 億ページをクロールすることはできません。作品を配布します:

- ドメイン名の **一貫したハッシュ** により、各ドメインが特定のクローラ ノードに割り当てられます。これにより礼儀正しさが保証されます。指定されたドメインをクロールするノードは 1 つだけです
- **URL フロンティア**はハッシュ リングに基づいてノード間で分割されます
- ノードの割り当てを管理し、ノードが参加または離脱するときに再バランスを行う軽量サービスを介した **調整**

### DNS 解決キャッシュ
DNS ルックアップでは、リクエストごとに 10 ～ 100 ミリ秒が追加されます。大規模になると、これが大きなボトルネックになります。
- クローラー ノードごとにローカル DNS キャッシュを維持する
- キューに入れられた URL のバッチ DNS 事前解決
- 専用の DNS リゾルバーを使用して、パブリック DNS サーバーに負荷がかかるのを回避します。

### クモトラップの検出
悪意のあるサイトや構築が不十分なサイトでは、無限の URL スペースが作成される可能性があります。
- `/page/1/page/1/page/1/...` - パスパターンの繰り返し
- 将来の日付ごとに URL を生成するカレンダー ページ
- 同一のコンテンツに対して一意の URL を作成する URL 内のセッション ID

**防御:** URL の最大長、ドメインごとの最大クロール深度、反復的な URL 構造のパターン検出、およびドメインレベルのページ数制限。

## ステップ 7 - ボトルネックと最適化

|ボトルネック |ソリューション |
|----------|----------|
| DNS 解決の遅延 |ローカル DNS キャッシュ、バッチ事前解決 |
|サーバーが遅い/応答しない |タイムアウト (30 秒)、非同期 I/O、再試行後のスキップ |
|クロールされたコンテンツのストレージ |ページを圧縮し、変更されたコンテンツのみを保存 |
| URL フロンティアメモリー |ディスクバックアップの優先キュー (RocksDB) |
|重複したコンテンツ | SimHash フィンガープリンティング、正規 URL 検出 |

<ThinkAboutIt>検索エンジンは、クロールの鮮度 (ページを頻繁に再クロールする) と検出 (新しいページを見つける) のバランスを取る必要があります。クローラーの固定予算が 1 日あたり 100 万ページである場合、その予算を既存のページの再クロールと新しいページの検出にどのように分割しますか?</ThinkAboutIt>
