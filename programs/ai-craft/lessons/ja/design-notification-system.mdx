# 通知システムの設計 - 数十億規模のプッシュ、電子メール、SMS

最新のアプリケーションは、複数のチャネルにわたって毎日数十億件の通知を送信します。このシステムの設計では、メッセージ キュー、サードパーティの統合、および大規模な障害の適切な処理について学びます。

## ステップ 1 - 要件の収集

### 機能要件
- 複数のチャネルをサポート: プッシュ通知、電子メール、SMS、アプリ内
- ユーザーは通知設定を構成し、チャネルごとにオプトアウトできます
- パーソナライズされたテンプレート化されたメッセージ (例: 「こんにちは、{名前}、ご注文は発送されました」)
- スケジュールされた通知と即時通知のサポート

### 非機能要件
- **スケーラビリティ** - 1 日あたり 1,000 万件以上の通知を処理
- **信頼性** - 通知が失われることはありません。少なくとも 1 回の配信
- **低遅延** - 緊急通知は数秒以内に配信されます
- **拡張性** - 新しいチャネルを簡単に追加できます (WhatsApp、Slack)

<ThinkAboutIt>通知の配信は 1 回だけ行うべきですか、それとも少なくとも 1 回行うべきですか?重複した SMS を受信した場合と、重要なセキュリティ警告を見逃した場合のユーザー エクスペリエンスを考慮してください。</ThinkAboutIt>

## ステップ 2 - 上位レベルのアーキテクチャ

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### コアコンポーネント
1. **通知サービス** - リクエストを検証し、ユーザー設定を確認し、テンプレートをレンダリングし、メッセージをキューに入れます。
2. **メッセージ キュー** - 独立したスケーリングと分離を実現するチャネルごとに個別のキュー
3. **デリバリー ワーカー** - サードパーティ API 呼び出しを処理するチャネル固有のワーカー
4. **テンプレート サービス** - 変数置換を使用して通知テンプレートを保存およびレンダリングします

## ステップ 3 - 詳細: 主要コンポーネント

### ユーザー設定とオプトアウト
ユーザーごとおよび通知タイプごとに設定を保存します。

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

通知サービスはキューに入れる前に設定をチェックします。ユーザーが望まないものは決して送信しません。

### 優先キュー
すべての通知が同じというわけではありません。優先レベルを使用します。
- **重要** - セキュリティ アラート、OTP コード → すぐに処理されます
- **高** - 注文確認、支払い受領 → 数秒
- **中** - ソーシャル インタラクション、コメント → 分単位で許容可能
- **低** - マーケティング、レコメンデーション → バッチ処理可能

## ステップ 4 - 信頼性と障害の処理

### 重複排除
冪等キーを使用して重複した通知を防止します。処理する前に、通知 ID が重複排除ストア (TTL を備えた Redis) に存在するかどうかを確認します。

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### 指数バックオフによる再試行
サードパーティのサービスが失敗します。遅延を増やして再試行を実装します。

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### ユーザーごとのレート制限
ユーザーを通知疲れから保護します。
- ユーザーあたり 1 時間あたり最大 3 つのプッシュ通知
- 1 日あたり最大 1 件のマーケティングメール
- セキュリティ通知はレート制限をバイパスします

<FunFact>Facebook は毎日 100 億件を超えるプッシュ通知を送信します。これに対処するために、iOS (APN) と Android (FCM) に個別の配信パスを使用して、1 秒あたり数百万のメッセージを処理できるカスタム通知パイプラインを構築しました。</FunFact>

## ステップ 5 - サードパーティの統合

|チャンネル |プロバイダー |プロトコル |課題 |
|-----------|----------|----------|-----------|
|プッシュ (iOS) | APN | HTTP/2 |トークン管理、サイレントプッシュ制限 |
|プッシュ (Android) | FCM | HTTP |話題性放送 |
|電子メール |センドグリッド/SES | SMTP/API |到達性、スパムフィルター |
| SMS |トゥイリオ | REST API |メッセージあたりのコスト、地域のコンプライアンス |
|アプリ内 |ウェブソケット | WS |接続管理、オフラインバッファリング |

### 分析パイプライン
すべてのメッセージの通知ライフサイクルを追跡します。
- **作成** → **キューに登録** → **送信** → **配信** → **開封** → **クリック**

イベントを時系列データベースまたはイベント ストリームに保存して、チャネルおよび通知タイプごとの配信率、開封率、クリックスルー率などのダッシュボード レポートを作成します。

## ステップ 6 - ボトルネックと最適化

|ボトルネック |ソリューション |
|----------|----------|
|サードパーティのレート制限 |プロバイダーごとにスループットを制御したキュー |
|大規模なテンプレートのレンダリング |共通テンプレートを事前レンダリングしてキャッシュする |
|メッセージごとのプリファレンス検索 | Redis でユーザー設定をキャッシュする |
|ピーク時のトラフィックの急増 |キューの深さに基づいてワーカーを自動スケール |
|地域を越えた配送 |プロバイダーのエンドポイントの近くにワーカーをデプロイする |

<ThinkAboutIt>ブラック フライデー セールの 5,000 万件のパーソナライズされた電子メールを 2 時間以内に送信しながら、1 秒未満の遅延でリアルタイムのセキュリティ警告を配信できる通知システムをどのように設計しますか?</ThinkAboutIt>
