## 面接プロンプト

*「1 対 1 のメッセージング、グループ チャット、オンライン プレゼンス インジケーターをサポートする WhatsApp や Slack などのチャット アプリケーションを設計します。」*

これは、リアルタイム通信、接続管理、大規模なストレージ、分散システムのトレードオフをすべて 1 つの問題としてテストするため、システム設計の面接で人気があります。

## ステップ 1: 要件の収集

**機能要件:**
- 配信および開封確認を含む 1 対 1 のメッセージング
- グループチャット（最大500人のメンバー）
- オンライン/オフラインのプレゼンスインジケーター
- メッセージ履歴と検索
- オフライン ユーザーへのプッシュ通知

**非機能要件:**
- 低遅延: メッセージは 200 ミリ秒以内に配信されます
- 高可用性: 99.99% の稼働時間
- 会話内でのメッセージの順序付けが保証される
- 5,000 万の同時接続をサポート

<Callout>非機能要件を常に具体的な数値で定量化します。 「高速配信」は曖昧です。「200 ミリ秒未満の配信」は、ドメインを理解していることを示します。
</Callout>

## ステップ 2: API 設計

REST 専用システムとは異なり、チャットには **双方向通信** が必要です。 2 つのプロトコルが必要です。

**REST API** (非リアルタイム操作用):
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket** (リアルタイム メッセージング用):
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## ステップ 3: WebSocket 接続管理

接続されている各ユーザーは、永続的な WebSocket 接続を維持します。同時ユーザー数が 5,000 万人になると、これはエンジニアリング上の重大な課題になります。

**接続サーバー** (ゲートウェイ サーバーと呼ばれることもあります) は、WebSocket 接続を保持します。各サーバーはおよそ 50,000 ～ 100,000 の同時接続を処理できます。つまり、500 ～ 1,000 の接続サーバーが必要になります。

**接続レジストリ** (Redis クラスター) は、各ユーザーを接続サーバーにマップします。
```
user_123 → ws-server-042
user_456 → ws-server-187
```

ユーザー A がユーザー B にメッセージを送信するときのフローは次のとおりです。
1. メッセージは WebSocket 経由で A の接続サーバーに到着します
2. サーバーは Redis で B の接続サーバーを検索します
3. メッセージは内部メッセージング経由で B の接続サーバーにルーティングされます。
4. B のサーバーがメッセージを B の WebSocket にプッシュします。

## ステップ 4: メッセージの保存

チャット アプリケーションは膨大な量のデータを生成します。 WhatsApp は毎日 1,000 億を超えるメッセージを処理します。

**ストレージ戦略:**
- **最近のメッセージ** - 会話 ID によってパーティション化された高速データストア (Cassandra または HBase) に保存されます。
- **メッセージ インデックス** - Elasticsearch による検索が可能になります
- **メディア ファイル** - CDN 配信によりオブジェクト ストレージ (S3) に保存されます

**スキーマ設計 (Cassandra):**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

この設計により、会話内のすべてのメッセージが同じパーティションに同じ場所に配置されるため、「古いメッセージの読み込み」クエリが非常に効率的になります (1 つのパーティション内で順次読み取りを行うだけです)。

## ステップ 5: プレゼンス システム

誰がオンラインであるかを表示するのは簡単なようですが、規模が大きくなると驚くほど難しいものです。連絡先リスト内のすべてのユーザーについてデータベースを数秒ごとにポーリングすることはできません。

**ハートビートアプローチ:**
1. 接続されたクライアントは WebSocket 経由で 30 秒ごとにハートビートを送信します
2. サーバーは、60 秒の TTL で Redis キーを更新します: `presence:user_123 → online (TTL 60s)`
3. ハートビートが到着しない場合、キーの有効期限が切れ、ユーザーはオフラインとして表示されます。

**ステータス更新用のファンアウト:**
ユーザーがオンラインになると、そのステータスが同じくオンラインであるすべての連絡先にプッシュされる必要があります。 500 件の連絡先を持つユーザーの場合、これはどの連絡先がオンラインであるかを確認し、それらの連絡先にのみプレゼンス更新を送信することを意味します。**遅延ファンアウト** により、オフライン ユーザーへのブロードキャストが回避されます。

<FunFact>WhatsApp の「最後に見た」機能は、世界中で予期せぬ社会ドラマを引き起こしました。一部の国では、パートナーが互いの正確な最終アクティブ タイムスタンプを確認できるため、関係に関する紛争が急増しました。 WhatsApp は最終的に、この情報を非表示にするプライバシー制御を追加しました。
</FunFact>

## ステップ 6: プッシュ通知

ユーザーがオフラインの場合 (アクティブな WebSocket がない場合)、メッセージはプッシュ通知経由でユーザーに届く必要があります。

メッセージ フローが変わります。
1. 接続レジストリでユーザー B がオフラインであることが示される
2. メッセージは「未配信」ステータスでデータベースに保存されます。
3. 通知サービスが APN (iOS) または FCM (Android) 経由でプッシュを送信します。
4. ユーザー B が再接続すると、未配信のメッセージが取得され、WebSocket 経由で送信されます。
5. 受領確認のため、納品書を返送します。

<ThinkAboutIt>500 人のメンバーとのグループ チャットでは、ファンアウトの課題が生じます。 400 人のメンバーがオフラインであるグループにメッセージが送信された場合、プッシュ通知は 400 件になります。ピーク時の大量の通知サービスを避けるために、これらをバッチ処理してレート制限するにはどうすればよいでしょうか?
</ThinkAboutIt>

## ステップ 7: エンドツーエンド暗号化の基本

インタビューでのディスカッションで E2E 暗号化について簡単に言及すると、セキュリティに対する意識が表れます。

- 各ユーザーは自分のデバイス上で **公開鍵/秘密鍵のペア**を生成します
- メッセージは、送信者のデバイスから送信される前に受信者の公開キーで暗号化されます。
- サーバーは暗号文のみを参照し、メッセージの内容を読み取ることはできません
- グループ チャットでは、メンバーが参加または脱退するときにローテーションされる **共有グループ キー**を使用します

これは、サーバーのメッセージ ストレージには暗号化された BLOB のみが含まれていることを意味し、データ コンプライアンスの観点からは実際にはこれがより簡単です。

## ステップ 8: 数百万に拡張する

**主要なスケーリング戦略:**
- **接続サーバー** は水平方向に拡張可能 - ユーザーの増加に応じてサーバーを追加します
- **メッセージ ルーティング** は、サーバー間通信に Kafka または Redis Pub/Sub を使用します
- 会話 ID による **データベース シャーディング** により、ストレージの負荷が分散されます
- **地理的分散** - 接続サーバーを複数の地域に展開して遅延を削減します
- **メッセージ キューのバッファリング** - 使用量のピーク時のスパイクを吸収します。

## チャット システム設計のための面接のヒント

1. **WebSocket の決定から始めます** - この規模では HTTP ポーリングが機能しない理由を説明します
2. **接続容量を定量化** - サーバーの制限 (サーバーあたり最大 50 ～ 100,000 の接続) を理解していることを示します。
3. **オフライン配信に取り組む** - 多くの候補者は、ユーザーが常に接続しているわけではないことを忘れています
4. **メッセージの順序付けについて言及** - 競合解決を備えたタイムスタンプベースの順序付け

<ThinkAboutIt>Slack と WhatsApp は、メッセージ履歴に対してまったく異なるアプローチを採用しています。 WhatsApp はメッセージをデバイスに保存し、完全な履歴を新しいデバイスに同期しません。 Slack はすべてをサーバー側に保存し、完全な検索を提供します。各アプローチのプライバシー、コスト、ユーザー エクスペリエンスのトレードオフは何ですか?
</ThinkAboutIt>

## 重要なポイント

- チャット システムにはリアルタイムの双方向通信のために WebSocket が必要です
- 大規模な接続管理には、ユーザーをサーバーにマッピングするレジストリが必要です
- Cassandra の書き込みスループットとパーティションベースのクエリはチャット メッセージのストレージに適しています
- プレゼンス システムは、Redis で TTL ベースの有効期限を持つハートビートを使用します
- プッシュ通知はオフラインのメッセージ配信を処理します
- 地理的分散と水平スケーリングにより、グローバルなレイテンシ要件に対応
