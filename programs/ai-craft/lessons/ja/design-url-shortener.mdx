## 面接プロンプト

*「長い URL を受け取り、短くて固有のコードを生成する bit.ly のような URL 短縮サービスを設計します。」*

これは、一見単純ですが、API 設計、エンコード戦略、データベースの選択、キャッシュ、スケーリングなどの中心的な概念をカバーしているため、システム設計の最初の質問として最も一般的です。レッスン 1 の構造化されたフレームワークを使用して作業してみましょう。

## ステップ 1: 要件の収集 (5 分)

**機能要件:**
- 長い URL を指定すると、短い一意の URL を生成します
- 短い URL 経由でリダイレクトすると、元の長い URL が返されます。
- ユーザーはオプションでカスタムショートコードを設定できます
- リンクは設定可能な期間が経過すると期限切れになります (デフォルト: 5 年)
- 基本的な分析: クリック数、リファラー、地理

**非機能要件:**
- 毎月 1 億件の URL が生成 (1 秒あたり約 40)
- 読み取り負荷が高い: 読み取りと書き込みの比率 100:1 → 1 秒あたり 4,000 回のリダイレクト
- URL リダイレクトの遅延は 50 ミリ秒未満
- 短縮 URL はできるだけ短くする必要があります。
- 高可用性 - リンク切れはひどいユーザーエクスペリエンスをもたらします

<Callout>すべてのシステム設計面接は、明確な質問から始めます。明示的な数字 (40 書き込み/秒、4,000 読み取り/秒) を書き留めることで、規模について定量的に推論できることがわかります。
</Callout>

## ステップ 2: API 設計 (5 分)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**なぜ HTTP 301 と 302 を使うのですか?**
- **301 (永続リダイレクト)** - ブラウザーがキャッシュし、サーバーの負荷を軽減します。
- **302 (一時リダイレクト)** - ブラウザは常に当社のサーバーにアクセスするため、正確な分析が可能になります。

クリックを追跡するサービスの場合、すべてのリダイレクトがサーバーを通過するため、通常は **302 がより良い選択です**。

## ステップ 3: エンコード戦略

中心的な課題は、短くてユニークなコードをどのように生成するかということです。

**Base62 エンコード** では、`[a-zA-Z0-9]` - 62 文字が使用されます。 7 文字のコードでは 62⁷ = **3.5 兆** の一意の組み合わせが得られ、これは当社の規模には十分以上です。

**オプション A - カウンターベース:**
- 自動インクリメントカウンター (1、2、3、...) を使用し、base62 に変換します。
- カウンタ 1000 → `g8` |カウンタ 1000000 → `4c92`
- **長所:** ユニークでシンプル、衝突がないことが保証されています
- **短所:** 予測可能 (ユーザーは次の URL を推測できる)、集中カウンターが必要

**オプション B - ハッシュベース:**
- 長い URL を MD5/SHA-256 でハッシュし、base62 の最初の 7 文字を取得します。
- **長所:** ステートレス、中央調整が不要
- **短所:** 衝突の可能性 - データベースを確認して再試行する必要があります

**オプション C - 事前に生成されたキー (推奨):**
- バックグラウンド サービスが数百万の一意の Base62 コードを事前に生成し、キー プールに保存します。
- 新しい URL が到着したら、プールから次に利用可能なコードを取得します。
- **長所:** 高速、衝突リスクなし、予測可能性なし
- **短所:** キー生成サービスの管理が必要

<FunFact>オリジナルの TinyURL サービスは 2002 年に開始され、現在も実行されています。ある時点では、1 日あたり 100 万を超える短縮 URL が生成されていました。 tinyurl.com というドメイン自体は非常に象徴的なものになっているため、「tinyurl」は URL 短縮の総称として使用されています。
</FunFact>

## ステップ 4: データベースの選択とスキーマ

毎月 1 億件の新しい URL と 5 年間の保存期間により、約 **60 億レコード** が保存されます。これは、単純なキーと値の検索を伴う読み取り負荷の高いワークロードです。

**データベースの選択: DynamoDB または Cassandra**
- ルックアップは常にショート コード (パーティション キー) によって行われます - 複雑な結合は必要ありません
- どちらも水平スケーリングで大量の読み取りスループットを処理します
- どちらもパーティション キーによる 10 ミリ秒未満のルックアップを提供します

**スキーマ:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

分析用に、別の時系列テーブルに個々のクリック イベントが保存されます。
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## ステップ 5: キャッシュ戦略

1 秒あたり 4,000 回の読み取りとヘビーテール配信 (一部の URL では数百万回のクリックが発生しますが、ほとんどの URL ではごくわずかしか発生しません) では、キャッシュが不可欠です。

**Redis キャッシュ** には、最も頻繁にアクセスされるマッピングが保存されます。
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**キャッシュ ヒット フロー (高速パス):**
1. リクエストが到着します: `GET /aB3kx9`
2. Redisを確認→キャッシュヒット→302リダイレクトを返す
3. クリック イベントを Kafka に非同期的に記録します。

**キャッシュミスフロー:**
1.Redisをチェック→ミス
2. データベースにクエリ → 見つかった
3. Redis キャッシュを設定する
4. リターン 302 リダイレクト

キャッシュ ヒット率が 80% の場合、1 秒あたり 4,000 リクエストのうち実際にデータベースに到達するのは 800 リクエストのみです。

## ステップ 6: 分析とクリック追跡

クリック追跡によりリダイレクトが遅くなってはなりません。分析が非同期で処理されている間、リダイレクト応答はすぐに返される必要があります。

**アーキテクチャ:**
1. リダイレクト ハンドラーがクリック イベントを **Kafka** に発行します
2. クリック処理サービスはイベントを消費し、次のことを行います。
 - URL レコードの `click_count` をインクリメントします
 - 詳細なクリック データをクリック テーブルに書き込みます
 - ストリーミング集約を介してリアルタイムのダッシュボードを更新します

この分離により、遅い分析パイプラインがリダイレクトのレイテンシに影響を与えることがなくなります。

<ThinkAboutIt>URL 短縮ツールは、悪意のあるリンクを偽装するために使用されることがあります。 bit.ly を設計している場合、短縮プロセスに大幅な遅延を加えずに、フィッシングやマルウェアがないかリンク先 URL をスキャンする安全性チェックをどのように実装しますか?
</ThinkAboutIt>

## ステップ 7: システムのスケーリング

**水平スケーリングアプローチ:**
- **API サーバー** はステートレスです - ロード バランサーの背後にインスタンスを追加することでスケールします
- **キー生成サービス**は、事前に生成されたコードの独自のデータベースを備えた別個のマイクロサービスとして実行されます。
- **Redis クラスター** は、一貫したハッシュを使用してノード間のキャッシュ分散を処理します
- ショートコードの最初の文字による**データベースシャーディング**により、データが均等に分散されます。

**ピーク負荷の処理:**
- バイラル イベント中は、単一の URL が 1 分あたり数百万件のヒットを受信する可能性があります。
- Redis キャッシュはこれを自然に吸収します - 1 つのキャッシュ エントリが無制限の読み取りを処理します
- Kafka はクリック イベントをバッファーし、分析データベースへの書き込み負荷を平滑化します。

<Quiz question="URL が急速に広まり、1 分あたり 500,000 回のクリックが発生します。影響を受けない可能性が最も高いコンポーネントはどれですか?" options="Redis キャッシュ (単一のキーがすべてのリクエストに対応)|Kafka のクリックイベント コンシューマー|分析データベースの書き込みパス|APIサーバーのCPU" answer="0" explanation="Redis は、キャッシュされた 1 つのキーに対する 1 秒あたり数百万件の読み取りを簡単に処理します。 Kafka コンシューマと分析データベースは 500K の書き込み/分に直面し、API サーバーは 500K のリクエスト/分を処理し、すべて大きな負荷がかかります。" />

<ThinkAboutIt>bit.ly のような企業は、毎月数十億件のリダイレクトを処理します。短縮 URL が看板やテレビ広告で共有されると、トラフィックが数秒でゼロから数百万に急増する可能性があります。このような突然の予測不可能なトラフィックの急増を吸収するために、キャッシュ以外にどのような戦略を使用しますか?
</ThinkAboutIt>

<FunFact>2009 年、bit.ly は 1 日あたり 8,000 万以上のクリックを処理していました。国コードが .ly であるリビアが政情不安を理由に .ly ドメインを一時的に削除したとき、何百万もの短縮リンクが一時的に機能しなくなり、インターネット全体にパニックを引き起こしました。
</FunFact>

## 重要なポイント

- フレームワークに従います: 要件 → API → エンコーディング → データモデル → アーキテクチャ → 詳細
- 7 文字の Base62 は 3.5 兆個の一意のコードを生成 - 十分すぎる
- 事前に生成されたキープールにより、衝突の問題と中央カウンターのボトルネックを回避します
- 正確なクリック分析が必要な場合は、301 ではなく 302 リダイレクトを使用します。
- Redis キャッシュにより、読み取り負荷の高いワークロードのデータベース負荷が大幅に軽減されます。
- 非同期処理に Kafka を使用してリダイレクト パスから分析を分離する
