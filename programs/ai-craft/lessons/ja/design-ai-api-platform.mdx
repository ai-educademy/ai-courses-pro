## 面接プロンプト

*「OpenAI や Hugging Face が大規模にモデルを提供する方法と同様に、REST API を介して開発者に複数の機械学習モデルを提供する AI API プラットフォームを設計します。」*

この質問は、**API プラットフォーム設計** と AI ワークロードに特有の **GPU インフラストラクチャの課題** を組み合わせているため、インタビューでの人気が高まっています。

## ステップ 1: 要件の収集

**機能要件:**
- REST API 経由で複数の AI モデル (テキスト生成、画像分類、埋め込み) を提供します
- キーごとの使用量割り当てによる API キー認証
- API呼び出しごとの使用状況の追跡と請求
- A/B テストによる複数のモデル バージョンのサポート
- 長時間実行される生成タスクのストリーミング応答

**非機能要件:**
- レイテンシー: 埋め込みモデルの場合は p50 500 ミリ秒未満、生成モデルの場合は p50 2 秒未満
- スループット: すべてのモデルで 1 秒あたり 10,000 リクエスト
- 可用性: 99.9% の稼働率 (グレースフル デグラデーション)
- コスト効率: GPU は高価です - 使用率を最大化します

<Callout>AI プラットフォームには固有の可変遅延があります。テキスト補完リクエストは、出力の長さに応じて 200 ミリ秒または 30 秒かかる場合があります。設計でこの差異をどのように処理するかについて常に議論してください。
</Callout>

## ステップ 2: API 設計

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-4", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - list available models
GET  /v1/usage?start=2024-01-01    - usage and billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

**サーバー送信イベント (SSE)** を介したストリーミングは、生成モデルにとって重要です。ユーザーは、完全な応答を待つのではなく、トークンが徐々に表示されるのを確認します。

## ステップ 3: API ゲートウェイと認証

API ゲートウェイはプラットフォームへの玄関口です。

- **認証** - キー ストアに対して API キーを検証します (速度については Redis、永続性についてはデータベース)
- **レート制限** - キーごとの制限を強制します (例: 無料枠では 60 リクエスト/分)
- **リクエスト ルーティング** - リクエストを正しいモデル提供クラスターに送信します。
- **検証のリクエスト** - ペイロード スキーマ、モデルの可用性、トークン制限を確認します

**レート制限の実装:**
Redis で **スライディング ウィンドウ カウンター**を使用します。
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

リクエストごとにカウンターがインクリメントされます。制限を超えた場合は HTTP 429 を返します。

## ステップ 4: モデルの提供と GPU の割り当て

ここが、AI プラットフォームが従来の Web サービスと根本的に異なる点です。 GPU は希少で高価であり、特殊なオーケストレーションが必要です。

**モデル サービス レイヤ:**
- モデルは **Triton Inference Server** や **vLLM** などのフレームワークを使用して GPU メモリにロードされます
- 各モデルのバージョンは、GPU インスタンスの専用プールで実行されます。
- 大規模言語モデル (LLM) では、複数の GPU にわたる **モデルの並列処理** が必要な場合があります

**リクエストのバッチ処理:**
個々の推論リクエストは GPU では非効率的です。 **動的バッチ処理** は、複数のリクエストをグループ化し、一緒に処理します。
- 最大 10 ミリ秒、またはバッチが 32 リクエストに達するまでリクエストを収集します
- 1 つの GPU 順方向パスでバッチ全体を処理します
- 各発信者に個別の応答を返します

これにより、リクエストを個別に処理する場合と比較して、スループットが 5 ～ 10 倍向上します。

<FunFact>1 つの NVIDIA H100 GPU の価格はおよそ 25,000 ポンドで、消費電力は 700 ワットです。モデルを提供するために 1,000 個の GPU のクラスターを実行するには、電気代とハードウェアだけで月あたり 200 万ポンド以上の費用がかかります。そのため、効率的なバッチ処理と使用率が非常に重要になります。
</FunFact>

## ステップ 5: モデル バージョン間の A/B テスト

新しいモデル バージョンを展開するときは、制御されたロールアウトが必要です。

- **トラフィック分割** - リクエストの 5% を新しいモデルにルーティングし、95% を現在のモデルにルーティングします。
- **シャドウ モード** - 結果をユーザーに返さずに、運用トラフィックで新しいモデルを実行します。
- **メトリクスの比較** - レイテンシー、出力品質スコア、エラー率、リクエストあたりのコスト
- **段階的なロールアウト** - 信頼性が高まるにつれて、新しいバージョンへのトラフィックが増加します

ルーティング ロジックは API ゲートウェイ内に存在します。
```
model: "gpt-4"  →  95% → gpt-4-v2.1 (current)
                →   5% → gpt-4-v2.2 (candidate)
```

<ThinkAboutIt>新しい LLM バージョンが「優れている」かどうかを評価することは驚くほど困難です。分類モデルとは異なり、単純な精度の指標はありません。生成 AI モデルの自動品質評価システムをどのように設計しますか?
</ThinkAboutIt>

## ステップ 6: 使用量の追跡と請求

AI API は通常、トークンごとに請求されます (LLM の場合は入力 + 出力トークン、他のモデルの場合はリクエストごと)。

**イベント駆動型の請求パイプライン:**
1. 各 API 応答には、使用法ヘッダーが含まれます: `x-usage-tokens: 847`
2. 課金イベントが Kafka に発行されます: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. 請求集約サービスはイベントを消費し、累計を更新します。
4. 使用状況ダッシュボードは、時系列データベースから集計されたデータをクエリします

**Kafka を使用する理由** 請求は信頼性が高くなければなりませんが、同期である必要はありません。課金サービスが一時的にダウンした場合、イベントは Kafka のキューに入れられ、回復時に処理されます。使用状況データは失われません。

<Quiz question="請求パイプラインは、Kafka を介して使用状況イベントを非同期に処理します。顧客が使用状況ダッシュボードを確認すると、予想よりも低い数値が表示されます。最も考えられる原因は何ですか?" options="Kafka パーティションの障害によりイベントが失われた|集約サービスには処理ラグがあります - イベントはまだ消費されていません|API ゲートウェイが使用状況イベントを発行できませんでした|顧客の API キーにはレート制限がありました" answer="1" explanation="非同期パイプラインには本質的に遅延があります。 Kafka にパブリッシュされたイベントは、消費されて集約されるまでに数秒または数分かかる場合があるため、ダッシュボードには使用状況が少し遅れて表示されます。" />

## ステップ 7: 監視と可観測性

AI プラットフォームには、標準的な Web サービスを超えた監視が必要です。

|メトリック |なぜそれが重要なのか |
|------|----------------|
|推論レイテンシー (p50、p95、p99) |ユーザー エクスペリエンスと SLA 準拠 |
| GPU 使用率 |コスト効率 - アイドル状態の GPU はお金を無駄にします。
| 1 秒あたりのトークン数 |スループット容量とスケーリング信号 |
|モデルごとのエラー率 |モデル固有の障害を検出 |
|キューの深さ |スケーリング トリガー - キューが深いと需要が容量を超えることを意味します |
|出力品質スコア |モデルの劣化を検出する (自動評価経由) |

**アラートしきい値:** GPU 使用率が 40% を下回ると、スケールダウンがトリガーされます。キューの深さが 100 を超えると、スケールアップがトリガーされます。

## ステップ 8: 自動スケーリング

AI ワークロードの需要は非常に変動します。自動スケーリングでは、応答性とコストのバランスをとる必要があります。

- **水平スケーリング** - キューの深さまたはレイテンシーがしきい値を超えた場合に、GPU インスタンスを追加します。
- **予測スケーリング** - 過去のトラフィック パターンを使用して、予想されるピークの前に容量を事前にプロビジョニングします
- **ゼロへのスケール** - ほとんど使用されないモデルの場合、すべてのインスタンスをスピンダウンし、オンデマンドでコールドスタートします。
- **ウォーム プール** - コールド スタートのレイテンシーを回避するために、モデルが事前にロードされた少数のインスタンスを維持します。

ゼロへのスケール戦略は、数百のモデルをホストするプラットフォームにとって特に重要です。すべてのモデルを常に GPU メモリにロードしておくことはできません。

<Quiz question="現在、1 時間あたり 2 つのリクエストを受信するモデルは、1 つの常時稼働 GPU インスタンスで実行されており、料金は 1 時間あたり £3 です。ゼロからのコールドスタートには 45 秒かかります。最適なスケーリング戦略は何ですか?" options="インスタンスを常にオンにしておく - 45 秒は待つには長すぎます|ゼロにスケールし、最初のリクエストに対して 45 秒のコールド スタートを受け入れる|オンデマンドで GPU にオフロードする 1 つの CPU インスタンスのウォーム プールを使用する|2 つのリクエストを 1 つのスケジュールされたジョブにまとめます" answer="1" explanation="1 時間あたり 2 リクエストの場合、GPU は 99.9% の時間アイドル状態になります。ゼロにスケールして 45 秒のコールド スタートを受け入れると、モデルごとに月あたり 2,100 ポンド近く節約できます。これは、低トラフィック モデルの場合は時折遅延する価値があります。" />

<ThinkAboutIt>OpenAI のプラットフォームは、高速な埋め込みモデルから低速な推論モデルに至るまでのモデルを提供します。それぞれに異なるレイテンシー特性、GPU 要件、および価格設定があります。このように異なるプロファイルを持つモデル間で有限の GPU クラスターを効率的に共有するには、ルーティング層をどのように設計すればよいでしょうか?
</ThinkAboutIt>

<FunFact>OpenAI は毎日 1 億を超える API リクエストを処理すると報告されています。リクエストあたりの推定平均 500 トークンは、1 日あたり 500 億トークンに相当し、数千の GPU を継続的に実行する必要があります。
</FunFact>

## 重要なポイント

- AI API プラットフォームは、従来の API 設計と GPU 固有のインフラストラクチャの課題を組み合わせています
- リクエストのバッチ処理により、GPU スループットとコスト効率が大幅に向上します
- レート制限により、プラットフォームと顧客の両方を暴走コストから保護します
- Kafka を介した非同期請求により、リクエストをブロックすることなく信頼性の高い使用量追跡が保証されます
- 自動スケーリングは応答性とコストのバランスを取る必要があります - 低トラフィック モデルの場合はゼロまでスケールします
- GPU 使用率とキューの深さを監視することで、インテリジェントなスケーリングの決定を推進します
