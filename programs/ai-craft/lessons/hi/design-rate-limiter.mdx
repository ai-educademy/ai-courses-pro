# रेट लिमिटर डिज़ाइन करें - स्केल पर API की सुरक्षा

रेट लिमिटिंग सबसे व्यावहारिक सिस्टम डिज़ाइन विषयों में से एक है। GitHub से Stripe तक हर प्रोडक्शन API दुरुपयोग रोकने, निष्पक्ष उपयोग सुनिश्चित करने और बैकएंड सेवाओं को ओवरलोड होने से बचाने के लिए इस पर निर्भर करती है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- कॉन्फ़िगर की जा सकने वाली नियमों के आधार पर अनुरोध सीमित करें (हर उपयोगकर्ता, IP या API कुंजी)
- क्लाइंट throttled होने पर साफ़ feedback लौटाएं (HTTP 429)
- एक साथ कई रेट लिमिटिंग नियमों का समर्थन करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **कम लेटेंसी** - लिमिटर को महत्वपूर्ण ओवरहेड नहीं जोड़ना चाहिए
- **वितरित** - कई सर्वरों पर काम करे
- **फ़ॉल्ट-टॉलरेंट** - लिमिटर विफल हो तो भी ट्रैफ़िक चलता रहे (विफल-open)

<ThinkAboutIt>रेट लिमिटर क्रैश होने पर विफल-open (ट्रैफ़िक अनुमति) होना चाहिए या विफल-closed (ट्रैफ़िक ब्लॉक)? ई-कॉमर्स साइट बनाम बैंकिंग API के लिए समझौते क्या हैं?</ThinkAboutIt>

## चरण 2 - रेट लिमिटिंग एल्गोरिदम

### Fixed विंडो काउंटर
समय को तय विंडो में बांटें (जैसे 60-सेकंड अंतराल)। हर अनुरोध पर काउंटर बढ़ाएं। विंडो सीमा पर रीसेट करें। **समस्या:** विंडो के किनारों पर बर्स्ट ट्रैफ़िक सीमा का 2× तक अनुमति दे सकता है।

### स्लाइडिंग विंडो Log
हर अनुरोध का टाइमस्टैम्प स्टोर करें। पिछली विंडो के भीतर की एंट्री गिनें। सटीक है लेकिन **मेमोरी-प्रधान** है। स्केल पर हर टाइमस्टैम्प स्टोर करना महंगा है।

### स्लाइडिंग विंडो काउंटर
एक हाइब्रिड: वर्तमान विंडो काउंट को पिछली विंडो के weighted हिस्से के साथ मिलाएं। सटीकता और मेमोरी दक्षता का संतुलन देता है।

### Token Bucket Algorithm (सबसे लोकप्रिय)
एक बकेट अधिकतम क्षमता तक टोकन रखता है। टोकन एक तय दर पर जोड़े जाते हैं। हर अनुरोध एक टोकन खर्च करता है। बकेट खाली हो तो अनुरोध अस्वीकार होता है।

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### एल्गोरिदम तुलना

| एल्गोरिदम | मेमोरी | सटीकता | बर्स्ट संभालना |
|-----------|--------|----------|----------------|
| Fixed विंडो | कम | कम (किनारे के बर्स्ट) | खराब |
| स्लाइडिंग Log | अधिक | बिल्कुल सटीक | अच्छा |
| स्लाइडिंग काउंटर | मध्यम | लगभग सटीक | अच्छा |
| Token Bucket | कम | अच्छा | उत्कृष्ट |

## चरण 3 - उच्च-स्तरीय आर्किटेक्चर

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/डिज़ाइन-रेट-limiter.svg" alt="क्लाइंट, रेट लिमिटिंग middleware वाला API गेटवे, वितरित स्टेट के लिए Redis क्लस्टर और बैकएंड सेवाएं दिखाने वाला रेट लिमिटर आर्किटेक्चर" caption="रेट लिमिटर API गेटवे में बैठता है और वितरित काउंटर स्टोरेज के लिए Redis इस्तेमाल करता है" />

### रेट लिमिटर कहां रखें
- **क्लाइंट-साइड** - नकली बनाना आसान, अविश्वसनीय
- **सर्वर-साइड** - केवल प्रति-इंस्टेंस, स्केल नहीं करता
- **API गेटवे / Middleware** - वितरित सिस्टम के लिए सबसे अच्छा तरीका। सभी इंस्टेंस पर केंद्रीकृत enforcement

## चरण 4 - डीप डाइव: वितरित रेट लिमिटिंग

### Redis + Lua Scripts
वितरित व्यवस्था में कई सर्वरों को रेट लिमिटिंग स्टेट साझा करनी होती है। Redis अपनी एटॉमिक ऑपरेशन और sub-millisecond लेटेंसी के कारण मानक चुनाव है।

Lua स्क्रिप्ट atomicity सुनिश्चित करती है। check-and-decrement एक ही Redis operation में होता है, जिससे race conditions रुकती हैं:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### उत्तर Headers
अच्छे रेट लिमिटर क्लाइंट को स्टेट वापस बताते हैं:
- `X-RateLimit-Limit: 100` - प्रति विंडो अधिकतम अनुरोध
- `X-RateLimit-Remaining: 42` - बचे हुए अनुरोध
- `X-RateLimit-Reset: 1672531200` - UTC epoch जब विंडो रीसेट होगी
- HTTP `429 Too Many Requests` के साथ `Retry-After` header

## चरण 5 - Edge Cases संभालना

### Race Conditions
एटॉमिक ऑपरेशन के बिना समवर्ती अनुरोध सीमाएं पार कर सकते हैं। समाधान: Redis Lua स्क्रिप्ट या Redis `MULTI/EXEC` transactions।

### रेट Limiting Dimensions
एक साथ कई स्तरों पर लिमिट लागू करें:
- **हर उपयोगकर्ता** - authenticated उपयोगकर्ता के लिए 100 अनुरोध/मिनट
- **हर IP** - anonymous ट्रैफ़िक के लिए 50 अनुरोध/मिनट
- **हर API कुंजी** - tiered plans (फ्री: 10/min, pro: 1000/min)

### वितरित घड़ी का अंतर
सर्वरों की घड़ियां थोड़ी अलग हो सकती हैं। ऐप्लिकेशन सर्वर टाइमस्टैम्प पर निर्भर रहने के बजाय Redis सर्वर समय को single स्रोत of truth की तरह इस्तेमाल करें।

<FunFact>GitHub की REST API authenticated उपयोगकर्ता को हर घंटे 5,000 अनुरोध देती है, लेकिन unauthenticated अनुरोध को केवल 60 प्रति घंटे। Stripe live और test मोड API कुंजियां के लिए अलग लिमिट के साथ स्लाइडिंग विंडो तरीका इस्तेमाल करता है।</FunFact>

## चरण 6 - बाधाएं और ऑप्टिमाइज़ेशन

| बाधा | समाधान |
|-----------|----------|
| Redis single point of विफलता | replication के साथ Redis Cluster |
| Redis तक नेटवर्क लेटेंसी | periodic sync के साथ local in-मेमोरी कैश |
| Hot कुंजियां (लोकप्रिय API कुंजियां) | कई Redis नोड में shard करें |
| Rule evaluation ओवरहेड | नियम पहले से compile करें, कॉन्फ़िगरेशन कैश करें |

<ThinkAboutIt>अगर आप London, New York और Tokyo डेटा सेंटर वाली वैश्विक API के लिए रेट लिमिटिंग डिज़ाइन कर रहे हैं, तो क्या आप एक केंद्रीय Redis इस्तेमाल करेंगे या क्षेत्रीय Redis clusters? आप कौन से consistency trade-offs स्वीकार करेंगे?</ThinkAboutIt>
