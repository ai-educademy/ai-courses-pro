# दर लिमिटेर डिज़ाइन करें - APIs को बड़े पैमाने पर प्रोटेक्ट करना

दर लिमिटिङ सबसे व्यावहारिक सिस्टम डिज़ाइन विषय में से एक है। हर प्रोडक्शन API - GitHub से लेकर Stripe तक - इस पर निर्भर करती है ताकि अबुसे रोका जा सके, फ़ैर उसगे सुनिश्चित हो, और बकेनद सेरविकेस को ओवेरवहेलम होने से बचाया जा सके।

## चरण 1 - ज़रूरतें इकट्ठा करना

### फ़ुनकशनल ज़रूरतें
- कोनफ़िगुरबले रुलेस के आधार पर रिक्वेस्ट लिमिट करें (प्रति यूज़र, IP, या API की)
- कलिएनट को थरोटटले होने पर स्पष्ट फ़ीडबैक दें (HTTP 429)
- एक साथ कई दर लिमिटिङ रुलेस सपोर्ट करें

### नोन-फ़ुनकशनल ज़रूरतें
- **कम लेटेंसी** - लिमिटेर को सिगनिफ़िकनट ओवेरहेअद नहीं जोड़ें करना चाहिए
- **दिसटरिबुटेद** - कई सर्वर पर काम करे
- **फ़ौलट-टोलेरनट** - अगर लिमिटेर फ़ेल हो जाए, तो ट्रैफ़िक फ़लोव होता रहे (फ़ैल-ओपेन)

<ThinkAboutIt>क्या रेट लिमिटर करश होने पर फ़ैल-ओपेन (ट्रैफ़िक अललोव करे) होना चाहिए या फ़ैल-कलोसेद (ट्रैफ़िक ब्लॉक करे)? एक ए-कोममेरके सिटे vs बनकिङ API के लिए टरदे-ओफ़फ़स क्या होंगे?</ThinkAboutIt>

## चरण 2 - दर लिमिटिङ अलगोरिथमस

### फ़िक्सेद विनदोव कोउनटेर
समय को फ़िक्सेद विनदोवस में दिविदे करें (जैसे 60-सेकोनद इनटेरवलस)। हर रिक्वेस्ट पर कोउनटेर इनकरेमेनट करें। विनदोव बोउनदरय पर रेसेट करें। **समस्या:** विंडो एदगेस पर बुरसट ट्रैफ़िक 2× लिमिट अललोव कर सकता है।

### सलिदिङ विनदोव लोग
हर रिक्वेस्ट का टिमेसटमप सटोरे करें। टरैलिङ विंडो के अंदर एनटरिएस गणना करें। परेकिसे लेकिन **मेमोरय-गहन** - स्केल पर हर टिमेसटमप सटोरे करना महँगा है।

### सलिदिङ विनदोव कोउनटेर
एक हाइब्रिड तरीका: वर्तमान विंडो गणना को पिछली विंडो के भारित हिस्सा के साथ जोड़ते करें। अककुरकय और मेमोरी एफ़फ़िकिएनकय का संतुलन बनाए रखता है।

### टोकेन बुकेट अलगोरिथम (सबसे लोकप्रिय)
एक बुकेट मक्सिमुम कपकिटय तक टोकन बनाए करता है। टोकेनस एक फ़िक्सेद दर पर जोड़ें होते हैं। हर रिक्वेस्ट एक टोकन लेते करती है। अगर बुकेट एमपटय है, तो रिक्वेस्ट रेजेकट हो जाती है।

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### अलगोरिथम कोमपरिसोन

| अलगोरिथम | मेमोरय | अककुरकय | बुरसट हनदलिङ |
|-----------|--------|----------|----------------|
| फ़िक्सेद विनदोव | कम | कम (बढ़त बुरसटस) | खराब |
| सलिदिङ लोग | ज़्यादा | एक्सकट | अच्छी |
| सलिदिङ कोउनटेर | मध्यम | अपपरोक्सिमटे | अच्छी |
| टोकेन बुकेट | कम | अच्छी | बेहतरीन |

## चरण 3 - हिघ-लेवेल आर्किटेक्चर

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-rate-limiter.svg" alt="दर लिमिटेर आर्किटेक्चर जिसमें कलिएनटस, दर लिमिटिङ मिददलेवरे वाला API गेटवे, वितरित सटटे के लिए Redis क्लस्टर, और बकेनद सेरविकेस दिखाए गए हैं" caption="दर लिमिटेर API गेटवे में बैठता है, वितरित कोउनटेर स्टोरेज के लिए Redis का इस्तेमाल करता है" />

### दर लिमिटेर कहाँ रखें
- **कलिएनट-सिदे** - सपूफ़ करना आसान, उनरेलिअबले
- **सेरवेर-सिदे** - सिर्फ पेर-इनसटनके, स्केल नहीं करता
- **API गटेवय / मिददलेवरे** - वितरित सिस्टम के लिए सबसे अच्छा तरीका; सभी इनसटनकेस पर केनटरलिसेद एनफ़ोरकेमेनट

## चरण 4 - दीप दिवे: दिसटरिबुटेद दर लिमिटिङ

### Redis + लुअ सकरिपटस
दिसटरिबुटेद सेटअप में, कई सर्वर को दर लिमिटिङ सटटे साझा करनी होती है। Redis सटनदरद चोइके है क्योंकि इसके अटोमिक ऑपरेशन और सुब-मिललिसेकोनद लेटेंसी होती है।

लुअ सकरिपट अटोमिकिटय सुनिश्चित करता है - चेक-अनद-देकरेमेनट एक एकल Redis ऑपरेशन में होता है, जिससे रके कोनदिशनस परेवेनट होती हैं:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### रेसपोनसे हेअदेरस
अच्छे दर लिमिटेरस कलिएनटस को सटटे कोममुनिकटे करते हैं:
- `X-RateLimit-Limit: 100` - प्रति विंडो मक्सिमुम रिक्वेस्ट
- `X-RateLimit-Remaining: 42` - बची हुई रिक्वेस्ट
- `X-RateLimit-Reset: 1672531200` - UTC एपोच जब विंडो रेसेट होगी
- HTTP `429 Too Many Requests` के साथ a `Retry-After` हेअदेर

## चरण 5 - किनारे के मामले हनदले करना

### रके कोनदिशनस
अटोमिक ऑपरेशन के बिना, कोनकुररेनट रिक्वेस्ट सीमाएँ बयपस कर सकती हैं। सोलुशनस: Redis लुअ स्क्रिप्ट या Redis `MULTI/EXEC` टरनसकशनस।

### दर लिमिटिङ दिमेनसिओनस
एक साथ कई लेवेलस पर सीमाएँ अपपलय करें:
- **प्रति यूज़र** - औtheनटिकटेद यूज़र के लिए 100 रेक्वेसटस/मिनुटे
- **प्रति IP** - अनोन्यमोउस ट्रैफ़िक के लिए 50 रेक्वेसटस/मिनुटे
- **प्रति API की** - टिएरेद पलनस (मुफ़्त: 10/मिन, pro: 1000/मिन)

### दिसटरिबुटेद कलोक सकेव
सेरवेरस के कलोकस थोड़े अलग हो सकते हैं। अपपलिकशन सर्वर टिमेसटमपस पर निर्भर करने की बजाय Redis सर्वर समय को एकल सोउरके of टरुथ के रूप में इस्तेमाल करें।

<FunFact>GitHub की REST API औtheनटिकटेद यूज़र के लिए 5,000 रिक्वेस्ट प्रति होउर अललोव करती है लेकिन उनौtheनटिकटेद रिक्वेस्ट के लिए सिर्फ 60 प्रति होउर। Stripe स्लाइडिंग विंडो तरीका उपयोग करता है जिसमें लाइव और टेस्ट मोदे API की के लिए अलग-अलग सीमाएँ होती हैं।</FunFact>

## चरण 6 - बोटटलेनेकस और ओपटिमिसशनस

| बोटटलेनेक | सोलुशन |
|-----------|----------|
| Redis एकल बिंदु of फ़ैलुरे | रेपलिकशन के साथ Redis कलुसटेर |
| Redis तक नेटवर्क लेटेंसी | पेरिओदिक सयनक के साथ स्थानीय इन-मेमोरय कैश |
| होट की (लोकप्रिय API की) | मुलटिपले Redis नोड पर शरद करें |
| रुले मूल्यांकन ओवेरहेअद | रुलेस परे-कोमपिले करें, कोनफ़िगुरशनस कैश करें |
