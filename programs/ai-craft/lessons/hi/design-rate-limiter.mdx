# दर लिमिटेर डिज़ाइन करें - APIs को बड़े पैमाने पर प्रोटेक्ट करना

दर लिमिटिंग सबसे व्यावहारिक सिस्टम डिज़ाइन विषय में से एक है। हर प्रोडक्शन API - GitHub से लेकर Stripe तक - इस पर निर्भर करती है ताकि अबुसे रोका जा सके, फ़ैर अपयोग सुनिश्चित हो, और बकेनद सेवाएँ को ओवरवेल्म होने से बचाया जा सके।

## चरण 1 - ज़रूरतें इकट्ठा करना

### कार्यात्मक ज़रूरतें
- कोनफ़िगुरबले नियम के आधार पर रिक्वेस्ट लिमिट करें (प्रति यूज़र, IP, या API key)
- कलिएनट को थरोTTLे होने पर स्पष्ट फ़ीडबैक दें (HTTP 429)
- एक साथ कई दर लिमिटिंग नियम सपोर्ट करें

### गैर-कार्यात्मक ज़रूरतें
- **कम लेटेंसी** - लिमिटेर को साइनिफ़िकनट ओवरहेड नहीं जोड़ें करना चाहिए
- **वितरितद** - कई सर्वर पर काम करे
- **फ़ौलट-टोलेरनट** - अगर लिमिटेर फ़ेल हो जाए, तो ट्रैफ़िक फ़्लो होता रहे (फ़ैल-ओपेन)

<ThinkAboutIt>क्या रेट लिमिटर क्रैश होने पर फ़ैल-ओपेन (ट्रैफ़िक अनुमति करे) होना चाहिए या फ़ैल-कखोनाेद (ट्रैफ़िक ब्लॉक करे)? एक ए-कोममेरके सिटे vs बनकिङ API के लिए ट्रेड-offs क्या होंगे?</ThinkAboutIt>

## चरण 2 - दर लिमिटिंग एल्गोरिदमस

### फ़िक्स्ड विंडो काउंटर
समय को फ़िक्स्ड विंडो में बाँटें (जैसे 60-सेकंड अंतराल)। हर रिक्वेस्ट पर काउंटर बढ़ाएँ। विंडो सीमा पर रीसेट करें। **समस्या:** विंडो के किनारों पर बर्स्ट ट्रैफ़िक 2× लिमिट अनुमति कर सकता है।

### स्लाइडिंग विंडो लोग
हर रिक्वेस्ट का टाइमस्टैम्प स्टोर करें। ट्रेलिंग विंडो के अंदर एंट्री गणना करें। सटीक लेकिन **मेमोरी-गहन** - स्केल पर हर टाइमस्टैम्प स्टोर करना महँगा है।

### स्लाइडिंग विंडो काउंटर
एक हाइब्रिड तरीका: वर्तमान विंडो गणना को पिछली विंडो के भारित हिस्सा के साथ जोड़ते करें। सटीकता और मेमोरी दक्षता का संतुलन बनाए रखता है।

### टोकेन बुकेट एल्गोरिदम (सबसे लॉकप्रिय)
एक बुकेट मक्सिमुम क्षमता तक टोकन बनाए करता है। टोकन एक फ़िक्स्ड दर पर जोड़ें होते हैं। हर रिक्वेस्ट एक टोकन लेते करती है। अगर बुकेट खाली है, तो रिक्वेस्ट रेजेकट हो जाती है।

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### एल्गोरिदम कोमपरिसोन

| एल्गोरिदम | मेमोरी | सटीकता | बुरसट हनदलिङ |
|-----------|--------|----------|----------------|
| फ़िक्स्ड विंडो | कम | कम (एज बर्स्ट) | खराब |
| सलिदिङ लोग | ज़्यादा | सटीक | अच्छी |
| सलिदिङ काउंटर | मध्यम | अपपरोक्सिमटे | अच्छी |
| टोकेन बुकेट | कम | अच्छी | बेहतरीन |

## चरण 3 - उच्च-level आर्किटेक्चर

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-rate-limiter.svg" alt="दर लिमिटेर आर्किटेक्चर जिसमें क्लाइंट, दर लिमिटिंग मिडलवेयर वाला API गेटवे, वितरित सटटे के लिए Redis क्लस्टर, और बकेनद सेवाएँ दिखाए गए हैं" caption="दर लिमिटेर API गेटवे में बैठता है, वितरित काउंटर स्टोरेज के लिए Redis का इस्तेमाल करता है" />

### दर लिमिटेर कहाँ रखें
- **कलिएनट-साइड** - सपूफ़ करना आसान, उनरेलिअबले
- **सर्वर-साइड** - सिर्फ पेर-इंस्टेंस, स्केल नहीं करता
- **API गेटवे / मिडलवेयर** - वितरित सिस्टम के लिए सबसे अच्छा तरीका; सभी इंस्टेंस पर केंद्रीकृत लागूकरण

## चरण 4 - दीप दिवे: वितरितद दर लिमिटिंग

### Redis + Lua स्क्रिप्ट
वितरित व्यवस्था में कई सर्वरों को दर-सीमा key स्थिति साझा करनी होती है। Redis मानक विकल्प है क्योंकि इसके ऑपरेशन एटॉमिक हैं और लेटेंसी एक मिलीसेकंड से कम रहती है।

Lua सकरिपट एटॉमिसिटी सुनिश्चित करता है - चेक-अनद-घटाएँ एक एकल Redis ऑपरेशन में होता है, जिससे रके स्थितियाँ रोकता होती हैं:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### रिस्पॉन्स हेडरस
अच्छे दर लिमिटेरस क्लाइंट को सटटे कोममुनिकटे करते हैं:
- `X-RateLimit-Limit: 100` - प्रति विंडो मक्सिमुम रिक्वेस्ट
- `X-RateLimit-Remaining: 42` - बची हुई रिक्वेस्ट
- `X-RateLimit-Reset: 1672531200` - UTC एपोच जब विंडो रीसेट होगी
- HTTP `429 Too Many Requests` के साथ a `Retry-After` हेडर

## चरण 5 - किनारे के मामले हनदले करना

### रके स्थितियाँ
एटॉमिक ऑपरेशन के बिना, समवर्ती रिक्वेस्ट सीमाएँ बाइपास कर सकती हैं। समाधान: Redis Lua स्क्रिप्ट या Redis `MULTI/EXEC` ट्रांज़ैक्शन।

### दर लिमिटिंग दिमेनसिओनस
एक साथ कई levelस पर सीमाएँ लागू करें:
- **प्रति यूज़र** - ऑथेंटिकेटेड यूज़र के लिए 100 रिक्वेस्ट/मिनट
- **प्रति IP** - अनोन्यमोउस ट्रैफ़िक के लिए 50 रिक्वेस्ट/मिनट
- **प्रति API key** - स्तरीय प्लान (मुफ़्त: 10/मिन, pro: 1000/मिन)

### वितरितद कलॉक सकेव
सर्वरस के कलॉकस थोड़े अलग हो सकते हैं। ऐप्लिकेशन सर्वर टाइमस्टैम्प पर निर्भर करने key बजाय Redis सर्वर समय को एकल स्रोत of सत्य के रूप में इस्तेमाल करें।

<FunFact>GitHub key REST API ऑथेंटिकेटेड यूज़र के लिए 5,000 रिक्वेस्ट प्रति होउर अनुमति करती है लेकिन बिना ऑथेंटिकेशन वाले रिक्वेस्ट के लिए सिर्फ 60 प्रति होउर। Stripe स्लाइडिंग विंडो तरीका अपयोग करता है जिसमें लाइव और टेस्ट मोदे API key के लिए अलग-अलग सीमाएँ होती हैं।</FunFact>

## चरण 6 - बॉटलनेक और ऑप्टिमाइज़ेशन

| बोTTLेनेक | सोलुशन |
|-----------|----------|
| Redis एकल बिंदु of फ़ैलुरे | रेपलिकशन के साथ Redis कलुसटेर |
| Redis तक नेटवर्क लेटेंसी | नियमित सिंक के साथ स्थानीय इन-मेमोरी कैश |
| होट key (लॉकप्रिय API key) | मुलटिपले Redis नोड पर शार्ड करें |
| नियम मूल्यांकन ओवरहेड | नियम pre-compile करें, कॉन्फ़िगरेशन कैश करें |
