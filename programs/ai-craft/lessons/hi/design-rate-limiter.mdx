# दर लिमिटेर डिज़ाइन करें - APIs को बड़े पैमाने पर प्रोटेक्ट करना

दर लिमिटिङ सबसे व्यावहारिक सिस्टम डिज़ाइन विषय में से एक है। हर प्रोडक्शन API - GitHub से लेकर Stripe तक - इस पर निर्भर करती है ताकि अबुसे रोका जा सके, फ़ैर उसगे सुनिश्चित हो, और बकेनद सेवाएँ को ओवेरवहेलम होने से बचाया जा सके।

## चरण 1 - ज़रूरतें इकट्ठा करना

### कार्यात्मक ज़रूरतें
- कोनफ़िगुरबले रुलेस के आधार पर रिक्वेस्ट लिमिट करें (प्रति यूज़र, IP, या API की)
- कलिएनट को थरोटटले होने पर स्पष्ट फ़ीडबैक दें (HTTP 429)
- एक साथ कई दर लिमिटिङ रुलेस सपोर्ट करें

### गैर-कार्यात्मक ज़रूरतें
- **कम लेटेंसी** - लिमिटेर को सिगनिफ़िकनट ओवरहेड नहीं जोड़ें करना चाहिए
- **वितरितद** - कई सर्वर पर काम करे
- **फ़ौलट-टोलेरनट** - अगर लिमिटेर फ़ेल हो जाए, तो ट्रैफ़िक फ़लोव होता रहे (फ़ैल-ओपेन)

<ThinkAboutIt>क्या रेट लिमिटर करश होने पर फ़ैल-ओपेन (ट्रैफ़िक सभीोव करे) होना चाहिए या फ़ैल-कलोसेद (ट्रैफ़िक ब्लॉक करे)? एक ए-कोममेरके सिटे vs बनकिङ API के लिए टरदे-ओफ़फ़स क्या होंगे?</ThinkAboutIt>

## चरण 2 - दर लिमिटिङ एल्गोरिदमस

### फ़िक्सेद विनदोव कोउनटेर
समय को fixed windows में बाँटें (जैसे 60-second intervals)। हर request पर counter increment करें। Window boundary पर reset करें। **समस्या:** window edges पर burst traffic 2× limit allow कर सकता है।

### स्लाइडिंग विंडो लोग
हर request का timestamp store करें। Trailing window के अंदर entries count करें। Precise लेकिन **memory-intensive** - scale पर हर timestamp store करना महँगा है।

### स्लाइडिंग विंडो कोउनटेर
एक हाइब्रिड तरीका: वर्तमान विंडो गणना को पिछली विंडो के भारित हिस्सा के साथ जोड़ते करें। सटीकता और मेमोरी एफ़फ़िकिएनकय का संतुलन बनाए रखता है।

### टोकेन बुकेट एल्गोरिदम (सबसे लोकप्रिय)
एक bucket maximum capacity तक tokens रखती है। Tokens fixed rate पर जोड़े जाते हैं। हर request एक token consume करती है। अगर bucket empty है, तो request reject हो जाती है।

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### एल्गोरिदम कोमपरिसोन

| एल्गोरिदम | मेमोरय | सटीकता | बुरसट हनदलिङ |
|-----------|--------|----------|----------------|
| Fixed Window | कम | कम (edge bursts) | खराब |
| सलिदिङ लोग | ज़्यादा | एक्सकट | अच्छी |
| सलिदिङ कोउनटेर | मध्यम | अपपरोक्सिमटे | अच्छी |
| टोकेन बुकेट | कम | अच्छी | बेहतरीन |

## चरण 3 - उच्च-लेवेल आर्किटेक्चर

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-rate-limiter.svg" alt="दर लिमिटेर आर्किटेक्चर जिसमें कलिएनटस, दर लिमिटिङ मिददलेवरे वाला API गेटवे, वितरित सटटे के लिए Redis क्लस्टर, और बकेनद सेवाएँ दिखाए गए हैं" caption="दर लिमिटेर API गेटवे में बैठता है, वितरित कोउनटेर स्टोरेज के लिए Redis का इस्तेमाल करता है" />

### दर लिमिटेर कहाँ रखें
- **कलिएनट-सिदे** - सपूफ़ करना आसान, उनरेलिअबले
- **Server-side** - सिर्फ़ per-instance, scale नहीं करता
- **API Gateway / Middleware** - distributed systems के लिए सबसे अच्छा तरीका। सभी instances पर centralised enforcement

## चरण 4 - दीप दिवे: वितरितद दर लिमिटिङ

### Redis + लुअ स्क्रिप्ट
वितरित व्यवस्था में कई सर्वरों को दर-सीमा की स्थिति साझा करनी होती है। Redis मानक विकल्प है क्योंकि इसके ऑपरेशन एटॉमिक हैं और लेटेंसी एक मिलीसेकंड से कम रहती है।

लुअ सकरिपट अटोमिकिटय सुनिश्चित करता है - चेक-अनद-देकरेमेनट एक एकल Redis ऑपरेशन में होता है, जिससे रके कोनदिशनस परेवेनट होती हैं:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### रेसपोनसे हेअदेरस
अच्छे दर लिमिटेरस कलिएनटस को सटटे कोममुनिकटे करते हैं:
- `X-RateLimit-Limit: 100` - प्रति विंडो मक्सिमुम रिक्वेस्ट
- `X-RateLimit-Remaining: 42` - बची हुई रिक्वेस्ट
- `X-RateLimit-Reset: 1672531200` - UTC एपोच जब विंडो रेसेट होगी
- HTTP `429 Too Many Requests` के साथ a `Retry-After` हेअदेर

## चरण 5 - किनारे के मामले हनदले करना

### रके कोनदिशनस
Atomic operations के बिना, concurrent requests limits bypass कर सकती हैं। समाधान: Redis Lua scripts या Redis `MULTI/EXEC` transactions।

### दर लिमिटिङ दिमेनसिओनस
एक साथ कई levels पर limits apply करें:
- **प्रति यूज़र** - ऑथेंटिकेटेड यूज़र के लिए 100 रेक्वेसटस/मिनुटे
- **प्रति IP** - अनोन्यमोउस ट्रैफ़िक के लिए 50 रेक्वेसटस/मिनुटे
- **प्रति API key** - tiered plans (free: 10/min, pro: 1000/min)

### वितरितद कलोक सकेव
Servers की clocks थोड़ी अलग हो सकती हैं। Application server timestamps पर निर्भर करने की बजाय Redis server time को single source of truth की तरह इस्तेमाल करें।

<FunFact>GitHub की REST API ऑथेंटिकेटेड यूज़र के लिए 5,000 रिक्वेस्ट प्रति होउर सभीोव करती है लेकिन बिना ऑथेंटिकेशन वाले रिक्वेस्ट के लिए सिर्फ 60 प्रति होउर। Stripe स्लाइडिंग विंडो तरीका उपयोग करता है जिसमें लाइव और टेस्ट मोदे API की के लिए अलग-अलग सीमाएँ होती हैं।</FunFact>

## चरण 6 - Bottlenecks और Optimisations

| बोटटलेनेक | सोलुशन |
|-----------|----------|
| Redis एकल बिंदु of फ़ैलुरे | रेपलिकशन के साथ Redis कलुसटेर |
| Redis तक network latency | periodic sync के साथ local in-memory cache |
| होट की (लोकप्रिय API की) | मुलटिपले Redis नोड पर शार्ड करें |
| Rule evaluation overhead | rules pre-compile करें, configurations cache करें |
