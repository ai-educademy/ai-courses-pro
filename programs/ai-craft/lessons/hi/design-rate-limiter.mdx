# दर लिमिटेर डिज़ाइन करें - APIs को बड़े पैमाने पर प्रोटेक्ट करना

दर लिमिटिंग सबसे व्यावहारिक सिस्टम डिज़ाइन विषय में से एक है। हर प्रोडक्शन API - GitHub से लेकर Stripe तक - इस पर निर्भर करती है ताकि अबुसे रोका जा सके, फ़ैर उपयोग सुनिश्चित हो, और बकेनद सेवाएँ को ओवेरवहेलम होने से बचाया जा सके।

## चरण 1 - ज़रूरतें इकट्ठा करना

### कार्यात्मक ज़रूरतें
- कोनफ़िगुरबले रुलेस के आधार पर रिक्वेस्ट लिमिट करें (प्रति यूज़र, IP, या API की)
- कलिएनट को थरोटटले होने पर स्पष्ट फ़ीडबैक दें (HTTP 429)
- एक साथ कई दर लिमिटिंग रुलेस सपोर्ट करें

### गैर-कार्यात्मक ज़रूरतें
- **कम लेटेंसी** - लिमिटेर को सिगनिफ़िकनट ओवरहेड नहीं जोड़ें करना चाहिए
- **वितरितद** - कई सर्वर पर काम करे
- **फ़ौलट-टोलेरनट** - अगर लिमिटेर फ़ेल हो जाए, तो ट्रैफ़िक फ़कम होता रहे (फ़ैल-ओपेन)

<ThinkAboutIt>क्या रेट लिमिटर क्रैश होने पर फ़ैल-ओपेन (ट्रैफ़िक सभीोव करे) होना चाहिए या फ़ैल-कलोसेद (ट्रैफ़िक ब्लॉक करे)? एक ए-कोममेरके सिटे vs बनकिङ API के लिए टरदे-ओफ़फ़स क्या होंगे?</ThinkAboutIt>

## चरण 2 - दर लिमिटिंग एल्गोरिदमस

### फ़िक्स्ड विंडो कोउनटेर
समय को फ़िक्स्ड विंडो में बाँटें (जैसे 60-सेकंड अंतराल)। हर रिक्वेस्ट पर काउंटर बढ़ाएँ। विंडो सीमा पर रीसेट करें। **समस्या:** विंडो के किनारों पर बर्स्ट ट्रैफ़िक 2× लिमिट अनुमति कर सकता है।

### स्लाइडिंग विंडो लोग
हर रिक्वेस्ट का टाइमस्टैम्प स्टोर करें। टरैलिङ विंडो के अंदर एंट्री गणना करें। परेकिसे लेकिन **मेमोरी-गहन** - स्केल पर हर टाइमस्टैम्प स्टोर करना महँगा है।

### स्लाइडिंग विंडो कोउनटेर
एक हाइब्रिड तरीका: वर्तमान विंडो गणना को पिछली विंडो के भारित हिस्सा के साथ जोड़ते करें। सटीकता और मेमोरी एफ़फ़िकिएनकय का संतुलन बनाए रखता है।

### टोकेन बुकेट एल्गोरिदम (सबसे लोकप्रिय)
एक बुकेट मक्सिमुम क्षमता तक टोकन बनाए करता है। टोकन एक फ़िक्स्ड दर पर जोड़ें होते हैं। हर रिक्वेस्ट एक टोकन लेते करती है। अगर बुकेट खाली है, तो रिक्वेस्ट रेजेकट हो जाती है।

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### एल्गोरिदम कोमपरिसोन

| एल्गोरिदम | मेमोरी | सटीकता | बुरसट हनदलिङ |
|-----------|--------|----------|----------------|
| फ़िक्स्ड विंडो | कम | कम (एज बर्स्ट) | खराब |
| सलिदिङ लोग | ज़्यादा | एक्सकट | अच्छी |
| सलिदिङ कोउनटेर | मध्यम | अपपरोक्सिमटे | अच्छी |
| टोकेन बुकेट | कम | अच्छी | बेहतरीन |

## चरण 3 - उच्च-लेवेल आर्किटेक्चर

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-दर-limiter.svg" alt="दर लिमिटेर आर्किटेक्चर जिसमें कलिएनटस, दर लिमिटिंग मिददलेवरे वाला API गेटवे, वितरित सटटे के लिए Redis क्लस्टर, और बकेनद सेवाएँ दिखाए गए हैं" caption="दर लिमिटेर API गेटवे में बैठता है, वितरित कोउनटेर स्टोरेज के लिए Redis का इस्तेमाल करता है" />

### दर लिमिटेर कहाँ रखें
- **कलिएनट-सिदे** - सपूफ़ करना आसान, उनरेलिअबले
- **सेरवेर-सिदे** - सिर्फ पेर-इंस्टेंस, स्केल नहीं करता
- **API गटेवय / मिददलेवरे** - वितरित सिस्टम के लिए सबसे अच्छा तरीका; सभी इंस्टेंस पर केंद्रीयिसेद एनफ़ोरकेमेनट

## चरण 4 - दीप दिवे: वितरितद दर लिमिटिंग

### Redis + लुअ स्क्रिप्ट
वितरित व्यवस्था में कई सर्वरों को दर-सीमा की स्थिति साझा करनी होती है। Redis मानक विकल्प है क्योंकि इसके ऑपरेशन एटॉमिक हैं और लेटेंसी एक मिलीसेकंड से कम रहती है।

लुअ सकरिपट अटोमिकिटय सुनिश्चित करता है - चेक-अनद-देकरेमेनट एक एकल Redis ऑपरेशन में होता है, जिससे रके कोनदिशनस रोकता होती हैं:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### रिस्पॉन्स हेअदेरस
अच्छे दर लिमिटेरस कलिएनटस को सटटे कोममुनिकटे करते हैं:
- `X-RateLimit-Limit: 100` - प्रति विंडो मक्सिमुम रिक्वेस्ट
- `X-RateLimit-Remaining: 42` - बची हुई रिक्वेस्ट
- `X-RateLimit-Reset: 1672531200` - UTC एपोच जब विंडो रीसेट होगी
- HTTP `429 Too Many Requests` के साथ a `Retry-After` हेअदेर

## चरण 5 - किनारे के मामले हनदले करना

### रके कोनदिशनस
अटोमिक ऑपरेशन के बिना, समवर्ती रिक्वेस्ट सीमाएँ बाइपास कर सकती हैं। समाधान: Redis लुअ स्क्रिप्ट या Redis `MULTI/EXEC` ट्रांज़ैक्शनस।

### दर लिमिटिंग दिमेनसिओनस
एक साथ कई लेवेलस पर सीमाएँ लागू करें:
- **प्रति यूज़र** - ऑथेंटिकेटेड यूज़र के लिए 100 रिक्वेस्ट/मिनट
- **प्रति IP** - अनोन्यमोउस ट्रैफ़िक के लिए 50 रिक्वेस्ट/मिनट
- **प्रति API की** - टिएरेद प्लान (मुफ़्त: 10/मिन, pro: 1000/मिन)

### वितरितद कलोक सकेव
सेरवेरस के कलोकस थोड़े अलग हो सकते हैं। ऐप्लिकेशन सर्वर टाइमस्टैम्प पर निर्भर करने की बजाय Redis सर्वर समय को एकल स्रोत of टरुथ के रूप में इस्तेमाल करें।

<FunFact>GitHub की REST API ऑथेंटिकेटेड यूज़र के लिए 5,000 रिक्वेस्ट प्रति होउर सभीोव करती है लेकिन बिना ऑथेंटिकेशन वाले रिक्वेस्ट के लिए सिर्फ 60 प्रति होउर। Stripe स्लाइडिंग विंडो तरीका उपयोग करता है जिसमें लाइव और टेस्ट मोदे API की के लिए अलग-अलग सीमाएँ होती हैं।</FunFact>

## चरण 6 - बोटटलेनेकस और ऑप्टिमाइज़ेशन

| बोटटलेनेक | सोलुशन |
|-----------|----------|
| Redis एकल बिंदु of फ़ैलुरे | रेपलिकशन के साथ Redis कलुसटेर |
| Redis तक नेटवर्क लेटेंसी | पेरिओदिक सिंक के साथ स्थानीय इन-मेमोरी कैश |
| होट की (लोकप्रिय API की) | मुलटिपले Redis नोड पर शार्ड करें |
| रुले मूल्यांकन ओवरहेड | रुलेस परे-कोमपिले करें, कॉन्फ़िगरेशन कैश करें |
