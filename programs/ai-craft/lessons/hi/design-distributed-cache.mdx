# वितरित कैश डिज़ाइन करें - Redis आर्किटेक्चर शुरू से

कैशिंग सिस्टम प्रदर्शन बेहतर करने की सबसे प्रभावी टेचनिक्वे है। एक अच्छी तरह डिज़ाइन किया गया वितरित कैश डेटाबेस लोड को 90%+ तक कम कर सकता है और प्रतिक्रिया टिमेस को सैकड़ों मिललिसेकंडस से सब-मिलीसेकंड तक ला सकता है।

## चरण 1 - ज़रूरतें इकट्ठा करना

### कार्यात्मक ज़रूरतें
- केय-वलुए जोड़ियाँ स्टोर करना वैकल्पिक TTL (टिमे-टो-लिवे) के साथ
- आम ऑपरेशन सपोर्ट करना: GET, SET, DELETE, और बुलक ऑपरेशन
- हॉरिज़ॉन्टल स्केलिंग के लिए डेटा को कई नोड में वितरित करना

### गैर-कार्यात्मक ज़रूरतें
- **कम लेटेंसी** - कैश हिट के लिए सब-मिलीसेकंड रीड
- **उच्च थ्रूपुट** - प्रति नोड 100K+ ऑपरेशन प्रति सेकंड
- **उच्च उपलब्धता** - कैश विफलताएँ से सिस्टम डाउन नहीं होना चाहिए
- **स्केलेबिलिटी** - बिना डाउनटिमे के नोड जोड़ना

### कब कैश करें
- **रीड-हेवी वर्कलोड** - जब रीड, राइट से बहुत ज़्यादा हों
- **एक्सपेनसिवे गणनाओं** - ML मॉडल इन्फ़रेंस नतीजे, जटिल एग्रीगेशन
- **बार-बार एक्सेस डेटा** - यूज़र सेशन, उत्पाद कैटलॉग, कॉन्फ़िगरेशन

## चरण 2 - कैशिंग रणनीतियों

### कैश-असाइड (लेज़ी लोडिङ)
सबसे आम पैटर्न। ऐप्लिकेशन पहले कैश जाँच करता है; मिस होने पर डेटाबेस से रीड करता है, फिर कैश पॉपुलटे करता है:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**परोस:** सिर्फ़ वही कैश होता है जो वास्तव में रिक्वेस्ट किया जाता है। **नुकसान:** कैश मिस पर लेटेंसी ज़्यादा है; डेटा स्थिर हो सकता है।

### रीड-थ्रू
कैश खुद मिस होने पर डेटाबेस रीड संभाल करता है। ऐप्लिकेशन सिर्फ़ कैश परत से बात करती है, जो डेटा स्रोत को अमूर्त करता है।

### राइट-थ्रू
हर राइट कैश और डेटाबेस दोनों में सिंक्रोनस रूप से जाता है। कैश हमेशा कंसिस्टेंट रहता है लेकिन राइट लेटेंसी ज़्यादा है।

### राइट-बिहाइंड (राइट-बैक)
राइट तुरंत कैश में जाते हैं; कैश असिंक्रोनस रूप से बैच में डेटाबेस को फ्लश करता है। राइट लेटेंसी कम होती है लेकिन अगर कैश नोड फ्लश से पहले क्रैश हो जाए तो डेटा खोना का जोखिम है।

| रणनीति | संगति | रीड लेटेंसी | राइट लेटेंसी | उपयोग कसे |
|----------|-------------|-------------|---------------|----------|
| कैश-असाइड | इवेंटुअल | मिस पेनल्टी | N/A | सामान्य उद्देश्य |
| रीड-थ्रू | इवेंटुअल | मिस पेनल्टी | N/A | सरल रीड |
| राइट-थ्रू | मज़बूत | तेज़ | धीमा | संगति-महत्वपूर्ण |
| राइट-बिहाइंड | इवेंटुअल | तेज़ | तेज़ | राइट-हेवी वर्कलोड |

## चरण 3 - इविक्शन नीतियाँ

जब कैश भर जाए, तो कौन सी एंट्री हटाएँ?

- **LRU (सबसे कम हाल में इस्तेमाल)** - सबसे लंबे समय से एक्सेस न कुंजी गई एंट्री को निकालता है। सबसे अच्छी सामान्य-उद्देश्य पॉलिसी
- **LFU (सबसे कम बार इस्तेमाल)** - सबसे कम बार एक्सेस कुंजी गई एंट्री को निकालता है। टेढ़े एक्सेस पैटर्न के लिए बेहतर
- **TTL-आधारित** - एंट्री एक सेट समय बाद एक्सपायर होती हैं चाहे एक्सेस हों या नहीं। डेटा ताज़गी के लिए ज़रूरी
- **रैंडम** - हैरान करने वाला प्रभावी और लागू करने में बहुत सरल

<FunFact>Redis एक लगभग LRU एल्गोरिदम उपयोग करता है जो कुछ कुंजी सैंपल करता है (डिफ़ॉल्ट: 5) और उनमें से सबसे कम हाल में इस्तेमाल को निकालता है। यह true LRU जितना ही सटीक है लेकिन एक्सेस ऑर्डर रिकॉर्ड करने के लिए शून्य अतिरिक्त मेमोरी ओवरहेड लगती है।</FunFact>

## चरण 4 - वितरण के लिए कंसिस्टेंट हैशिंग

### सरल हैशिंग कुंजी समस्या
`hash(key) % N` नोड के साथ, कोई नोड जोड़ें या हटा करने पर लगभग सारी कुंजी रीमैप हो जाती हैं, जिससे बहुत बड़ा कैश मिस स्टॉर्म आता है।

### वर्चुअल नोदेस के साथ कंसिस्टेंट हैशिंग
कंसिस्टेंट हैशिंग कुंजी और नोड दोनों को एक रिङ पर मैप करता है। हर कुंजी रिङ पर अगले क्लॉकवाइज़ नोड को असाइन होती है:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**वर्चुअल नोड** उनेवेन वितरण समस्या हल करते हैं। हर फिजिकल नोड को रिङ पर कई स्थान मिलती हैं, जिससे कम फिजिकल नोड होने पर भी संतुलित लोड सुनिश्चित होता है।

जब कोई नोड जोड़ें या हटा होता है, तो सिर्फ़ रिङ पर उसके लगती हुई कुंजी रीमैप होती हैं - लगभग `K/N` कुंजी (जहाँ K कुल कुंजी और N नोड गणना है), सारी नहीं।

## चरण 5 - कैश स्टैम्पीड रोकथाम

**कैश स्टैम्पीड** तब होता है जब कोई लॉकप्रिय कचेद एंट्री एक्सपायर होती है और सैकड़ों समवर्ती रिक्वेस्ट एक साथ कैश मिस करती हैं और डेटाबेस को हिट करती हैं।

### समाधान

**मुटेक्स/लॉकिङ:** कैश मिस होने पर एक वितरित लॉक हासिल करें। सिर्फ़ एक रिक्वेस्ट डेटाबेस से फ़ेटच करती है; बाकी कैश फिर भरने होने तक इंतज़ार करती हैं।

**प्रायिक जल्दी एक्सपायरी:** हर रिक्वेस्ट को TTL एक्सपायर होने से पहले कैश रीफ़्रेश करने का एक छोटा रैंडम संभावना होता है। इससे रीफ़्रेश लोड समय में फैलता होता है बजाय एक्सपायरी पर थंडरिंग हर्ड बनने के।

**पृष्ठभूमि रेफ़रेश:** एक पृष्ठभूमि प्रोसेस लॉकप्रिय कैश एंट्री को एक्सपायर होने से पहले रीफ़्रेश करता है। होट कुंजी के लिए कैश कभी खाली नहीं होता।

<ThinkAboutIt>एक फ़्लैश सेल सोचिए जहाँ एक उत्पाद पेज को 100,000 रिक्वेस्ट प्रति सेकंड मिल रही हैं। उत्पाद विवरण कैश एंट्री एक्सपायर हो जाती है। स्टैम्पीड रोकथाम के बिना, सभी 100K रिक्वेस्ट एक साथ डेटाबेस हिट करेंगी। आप कौन सी रोकथाम रणनीति चुनेंगे, और क्यों?</ThinkAboutIt>

## चरण 6 - Redis क्लस्टर आर्किटेक्चर

Redis क्लस्टर सबसे विदेरी तैनात वितरित कैश है:

- **16,384 हैश स्लॉट** मास्टर नोड में वितरित होते हैं
- हर कुंजी एक सलोट पर मैप होती है `CRC16(key) % 16384` से
- **रेप्लिकेशन:** हर मास्टर के पास फ़ैकमेर के लिए एक या ज़्यादा रेप्लिका होते हैं
- **ऑटोमटिक फ़ैकमेर:** अगर मास्टर फ़ेल होता है, तो उसका रेपलिक सेकंड में बढ़ावा हो जाता है

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### मुख्य बात मेट्रिक्स मॉनिटर करना
- **हिट अनुपात** - लक्षित 95%+; 80% से नीचे कैशिंग समस्या इनदिकटे करता है
- **मेमोरी उपयोग** - इविक्शन से बचने के लिए 80% से नीचे रखें
- **इविक्शन दर** - ज़्यादा इविक्शन मतलब कैश छोटा है
- **लेटेंसी प्रतिशतिलेस** - कैश हिट के लिए p99 1ms से कम होना चाहिए

## चरण 7 - वास्तविक दुनिया कैशिंग पैटर्न

| पटटेरन | कार्यान्वयन | TTL |
|---------|---------------|-----|
| सेशन स्टोर | `SET session:{id} {data}` | 30 मिनट |
| API प्रतिक्रिया कैश | `SET api:/users/123 {json}` | 5 मिनट |
| डेटाबेस क्वेरी कैश | `SET query:{hash} {result}` | 1 मिनट |
| दर लिमिटर काउंटर | `INCR ratelimit:{user}:{window}` | विंडो अवधि |
| फ़ीचर फ़्लैग | `HSET features {flag} {value}` | 10 सेकंड |

### कैश इनवैलिडेशन
कंप्यूटर विज्ञान कुंजी सबसे कठिन समस्या (नामकरण बिंदु के साथ):
- **TTL-आधारित** - सरल, TTL अवधि तक बासापन टोलेरेट करता है
- **इवेंट-driven** - डेटा बदलने पर इनवैलिडेशन इवेंट पब्लिश करें (Kafka या Redis पुब/सुब से)
- **वर्शन-आधारित** - कैश कुंजी में वर्शन शामिल करें; राइट पर वर्शन बढ़ाएँ ताकि पुरानी एंट्री प्रभावी रूप से अमान्य हों
