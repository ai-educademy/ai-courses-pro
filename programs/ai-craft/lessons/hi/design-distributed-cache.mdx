# वितरित कैश डिज़ाइन करें - Redis आर्किटेक्चर शुरू से

कैशिंग सिस्टम प्रदर्शन सुधारने की सबसे प्रभावी तकनीक है। अच्छी तरह डिज़ाइन किया गया वितरित कैश डेटाबेस लोड 90%+ तक घटा सकता है और उत्तर बार को सैकड़ों milliseconds से sub-millisecond तक ला सकता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- Optional TTL (समय-to-live) के साथ कुंजी-मान pairs स्टोर करें
- सामान्य ऑपरेशन का समर्थन करें: GET, SET, DELETE और bulk ऑपरेशन
- Horizontal स्केलिंग के लिए डेटा को कई नोड में distribute करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **कम लेटेंसी** - कैश हिट के लिए sub-millisecond पढ़ाई
- **High थ्रूपुट** - हर नोड पर 100K+ ऑपरेशन per सेकंड
- **High अवेलेबिलिटी** - कैश failures से सिस्टम बंद नहीं होना चाहिए
- **Scalability** - downtime के बिना नोड जोड़ें

### कब कैश करें
- **Read-heavy वर्कलोड** - जब पढ़ाई, लिखाई से बहुत अधिक हों
- **Expensive computations** - ML मॉडल इन्फ़रेंस results, complex aggregations
- **Frequently accessed डेटा** - उपयोगकर्ता sessions, उत्पाद catalogues, कॉन्फ़िगरेशन

## चरण 2 - कैशिंग Strategies

### कैश-Aside (Lazy Loading)
सबसे आम पैटर्न। Application पहले कैश जांचता है। मिस होने पर डेटाबेस से पढ़ता है, फिर कैश भरता है:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**लाभ:** केवल वही डेटा कैश होता है जो वास्तव में requested है। **हानि:** कैश मिस लेटेंसी जोड़ते हैं, डेटा पुराना हो सकता है।

### Read-Through
कैश खुद मिस होने पर डेटाबेस पढ़ाई संभालता है। Application केवल कैश layer से बात करता है, जो डेटा स्रोत को abstract करती है।

### लिखाई-Through
हर लिखाई सिंक्रोनस रूप से कैश और डेटाबेस दोनों पर जाता है। कैश हमेशा कंसिस्टेंट रहता है, लेकिन लिखाई लेटेंसी बढ़ती है।

### लिखाई-Behind (लिखाई-Back)
लिखाई तुरंत कैश पर जाते हैं। कैश असिंक्रोनस रूप से batches में डेटाबेस को फ़्लश करता है। लिखाई लेटेंसी कम होती है, लेकिन फ़्लश से पहले कैश नोड crash हो तो डेटा loss का जोखिम है।

| रणनीति | Consistency | Read लेटेंसी | लिखाई लेटेंसी | Use Case |
|----------|-------------|-------------|---------------|----------|
| कैश-Aside | Eventual | मिस पेनल्टी | N/A | General purpose |
| Read-Through | Eventual | मिस पेनल्टी | N/A | Simplified पढ़ाई |
| लिखाई-Through | Strong | Fast | Slower | Consistency-critical |
| लिखाई-Behind | Eventual | Fast | Fast | लिखाई-heavy वर्कलोड |

## चरण 3 - इविक्शन पॉलिसी

कैश भर जाने पर कौन सी एंट्री हटाएं?

- **LRU (Least Recently Used)** - उस एंट्री को इविक्ट करता है जिसे सबसे लंबे समय से एक्सेस नहीं किया गया। सबसे अच्छी general-purpose policy
- **LFU (Least Frequently Used)** - सबसे कम बार एक्सेस की गई एंट्री हटाता है। Skewed एक्सेस पैटर्न के लिए बेहतर
- **TTL-based** - एक्सेस से स्वतंत्र रूप से एंट्री तय समय बाद एक्सपायर होती हैं। डेटा ताज़गी के लिए जरूरी
- **Random** - आश्चर्यजनक रूप से प्रभावी और लागू करने में बहुत सरल

<FunFact>Redis approximated LRU algorithm इस्तेमाल करता है, जो कुछ कुंजियां (default: 5) sample करता है और उनमें से least recently used को इविक्ट करता है। यह true LRU जितना लगभग सटीक है, लेकिन एक्सेस order ट्रैक करने के लिए अतिरिक्त मेमोरी ओवरहेड शून्य है।</FunFact>

## चरण 4 - वितरण के लिए कंसिस्टेंट हैशिंग

### Simple हैशिंग की समस्या
`hash(key) % N` नोड के साथ, नोड जोड़ने या हटाने पर लगभग सभी कुंजियां रीमैप हो जाती हैं, जिससे भारी कैश मिस storm होता है।

### Virtual नोड के साथ कंसिस्टेंट हैशिंग
कंसिस्टेंट हैशिंग कुंजियां और नोड दोनों को रिंग पर map करती है। हर कुंजी रिंग पर क्लॉकवाइज़ अगला नोड पाती है:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**Virtual नोड** uneven वितरण समस्या हल करते हैं। हर भौतिक नोड को रिंग पर कई positions मिलती हैं, जिससे कम भौतिक नोड के साथ भी लोड balanced रहता है।

जब नोड जोड़ा या हटाया जाता है, तो केवल रिंग पर उसके पास वाली कुंजियां रीमैप होती हैं। लगभग `K/N` कुंजियां (जहां K कुल कुंजियां और N नोड संख्या है), सभी नहीं।

## चरण 5 - कैश स्टाम्पीड रोकथाम

**कैश स्टाम्पीड** तब होता है जब कोई लोकप्रिय cached एंट्री एक्सपायर होती है और सैकड़ों समवर्ती अनुरोध एक साथ कैश मिस करके डेटाबेस पर पहुंचती हैं।

### समाधान

**Mutex/Locking:** कैश मिस होने पर वितरित lock लें। केवल एक अनुरोध डेटाबेस से फ़ेच करती है। बाकी कैश फिर से भरने का इंतज़ार करती हैं।

**Probabilistic Early Expiry:** हर अनुरोध के पास TTL वास्तव में एक्सपायर होने से पहले कैश रीफ़्रेश करने का छोटा random chance होता है। इससे रीफ़्रेश लोड समय में फैलता है, expiry पर thundering herd नहीं बनता।

**Background रीफ़्रेश:** Background प्रोसेस लोकप्रिय कैश एंट्री को एक्सपायर होने से पहले रीफ़्रेश करता है। Hot कुंजियां के लिए कैश कभी खाली नहीं होता।

<ThinkAboutIt>Flash sale पर विचार करें जहां उत्पाद पेज को 100,000 अनुरोध per सेकंड मिलते हैं। उत्पाद details कैश एंट्री एक्सपायर हो जाती है। स्टाम्पीड रोकथाम के बिना सभी 100K अनुरोध डेटाबेस को एक साथ hit करती हैं। आप कौन सी रोकथाम रणनीति चुनेंगे, और क्यों?</ThinkAboutIt>

## चरण 6 - Redis Cluster आर्किटेक्चर

Redis Cluster सबसे व्यापक रूप से deployed वितरित कैश है:

- Master नोड में वितरित **16,384 हैश स्लॉट**
- हर कुंजी `CRC16(key) % 16384` से स्लॉट पर map होती है
- **Replication:** हर मास्टर के पास failover के लिए एक या अधिक रेप्लिका होते हैं
- **Automatic failover:** मास्टर विफल होने पर उसका रेप्लिका सेकंड में promote होता है

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### Monitoring कुंजी Metrics
- **Hit ratio** - target 95%+; 80% से कम कैशिंग समस्या दिखाता है
- **मेमोरी usage** - evictions से बचने के लिए 80% से कम रहें
- **इविक्शन रेट** - high evictions का मतलब कैश छोटा है
- **लेटेंसी percentiles** - कैश हिट के लिए p99 1ms से कम होना चाहिए

## चरण 7 - Real-World कैशिंग पैटर्न

| पैटर्न | Implementation | TTL |
|---------|---------------|-----|
| Session स्टोर | `SET session:{id} {data}` | 30 मिनट |
| API उत्तर कैश | `SET api:/users/123 {json}` | 5 मिनट |
| डेटाबेस query कैश | `SET query:{hash} {result}` | 1 minute |
| रेट limiter काउंटर | `INCR ratelimit:{user}:{window}` | विंडो duration |
| Feature flags | `HSET features {flag} {value}` | 10 सेकंड |

### कैश इनवैलिडेशन
Computer science की सबसे कठिन समस्या (नामकरण चीज़ें के साथ):
- **TTL-based** - सरल, TTL अवधि तक staleness सहता है
- **Event-driven** - डेटा बदलने पर इनवैलिडेशन इवेंट publish करें (Kafka या Redis Pub/Sub से)
- **Version-based** - कैश कुंजी में version शामिल करें। लिखाई पर version बढ़ाकर पुरानी एंट्री प्रभावी रूप से invalidate करें
