# Distributed Cache डिज़ाइन करें - Redis Architecture शुरू से

Caching system performance सुधारने की सबसे प्रभावी तकनीक है। अच्छी तरह डिज़ाइन किया गया distributed cache database load 90%+ तक घटा सकता है और response times को सैकड़ों milliseconds से sub-millisecond तक ला सकता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- Optional TTL (time-to-live) के साथ key-value pairs store करें
- सामान्य operations का समर्थन करें: GET, SET, DELETE और bulk operations
- Horizontal scaling के लिए data को कई nodes में distribute करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **कम लेटेंसी** - cache hits के लिए sub-millisecond reads
- **High throughput** - हर node पर 100K+ operations per second
- **High availability** - cache failures से system बंद नहीं होना चाहिए
- **Scalability** - downtime के बिना nodes जोड़ें

### कब Cache करें
- **Read-heavy workloads** - जब reads, writes से बहुत अधिक हों
- **Expensive computations** - ML model inference results, complex aggregations
- **Frequently accessed data** - user sessions, product catalogues, configuration

## चरण 2 - Caching Strategies

### Cache-Aside (Lazy Loading)
सबसे आम pattern। Application पहले cache जांचता है। Miss होने पर database से पढ़ता है, फिर cache भरता है:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**लाभ:** केवल वही data cache होता है जो वास्तव में requested है। **हानि:** cache misses latency जोड़ते हैं, data stale हो सकता है।

### Read-Through
Cache खुद miss होने पर database reads संभालता है। Application केवल cache layer से बात करता है, जो data source को abstract करती है।

### Write-Through
हर write synchronously cache और database दोनों पर जाता है। Cache हमेशा consistent रहता है, लेकिन write latency बढ़ती है।

### Write-Behind (Write-Back)
Writes तुरंत cache पर जाते हैं। Cache asynchronously batches में database को flush करता है। Write latency कम होती है, लेकिन flush से पहले cache node crash हो तो data loss का जोखिम है।

| Strategy | Consistency | Read Latency | Write Latency | Use Case |
|----------|-------------|-------------|---------------|----------|
| Cache-Aside | Eventual | Miss penalty | N/A | General purpose |
| Read-Through | Eventual | Miss penalty | N/A | Simplified reads |
| Write-Through | Strong | Fast | Slower | Consistency-critical |
| Write-Behind | Eventual | Fast | Fast | Write-heavy workloads |

## चरण 3 - Eviction Policies

Cache भर जाने पर कौन सी entries हटाएं?

- **LRU (Least Recently Used)** - उस entry को evict करता है जिसे सबसे लंबे समय से access नहीं किया गया। सबसे अच्छी general-purpose policy
- **LFU (Least Frequently Used)** - सबसे कम बार access की गई entry हटाता है। Skewed access patterns के लिए बेहतर
- **TTL-based** - access से स्वतंत्र रूप से entries तय समय बाद expire होती हैं। Data freshness के लिए जरूरी
- **Random** - आश्चर्यजनक रूप से प्रभावी और लागू करने में बहुत सरल

<FunFact>Redis approximated LRU algorithm इस्तेमाल करता है, जो कुछ keys (default: 5) sample करता है और उनमें से least recently used को evict करता है। यह true LRU जितना लगभग accurate है, लेकिन access order track करने के लिए अतिरिक्त memory overhead शून्य है।</FunFact>

## चरण 4 - Distribution के लिए Consistent Hashing

### Simple Hashing की समस्या
`hash(key) % N` nodes के साथ, node जोड़ने या हटाने पर लगभग सभी keys remap हो जाती हैं, जिससे भारी cache miss storm होता है।

### Virtual Nodes के साथ Consistent Hashing
Consistent hashing keys और nodes दोनों को ring पर map करती है। हर key ring पर clockwise अगला node पाती है:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**Virtual nodes** uneven distribution समस्या हल करते हैं। हर physical node को ring पर कई positions मिलती हैं, जिससे कम physical nodes के साथ भी load balanced रहता है।

जब node जोड़ा या हटाया जाता है, तो केवल ring पर उसके पास वाली keys remap होती हैं। लगभग `K/N` keys (जहां K कुल keys और N node count है), सभी नहीं।

## चरण 5 - Cache Stampede Prevention

**Cache stampede** तब होता है जब कोई लोकप्रिय cached entry expire होती है और सैकड़ों concurrent requests एक साथ cache miss करके database पर पहुंचती हैं।

### समाधान

**Mutex/Locking:** Cache miss होने पर distributed lock लें। केवल एक request database से fetch करती है। बाकी cache फिर से भरने का इंतज़ार करती हैं।

**Probabilistic Early Expiry:** हर request के पास TTL वास्तव में expire होने से पहले cache refresh करने का छोटा random chance होता है। इससे refresh load समय में फैलता है, expiry पर thundering herd नहीं बनता।

**Background Refresh:** Background process लोकप्रिय cache entries को expire होने से पहले refresh करता है। Hot keys के लिए cache कभी खाली नहीं होता।

<ThinkAboutIt>Flash sale पर विचार करें जहां product page को 100,000 requests per second मिलते हैं। Product details cache entry expire हो जाती है। Stampede prevention के बिना सभी 100K requests database को एक साथ hit करती हैं। आप कौन सी prevention strategy चुनेंगे, और क्यों?</ThinkAboutIt>

## चरण 6 - Redis Cluster Architecture

Redis Cluster सबसे व्यापक रूप से deployed distributed cache है:

- Master nodes में वितरित **16,384 hash slots**
- हर key `CRC16(key) % 16384` से slot पर map होती है
- **Replication:** हर master के पास failover के लिए एक या अधिक replicas होते हैं
- **Automatic failover:** master fail होने पर उसका replica seconds में promote होता है

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### Monitoring Key Metrics
- **Hit ratio** - target 95%+; 80% से कम caching समस्या दिखाता है
- **Memory usage** - evictions से बचने के लिए 80% से कम रहें
- **Eviction rate** - high evictions का मतलब cache छोटा है
- **Latency percentiles** - cache hits के लिए p99 1ms से कम होना चाहिए

## चरण 7 - Real-World Caching Patterns

| Pattern | Implementation | TTL |
|---------|---------------|-----|
| Session store | `SET session:{id} {data}` | 30 minutes |
| API response cache | `SET api:/users/123 {json}` | 5 minutes |
| Database query cache | `SET query:{hash} {result}` | 1 minute |
| Rate limiter counter | `INCR ratelimit:{user}:{window}` | Window duration |
| Feature flags | `HSET features {flag} {value}` | 10 seconds |

### Cache Invalidation
Computer science की सबसे कठिन समस्या (naming things के साथ):
- **TTL-based** - सरल, TTL अवधि तक staleness सहता है
- **Event-driven** - data बदलने पर invalidation events publish करें (Kafka या Redis Pub/Sub से)
- **Version-based** - cache key में version शामिल करें। Writes पर version बढ़ाकर पुरानी entries प्रभावी रूप से invalidate करें
