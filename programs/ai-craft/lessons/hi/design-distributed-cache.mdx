# वितरितद कैश डिज़ाइन करें - Redis आर्किटेक्चर शुरू से

कैशिंग सिस्टम प्रदर्शन बेहतर करने की सबसे प्रभावी टेचनिक्वे है। एक अच्छी तरह डिज़ाइन किया गया वितरित कैश डेटाबेस लोड को 90%+ तक कम कर सकता है और प्रतिक्रिया टिमेस को सैकड़ों मिललिसेकंडस से सुब-मिललिसेकंड तक ला सकता है।

## चरण 1 - ज़रूरतें इकट्ठा करना

### कार्यात्मक ज़रूरतें
- केय-वलुए पैरस स्टोर करना वैकल्पिक TTL (टिमे-टो-लिवे) के साथ
- कोममोन ऑपरेशन सपोर्ट करना: GET, SET, DELETE, और बुलक ऑपरेशन
- होरिज़ोनटल स्केलिंग के लिए डेटा को कई नोड में वितरित करना

### गैर-कार्यात्मक ज़रूरतें
- **कम लेटेंसी** - कैश हिटस के लिए सुब-मिललिसेकंड रीड
- **उच्च थरोउघपुट** - प्रति नोड 100K+ ऑपरेशन प्रति सेकंड
- **उच्च उपलब्धता** - कैश विफलताएँ से सिस्टम दोवन नहीं होना चाहिए
- **स्केलेबिलिटी** - बिना दोवनटिमे के नोड जोड़ें करना

### कब कैश करें
- **रेअद-हेअवय वोरककमिज्ञापन** - जब रीड, राइट से बहुत ज़्यादा हों
- **एक्सपेनसिवे गणनाओं** - ML मॉडल इन्फ़रेंस नतीजे, जटिल एग्रीगेशन
- **बार-बार एक्सेस डेटा** - यूज़र सेसिओनस, उत्पाद कैटलॉग, कॉन्फ़िगरेशन

## चरण 2 - कैशिंग रणनीतियाँ

### कचे-असिदे (लज़य लोअदिङ)
सबसे आम पैटर्न। ऐप्लिकेशन पहले कैश जाँच करता है; मिस होने पर डेटाबेस से रेअद करता है, फिर कैश पॉपुलटे करता है:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**परोस:** सिर्फ़ वही कैश होता है जो वास्तव में रिक्वेस्ट किया जाता है। **कोनस:** कैश मिसेस पर लेटेंसी एजी है; डेटा सटले हो सकता है।

### रेअद-थरोउघ
कैश खुद मिस होने पर डेटाबेस रीड संभाल करता है। ऐप्लिकेशन सिर्फ़ कैश परत से बात करती है, जो डेटा स्रोत को अमूर्त करता है।

### वरिटे-थरोउघ
हर राइट कैश और डेटाबेस दोनों में सिंक्रोनस रूप से जाता है। कैश हमेशा कोनसिसटेनट रहता है लेकिन राइट लेटेंसी एजी है।

### वरिटे-बेहिनद (वरिटे-बक)
वरिटेस तुरंत कैश में जाते हैं; कैश असिंक्रोनस रूप से बटचेस में डेटाबेस को फ़लुश करता है। वरिटे लेटेंसी कम होती है लेकिन अगर कैश नोड फ़लुश से पहले क्रैश हो जाए तो डेटा लोस का जोखिम है।

| सटरेटगय | संगति | रेअद लेटेंसी | वरिटे लेटेंसी | उपयोग कसे |
|----------|-------------|-------------|---------------|----------|
| कचे-असिदे | इवेंटुअल | मिस पेनल्टी | N/A | सामान्य उद्देश्य |
| रेअद-थरोउघ | इवेंटुअल | मिस पेनल्टी | N/A | सरल रीड |
| वरिटे-थरोउघ | सटरोङ | तेज़ | सकमेर | कोनसिसटेनकय-महत्वपूर्ण |
| वरिटे-बेहिनद | इवेंटुअल | तेज़ | तेज़ | वरिटे-हेअवय वोरककमिज्ञापन |

## चरण 3 - इविक्शन पोलिकिएस

जब कैश भर जाए, तो कौन सी एंट्री हटाएँ?

- **LRU (सबसे कम हाल में इस्तेमाल)** - सबसे लंबे समय से एक्सेस न की गई एंट्री को निकाल करता है। सबसे अच्छी सामान्य-उद्देश्य पॉलिसी
- **LFU (सबसे कम बार इस्तेमाल)** - सबसे कम बार एक्सेस की गई एंट्री को निकाल करता है। टेढ़े एक्सेस पैटर्न के लिए बेहतर
- **टटल-बसेद** - एंट्री एक सेट समय बाद एक्सपिरे होती हैं चाहे एक्सेस हों या नहीं। डेटा ताज़गी के लिए ज़रूरी
- **रैंडम** - हैरान करने वाला प्रभावी और लागू करने में बहुत सरल

<FunFact>Redis एक लगभग LRU एल्गोरिदम उपयोग करता है जो कुछ की सैंपल करता है (डिफ़ॉल्ट: 5) और उnameं से सबसे कम हाल में इस्तेमाल को निकाल करता है। यह true LRU जितना ही सटीक है लेकिन एक्सेस ऑर्डर रिकॉर्ड करने के लिए शून्य अतिरिक्त मेमोरी ओवरहेड लगती है।</FunFact>

## चरण 4 - डिस्ट्रिब्यूशन के लिए कोनसिसटेनट हशिङ

### सिमपले हशिङ की समस्या
`hash(key) % N` नोड के साथ, कोई नोड जोड़ें या हटा करने पर लगभग सारी की रीमैप हो जाती हैं, जिससे बहुत बड़ा कैश मिस सटोरम आता है।

### विरटुअल नोदेस के साथ कोनसिसटेनट हशिङ
कोनसिसटेनट हशिङ की और नोड दोनों को एक रिङ पर मैप करता है। हर की रिङ पर अगले क्लॉकवाइज़ नोड को असाइन होती है:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**विरटुअल नोड** उनेवेन डिस्ट्रिब्यूशन समस्या हल करते हैं। हर फयसिकल नोड को रिङ पर कई पोसिशनस मिलती हैं, जिससे कम फयसिकल नोड होने पर भी संतुलित लोड सुनिश्चित होता है।

जब कोई नोड जोड़ें या हटा होता है, तो सिर्फ़ रिङ पर उसके अदजकेनट की रीमैप होती हैं - लगभग `K/N` की (जहाँ K कुल की और N नोड गणना है), सारी नहीं।

## चरण 5 - कैश सटमपेदे परेवेनशन

**कैश सटमपेदे** तब होता है जब कोई लोकप्रिय कचेद एंट्री एक्सपिरे होती है और सैकड़ों समवर्ती रिक्वेस्ट एक साथ कैश मिस करती हैं और डेटाबेस को हिट करती हैं।

### समाधान

**मुटेक्स/लोकिङ:** कैश मिस होने पर एक वितरित लोक अकक्विरे करें। सिर्फ़ एक रिक्वेस्ट डेटाबेस से फ़ेटच करती है; बाकी कैश रेपॉपुलटे होने तक इंतज़ार करती हैं।

**प्रायिक जल्दी एक्सपायरी:** हर रिक्वेस्ट को TTL एक्सपिरे होने से पहले कैश रीफ़्रेश करने का एक छोटा रैंडम संभावना होता है। इससे रीफ़्रेश लोड समय में फैलता होता है बजाय एक्सपायरी पर थंडरिंग हर्ड बनने के।

**पृष्ठभूमि रेफ़रेश:** एक पृष्ठभूमि प्रोसेस लोकप्रिय कैश एंट्री को एक्सपिरे होने से पहले रीफ़्रेश करता है। होट की के लिए कैश कभी खाली नहीं होता।

<ThinkAboutIt>एक फ़्लैश सेल सोचिए जहाँ एक उत्पाद पेज को 100,000 रिक्वेस्ट प्रति सेकंड मिल रही हैं। उत्पाद विवरण कैश एंट्री एक्सपिरे हो जाती है। सटमपेदे परेवेनशन के बिना, सभी 100K रिक्वेस्ट एक साथ डेटाबेस हिट करेंगी। आप कौन सी परेवेनशन रणनीति चुनेंगे, और क्यों?</ThinkAboutIt>

## चरण 6 - Redis कलुसटेर आर्किटेक्चर

Redis कलुसटेर सबसे विदेलय तैनात वितरित कैश है:

- **16,384 हैश सलोटस** मास्टर नोड में वितरित होते हैं
- हर की एक सलोट पर मैप होती है `CRC16(key) % 16384` से
- **रेपलिकशन:** हर मास्टर के पास फ़ैकमेर के लिए एक या ज़्यादा रेपलिकस होते हैं
- **ऑटोमटिक फ़ैकमेर:** अगर मास्टर फ़ेल होता है, तो उसका रेपलिक सेकंड में बढ़ावा हो जाता है

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### मुख्य बात मेट्रिक्स मोनिटोर करना
- **हिट अनुपात** - लक्षित 95%+; 80% से नीचे कैशिंग समस्या इनदिकटे करता है
- **मेमोरी उपयोग** - इविक्शनs से बचने के लिए 80% से नीचे रखें
- **इविक्शन दर** - ज़्यादा इविक्शनs मतलब कैश छोटा है
- **लेटेंसी पेरकेनटिलेस** - कैश हिटस के लिए p99 1ms से कम होना चाहिए

## चरण 7 - वास्तविक दुनिया कैशिंग पैटर्न

| पटटेरन | कार्यान्वयन | TTL |
|---------|---------------|-----|
| सेशन स्टोर | `SET session:{id} {डेटा}` | 30 मिनट |
| API प्रतिक्रिया कैश | `SET api:/users/123 {json}` | 5 मिनट |
| दटबसे क्वेरी कैश | `SET query:{hash} {result}` | 1 मिनट |
| दर लिमिटेर कोउनटेर | `INCR दरlimit:{user}:{window}` | विंडो अवधि |
| फ़ीचर फ़्लैग | `HSET features {flag} {value}` | 10 सेकंड |

### कैश इनवैलिडेशन
कंप्यूटर विज्ञान की सबसे कठिन समस्या (नमिङ थिङस के साथ):
- **टटल-बसेद** - सरल, TTL अवधि तक सटलेनेस टोलेरेट करता है
- **एवेनट-चलातेन** - डेटा बदलने पर इनवैलिडेशन इवेंट पुबलिश करें (Kafka या Redis पुब/सुब से)
- **वर्शन-आधारित** - कैश की में वर्शन शामिल करें; राइट पर वर्शन इनकरेमेनट करें ताकि पुरानी एंट्री एफ़फ़ेकटिवेलय इनवलिदटे हों
