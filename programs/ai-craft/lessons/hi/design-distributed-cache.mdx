# वितरितद कैश डिज़ाइन करें - Redis आर्किटेक्चर शुरू से

कैशिंग सिस्टम प्रदर्शन बेहतर करने की सबसे प्रभावी टेचनिक्वे है। एक अच्छी तरह डिज़ाइन किया गया वितरित कैश डेटाबेस लोड को 90%+ तक कम कर सकता है और प्रतिक्रिया टिमेस को सैकड़ों मिललिसेकोनदस से सुब-मिललिसेकोनद तक ला सकता है।

## चरण 1 - ज़रूरतें इकट्ठा करना

### कार्यात्मक ज़रूरतें
- वैकल्पिक TTL (time-to-live) के साथ key-value pairs स्टोर करना
- कोममोन ऑपरेशन सपोर्ट करना: GET, SET, DELETE, और बुलक ऑपरेशन
- होरिज़ोनटल स्केलिंग के लिए डेटा को कई नोड में वितरित करना

### गैर-कार्यात्मक ज़रूरतें
- **कम लेटेंसी** - कैश हिटस के लिए सुब-मिललिसेकोनद रीड
- **उच्च थरोउघपुट** - प्रति नोड 100K+ ऑपरेशन प्रति सेकंड
- **उच्च उपलब्धता** - कैश फ़ैलुरेस से सिस्टम दोवन नहीं होना चाहिए
- **सकलबिलिटय** - बिना दोवनटिमे के नोड जोड़ें करना

### कब कैश करें
- **रेअद-हेअवय वोरकलोविज्ञापन** - जब रीड, राइट से बहुत ज़्यादा हों
- **महंगी computations** - ML मॉडल inference results, जटिल aggregations
- **बार-बार एक्सेस डेटा** - यूज़र सेसिओनस, उत्पाद कैटलॉग, कॉन्फ़िगरेशन

## चरण 2 - कैशिंग रणनीतियाँ

### कचे-असिदे (लज़य लोअदिङ)
सबसे आम पैटर्न। अपपलिकशन पहले कैश जाँच करता है; मिस होने पर डेटाबेस से रेअद करता है, फिर कैश पॉपुलटे करता है:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**परोस:** सिर्फ़ वही कैश होता है जो वास्तव में रिक्वेस्ट किया जाता है। **कोनस:** कैश मिसेस पर लेटेंसी एजी है; डेटा सटले हो सकता है।

### रेअद-थरोउघ
मिस होने पर cache खुद database reads संभालता है। ऐप्लिकेशन सिर्फ़ cache layer से बात करती है, जो data source को abstract कर देती है।

### वरिटे-थरोउघ
हर write cache और database दोनों में synchronously जाता है। Cache हमेशा consistent रहता है, लेकिन write latency बढ़ती है।

### वरिटे-बेहिनद (वरिटे-बक)
Writes तुरंत cache में जाते हैं। Cache asynchronously batches में database को flush करता है। Write latency कम होती है, लेकिन अगर cache node flush से पहले crash हो जाए तो data loss का जोखिम है।

| सटरटेगय | संगति | रेअद लेटेंसी | वरिटे लेटेंसी | उपयोग कसे |
|----------|-------------|-------------|---------------|----------|
| Cache-Aside | Eventual | Miss penalty | N/A | सामान्य उपयोग |
| Read-Through | Eventual | Miss penalty | N/A | सरल reads |
| वरिटे-थरोउघ | सटरोङ | तेज़ | सलोवेर | कोनसिसटेनकय-महत्वपूर्ण |
| वरिटे-बेहिनद | एवेनटुअल | तेज़ | तेज़ | वरिटे-हेअवय वोरकलोविज्ञापन |

## चरण 3 - एविकशन पोलिकिएस

जब कैश भर जाए, तो कौन सी एनटरिएस हटाएँ?

- **LRU (Least Recently Used)** - जिस entry को सबसे लंबे समय से access नहीं किया गया, उसे evict करता है। सबसे अच्छी general-purpose policy
- **LFU (Least Frequently Used)** - सबसे कम बार access की गई entry को evict करता है। Skewed access patterns के लिए बेहतर
- **टटल-बसेद** - एनटरिएस एक सेट समय बाद एक्सपिरे होती हैं चाहे एक्सेस हों या नहीं। डेटा ताज़गी के लिए ज़रूरी
- **रनदोम** - हैरान करने वाला प्रभावी और लागू करने में बहुत सरल

<FunFact>Redis एक लगभग LRU एल्गोरिदम उपयोग करता है जो कुछ की सैंपल करता है (डिफ़ॉल्ट: 5) और उnameं से सबसे कम हाल में इस्तेमाल को निकाल करता है। यह true LRU जितना ही सटीक है लेकिन एक्सेस ऑर्डर रिकॉर्ड करने के लिए शून्य अतिरिक्त मेमोरी ओवरहेड लगती है।</FunFact>

## चरण 4 - डिस्ट्रिब्यूशन के लिए कोनसिसटेनट हशिङ

### सिमपले हशिङ की समस्या
`hash(key) % N` नोड के साथ, कोई नोड जोड़ें या हटा करने पर लगभग सारी की रेमप हो जाती हैं, जिससे बहुत बड़ा कैश मिस सटोरम आता है।

### विरटुअल नोदेस के साथ कोनसिसटेनट हशिङ
कोनसिसटेनट हशिङ की और नोड दोनों को एक रिङ पर मैप करता है। हर की रिङ पर अगले कलोकविसे नोड को असाइन होती है:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**विरटुअल नोड** उनेवेन डिस्ट्रिब्यूशन समस्या हल करते हैं। हर फयसिकल नोड को रिङ पर कई पोसिशनस मिलती हैं, जिससे कम फयसिकल नोड होने पर भी संतुलित लोड सुनिश्चित होता है।

जब कोई नोड जोड़ें या हटा होता है, तो सिर्फ़ रिङ पर उसके अदजकेनट की रेमप होती हैं - लगभग `K/N` की (जहाँ K कुल की और N नोड गणना है), सारी नहीं।

## चरण 5 - कैश सटमपेदे परेवेनशन

**Cache stampede** तब होता है जब कोई लोकप्रिय cached entry expire होती है और सैकड़ों concurrent requests एक साथ cache miss करके database को hit करती हैं।

### समाधान

**मुटेक्स/लोकिङ:** कैश मिस होने पर एक वितरित लोक अकक्विरे करें। सिर्फ़ एक रिक्वेस्ट डेटाबेस से फ़ेटच करती है; बाकी कैश रेपॉपुलटे होने तक इंतज़ार करती हैं।

**Probabilistic Early Expiry:** हर request के पास TTL सच में expire होने से पहले cache refresh करने का एक छोटा random chance होता है। इससे refresh load समय के साथ फैलता है, बजाय expiry पर thundering herd बनाने के।

**Background Refresh:** एक background process लोकप्रिय cache entries को expire होने से पहले refresh करता है। Hot keys के लिए cache कभी empty नहीं होता।

<ThinkAboutIt>एक flash sale सोचिए जहाँ product page को 100,000 requests प्रति सेकंड मिल रही हैं। Product details cache entry expire हो जाती है। Stampede prevention के बिना, सभी 100K requests एक साथ database hit करेंगी। आप कौन सी prevention strategy चुनेंगे, और क्यों?</ThinkAboutIt>

## चरण 6 - Redis कलुसटेर आर्किटेक्चर

Redis कलुसटेर सबसे विदेलय तैनात वितरित कैश है:

- **16,384 हैश सलोटस** मास्टर नोड में वितरित होते हैं
- हर की एक सलोट पर मैप होती है `CRC16(key) % 16384` से
- **रेपलिकशन:** हर मास्टर के पास फ़ैलोवेर के लिए एक या ज़्यादा रेपलिकस होते हैं
- **औटोमटिक फ़ैलोवेर:** अगर मास्टर फ़ेल होता है, तो उसका रेपलिक सेकंड में बढ़ावा हो जाता है

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### मुख्य बात मेट्रिक्स मोनिटोर करना
- **हिट अनुपात** - लक्षित 95%+; 80% से नीचे कैशिंग समस्या इनदिकटे करता है
- **Memory usage** - evictions से बचने के लिए 80% से नीचे रखें
- **Eviction rate** - ज़्यादा evictions का मतलब cache undersized है
- **लेटेंसी पेरकेनटिलेस** - कैश हिटस के लिए p99 1ms से कम होना चाहिए

## चरण 7 - वास्तविक दुनिया कैशिंग पैटर्न

| Pattern | Implementation | TTL |
|---------|---------------|-----|
| सेशन स्टोर | `SET session:{id} {data}` | 30 मिनट |
| API प्रतिक्रिया कैश | `SET api:/users/123 {json}` | 5 मिनट |
| दटबसे क्वेरी कैश | `SET query:{hash} {result}` | 1 मिनुटे |
| दर लिमिटेर कोउनटेर | `INCR ratelimit:{user}:{window}` | विंडो अवधि |
| Feature flags | `HSET features {flag} {value}` | 10 सेकंड |

### कैश इनवैलिडेशन
कंप्यूटर विज्ञान की सबसे कठिन समस्या (नमिङ थिङस के साथ):
- **टटल-बसेद** - सरल, TTL अवधि तक सटलेनेस टोलेरटे करता है
- **एवेनट-दरिवेन** - डेटा बदलने पर इनवैलिडेशन इवेंट पुबलिश करें (Kafka या Redis पुब/सुब से)
- **वर्शन-आधारित** - कैश की में वर्शन शामिल करें; राइट पर वर्शन इनकरेमेनट करें ताकि पुरानी एनटरिएस एफ़फ़ेकटिवेलय इनवलिदटे हों
