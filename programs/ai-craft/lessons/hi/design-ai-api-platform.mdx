## इंटरव्यू प्रॉम्प्ट

*"एक AI API प्लैटफ़ॉर्म डिज़ाइन करें जो कई मशीन लर्निंग मॉडल को डेवलपरों को REST API के ज़रिए सर्व करे - बिल्कुल वैसे जैसे OpenAI या Hugging Face स्केल पर मॉडल सर्व करते हैं।"*

यह सवाल इंटरव्यू में काफ़ी लोकप्रिय हो रहा है क्योंकि इसमें **API प्लैटफ़ॉर्म डिज़ाइन** और **GPU इन्फ़्रास्ट्रक्चर चललेङेस** दोनों जोड़ते होते हैं जो AI वोरकलोविज्ञापन के लिए उनिक्वे हैं।

## चरण 1: ज़रूरतें समझना

**कार्यात्मक ज़रूरतें:**
- मुलटिपले AI मॉडल (टेक्स्ट जनरेशन, इमगे वर्गीकरण, एम्बेडिंग) को REST API से सर्व करना
- API की प्रमाणीकरण के साथ पेर-केय उसगे क्वोटस
- हर API कॉल पर उसगे टरकिङ और बिललिङ
- मुलटिपले मॉडल वेरसिओनस को A/B परीक्षण के साथ सपोर्ट करना
- लोङ-रुननिङ जनरेशन कार्यों के लिए स्ट्रीमिंग रेसपोनसेस

**गैर-कार्यात्मक ज़रूरतें:**
- लेटेंसी: एमबेददिङ मॉडल के लिए p50 500ms से कम, गेनेरटिवे मॉडल के लिए p50 2s से कम
- थरोउघपुट: सभी मॉडल पर 10,000 रिक्वेस्ट प्रति सेकंड
- अवैलबिलिटय: सुचारु गिरावट के साथ 99.9% उपटिमे
- लागत एफ़फ़िकिएनकय: GPUs महँगे हैं - उटिलिसशन मक्सिमिसे करना ज़रूरी है

<Callout>
AI पलटफ़ोरमस की लेटेंसी बहुत वरिअबले होती है। एक टेक्स्ट कोमपलेशन रिक्वेस्ट 200ms या 30 सेकंड भी ले सकता है - आउटपुट लेङथ पर निर्भर करता है। हमेशा दिसकुस करें कि आपका डिज़ाइन इस वरिअनके को कैसे संभाल करता है।
</Callout>

## चरण 2: API डिज़ाइन

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-6-astra", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - available models की list
GET  /v1/usage?start=2024-01-01    - usage और billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

गेनेरटिवे मॉडल के लिए **सेरवेर-सेनट इवेंट (SSE)** से स्ट्रीमिंग बहुत महत्वपूर्ण है - यूज़र को टोकन परोगरेसिवेलय दिखते हैं बजाय पूरा प्रतिक्रिया आने का इंतज़ार करने के।

## चरण 3: API गटेवय और ऑथेंटिकेशन

API गेटवे प्लैटफ़ॉर्म का फ़रोनट दूर है:

- **ऑथेंटिकेशन** - API की को की स्टोर से वलिदटे करें (स्पीड के लिए Redis, पेरसिसटेनके के लिए डेटाबेस)
- **दर लिमिटिङ** - पेर-केय सीमाएँ एनफ़ोरके करें (जैसे मुफ़्त टिएर के लिए 60 रेक्वेसटस/मिनुटे)
- **रिक्वेस्ट रूटिंग** - रिक्वेस्ट को सही मोदेल-सेरविङ क्लस्टर पर दिरेकट करें
- **रिक्वेस्ट वैलिडेशन** - पयलोअद सचेम, मॉडल उपलब्धता, टोकन सीमाएँ जाँच करें

**रेट लिमिटिंग का कार्यान्वयन:**
Redis में **स्लाइडिंग विंडो कोउनटेर** इस्तेमाल करें:
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

हर रिक्वेस्ट कोउनटेर इनकरेमेनट करती है। लिमिट एक्सकीद होने पर HTTP 429 लौटाएँ।

## चरण 4: मॉडल सेरविङ और GPU सभीोकशन

यहीं AI प्लैटफ़ॉर्म पारंपरिक वेब सेवाओं से मूल रूप से अलग होते हैं। GPUs दुर्लभ और महँगे हैं, और इन्हें विशेष ऑर्केस्ट्रेशन चाहिए।

**मॉडल सर्विंग परत:**
- मॉडल को **Triton इन्फ़रेंस सेरवेर** या **vLLM** जैसे ढाँचे से GPU मेमोरी में लोड किया जाता है
- हर मॉडल वर्शन GPU इंस्टेंस के समर्पित पूल पर चलता है
- बड़े भाषा मॉडल (LLMs) को कई GPUs पर **मॉडल परललेलिसम** की ज़रूरत हो सकती है

**रिक्वेस्ट बटचिङ:**
GPUs पर इनदिविदुअल इन्फ़रेंस रिक्वेस्ट इनेफ़फ़िकिएनट होते हैं। **दयनमिक बटचिङ** कई रिक्वेस्ट को गरोउप करके एक साथ प्रोसेस करता है:
- 10ms तक या 32 रिक्वेस्ट तक कोललेकट करें
- पूरे बैच को एक GPU forward pass में प्रोसेस करें
- हर कललेर को इनदिविदुअल प्रतिक्रिया लौटाएँ

इनदिविदुसभीय प्रोसेस करने की तुलना में यह थरोउघपुट को 5-10x बेहतर कर सकता है।

<FunFact>
एक NVIDIA H100 GPU की कीमत लगभग £25,000 है और यह 700 watts बिजली लेता है। मॉडल सर्विंग के लिए 1,000 GPUs का क्लस्टर चलाने में सिर्फ़ बिजली और हार्डवेयर पर £2 मिलियन प्रति महीने से ज़्यादा खर्च होता है - इसीलिए कुशल बैचिंग और उपयोग बहुत मायने रखते हैं।
</FunFact>

## चरण 5: मॉडल वेरसिओनस के बीच A/B परीक्षण

नया मॉडल वर्शन तैनात करते वक़्त कोनटरोललेद रोललोउट ज़रूरी है:

- **ट्रैफ़िक विभाजन** - 5% रिक्वेस्ट नए मॉडल पर, 95% वर्तमान पर रूट करें
- **शदोव मोदे** - प्रोडक्शन ट्रैफ़िक पर नया मॉडल रुन करें बिना यूज़र को नतीजे लौटाएँ किए
- **मेट्रिक्स कोमपरिसोन** - लेटेंसी, आउटपुट गुणवत्ता सकोरेस, एररोर दरें, लागत प्रति रिक्वेस्ट
- **गरदुअल रोललोउट** - विश्वास बढ़ने पर नए वर्शन पर ट्रैफ़िक बढ़ाएँ

रोउटिङ तर्क API गेटवे में रहती है:
```
model: "gpt-6-astra"  →  95% → gpt-6-astra (current)
                →   5% → claude-opus-5-5 (candidate)
```

<ThinkAboutIt>
नए LLM वर्शन को "बेटटेर" मूल्यांकन करना हैरान करने वाला मुश्किल है - वर्गीकरण मॉडल के विपरीत, कोई सरल सटीकता मेट्रिक नहीं है। गेनेरटिवे AI मॉडल के लिए स्वचालित गुणवत्ता मूल्यांकन सिस्टम आप कैसे डिज़ाइन करेंगे?
</ThinkAboutIt>

## चरण 6: उसगे टरकिङ और बिललिङ

AI APIs आमतौर पर प्रति टोकन बिलल करती हैं (LLMs के लिए इनपुट + आउटपुट टोकन, बाकी मॉडल के लिए प्रति रिक्वेस्ट)।

**एवेनट-दरिवेन बिललिङ पाइपलाइन:**
1. हर API प्रतिक्रिया में उसगे हेअदेर होता है: `x-usage-tokens: 847`
2. Kafka पर बिललिङ घटना पुबलिश होता है: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. बिललिङ अगगरेगशन सर्विस इवेंट लेते करके रुननिङ टोटलस अपडेट करती है
4. उसगे डैशबोर्ड टिमे-सेरिएस डेटाबेस से अगगरेगटेद डेटा क्वेरी करते हैं

**Kafka क्यों?** बिलिंग भरोसेमंद होनी चाहिए, लेकिन उसका सिंक्रोनस होना ज़रूरी नहीं। अगर बिलिंग सर्विस अस्थायी रूप से डाउन है, तो इवेंट Kafka में क्यू होते हैं और रिकवर होने पर प्रोसेस होते हैं - कोई usage डेटा खोता नहीं है।

## चरण 7: मोनिटोरिङ और ओबसेरवबिलिटय

AI प्लैटफ़ॉर्म को सामान्य वेब सेवाओं से ज़्यादा निगरानी चाहिए:

| मेट्रिक | क्यों ज़रूरी है |
|--------|----------------|
| इन्फ़रेंस लेटेंसी (p50, p95, p99) | यूज़र अनुभव और SLA अनुपालन |
| GPU उटिलिसशन | लागत एफ़फ़िकिएनकय - इदले GPUs पैसे बर्बाद करते हैं |
| टोकेनस प्रति सेकंड | थरोउघपुट कपकिटय और स्केलिंग सिग्नल |
| एररोर दर by मॉडल | मोदेल-सपेकिफ़िक फ़ैलुरेस देटेकट करना |
| क्यू गहराई | स्केलिंग ट्रिगर - गहरी क्यू मतलब देमनद कपकिटय से ज़्यादा है |
| आउटपुट गुणवत्ता सकोरेस | मॉडल गिरावट देटेकट करना (स्वचालित एवल से) |

**अलेरटिङ थरेशोलदस:** GPU उटिलिसशन 40% से नीचे जाए तो सकले-दोवन ट्रिगर; क्यू गहराई 100 से ऊपर जाए तो सकले-उप ट्रिगर।

## चरण 8: औटो-स्केलिंग

AI वोरकलोविज्ञापन की देमनद बहुत वरिअबले होती है। औटो-स्केलिंग को रेसपोनसिवेनेस और लागत संतुलन करना होता है:

- **होरिज़ॉन्टल स्केलिंग** - क्यू गहराई या लेटेंसी थ्रेशोल्ड पार होने पर और GPU इंस्टेंस जोड़ें
- **प्रेडिक्टिव स्केलिंग** - ऐतिहासिक ट्रैफ़िक पैटर्न से अपेक्षित पीक से पहले क्षमता प्री-प्रोविज़न करें
- **स्केल-टू-ज़ीरो** - कम इस्तेमाल होने वाले मॉडल के लिए सभी इंस्टेंस बंद करें और मांग आने पर कोल्ड-स्टार्ट करें
- **Warm pools** - कोल्ड-स्टार्ट लेटेंसी से बचने के लिए कुछ इंस्टेंस में मॉडल पहले से लोड रखें

सकले-टो-ज़ेरो रणनीति उन पलटफ़ोरमस के लिए ख़ास ज़रूरी है जो सैकड़ों मॉडल होसट करते हैं - हर मॉडल को हर वक़्त GPU मेमोरी में लोअदेद नहीं रख सकते।
