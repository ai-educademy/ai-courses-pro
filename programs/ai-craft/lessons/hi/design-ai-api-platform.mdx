## इंटरव्यू प्रॉम्प्ट

*"एक AI API प्लैटफ़ॉर्म डिज़ाइन करें जो कई मशीन लर्निंग मॉडल को डेवलपरों को REST API के ज़रिए सर्व करे - बिल्कुल वैसे जैसे OpenAI या Hugging Face स्केल पर मॉडल सर्व करते हैं।"*

यह सवाल इंटरव्यू में काफ़ी लॉकप्रिय हो रहा है क्योंकि इसमें **API प्लैटफ़ॉर्म डिज़ाइन** और **GPU इन्फ़्रास्ट्रक्चर चुनौतियाँ** दोनों जोड़ते होते हैं जो AI वर्कलोड के लिए उनिक्वे हैं।

## चरण 1: ज़रूरतें समझना

**कार्यात्मक ज़रूरतें:**
- कई AI मॉडल (टेक्स्ट जनरेशन, इमेज वर्गीकरण, एम्बेडिंग) को REST API से सर्व करना
- API कुंजी प्रमाणीकरण के साथ प्रति-कुंजी उपयोग कोटा
- हर API कॉल पर उपयोग ट्रैकिंग और बिलिंग
- कई मॉडल वर्ज़न को A/B परीक्षण के साथ सपोर्ट करना
- लंबे-चलता हुआ जनरेशन कार्यों के लिए स्ट्रीमिंग रिस्पॉन्स

**गैर-कार्यात्मक ज़रूरतें:**
- लेटेंसी: एम्बेडिंग मॉडल के लिए p50 500ms से कम, जनरेटिव मॉडल के लिए p50 2s से कम
- थ्रूपुट: सभी मॉडल पर 10,000 रिक्वेस्ट प्रति सेकंड
- उपलब्धता: सुचारु गिरावट के साथ 99.9% अपटाइम
- लागत दक्षता: GPUs महँगे हैं - उपयोग अधिकतम करना ज़रूरी है

<Callout>
AI प्लैटफ़ॉर्म कुंजी लेटेंसी बहुत परिवर्तनशील होती है। एक टेक्स्ट कम्प्लीशन रिक्वेस्ट 200ms या 30 सेकंड भी ले सकता है - आउटपुट लंबाई पर निर्भर करता है। हमेशा चर्चा करें कि आपका डिज़ाइन इस फ़र्क को कैसे संभाल करता है।
</Callout>

## चरण 2: API डिज़ाइन

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-6-astra", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - available models की list
GET  /v1/usage?start=2024-01-01    - usage और billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

जनरेटिव मॉडल के लिए **सर्वर-सेंट इवेंट (SSE)** से स्ट्रीमिंग बहुत महत्वपूर्ण है - यूज़र को टोकन क्रमिक रूप से दिखते हैं बजाय पूरा प्रतिक्रिया आने का इंतज़ार करने के।

## चरण 3: API गेटवे और ऑथेंटिकेशन

API गेटवे प्लैटफ़ॉर्म का फ़्रंट डोर है:

- **ऑथेंटिकेशन** - API कुंजी को कुंजी स्टोर से वैलिडेट करें (स्पीड के लिए Redis, स्थायित्व के लिए डेटाबेस)
- **दर लिमिटिंग** - प्रति-कुंजी सीमाएँ लागू करें (जैसे मुफ़्त टियर के लिए 60 रिक्वेस्ट/मिनट)
- **रिक्वेस्ट रूटिंग** - रिक्वेस्ट को सही मॉडल-सर्विंग क्लस्टर पर दिरेकट करें
- **रिक्वेस्ट वैलिडेशन** - पेलोड स्कीमा, मॉडल उपलब्धता, टोकन सीमाएँ जाँच करें

**दर लिमिटिंग कार्यान्वयन:**
Redis में **स्लाइडिंग विंडो काउंटर** इस्तेमाल करें:
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

हर रिक्वेस्ट काउंटर बढ़ाती है। लिमिट पार होने पर HTTP 429 लौटाएँ।

## चरण 4: मॉडल सर्विंग और GPU आवंटन

यहाँ AI प्लैटफ़ॉर्म पारंपरिक वेब सेवाएँ से मूल रूप से अलग हैं। GPUs दुर्लभ हैं, महँगे हैं और विशेष ऑर्केस्ट्रेशन चाहिए।

**मॉडल सर्विंग परत:**
- मॉडल को **Triton इन्फ़रेंस सर्वर** या **vLLM** जैसे ढाँचे से GPU मेमोरी में लोड किया जाता है
- हर मॉडल वर्शन एक समर्पित GPU इंस्टेंस पूल पर चलता है
- बड़े भाषा मॉडल (LLMs) को कई GPUs पर **मॉडल समानांतरता** कुंजी ज़रूरत हो सकती है

**रिक्वेस्ट बैचिंग:**
GPUs पर व्यक्तिगत इन्फ़रेंस रिक्वेस्ट अक्षम होते हैं। **डायनेमिक बैचिंग** कई रिक्वेस्ट को समूह करके एक साथ प्रोसेस करता है:
- 10ms तक या 32 रिक्वेस्ट तक इकट्ठा करें
- पूरे बैच को एक GPU फ़ॉरवर्ड पास में प्रोसेस करें
- हर कॉलर को व्यक्तिगत प्रतिक्रिया लौटाएँ

व्यक्तिगत रूप से प्रोसेस करने की तुलना में यह थ्रूपुट को 5-10x बेहतर कर सकता है।

<FunFact>
एक NVIDIA H100 GPU कुंजी कीमत लगभग £25,000 है और यह 700 वॉट बिजली लेता है। मॉडल सर्विंग के लिए 1,000 GPUs का क्लस्टर चलाने में सिर्फ़ बिजली और हार्डवेयर में £2 मिलियन प्रति महीने से ज़्यादा खर्च होता है - इसीलिए कुशल बैचिंग और उपयोग बहुत मायने रखती है।
</FunFact>

## चरण 5: मॉडल वर्ज़न के बीच A/B परीक्षण

नया मॉडल वर्शन तैनात करते वक़्त नियंत्रित रोलआउट ज़रूरी है:

- **ट्रैफ़िक विभाजन** - 5% रिक्वेस्ट नए मॉडल पर, 95% वर्तमान पर रूट करें
- **शैडो मोड** - प्रोडक्शन ट्रैफ़िक पर नया मॉडल चल करें बिना यूज़र को नतीजे लौटाएँ किए
- **मेट्रिक्स तुलना** - लेटेंसी, आउटपुट गुणवत्ता स्कोर, एरर दरें, लागत प्रति रिक्वेस्ट
- **क्रमिक रोलआउट** - विश्वास बढ़ने पर नए वर्शन पर ट्रैफ़िक बढ़ाएँ

रूटिंग तर्क API गेटवे में रहती है:
```
model: "gpt-6-astra"  →  95% → gpt-6-astra (current)
                →   5% → claude-opus-5-5 (candidate)
```

<ThinkAboutIt>
नए LLM वर्शन को "बेहतर" मूल्यांकन करना हैरान करने वाला मुश्किल है - वर्गीकरण मॉडल के विपरीत, कोई सरल सटीकता मेट्रिक नहीं है। जनरेटिव AI मॉडल के लिए स्वचालित गुणवत्ता मूल्यांकन सिस्टम आप कैसे डिज़ाइन करेंगे?
</ThinkAboutIt>

## चरण 6: उपयोग ट्रैकिंग और बिलिंग

AI APIs आमतौर पर प्रति टोकन बिल करती हैं (LLMs के लिए इनपुट + आउटपुट टोकन, बाकी मॉडल के लिए प्रति रिक्वेस्ट)।

**इवेंट-driven बिलिंग पाइपलाइन:**
1. हर API प्रतिक्रिया में उपयोग हेडर होता है: `x-usage-tokens: 847`
2. Kafka पर बिलिंग घटना पब्लिश होता है: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. बिलिंग एग्रीगेशन सर्विस इवेंट लेकर चलता हुआ कुल अपडेट करती है
4. उपयोग डैशबोर्ड टाइम-सीरीज़ डेटाबेस से एग्रीगेट किया गया डेटा क्वेरी करते हैं

**Kafka क्यों?** बिलिंग भरोसेमंद होनी चाहिए लेकिन सिंक्रोनस होना ज़रूरी नहीं। अगर बिलिंग सर्विस अस्थायी रूप से डाउन है, इवेंट Kafka में क्यू होते हैं और उबरने पर प्रोसेस होते हैं - कोई उपयोग डेटा खोता नहीं होता।

## चरण 7: मॉनिटरिंग और ऑब्ज़र्वेबिलिटी

AI प्लैटफ़ॉर्म को सामान्य वेब सेवाएँ से ज़्यादा निगरानी चाहिए:

| मेट्रिक | क्यों ज़रूरी है |
|--------|----------------|
| इन्फ़रेंस लेटेंसी (p50, p95, p99) | यूज़र अनुभव और SLA अनुपालन |
| GPU उपयोग | लागत दक्षता - निष्क्रिय GPUs पैसे बर्बाद करते हैं |
| टोकन प्रति सेकंड | थ्रूपुट क्षमता और स्केलिंग सिग्नल |
| एरर दर by मॉडल | मॉडल-विशिष्ट विफलताएँ पहचान करना |
| क्यू गहराई | स्केलिंग ट्रिगर - गहरी क्यू मतलब मांग क्षमता से ज़्यादा है |
| आउटपुट गुणवत्ता स्कोर | मॉडल गिरावट पहचान करना (स्वचालित एवल से) |

**अलर्टिंग थ्रेशोल्ड:** GPU उपयोग 40% से नीचे जाए तो स्केल-डाउन ट्रिगर; क्यू गहराई 100 से ऊपर जाए तो स्केल-अप ट्रिगर।

## चरण 8: ऑटो-स्केलिंग

AI वर्कलोड कुंजी मांग बहुत परिवर्तनशील होती है। ऑटो-स्केलिंग को प्रतिक्रियाशीलता और लागत संतुलन करना होता है:

- **हॉरिज़ॉन्टल स्केलिंग** - क्यू गहराई या लेटेंसी थ्रेशोल्ड पार होने पर और GPU इंस्टेंस जोड़ें करें
- **प्रेडिक्टिव स्केलिंग** - ऐतिहासिक ट्रैफ़िक पैटर्न से अपेक्षित पीक से पहले क्षमता pre-provision करें
- **स्केल-टो-ज़ेरो** - कम इस्तेमाल मॉडल के लिए सब इंस्टेंस बंद करें और मांग पर कोल्ड-स्टार्ट करें
- **वॉर्म पूल** - कोल्ड-स्टार्ट लेटेंसी से बचने के लिए कुछ इंस्टेंस मॉडल पहले से लोड रखें

स्केल-टो-ज़ेरो रणनीति उन प्लैटफ़ॉर्म के लिए ख़ास ज़रूरी है जो सैकड़ों मॉडल होस्ट करते हैं - हर मॉडल को हर वक़्त GPU मेमोरी में लोड नहीं रख सकते।
