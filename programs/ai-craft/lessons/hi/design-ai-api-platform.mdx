## इंटरव्यू प्रॉम्प्ट

*"एक AI API प्लेटफ़ॉर्म डिज़ाइन करें, जो REST API के जरिए डेवलपरों को कई मशीन लर्निंग मॉडल सर्व करता हो, वैसा ही जैसे OpenAI या Hugging Face स्केल पर मॉडल सर्व करते हैं।"*

यह प्रश्न इंटरव्यू में लगातार अधिक लोकप्रिय हो रहा है क्योंकि यह **API प्लेटफ़ॉर्म डिज़ाइन** को AI वर्कलोड की खास **GPU इंफ़्रास्ट्रक्चर चुनौतियों** के साथ जोड़ता है।

## चरण 1: आवश्यकताएं इकट्ठी करना

**फ़ंक्शनल आवश्यकताएं:**
- REST API के जरिए कई AI मॉडल (टेक्स्ट जनरेशन, इमेज क्लासिफ़िकेशन, एम्बेडिंग) सर्व करें
- हर API key के लिए उपयोग कोटा के साथ API key प्रमाणीकरण
- हर API कॉल के लिए उपयोग ट्रैकिंग और बिलिंग
- A/B टेस्टिंग के साथ कई मॉडल संस्करणों का समर्थन
- लंबे समय तक चलने वाले जनरेशन कार्यों के लिए स्ट्रीमिंग उत्तर

**नॉन-फ़ंक्शनल आवश्यकताएं:**
- लेटेंसी: एम्बेडिंग मॉडल के लिए p50 500ms से कम, जनरेटिव मॉडल के लिए p50 2s से कम
- थ्रूपुट: सभी मॉडलों में कुल 10,000 अनुरोध प्रति सेकंड
- अवेलेबिलिटी: सुगम गिरावट के साथ 99.9% अपटाइम
- लागत दक्षता: GPU महंगे हैं। उपयोग को अधिकतम करें

<Callout>
AI प्लेटफ़ॉर्म की लेटेंसी बहुत बदलती रहती है। आउटपुट लंबाई के आधार पर टेक्स्ट कम्प्लीशन अनुरोध 200ms या 30 सेकंड ले सकता है। हमेशा चर्चा करें कि आपका डिज़ाइन इस बदलाव को कैसे संभालता है।
</Callout>

## चरण 2: API डिज़ाइन

```
POST /v1/completions
Headers: Authorization: ******
Body: { "model": "gpt-6-astra", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: ******
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - list available models
GET  /v1/usage?start=2024-01-01    - usage and billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

जनरेटिव मॉडल के लिए **Server-Sent Events (SSE)** से स्ट्रीमिंग महत्वपूर्ण है। उपयोगकर्ता पूरे उत्तर का इंतज़ार करने के बजाय टोकन धीरे-धीरे आते हुए देखते हैं।

## चरण 3: API गेटवे और प्रमाणीकरण

API गेटवे प्लेटफ़ॉर्म का मुख्य दरवाज़ा है:

- **प्रमाणीकरण** - key store के विरुद्ध API key जांचें (गति के लिए Redis, स्थायित्व के लिए डेटाबेस)
- **रेट लिमिटिंग** - हर key पर सीमा लागू करें (जैसे free tier के लिए 60 अनुरोध/मिनट)
- **अनुरोध रूटिंग** - अनुरोधों को सही मॉडल-सर्विंग क्लस्टर पर भेजें
- **अनुरोध वैलिडेशन** - पेलोड स्कीमा, मॉडल उपलब्धता और टोकन सीमा जांचें

**रेट लिमिटिंग लागू करना:**
Redis में **sliding window counter** इस्तेमाल करें:
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

हर अनुरोध काउंटर बढ़ाता है। सीमा से ऊपर जाने पर HTTP 429 लौटाएं।

## चरण 4: मॉडल सर्विंग और GPU आवंटन

यहीं AI प्लेटफ़ॉर्म पारंपरिक वेब सेवाओं से मूल रूप से अलग होते हैं। GPU दुर्लभ, महंगे और विशेष ऑर्केस्ट्रेशन मांगते हैं।

**मॉडल सर्विंग परत:**
- मॉडल **Triton Inference Server** या **vLLM** जैसे फ़्रेमवर्क से GPU मेमोरी में लोड किए जाते हैं
- हर मॉडल संस्करण GPU इंस्टेंस के समर्पित पूल पर चलता है
- बड़े भाषा मॉडल (LLM) को कई GPU में **model parallelism** चाहिए हो सकता है

**अनुरोध बैचिंग:**
अलग-अलग इन्फ़रेंस अनुरोध GPU पर अकुशल होते हैं। **Dynamic batching** कई अनुरोधों को समूह में रखता है और साथ प्रोसेस करता है:
- अधिकतम 10ms तक अनुरोध इकट्ठे करें या बैच 32 अनुरोधों तक पहुंचने तक प्रतीक्षा करें
- पूरे बैच को एक GPU forward pass में प्रोसेस करें
- हर कॉलर को उसका अलग उत्तर लौटाएं

यह अलग-अलग अनुरोध प्रोसेस करने की तुलना में थ्रूपुट 5-10 गुना सुधार सकता है।

<FunFact>
एक NVIDIA H100 GPU की कीमत लगभग £25,000 है और यह 700 watts बिजली खाता है। मॉडल सर्विंग के लिए 1,000 GPU का क्लस्टर चलाने पर सिर्फ बिजली और हार्डवेयर में हर महीने £2 मिलियन से अधिक लागत आती है। इसी कारण कुशल बैचिंग और उपयोग अत्यंत महत्वपूर्ण हैं।
</FunFact>

## चरण 5: मॉडल संस्करणों के बीच A/B टेस्टिंग

नया मॉडल संस्करण डिप्लॉय करते समय नियंत्रित रोलआउट चाहिए:

- **ट्रैफ़िक विभाजन** - 5% अनुरोध नए मॉडल पर, 95% मौजूदा मॉडल पर रूट करें
- **Shadow mode** - नए मॉडल को प्रोडक्शन ट्रैफ़िक पर चलाएं लेकिन उसके परिणाम उपयोगकर्ताओं को न लौटाएं
- **मेट्रिक तुलना** - लेटेंसी, आउटपुट गुणवत्ता स्कोर, त्रुटि दर, प्रति अनुरोध लागत
- **क्रमिक रोलआउट** - भरोसा बढ़ने पर नए संस्करण की ट्रैफ़िक हिस्सेदारी बढ़ाएं

रूटिंग लॉजिक API गेटवे में रहता है:
```
model: "gpt-6-astra"  →  95% → gpt-6-astra (current)
                →   5% → claude-opus-5-5 (candidate)
```

<ThinkAboutIt>
नया LLM संस्करण "बेहतर" है या नहीं, यह आंकना आश्चर्यजनक रूप से कठिन है। क्लासिफ़िकेशन मॉडल से अलग, कोई सरल accuracy मेट्रिक नहीं है। जनरेटिव AI मॉडल के लिए आप स्वचालित गुणवत्ता मूल्यांकन सिस्टम कैसे डिज़ाइन करेंगे?
</ThinkAboutIt>

## चरण 6: उपयोग ट्रैकिंग और बिलिंग

AI API आम तौर पर प्रति टोकन बिल करते हैं (LLM के लिए input + output tokens, अन्य मॉडलों के लिए प्रति अनुरोध)।

**इवेंट-ड्रिवन बिलिंग पाइपलाइन:**
1. हर API उत्तर में उपयोग हेडर शामिल होता है: `x-usage-tokens: 847`
2. Kafka में बिलिंग इवेंट प्रकाशित होता है: `{ api_key, model, input_tokens, output_tokens, timestamp }`
3. बिलिंग एग्रीगेशन सेवा इवेंट कंज़्यूम करती है और चलती हुई कुल राशि अपडेट करती है
4. उपयोग डैशबोर्ड time-series डेटाबेस से एग्रीगेटेड डेटा क्वेरी करते हैं

**Kafka क्यों?** बिलिंग विश्वसनीय होनी चाहिए लेकिन उसे synchronous होने की जरूरत नहीं। अगर बिलिंग सेवा अस्थायी रूप से बंद हो, तो इवेंट Kafka में क्यू होते हैं और सेवा वापस आने पर प्रोसेस होते हैं। कोई उपयोग डेटा खोता नहीं है।

## चरण 7: मॉनिटरिंग और ऑब्ज़र्वेबिलिटी

AI प्लेटफ़ॉर्म को सामान्य वेब सेवाओं से आगे की मॉनिटरिंग चाहिए:

| मेट्रिक | क्यों मायने रखता है |
|--------|----------------|
| इन्फ़रेंस लेटेंसी (p50, p95, p99) | उपयोगकर्ता अनुभव और SLA अनुपालन |
| GPU उपयोग | लागत दक्षता। निष्क्रिय GPU पैसा बर्बाद करते हैं |
| प्रति सेकंड टोकन | थ्रूपुट क्षमता और स्केलिंग संकेत |
| मॉडल के अनुसार त्रुटि दर | मॉडल-विशिष्ट विफलताएं पकड़ना |
| क्यू गहराई | स्केलिंग ट्रिगर। गहरी क्यू का मतलब मांग क्षमता से अधिक है |
| आउटपुट गुणवत्ता स्कोर | मॉडल गिरावट पकड़ना (स्वचालित eval से) |

**अलर्ट सीमा:** 40% से कम GPU उपयोग scale-down ट्रिगर करता है। 100 से अधिक क्यू गहराई scale-up ट्रिगर करती है।

## चरण 8: ऑटो-स्केलिंग

AI वर्कलोड की मांग बहुत बदलती रहती है। ऑटो-स्केलिंग को प्रतिक्रिया गति और लागत के बीच संतुलन चाहिए:

- **क्षैतिज स्केलिंग** - क्यू गहराई या लेटेंसी सीमा पार करे तो अधिक GPU इंस्टेंस जोड़ें
- **पूर्वानुमानित स्केलिंग** - अपेक्षित पीक से पहले क्षमता तैयार करने के लिए ऐतिहासिक ट्रैफ़िक पैटर्न इस्तेमाल करें
- **Scale-to-zero** - कम उपयोग वाले मॉडलों के लिए सभी इंस्टेंस बंद करें और मांग पर cold-start करें
- **Warm pools** - cold-start लेटेंसी से बचने के लिए मॉडल पहले से लोड किए हुए कुछ इंस्टेंस रखें

Scale-to-zero रणनीति सैकड़ों मॉडल होस्ट करने वाले प्लेटफ़ॉर्म के लिए खास तौर पर महत्वपूर्ण है। आप हर मॉडल को हर समय GPU मेमोरी में लोड नहीं रख सकते।

<ThinkAboutIt>
OpenAI का प्लेटफ़ॉर्म तेज़ एम्बेडिंग मॉडल से लेकर धीमे reasoning मॉडल तक सर्व करता है। हर मॉडल की लेटेंसी विशेषताएं, GPU जरूरतें और मूल्य अलग हैं। सीमित GPU क्लस्टर को इतने अलग प्रोफ़ाइल वाले मॉडलों में कुशलता से साझा करने के लिए आप रूटिंग परत कैसे डिज़ाइन करेंगे?
</ThinkAboutIt>

<FunFact>
OpenAI कथित रूप से रोज़ 100 मिलियन से अधिक API अनुरोध प्रोसेस करता है। प्रति अनुरोध औसतन 500 टोकन मानें, तो यह रोज़ 50 बिलियन टोकन है, जिसके लिए लगातार चल रहे हजारों GPU चाहिए।

## मुख्य बातें

- AI API प्लेटफ़ॉर्म पारंपरिक API डिज़ाइन को GPU-विशिष्ट इंफ़्रास्ट्रक्चर चुनौतियों से मिलाते हैं
- अनुरोध बैचिंग GPU थ्रूपुट और लागत दक्षता को नाटकीय रूप से सुधारती है
