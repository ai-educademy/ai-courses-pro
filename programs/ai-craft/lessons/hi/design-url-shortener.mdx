## इंटरव्यू का प्रॉम्प्ट

*"बिट.ly जैसी एक URL शोरेटनिङ सर्विस डिज़ाइन करें जो लंबे उरलस लेकर छोटे, उनिक्वे कोदेस बनाती है।"*

यह सिस्टम डिज़ाइन का सबसे आम पहला सवाल है क्योंकि यह देखने में सरल लगता है लेकिन कोरे कोनकेपटस कवर करता है: API डिज़ाइन, एनकोदिङ रणनीतियों, डेटाबेस चोइकेस, कैशिंग, और स्केलिंग। चलिए इसे पाठ 1 के संरचित ढाँचा से हल करते हैं।

## चरण 1: ज़रूरतें इकट्ठा करना (5 मिनट)

**कार्यात्मक ज़रूरतें:**
- एक लंबे URL से एक छोटा उनिक्वे URL जनरेट करें
- शोरट URL से रेदिरेकट करने पर ओरिगिनल लोङ URL मिले
- यूज़र वैकल्पिक कस्टम छोटी कोदेस सेट कर सकें
- लिनकस एक कोनफ़िगुरबले पेरिओद के बाद एक्सपायर हों (डिफ़ॉल्ट: 5 साल)
- बसिक एनालिटिक्स: क्लिक गणना, रेफ़ेररेर, भूगोल

**गैर-कार्यात्मक ज़रूरतें:**
- हर महीने 100 मिलियन उरलस जनरेट (~40 प्रति सेकंड)
- रीड-हेअवय: 100:1 रीड-टो-राइट अनुपात → 4,000 रीडायरेक्ट प्रति सेकंड
- URL रेदिरेकशन लेटेंसी 50ms से कम
- शोरट उरलस जितने छोटे हो सकें उतने छोटे हों
- उच्च अपलब्धता - एक टूटा हुआ लिनक टेररिबले यूज़र अनुभव है

<Callout>
हर सिस्टम डिज़ाइन इंटरव्यू key शुरुआत कलरिफ़यिङ प्रश्न पूछकर करें। एक्सपलिकिट नंबर लिखना (40 राइट/सेक, 4,000 रेविज्ञापन/सेक) दिखाता है कि आप स्केल के बारे में क्वनटिटटिवेलय सोच सकते हैं।
</Callout>

## चरण 2: API डिज़ाइन (5 मिनट)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**HTTP 301 vs 302 क्यों?**
- **301 (पेरमनेनट रीडायरेक्ट)** - ब्राउज़रस इसे कैश करते हैं, जिससे सर्वर पर लोड कम होता है
- **302 (टेमपोररय रीडायरेक्ट)** - ब्राउज़रस हमेशा हमारे सर्वर को हिट करते हैं, जिससे सटीक एनालिटिक्स मिलती है

क्लिक टरकिङ वाली सर्विस के लिए **302 ज़्यादा बेहतर चोइके है** क्योंकि हर रेदिरेकट हमारे सर्वर से होकर गुज़रता है।

## चरण 3: एनकोदिङ सटरेटगय

मुख्य चललेङे: छोटे, उनिक्वे कोदेस कैसे जनरेट करें?

**बसे62 एनकोदिङ** `[a-zA-Z0-9]` अपयोग करती है - 62 चरकटेरस। 7-चरकटेर कोड से हमें 62⁷ = **3.5 टरिललिओन** उनिक्वे संयोजन मिलते हैं, हमारे स्केल के लिए काफ़ी से ज़्यादा।

**ओपशन A - काउंटर-आधारित:**
- ऑटो-बढ़ाएँिङ काउंटर (1, 2, 3, ...) को बसे62 में कोनवेरट करें
- काउंटर 1000 → `g8` | काउंटर 1000000 → `4c92`
- **फ़ायदे:** गारंटीद उनिक्वे, सरल, कोई कोललिसिओनस नहीं
- **नुकसान:** पूर्वानुमेय (यूज़र अगला URL गुएस कर सकते हैं), केंद्रीकृत काउंटर चाहिए

**ओपशन B - हश-आधारित:**
- लोङ URL को MD5/SHA-256 से हैश करें, बसे62 के पहले 7 चरकटेरस लें
- **फ़ायदे:** स्टेटलेस, कोई केंद्रीय समन्वय नहीं चाहिए
- **नुकसान:** कोललिसिओनस पोसिबले - डेटाबेस जाँच करके फिर कोशिश करना होगा

**ओपशन C - परे-गेनेरेटद key (रेकोममेनदेद):**
- एक पृष्ठभूमि सर्विस पहले से मिलियन of उनिक्वे बसे62 कोदेस जनरेट करके key पूल में स्टोर करती है
- नया URL आने पर पूल से अगला अवैलबले कोड ले लें
- **फ़ायदे:** तेज़, कोई कोललिसिओन जोखिम नहीं, पूर्वानुमेय भी नहीं
- **नुकसान:** key जनरेशन सर्विस मनगे करनी होगी

<FunFact>
ओरिगिनल टिन्युरल सर्विस 2002 में लौनच हुई थी और आज भी चल रही है। एक समय पर यह हर दिन 10 लाख से ज़्यादा छोटी उरलस जनरेट कर रही थी। डोमेन टिन्युरल.कोम इतना इकोनिक बन गया कि "टिन्युरल" शब्द URL शोरेटनिङ के लिए गेनेरिक टेरम बन गया।
</FunFact>

## चरण 4: डेटाबेस चोइके और स्कीमा

हर महीने 100 मिलियन नए उरलस और 5 साल रिटेंशन के साथ, हम लगभग **6 बिलियन रेकोरदस** स्टोर करेंगे। यह रीड-हेअवय वोरकलोड है जिसमें सरल केय-वलुए लूकुपस होते हैं।

**डेटाबेस चोइके: दयनमोदब या Cassandra**
- लूकुपस हमेशा छोटी कोड (पार्टिशन key) से होते हैं - जटिल जॉइन नहीं चाहिए
- दोनों बहुत बड़ा रीड थ्रूपुट संभाल करते हैं हॉरिज़ॉन्टल स्केलिंग के साथ
- दोनों पार्टिशन key से सुब10ms लूकुपस देते हैं

**स्कीमा:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

विश्लेषण के लिए, एक अलग टिमे-series टेबल इनदिविदुअल क्लिक इवेंट स्टोर करती है:
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## चरण 5: कैशिंग सटरेटगय

4,000 रीड प्रति सेकंड और हेअवय-टैलेद वितरण (कुछ उरलस को मिलियन of क्लिक मिलते हैं, ज़्यादातर को बहुत कम) के साथ कैशिंग ज़रूरी है।

**Redis कैश** सबसे अक्सर एक्सेस मैपिंगस स्टोर करता है:
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**कैश हिट फ़्लो (तेज़ रास्ता):**
1. रिक्वेस्ट आती है: `GET /aB3kx9`
2. Redis जाँच → कैश हिट → 302 रेदिरेकट लौटाएँ
3. असिंक्रोनस रूप से क्लिक घटना Kafka में लॉग

**कैश मिस फ़्लो:**
1. Redis जाँच → मिस
2. डेटाबेस क्वेरी → फ़ोउनद
3. Redis कैश पॉपुलटे करें
4. 302 रेदिरेकट लौटाएँ

80% कैश हिट दर के साथ, 4,000 में से सिर्फ़ 800 रिक्वेस्ट प्रति सेकंड ही डेटाबेस तक पहुँचती हैं।

## चरण 6: विश्लेषण और क्लिक टरकिङ

क्लिक टरकिङ से रीडायरेक्ट धीमे नहीं होने चाहिए। रीडायरेक्ट प्रतिक्रिया तुरंत लौटाएँ होना चाहिए जबकि एनालिटिक्स असिंक्रोनस रूप से प्रोसेस हों।

**आर्किटेक्चर:**
1. रीडायरेक्ट हैंडलर क्लिक घटना को Kafka में प्रकाशित करता है
2. एक क्लिक-परोकेसिङ सर्विस इवेंट लेते करती है और:
   - URL रिकॉर्ड में `click_count` बढ़ाएँ करती है
   - क्लिकस टेबल में देटैलेद क्लिक डेटा लिखती है
   - स्ट्रीमिंग एग्रीगेशन से रीयल-टाइम डैशबोर्ड अपडेट करती है

यह देकोअपलिङ सुनिश्चित करता है कि धीमे एनालिटिक्स पाइपलाइन कभी रेदिरेकट लेटेंसी को प्रभाव न करे।

<ThinkAboutIt>
URL शॉर्टनर का इस्तेमाल कभी-कभी दुर्भावनापूर्ण लिंक छुपाने के लिए होता है। अगर आप बिट.ly डिज़ाइन कर रहे होते, तो देसटिनशन उरलस को फिशिङ या मलवरे के लिए सकन करने का सुरक्षा जाँच कैसे लागू करते - बिना शोरेटनिङ प्रोसेस में साइनिफ़िकनट लेटेंसी जोड़े?
</ThinkAboutIt>

## चरण 7: सिस्टम को स्केल करना

**हॉरिज़ॉन्टल स्केलिंग तरीका:**
- **API सर्वर** स्टेटलेस हैं - लोड बैलेंसर के पीछे इंस्टेंस जोड़ें करके स्केल करें
- **मुख्य बात जनरेशन सर्विस** अलग मिकरोसेरविके के रूप में चलती है अपने परे-गेनेरेटद कोदेस के डेटाबेस के साथ
- **Redis क्लस्टर** कंसिस्टेंट हैशिंग से नोड में कैश वितरित करता है
- **डेटाबेस शार्डिंग** छोटी कोड के पहले चरकटेर से डेटा एवेनलय वितरित करती है

**पीक कमिज्ञापन संभाल करना:**
- विरल इवेंट में एक URL को प्रति मिनट मिलियन of हिटस मिल सकते हैं
- Redis कैश स्वाभाविक रूप से इसे एब्ज़ॉर्ब करता है - एक कैश एंट्री उनसीमित रीड सर्व करती है
- Kafka क्लिक इवेंट बफ़र करता है, एनालिटिक्स डेटाबेस पर राइट लोड समूथ करता है

<Quiz question="एक URL वायरल हो जाता है और प्रति मिनट 500,000 क्लिक आते हैं। कौन सा कोमपोनेनट सबसे कम अफ़फ़ेकट होगा?" options="Redis कैश (एकल key सारी रिक्वेस्ट सर्व करता है)|Kafka क्लिक-इवेंट कोनसुमेरस|विश्लेषण डेटाबेस राइट रास्ता|API सर्वर CPU" answer="0" explanation="Redis एक कचेद key के लिए मिलियन of रीड प्रति सेकंड आसानी से संभाल करता है। Kafka कोनसुमेरस और एनालिटिक्स डेटाबेस को 500K राइट/मिनट झेलने होंगे, और API सर्वर को 500K रिक्वेस्ट/मिनट - सब पर साइनिफ़िकनट लोड।" />

<ThinkAboutIt>
बिट.ly जैसी कंपनियाँ हर महीने बिलियनस of रीडायरेक्ट संभाल करती हैं। अगर कोई छोटी URL बिललबोअरद या TV ad पर साझा हो, तो ट्रैफ़िक सेकंडों में शून्य से मिलियन तक स्पाइक कर सकता है। कैशिंग के अलावा, इन अचानक, अनिश्चित ट्रैफ़िक बर्स्ट को एब्ज़ॉर्ब करने के लिए आप और कौन सी रणनीतियों इस्तेमाल करेंगे?
</ThinkAboutIt>

<FunFact>
2009 में बिट.ly हर दिन 80 मिलियन से ज़्यादा क्लिक प्रोसेस कर रहा था। जब लिबय - जिसका देश कोड .ly है - ने पोलिटिकल इनसटबिलिटय के कारण .ly दोमैनस टेमपोररिलय बंद किए, तो पूरे इनटेरनेट में पनिक मच गई क्योंकि मिलियन of शोरेटनेद लिंक अचानक काम करना बंद कर दिए।
</FunFact>

## मुख्य बातें

- ढाँचा फ़ॉलो करें: ज़रूरतें → API → एनकोदिङ → डेटा मॉडल → आर्किटेक्चर → गहरी गोताखोरी
- 7 चरकटेरस key बसे62 से 3.5 टरिललिओन उनिक्वे कोदेस मिलते हैं - काफ़ी से ज़्यादा
