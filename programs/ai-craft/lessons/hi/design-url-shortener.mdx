## इंटरव्यू का प्रॉम्प्ट

*"बिट.ly जैसी एक URL शोरटेनिङ सर्विस डिज़ाइन करें जो लंबे उरलस लेकर छोटे, उनिक्वे कोदेस बनाती है।"*

यह सिस्टम डिज़ाइन का सबसे आम पहला सवाल है क्योंकि यह देखने में सरल लगता है लेकिन कोरे कोनकेपटस कवर करता है: API डिज़ाइन, एनकोदिङ रणनीतियाँ, डेटाबेस चोइकेस, कैशिंग, और स्केलिंग। चलिए इसे पाठ 1 के संरचित ढाँचा से हल करते हैं।

## चरण 1: ज़रूरतें इकट्ठा करना (5 मिनट)

**कार्यात्मक ज़रूरतें:**
- एक लंबे URL से एक छोटा उनिक्वे URL जनरेट करें
- शोरट URL से रेदिरेकट करने पर ओरिगिनल लोङ URL मिले
- Users optionally custom short codes set कर सकें
- लिनकस एक कोनफ़िगुरबले पेरिओद के बाद एक्सपिरे हों (डिफ़ॉल्ट: 5 साल)
- Basic analytics: click count, referrer, geography

**गैर-कार्यात्मक ज़रूरतें:**
- हर महीने 100 मिलियन उरलस जनरेट (~40 प्रति सेकंड)
- रेअद-हेअवय: 100:1 रेअद-टो-वरिटे अनुपात → 4,000 रीडायरेक्ट प्रति सेकंड
- URL रेदिरेकशन लेटेंसी 50ms से कम
- शोरट उरलस जितने छोटे हो सकें उतने छोटे हों
- उच्च उपलब्धता - एक टूटा हुआ लिनक टेररिबले यूज़र अनुभव है

<Callout>
हर सिस्टम डिज़ाइन इंटरव्यू की शुरुआत कलरिफ़यिङ प्रश्न पूछकर करें। एक्सपलिकिट नंबर लिखना (40 वरिटेस/सेक, 4,000 रेविज्ञापन/सेक) दिखाता है कि आप स्केल के बारे में क्वनटिटटिवेलय सोच सकते हैं।
</Callout>

## चरण 2: API डिज़ाइन (5 मिनट)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**HTTP 301 vs 302 क्यों?**
- **301 (पेरमनेनट रीडायरेक्ट)** - बरोवसेरस इसे कैश करते हैं, जिससे सर्वर पर लोड कम होता है
- **302 (टेमपोररय रीडायरेक्ट)** - बरोवसेरस हमेशा हमारे सर्वर को हिट करते हैं, जिससे सटीक एनालिटिक्स मिलती है

क्लिक टरकिङ वाली सर्विस के लिए **302 ज़्यादा बेहतर चोइके है** क्योंकि हर रेदिरेकट हमारे सर्वर से होकर गुज़रता है।

## चरण 3: एनकोदिङ सटरटेगय

मुख्य चललेङे: छोटे, उनिक्वे कोदेस कैसे जनरेट करें?

**Base62 encoding** `[a-zA-Z0-9]` use करती है - 62 characters। 7-character code से हमें 62⁷ = **3.5 trillion** unique combinations मिलते हैं, हमारे scale के लिए काफ़ी से ज़्यादा।

**ओपशन A - कोउनटेर-बसेद:**
- औटो-इनकरेमेनटिङ कोउनटेर (1, 2, 3, ...) को बसे62 में कोनवेरट करें
- कोउनटेर 1000 → `g8` | कोउनटेर 1000000 → `4c92`
- **फ़ायदे:** गारंटीद उनिक्वे, सरल, कोई कोललिसिओनस नहीं
- **नुकसान:** पूर्वानुमेय (यूज़र अगला URL गुएस कर सकते हैं), केनटरलिसेद कोउनटेर चाहिए

**ओपशन B - हश-बसेद:**
- लोङ URL को MD5/SHA-256 से हैश करें, बसे62 के पहले 7 चरकटेरस लें
- **फ़ायदे:** stateless, कोई central coordination नहीं चाहिए
- **नुकसान:** कोललिसिओनस पोसिबले - डेटाबेस जाँच करके फिर कोशिश करना होगा

**ओपशन C - परे-गेनेरटेद की (रेकोममेनदेद):**
- एक पृष्ठभूमि सर्विस पहले से मिलियन of उनिक्वे बसे62 कोदेस जनरेट करके की पूल में स्टोर करती है
- नया URL आने पर पूल से अगला अवैलबले कोड ले लें
- **फ़ायदे:** तेज़, कोई कोललिसिओन जोखिम नहीं, पूर्वानुमेय भी नहीं
- **नुकसान:** की जनरेशन सर्विस मनगे करनी होगी

<FunFact>
ओरिगिनल टिन्युरल सर्विस 2002 में लौनच हुई थी और आज भी चल रही है। एक समय पर यह हर दिन 10 लाख से ज़्यादा छोटी उरलस जनरेट कर रही थी। डोमेन टिन्युरल.कोम इतना इकोनिक बन गया कि "टिन्युरल" शब्द URL शोरटेनिङ के लिए गेनेरिक टेरम बन गया।
</FunFact>

## चरण 4: दटबसे चोइके और सचेम

हर महीने 100 मिलियन नए उरलस और 5 साल रिटेंशन के साथ, हम लगभग **6 बिललिओन रेकोरदस** स्टोर करेंगे। यह रेअद-हेअवय वोरकलोअद है जिसमें सरल केय-वलुए लूकुपस होते हैं।

**Database choice: DynamoDB या Cassandra**
- लूकुपस हमेशा छोटी कोड (पार्टिशन की) से होते हैं - जटिल जोइनस नहीं चाहिए
- दोनों बहुत बड़ा रेअद थरोउघपुट संभाल करते हैं होरिज़ोनटल स्केलिंग के साथ
- दोनों पार्टिशन की से सुब10ms लूकुपस देते हैं

**सचेम:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

विश्लेषण के लिए, एक अलग टिमे-सेरिएस टेबल इनदिविदुअल कलिक इवेंट स्टोर करती है:
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## चरण 5: कैशिंग सटरटेगय

4,000 रीड प्रति सेकंड और हेअवय-टैलेद डिस्ट्रिब्यूशन (कुछ उरलस को मिलियन of क्लिक मिलते हैं, ज़्यादातर को बहुत कम) के साथ कैशिंग ज़रूरी है।

**Redis कैश** सबसे अक्सर एक्सेस मपपिङस स्टोर करता है:
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**कैश हिट फ़लोव (तेज़ रास्ता):**
1. रिक्वेस्ट आती है: `GET /aB3kx9`
2. Redis जाँच → कैश हिट → 302 रेदिरेकट लौटाएँ
3. असिंक्रोनस रूप से कलिक घटना Kafka में लॉग

**कैश मिस फ़लोव:**
1. Redis जाँच → मिस
2. दटबसे क्वेरी → फ़ोउनद
3. Redis कैश पॉपुलटे करें
4. 302 रेदिरेकट लौटाएँ

80% कैश हिट दर के साथ, 4,000 में से सिर्फ़ 800 रिक्वेस्ट प्रति सेकंड ही डेटाबेस तक पहुँचती हैं।

## चरण 6: विश्लेषण और क्लिक टरकिङ

Click tracking से redirects धीमे नहीं होने चाहिए। Redirect response तुरंत return होना चाहिए, जबकि analytics asynchronously process हों।

**आर्किटेक्चर:**
1. रीडायरेक्ट हैंडलर क्लिक घटना को Kafka में प्रकाशित करता है
2. एक कलिक-परोकेसिङ सर्विस इवेंट लेते करती है और:
   - URL रिकॉर्ड में `click_count` इनकरेमेनट करती है
   - कलिकस टेबल में देटैलेद कलिक डेटा लिखती है
   - स्ट्रीमिंग अगगरेगशन से रीयल-टाइम डैशबोर्ड अपडेट करती है

यह देकोउपलिङ सुनिश्चित करता है कि धीमे एनालिटिक्स पाइपलाइन कभी रेदिरेकट लेटेंसी को प्रभाव न करे।

<ThinkAboutIt>
URL शॉर्टनर का इस्तेमाल कभी-कभी दुर्भावनापूर्ण लिंक छुपाने के लिए होता है। अगर आप बिट.ly डिज़ाइन कर रहे होते, तो देसटिनशन उरलस को फिशिङ या मलवरे के लिए सकन करने का सुरक्षा जाँच कैसे लागू करते - बिना शोरटेनिङ प्रोसेस में सिगनिफ़िकनट लेटेंसी जोड़े?
</ThinkAboutIt>

## चरण 7: सिस्टम को सकले करना

**होरिज़ोनटल स्केलिंग तरीका:**
- **API servers** stateless हैं - load balancer के पीछे instances जोड़कर scale करें
- **मुख्य बात जनरेशन सर्विस** अलग मिकरोसेरविके के रूप में चलती है अपने परे-गेनेरटेद कोदेस के डेटाबेस के साथ
- **Redis क्लस्टर** कोनसिसटेनट हशिङ से नोड में कैश वितरित करता है
- **दटबसे शार्डिंग** छोटी कोड के पहले चरकटेर से डेटा एवेनलय वितरित करती है

**पीक लोविज्ञापन संभाल करना:**
- विरल इवेंट में एक URL को प्रति मिनुटे मिलियन of हिटस मिल सकते हैं
- Redis cache इसे naturally absorb करता है - एक cache entry unlimited reads serve करती है
- Kafka कलिक इवेंट बुफ़फ़ेर करता है, एनालिटिक्स डेटाबेस पर राइट लोड समूथ करता है

<ThinkAboutIt>
bit.ly जैसी कंपनियाँ हर महीने billions of redirects संभालती हैं। अगर कोई short URL billboard या TV advert पर साझा हो, तो traffic सेकंडों में शून्य से millions तक spike कर सकता है। Caching के अलावा, इन अचानक और unpredictable traffic bursts को absorb करने के लिए आप और कौन सी strategies इस्तेमाल करेंगे?
</ThinkAboutIt>

<FunFact>
2009 में bit.ly हर दिन 80 million से ज़्यादा clicks process कर रहा था। जब Libya - जिसका country code .ly है - ने political instability के कारण .ly domains अस्थायी रूप से बंद किए, तो पूरे internet में panic मच गई क्योंकि millions of shortened links कुछ समय के लिए काम करना बंद कर गए।
</FunFact>

## मुख्य बातें

- ढाँचा फ़ॉलो करें: ज़रूरतें → API → एनकोदिङ → डेटा मॉडल → आर्किटेक्चर → गहरी गोताखोरी
- 7 चरकटेरस की बसे62 से 3.5 टरिललिओन उनिक्वे कोदेस मिलते हैं - काफ़ी से ज़्यादा
- Pre-generated key pools collision issues और central counter bottlenecks से बचाते हैं
- अककुरटे कलिक एनालिटिक्स चाहिए तो 302 रीडायरेक्ट इस्तेमाल करें (301 नहीं)
- Redis कैशिंग रेअद-हेअवय वोरकलोविज्ञापन के लिए डेटाबेस लोड काफ़ी कम करती है
- Kafka से async processing करके analytics को redirect path से decouple करें
