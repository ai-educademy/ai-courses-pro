## इंटरव्यू का प्रॉम्प्ट

*"बिट.ly जैसी एक URL शॉर्टनिंग सर्विस डिज़ाइन करें जो लंबे URLs लेकर छोटे, उनिक्वे कोड बनाती है।"*

यह सिस्टम डिज़ाइन का सबसे आम पहला सवाल है क्योंकि यह देखने में सरल लगता है लेकिन मुख्य अवधारणाएँ कवर करता है: API डिज़ाइन, एन्कोडिंग रणनीतियों, डेटाबेस विकल्पस, कैशिंग, और स्केलिंग। चलिए इसे पाठ 1 के संरचित ढाँचा से हल करते हैं।

## चरण 1: ज़रूरतें इकट्ठा करना (5 मिनट)

**कार्यात्मक ज़रूरतें:**
- एक लंबे URL से एक छोटा उनिक्वे URL जनरेट करें
- शोरट URL से रीडायरेक्ट करने पर ओरिगिनल लंबे URL मिले
- यूज़र वैकल्पिक कस्टम छोटी कोड सेट कर सकें
- लिंक एक कॉन्फ़िगर करने योग्य पेरिओद के बाद एक्सपायर हों (डिफ़ॉल्ट: 5 साल)
- बसिक एनालिटिक्स: क्लिक गणना, रेफ़ेदुर्लभर, भूगोल

**गैर-कार्यात्मक ज़रूरतें:**
- हर महीने 100 मिलियन URLs जनरेट (~40 प्रति सेकंड)
- रीड-हेवी: 100:1 रीड-टो-राइट अनुपात → 4,000 रीडायरेक्ट प्रति सेकंड
- URL रीडायरेक्शन लेटेंसी 50ms से कम
- शोरट URLs जितने छोटे हो सकें उतने छोटे हों
- उच्च उपलब्धता - एक टूटा हुआ लिनक टेररिबले यूज़र अनुभव है

<Callout>
हर सिस्टम डिज़ाइन इंटरव्यू की शुरुआत स्पष्ट करने वाले प्रश्न पूछकर करें। स्पष्ट नंबर लिखना (40 राइट/सेक, 4,000 रीड/सेक) दिखाता है कि आप स्केल के बारे में परिमाणात्मक रूप से सोच सकते हैं।
</Callout>

## चरण 2: API डिज़ाइन (5 मिनट)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**HTTP 301 vs 302 क्यों?**
- **301 (पेरमनेनट रीडायरेक्ट)** - ब्राउज़रस इसे कैश करते हैं, जिससे सर्वर पर लोड कम होता है
- **302 (अस्थायी रीडायरेक्ट)** - ब्राउज़रस हमेशा हमारे सर्वर को हिट करते हैं, जिससे सटीक एनालिटिक्स मिलती है

क्लिक ट्रैकिंग वाली सर्विस के लिए **302 ज़्यादा बेहतर विकल्प है** क्योंकि हर रीडायरेक्ट हमारे सर्वर से होकर गुज़रता है।

<Quiz question="आपके URL शॉर्टनर को सटीक क्लिक एनालिटिक्स चाहिए। कौन सा HTTP रीडायरेक्ट स्टेटस कोड इस्तेमाल करेंगे और क्यों?" options="200 OK - पेज कंटेंट सीधे लौटाएँ|301 पेरमनेनट रीडायरेक्ट - ब्राउज़रस स्पीड के लिए कैश करते हैं|302 अस्थायी रीडायरेक्ट - हर क्लिक हमारे सर्वर पर आती है गिनती के लिए|404 नोट मिला - फिर JavaScript से क्लाइंट-साइड रीडायरेक्ट करें" answer="2" explanation="302 अस्थायी रीडायरेक्ट यह सुनिश्चित करता है कि ब्राउज़र हर क्लिक पर हमारे सर्वर से संपर्क करे, जिससे हम एनालिटिक्स के लिए विसिट रिकॉर्ड कर सकें। 301 ब्राउज़र कैश हो जाता, यानी दोहराई गई विज़िट गणना नहीं होतीं।" />

## चरण 3: एन्कोडिंग रणनीति

मुख्य चललेङे: छोटे, उनिक्वे कोड कैसे जनरेट करें?

**बसे62 एन्कोडिंग** `[a-zA-Z0-9]` उपयोग करती है - 62 अक्षरस। 7-अक्षर कोड से हमें 62⁷ = **3.5 ट्रिलियन** उनिक्वे संयोजन मिलते हैं, हमारे स्केल के लिए काफ़ी से ज़्यादा।

**विकल्प A - काउंटर-आधारित:**
- ऑटो-इन्क्रीमेंटिंग काउंटर (1, 2, 3, ...) को बसे62 में बदलें करें
- काउंटर 1000 → `g8` | काउंटर 1000000 → `4c92`
- **फ़ायदे:** गारंटीद उनिक्वे, सरल, कोई टकराव नहीं
- **नुकसान:** पूर्वानुमेय (यूज़र अगला URL गुएस कर सकते हैं), केंद्रीकृत काउंटर चाहिए

**विकल्प B - हश-आधारित:**
- लंबे URL को MD5/SHA-256 से हैश करें, बसे62 के पहले 7 अक्षरस लें
- **फ़ायदे:** स्टेटलेस, कोई केंद्रीय समन्वय नहीं चाहिए
- **नुकसान:** टकराव पोसिबले - डेटाबेस जाँच करके फिर कोशिश करना होगा

**विकल्प C - पहले से जनरेट किए कुंजी (अनुशंसित):**
- एक पृष्ठभूमि सर्विस पहले से मिलियन of उनिक्वे बसे62 कोड जनरेट करके कुंजी पूल में स्टोर करती है
- नया URL आने पर पूल से अगला उपलब्ध कोड ले लें
- **फ़ायदे:** तेज़, कोई टकराव जोखिम नहीं, पूर्वानुमेय भी नहीं
- **नुकसान:** कुंजी जनरेशन सर्विस मनगे करनी होगी

<FunFact>
ओरिगिनल टिन्युरल सर्विस 2002 में लौनच हुई थी और आज भी चल रही है। एक समय पर यह हर दिन 10 लाख से ज़्यादा छोटी URLs जनरेट कर रही थी। डोमेन टिन्युरल.कोम इतना प्रसिद्ध बन गया कि "टिन्युरल" शब्द URL शॉर्टनिंग के लिए गेनेरिक टेरम बन गया।
</FunFact>

## चरण 4: डेटाबेस विकल्प और स्कीमा

हर महीने 100 मिलियन नए URLs और 5 साल रिटेंशन के साथ, हम लगभग **6 बिलियन रिकॉर्ड** स्टोर करेंगे। यह रीड-हेवी वोरकलोड है जिसमें सरल केय-वलुए खोज होते हैं।

**डेटाबेस विकल्प: DynamoDB या Cassandra**
- खोज हमेशा छोटी कोड (पार्टिशन कुंजी) से होते हैं - जटिल जॉइन नहीं चाहिए
- दोनों बहुत बड़ा रीड थ्रूपुट संभाल करते हैं हॉरिज़ॉन्टल स्केलिंग के साथ
- दोनों पार्टिशन कुंजी से सुब10ms खोज देते हैं

**स्कीमा:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

विश्लेषण के लिए, एक अलग टाइम-सीरीज़ टेबल व्यक्तिगत क्लिक इवेंट स्टोर करती है:
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## चरण 5: कैशिंग रणनीति

4,000 रीड प्रति सेकंड और हेवी-टेल्ड वितरण (कुछ URLs को मिलियन of क्लिक मिलते हैं, ज़्यादातर को बहुत कम) के साथ कैशिंग ज़रूरी है।

**Redis कैश** सबसे अक्सर एक्सेस मैपिंगस स्टोर करता है:
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**कैश हिट फ़्लो (तेज़ रास्ता):**
1. रिक्वेस्ट आती है: `GET /aB3kx9`
2. Redis जाँच → कैश हिट → 302 रीडायरेक्ट लौटाएँ
3. असिंक्रोनस रूप से क्लिक घटना Kafka में लॉग

**कैश मिस फ़्लो:**
1. Redis जाँच → मिस
2. डेटाबेस क्वेरी → मिला
3. Redis कैश पॉपुलटे करें
4. 302 रीडायरेक्ट लौटाएँ

80% कैश हिट दर के साथ, 4,000 में से सिर्फ़ 800 रिक्वेस्ट प्रति सेकंड ही डेटाबेस तक पहुँचती हैं।

## चरण 6: विश्लेषण और क्लिक ट्रैकिंग

क्लिक ट्रैकिंग से रीडायरेक्ट धीमे नहीं होने चाहिए। रीडायरेक्ट प्रतिक्रिया तुरंत लौटाएँ होना चाहिए जबकि एनालिटिक्स असिंक्रोनस रूप से प्रोसेस हों।

**आर्किटेक्चर:**
1. रीडायरेक्ट हैंडलर क्लिक घटना को Kafka में प्रकाशित करता है
2. एक क्लिक-प्रोसेसिंग सर्विस इवेंट लेते करती है और:
   - URL रिकॉर्ड में `click_count` बढ़ाती है
   - क्लिकस टेबल में विस्तृत क्लिक डेटा लिखती है
   - स्ट्रीमिंग एग्रीगेशन से रीयल-टाइम डैशबोर्ड अपडेट करती है

यह अलगाव सुनिश्चित करता है कि धीमे एनालिटिक्स पाइपलाइन कभी रीडायरेक्ट लेटेंसी को प्रभाव न करे।

<ThinkAboutIt>
URL शॉर्टनर का इस्तेमाल कभी-कभी दुर्भावनापूर्ण लिंक छुपाने के लिए होता है। अगर आप बिट.ly डिज़ाइन कर रहे होते, तो गंतव्य URLs को फिशिङ या मैलवेयर के लिए सकन करने का सुरक्षा जाँच कैसे लागू करते - बिना शॉर्टनिंग प्रोसेस में महत्वपूर्ण लेटेंसी जोड़े?
</ThinkAboutIt>

## चरण 7: सिस्टम को स्केल करना

**हॉरिज़ॉन्टल स्केलिंग तरीका:**
- **API सर्वर** स्टेटलेस हैं - लोड बैलेंसर के पीछे इंस्टेंस जोड़ें करके स्केल करें
- **कुंजी जनरेशन सर्विस** अलग माइक्रोसर्विस के रूप में चलती है अपने पहले से जनरेट किए कोड के डेटाबेस के साथ
- **Redis क्लस्टर** कंसिस्टेंट हैशिंग से नोड में कैश वितरित करता है
- **डेटाबेस शार्डिंग** छोटी कोड के पहले अक्षर से डेटा समान रूप से वितरित करती है

**पीक कमिज्ञापन संभाल करना:**
- विरल इवेंट में एक URL को प्रति मिनट मिलियन of हिट मिल सकते हैं
- Redis कैश स्वाभाविक रूप से इसे एब्ज़ॉर्ब करता है - एक कैश एंट्री उनसीमित रीड सर्व करती है
- Kafka क्लिक इवेंट बफ़र करता है, एनालिटिक्स डेटाबेस पर राइट लोड समूथ करता है

<Quiz question="एक URL वायरल हो जाता है और प्रति मिनट 500,000 क्लिक आते हैं। कौन सा घटक सबसे कम प्रभावित होगा?" options="Redis कैश (एकल कुंजी सारी रिक्वेस्ट सर्व करता है)|Kafka क्लिक-इवेंट कंज़्यूमर|विश्लेषण डेटाबेस राइट रास्ता|API सर्वर CPU" answer="0" explanation="Redis एक कचेद कुंजी के लिए मिलियन of रीड प्रति सेकंड आसानी से संभाल करता है। Kafka कंज़्यूमर और एनालिटिक्स डेटाबेस को 500K राइट/मिनट झेलने होंगे, और API सर्वर को 500K रिक्वेस्ट/मिनट - सब पर महत्वपूर्ण लोड।" />

<ThinkAboutIt>
बिट.ly जैसी कंपनियाँ हर महीने अरबों of रीडायरेक्ट संभाल करती हैं। अगर कोई छोटी URL बिलबोअरद या TV ad पर साझा हो, तो ट्रैफ़िक सेकंडों में शून्य से मिलियन तक स्पाइक कर सकता है। कैशिंग के अलावा, इन अचानक, अनिश्चित ट्रैफ़िक बर्स्ट को एब्ज़ॉर्ब करने के लिए आप और कौन सी रणनीतियों इस्तेमाल करेंगे?
</ThinkAboutIt>

<FunFact>
2009 में बिट.ly हर दिन 80 मिलियन से ज़्यादा क्लिक प्रोसेस कर रहा था। जब लिबय - जिसका देश कोड .ly है - ने पोलिटिकल अस्थिरता के कारण .ly डोमेन अस्थायी रूप से बंद किए, तो पूरे इनटेरनेट में पनिक मच गई क्योंकि मिलियन of शोरेटनेद लिंक अचानक काम करना बंद कर दिए।
</FunFact>

## मुख्य बातें

- ढाँचा फ़ॉलो करें: ज़रूरतें → API → एन्कोडिंग → डेटा मॉडल → आर्किटेक्चर → गहरी गोताखोरी
- 7 अक्षरस कुंजी बसे62 से 3.5 ट्रिलियन उनिक्वे कोड मिलते हैं - काफ़ी से ज़्यादा
