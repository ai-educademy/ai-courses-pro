## इंटरव्यू प्रॉम्प्ट

*"bit.ly जैसी URL शॉर्टनिंग सेवा डिज़ाइन करें, जो लंबे URL लेकर छोटे, अद्वितीय कोड बनाती है।"*

यह सबसे आम पहला सिस्टम डिज़ाइन प्रश्न है क्योंकि यह दिखने में सरल है, लेकिन मुख्य अवधारणाओं को कवर करता है: API डिज़ाइन, एनकोडिंग रणनीतियां, डेटाबेस चुनाव, कैशिंग और स्केलिंग। आइए इसे पाठ 1 के संरचित फ़्रेमवर्क से हल करें।

## चरण 1: आवश्यकताएं इकट्ठी करना (5 मिनट)

**फ़ंक्शनल आवश्यकताएं:**
- लंबे URL से छोटा अद्वितीय URL बनाएं
- छोटे URL के जरिए रीडायरेक्ट करने पर मूल लंबा URL लौटे
- उपयोगकर्ता वैकल्पिक रूप से कस्टम शॉर्ट कोड सेट कर सकते हैं
- लिंक कॉन्फ़िगर की जा सकने वाली अवधि के बाद समाप्त हों (डिफ़ॉल्ट: 5 वर्ष)
- मूल एनालिटिक्स: क्लिक संख्या, रेफ़रर, भूगोल

**नॉन-फ़ंक्शनल आवश्यकताएं:**
- हर महीने 100 मिलियन URL बनाए जाते हैं (~40 प्रति सेकंड)
- पढ़ाई-प्रधान: पढ़ने और लिखने का अनुपात 100:1 → 4,000 रीडायरेक्ट प्रति सेकंड
- URL रीडायरेक्शन लेटेंसी 50ms से कम
- छोटे URL जितने हो सकें उतने छोटे हों
- उच्च अवेलेबिलिटी। टूटा हुआ लिंक बहुत खराब उपयोगकर्ता अनुभव है

<Callout>
हर सिस्टम डिज़ाइन इंटरव्यू स्पष्ट करने वाले प्रश्नों से शुरू करें। स्पष्ट संख्याएं लिखना (40 लिखाई/सेकंड, 4,000 पढ़ाई/सेकंड) दिखाता है कि आप स्केल के बारे में मात्रात्मक रूप से सोच सकते हैं।
</Callout>

## चरण 2: API डिज़ाइन (5 मिनट)

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**HTTP 301 बनाम 302 क्यों?**
- **301 (Permanent Redirect)** - ब्राउज़र इसे कैश करते हैं, जिससे हमारे सर्वरों पर लोड घटता है
- **302 (Temporary Redirect)** - ब्राउज़र हमेशा हमारे सर्वरों तक आते हैं, जिससे सटीक एनालिटिक्स संभव होती है

क्लिक ट्रैक करने वाली सेवा के लिए **302 आम तौर पर बेहतर चुनाव है** क्योंकि हर रीडायरेक्ट हमारे सर्वरों से होकर गुजरता है।

## चरण 3: एनकोडिंग रणनीति

मुख्य चुनौती: हम छोटे, अद्वितीय कोड कैसे बनाएं?

**Base62 एनकोडिंग** `[a-zA-Z0-9]` का इस्तेमाल करती है। इसमें 62 वर्ण हैं। 7-वर्ण का कोड हमें 62⁷ = **3.5 ट्रिलियन** अद्वितीय संयोजन देता है, जो हमारे स्केल के लिए पर्याप्त से अधिक है।

**विकल्प A - काउंटर-आधारित:**
- ऑटो-इंक्रीमेंटिंग काउंटर (1, 2, 3, ...) इस्तेमाल करें और उसे base62 में बदलें
- काउंटर 1000 → `g8` | काउंटर 1000000 → `4c92`
- **लाभ:** अद्वितीयता की गारंटी, सरल, कोई कोलिज़न नहीं
- **हानि:** अनुमान लगाया जा सकता है (उपयोगकर्ता अगला URL अंदाज़ा लगा सकते हैं), केंद्रीकृत काउंटर चाहिए

**विकल्प B - हैश-आधारित:**
- लंबे URL को MD5/SHA-256 से हैश करें, base62 के पहले 7 वर्ण लें
- **लाभ:** स्टेटलेस, केंद्रीय समन्वय की जरूरत नहीं
- **हानि:** कोलिज़न संभव हैं। डेटाबेस जांचना और फिर कोशिश करनी होगी

**विकल्प C - पहले से बने की (अनुशंसित):**
- एक बैकग्राउंड सेवा लाखों अद्वितीय base62 कोड पहले से बनाती है और उन्हें की पूल में स्टोर करती है
- नया URL आने पर पूल से अगला उपलब्ध कोड लें
- **लाभ:** तेज़, कोलिज़न जोखिम नहीं, अनुमान लगाना मुश्किल
- **हानि:** की जनरेशन सेवा को मैनेज करना पड़ता है

<FunFact>
मूल TinyURL सेवा 2002 में शुरू हुई थी और आज भी चल रही है। एक समय पर यह हर दिन 1 मिलियन से अधिक छोटे URL बना रही थी। डोमेन TinyURL.com इतना प्रसिद्ध हो गया कि "TinyURL" URL शॉर्टनिंग के लिए सामान्य शब्द की तरह इस्तेमाल होने लगा।
</FunFact>

## चरण 4: डेटाबेस चुनाव और स्कीमा

हर महीने 100 मिलियन नए URL और 5-वर्ष रिटेंशन के साथ, हम लगभग **6 बिलियन रिकॉर्ड** स्टोर करेंगे। यह सरल कुंजी-मान खोज वाला पढ़ाई-प्रधान वर्कलोड है।

**डेटाबेस चुनाव: DynamoDB या Cassandra**
- खोज हमेशा शॉर्ट कोड (पार्टिशन कुंजी) से होती है। जटिल जॉइन नहीं चाहिए
- दोनों क्षैतिज स्केलिंग के साथ विशाल पढ़ाई थ्रूपुट संभालते हैं
- दोनों पार्टिशन कुंजी से sub-10ms खोज देते हैं

**स्कीमा:**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

एनालिटिक्स के लिए, अलग टाइम-सीरीज़ तालिका व्यक्तिगत क्लिक इवेंट स्टोर करती है:
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## चरण 5: कैशिंग रणनीति

4,000 पढ़ाई प्रति सेकंड और भारी-टेल वितरण (कुछ URL को लाखों क्लिक मिलते हैं, अधिकांश को बहुत कम) पर कैशिंग जरूरी है।

**Redis कैश** सबसे अधिक उपयोग किए जाने वाले मैपिंग स्टोर करता है:
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**कैश हिट प्रवाह (तेज़ पथ):**
1. अनुरोध आता है: `GET /aB3kx9`
2. Redis जांचें → कैश हिट → 302 रीडायरेक्ट लौटाएं
3. क्लिक इवेंट को असिंक्रोनस रूप से Kafka में लॉग करें

**कैश मिस प्रवाह:**
1. Redis जांचें → मिस
2. डेटाबेस क्वेरी करें → मिला
3. Redis कैश भरें
4. 302 रीडायरेक्ट लौटाएं

80% कैश हिट दर के साथ, 4,000 अनुरोध प्रति सेकंड में से केवल 800 ही वास्तव में डेटाबेस तक पहुंचते हैं।

## चरण 6: एनालिटिक्स और क्लिक ट्रैकिंग

क्लिक ट्रैकिंग को रीडायरेक्ट धीमा नहीं करना चाहिए। रीडायरेक्ट उत्तर तुरंत लौटना चाहिए, जबकि एनालिटिक्स असिंक्रोनस रूप से प्रोसेस हों।

**आर्किटेक्चर:**
1. रीडायरेक्ट हैंडलर **Kafka** में क्लिक इवेंट प्रकाशित करता है
2. क्लिक-प्रोसेसिंग सेवा इवेंट कंज़्यूम करती है और:
   - URL रिकॉर्ड में `click_count` बढ़ाती है
   - क्लिक तालिका में विस्तृत क्लिक डेटा लिखती है
   - स्ट्रीमिंग एग्रीगेशन के जरिए रीयल-टाइम डैशबोर्ड अपडेट करती है

यह डिकपलिंग सुनिश्चित करती है कि धीमी एनालिटिक्स पाइपलाइन कभी रीडायरेक्ट लेटेंसी को प्रभावित न करे।

<ThinkAboutIt>
URL शॉर्टनर कभी-कभी दुर्भावनापूर्ण लिंक छिपाने के लिए इस्तेमाल होते हैं। अगर आप bit.ly डिज़ाइन कर रहे होते, तो शॉर्टनिंग प्रक्रिया में बड़ी लेटेंसी जोड़े बिना फ़िशिंग या मैलवेयर के लिए गंतव्य URL स्कैन करने वाला सुरक्षा चेक कैसे लागू करते?
</ThinkAboutIt>

## चरण 7: सिस्टम को स्केल करना

**क्षैतिज स्केलिंग तरीका:**
- **API सर्वर** स्टेटलेस हैं। लोड बैलेंसर के पीछे इंस्टेंस जोड़कर स्केल करें
- **की जनरेशन सेवा** अपने पहले से बने कोड वाले डेटाबेस के साथ अलग माइक्रोसर्विस के रूप में चलती है
- **Redis क्लस्टर** कंसिस्टेंट हैशिंग से नोड्स में कैश वितरण संभालता है
- **डेटाबेस शार्डिंग** शॉर्ट कोड के पहले वर्ण से डेटा समान रूप से बांटती है

**पीक लोड संभालना:**
- वायरल इवेंट के दौरान एक URL को हर मिनट लाखों हिट मिल सकते हैं
- Redis कैश इसे स्वाभाविक रूप से सोख लेता है। एक कैश एंट्री असीमित पढ़ाई दे सकती है
- Kafka क्लिक इवेंट को बफ़र करता है, जिससे एनालिटिक्स डेटाबेस पर लिखाई लोड समतल होता है

<ThinkAboutIt>
bit.ly जैसी कंपनियां हर महीने अरबों रीडायरेक्ट संभालती हैं। अगर कोई छोटा URL बिलबोर्ड या TV विज्ञापन पर साझा हो, तो ट्रैफ़िक शून्य से सेकंडों में लाखों तक जा सकता है। कैशिंग के अलावा, ऐसे अचानक और अनिश्चित ट्रैफ़िक बर्स्ट सोखने के लिए आप कौन सी रणनीतियां इस्तेमाल करेंगे?
</ThinkAboutIt>

<FunFact>
2009 में bit.ly हर दिन 80 मिलियन से अधिक क्लिक प्रोसेस कर रहा था। जब Libya, जिसका देश कोड .ly है, ने राजनीतिक अस्थिरता के कारण .ly डोमेन कुछ समय के लिए बंद कर दिए, तो इंटरनेट पर घबराहट फैल गई क्योंकि लाखों छोटे लिंक अस्थायी रूप से काम करना बंद कर गए।
</FunFact>

## मुख्य बातें

- फ़्रेमवर्क का पालन करें: आवश्यकताएं → API → एनकोडिंग → डेटा मॉडल → आर्किटेक्चर → डीप डाइव
- 7 वर्णों वाला Base62 3.5 ट्रिलियन अद्वितीय कोड देता है। यह पर्याप्त से अधिक है
- पहले से बने की पूल कोलिज़न समस्याओं और केंद्रीय काउंटर बाधाओं से बचाते हैं
