## इंटरव्यू प्रॉम्प्ट

*"WhatsApp या Slack जैसी चैट ऐप्लिकेशन डिज़ाइन करें जो एक-से-एक संदेश, समूह चैटस, और ऑनलाइन अपस्थिति संकेतक सपोर्ट करे।"*

यह सिस्टम डिज़ाइन इंटरव्यू में एक पसंदीदा सवाल है क्योंकि यह एक ही समस्या में रीयल-टाइम संचार, कनेक्शन प्रबंधन, स्टोरेज at स्केल, और वितरित सिस्टम ट्रेड-offs - सब कुछ टेस्ट करता है।

## चरण 1: ज़रूरतें समझना

**कार्यात्मक ज़रूरतें:**
- एक-से-एक संदेश के साथ डिलीवरी और रीड रसीदें
- समूह चैट (500 मेमबेरस तक)
- ऑनलाइन/ऑफ़लाइन अपस्थिति संकेतक
- संदेश इतिहास और सर्च
- ऑफ़लाइन यूज़र के लिए पुश नोटिफ़िकेशन

**गैर-कार्यात्मक ज़रूरतें:**
- कम लेटेंसी: संदेश 200ms के अंदर देलिवेर हों
- उच्च अपलब्धता: 99.99% अपटिमे
- एक बातचीत के अंदर संदेश क्रम गारंटीद
- 50 मिलियन समवर्ती कनेक्शन सपोर्ट करे

<Callout>
गैर-कार्यात्मक ज़रूरतें को हमेशा विशिष्ट नंबर से क्वनटिफ़य करें। "तेज़ डिलीवरी" वगुए है - "सुब200ms डिलीवरी" दिखाता है कि आपको डोमेन key समझ है।
</Callout>

## चरण 2: API डिज़ाइन

रेसट-ओनलय सिस्टम के विपरीत, चैट को **द्विदिश संचार** चाहिए। हमें दो प्रोटोकॉल key ज़रूरत है:

**REST API** (नोन-रेअल-टिमे ऑपरेशन के लिए):
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket** (रीयल-टाइम मैसेजिंग के लिए):
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## चरण 3: WebSocket कनेक्शन मनगेमेनट

हर कनेक्टेड यूज़र एक पेरसिसटेनट WebSocket कनेक्शन बनाए करता है। 50 मिलियन समवर्ती यूज़र पर यह एक बड़ी इंजीनियरिंग चललेङे है।

**कनेक्शन सर्वर** (जिन्हें गेटवे सर्वर भी कहते हैं) WebSocket कनेक्शन बनाए करते हैं। हर सर्वर लगभग 50,000-100,000 समवर्ती कनेक्शन संभाल कर सकता है, यानी हमें 500-1,000 कनेक्शन सर्वर चाहिए।

एक **कनेक्शन रजिस्ट्री** (Redis क्लस्टर) हर यूज़र को उनके कनेक्शन सर्वर से मैप करती है:
```
user_123 → ws-server-042
user_456 → ws-server-187
```

जब यूज़र A, यूज़र B को संदेश भेजता है, फ़्लो यह होता है:
1. संदेश, A के कनेक्शन सर्वर पर WebSocket से आता है
2. सर्वर, Redis में B का कनेक्शन सर्वर ढूँढता है
3. संदेश इनटेरनल मैसेजिंग से B के कनेक्शन सर्वर को रूट होता है
4. B का सर्वर, B के WebSocket पर संदेश पुश करता है

## चरण 4: संदेश सटोरगे

चैट ऐप्लिकेशन बहुत बड़ी वॉल्यूम में डेटा जनरेट करती हैं। WhatsApp रोज़ 100 बिलियन से ज़्यादा संदेश प्रोसेस करता है।

**सटोरगे रणनीति:**
- **रेकेनट संदेश** - तेज़ डेटास्टोर (Cassandra या HBase) में, बातचीत ID से पार्टिशन किए हुए
- **संदेश इंडेक्स** - Elasticसर्च से सर्च सक्षम करता है
- **मेदिअ फ़ाइलस** - ऑब्जेक्ट स्टोरेज (S3) में CDN डिलीवरी के साथ

**स्कीमा डिज़ाइन (Cassandra):**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

यह डिज़ाइन सुनिश्चित करती है कि एक बातचीत के सारे संदेश समान पार्टिशन पर को-लॉकटेद हों, जिससे "पुराने संदेश लोड करो" क्वेरी बहुत कुशल हो जाती हैं - बस एक पार्टिशन में सेक्वेनटिअल रीड।

## चरण 5: अपस्थिति सिस्टम

कौन ऑनलाइन है दिखाना सरल लगता है लेकिन स्केल पर हैरान करने वाला पेचीदा है। आप अपनी संपर्क लिस्ट के हर यूज़र के लिए हर कुछ सेकंड में डेटाबेस पोल नहीं कर सकते।

**हेअरटबेअट तरीका:**
1. कनेक्टेड क्लाइंट हर 30 सेकंड में WebSocket से हेअरटबेअट भेजते हैं
2. सर्वर एक Redis key अपडेट करता है जिसमें 60 सेकंड का TTL होता है: `presence:user_123 → online (TTL 60s)`
3. अगर हेअरटबेअट नहीं आता, key एक्सपायर हो जाती है और यूज़र ऑफ़लाइन दिखता है

**स्टेटस अपडेट के लिए fan-out:**
जब कोई यूज़र ऑनलाइन आता है, उसका स्टेटस सभी ऑनलाइन कॉन्टैक्ट को पुश होना चाहिए। 500 कॉन्टैक्ट वाले यूज़र के लिए, यह जाँच करना पड़ता है कि कौन-से कॉन्टैक्ट ऑनलाइन हैं और सिर्फ उन्हें अपस्थिति अपडेट भेजने हैं - **लेज़ी fan-out** ऑफ़लाइन यूज़र को ब्रॉडकास्ट करने से बचाता है।

<FunFact>
WhatsApp के "लास्ट सीन" फ़ीचर ने दुनिया भर में अनपेक्षित सामाजिक तनाव पैदा किया। कुछ देशों में रिश्ते विवाद बढ़ गए क्योंकि साथी एक-दूसरे के सटीक लास्ट-सक्रिय टाइमस्टैम्प देख सकते थे। WhatsApp ने आखिरकार यह जानकारी छुपाने के लिए गोपनीयता नियंत्रण जोड़ें किए।
</FunFact>

## चरण 6: पुश नोटिफ़िकेशन

जब यूज़र ऑफ़लाइन हो (कोई सक्रिय WebSocket नहीं), तो संदेश पुश नोटिफ़िकेशन से पहुँचने चाहिए।

संदेश फ़्लो बदल जाता है:
1. कनेक्शन रजिस्ट्री दिखाती है कि यूज़र B ऑफ़लाइन है
2. संदेश डेटाबेस में "उनदेलिवेरेद" स्टेटस के साथ स्टोर होता है
3. नोटिफ़िकेशन सर्विस अपनस (iOS) या FCM (अनदरोइद) से पुश भेजती है
4. जब यूज़र B रेकोननेकट करता है, उनदेलिवेरेद संदेश फ़ेटच करके WebSocket से भेजे जाते हैं
5. रेकेइपट कोनफ़िरम करने के लिए डिलीवरी रसीदें भेजी जाती हैं

<ThinkAboutIt>
500 मेमबेरस वाले समूह चैटस में fan-out चललेङे होती है। अगर एक संदेश ऐसे समूह में भेजा जाए जहाँ 400 मेमबेरस ऑफ़लाइन हैं, तो 400 पुश नोटिफ़िकेशन भेजनी पड़ेंगी। पीक घंटे में नोटिफ़िकेशन सेवाएँ को ओवरवेल्म होने से बचाने के लिए आप इन्हें कैसे बैच और रेट-लिमिट करेंगे?
</ThinkAboutIt>

## चरण 7: E2E एन्क्रिप्शन बसिकस

इंटरव्यू चर्चाओं में E2E एन्क्रिप्शन का ज़िक्र सुरक्षा अवरेनेस दिखाता है:

- हर यूज़र अपने डिवाइस पर **पुबलिक/परिवटे key पैर** जनरेट करता है
- संदेशस रेकिपिएनट key पुबलिक key से एन्क्रिप्ट होते हैं सेनदेर का डिवाइस छोड़ने से पहले
- सर्वर को सिर्फ किफेरेटक्सट दिखता है - वह संदेश कंटेंट नहीं पढ़ सकता
- समूह चैटस एक **शरेद समूह key** अपयोग करते हैं जो मेमबेरस जुड़ें या लेअवे करने पर रोटटे होती है

इसका मतलब सर्वर के संदेश स्टोरेज में सिर्फ एन्क्रिप्टेड बलोबस होते हैं, जो डेटा अनुपालन के नज़रिये से वास्तव में सरल है।

## चरण 8: मिललिओनस तक स्केल करना

**मुख्य बात स्केलिंग रणनीतियों:**
- **कनेक्शन सर्वर** क्षैतिज रूप से स्केल होते हैं - यूज़र बढ़ने पर सर्वर जोड़ें करें
- **संदेश रूटिंग** इनटेर-सर्वर संचार के लिए Kafka या Redis पुब/सुब अपयोग करती है
- **डेटाबेस शार्डिंग** बातचीत ID से स्टोरेज लोड वितरित करती है
- **गेओग्राफ़िक वितरण** - लेटेंसी कम करने के लिए कई रेगिओनस में कनेक्शन सर्वर तैनात करें
- **संदेश क्यू बफ़रिङ** - पीक अपयोग घंटे में स्पाइक एब्ज़ॉर्ब करे

## इंटरव्यू टिपस

1. **WebSocket निर्णय से शुरू करें** - एक्सपलैन करें कि इस स्केल पर HTTP पोलिङ क्यों काम नहीं करेगा
2. **कनेक्शन क्षमता क्वनटिफ़य करें** - दिखाएं कि आपको सर्वर सीमाएँ समझ हैं (~50-100K कनेक्शन प्रति सर्वर)
3. **ऑफ़लाइन डिलीवरी हल करें** - बहुत से उम्मीदवार भूल जाते हैं कि यूज़र हमेशा कनेक्टेड नहीं होते
4. **संदेश क्रम ज़िक्र करें** - टाइमस्टैम्प-आधारित क्रम के साथ टकराव समाधान

<ThinkAboutIt>
Slack और WhatsApp संदेश इतिहास के लिए बहुत अलग तरीके लेते हैं। WhatsApp संदेश डिवाइस पर स्टोर करता है और नया डिवाइस पर पूरा इतिहास सिंक नहीं करता। Slack सब कुछ सर्वर-साइड स्टोर करता है और पूरा सर्च देता है। दोनों तरीके के गोपनीयता, लागत, और यूज़र अनुभव ट्रेड-offs क्या हैं?
</ThinkAboutIt>

## मुख्य बात मुख्य सीख

- चैट सिस्टम को रीयल-टाइम द्विदिश संचार के लिए वेबसोकेटस चाहिए
