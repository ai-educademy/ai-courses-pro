## इंटरव्यू प्रॉम्प्ट

*"WhatsApp या Slack जैसी चैट ऐप्लिकेशन डिज़ाइन करें, जो one-to-one messaging, group chats और ऑनलाइन presence indicators सपोर्ट करे।"*

यह सिस्टम डिज़ाइन इंटरव्यू में एक पसंदीदा सवाल है क्योंकि यह एक ही समस्या में रीयल-टाइम संचार, कोननेकशन प्रबंधन, स्टोरेज at स्केल, और वितरित सिस्टम टरदे-ओफ़फ़स - सब कुछ टेस्ट करता है।

## चरण 1: ज़रूरतें समझना

**कार्यात्मक ज़रूरतें:**
- ओने-टो-ओने मेसगिङ के साथ डिलीवरी और रेअद रसीदें
- गरोउप चट (500 मेमबेरस तक)
- ओनलिने/ओफ़फ़लिने परेसेनके इनदिकटोरस
- मेसगे इतिहास और सर्च
- ऑफ़लाइन यूज़र के लिए push notifications

**गैर-कार्यात्मक ज़रूरतें:**
- कम लेटेंसी: संदेश 200ms के अंदर देलिवेर हों
- उच्च उपलब्धता: 99.99% उपटिमे
- एक conversation के अंदर message ordering की गारंटी
- 50 मिलियन कोनकुररेनट कनेक्शन सपोर्ट करे

<Callout>
गैर-कार्यात्मक ज़रूरतें को हमेशा विशिष्ट नंबर से क्वनटिफ़य करें। "तेज़ डिलीवरी" वगुए है - "सुब200ms डिलीवरी" दिखाता है कि आपको डोमेन की समझ है।
</Callout>

## चरण 2: API डिज़ाइन

REST-only सिस्टम के विपरीत, चैट को **द्विदिश संचार** चाहिए। हमें दो प्रोटोकॉल चाहिए:

**REST API** (नोन-रेअल-टिमे ऑपरेशन के लिए):
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket** (रीयल-टाइम मेसगिङ के लिए):
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## चरण 3: WebSocket कोननेकशन मनगेमेनट

हर कोननेकटेद यूज़र एक पेरसिसटेनट WebSocket कोननेकशन बनाए करता है। 50 मिलियन कोनकुररेनट यूज़र पर यह एक बड़ी इंजीनियरिंग चललेङे है।

**कनेक्शन सर्वर** (जिन्हें गेटवे सर्वर भी कहते हैं) WebSocket कनेक्शन बनाए करते हैं। हर सर्वर लगभग 50,000-100,000 कोनकुररेनट कनेक्शन संभाल कर सकता है, यानी हमें 500-1,000 कनेक्शन सर्वर चाहिए।

एक **connection registry** (Redis क्लस्टर) हर यूज़र को उनके connection server से मैप करती है:
```
user_123 → ws-server-042
user_456 → ws-server-187
```

जब यूज़र A, यूज़र B को संदेश भेजता है, फ़लोव यह होता है:
1. मेसगे, A के कोननेकशन सर्वर पर WebSocket से आता है
2. सेरवेर, Redis में B का कोननेकशन सर्वर लूक up करता है
3. मेसगे इनटेरनल मेसगिङ से B के कोननेकशन सर्वर को रूट होता है
4. B का सर्वर, B के WebSocket पर संदेश पुश करता है

## चरण 4: मेसगे सटोरगे

चैट ऐप्लिकेशन बहुत बड़ी मात्रा में डेटा बनाती हैं। WhatsApp रोज़ 100 billion से ज़्यादा संदेश प्रोसेस करता है।

**सटोरगे रणनीति:**
- **हाल के संदेश** - तेज़ datastore (Cassandra या HBase) में, conversation ID से partitioned
- **मेसगे इंडेक्स** - Elasticsearch से सर्च एनबले करता है
- **मेदिअ फ़ाइलस** - ओबजेकट स्टोरेज (S3) में CDN डिलीवरी के साथ

**Schema design (Cassandra):**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

यह डिज़ाइन सुनिश्चित करता है कि एक conversation के सभी संदेश उसी partition पर co-located रहें, जिससे "पुराने संदेश लोड करो" queries बहुत कुशल हो जाती हैं - बस एक partition के भीतर sequential read।

## चरण 5: परेसेनके सिस्टम

कौन ऑनलाइन है दिखाना सरल लगता है, लेकिन scale पर यह चौंकाने वाला पेचीदा है। आप अपनी contact list के हर यूज़र के लिए हर कुछ सेकंड में डेटाबेस poll नहीं कर सकते।

**हेअरटबेअट तरीका:**
1. कोननेकटेद कलिएनटस हर 30 सेकंड में WebSocket से हेअरटबेअट भेजते हैं
2. सेरवेर एक Redis की अपडेट करता है जिसमें 60 सेकंड का TTL होता है: `presence:user_123 → online (TTL 60s)`
3. अगर हेअरटबेअट नहीं आता, की एक्सपिरे हो जाती है और यूज़र ऑफ़लाइन दिखता है

**सटटुस अपडेट के लिए फ़न-ओउट:**
जब कोई यूज़र ऑनलाइन आता है, तो उसका status उन सभी contacts तक push होना चाहिए जो ऑनलाइन हैं। 500 contacts वाले यूज़र के लिए, इसका मतलब है कि कौन-से contacts ऑनलाइन हैं यह जाँचना और सिर्फ़ उन्हें presence updates भेजना - **lazy fan-out** ऑफ़लाइन यूज़र को broadcast करने से बचाता है।

<FunFact>
WhatsApp के "last seen" फ़ीचर ने दुनिया भर में अनपेक्षित social drama पैदा किया। कुछ देशों में relationship disputes बढ़े क्योंकि partners एक-दूसरे के exact last-active timestamps देख सकते थे। WhatsApp ने आखिरकार यह जानकारी छुपाने के लिए privacy controls जोड़े।
</FunFact>

## चरण 6: Push Notifications

जब यूज़र ऑफ़लाइन हो (कोई active WebSocket नहीं), तो संदेश push notifications के ज़रिए भी पहुँचने चाहिए।

मेसगे फ़लोव बदल जाता है:
1. Connection registry दिखाती है कि यूज़र B ऑफ़लाइन है
2. मेसगे डेटाबेस में "उनदेलिवेरेद" सटटुस के साथ स्टोर होता है
3. नोटिफ़िकशन सर्विस अपनस (इओस) या FCM (अनदरोइद) से पुश भेजती है
4. जब यूज़र B रेकोननेकट करता है, उनदेलिवेरेद संदेश फ़ेटच करके WebSocket से भेजे जाते हैं
5. रेकेइपट कोनफ़िरम करने के लिए डिलीवरी रसीदें भेजी जाती हैं

<ThinkAboutIt>
500 members वाली group chats में fan-out challenge होता है। अगर एक संदेश ऐसे group में भेजा जाए जहाँ 400 members ऑफ़लाइन हैं, तो 400 push notifications भेजनी पड़ेंगी। Peak hours में notification services को overwhelmed होने से बचाने के लिए आप इन्हें कैसे batch और rate-limit करेंगे?
</ThinkAboutIt>

## चरण 7: E2E Encryption की बुनियाद

इंटरव्यू चर्चा में E2E encryption का संक्षिप्त ज़िक्र security awareness दिखाता है:

- हर यूज़र अपने डिवाइस पर **पुबलिक/परिवटे की पैर** जनरेट करता है
- Messages sender के device से निकलने से पहले recipient की public key से encrypt होते हैं
- सेरवेर को सिर्फ किफेरटेक्सट दिखता है - वह संदेश कंटेंट नहीं पढ़ सकता
- गरोउप चटस एक **शरेद गरोउप की** उपयोग करते हैं जो मेमबेरस जुड़ें या लेअवे करने पर रोटटे होती है

इसका मतलब है कि सर्वर के message storage में सिर्फ़ encrypted blobs होते हैं, जो data compliance के नज़रिये से वास्तव में सरल है।

## चरण 8: मिललिओनस तक सकले करना

**मुख्य बात स्केलिंग रणनीतियाँ:**
- **Connection servers** horizontally scale होते हैं - यूज़र बढ़ने पर और servers जोड़ें
- **मेसगे रूटिंग** इनटेर-सेरवेर संचार के लिए Kafka या Redis पुब/सुब उपयोग करती है
- **Database sharding** conversation ID से storage load वितरित करती है
- **गेओगरफिक डिस्ट्रिब्यूशन** - लेटेंसी कम करने के लिए कई रेगिओनस में कनेक्शन सर्वर तैनात करें
- **मेसगे क्यू बुफ़फ़ेरिङ** - पीक उसगे घंटे में सचुनताेस अबसोरब करे

## इंटरव्यू टिपस

1. **WebSocket निर्णय से शुरू करें** - एक्सपलैन करें कि इस स्केल पर HTTP पोललिङ क्यों काम नहीं करेगा
2. **कोननेकशन कपकिटय क्वनटिफ़य करें** - दिखाएं कि आपको सर्वर सीमाएँ समझ हैं (~50-100K कनेक्शन प्रति सर्वर)
3. **ओफ़फ़लिने डिलीवरी हल करें** - बहुत से उम्मीदवार भूल जाते हैं कि यूज़र हमेशा कोननेकटेद नहीं होते
4. **Message ordering का ज़िक्र करें** - timestamp-based ordering के साथ conflict resolution

<ThinkAboutIt>
Slack और WhatsApp message history के लिए बहुत अलग approaches अपनाते हैं। WhatsApp messages को device पर store करता है और नए devices पर पूरा history sync नहीं करता। Slack सब कुछ server-side store करता है और full search देता है। दोनों approaches में privacy, cost और user experience के trade-offs क्या हैं?
</ThinkAboutIt>

## मुख्य बात टकेअवयस

- चैट सिस्टम को real-time bidirectional communication के लिए WebSockets चाहिए
- बड़े पैमाने पर connection management के लिए users-to-servers mapping registry ज़रूरी है
- Cassandra का write throughput और partition-based queries चैट message storage के लिए उपयुक्त हैं
- परेसेनके सिस्टम Redis में टटल-बसेद एक्सपिरय के साथ हेअरटबेअटस उपयोग करते हैं
- Push notifications ऑफ़लाइन message delivery संभालती हैं
- गेओगरफिक डिस्ट्रिब्यूशन और होरिज़ोनटल स्केलिंग गलोबल लेटेंसी ज़रूरतें हल करते हैं
