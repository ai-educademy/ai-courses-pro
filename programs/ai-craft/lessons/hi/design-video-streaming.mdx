# वीडियो स्ट्रीमिंग प्लेटफ़ॉर्म डिज़ाइन करें - YouTube/Netflix आर्किटेक्चर

वीडियो स्ट्रीमिंग वैश्विक इंटरनेट ट्रैफ़िक के 65% से अधिक के लिए जिम्मेदार है। ऐसा सिस्टम डिज़ाइन करना file processing pipelines, CDN architecture और adaptive streaming को कवर करता है। ये अवधारणाएं वीडियो से बहुत आगे भी लागू होती हैं।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- वीडियो upload करें (हर फ़ाइल 1 GB तक)
- नेटवर्क स्थितियों के आधार पर adaptive quality के साथ वीडियो stream करें
- Title, description और tags से वीडियो search करें
- View counts और engagement metrics track करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **अवेलेबिलिटी** - streaming के लिए 99.99% uptime
- **कम लेटेंसी** - video playback 2 seconds के भीतर शुरू हो
- **वैश्विक पहुंच** - सभी महाद्वीपों में users को कुशलता से serve करें
- **लागत-कुशल** - storage और bandwidth को optimise करें (दो सबसे बड़ी लागतें)

## चरण 2 - उच्च-स्तरीय आर्किटेक्चर

```
Upload Flow:
Client → Upload Service → Object Storage (raw)
                              ↓
                    Transcoding Pipeline (async)
                         ↓          ↓
                   Multiple      Thumbnail
                   Qualities     Generator
                         ↓          ↓
                    CDN Origin Storage → CDN Edge Servers

Streaming Flow:
Client → CDN Edge → (cache miss) → CDN Origin → Object Storage
```

## चरण 3 - वीडियो Upload Pipeline

### चरण-दर-चरण Processing
1. **Upload** - client raw video को large files के लिए resumable uploads के साथ pre-signed URLs से object storage (जैसे S3) पर upload करता है
2. **Transcoding** - source video को कई resolutions (1080p, 720p, 480p, 360p) और codecs (H.264, VP9, AV1) में बदलें
3. **Adaptive Bitrate Packaging** - HLS/DASH streaming के लिए हर quality level को छोटे segments (2-10 seconds) में बांटें
4. **Thumbnail Generation** - preview thumbnails के लिए नियमित अंतराल पर frames निकालें
5. **Metadata Update** - सभी processing पूरी होने पर database में video को "ready" mark करें

### Scale पर Transcoding
एक 10-minute 4K video को एक machine पर transcode करने में 30+ minutes लग सकते हैं। हजारों concurrent uploads संभालने के लिए:
- Video को chunks में split करें और DAG-based workflow (जैसे AWS Step Functions) से parallel transcode करें
- Compute costs 60-80% घटाने के लिए spot/preemptible instances इस्तेमाल करें

## चरण 4 - Streaming Protocols और CDN

### Adaptive Bitrate Streaming
Player viewer की network speed के आधार पर quality अपने आप बदलता है:

| Protocol | Used By | Segment Format | Manifest |
|----------|---------|----------------|----------|
| HLS | Apple, most browsers | .ts or .fmp4 | .m3u8 playlist |
| DASH | YouTube, Netflix | .mp4 segments | .mpd manifest |

Client उपलब्ध quality levels वाली manifest file download करता है, फिर एक-एक segment request करता है और bandwidth बदलने पर seamless तरीके से quality switch करता है।

### CDN Architecture
Streaming performance के लिए CDN सबसे महत्वपूर्ण component है:

```
User in London → London Edge PoP (cache hit: 95%)
                     ↓ (cache miss)
              European Regional Cache
                     ↓ (cache miss)
              Origin Storage (S3)
```

**मुख्य insight:** लोकप्रिय वीडियो users के सबसे पास edge locations पर cache होते हैं। Long-tail content केवल regional nodes पर cache हो सकता है, और rare content के लिए origin fetch होते हैं।

<FunFact>Netflix हर सप्ताह 700 मिलियन घंटे से अधिक video serve करता है। उनका Open Connect CDN custom hardware appliances को सीधे ISP data centres के भीतर रखता है, जिससे लोकप्रिय content last mile पर cache होता है और internet backbone traffic 90% से अधिक घटता है।</FunFact>

## चरण 5 - Supporting Services

### Video Metadata Service
Title, description, tags, upload date, view counts और processing status store करता है। Structured queries और search indexing के लिए relational database (PostgreSQL) इस्तेमाल करें।

### Scale पर View Counting
Naive तरीका (हर view पर increment) write hotspot बनाता है। इसके बजाय:
- View events को stream (Kafka) में batch करें
- Counts को periodic रूप से aggregate करें (हर 30 seconds)
- Real-time display के लिए approximate counting, analytics के लिए exact counts इस्तेमाल करें

### Live Streaming Architecture
Live streaming on-demand से मुख्य तरीकों में अलग है:
- **No pre-transcoding** - video को real-time में transcode करना पड़ता है
- **Ultra-low latency** - viewers sub-5-second delay की अपेक्षा करते हैं
- **Ingestion protocol** - streamers RTMP से push करते हैं, viewers low-latency extensions के साथ HLS/DASH से receive करते हैं

## चरण 6 - Cost Breakdown और Optimisations

Video platforms चलाना **बहुत महंगा** है। तीन सबसे बड़ी लागतें:

| Cost Centre | Estimate (10M daily users) | Optimisation |
|------------|---------------------------|--------------|
| Storage | ~$200K/month | Tiered storage (hot/warm/cold), failed uploads delete करें |
| CDN Bandwidth | ~$500K/month | Edge caching, modern codecs (AV1) से compress करें |
| Transcoding Compute | ~$100K/month | Spot instances, rarely-watched quality levels skip करें |

<ThinkAboutIt>Netflix content delivery पर हर साल billions खर्च करता है। अगर आप उनका system शुरू से design कर रहे होते, तो अपना CDN बनाते (जैसे Netflix Open Connect) या commercial CDN इस्तेमाल करते (जैसे CloudFront)? किस scale पर अपना CDN बनाना cost-effective हो जाता है?</ThinkAboutIt>

### Content Protection (DRM)
Premium content को Digital Rights Management चाहिए:
- **Widevine** (Google) - Chrome, Android
- **FairPlay** (Apple) - Safari, iOS
- **PlayReady** (Microsoft) - Edge, Windows

हर DRM system को अलग encryption और licence server integration चाहिए, जिससे काफी complexity जुड़ती है।

<ThinkAboutIt>YouTube 800 million से अधिक videos store करता है। अगर हर video 5 quality levels में transcode किया गया है और हर level औसतन 500 MB है, तो कुल storage कितना चाहिए होगा? आप cost-effective storage strategy कैसे design करेंगे?</ThinkAboutIt>
