# वेब क्रॉलर डिज़ाइन करें - Google इंटरनेट को कैसे इंडेक्स करता है

वेब क्रॉलर वेब पेज डाउनलोड और इंडेक्स करने के लिए व्यवस्थित रूप से इंटरनेट ब्राउज़ करता है। यह हर खोज इंजन की बुनियाद है, और इसे डिज़ाइन करना आपको वितरित सिस्टम, ग्राफ़ ट्रैवर्सल और वास्तविक वेब की अव्यवस्था संभालना सिखाता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- Seed URL के सेट से शुरू करके वेब पेज क्रॉल करें
- नए पेज खोजने के लिए हाइपरलिंक निकालें और फ़ॉलो करें
- Indexing और प्रोसेसिंग के लिए डाउनलोडेड सामग्री स्टोर करें
- रोबोट्स.txt और क्रॉल शिष्टाचार नियम का सम्मान करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **स्केल** - हर महीने 1 बिलियन पेज क्रॉल करें
- **शिष्टाचार** - किसी एक वेब सर्वर को कभी ओवरवेल्म न करें
- **ताज़गी** - महत्वपूर्ण पेज को नियमित रूप से re-क्रॉल करें
- **Robustness** - खराब HTML, अनंत लूप और स्पाइडर ट्रैप संभालें

## चरण 2 - उच्च-स्तरीय आर्किटेक्चर

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## चरण 3 - क्रॉल Loop

### BFS बनाम DFS क्रॉलिंग
- **BFS (Breadth-First)** - वेब क्रॉलिंग के लिए पसंदीदा। यह डोमेन का विस्तृत सेट जल्दी खोजता है और किसी एक साइट में बहुत गहराई तक फंसने से बचता है
- **DFS (Depth-First)** - दूसरे डोमेन खोजने से पहले डायनेमिक रूप से बने हुए पेज में अनंत गहराई तक जाने का जोखिम रखता है

### URL फ़्रंटियर डिज़ाइन
फ़्रंटियर कोई सरल क्यू नहीं है। यह दो sub-components वाला उन्नत प्राथमिकता सिस्टम है:

1. **प्राथमिकता क्यू (Front)** - URL को महत्व से रैंक करती है। कारकों में PageRank, अपडेट आवृत्ति और डोमेन अथॉरिटी शामिल हैं
2. **शिष्टाचार क्यू (Back)** - सुनिश्चित करती है कि हर डोमेन की अपनी FIFO क्यू हो। Scheduler अलग-अलग डोमेन क्यू से चुनता है ताकि किसी एक सर्वर पर अत्यधिक लोड न पड़े

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## चरण 4 - शिष्टाचार और Robots.txt

### Robots.txt का सम्मान
किसी भी डोमेन को क्रॉल करने से पहले उसकी `robots.txt` फ़ाइल फ़ेच और कैश करें:

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

Robots.txt को हर डोमेन के लिए TTL (24 घंटे) के साथ कैश करें। हमेशा `Disallow` नियम और `Crawl-delay` निर्देश का सम्मान करें।

### क्रॉल रेट Limiting
स्पष्ट `Crawl-delay` न होने पर भी शिष्टाचार बनाए रखें:
- हर डोमेन पर अधिकतम 1 अनुरोध per सेकंड (कॉन्फ़िगर-योग्य)
- हर डोमेन की अलग डाउनलोड क्यू इस्तेमाल करें
- उत्तर बार ट्रैक करें। सर्वर धीमा हो तो अपने-आप बैक off करें

<FunFact>Google का वेब क्रॉलर (Googlebot) सैकड़ों अरब पेज क्रॉल करता है। Polite रहने के लिए यह सर्वर उत्तर बार मॉनिटर करता है और अगर कोई साइट धीमी उत्तर देने लगे तो अपनी क्रॉल रेट घटा देता है। इससे वेबसाइट क्रॉलर के विरुद्ध प्रभावी रूप से "पुश बैक" कर सकती है।</FunFact>

## चरण 5 - डीडुप्लिकेशन

### URL डीडुप्लिकेशन (Bloom फ़िल्टर)
अरबों URL के साथ यह जांचना कि कोई URL पहले देखा गया है या नहीं, एक कुशल डेटा संरचना मांगता है। Bloom फ़िल्टर छोटे मेमोरी फ़ुटप्रिंट के साथ O(1) खोज देता है:

- **Space:** 1% फ़ॉल्स पॉज़िटिव रेट पर 1 बिलियन URL के लिए ~1 GB
- **Trade-off:** कभी-कभी किसी पेज को दोबारा क्रॉल कर सकता है (फ़ॉल्स पॉज़िटिव), लेकिन नया URL कभी नहीं चूकता (no फ़ॉल्स निगेटिव)

जांचने से पहले URL नॉर्मलाइज़ करें: फ़्रैगमेंट (#) हटाएं, क्वेरी पैरामीटर सॉर्ट करें, होस्टनेम लोअरकेस करें और रिलेटिव पथ रिज़ॉल्व करें।

### सामग्री डीडुप्लिकेशन (SimHash)
अलग URL समान सामग्री सर्व कर सकते हैं (मिरर, कॉपी लेख)। SimHash पेज सामग्री का फ़िंगरप्रिंट बनाता है। समान फ़िंगरप्रिंट (छोटी Hamming दूरी) वाले पेज संभवतः डुप्लिकेट होते हैं:

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## चरण 6 - वितरित क्रॉलिंग

### क्षैतिज रूप से स्केल करना
एक अकेली मशीन हर महीने बिलियन पेज क्रॉल नहीं कर सकती। काम को बांटें:

- डोमेन नाम पर **कंसिस्टेंट हैशिंग** हर डोमेन को खास क्रॉलर नोड पर असाइन करती है। इससे शिष्टाचार सुनिश्चित होती है, क्योंकि कोई दिया हुआ डोमेन केवल एक नोड क्रॉल करता है
- **URL फ़्रंटियर** हैश रिंग के आधार पर नोड में पार्टिशन होता है
- **Coordination** हल्की सेवा से होती है, जो नोड असाइनमेंट मैनेज करती है और नोड जुड़ें या हटें होने पर रीबैलेंस करती है

### DNS Resolution कैशिंग
DNS खोज हर अनुरोध में 10-100ms जोड़ते हैं। स्केल पर यह बड़ी बाधा है:
- हर क्रॉलर नोड पर स्थानीय DNS कैश रखें
- Queued URL के लिए बैच DNS pre-समाधान करें
- पब्लिक DNS सर्वर को ओवरवेल्म करने से बचने के लिए समर्पित DNS रिज़ॉल्वर इस्तेमाल करें

### Spider Trap Detection
दुर्भावनापूर्ण या खराब बनी साइटें अनंत URL स्पेस बना सकती हैं:
- `/page/1/page/1/page/1/...` - दोहराए जाने वाले पथ पैटर्न
- हर भविष्य तारीख के लिए URL बनाने वाले कैलेंडर पेज
- Identical सामग्री के लिए अद्वितीय URL बनाने वाले सेशन IDs

**बचाव:** अधिकतम URL लंबाई, हर डोमेन पर अधिकतम क्रॉल गहराई, दोहरावदार URL संरचनाएं के लिए पैटर्न पहचान और डोमेन-स्तर पेज संख्या लिमिट।

<ThinkAboutIt>अगर आपको खोज इंडेक्स ताज़ा रखना हो, तो आप पहले किन पेज को re-क्रॉल करने का निर्णय कैसे लेंगे? एक समाचार साइट जो हर-घंटे अपडेट होती है बनाम Wikipedia लेख जो मासिक बदलता है, इस पर विचार करें। फिर से क्रॉल करने की शेड्यूलिंग को प्राथमिकता करने के लिए आप कौन से संकेत इस्तेमाल करेंगे?</ThinkAboutIt>

## चरण 7 - बाधाएं और ऑप्टिमाइज़ेशन

| बाधा | समाधान |
|-----------|----------|
| DNS समाधान लेटेंसी | Local DNS कैश, बैच pre-समाधान |
| धीमे/उत्तर न देने वाले सर्वर | टाइमआउट (30s), असिंक्रोनस I/O, रीट्राई के बाद छोड़ें |
| Crawled सामग्री के लिए स्टोरेज | पेज कम्प्रेस करें, केवल बदली सामग्री स्टोर करें |
| URL फ़्रंटियर मेमोरी | Disk-backed प्राथमिकता क्यू (RocksDB) |
| Duplicate सामग्री | SimHash फ़िंगरप्रिंटिंग, कैनोनिकल URL पहचान |

<ThinkAboutIt>खोज इंजन को क्रॉल ताज़गी (पेज को बार-बार re-क्रॉल करना) और खोज (नए पेज खोजना) में संतुलन बनाना पड़ता है। अगर आपके क्रॉलर का तय बजट 1 मिलियन पेज per day है, तो आप इस बजट को मौजूदा पेज re-क्रॉल करने और नए पेज खोजें करने के बीच कैसे बांटेंगे?</ThinkAboutIt>
