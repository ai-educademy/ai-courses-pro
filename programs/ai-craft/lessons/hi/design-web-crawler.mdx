# वेब क्रॉलर डिज़ाइन करें - Google इंटरनेट को कैसे इंडेक्स करता है

वेब क्रॉलर वेब पेज डाउनलोड और इंडेक्स करने के लिए व्यवस्थित रूप से इंटरनेट ब्राउज़ करता है। यह हर search engine की बुनियाद है, और इसे डिज़ाइन करना आपको वितरित systems, graph traversal और वास्तविक वेब की अव्यवस्था संभालना सिखाता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- Seed URL के सेट से शुरू करके web पेज क्रॉल करें
- नए पेज खोजने के लिए hyperlinks निकालें और follow करें
- Indexing और प्रोसेसिंग के लिए downloaded सामग्री स्टोर करें
- robots.txt और क्रॉल शिष्टाचार rules का सम्मान करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **Scale** - हर महीने 1 billion पेज क्रॉल करें
- **शिष्टाचार** - किसी एक web server को कभी overwhelm न करें
- **Freshness** - महत्वपूर्ण पेज को नियमित रूप से re-क्रॉल करें
- **Robustness** - malformed HTML, infinite loops और spider traps संभालें

## चरण 2 - उच्च-स्तरीय आर्किटेक्चर

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## चरण 3 - क्रॉल Loop

### BFS बनाम DFS Crawling
- **BFS (Breadth-First)** - web crawling के लिए पसंदीदा। यह domains का विस्तृत सेट जल्दी खोजता है और किसी एक साइट में बहुत गहराई तक फंसने से बचता है
- **DFS (Depth-First)** - दूसरे domains खोजने से पहले dynamically generated पेज में अनंत गहराई तक जाने का जोखिम रखता है

### URL फ़्रंटियर Design
फ़्रंटियर कोई simple क्यू नहीं है। यह दो sub-components वाला sophisticated प्राथमिकता सिस्टम है:

1. **प्राथमिकता क्यू (Front)** - URL को importance से rank करती है। कारकों में PageRank, अपडेट frequency और डोमेन authority शामिल हैं
2. **शिष्टाचार क्यू (Back)** - सुनिश्चित करती है कि हर डोमेन की अपनी FIFO क्यू हो। Scheduler अलग-अलग डोमेन क्यू से चुनता है ताकि किसी एक server पर अत्यधिक लोड न पड़े

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## चरण 4 - शिष्टाचार और Robots.txt

### Robots.txt का सम्मान
किसी भी डोमेन को क्रॉल करने से पहले उसकी `robots.txt` file fetch और कैश करें:

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

Robots.txt को हर डोमेन के लिए TTL (24 hours) के साथ कैश करें। हमेशा `Disallow` rules और `Crawl-delay` directives का सम्मान करें।

### क्रॉल रेट Limiting
स्पष्ट `Crawl-delay` न होने पर भी शिष्टाचार बनाए रखें:
- हर डोमेन पर अधिकतम 1 अनुरोध per सेकंड (configurable)
- हर डोमेन की अलग download क्यू इस्तेमाल करें
- उत्तर times ट्रैक करें। Server धीमा हो तो automatically back off करें

<FunFact>Google का web क्रॉलर (Googlebot) सैकड़ों अरब पेज क्रॉल करता है। Polite रहने के लिए यह server उत्तर times monitor करता है और अगर कोई साइट धीमी उत्तर देने लगे तो अपनी क्रॉल रेट घटा देता है। इससे website क्रॉलर के विरुद्ध प्रभावी रूप से "पुश back" कर सकती है।</FunFact>

## चरण 5 - डीडुप्लिकेशन

### URL डीडुप्लिकेशन (Bloom Filter)
अरबों URL के साथ यह जांचना कि कोई URL पहले देखा गया है या नहीं, एक कुशल डेटा structure मांगता है। Bloom filter छोटे memory footprint के साथ O(1) lookups देता है:

- **Space:** 1% फ़ॉल्स पॉज़िटिव रेट पर 1 billion URL के लिए ~1 GB
- **Trade-off:** कभी-कभी किसी पेज को दोबारा क्रॉल कर सकता है (फ़ॉल्स पॉज़िटिव), लेकिन नया URL कभी नहीं चूकता (no फ़ॉल्स निगेटिव)

जांचने से पहले URL नॉर्मलाइज़ करें: fragments (#) हटाएं, query parameters sort करें, hostname lowercase करें और relative paths resolve करें।

### सामग्री डीडुप्लिकेशन (SimHash)
अलग URL identical सामग्री serve कर सकते हैं (mirrors, copied articles)। SimHash पेज सामग्री का fingerprint बनाता है। समान fingerprints (छोटी Hamming distance) वाले पेज संभवतः duplicates होते हैं:

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## चरण 6 - वितरित Crawling

### क्षैतिज रूप से स्केल करना
एक अकेली machine हर महीने billion पेज क्रॉल नहीं कर सकती। काम को बांटें:

- डोमेन names पर **कंसिस्टेंट हैशिंग** हर डोमेन को खास क्रॉलर नोड पर assign करती है। इससे शिष्टाचार सुनिश्चित होती है, क्योंकि कोई दिया हुआ डोमेन केवल एक नोड क्रॉल करता है
- **URL फ़्रंटियर** हैश रिंग के आधार पर नोड में partitioned होता है
- **Coordination** हल्की सेवा से होती है, जो नोड assignments manage करती है और नोड join या leave होने पर rebalance करती है

### DNS Resolution कैशिंग
DNS lookups हर अनुरोध में 10-100ms जोड़ते हैं। Scale पर यह बड़ी बाधा है:
- हर क्रॉलर नोड पर local DNS कैश रखें
- Queued URL के लिए बैच DNS pre-resolution करें
- Public DNS servers को overwhelm करने से बचने के लिए dedicated DNS resolver इस्तेमाल करें

### Spider Trap Detection
दुर्भावनापूर्ण या खराब बनी sites अनंत URL spaces बना सकती हैं:
- `/page/1/page/1/page/1/...` - दोहराए जाने वाले path patterns
- हर future date के लिए URL बनाने वाले calendar पेज
- Identical सामग्री के लिए unique URL बनाने वाले session IDs

**बचाव:** maximum URL length, हर डोमेन पर maximum क्रॉल depth, repetitive URL structures के लिए pattern detection और डोमेन-स्तर पेज count limits।

<ThinkAboutIt>अगर आपको search index fresh रखना हो, तो आप पहले किन पेज को re-क्रॉल करने का निर्णय कैसे लेंगे? एक news साइट जो hourly अपडेट होती है बनाम Wikipedia article जो monthly बदलता है, इस पर विचार करें। Re-क्रॉल scheduling को prioritise करने के लिए आप कौन से signals इस्तेमाल करेंगे?</ThinkAboutIt>

## चरण 7 - बाधाएं और ऑप्टिमाइज़ेशन

| बाधा | समाधान |
|-----------|----------|
| DNS resolution लेटेंसी | Local DNS कैश, बैच pre-resolution |
| Slow/unresponsive servers | Timeouts (30s), async I/O, रीट्राई के बाद skip करें |
| Crawled सामग्री के लिए स्टोरेज | पेज compress करें, केवल changed सामग्री स्टोर करें |
| URL फ़्रंटियर memory | Disk-backed प्राथमिकता क्यू (RocksDB) |
| Duplicate सामग्री | SimHash fingerprinting, canonical URL detection |

<ThinkAboutIt>Search engines को क्रॉल freshness (पेज को बार-बार re-क्रॉल करना) और discovery (नए पेज खोजना) में संतुलन बनाना पड़ता है। अगर आपके क्रॉलर का fixed budget 1 million पेज per day है, तो आप इस budget को existing पेज re-क्रॉल करने और नए पेज discover करने के बीच कैसे बांटेंगे?</ThinkAboutIt>
