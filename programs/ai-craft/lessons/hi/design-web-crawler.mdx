# वेब क्रॉलर डिज़ाइन करें - Google इंटरनेट को कैसे इंडेक्स करता है

वेब क्रॉलर वेब पेज डाउनलोड और इंडेक्स करने के लिए व्यवस्थित रूप से इंटरनेट ब्राउज़ करता है। यह हर search engine की बुनियाद है, और इसे डिज़ाइन करना आपको distributed systems, graph traversal और वास्तविक वेब की अव्यवस्था संभालना सिखाता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- Seed URLs के सेट से शुरू करके web pages crawl करें
- नए pages खोजने के लिए hyperlinks निकालें और follow करें
- Indexing और processing के लिए downloaded content store करें
- robots.txt और crawl politeness rules का सम्मान करें

### नॉन-फ़ंक्शनल आवश्यकताएं
- **Scale** - हर महीने 1 billion pages crawl करें
- **Politeness** - किसी एक web server को कभी overwhelm न करें
- **Freshness** - महत्वपूर्ण pages को नियमित रूप से re-crawl करें
- **Robustness** - malformed HTML, infinite loops और spider traps संभालें

## चरण 2 - उच्च-स्तरीय आर्किटेक्चर

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## चरण 3 - Crawl Loop

### BFS बनाम DFS Crawling
- **BFS (Breadth-First)** - web crawling के लिए पसंदीदा। यह domains का विस्तृत सेट जल्दी खोजता है और किसी एक site में बहुत गहराई तक फंसने से बचता है
- **DFS (Depth-First)** - दूसरे domains खोजने से पहले dynamically generated pages में अनंत गहराई तक जाने का जोखिम रखता है

### URL Frontier Design
Frontier कोई simple queue नहीं है। यह दो sub-components वाला sophisticated priority system है:

1. **Priority Queue (Front)** - URLs को importance से rank करती है। कारकों में PageRank, update frequency और domain authority शामिल हैं
2. **Politeness Queue (Back)** - सुनिश्चित करती है कि हर domain की अपनी FIFO queue हो। Scheduler अलग-अलग domain queues से चुनता है ताकि किसी एक server पर अत्यधिक load न पड़े

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## चरण 4 - Politeness और Robots.txt

### Robots.txt का सम्मान
किसी भी domain को crawl करने से पहले उसकी `robots.txt` file fetch और cache करें:

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

Robots.txt को हर domain के लिए TTL (24 hours) के साथ cache करें। हमेशा `Disallow` rules और `Crawl-delay` directives का सम्मान करें।

### Crawl Rate Limiting
स्पष्ट `Crawl-delay` न होने पर भी politeness बनाए रखें:
- हर domain पर अधिकतम 1 request per second (configurable)
- हर domain की अलग download queues इस्तेमाल करें
- Response times track करें। Server धीमा हो तो automatically back off करें

<FunFact>Google का web crawler (Googlebot) सैकड़ों अरब pages crawl करता है। Polite रहने के लिए यह server response times monitor करता है और अगर कोई site धीमी response देने लगे तो अपनी crawl rate घटा देता है। इससे website crawler के विरुद्ध प्रभावी रूप से "push back" कर सकती है।</FunFact>

## चरण 5 - Deduplication

### URL Deduplication (Bloom Filter)
अरबों URLs के साथ यह जांचना कि कोई URL पहले देखा गया है या नहीं, एक कुशल data structure मांगता है। Bloom filter छोटे memory footprint के साथ O(1) lookups देता है:

- **Space:** 1% false positive rate पर 1 billion URLs के लिए ~1 GB
- **Trade-off:** कभी-कभी किसी page को दोबारा crawl कर सकता है (false positive), लेकिन नया URL कभी नहीं चूकता (no false negatives)

जांचने से पहले URLs normalize करें: fragments (#) हटाएं, query parameters sort करें, hostname lowercase करें और relative paths resolve करें।

### Content Deduplication (SimHash)
अलग URLs identical content serve कर सकते हैं (mirrors, copied articles)। SimHash page content का fingerprint बनाता है। समान fingerprints (छोटी Hamming distance) वाले pages संभवतः duplicates होते हैं:

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## चरण 6 - Distributed Crawling

### क्षैतिज रूप से स्केल करना
एक अकेली machine हर महीने billion pages crawl नहीं कर सकती। काम को बांटें:

- Domain names पर **consistent hashing** हर domain को खास crawler node पर assign करती है। इससे politeness सुनिश्चित होती है, क्योंकि कोई दिया हुआ domain केवल एक node crawl करता है
- **URL frontier** hash ring के आधार पर nodes में partitioned होता है
- **Coordination** हल्की सेवा से होती है, जो node assignments manage करती है और nodes join या leave होने पर rebalance करती है

### DNS Resolution Caching
DNS lookups हर request में 10-100ms जोड़ते हैं। Scale पर यह बड़ी बाधा है:
- हर crawler node पर local DNS cache रखें
- Queued URLs के लिए batch DNS pre-resolution करें
- Public DNS servers को overwhelm करने से बचने के लिए dedicated DNS resolver इस्तेमाल करें

### Spider Trap Detection
दुर्भावनापूर्ण या खराब बनी sites अनंत URL spaces बना सकती हैं:
- `/page/1/page/1/page/1/...` - दोहराए जाने वाले path patterns
- हर future date के लिए URLs बनाने वाले calendar pages
- Identical content के लिए unique URLs बनाने वाले session IDs

**बचाव:** maximum URL length, हर domain पर maximum crawl depth, repetitive URL structures के लिए pattern detection और domain-level page count limits।

<ThinkAboutIt>अगर आपको search index fresh रखना हो, तो आप पहले किन pages को re-crawl करने का निर्णय कैसे लेंगे? एक news site जो hourly update होती है बनाम Wikipedia article जो monthly बदलता है, इस पर विचार करें। Re-crawl scheduling को prioritise करने के लिए आप कौन से signals इस्तेमाल करेंगे?</ThinkAboutIt>

## चरण 7 - बाधाएं और ऑप्टिमाइज़ेशन

| बाधा | समाधान |
|-----------|----------|
| DNS resolution latency | Local DNS cache, batch pre-resolution |
| Slow/unresponsive servers | Timeouts (30s), async I/O, retries के बाद skip करें |
| Crawled content के लिए storage | Pages compress करें, केवल changed content store करें |
| URL frontier memory | Disk-backed priority queue (RocksDB) |
| Duplicate content | SimHash fingerprinting, canonical URL detection |

<ThinkAboutIt>Search engines को crawl freshness (pages को बार-बार re-crawl करना) और discovery (नए pages खोजना) में संतुलन बनाना पड़ता है। अगर आपके crawler का fixed budget 1 million pages per day है, तो आप इस budget को existing pages re-crawl करने और नए pages discover करने के बीच कैसे बांटेंगे?</ThinkAboutIt>
