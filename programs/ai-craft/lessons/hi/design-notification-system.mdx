# नोटिफ़िकशन सयसटेम डिज़ाइन करें - पुश, एमैल, और SMS बिललिओन बड़े पैमाने पर

मोदेरन अपपलिकशनस हर दिन अरबों नोटिफ़िकशनस भेजती हैं, वो भी कई चननेलस पर। इस सयसटेम को डिज़ाइन करना आपको संदेश क्यू, थिरद-परटय इनटेगरशनस, और स्केल पर फ़ैलुरेस को गरकेफ़ुललय संभाल करना सिखाता है।

## चरण 1 - ज़रूरतें समझना

### फ़ुनकशनल ज़रूरतें
- मुलटिपले चननेलस सपोर्ट करें: पुश नोटिफ़िकशनस, एमैल, SMS, और इन-अपप
- यूज़र अपनी नोटिफ़िकशन प्राथमिकताएँ कोनफ़िगुरे कर सकें और प्रति चननेल ओपट ओउट कर सकें
- टेमपलटेद संदेश के साथ वैयक्तिकरण (जैसे, "Hi {नमे}, आपका order भेज हो गया है")
- सचेदुलेद और इममेदिअटे नोटिफ़िकशनस का सपोर्ट

### नोन-फ़ुनकशनल ज़रूरतें
- **सकलबिलिटय** - 10 मिलियन+ नोटिफ़िकशनस प्रतिदिन संभालें
- **रेलिअबिलिटय** - कोई नोटिफ़िकशन लोसट न हो; अट-लेअसट-ओनके डिलीवरी
- **कम लेटेंसी** - उरगेनट नोटिफ़िकशनस सेकंडों में देलिवेर हों
- **एक्सटेनसिबले** - नए चननेलस (वहटसपप, Slack) आसानी से जोड़ें करें

<ThinkAboutIt>नोटिफ़िकशन डिलीवरी एक्सकटलय-ओनके होनी चाहिए या अट-लेअसट-ओनके? सोचिए - दुपलिकटे SMS मिलने का अनुभव बनाम एक करिटिकल सुरक्षा अलेरट मिस हो जाने का।</ThinkAboutIt>

## चरण 2 - हिघ-लेवेल आर्किटेक्चर

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### कोरे कोमपोनेनटस
1. **नोटिफ़िकशन सर्विस** - रिक्वेस्ट वलिदटे करता है, यूज़र प्राथमिकताएँ जाँच करता है, टेमपलटेस रेनदेर करता है, और संदेश एनक्वेउए करता है
2. **मेसगे क्वेउएस** - हर चननेल के लिए अलग क्यू ताकि इनदेपेनदेनट स्केलिंग और इसोलशन मिले
3. **देलिवेरय वोरकेरस** - चननेल-सपेकिफ़िक वोरकेरस जो थिरद-परटय API कललस संभाल करते हैं
4. **टेमपलटे सर्विस** - नोटिफ़िकशन टेमपलटेस सटोरे और रेनदेर करता है वरिअबले सुबसटिटुशन के साथ

## चरण 3 - दीप दिवे: मुख्य बात कोमपोनेनटस

### यूज़र परेफ़ेरेनकेस और ओपट-ओउट
हर यूज़र और नोटिफ़िकशन type के लिए प्राथमिकताएँ सटोरे करें:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

नोटिफ़िकशन सर्विस एनक्वेउए करने **से पहले** प्राथमिकताएँ जाँच करता है - जो यूज़र नहीं चाहता वो कभी सेनद न करें।

### परिओरिटय क्वेउएस
सभी नोटिफ़िकशनस एक्वल नहीं होतीं। परिओरिटय लेवेलस इस्तेमाल करें:
- **करिटिकल** - सुरक्षा अलेरटस, OTP कोदेस → तुरंत प्रोसेस
- **हिघ** - order कोनफ़िरमशनस, पेमेंट रेकेइपटस → सेकंडों में
- **मेदिउम** - सोकिअल इंटरैक्शन, टिप्पणियाँ → मिनटों में ठीक है
- **कम** - मरकेटिङ, अनुशंसाएँ → बैच किया जा सकता है

## चरण 4 - रेलिअबिलिटय और फ़ैलुरे हनदलिङ

### देदुपलिकशन
दुपलिकटे नोटिफ़िकशनस रोकने के लिए इदेमपोटेनकय की इस्तेमाल करें। परोकेस करने से पहले जाँच करें कि नोटिफ़िकशन ID देदुपलिकशन सटोरे (Redis के साथ TTL) में मौजूद करती है या नहीं:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### रेटरय के साथ एक्सपोनेनटिअल बकोफ़फ़
थिरद-परटय सेरविकेस फ़ेल होती हैं। बढ़ते देलयस के साथ रेटरिएस लागू करें:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### प्रति यूज़र दर लिमिटिङ
यूज़र को नोटिफ़िकशन थकान से बचाएं:
- अधिकतम 3 पुश नोटिफ़िकशनस प्रति होउर प्रति यूज़र
- अधिकतम 1 मरकेटिङ एमैल प्रति दय
- सुरक्षा नोटिफ़िकशनस दर सीमाएँ बयपस करती हैं

<FunFact>फ़केबूक रोज़ 10 बिललिओन से ज़्यादा पुश नोटिफ़िकशनस भेजता है। इसके लिए उन्होंने एक कुसटोम नोटिफ़िकशन पाइपलाइन बनाया जो प्रति सेकंड मिलियन of संदेश प्रोसेस कर सकता है, इओस (अपनस) और अनदरोइद (FCM) के लिए अलग डिलीवरी रास्ते के साथ।</FunFact>

## चरण 5 - थिरद-परटय इनटेगरशन

| चननेल | परोविदेर | परोटोकोल | चललेङेस |
|---------|----------|----------|------------|
| पुश (इओस) | अपनस | HTTP/2 | टोकेन प्रबंधन, सिलेनट पुश सीमाएँ |
| पुश (अनदरोइद) | FCM | HTTP | टोपिक-बसेद बरोअदकसटिङ |
| एमैल | सेनदगरिद/SES | SMTP/API | देलिवेरबिलिटय, स्पैम फ़िल्टर |
| SMS | टविलिओ | REST API | प्रति संदेश लागत, रेगिओनल अनुपालन |
| इन-अपप | WebSocket | WS | कोननेकशन प्रबंधन, ऑफ़लाइन बुफ़फ़ेरिङ |

### विश्लेषण पाइपलाइन
हर संदेश का नोटिफ़िकशन लिफ़ेकयकले रिकॉर्ड करें:
- **करेअटेद** → **क्वेउएद** → **सेनट** → **देलिवेरेद** → **ओपेनेद** → **कलिकेद**

दशबोअरद रेपोरटिङ के लिए इवेंट को टिमे-सेरिएस डेटाबेस या घटना सटरेअम में सटोरे करें: डिलीवरी दरें, ओपेन दरें, और कलिक-थरोउघ दरें प्रति चननेल और नोटिफ़िकशन type।

## चरण 6 - बोटटलेनेकस और ओपटिमिसशनस

| बोटटलेनेक | सोलुशन |
|-----------|----------|
| थिरद-परटय दर सीमाएँ | प्रति परोविदेर कोनटरोललेद थरोउघपुट वाली क्यू |
| बड़े पैमाने पर टेमपलटे रेनदेरिङ | कोममोन टेमपलटेस परे-रेनदेर और कैश करें |
| प्रति संदेश परेफ़ेरेनके लूकुपस | Redis में यूज़र प्राथमिकताएँ कैश करें |
| पीक ट्रैफ़िक सपिकेस | क्वेउए गहराई के आधार पर वोरकेरस औटो-सकले करें |
| करोस-रेगिओन डिलीवरी | परोविदेर एनदपोइनटस के पास वोरकेरस तैनात करें |

<ThinkAboutIt>आप एक ऐसा नोटिफ़िकेशन सिस्टम कैसे डिज़ाइन करेंगे जो बलक फ़रिदय सले के लिए 2 घंटे के अंदर 50 मिलियन वैयक्तिकृत एमैलस भेज सके, और साथ ही रीयल-टाइम सुरक्षा अलेरटस सुब-सेकोनद लेटेंसी के साथ देलिवेर करे?</ThinkAboutIt>
