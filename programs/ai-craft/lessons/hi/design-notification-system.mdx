# नोटिफ़िकशन सिस्टम डिज़ाइन करें - पुश, ईमेल, और SMS बिललिओन बड़े पैमाने पर

आधुनिक ऐप्लिकेशन हर दिन कई channels पर अरबों notifications भेजती हैं। इस system को डिज़ाइन करना आपको message queues, third-party integrations और scale पर failures को सहज ढंग से संभालना सिखाता है।

## चरण 1 - ज़रूरतें समझना

### कार्यात्मक ज़रूरतें
- कई channels support करें: push notifications, email, SMS और in-app
- यूज़र अपनी नोटिफ़िकशन प्राथमिकताएँ कोनफ़िगुरे कर सकें और प्रति चननेल ओपट ओउट कर सकें
- टेम्पलेटेड संदेश के साथ वैयक्तिकरण (जैसे, "Hi {name}, आपका ऑर्डर भेज हो गया है")
- scheduled और immediate notifications का support

### गैर-कार्यात्मक ज़रूरतें
- **Scalability** - 10 million+ notifications प्रतिदिन संभालें
- **Reliability** - कोई notification खो न जाए। At-least-once delivery
- **कम latency** - urgent notifications सेकंडों में deliver हों
- **Extensible** - नए channels (WhatsApp, Slack) आसानी से जोड़ सकें

<ThinkAboutIt>Notification delivery exactly-once होनी चाहिए या at-least-once? Duplicate SMS मिलने के user experience और critical security alert miss होने के बीच trade-off पर सोचिए।</ThinkAboutIt>

## चरण 2 - उच्च-लेवेल आर्किटेक्चर

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

<Illustration src="/images/lessons/design-notification-system.svg" alt="Notification system architecture, जिसमें caller services, notification service, Kafka message queues, channel-specific workers और third-party providers हैं" caption="Message queues notification service को delivery workers से decouple करते हैं, जिससे हर channel independently scale हो सकता है" />

### कोरे कोमपोनेनटस
1. **नोटिफ़िकशन सर्विस** - रिक्वेस्ट वलिदटे करता है, यूज़र प्राथमिकताएँ जाँच करता है, टेमपलटेस रेनदेर करता है, और संदेश एनक्यू करता है
2. **मेसगे क्यूस** - हर चननेल के लिए अलग क्यू ताकि इनदेपेनदेनट स्केलिंग और इसोलशन मिले
3. **Delivery Workers** - channel-specific workers जो third-party API calls संभालते हैं
4. **टेमपलटे सर्विस** - नोटिफ़िकशन टेमपलटेस स्टोर और रेनदेर करता है वरिअबले सुबसटिटुशन के साथ

## चरण 3 - दीप दिवे: मुख्य बात कोमपोनेनटस

### यूज़र परेफ़ेरेनकेस और ओपट-ओउट
हर यूज़र और नोटिफ़िकशन प्रकार के लिए प्राथमिकताएँ स्टोर करें:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

नोटिफ़िकशन सर्विस एनक्यू करने **से पहले** प्राथमिकताएँ जाँच करता है - जो यूज़र नहीं चाहता वो कभी सेनद न करें।

### परिओरिटय क्यूस
सभी notifications बराबर नहीं होतीं। Priority levels इस्तेमाल करें:
- **महत्वपूर्ण** - सुरक्षा अलेरटस, OTP कोदेस → तुरंत प्रोसेस
- **उच्च** - ऑर्डर पुष्टियाँ, पेमेंट रसीदें → सेकंडों में
- **मेदिउम** - सोकिअल इंटरैक्शन, टिप्पणियाँ → मिनटों में ठीक है
- **कम** - मरकेटिङ, अनुशंसाएँ → बैच किया जा सकता है

## चरण 4 - रेलिअबिलिटय और फ़ैलुरे हनदलिङ

### देदुपलिकशन
Duplicate notifications रोकने के लिए idempotency key इस्तेमाल करें। Process करने से पहले जाँचें कि notification ID deduplication store (TTL वाले Redis) में मौजूद है या नहीं:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### रेटरय के साथ एक्सपोनेनटिअल बकोफ़फ़
Third-party services fail होती हैं। बढ़ते delays के साथ retries लागू करें:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### प्रति यूज़र दर लिमिटिङ
यूज़र को नोटिफ़िकशन थकान से बचाएं:
- अधिकतम 3 push notifications प्रति hour प्रति user
- अधिकतम 1 मरकेटिङ ईमेल प्रति दय
- Security notifications rate limits bypass करती हैं

<FunFact>Facebook रोज़ 10 billion से ज़्यादा push notifications भेजता है। इसे संभालने के लिए उन्होंने custom notification pipeline बनाई, जो प्रति सेकंड millions of messages process कर सकती है, iOS (APNs) और Android (FCM) के लिए अलग delivery paths के साथ।</FunFact>

## चरण 5 - Third-Party Integration

| चननेल | परोविदेर | परोटोकोल | चललेङेस |
|---------|----------|----------|------------|
| पुश (इओस) | अपनस | HTTP/2 | टोकेन प्रबंधन, सिलेनट पुश सीमाएँ |
| पुश (अनदरोइद) | FCM | HTTP | टोचुनता-बसेद बरोअदकसटिङ |
| ईमेल | सेनदगरिद/SES | SMTP/API | देलिवेरबिलिटय, स्पैम फ़िल्टर |
| SMS | टविलिओ | REST API | प्रति संदेश लागत, रेगिओनल अनुपालन |
| इन-अपप | WebSocket | WS | कोननेकशन प्रबंधन, ऑफ़लाइन बुफ़फ़ेरिङ |

### विश्लेषण पाइपलाइन
हर संदेश का नोटिफ़िकशन लिफ़ेकयकले रिकॉर्ड करें:
- **करेअटेद** → **क्यूद** → **सेनट** → **देलिवेरेद** → **ओपेनेद** → **कलिकेद**

दशबोअरद रेपोरटिङ के लिए इवेंट को टिमे-सेरिएस डेटाबेस या घटना सटरेअम में स्टोर करें: डिलीवरी दरें, ओपेन दरें, और कलिक-थरोउघ दरें प्रति चननेल और नोटिफ़िकशन प्रकार।

## चरण 6 - Bottlenecks और Optimisations

| बोटटलेनेक | सोलुशन |
|-----------|----------|
| Third-party rate limits | प्रति provider controlled throughput वाली queue |
| बड़े पैमाने पर टेमपलटे रेनदेरिङ | कोममोन टेमपलटेस परे-रेनदेर और कैश करें |
| प्रति संदेश परेफ़ेरेनके लूकुपस | Redis में यूज़र प्राथमिकताएँ कैश करें |
| पीक ट्रैफ़िक सचुनताेस | क्यू गहराई के आधार पर वोरकेरस औटो-सकले करें |
| करोस-रेगिओन डिलीवरी | परोविदेर एनदपोइनटस के पास वोरकेरस तैनात करें |

<ThinkAboutIt>आप एक ऐसा नोटिफ़िकेशन सिस्टम कैसे डिज़ाइन करेंगे जो बलक शुक्रवार सले के लिए 2 घंटे के अंदर 50 मिलियन वैयक्तिकृत ईमेल भेज सके, और साथ ही रीयल-टाइम सुरक्षा अलेरटस सुब-सेकोनद लेटेंसी के साथ देलिवेर करे?</ThinkAboutIt>
