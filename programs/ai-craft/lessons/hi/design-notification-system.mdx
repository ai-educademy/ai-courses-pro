# नोटिफ़िकेशन सिस्टम डिज़ाइन करें - अरबों के स्केल पर पुश, ईमेल और SMS

आधुनिक ऐप्लिकेशन रोज़ कई चैनलों पर अरबों नोटिफ़िकेशन भेजते हैं। ऐसा सिस्टम डिज़ाइन करना आपको message queues, third-party integrations और स्केल पर graceful failure handling सिखाता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- कई चैनलों का समर्थन करें: push notifications, email, SMS और in-app
- उपयोगकर्ता notification preferences कॉन्फ़िगर कर सकें और हर चैनल से opt out कर सकें
- Personalisation के साथ templated messages (जैसे, "Hi {name}, your order shipped")
- Scheduled और immediate notifications का समर्थन

### नॉन-फ़ंक्शनल आवश्यकताएं
- **स्केलेबिलिटी** - रोज़ 10 मिलियन से अधिक notifications संभालें
- **विश्वसनीयता** - कोई notification खोए नहीं। at-least-once delivery
- **कम लेटेंसी** - urgent notifications सेकंडों में डिलीवर हों
- **विस्तार योग्य** - नए चैनल (WhatsApp, Slack) जोड़ना आसान हो

<ThinkAboutIt>Notification delivery exactly-once होनी चाहिए या at-least-once? Duplicate SMS मिलने बनाम critical security alert छूटने के उपयोगकर्ता अनुभव पर विचार करें।</ThinkAboutIt>

## चरण 2 - उच्च-स्तरीय आर्किटेक्चर

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

<Illustration src="/images/lessons/design-notification-system.svg" alt="Caller services, notification service, Kafka message queues, channel-specific workers और third-party providers वाला notification system architecture" caption="Message queues notification service को delivery workers से अलग करते हैं, जिससे हर channel स्वतंत्र रूप से scale हो सकता है" />

### मुख्य घटक
1. **Notification Service** - requests validate करता है, user preferences जांचता है, templates render करता है और messages enqueue करता है
2. **Message Queues** - स्वतंत्र scaling और isolation के लिए हर channel की अलग queue
3. **Delivery Workers** - channel-specific workers जो third-party API calls संभालते हैं
4. **Template Service** - variable substitution के साथ notification templates store और render करता है

## चरण 3 - डीप डाइव: मुख्य घटक

### User Preferences और Opt-Out
Preferences को हर उपयोगकर्ता और notification type के लिए store करें:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

Notification service enqueue करने से **पहले** preferences जांचती है। जो उपयोगकर्ता नहीं चाहता, उसे कभी न भेजें।

### Priority Queues
सभी notifications समान नहीं होते। Priority levels इस्तेमाल करें:
- **Critical** - security alerts, OTP codes → तुरंत processed
- **High** - order confirmations, payment receipts → सेकंडों में
- **Medium** - social interactions, comments → मिनट स्वीकार्य
- **Low** - marketing, recommendations → batch किए जा सकते हैं

## चरण 4 - विश्वसनीयता और विफलता संभालना

### Deduplication
Idempotency key से duplicate notifications रोकें। Processing से पहले जांचें कि notification ID deduplication store (TTL के साथ Redis) में मौजूद है या नहीं:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### Exponential Backoff के साथ Retry
Third-party सेवाएं विफल होती हैं। बढ़ते delay के साथ retries लागू करें:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### हर उपयोगकर्ता पर Rate Limiting
उपयोगकर्ताओं को notification fatigue से बचाएं:
- हर उपयोगकर्ता को अधिकतम 3 push notifications प्रति घंटा
- अधिकतम 1 marketing email प्रति दिन
- Security notifications rate limits को bypass करते हैं

<FunFact>Facebook रोज़ 10 बिलियन से अधिक push notifications भेजता है। इसे संभालने के लिए उन्होंने custom notification pipeline बनाई जो iOS (APNs) और Android (FCM) के लिए अलग delivery paths के साथ प्रति सेकंड लाखों messages process कर सकती है।</FunFact>

## चरण 5 - Third-Party Integration

| Channel | Provider | Protocol | Challenges |
|---------|----------|----------|------------|
| Push (iOS) | APNs | HTTP/2 | Token management, silent push limits |
| Push (Android) | FCM | HTTP | Topic-based broadcasting |
| Email | SendGrid/SES | SMTP/API | Deliverability, spam filters |
| SMS | Twilio | REST API | Cost per message, regional compliance |
| In-App | WebSocket | WS | Connection management, offline buffering |

### Analytics Pipeline
हर message के notification lifecycle को track करें:
- **Created** → **Queued** → **Sent** → **Delivered** → **Opened** → **Clicked**

Dashboard reporting के लिए events को time-series database या event stream में store करें: हर channel और notification type के लिए delivery rates, open rates और click-through rates।

## चरण 6 - बाधाएं और ऑप्टिमाइज़ेशन

| बाधा | समाधान |
|-----------|----------|
| Third-party rate limits | हर provider के लिए controlled throughput वाली queue |
| Scale पर template rendering | Common templates को pre-render और cache करें |
| हर message पर preference lookups | Redis में user preferences cache करें |
| Peak traffic spikes | Queue depth के आधार पर workers auto-scale करें |
| Cross-region delivery | Workers को provider endpoints के पास deploy करें |

<ThinkAboutIt>आप ऐसा notification system कैसे डिज़ाइन करेंगे जो Black Friday sale के लिए 2 घंटे की window में 50 मिलियन personalised emails भेज सके, और फिर भी real-time security alerts को sub-second latency के साथ deliver करे?</ThinkAboutIt>
