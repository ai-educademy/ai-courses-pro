# नोटिफ़िकेशन सिस्टम डिज़ाइन करें - अरबों के स्केल पर पुश, ईमेल और SMS

आधुनिक ऐप्लिकेशन रोज़ कई चैनलों पर अरबों नोटिफ़िकेशन भेजते हैं। ऐसा सिस्टम डिज़ाइन करना आपको संदेश क्यू, थर्ड-पार्टी integrations और स्केल पर graceful विफलता handling सिखाता है।

## चरण 1 - आवश्यकताएं इकट्ठी करना

### फ़ंक्शनल आवश्यकताएं
- कई चैनलों का समर्थन करें: पुश नोटिफ़िकेशन, ईमेल, SMS और इन-ऐप
- उपयोगकर्ता नोटिफ़िकेशन पसंद कॉन्फ़िगर कर सकें और हर चैनल से opt out कर सकें
- Personalisation के साथ templated संदेश (जैसे, "Hi {name}, आपके order shipped")
- Scheduled और immediate नोटिफ़िकेशन का समर्थन

### नॉन-फ़ंक्शनल आवश्यकताएं
- **स्केलेबिलिटी** - रोज़ 10 मिलियन से अधिक नोटिफ़िकेशन संभालें
- **विश्वसनीयता** - कोई नोटिफ़िकेशन खोए नहीं। at-least-once डिलीवरी
- **कम लेटेंसी** - urgent नोटिफ़िकेशन सेकंडों में डिलीवर हों
- **विस्तार योग्य** - नए चैनल (WhatsApp, Slack) जोड़ना आसान हो

<ThinkAboutIt>नोटिफ़िकेशन डिलीवरी exactly-once होनी चाहिए या at-least-once? Duplicate SMS मिलने बनाम critical सुरक्षा अलर्ट छूटने के उपयोगकर्ता अनुभव पर विचार करें।</ThinkAboutIt>

## चरण 2 - उच्च-स्तरीय आर्किटेक्चर

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### मुख्य घटक
1. **नोटिफ़िकेशन सेवा** - अनुरोध validate करता है, उपयोगकर्ता पसंद जांचता है, टेम्पलेट रेंडर करता है और संदेश एनक्यू करता है
2. **संदेश Queues** - स्वतंत्र स्केलिंग और अलगाव के लिए हर चैनल की अलग क्यू
3. **डिलीवरी Workers** - चैनल-विशिष्ट वर्कर जो थर्ड-पार्टी API calls संभालते हैं
4. **Template सेवा** - variable substitution के साथ नोटिफ़िकेशन टेम्पलेट स्टोर और रेंडर करता है

## चरण 3 - डीप डाइव: मुख्य घटक

### उपयोगकर्ता Preferences और Opt-Out
Preferences को हर उपयोगकर्ता और नोटिफ़िकेशन प्रकार के लिए स्टोर करें:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

नोटिफ़िकेशन सेवा एनक्यू करने से **पहले** पसंद जांचती है। जो उपयोगकर्ता नहीं चाहता, उसे कभी न भेजें।

### प्राथमिकता Queues
सभी नोटिफ़िकेशन समान नहीं होते। प्राथमिकता स्तर इस्तेमाल करें:
- **Critical** - सुरक्षा अलर्ट, OTP codes → तुरंत processed
- **High** - order confirmations, payment receipts → सेकंडों में
- **Medium** - social interactions, comments → मिनट स्वीकार्य
- **Low** - मार्केटिंग, रिकमेंडेशन → बैच किए जा सकते हैं

## चरण 4 - विश्वसनीयता और विफलता संभालना

### डीडुप्लिकेशन
Idempotency कुंजी से डुप्लिकेट नोटिफ़िकेशन रोकें। प्रोसेसिंग से पहले जांचें कि नोटिफ़िकेशन ID डीडुप्लिकेशन स्टोर (TTL के साथ Redis) में मौजूद है या नहीं:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### Exponential Backoff के साथ Retry
थर्ड-पार्टी सेवाएं विफल होती हैं। बढ़ते देरी के साथ रीट्राई लागू करें:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### हर उपयोगकर्ता पर रेट Limiting
उपयोगकर्ताओं को नोटिफ़िकेशन fatigue से बचाएं:
- हर उपयोगकर्ता को अधिकतम 3 पुश नोटिफ़िकेशन प्रति घंटा
- अधिकतम 1 मार्केटिंग ईमेल प्रति दिन
- सुरक्षा नोटिफ़िकेशन रेट लिमिट को bypass करते हैं

<FunFact>Facebook रोज़ 10 बिलियन से अधिक पुश नोटिफ़िकेशन भेजता है। इसे संभालने के लिए उन्होंने कस्टम नोटिफ़िकेशन पाइपलाइन बनाई जो iOS (APNs) और Android (FCM) के लिए अलग डिलीवरी पथ के साथ प्रति सेकंड लाखों संदेश प्रोसेस कर सकती है।</FunFact>

## चरण 5 - Third-Party Integration

| चैनल | Provider | Protocol | Challenges |
|---------|----------|----------|------------|
| पुश (iOS) | APNs | HTTP/2 | Token प्रबंधन, silent पुश लिमिट |
| पुश (Android) | FCM | HTTP | Topic-आधारित broadcasting |
| ईमेल | SendGrid/SES | SMTP/API | Deliverability, spam फ़िल्टर |
| SMS | Twilio | REST API | Cost per संदेश, क्षेत्रीय compliance |
| In-App | WebSocket | WS | Connection प्रबंधन, offline buffering |

### Analytics पाइपलाइन
हर संदेश के नोटिफ़िकेशन lifecycle को ट्रैक करें:
- **Created** → **Queued** → **Sent** → **Delivered** → **Opened** → **Clicked**

Dashboard reporting के लिए इवेंट को टाइम-सीरीज़ डेटाबेस या इवेंट स्ट्रीम में स्टोर करें: हर चैनल और नोटिफ़िकेशन प्रकार के लिए डिलीवरी दरें, open दरें और click-through दरें।

## चरण 6 - बाधाएं और ऑप्टिमाइज़ेशन

| बाधा | समाधान |
|-----------|----------|
| थर्ड-पार्टी रेट लिमिट | हर प्रोवाइडर के लिए controlled थ्रूपुट वाली क्यू |
| स्केल पर टेम्पलेट rendering | Common टेम्पलेट को pre-रेंडर और कैश करें |
| हर संदेश पर पसंद खोज | Redis में उपयोगकर्ता पसंद कैश करें |
| Peak ट्रैफ़िक spikes | क्यू गहराई के आधार पर वर्कर auto-स्केल करें |
| Cross-रीजन डिलीवरी | Workers को प्रोवाइडर endpoints के पास deploy करें |

<ThinkAboutIt>आप ऐसा नोटिफ़िकेशन सिस्टम कैसे डिज़ाइन करेंगे जो Black Friday सेल के लिए 2 घंटे की विंडो में 50 मिलियन personalised emails भेज सके, और फिर भी रीयल-टाइम सुरक्षा अलर्ट को sub-सेकंड लेटेंसी के साथ deliver करे?</ThinkAboutIt>
