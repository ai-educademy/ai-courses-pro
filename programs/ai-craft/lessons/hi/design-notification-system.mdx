# नोटिफ़िकेशन सिस्टम डिज़ाइन करें - पुश, ईमेल, और SMS बिलियन बड़े पैमाने पर

आधुनिक ऐप्लिकेशन हर दिन अरबों नोटिफ़िकेशन भेजती हैं, वो भी कई चैनलस पर। इस सिस्टम को डिज़ाइन करना आपको संदेश क्यू, थिरद-पार्टी इंटीग्रेशनस, और स्केल पर विफलताएँ को सुचारु ढंग से संभाल करना सिखाता है।

## चरण 1 - ज़रूरतें समझना

### कार्यात्मक ज़रूरतें
- मुलटिपले चैनलस सपोर्ट करें: पुश नोटिफ़िकेशन, ईमेल, SMS, और इन-अपप
- यूज़र अपनी नोटिफ़िकेशन प्राथमिकताएँ कोनफ़िगुरे कर सकें और प्रति चैनल ओपट ओउट कर सकें
- टेम्पलेटेड संदेश के साथ वैयक्तिकरण (जैसे, "Hi {name}, आपका ऑर्डर भेज हो गया है")
- सचेदुलेद और इममेदिअटे नोटिफ़िकेशन का सपोर्ट

### गैर-कार्यात्मक ज़रूरतें
- **स्केलेबिलिटी** - 10 मिलियन+ नोटिफ़िकेशन प्रतिदिन संभालें
- **रेलिअबिलिटय** - कोई नोटिफ़िकेशन खोनाट न हो; अट-least-ओनके डिलीवरी
- **कम लेटेंसी** - उरगेनट नोटिफ़िकेशन सेकंडों में देलिवेर हों
- **एक्सटेनसिबले** - नए चैनलस (WhatsApp, Slack) आसानी से जोड़ें करें

<ThinkAboutIt>नोटिफ़िकेशन डिलीवरी ठीक-ठीक-ओनके होनी चाहिए या अट-least-ओनके? सोचिए - डुप्लिकेट SMS मिलने का अनुभव बनाम एक महत्वपूर्ण सुरक्षा अलेरट मिस हो जाने का।</ThinkAboutIt>

## चरण 2 - उच्च-level आर्किटेक्चर

```
Caller Services → Notification Service → Validation + Preference Check
                                              ↓
                                    Message Queue (Kafka)
                                    ↓       ↓       ↓       ↓
                                 Push    Email    SMS    In-App
                                Worker   Worker  Worker  Worker
                                  ↓        ↓       ↓       ↓
                                 FCM   SendGrid  Twilio  WebSocket
```

### कोरे कोमपोनेनटस
1. **नोटिफ़िकेशन सर्विस** - रिक्वेस्ट वलिदटे करता है, यूज़र प्राथमिकताएँ जाँच करता है, टेमपलटेस रेनदेर करता है, और संदेश एनक्यू करता है
2. **संदेश क्यूस** - हर चैनल के लिए अलग क्यू ताकि इनदेपेनदेनट स्केलिंग और इसोलशन मिले
3. **देलिवेरय वोरकेरस** - चैनल-विशिष्ट वोरकेरस जो थिरद-पार्टी API कॉल संभाल करते हैं
4. **टेमपलटे सर्विस** - नोटिफ़िकेशन टेमपलटेस स्टोर और रेनदेर करता है वरिअबले सुबसटिटुशन के साथ

## चरण 3 - दीप दिवे: मुख्य बात कोमपोनेनटस

### यूज़र परेफ़ेरेनकेस और ओपट-ओउट
हर यूज़र और नोटिफ़िकेशन प्रकार के लिए प्राथमिकताएँ स्टोर करें:

```
user_preferences:
  user_id: "u123"
  channels:
    email: { enabled: true, quiet_hours: "22:00-08:00" }
    push: { enabled: true }
    sms: { enabled: false }
  categories:
    marketing: { enabled: false }
    security: { enabled: true, override_quiet_hours: true }
```

नोटिफ़िकेशन सर्विस एनक्यू करने **से पहले** प्राथमिकताएँ जाँच करता है - जो यूज़र नहीं चाहता वो कभी सेनद न करें।

### परिओरिटय क्यूस
सभी नोटिफ़िकेशन एक्वल नहीं होतीं। परिओरिटय levelस इस्तेमाल करें:
- **महत्वपूर्ण** - सुरक्षा अलेरटस, OTP कोदेस → तुरंत प्रोसेस
- **उच्च** - ऑर्डर पुष्टियाँ, पेमेंट रसीदें → सेकंडों में
- **मेदिउम** - सामाजिक इंटरैक्शन, टिप्पणियाँ → मिनटों में ठीक है
- **कम** - मरकेटिङ, अनुशंसाएँ → बैच किया जा सकता है

## चरण 4 - रेलिअबिलिटय और फ़ैलुरे हनदलिङ

### डीडुप्लिकेशन
डुप्लिकेट नोटिफ़िकेशन रोकने के लिए इडेम्पोटेंसी key इस्तेमाल करें। परोकेस करने से पहले जाँच करें कि नोटिफ़िकेशन ID डीडुप्लिकेशन स्टोर (Redis के साथ TTL) में मौजूद करती है या नहीं:

```
Key: "dedup:{notification_id}" → TTL: 24 hours
If key exists → skip (already sent)
If not → process and set key
```

### रीट्राई के साथ एक्सपोनेनटिअल बकोफ़फ़
थिरद-पार्टी सेवाएँ फ़ेल होती हैं। एजे देलयस के साथ रेटरिएस लागू करें:

```
Attempt 1: immediate
Attempt 2: wait 1 second
Attempt 3: wait 4 seconds
Attempt 4: wait 16 seconds
Attempt 5: move to dead-letter queue
```

### प्रति यूज़र दर लिमिटिंग
यूज़र को नोटिफ़िकेशन थकान से बचाएं:
- अधिकतम 3 पुश नोटिफ़िकेशन प्रति होउर प्रति यूज़र
- अधिकतम 1 मरकेटिङ ईमेल प्रति दय
- सुरक्षा नोटिफ़िकेशन दर सीमाएँ बाइपास करती हैं

<FunFact>फ़केबूक रोज़ 10 बिलियन से ज़्यादा पुश नोटिफ़िकेशन भेजता है। इसके लिए उन्होंने एक कस्टम नोटिफ़िकेशन पाइपलाइन बनाया जो प्रति सेकंड मिलियन of संदेश प्रोसेस कर सकता है, iOS (अपनस) और अनदरोइद (FCM) के लिए अलग डिलीवरी रास्ते के साथ।</FunFact>

## चरण 5 - थिरद-पार्टी इंटीग्रेशन

| चैनल | प्रदाता | प्रोटोकॉल | चुनौतियाँ |
|---------|----------|----------|------------|
| पुश (iOS) | अपनस | HTTP/2 | टोकेन प्रबंधन, सिलेनट पुश सीमाएँ |
| पुश (अनदरोइद) | FCM | HTTP | टोचुनता-आधारित ब्रॉडकास्टिङ |
| ईमेल | सेनदगरिद/SES | SMTP/API | देलिवेरबिलिटय, स्पैम फ़िल्टर |
| SMS | टविलिओ | REST API | प्रति संदेश लागत, रेगिओनल अनुपालन |
| इन-अपप | WebSocket | WS | कनेक्शन प्रबंधन, ऑफ़लाइन बफ़रिङ |

### विश्लेषण पाइपलाइन
हर संदेश का नोटिफ़िकेशन लिफ़ेकयकले रिकॉर्ड करें:
- **करेअटेद** → **क्यूद** → **सेनट** → **देलिवेरेद** → **ओपेनेद** → **क्लिकेद**

डैशबोर्ड रेपोरटिङ के लिए इवेंट को टिमे-series डेटाबेस या घटना स्ट्रीम में स्टोर करें: डिलीवरी दरें, ओपेन दरें, और क्लिक-थ्रू दरें प्रति चैनल और नोटिफ़िकेशन प्रकार।

## चरण 6 - बॉटलनेक और ऑप्टिमाइज़ेशन

| बोTTLेनेक | सोलुशन |
|-----------|----------|
| थिरद-पार्टी दर सीमाएँ | प्रति प्रदाता नियंत्रित थ्रूपुट वाली क्यू |
| बड़े पैमाने पर टेमपलटे रेनदेरिङ | कोममोन टेमपलटेस परे-रेनदेर और कैश करें |
| प्रति संदेश परेफ़ेरेनके लूकुपस | Redis में यूज़र प्राथमिकताएँ कैश करें |
| पीक ट्रैफ़िक स्पाइक | क्यू गहराई के आधार पर वोरकेरस ऑटो-स्केल करें |
| करोस-रेगिओन डिलीवरी | प्रदाता एनदपोइनटस के पास वोरकेरस तैनात करें |
