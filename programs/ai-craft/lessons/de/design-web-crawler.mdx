# Entwerfen Sie einen Webcrawler - So indiziert Google das Internet

Ein Webcrawler durchsucht systematisch das Internet, um Webseiten herunterzuladen und zu indizieren. Es ist die Grundlage jeder Suchmaschine, und wenn Sie eine solche entwerfen, lernen Sie etwas über verteilte Systeme, das Durchlaufen von Graphen und den Umgang mit der Unordnung im echten Web.

## Schritt 1 - Anforderungserfassung

### Funktionale Anforderungen
- Crawlen Sie Webseiten ausgehend von einer Reihe von Start-URLs
- Extrahieren und folgen Sie Hyperlinks, um neue Seiten zu entdecken
- Speichern Sie heruntergeladene Inhalte zur Indizierung und Verarbeitung
- Respektieren Sie die robots.txt-Datei und die Höflichkeitsregeln für Crawler

### Nichtfunktionale Anforderungen
- **Skalierung** - 1 Milliarde Seiten pro Monat crawlen
- **Höflichkeit** - Überfordern Sie niemals einen einzelnen Webserver
- **Aktivität** - Durchsuchen Sie wichtige Seiten regelmäßig erneut
- **Robustheit** - Umgang mit fehlerhaftem HTML, Endlosschleifen und Spinnenfallen

## Schritt 2 - High-Level-Architektur

```
Seed URLs → URL Frontier (priority queue)
                  ↓
            URL Scheduler (politeness + priority)
                  ↓
         Fetcher (HTTP client pool)
                  ↓
         HTML Parser → Extract URLs → URL Filter
              ↓                           ↓
       Content Store              URL Dedup (Bloom Filter)
       (S3 / HDFS)                      ↓
                                 URL Frontier (loop)
```

## Schritt 3 - Die Crawl-Schleife

### BFS vs. DFS Crawling
- **BFS (Breadth-First)** - bevorzugt für Web-Crawling. Erkennt schnell eine breite Palette von Domänen und vermeidet, sich tief in einer einzelnen Site festzuklammern
- **DFS (Depth-First)** - riskiert, unendlich tief in dynamisch generierte Seiten einzudringen, bevor andere Domänen entdeckt werden

### URL Spitzen Design
Die Grenze ist keine einfache Warteschlange - es ist ein ausgeklügeltes Prioritätssystem mit zwei Unterkomponenten:

1. **Prioritätswarteschlange (vorne)** - ordnet URLs nach Wichtigkeit. Zu den Faktoren gehören PageRank, Aktualisierungshäufigkeit und Domänenautorität
2. **Höflichkeitswarteschlange (zurück)** - stellt sicher, dass jede Domäne über eine eigene FIFO-Warteschlange verfügt. Ein Scheduler wählt aus verschiedenen Domänenwarteschlangen aus, um zu vermeiden, dass ein einzelner Server überlastet wird

```
Front (Priority):       Back (Politeness):
┌──────────────┐       ┌─── bbc.co.uk queue ───┐
│ High Priority │ ───→  │ url1 → url4 → url7    │
│ Med Priority  │ ───→  ├─── github.com queue ──┤
│ Low Priority  │ ───→  │ url2 → url5 → url8    │
└──────────────┘       ├─── wikipedia.org queue ┤
                        │ url3 → url6 → url9    │
                        └───────────────────────┘
```

## Schritt 4 - Höflichkeit und Robots.txt

### Respekt vor Robots.txt
Bevor Sie eine Domain crawlen, rufen Sie deren `robots.txt`-Datei ab und speichern Sie sie im Cache:

```
# Example robots.txt
User-agent: *
Disallow: /admin/
Disallow: /private/
Crawl-delay: 2
```

Zwischenspeichern von robots.txt pro Domain mit einer TTL (24 Stunden). Befolgen Sie stets die `Disallow`-Regeln und `Crawl-delay`-Anweisungen.

### Begrenzung der Crawling-Rate
Behalten Sie auch ohne explizites `Crawl-delay` Höflichkeit bei:
- Maximal 1 Anfrage pro Sekunde pro Domain (konfigurierbar)
- Verwenden Sie separate Download-Warteschlangen pro Domain
- Verfolgen Sie die Reaktionszeiten. Wenn ein Server langsamer wird, schalten Sie ihn automatisch ab

<FunFact>Der Webcrawler von Google (Googlebot) crawlt Hunderte Milliarden Seiten. Der Höflichkeit halber muss man sagen, dass es die Antwortzeiten des Servers überwacht und die Crawling-Rate reduziert, wenn eine Website beginnt, langsam zu reagieren - wodurch die Website effektiv gegen den Crawler „zurückdrängen“ kann.</FunFact>

## Schritt 5 - Deduplizierung

### URL-Deduplizierung (Bloom-Filter)
Bei Milliarden von URLs erfordert die Überprüfung, ob eine URL schon einmal gesehen wurde, eine effiziente Datenstruktur. Ein Bloom-Filter bietet O(1)-Suchvorgänge mit geringem Speicherbedarf:

- **Speicherplatz:** ~1 GB für 1 Milliarde URLs bei 1 % Falsch-Positiv-Rate
- **Kompromiss:** Eine Seite wird gelegentlich erneut gecrawlt (falsch-positive Ergebnisse), es wird jedoch nie eine neue URL übersehen (keine falsch-negativen Ergebnisse).

Normalisieren Sie URLs vor der Prüfung: Entfernen Sie Fragmente (#), sortieren Sie Abfrageparameter, schreiben Sie den Hostnamen in Kleinbuchstaben und lösen Sie relative Pfade auf.

### Inhaltsdeduplizierung (SimHash)
Verschiedene URLs können identische Inhalte (Spiegel, kopierte Artikel) bereitstellen. SimHash generiert einen Fingerabdruck des Seiteninhalts - Seiten mit ähnlichen Fingerabdrücken (kleiner Hamming-Abstand) sind wahrscheinlich Duplikate:

```
Page A content → SimHash → 10110010...
Page B content → SimHash → 10110011...
Hamming distance = 1 → likely duplicate, skip storing
```

## Schritt 6 - Verteiltes Crawling

### Horizontale Skalierung
Eine einzelne Maschine kann nicht monatlich eine Milliarde Seiten crawlen. Verteilen Sie die Arbeit:

- **Konsistentes Hashing** für Domänennamen weist jede Domäne einem bestimmten Crawler-Knoten zu. Dies sorgt für Höflichkeit - nur ein Knoten crawlt eine bestimmte Domain
- **URL-Grenze** wird basierend auf dem Hash-Ring über Knoten verteilt
- **Koordination** über einen einfachen Dienst, der Knotenzuweisungen verwaltet und neu ausbalanciert, wenn Knoten beitreten oder gehen

### DNS-Auflösungs-Caching
DNS-Lookups fügen 10-100 ms pro Anfrage hinzu. Im Maßstab stellt dies einen großen Engpass dar:
- Pflegen Sie einen lokalen DNS-Cache pro Crawler-Knoten
- Batch-DNS-Vorauflösung für URLs in der Warteschlange
- Verwenden Sie einen dedizierten DNS-Resolver, um eine Überlastung öffentlicher DNS-Server zu vermeiden

### Spinnenfallenerkennung
Schädliche oder schlecht erstellte Websites können unendlich viele URL-Bereiche erzeugen:
- `/page/1/page/1/page/1/...` - sich wiederholende Pfadmuster
- Kalenderseiten, die URLs für jedes zukünftige Datum generieren
- Sitzungs-IDs in URLs, die eindeutige URLs für identische Inhalte erstellen

**Schutzmaßnahmen:** maximale URL-Länge, maximale Crawling-Tiefe pro Domain, Mustererkennung für sich wiederholende URL-Strukturen und Seitenanzahlbegrenzungen auf Domain-Ebene.

Stellen Sie sich eine Nachrichtenseite vor, die stündlich aktualisiert wird, im Vergleich zu einem Wikipedia-Artikel, der sich monatlich ändert. Welche Signale würden Sie verwenden, um die Planung des erneuten Crawlens zu priorisieren?</ThinkAboutIt>

## Schritt 7 - Engpässe und Optimierungen

| Engpass | Lösung |
|-----------|----------|
| Latenz der DNS-Auflösung | Lokaler DNS-Cache, Batch-Vorauflösung |
| Langsame/nicht reagierende Server | Zeitüberschreitungen (30 s), asynchrone E/A, Überspringen nach Wiederholungsversuchen |
| Speicher für gecrawlte Inhalte | Seiten komprimieren, nur geänderte Inhalte speichern |
| URL-Grenzspeicher | Festplattengestützte Prioritätswarteschlange (RocksDB) |
| Doppelter Inhalt | SimHash-Fingerprinting, kanonische URL-Erkennung |

<ThinkAboutIt>Suchmaschinen müssen die Crawl-Aktualität (häufiges erneutes Crawlen von Seiten) mit der Entdeckung (das Finden neuer Seiten) in Einklang bringen. Wenn Ihr Crawler über ein festes Budget von 1 Million Seiten pro Tag verfügt, wie würden Sie dieses Budget zwischen dem erneuten Crawlen vorhandener Seiten und dem Entdecken neuer Seiten aufteilen?</ThinkAboutIt>
