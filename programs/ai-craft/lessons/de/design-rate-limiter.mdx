# Entwerfen Sie einen Ratenbegrenzer – Schutz von APIs im großen Maßstab

Ratenbegrenzung ist eines der praktischsten Systemdesignthemen. Jede Produktions-API – von GitHub bis Stripe – verlässt sich darauf, um Missbrauch zu verhindern, eine faire Nutzung sicherzustellen und Backend-Dienste vor einer Überlastung zu schützen.

## Schritt 1 – Anforderungserfassung

### Funktionale Anforderungen
- Begrenzen Sie Anfragen basierend auf konfigurierbaren Regeln (pro Benutzer, IP oder API-Schlüssel).
- Geben Sie eine klare Rückmeldung zurück, wenn ein Client gedrosselt ist (HTTP 429)
- Unterstützen Sie mehrere Ratenbegrenzungsregeln gleichzeitig

### Nichtfunktionale Anforderungen
- **Geringe Latenz** – der Limiter darf keinen nennenswerten Overhead verursachen
- **Verteilt** – funktioniert auf mehreren Servern
- **Fehlertolerant** – wenn der Begrenzer ausfällt, sollte der Datenverkehr weiterhin fließen (Fail-Open)

## Schritt 2 – Ratenbegrenzungsalgorithmen

### Fensterzähler behoben
Teilen Sie die Zeit in feste Fenster ein (z. B. 60-Sekunden-Intervalle). Erhöhen Sie einen Zähler pro Anfrage. An Fenstergrenzen zurücksetzen. **Problem:** Burst-Verkehr an Fensterrändern kann das Zweifache des Grenzwerts zulassen.

### Schiebefensterprotokoll
Speichern Sie den Zeitstempel jeder Anfrage. Zählen Sie Einträge im nachfolgenden Fenster. Präzise, ​​aber **speicherintensiv** – die Speicherung jedes Zeitstempels ist bei großem Maßstab teuer.

### Schiebefenstertheke
Ein Hybrid: Kombinieren Sie die aktuelle Fensteranzahl mit einem gewichteten Teil des vorherigen Fensters. Gleicht Genauigkeit und Speichereffizienz aus.

### Token-Bucket-Algorithmus (am beliebtesten)
Ein Bucket fasst Token bis zu einer maximalen Kapazität. Token werden zu einem festen Preis hinzugefügt. Jede Anfrage verbraucht ein Token. Wenn der Bucket leer ist, wird die Anfrage abgelehnt.

```
Bucket: capacity=10, refill_rate=2/sec

Time 0s: [🪙🪙🪙🪙🪙🪙🪙🪙🪙🪙] → 10 tokens
Burst of 8 requests → [🪙🪙] → 2 tokens remain
Time 1s: refill +2 → [🪙🪙🪙🪙] → 4 tokens
```

### Algorithmusvergleich

| Algorithmus | Erinnerung | Genauigkeit | Burst-Handhabung |
|-----------|--------|----------|----------------|
| Festes Fenster | Niedrig | Niedrig (Kantenausbrüche) | Schlecht |
| Schiebeprotokoll | Hoch | Genau | Gut |
| Schiebetheke | Mittel | Ungefähr | Gut |
| Token-Eimer | Niedrig | Gut | Ausgezeichnet |

## Schritt 3 – High-Level-Architektur

```
Client → API Gateway (Rate Limiter Middleware) → Backend Services
                    ↕
              Redis Cluster
         (counters + token buckets)
```

<Illustration src="/images/lessons/design-rate-limiter.svg" alt="Ratenbegrenzer-Architektur mit Darstellung von Clients, API-Gateway mit ratenbegrenzender Middleware, Redis-Cluster für verteilten Zustand und Backend-Dienste" caption="Der Ratenbegrenzer befindet sich im API-Gateway und verwendet Redis für die verteilte Zählerspeicherung" />

### Wo soll der Geschwindigkeitsbegrenzer platziert werden?
- **Client-seitig** – leicht zu fälschen, unzuverlässig
- **Serverseitig** – nur pro Instanz, nicht skalierbar
- **API Gateway / Middleware** – der beste Ansatz für verteilte Systeme; zentralisierte Durchsetzung über alle Instanzen hinweg

## Schritt 4 – Tiefer Einblick: Verteilte Ratenbegrenzung

### Redis + Lua-Skripte
In einem verteilten Setup müssen mehrere Server den Ratenbegrenzungsstatus teilen. Redis ist aufgrund seiner atomaren Operationen und der Latenz von weniger als einer Millisekunde die Standardwahl.

Ein Lua-Skript stellt die Atomizität sicher – die Prüfung und Dekrementierung erfolgt in einem einzigen Redis-Vorgang und verhindert so Race-Bedingungen:

```
-- Token Bucket in Redis (pseudocode)
local tokens = redis.call('GET', key)
local last_refill = redis.call('GET', key..':time')
-- Calculate tokens to add based on elapsed time
-- If tokens > 0: decrement and ALLOW
-- Else: DENY
```

### Antwortheader
Gut konzipierte Ratenbegrenzer übermitteln den Status an die Kunden:
- `X-RateLimit-Limit: 100` – maximale Anfragen pro Fenster
- `X-RateLimit-Remaining: 42` – Anfragen übrig
- `X-RateLimit-Reset: 1672531200` – UTC-Epoche, wenn das Fenster zurückgesetzt wird
- HTTP `429 Too Many Requests` mit einem `Retry-After`-Header

## Schritt 5 – Umgang mit Randfällen

### Rennbedingungen
Ohne atomare Operationen können gleichzeitige Anforderungen Beschränkungen umgehen. Lösungen: Redis Lua-Skripte oder Redis `MULTI/EXEC`-Transaktionen.

### Ratenbegrenzende Abmessungen
Wenden Sie Grenzwerte auf mehreren Ebenen gleichzeitig an:
- **Pro Benutzer** – 100 Anfragen/Minute für authentifizierte Benutzer
- **Pro IP** – 50 Anfragen/Minute für anonymen Datenverkehr
- **Pro API-Schlüssel** – abgestufte Pläne (kostenlos: 10/Min., Pro: 1000/Min.)

### Distributed Clock Skew
Server können leicht unterschiedliche Uhren haben. Nutzen Sie die Redis-Serverzeit als einzige Quelle der Wahrheit, anstatt sich auf Zeitstempel des Anwendungsservers zu verlassen.

<FunFact>Die REST-API von GitHub ermöglicht 5.000 Anfragen pro Stunde für authentifizierte Benutzer, aber nur 60 pro Stunde für nicht authentifizierte Anfragen. Stripe verwendet einen Schiebefenster-Ansatz mit separaten Grenzwerten für Live- und Testmodus-API-Schlüssel.</FunFact>

## Schritt 6 – Engpässe und Optimierungen

| Engpass | Lösung |
|-----------|----------|
| Redis Single Point of Failure | Redis-Cluster mit Replikation |
| Netzwerklatenz zu Redis | Lokaler In-Memory-Cache mit regelmäßiger Synchronisierung |
| Hotkeys (beliebte API-Schlüssel) | Shard über mehrere Redis-Knoten |
| Regelauswertungsaufwand | Vorkompilierungsregeln, Cache-Konfigurationen |
