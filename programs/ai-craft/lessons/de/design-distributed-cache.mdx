# Entwerfen Sie einen verteilten Cache – Redis-Architektur von Grund auf

Caching ist die effektivste Technik zur Verbesserung der Systemleistung. Ein gut konzipierter verteilter Cache kann die Datenbanklast um über 90 % reduzieren und die Antwortzeiten von Hunderten von Millisekunden auf weniger als eine Millisekunde verkürzen.

## Schritt 1 – Anforderungserfassung

### Funktionale Anforderungen
- Speichern Sie Schlüssel-Wert-Paare mit optionaler TTL (Time-to-Live).
- Unterstützt allgemeine Vorgänge: GET, SET, DELETE und Massenvorgänge
- Verteilen Sie Daten zur horizontalen Skalierung auf mehrere Knoten

### Nichtfunktionale Anforderungen
- **Geringe Latenz** – Lesevorgänge für Cache-Treffer im Submillisekundenbereich
- **Hoher Durchsatz** – 100.000+ Vorgänge pro Sekunde und Knoten
- **Hohe Verfügbarkeit** – Cache-Fehler sollten das System nicht zum Absturz bringen
- **Skalierbarkeit** – Knoten ohne Ausfallzeit hinzufügen

### Wann zwischengespeichert werden soll
- **Leselastige Arbeitslast** – wenn die Zahl der Lesevorgänge die Zahl der Schreibvorgänge bei weitem übersteigt
– **Teure Berechnungen** – Ergebnisse der ML-Modellinferenz, komplexe Aggregationen
- **Daten, auf die häufig zugegriffen wird** – Benutzersitzungen, Produktkataloge, Konfiguration

## Schritt 2 – Caching-Strategien

### Cache-Aside (Lazy Loading)
Das häufigste Muster. Die Anwendung überprüft zuerst den Cache. Bei einem Fehlschlag liest es aus der Datenbank und füllt dann den Cache:

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**Vorteile:** speichert nur das, was tatsächlich angefordert wird. **Nachteile:** Cache-Fehler verursachen Latenz; Daten können veraltet sein.

### Durchlesen
Der Cache selbst verarbeitet Datenbanklesevorgänge bei einem Fehlschlag. Die Anwendung kommuniziert nur mit der Cache-Schicht, die die Datenquelle abstrahiert.

### Durchschreiben
Jeder Schreibvorgang erfolgt synchron sowohl in den Cache als auch in die Datenbank. Stellt sicher, dass der Cache immer konsistent ist, erhöht aber die Schreiblatenz.

### Write-Behind (Write-Back)
Schreibvorgänge werden sofort in den Cache verschoben. Der Cache wird stapelweise asynchron in die Datenbank geleert. Geringere Schreiblatenz, aber das Risiko eines Datenverlusts, wenn der Cache-Knoten vor dem Leeren abstürzt.

| Strategie | Konsistenz | Leselatenz | Schreiblatenz | Anwendungsfall |
|----------|-------------|-------------|---------------|----------|
| Cache-Aside | Eventuell | Fehlschussstrafe | N/A | Allzweck |
| Durchlesen | Eventuell | Fehlschussstrafe | N/A | Vereinfachte Lesarten |
| Durchschreiben | Stark | Schnell | Langsamer | Konsistenzkritisch |
| Write-Behind | Eventuell | Schnell | Schnell | Schreibintensive Arbeitslasten |

## Schritt 3 – Räumungsrichtlinien

Welche Einträge entfernen wir, wenn der Cache voll ist?

- **LRU (Least Recent Used)** – entfernt den Eintrag, auf den am längsten nicht zugegriffen wurde. Beste Allzweckpolice
- **LFU (Least Frequently Used)** – entfernt den Eintrag, auf den am seltensten zugegriffen wird. Besser für verzerrte Zugriffsmuster
- **TTL-basiert** – Einträge verfallen unabhängig vom Zugriff nach einer festgelegten Zeit. Unverzichtbar für die Aktualität der Daten
- **Zufällig** – überraschend effektiv und sehr einfach umzusetzen

<FunFact>Redis verwendet einen angenäherten LRU-Algorithmus, der eine kleine Anzahl von Schlüsseln abtastet (Standard: 5) und die zuletzt verwendeten davon entfernt. Dies ist fast so genau wie echtes LRU, erfordert jedoch keinen zusätzlichen Speicheraufwand für die Verfolgung der Zugriffsreihenfolge.</FunFact>

## Schritt 4 – Konsistentes Hashing für die Verteilung

### Das Problem mit einfachem Hashing
Bei `hash(key) % N`-Knoten werden durch das Hinzufügen oder Entfernen eines Knotens fast alle Schlüssel neu zugeordnet, was zu einem massiven Cache-Miss-Sturm führt.

### Konsistentes Hashing mit virtuellen Knoten
Konsistentes Hashing ordnet sowohl Schlüssel als auch Knoten einem Ring zu. Jeder Schlüssel wird dem nächsten Knoten im Uhrzeigersinn auf dem Ring zugewiesen:

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**Virtuelle Knoten** lösen das Problem der ungleichmäßigen Verteilung. Jeder physische Knoten erhält mehrere Positionen im Ring, sodass auch bei wenigen physischen Knoten eine gleichmäßige Auslastung gewährleistet ist.

Wenn ein Knoten hinzugefügt oder entfernt wird, werden nur die ihm benachbarten Schlüssel im Ring neu zugeordnet – ungefähr `K/N` Schlüssel (wobei K die Gesamtzahl der Schlüssel und N die Anzahl der Knoten ist), nicht alle.

## Schritt 5 – Verhinderung von Cache-Stampedes

Ein **Cache-Ansturm** tritt auf, wenn ein beliebter Cache-Eintrag abläuft und Hunderte von gleichzeitigen Anfragen gleichzeitig den Cache verpassen und die Datenbank erreichen.

### Lösungen

**Mutex/Sperrung:** Wenn ein Cache-Fehler auftritt, erwerben Sie eine verteilte Sperre. Es wird nur eine Anfrage aus der Datenbank abgerufen. andere warten darauf, dass der Cache neu gefüllt wird.

**Probabilistischer früher Ablauf:** Jede Anfrage hat eine kleine zufällige Chance, den Cache zu aktualisieren, bevor die TTL tatsächlich abläuft. Dies verteilt die Aktualisierungslast über die Zeit, anstatt bei Ablauf eine donnernde Herde zu erzeugen.

**Hintergrundaktualisierung:** Ein Hintergrundprozess aktualisiert beliebte Cache-Einträge, bevor sie ablaufen. Der Cache ist für Hotkeys nie leer.

## Schritt 6 – Redis-Cluster-Architektur

Redis Cluster ist der am weitesten verbreitete verteilte Cache:

- **16.384 Hash-Slots** verteilt auf Masterknoten
- Jede Taste wird über `CRC16(key) % 16384` einem Steckplatz zugeordnet.
- **Replikation:** Jeder Master verfügt über ein oder mehrere Replikate für das Failover
- **Automatisches Failover:** Wenn ein Master ausfällt, wird sein Replikat innerhalb von Sekunden hochgestuft

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### Überwachung wichtiger Kennzahlen
- **Trefferquote** – Ziel 95 %+; unter 80 % weist auf ein Caching-Problem hin
- **Speichernutzung** – bleiben Sie unter 80 %, um Räumungen zu vermeiden
- **Räumungsrate** – hohe Räumungen bedeuten, dass der Cache zu klein ist
– **Latenzperzentile** – p99 sollte für Cache-Treffer unter 1 ms liegen

## Schritt 7 – Reale Caching-Muster

| Muster | Umsetzung | TTL |
|---------|---------------|-----|
| Sitzungsspeicher | `SET session:{id} {data}` | 30 Minuten |
| API-Antwortcache | `SET api:/users/123 {json}` | 5 Minuten |
| Datenbankabfrage-Cache | `SET query:{hash} {result}` | 1 Minute |
| Ratenbegrenzerzähler | `INCR ratelimit:{user}:{window}` | Fensterdauer |
| Feature-Flags | `HSET features {flag} {value}` | 10 Sekunden |

### Cache-Ungültigkeitserklärung
Das schwierigste Problem in der Informatik (neben der Benennung von Dingen):
- **TTL-basiert** – einfach, toleriert Veraltung für die TTL-Dauer
- **Ereignisgesteuert** – Ungültigkeitsereignisse veröffentlichen, wenn sich Daten ändern (über Kafka oder Redis Pub/Sub)
- **Versionsbasiert** – eine Version in den Cache-Schlüssel aufnehmen; Erhöhen Sie die Version bei Schreibvorgängen, um alte Einträge effektiv ungültig zu machen
