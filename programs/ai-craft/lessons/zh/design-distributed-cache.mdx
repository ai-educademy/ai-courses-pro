# 从头开始​​设计分布式缓存 - Redis 架构

缓存是提高系统性能的最有效的技术。精心设计的分布式缓存可以将数据库负载减少 90% 以上，并将响应时间从数百毫秒缩短到亚毫秒。

## 步骤 1 - 需求收集

### 功能要求
- 使用可选的 TTL（生存时间）存储键值对
- 支持常用操作：GET、SET、DELETE、批量操作
- 将数据分布到多个节点以进行水平扩展

### 非功能性需求
- **低延迟** - 缓存命中的亚毫秒级读取
- **高吞吐量** - 每个节点每秒超过 100K 次操作
- **高可用性** - 缓存故障不应导致系统瘫痪
- **可扩展性** - 添加节点无需停机

### 何时缓存
- **读取繁重的工作负载** - 当读取数量远远超过写入数量时
- **昂贵的计算** - ML模型推理结果，复杂的聚合
- **经常访问的数据** - 用户会话、产品目录、配置

## 步骤 2 - 缓存策略

### 缓存旁路（延迟加载）
最常见的模式。应用程序首先检查缓存；如果失败，它会从数据库中读取，然后填充缓存：

```
GET user:123 → Cache HIT → return cached data
GET user:456 → Cache MISS → query DB → SET cache → return data
```

**优点：**仅缓存实际请求的内容。 **缺点：**缓存未命中会导致延迟；数据可能会变得陈旧。

### 通读
缓存本身会处理未命中的数据库读取。应用程序仅与缓存层对话，缓存层抽象了数据源。

### 直写式
每次写入都会同步写入缓存和数据库。确保缓存始终一致，但会增加写入延迟。

### 后写（回写）
写入立即进入缓存；缓存批量异步刷新到数据库。写入延迟较低，但如果缓存节点在刷新之前崩溃，则存在数据丢失的风险。

|战略|一致性|读取延迟 |写入延迟 |使用案例|
|----------|-------------|-------------|----------------|---------|
|缓存旁置|最终|错过点球|不适用 |通用|
|通读 |最终|错过点球|不适用 |简化阅读 |
|直写|强|快|慢一点 |一致性关键 |
|后写 |最终|快|快|写入繁重的工作负载 |

## 步骤 3 - 驱逐政策

当缓存已满时，我们要删除哪些条目？

- **LRU（最近最少使用）** - 逐出最长时间未访问的条目。最佳通用策略
- **LFU（最不常用）** - 逐出最不常访问的条目。更适合倾斜的访问模式
- **基于 TTL** - 条目在设定时间后过期，无论访问如何。对于数据新鲜度至关重要
- **随机** - 令人惊讶的有效且非常易于实施

<FunFact>Redis 使用近似 LRU 算法，对少量键（默认值：5）进行采样，并逐出其中最近最少使用的键。这几乎与真正的 LRU 一样准确，但跟踪访问顺序所需的额外内存开销为零。</FunFact>

## 步骤 4 - 用于分发的一致散列

### 简单哈希的问题
对于 `hash(key) % N` 节点，添加或删除节点会重新映射几乎所有键，从而导致大规模的缓存未命中风暴。

### 与虚拟节点的一致哈希
一致的散列将键和节点映射到环上。每个密钥都按顺时针方向分配给环上的下一个节点：

```
Hash Ring (0 to 2^32):
     Node A (3 virtual nodes: A1, A2, A3)
     Node B (3 virtual nodes: B1, B2, B3)
     Node C (3 virtual nodes: C1, C2, C3)

Key "user:123" → hash → lands between B2 and A1 → assigned to Node A
```

**虚拟节点**解决分布不均的问题。每个物理节点在环上有多个位置，即使物理节点较少也能保证负载均衡。

添加或删除节点时，仅重新映射环上与其相邻的键 - 大约 `K/N` 个键（其中 K 是键总数，N 是节点数），而不是全部。

## 步骤 5 - 缓存踩踏预防

当流行的缓存条目过期并且数百个并发请求同时错过缓存并命中数据库时，就会发生**缓存踩踏**。

### 解决方案

**互斥/锁定：** 当发生缓存未命中时，获取分布式锁。只有一个请求从数据库中获取；其他人等待缓存被重新填充。

**概率提前过期：** 每个请求在 TTL 实际过期之前都有很小的随机机会刷新缓存。这会随着时间的推移分散刷新负载，而不是在到期时产生雷鸣般的群体。

**后台刷新：** 后台进程会在流行的缓存条目过期之前对其进行刷新。对于热键来说，缓存永远不会是空的。

<ThinkAboutIt>考虑一次限时抢购，其中产品页面每秒收到 100,000 个请求。产品详细信息缓存条目已过期。如果没有踩踏预防，所有 100K 请求都会同时到达数据库。您会选择哪种预防策略，为什么？</ThinkAboutIt>

## 步骤 6 - Redis 集群架构

Redis Cluster是部署最广泛的分布式缓存：

- **16,384 个哈希槽**分布在主节点上
- 每个键通过 `CRC16(key) % 16384` 映射到一个插槽
- **复制：** 每个主节点都有一个或多个副本用于故障转移
- **自动故障转移：**如果主服务器发生故障，其副本将在几秒钟内升级

```
Slots 0-5460:     Master A ←→ Replica A'
Slots 5461-10922: Master B ←→ Replica B'
Slots 10923-16383: Master C ←→ Replica C'
```

### 监控关键指标
- **命中率** - 目标95%+；低于80%表示缓存有问题
- **内存使用率** - 保持在 80% 以下以避免被驱逐
- **逐出率** - 高逐出意味着缓存空间不足
- **延迟百分位数** - p99 的缓存命中率应低于 1 毫秒

## 步骤 7 - 现实世界的缓存模式

|图案|实施 | TTL |
|--------|----------------|-----|
|会话存储 | `SET session:{id} {data}` | 30 分钟 |
| API 响应缓存 | `SET api:/users/123 {json}` | 5 分钟 |
|数据库查询缓存| `SET query:{hash} {result}` | 1 分钟 |
|速率限制器计数器| `INCR ratelimit:{user}:{window}` |窗口持续时间|
|功能标志 | `HSET features {flag} {value}` | 10 秒 |

### 缓存失效
计算机科学中最难的问题（除了命名之外）：
- **基于 TTL** - 简单，可以容忍 TTL 持续时间内的陈旧性
- **事件驱动** - 当数据更改时发布失效事件（通过 Kafka 或 Redis Pub/Sub）
- **基于版本** - 在缓存键中包含版本；写入时增加版本以有效地使旧条目无效
