## 面试提示

*“设计一个聊天应用程序，如 WhatsApp 或 Slack，支持一对一消息传递、群聊和在线状态指示器。”*

这是系统设计面试中的最爱，因为它测试实时通信、连接管理、大规模存储和分布式系统权衡 - 所有这些都在一个问题中。

## 第 1 步：需求收集

**功能要求：**
- 一对一消息传递和已读回执
- 群聊（最多 500 名成员）
- 在线/离线状态指示器
- 消息历史记录和搜索
- 为离线用户推送通知

**非功能性要求：**
- 低延迟：消息在 200 毫秒内传送
- 高可用性：99.99% 正常运行时间
- 对话中保证消息排序
- 支持5000万并发连接

<Callout>始终用具体数字来量化您的非功能需求。 “快速交付”是模糊的 - “200 毫秒以下交付”表明您了解该领域。
</Callout>

## 第二步：API 设计

与纯 REST 系统不同，聊天需要**双向通信**。我们需要两个协议：

**REST API**（用于非实时操作）：
```
POST /api/users/login
GET  /api/conversations
GET  /api/conversations/:id/messages?before=timestamp&limit=50
POST /api/groups
```

**WebSocket**（用于实时消息传递）：
```
CONNECT  ws://chat.example.com/ws?token=jwt
SEND     { type: "message", to: "user_456", content: "Hello!" }
RECEIVE  { type: "message", from: "user_123", content: "Hello!", ts: 1706000000 }
SEND     { type: "ack", messageId: "msg_789", status: "read" }
```

## 步骤 3：WebSocket 连接管理

每个连接的用户都维护一个持久的 WebSocket 连接。对于 5000 万并发用户来说，这是一个重大的工程挑战。

**连接服务器**（有时称为网关服务器）保存 WebSocket 连接。每个服务器可以处理大约 50,000-100,000 个并发连接，这意味着我们需要 500-1,000 个连接服务器。

**连接注册表**（Redis 集群）将每个用户映射到其连接服务器：
```
user_123 → ws-server-042
user_456 → ws-server-187
```

当用户A向用户B发送消息时，流程为：
1.消息通过WebSocket到达A的连接服务器
2.服务器在Redis中查找B的连接服务器
3.消息通过内部消息路由到B的连接服务器
4. B的服务器将消息推送到B的WebSocket上

## 步骤4：消息存储

聊天应用程序会生成大量数据。 WhatsApp 每天处理超过 1000 亿条消息。

**存储策略：**
- **最近消息** - 保存在按对话 ID 分区的快速数据存储（Cassandra 或 HBase）中
- **消息索引** - 允许通过 Elasticsearch 进行搜索
- **媒体文件** - 通过 CDN 传输存储在对象存储 (S3) 中

**架构设计（Cassandra）：**
```
Table: messages
  partition_key: conversation_id
  clustering_key: message_timestamp (descending)
  columns: sender_id, content, type, status
```

这种设计确保对话中的所有消息都位于同一分区上，从而使“加载旧消息”查询极其高效 - 只需在一个分区内进行顺序读取即可。

## 步骤 5：状态系统

显示谁在线似乎很简单，但规模化却出人意料地棘手。您无法每隔几秒钟轮询一次数据库以查找联系人列表中的每个用户。

**心跳方法：**
1. 连接的客户端通过 WebSocket 每 30 秒发送一次心跳
2. 服务器更新一个 TTL 为 60 秒的 Redis key：`presence:user_123 → online (TTL 60s)`
3. 如果没有心跳到达，则密钥过期，用户显示离线

**状态更新的扇出：**
当用户上线时，必须将其状态推送给所有也在线的联系人。对于拥有 500 个联系人的用户，这意味着检查哪些联系人在线并仅向这些联系人发送状态更新 - **惰性扇出**避免向离线用户广播。

<FunFact>WhatsApp 的“最后上线”功能在全球范围内引发了意想不到的社交戏剧。一些国家的关系纠纷激增，因为合作伙伴可以看到彼此确切的最后活跃时间戳。 WhatsApp 最终添加了隐私控制来隐藏这些信息。
</FunFact>

## 步骤 6：推送通知

当用户离线（没有活动的 WebSocket）时，消息仍然必须通过推送通知到达他们。

消息流变化：
1.连接注册表显示用户B离线
2. 消息存储在数据库中，状态为“未发送”
3. 通知服务通过 APNs (iOS) 或 FCM (Android) 发送推送
4. 当用户B重新连接时，未发送的消息被获取并通过WebSocket发送
5. 发回送货收据以确认收货

<ThinkAboutIt>500 名成员的群聊提出了扇出挑战。如果向有 400 名成员离线的群组发送一条消息，则为 400 条推送通知。您将如何对这些内容进行批处理和速率限制，以避免在高峰时段出现过多的通知服务？
</ThinkAboutIt>

## 步骤 7：端到端加密基础知识

采访讨论中，简单提及端到端加密，可见安全意识：

- 每个用户在其设备上生成**公钥/私钥对**
- 消息在离开发件人的设备之前使用收件人的公钥进行加密
- 服务器只能看到密文 - 它无法读取消息内容
- 群组聊天使用**共享群组密钥**，该密钥在成员加入或离开时轮换

这意味着服务器的消息存储仅包含加密的 blob，从数据合规性的角度来看，这实际上更简单。

## 步骤 8：扩展到数百万

**关键扩展策略：**
- **连接服务器**水平扩展 - 随着用户的增长添加更多服务器
- **消息路由**使用Kafka或Redis Pub/Sub进行服务器间通信
- **数据库分片**通过对话ID分配存储负载
- **地理分布** - 在多个区域部署连接服务器以减少延迟
- **消息队列缓冲** - 在高峰使用时段吸收峰值

## 聊天系统设计的面试技巧

1. **从 WebSocket 决策开始** - 解释为什么 HTTP 轮询在这种规模下不起作用
2. **量化连接容量** - 表明您了解服务器限制（每台服务器约 50-100K 连接）
3. **解决离线交付** - 许多候选人忘记了用户并不总是处于连接状态
4. **提及消息排序** - 具有冲突解决功能的基于时间戳的排序

<ThinkAboutIt>Slack 和 WhatsApp 对消息历史记录采取截然不同的方法。 WhatsApp 将消息存储在设备上，并且不会将完整历史记录同步到新设备。 Slack 将所有内容存储在服务器端并提供完整的搜索。每种方法的隐私、成本和用户体验权衡是什么？
</ThinkAboutIt>

## 要点

- 聊天系统需要 WebSocket 进行实时双向通信
- 大规模连接管理需要一个将用户映射到服务器的注册表
- Cassandra 的写入吞吐量和基于分区的查询适合聊天消息存储
- 状态系统在 Redis 中使用基于 TTL 到期的心跳
- 推送通知处理离线消息传递
- 地理分布和水平扩展满足全球延迟要求
