## 面试提示

*“为电子商务平台设计一个推荐引擎，为 1 亿用户提供个性化产品建议。”*

这个问题测试您将**机器学习管道**与**可扩展系统设计**相结合的能力——这种组合在高层面试中越来越常见。

## 第 1 步：需求收集

**功能要求：**
- 首页个性化“为您推荐”（前20名产品）
- 产品页面上的“购买此商品的顾客也购买了”
- 基于区域活动的“您所在区域的趋势”
- 实时更新：建议在几分钟内反映最近的浏览情况

**非功能性要求：**
- 在 100 毫秒内提供建议（p99）
- 高峰时每秒处理 50,000 个请求
- 支持1亿用户和1000万种产品
- 优雅降级：如果个性化失败，则显示热门项目

<Callout>始终定义后备策略。面试官喜欢听到“如果 ML 模型失败，我们会优雅地降级为基于受欢迎程度的推荐”——这显示了生产思维。
</Callout>

## 步骤 2：推荐方法

大多数推荐系统都采用三种核心技术：

**协同过滤** - “与您相似的用户喜欢这些项目”
- 分析用户-项目交互矩阵（查看、购买、评分）
- 使用矩阵分解查找相似的用户或相似的项目
- 交互数据充足时效果良好

**基于内容的过滤** - “因为您喜欢具有这些功能的项目”
- 使用产品属性（类别、品牌、价格范围、描述）
- 使用变压器模型从产品描述生成嵌入
- 计算嵌入空间中项目之间的相似度

**混合方法** - 结合两种信号以获得更强有力的建议
- 大多数制作系统使用混合信号：用于个性化的协作信号、用于多样性的内容信号和冷启动覆盖

## 步骤 3：推荐管道

生产推荐系统通常使用**两阶段架构**：

**第 1 阶段 - 候选生成（离线/近实时）**
- 将 1000 万个产品缩小至每个用户约 1,000 个候选产品
- 使用轻量级模型：协同过滤、嵌入相似性
- 作为批处理作业（每小时/每天）运行或通过流式传输近实时运行

**第二阶段 - 排名（实时）**
- 使用更丰富的模型对约 1,000 名候选人进行评分
- 考虑上下文：一天中的时间、设备、最近的活动、购物车内容
- 返回排名前 20 的项目
- 必须在 100 毫秒延迟预算内执行

## 步骤 4：数据模型和特征存储

建议取决于从多个数据源计算出的丰富特征：

**用户特征：**购买历史记录、浏览模式、人口统计细分、最喜欢的类别
**项目特征：**类别、价格、评级、描述嵌入、销售速度
**互动特征：**点击率、观看时间、添加到购物车率

**功能商店**（例如 Feast、Tecton）提供：
- **离线功能** - 用于模型训练的预先计算的批处理功能
- **在线特征** - 低延迟特征检索以实现实时排名
- **一致性** - 训练和服务中使用相同的特征定义

```
Feature Store Schema:
  user_features:    { user_id → [purchase_vector, category_prefs, avg_price, ...] }
  item_features:    { item_id → [embedding, category, price, popularity_score, ...] }
  interaction_features: { (user_id, item_id) → [clicks, views, last_interaction, ...] }
```

<FunFact>Netflix 估计，其推荐系统通过减少用户流失，每年为公司节省 10 亿美元。收到相关建议的用户取消订阅的可能性明显降低。
</FunFact>

## 步骤 5：实时推荐与批量推荐

|方面|批量|实时|
|--------|--------|------------|
|新鲜度|几小时前 |秒老|
|计算成本|较低（预定工作）|更高（每个请求推断）|
|复杂性 |更简单的管道 |需要流媒体基础设施 |
|使用案例 |主页“为你”| “因为你刚刚看了X” |

**实用的混合方法：**
- 每隔几个小时批量预先计算候选人名单
- 使用最新的会话上下文实时重新排名
- 当事件发生时，使用流媒体（Kafka）近乎实时地更新用户特征

<ThinkAboutIt>当您在亚马逊上浏览产品时，推荐几乎会立即更新。但训练协同过滤模型需要几个小时。您认为亚马逊如何弥合批量模型训练和实时个性化之间的差距？
</ThinkAboutIt>

## 步骤 6：A/B 测试框架

推荐系统需要严格的实验：

- **流量分割** - 将一定比例的用户路由到新模型
- **指标** - 点击率 (CTR)、转化率、每次会话收入、多样性
- **统计显着性** - 运行足够长的测试以得出可靠的结论
- **Guardrail 指标** - 确保新模型不会降低整体收入或参与度

典型的设置使用**功能标志服务**来一致地将用户分配到实验存储桶（同一用户在测试期间始终看到相同的变体）。

## 步骤 7：冷启动解决方案

新用户和新项目都会出现冷启动问题：

**新用户：**
- 最初显示基于受欢迎程度的推荐
- 询问入职问题（“选择您感兴趣的类别”）
- 使用人口统计或地理信号作为初始特征
- 5-10次互动后过渡到个性化推荐

**新商品：**
- 使用基于内容的特征（描述、类别、价格）将项目放置在嵌入空间中
- 在专门的“新品”部分增加新商品
- 运行探索/利用策略（向用户子集显示新项目以收集交互数据）

## 步骤 8：扩展系统

**每秒 50K 请求的架构：**
- **API网关** - 速率限制、身份验证、请求路由
- **推荐服务** - 无状态，在负载均衡器后面水平扩展
- **特征存储** - 用于低延迟特征检索的 Redis 集群
- **模型服务** - 内存中预加载的模型（TensorFlow Serving、Triton）
- **预先计算的缓存** - 每个用户的热门推荐的 Redis 缓存，由批处理作业刷新
- **后备** - 如果缓存未命中且模型超时，则返回基于流行度的默认值

<FunFact>Spotify 的 Discover Weekly 播放列表每周一由批量推荐管道生成，该管道分析超过 1 亿用户的收听习惯。该功能非常成功，成为用户发现新音乐的主要方式。
</FunFact>

<ThinkAboutIt>推荐引擎可以创建“过滤气泡”，用户只能看到与他们已经消费过的商品相似的商品。您将如何设计一个平衡个性化与多样性和偶然性的推荐系统？
</ThinkAboutIt>

## 要点

- 使用两阶段架构：候选生成（广泛）→排名（精确）
- 混合方法（协作+基于内容）优于单一方法系统
- 特征存储确保模型训练和实时服务之间的一致性
- A/B 测试至关重要 - 针对业务指标进行优化，而不仅仅是 ML 指标
- 冷启动策略可防止新用户和项目出现不良体验
- 积极缓存并优雅降级以处理峰值流量
