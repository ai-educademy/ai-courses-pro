## 面试提示

*“设计一个 AI API 平台，通过 REST API 为开发人员提供多种机器学习模型 - 类似于 OpenAI 或 Hugging Face 大规模服务模型的方式。”*

这个问题在采访中越来越受欢迎，因为它结合了 AI 工作负载特有的 **API 平台设计** 和 **GPU 基础设施挑战**。

## 第 1 步：需求收集

**功能要求：**
- 通过 REST API 服务多个 AI 模型（文本生成、图像分类、嵌入）
- API 密钥身份验证以及每个密钥的使用配额
- 每次 API 调用的使用情况跟踪和计费
- 支持多个模型版本并进行A/B测试
- 长时间运行的生成任务的流响应

**非功能性要求：**
- 延迟：嵌入模型的 p50 低于 500 毫秒，生成模型的 p50 低于 2 秒
- 吞吐量：所有模型每秒 10,000 个请求
- 可用性：正常运行时间为 99.9%，降级正常
- 成本效率：GPU 很昂贵 - 最大化利用率

<Callout>人工智能平台具有独特的可变延迟。文本完成请求可能需要 200 毫秒或 30 秒，具体取决于输出长度。始终讨论您的设计如何处理这种差异。
</Callout>

## 第二步：API 设计

```
POST /v1/completions
Headers: Authorization: Bearer sk-abc123
Body: { "model": "gpt-4", "prompt": "Explain caching", "max_tokens": 200 }

POST /v1/embeddings
Headers: Authorization: Bearer sk-abc123
Body: { "model": "text-embedding-3", "input": "Hello world" }

GET  /v1/models                    - list available models
GET  /v1/usage?start=2024-01-01    - usage and billing data

SSE: POST /v1/completions (stream: true)
     → returns Server-Sent Events with incremental tokens
```

通过**服务器发送事件 (SSE)** 进行流式传输对于生成模型至关重要 - 用户会看到令牌逐渐出现，而不是等待完整响应。

## 步骤 3：API 网关和身份验证

API网关是平台的前门：

- **身份验证** - 根据密钥存储验证 API 密钥（Redis 提高速度，数据库提高持久性）
- **速率限制** - 强制执行每个键的限制（例如，免费套餐每分钟 60 个请求）
- **请求路由** - 将请求定向到正确的模型服务集群
- **请求验证** - 检查有效负载架构、模型可用性、令牌限制

**速率限制实施：**
在 Redis 中使用**滑动窗口计数器**：
```
Key:   rate:{api_key}:{window_minute}
Value: request count
TTL:   120 seconds
```

每个请求都会增加计数器。如果超出限制，则返回 HTTP 429。

<Quiz question="客户的 API 密钥的速率限制为每分钟 100 个请求。他们在前 30 秒内发送 80 个请求，然后在接下来的 30 秒内发送 40 个请求。在固定窗口方法下，会发生什么？" options="所有 120 个请求均成功 - 它们在每分钟限制之内|最后 20 个请求被拒绝 - 超过每分钟 100 个|第一个窗口中 120 个请求全部成功，但下一分钟的配额减少|系统因容量超限而崩溃" answer="1" explanation="固定窗口速率限制在分钟边界重置。如果 80 个请求在第 1 分钟的后半部分到达，40 个请求在第 2 分钟的前半部分到达，则所有请求都会成功 - 即使有 120 个请求在 60 秒内到达。这就是为什么滑动窗口算法是首选的。" />

## 步骤 4：模型服务和 GPU 分配

这就是人工智能平台与传统网络服务的根本区别。 GPU 稀缺、昂贵，并且需要专门的编排。

**模型服务层：**
- 使用 **Triton Inference Server** 或 **vLLM** 等框架将模型加载到 GPU 内存中
- 每个模型版本都在专用的 GPU 实例池上运行
- 大型语言模型 (LLM) 可能需要跨多个 GPU 的**模型并行性**

**请求批处理：**
单独的推理请求在 GPU 上效率很低。 **动态批处理** 将多个请求分组并一起处理：
- 收集请求最多 10ms 或直到批次达到 32 个请求
- 在一次 GPU 前向传递中处理整个批次
- 向每个呼叫者返回单独的回复

与单独处理请求相比，这可以将吞吐量提高 5-10 倍。

<FunFact>单个 NVIDIA H100 GPU 的成本约为 25,000 英镑，功耗为 700 瓦。运行一个由 1,000 个 GPU 组成的集群来提供模型服务，每月仅电力和硬件成本就超过 200 万英镑 - 这就是为什么高效批处理和利用率非常重要的原因。
</FunFact>

## 步骤 5：模型版本之间的 A/B 测试

部署新模型版本时，您需要受控部署：

- **流量分割** - 将 5% 的请求路由到新模型，95% 路由到当前模型
- **影子模式** - 在生产流量上运行新模型，而不将其结果返回给用户
- **指标比较** - 延迟、输出质量分数、错误率、每个请求的成本
- **逐步推出** - 随着信心的增长增加新版本的流量

路由逻辑位于 API 网关中：
```
model: "gpt-4"  →  95% → gpt-4-v2.1 (current)
                →   5% → gpt-4-v2.2 (candidate)
```

<ThinkAboutIt>评估新的法学硕士版本是否“更好”出奇地困难——与分类模型不同，没有简单的准确性指标。您将如何为生成式人工智能模型设计自动化质量评估系统？
</ThinkAboutIt>

## 步骤 6：使用情况跟踪和计费

AI API 通常按令牌计费（LLM 的输入 + 输出令牌，其他模型的每个请求）。

**事件驱动的计费管道：**
1. 每个 API 响应都包含一个使用标头：`x-usage-tokens: 847`
2. 计费事件发布到Kafka：`{ api_key, model, input_tokens, output_tokens, timestamp }`
3. 计费聚合服务使用事件并更新运行总计
4. 使用情况仪表板从时间序列数据库中查询聚合数据

**为什么选择 Kafka？** 计费必须可靠，但不需要同步。如果计费服务暂时关闭，事件会在 Kafka 中排队并在其恢复时进行处理 - 不会丢失使用数据。

<Quiz question="您的计费管道通过 Kafka 异步处理使用事件。客户检查他们的使用情况仪表板，发现数字低于预期。最可能的原因是什么？" options="由于 Kafka 分区故障，事件丢失|聚合服务存在处理延迟 - 事件尚未被消耗|API网关未能发出使用事件|客户的 API 密钥受到速率限制" answer="1" explanation="异步管道本质上存在滞后。发布到 Kafka 的事件可能需要几秒钟或几分钟的时间才能被消耗和聚合，因此仪表板显示的使用情况视图略有延迟。" />

## 步骤 7：监控和可观察性

AI 平台需要超出标准 Web 服务的监控：

|公制|为什么这很重要？
|--------|----------------|
|推理延迟（p50、p95、p99）|用户体验和 SLA 合规性 |
| GPU 利用率 |成本效率 - 闲置 GPU 浪费金钱
|每秒令牌数 |吞吐量和缩放信号|
|按模型划分的错误率 |检测特定型号的故障 |
|队列深度 |扩展触发器 - 深队列意味着需求超过容量 |
|输出质量分数 |检测模型退化（通过自动评估）|

**警报阈值：** GPU 利用率低于 40% 会触发缩减；队列深度超过 100 会触发纵向扩展。

## 步骤 8：自动缩放

人工智能工作负载的需求变化很大。自动扩展必须平衡响应能力和成本：

- **水平扩展** - 当队列深度或延迟超过阈值时添加更多 GPU 实例
- **预测扩展** - 使用历史流量模式在预期峰值之前预先配置容量
- **缩放到零** - 对于很少使用的模型，关闭所有实例并按需冷启动
- **温池** - 保留少量预加载模型的实例，以避免冷启动延迟

缩放至零策略对于托管数百个模型的平台尤其重要 - 您无法始终将每个模型加载到 GPU 内存中。

<Quiz question="目前，每小时接收 2 个请求的模型在一个始终在线的 GPU 实例上运行，成本为 3 英镑/小时。从零冷启动需要 45 秒。最好的扩展策略是什么？" options="保持实例始终开启 - 45 秒等待时间太长|缩放至零并接受第一个请求的 45 秒冷启动|使用一个 CPU 实例的热池，按需卸载到 GPU|将 2 个请求批处理到单个计划作业中" answer="1" explanation="如果每小时 2 个请求，GPU 99.9% 的时间都处于空闲状态。扩展到零并接受 45 秒冷启动，每个模型每月可节省近 2,100 英镑 - 对于低流量模型来说，偶尔的延迟是值得的。" />

<ThinkAboutIt>OpenAI 的平台提供从快速嵌入模型到慢速推理模型的各种模型。每个都有不同的延迟特性、GPU 要求和定价。您将如何设计路由层，以便在具有如此不同配置文件的模型之间有效共享有限的 GPU 集群？
</ThinkAboutIt>

<FunFact>据报道，OpenAI 每天处理超过 1 亿个 API 请求。按估计平均每个请求 500 个令牌，即每天 500 亿个令牌 - 需要数千个 GPU 持续运行。
</FunFact>

## 要点

- AI API 平台将传统 API 设计与 GPU 特定基础设施挑战相结合
- 请求批处理显着提高了 GPU 吞吐量和成本效率
- 速率限制可以保护平台和客户免受成本失控的影响
- 通过 Kafka 进行异步计费，确保可靠的使用情况跟踪，而不会阻塞请求
- 自动缩放必须平衡响应能力与成本 - 对于低流量模型缩放至零
- 监控 GPU 利用率和队列深度可推动智能扩展决策
