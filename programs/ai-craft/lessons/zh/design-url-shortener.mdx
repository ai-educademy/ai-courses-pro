## 面试提示

*“设计一个像 bit.ly 这样的 URL 缩短服务，它需要长 URL 并生成简短、独特的代码。”*

这是最常见的第一个系统设计问题，因为它看似简单，但却涵盖了核心概念：API 设计、编码策略、数据库选择、缓存和扩展。让我们使用第 1 课中的结构化框架来完成它。

## 步骤 1：需求收集（5 分钟）

**功能要求：**
- 给定一个长 URL，生成一个简短的唯一 URL
- 通过短 URL 重定向返回原始长 URL
- 用户可以选择设置自定义短代码
- 链接在可配置的期限后过期（默认：5 年）
- 基本分析：点击次数、推荐来源、地理位置

**非功能性要求：**
- 每月生成 1 亿个 URL（每秒约 40 个）
- 读重：100:1 读写比 → 每秒 4,000 次重定向
- URL 重定向延迟低于 50 毫秒
- 短网址应尽可能短
- 高可用性 - 断开的链接会带来糟糕的用户体验

<Callout>通过提出澄清问题来开始每次系统设计面试。写下明确的数字（40 次写入/秒，4,000 次读取/秒）表明您可以对规模进行定量推理。
</Callout>

## 步骤 2：API 设计（5 分钟）

```
POST /api/shorten
Body: { "url": "https://example.com/very/long/path", "custom_code": "mylink", "expires_in": "30d" }
Response: { "short_url": "https://sho.rt/aB3kx9", "expires_at": "2025-02-15T00:00:00Z" }

GET /:code
Response: HTTP 301 Redirect → Location: https://example.com/very/long/path

GET /api/analytics/:code
Response: { "clicks": 14523, "created_at": "...", "top_referrers": [...] }
```

**为什么选择 HTTP 301 与 302？**
- **301（永久重定向）** - 浏览器缓存它，减少我们服务器上的负载
- **302（临时重定向）** - 浏览器始终访问我们的服务器，从而实现准确的分析

对于跟踪点击的服务，**302 通常是更好的选择**，因为每个重定向都会经过我们的服务器。

## 第三步：编码策略

核心挑战：我们如何生成简短、独特的代码？

**Base62 编码** 使用 `[a-zA-Z0-9]` - 62 个字符。 7 个字符的代码为我们提供了 62⁷ = **3.5 万亿** 独特的组合，对于我们的规模来说绰绰有余。

**选项 A - 基于计数器：**
- 使用自动递增计数器（1、2、3、...）并转换为 base62
- 柜台 1000 → `g8` |计数器 1000000 → `4c92`
- **优点：**保证独特、简单、无冲突
- **缺点：** 可预测（用户可以猜测下一个 URL），需要一个集中计数器

**选项 B - 基于哈希：**
- 使用MD5/SHA-256对长URL进行哈希处理，取base62的前7个字符
- **优点：**无状态，无需中央协调
- **缺点：**可能发生冲突 - 必须检查数据库并重试

**选项 C - 预生成密钥（推荐）：**
- 后台服务预先生成数百万个唯一的base62代码并将它们存储在密钥池中
- 当新的 URL 到达时，从池中获取下一个可用的代码
- **优点：**快速、无碰撞风险、不可预测
- **缺点：**需要管理密钥生成服务

<FunFact>最初的 TinyURL 服务于 2002 年推出，至今仍在运行。它曾经一度每天生成超过 100 万个短 URL。域名本身——tinyurl.com——已经变得如此具有标志性，以至于“tinyurl”被用作 URL 缩短的通用术语。
</FunFact>

## 步骤 4：数据库选择和架构

每月新增 1 亿个 URL，保留 5 年，我们将存储大约 **60 亿条记录**。这是一个具有简单键值查找的读取密集型工作负载。

**数据库选择：DynamoDB 或 Cassandra**
- 查找始终通过短代码（分区键）进行 - 不需要复杂的连接
- 两者都可以通过水平扩展处理大量读取吞吐量
- 两者都提供按分区键进行不到 10 毫秒的查找

**架构：**
```
Table: urls
  short_code (partition key): "aB3kx9"
  long_url: "https://example.com/very/long/path"
  user_id: "user_123"
  created_at: 1706000000
  expires_at: 1863000000
  click_count: 14523
```

对于分析，单独的时间序列表存储各个点击事件：
```
Table: clicks
  short_code (partition key): "aB3kx9"
  timestamp (sort key): 1706000001
  referrer: "twitter.com"
  country: "GB"
  device: "mobile"
```

## 步骤 5：缓存策略

在每秒 4,000 次读取和重尾分布（某些 URL 获得数百万次点击，大多数点击很少）的情况下，缓存至关重要。

**Redis缓存**存储最常访问的映射：
```
Key:   url:aB3kx9
Value: "https://example.com/very/long/path"
TTL:   24 hours
```

**缓存命中流（快速路径）：**
1. 请求到达：`GET /aB3kx9`
2.检查Redis→缓存命中→返回302重定向
3.将点击事件异步记录到Kafka

**缓存未命中流：**
1.检查Redis→错过
2.查询数据库→找到
3.填充Redis缓存
4.返回302重定向

缓存命中率为 80% 时，每秒 4,000 个请求中只有 800 个实际到达数据库。

## 步骤 6：分析和点击跟踪

点击跟踪不得减慢重定向速度。在异步处理分析时，重定向响应应立即返回。

**架构：**
1.重定向处理程序将点击事件发布到**Kafka**
2. 点击处理服务使用事件并且：
   - 增加 URL 记录中的 `click_count`
   - 将详细的点击数据写入点击表
   - 通过流聚合更新实时仪表板

这种解耦确保缓慢的分析管道不会影响重定向延迟。

<ThinkAboutIt>URL 缩短器有时用于伪装恶意链接。如果您正在设计 bit.ly，您将如何实施安全检查来扫描目标 URL 是否存在网络钓鱼或恶意软件，而不会给缩短过程增加明显的延迟？
</ThinkAboutIt>

## 步骤 7：扩展系统

**水平扩展方法：**
- **API 服务器** 是无状态的 - 通过在负载均衡器后面添加实例来扩展
- **密钥生成服务** 作为单独的微服务运行，拥有自己的预生成代码数据库
- **Redis 集群** 使用一致性哈希处理跨节点的缓存分配
- **数据库分片**通过短代码的第一个字符均匀分布数据

**处理峰值负载：**
- 在病毒式传播事件期间，单个 URL 每分钟可能会收到数百万次点击
- Redis 缓存自然地吸收了这一点 - 一个缓存条目可提供无限的读取
- Kafka 缓冲点击事件，平滑分析数据库上的写入负载

<Quiz question="一个 URL 病毒式传播，每分钟获得 500,000 次点击。哪个组件最有可能不受影响？" options="Redis 缓存（单个密钥服务所有请求）|Kafka 点击事件消费者|分析数据库写入路径|API服务器CPU" answer="0" explanation="Redis 每秒可以毫不费力地处理单个缓存键的数百万次读取。 Kafka 消费者和分析数据库面临 50 万次写入/分钟，API 服务器处理 50 万次请求/分钟 - 所有这些都在巨大的负载下进行。" />

<ThinkAboutIt>像 bit.ly 这样的公司每月处理数十亿次重定向。如果在广告牌或电视广告上共享短网址，流量可能会在几秒钟内从零激增至数百万。除了缓存之外，您还会使用哪些其他策略来吸收这些突然的、不可预测的流量爆发？
</ThinkAboutIt>

<FunFact>2009 年，bit.ly 每天处理超过 8000 万次点击。当利比亚（其国家代码为 .ly）因政治不稳定而短暂关闭 .ly 域名时，数以百万计的缩短链接暂时停止工作，引起了互联网上的恐慌。
</FunFact>

## 要点

- 遵循框架：需求→API→编码→数据模型→架构→深入研究
- 7 个字符的 Base62 产生 3.5 万亿个唯一代码 - 绰绰有余
- 预先生成的密钥池避免冲突问题和中央柜台瓶颈
- 当您需要准确的点击分析时，使用 302 重定向（而不是 301）
- Redis 缓存可显着减少读取繁重工作负载的数据库负载
- 使用 Kafka 进行异步处理，将分析与重定向路径分离
