# 设计一个视频流平台 - YouTube/Netflix 架构

视频流占全球互联网流量的 65% 以上。该系统的设计涵盖了文件处理管道、CDN 架构和自适应流媒体——这些概念的应用远远超出了视频范围。

## 步骤 1 - 需求收集

### 功能要求
- 上传视频（每个文件最大 1 GB）
- 根据网络条件以自适应质量传输视频
- 按标题、描述和标签搜索视频
- 跟踪观看次数和参与度指标

### 非功能性需求
- **可用性** - 99.99% 的流媒体正常运行时间
- **低延迟** - 视频播放在 2 秒内开始
- **全球影响力** - 高效服务各大洲的用户
- **成本效益** - 优化存储和带宽（两个最大的成本）

## 步骤 2 - 高级架构

```
Upload Flow:
Client → Upload Service → Object Storage (raw)
                              ↓
                    Transcoding Pipeline (async)
                         ↓          ↓
                   Multiple      Thumbnail
                   Qualities     Generator
                         ↓          ↓
                    CDN Origin Storage → CDN Edge Servers

Streaming Flow:
Client → CDN Edge → (cache miss) → CDN Origin → Object Storage
```

## 步骤 3 - 视频上传管道

### 逐步处理
1. **上传** - 客户端通过预签名 URL 将原始视频上传到对象存储（例如 S3），并可恢复大文件上传
2. **转码** - 将源视频转换为多种分辨率（1080p、720p、480p、360p）和编解码器（H.264、VP9、AV1）
3. **自适应比特率打包** - 将每个质量级别分成小段（2-10 秒）以进行 HLS/DASH 流式传输
4. **缩略图生成** - 定期提取帧以预览缩略图
5. **元数据更新** - 所有处理完成后，将视频在数据库中标记为“就绪”

### 大规模转码
一个 10 分钟的 4K 视频在一台机器上转码可能需要 30 多分钟。要处理数千个并发上传：
- 使用基于 DAG 的工作流程（如 AWS Step Functions）将视频分割成块并并行转码
- 使用现货/抢占式实例将计算成本降低 60-80%

## 步骤 4 - 流媒体协议和 CDN

### 自适应比特率流媒体
播放器根据观看者的网络速度自动切换质量：

|协议|使用者 |段格式|清单 |
|----------|---------|----------------|----------|
| HLS | Apple，大多数浏览器| .ts 或 .fmp4 | .m3u8 播放列表 |
|达世币 | YouTube、Netflix | .mp4 片段 | .mpd 清单 |

客户端下载列出所有可用质量级别的清单文件，然后每次请求一个片段，随着带宽变化无缝切换质量。

### CDN架构
CDN 是流媒体性能最关键的组件：

```
User in London → London Edge PoP (cache hit: 95%)
                     ↓ (cache miss)
              European Regional Cache
                     ↓ (cache miss)
              Origin Storage (S3)
```

**关键见解：** 热门视频缓存在最靠近用户的边缘位置。长尾内容可能仅缓存在区域节点上，并通过源获取稀有内容。

<FunFact>Netflix 每周提供超过 7 亿小时的视频。他们的 Open Connect CDN 将定制硬件设备直接放置在 ISP 数据中心内，在最后一英里缓存流行内容，从而减少 90% 以上的互联网骨干流量。</FunFact>

## 步骤 5 - 支持服务

### 视频元数据服务
存储标题、描述、标签、上传日期、查看次数和处理状态。使用关系数据库 (PostgreSQL) 进行结构化查询和搜索索引。

### 查看大规模计数
简单的方法（在每个视图上增量）创建一个写入热点。相反：
- 批量查看事件到流中（Kafka）
- 定期聚合计数（每 30 秒）
- 使用近似计数进行实时显示，使用精确计数进行分析

### 直播架构
直播与点播的主要区别在于：
- **无预转码** - 视频必须实时转码
- **超低延迟** - 观众期望不到 5 秒的延迟
- **摄取协议** - 流媒体通过 RTMP 推送；观众通过具有低延迟扩展的 HLS/DASH 接收

## 步骤 6 - 成本细分和优化

视频平台的运营**极其昂贵**。三大成本：

|成本中心|估计（每日 1000 万用户）|优化|
|------------|----------------------------|--------------|
|存储| 〜20 万美元/月 |分层存储（热/温/冷），删除失败上传 |
| CDN 带宽 | 〜50 万美元/月 |边缘缓存，使用现代编解码器压缩 (AV1) |
|转码计算 | ~10 万美元/月 |发现实例，跳过很少观看的质量级别 |

<ThinkAboutIt>Netflix 每年在内容交付上花费数十亿美元。如果您从头开始设计他们的系统，您会构建自己的 CDN（如 Netflix Open Connect）还是使用商业 CDN（如 CloudFront）？自己建造什么规模才具有成本效益？</ThinkAboutIt>

### 内容保护 (DRM)
优质内容需要数字版权管理：
- **Widevine** (Google) - Chrome、Android
- **FairPlay** (Apple) - Safari、iOS
- **PlayReady** (微软) - Edge、Windows

每个 DRM 系统都需要单独的加密和许可证服务器集成，从而显着增加了复杂性。

<ThinkAboutIt>YouTube 存储了超过 8 亿个视频。如果每个视频转码为 5 个质量级别，每个级别平均为 500 MB，请估计所需的总存储空间。您将如何设计经济高效的存储策略？</ThinkAboutIt>
